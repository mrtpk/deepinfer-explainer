Two engines vote, each driver feeds its CP follower, the ranks share keys and experts, and the drivers sample.

The idea

The tour {{link tours/engine-step}} followed one step on one device. This tour runs the same kind of step on four devices, and watches the communication. At each stop you see which {{term rank | ranks}} work, which group talks, and the shapes of the data.

The set-up. python examples/offline_inference.py --ep 4 --cp 2 on one host with 4 GPUs. The script computes dp_size = max(4 // 2, 1) = 2 and a world of 4 ranks ({{cite examples/offline_inference.py:24-28}}). So there are two engines (two {{term data-parallelism | DP}} replicas), and each engine has two {{term context-parallelism | CP}} ranks:

RankEnginecp_rankProcessDevice

Rank = engine_rank × 2 + cp_rank ({{cite deepinfer/worker/base.py:329}}). The groups are: CP [0, 1] and [2, 3]; DP [0, 2] and [1, 3]; EP [0, 1, 2, 3]. The EP group is the world group, because ep_size equals the rank count ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:91-106}}).

The work. Engine 0 has one new request A with 8 prompt tokens. Engine 1 has no waiting request. The scheduler counter is at decode_step = 100, an ANY point. ZOS is on (the default). H is the hidden size of the checkpoint; the repository does not fix it.

The picture

Read panel 2 from top to bottom. Amber cards talk inside one engine (CP). Violet cards talk across both engines (EP). The green card is the only stop where the two drivers talk to each other directly.

We are in Scheduler::_schedule (C++), called from LLMEngine.step() on ranks 0 and 2. Only the engine processes run a scheduler; ranks 1 and 3 wait in their worker loop.

decode_step = 100, so this is an ANY point. Engine 0 wants a prefill (A is schedulable and the cache has room) and sends 0. Engine 1 sends 1. MIN(0, 1) = 0: both engines prefill. With ZOS, the vote uses the Gloo copy of the DP group [0, 2] and a CPU tensor ({{cite deepinfer/engine/llm_engine.py:313}}, {{cite csrc/engine/scheduler.hpp:170-182}}).

Before this call of step(), LLM._run_engine asked has_unfinished_requests(). Engine 0 sent 1 and engine 1 sent 0; the MAX is 1, so both engines call step() ({{cite deepinfer/engine/llm_engine.py:673-678}}).

After vote 1, engine 0 runs _schedule_prefill and gets a batch. Vote 2 then asks whether any engine got a batch: engine 0 sends 0, engine 1 sends 1, MIN = 0. Engine 1 returns an empty prompt step ({{cite csrc/engine/scheduler.hpp:332-340}}). The page {{link concepts/dp-step-votes}} explains the encodings.

Still in LLMEngine.step(). Engine 0 now has one {{term sequence-metadata}} for A, with seqlen_q = 8. The scheduler pads the CP work in its token budget to a multiple of 2 × cp = 4; 8 is already a multiple ({{cite csrc/engine/scheduler.hpp:515}}). Engine 1 has no sequence. The engine hands both cases to the worker in the same way:

On engine 1, is_placeholder is true. Its worker runs the model on one dummy sequence with one token ({{cite deepinfer/worker/worker.py:125-127}}, {{cite deepinfer/worker/model_runner.py:386-403}}).

# engine 0 (rank 0)                       # engine 1 (rank 2)
seq_metadata_list = [A]                     seq_metadata_list = []  # worker uses [placeholder]
is_prompt, is_placeholder = True, False     is_prompt, is_placeholder = True, True
A.seqlen_q = 8, A.seqlen_k = 8              placeholder: seqlen_q = 1, block_table = [0]

Both engines will run a prompt step. That is the point of the vote: the ranks of both engines must call the same collectives in the stops that follow.

We are in WorkerBase.run_workers on ranks 0 and 2. Before the driver runs execute_model_step itself, it sends the method name and the keyword arguments to its CP follower:

On ranks 1 and 3, the follower loop gets the tuple and calls the same method ({{cite deepinfer/worker/base.py:129-133}}). The channel is the {{term shm-message-queue | MessageQueue}} of the CP group: a ring buffer in {{term posix-shm | shared memory}}, written by CP rank 0 ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:17-23}}).

The follower gets ("execute_model_step", {"is_prompt": True, "is_placeholder": False}) on rank 1, and the same with is_placeholder = True on rank 3. The driver_kwargs (the sequence list and the scheduler outputs) stay on the driver ({{cite deepinfer/engine/llm_engine.py:965-973}}). So in execute_model_step, a follower has seq_metadata_list = None, and it skips the ZOS correction, which only the driver does ({{cite deepinfer/worker/worker.py:116-118}}).

The pickled tuple is a few tens of bytes, far below the 1 MiB chunk size of the queue ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:124}}). The page {{link code/shm-broadcast}} explains the queue.

We are in ModelRunner._prepare_input. The driver builds the {{term input-metadata}} of its batch in C++, moves it to the device, and broadcasts it in the CP group. The follower receives it:

broadcast_tensor_dict sends a list of keys, small values and (dtype, size) pairs through the shared-memory queue. Then it sends each tensor with a device broadcast from CP rank 0 ({{cite deepinfer/model_executor/parallel_utils/communication_op.py:51-82}}).

FieldValue on rank 0 and, after the broadcast, on rank 1

On engine 1, the placeholder has total_q = 1 and cp_mirror_len = 2 × ⌈1 / 4⌉ = 2. A second, smaller broadcast follows in stop 9, for the sampler inputs ({{cite deepinfer/worker/model_runner.py:250-275}}).

The broadcast is CP-only: ranks 0 and 1 talk, and ranks 2 and 3 talk. Each CP group has its own queue and its own NCCL group.

We are in DeepseekModel.forward, on all four ranks. Each rank embeds all tokens, computes the {{term cp-mirror | mirror}} indices, and keeps only its own rows:

A has 8 tokens and cp = 2, so it has 4 parts of 2 tokens. Rank 0 takes parts 0 and 3; rank 1 takes parts 1 and 2:

Rankmirror_cp_indexHidden states after the gather
0[0, 1, 6, 7][4, H]

2 (placeholder)[0, −1][2, H], row 1 is zeros
3 (placeholder)[−1, −1][2, H], all zeros

The values come from the repository's reference function for the kernel ({{cite deepinfer/model_executor/layers/tilelang_ops/prepare_cp_mirror.py:126-157}}). valid_token_mask is mirror_cp_index != −1 ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:208}}).

The kernel also returns mirror_cp_reverse_index, one entry per token. For A it is [0, 1, 4, 5, 6, 7, 2, 3]. An all-gather makes the tensor [rank 0 rows | rank 1 rows], and token 2 is row 4 of it. Stops 6 and 9 use it. The page {{link concepts/context-parallelism}} derives these numbers.

Rank 3 has no real row. It still runs every layer, because its collectives must match the other ranks.

We are in the attention layer (v4_modules/attn.py), inside each decoder layer, on all ranks. In a prefill step with CP, the layer opens a CP session and starts the all-gather of its projected K and V. It computes the queries while the data moves:

The all-gather runs through CPManager on a DeepEP BucketBuffer ({{cite deepinfer/model_executor/parallel_utils/cp.py:42-51}}). Each rank sends 4 rows and gets 8 rows: [2 × 4, ...]. The layer reorders them with mirror_cp_reverse_index back to token order ({{cite deepinfer/model_executor/models/v4_modules/attn.py:826-829}}). So rank 0 and rank 1 both store the K and V of all 8 tokens in their KV caches. Each rank computes attention only for its 4 query rows.

  • Ranks 0 and 1 exchange the K and V of A. Ranks 2 and 3 each send 2 rows; of these 4 rows, only one is a real token.
  • The two CP groups do not talk to each other in this stop.
  • The CP buffer was sized at start-up from max_num_prefilling_tokens = max_num_batched_tokens // cp_size ({{cite deepinfer/model_executor/model_loader.py:120}}, {{cite deepinfer/model_executor/parallel_utils/userbuffer.py:97-117}}).
  • Gathered tensors alias the buffer. The next session overwrites them, so the layer copies what it keeps ({{cite deepinfer/model_executor/parallel_utils/cp.py:10-14}}).

We are in DeepseekMoE.forward (v4_modules/mlp.py), after the attention of each layer. This is the stop where the two engines meet. The EP group holds all 4 ranks. So a token of A can go to an expert on rank 2 or rank 3, which belong to engine 1:

Each rank routes its own rows: 4 rows on ranks 0 and 1, 2 rows on ranks 2 and 3. The gate masks the rows with valid_token_mask = False ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:387}}). After the combine, each rank again has its own rows, [4, H] or [2, H].

Dispatch and combine are collectives over the EP group. Ranks 2 and 3 have no real token, but the experts on their devices can receive tokens of A. Assume that engine 1 ran a decode step now. It would call dispatch with the decode token limit, and it would run other layers (the draft model) after the forward pass ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:476}}). The vote in stop 1 prevents this.

The page shows the DeepEP path. If the EP group fits in one {{term nvlink-domain | NVLink domain}}, the layer can use mega-MoE instead, with the same group ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:184-188}}, {{link concepts/mega-moe}}). This site does not explain DeepEP internals.

The dispatch call also passes a counter: cumulative_local_expert_recv_stats=self._eplb_layer().expert_count ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:474}}). It adds the number of tokens that each local expert slot receives in this layer. After the forward pass, the sampler step calls the load balancer:

With EP above 1, step updates the rearrangement window, but only if rearrangement is on. Then it adds the token counts of the step to the statistics and sets the counters back to zero.

_update_load_balance_stats stores the token sum per layer for this step. Every DEEPINFER_MOE_LB_STAT_INTERVAL steps (default 128), it all-gathers the window over the EP group and computes the mean and the maximum per rank ({{cite deepinfer/model_executor/eplb/__init__.py:167-192}}, {{cite deepinfer/environ.py:118}}). This all-gather is one more reason why all 4 ranks must run the same number of steps, also the placeholder ranks. Shape of the counter: [num_moe_layers, num_local_physical_experts] ({{cite deepinfer/model_executor/eplb/__init__.py:49}}). See {{link concepts/eplb}}.

After the last layer, each CP group gathers the output rows and puts them back in token order. Every rank of engine 0 now has the hidden states of all 8 tokens, [8, H]:

Then the worker calls the sampler on all ranks. The driver sends the sampler inputs (row 7 for A: the last prompt token) with a second broadcast_tensor_dict ({{cite deepinfer/worker/model_runner.py:250-261}}, {{cite csrc/engine/prepare_sample.cpp:197}}). A follower makes SamplerInputs with no driver part ({{cite deepinfer/worker/model_runner.py:271-275}}). In the sampler, it computes the logits and returns an empty output:

So rank 0 samples the first output token of A. Rank 2 samples a token for the placeholder; the engine ignores it in stop 10.

  • Hidden states: [8, H] on ranks 0 and 1. On ranks 2 and 3 they are [1, H], because the placeholder has one token (total_q = 1).
  • selected_token_indices = [7] on engine 0: one row goes to the logits, fp32 [1, vocab].
  • A prefill step runs no draft model. In a decode step, the followers would also run the draft layers ({{cite deepinfer/model_executor/layers/sampler.py:155-160}}). The code gives no reason; our reading is that the draft MoE collectives need every rank.

We are back in Worker.execute_model_step. A prompt step is post-processed at once, also with ZOS ({{cite deepinfer/worker/worker.py:182-187}}). Only the driver calls the engine's callback and gets request outputs:

On rank 0, LLMEngine.post_process gives the token of A to the scheduler and builds a RequestOutput. On rank 2, the step is a placeholder, so the engine uses no sampler output ({{cite deepinfer/engine/llm_engine.py:987}}). Ranks 1 and 3 return an empty array and wait for the next method call.

The prompt step sets decode_step = 0 on both engines ({{cite csrc/engine/scheduler.hpp:676-677}}). That is an ALL point. Engine 1 still has no work, so vote 1 fails, and both engines run decode steps. In a decode step:

  • No mirror layout and no CP all-gather: both checks need is_prompt ({{cite deepinfer/model_executor/models/deepseek.py:168}}, {{cite deepinfer/model_executor/models/v4_modules/attn.py:766}}). Ranks 0 and 1 both run A's decode tokens, with the full KV cache that stop 6 stored.
  • With a CUDA graph, the driver sends only five small values; the graph broadcasts the metadata tensors itself ({{cite deepinfer/worker/model_runner.py:202-209}}, {{cite deepinfer/worker/cuda_graph_runner.py:61-65}}).
  • Engine 1 runs placeholder decode steps until it gets work.

What can go wrong

A collective finishes only when every rank of its group calls it. If one rank of the EP group does not reach the dispatch of a layer, the other three wait. DEEPINFER_GLOO_TIMEOUT (14400 s) applies only to the default Gloo group ({{cite deepinfer/worker/base.py:334-340}}). The split groups get no time-out argument, so the PyTorch defaults apply ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:34}}).
  • A follower dies. The driver waits in the next CP broadcast or all-gather. If the driver dies, the followers get SIGKILL ({{cite deepinfer/worker/base.py:129-130}}).
  • One idle engine slows the other. Engine 1 runs placeholder steps with full passes through all layers. Its empty ALL votes delay the next prefill of engine 0 ({{link concepts/dp-step-votes}}).
  • A CP group across hosts. The shared-memory queue assumes one host per CP group ({{cite deepinfer/distributed/shm_broadcast.py:442}}).
  • Wrong device order. Each engine sees cp_size devices from CUDA_VISIBLE_DEVICES. A follower uses local_rank = cp_rank % ngpus ({{cite deepinfer/engine/llm_engine.py:384}}). If the variable lists fewer devices than cp_size, two ranks share a device.

Why it matters. This step shows the three kinds of communication in DeepInfer. The DP group only votes. The CP group moves the inputs and the keys and values inside one engine. The EP group ties all engines together in every MoE layer. Most of the rules of the multi-GPU code follow from the last point.

In this tour, which ranks run a scheduler, and which ranks sample?

Ranks 0 and 2, the drivers of the two engines. The followers (ranks 1 and 3) have no scheduler and return before sampling ({{cite deepinfer/model_executor/layers/sampler.py:145-161}}).

 Through which channel does rank 1 learn that the next method is execute_model_step?

Through the shared-memory MessageQueue of the CP group: run_workers calls cp_broadcast_object((method, kwargs)), and the follower loop dequeues it ({{cite deepinfer/worker/base.py:300}}, {{cite deepinfer/worker/base.py:132}}).

 Which stop is the first in which ranks of engine 0 and ranks of engine 1 exchange device data?

Stop 7, the MoE dispatch. The votes in stop 1 exchange one-element CPU tensors over the Gloo group, between the drivers only. Stops 3, 4, 6 and 9 stay inside one CP group. The EP group is the world group [0, 1, 2, 3] ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:102-103}}).

 How many rows does rank 1 send in each attention all-gather of this step, and how many rows does it get back?

It sends its cp_mirror_len = 4 rows and gets 2 × 4 = 8 rows: the all-gather result has shape [cp_size × rows, ...] ({{cite deepinfer/model_executor/parallel_utils/cp.py:42-51}}).

 Rank 3 has no real token in this step. Name three collectives that it must still call, and the group of each.

(1) The broadcasts of the input metadata and the sampler inputs from rank 2, in the CP group [2, 3] ({{cite deepinfer/worker/model_runner.py:217}}, {{cite deepinfer/worker/model_runner.py:261}}). (2) The CP all-gathers in every attention layer and after the last layer, also in [2, 3] ({{cite deepinfer/model_executor/models/deepseek.py:241-244}}). (3) The MoE dispatch and combine in every layer, in the EP group [0, 1, 2, 3] ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:578-610}}). Every 128 steps, also the EPLB all-gather in the EP group.
