The idea

A {{term llm | large language model}} makes text one {{term token}} at a time. DeepInfer serves many requests at the same time. So it does not run one request from start to end. It runs steps. In each {{term engine-step | engine step}}, it selects a batch of requests, runs the model once for all of them, and adds new tokens to each request.

This tour follows one real request from examples/offline_inference.py. The request is the second prompt of the example, so its request id is "1":

prompt = ("Question: What is the largest planet in the solar system?\nAnswer: Jupiter\n\n"
          "Question: How many legs does a spider have?\nAnswer: Eight\n\n"
          "Question: Who wrote Romeo and Juliet?\nAnswer:")
params = SamplingParams(temperature=0.4, max_tokens=128, ignore_eos=False,
                        first_n_token_no_eos=1, top_logprobs=4, seq_seed=1)

The prompt and the parameters come from {{cite examples/_prompts.py:72-77}} and {{cite examples/_prompts.py:106-116}}. The tour has 13 stops. Stops 1 to 4 run once per request. Stops 5 to 12 run in every engine step, for all requests in the batch. Stop 13 runs when the user script collects the results.

An everyday comparison. Think of a restaurant kitchen. A waiter writes each order on a ticket (stop 4). The head chef looks at all tickets and decides which dishes the kitchen cooks in this round (stop 5). The cooks cook all selected dishes together (stops 7 to 11). After each round, the waiter carries finished plates to the tables (stops 12 and 13). The comparison stops being true in one place: a dish is not done after one round. Each round adds only one or a few tokens to each request, and a request needs many rounds.

Processes and threads

The example starts more than one process. The diagram below shows which processes and threads touch the request, and how they talk to each other.

  • Each DP replica is a full engine with its own scheduler. Our request lives in exactly one replica, the one with dp_rank 0 in this tour.
  • The replicas are not independent. They vote on the step type ({{cite csrc/engine/scheduler.hpp:295-341}}) and exchange tokens in the MoE layers ({{term expert-parallelism}}).
  • All work of stops 2 to 13 runs in the main thread of the replica. That thread is the {{term driver-worker | driver}}.

We are in examples/offline_inference.py. The script reads the parallel sizes from the command line. The defaults give 8 {{term data-parallelism | data-parallel}} (DP) ranks: dp_size = ep // cp = 8 // 1 ({{cite examples/offline_inference.py:24-28}}). The last line calls launch_dp(main, dp_size) ({{cite examples/offline_inference.py:112-113}}).

Each child process runs main(dp_size, dp_rank). It sets {{term environment-variable | environment variables}}, makes the LLM object, builds the prompts and calls generate():

Which tokenizer class. get_hf_tokenizer needs tokenizer.json and tokenizer_config.json in the model folder, else it raises FileNotFoundError. If the tokenizer config has an auto_map, it loads the class from the checkpoint. Else, with tokenizer_compatibility: "native" in config.json, it uses AutoTokenizer, and else LlamaTokenizerFast. The fix-ups above run for every class when the policy is "release", the default ({{cite deepinfer/hugging_face/tokenizer.py:89-121}}).

Multimodal tokens. The 21 placeholder tokens must get the ids 129280 to 129300 ({{cite deepinfer/hugging_face/tokenizer.py:48-56}}). The comment says that inference computes the image token ids as vocab_size + ImageTokenOffset ({{cite deepinfer/hugging_face/tokenizer.py:25-28}}). The engine reads vocab_size from the model config.json ({{cite deepinfer/config.py:121-122}}), which is not in the repository. The two rules agree only if vocab_size is 129280, so this tour uses 129280 (text ids 0 to 129279). This is an inference from the code, not a value that the code sets. You will see 129279 (vocab_size - 1) again in stop 11.

A vision model changes the ids again. The only model class in this release, DeepseekVLForCausalLM, has a vision part. So a NORMAL engine always has a MultimodalProcessor ({{cite deepinfer/engine/llm_engine.py:209-221}}, {{cite deepinfer/model_executor/models/__init__.py:15-17}}). In stop 4, overwrite_prompt replaces each image placeholder with vocab_size + IMAGE and many vocab_size + IMAGE_PAD ids. Our prompt has no image, so the ids stay the same. The function always returns a new array ({{cite deepinfer/ve/multimodal_processor.py:105-162}}).

Engram models. A model with {{link concepts/engram | Engram n-gram memory}} also needs compressed ids. add_request maps each id through a lookup table with CompressedTokenizer.encode ({{cite deepinfer/engine/llm_engine.py:564-567}}). Ids outside the table, for example image ids, become IMAGE_SENTINEL = -1 ({{cite deepinfer/model_executor/models/v4_modules/engram.py:62-66}}). The sequence keeps both lists. Without Engram, the compressed list is the same as the normal list.

The way back. The same tokenizer object turns ids into text at the end (stop 13). get_tokenizer() returns it ({{cite deepinfer/entrypoints/llm.py:87-88}}).

We are in deepinfer/engine/llm_engine.py. add_request checks the request, makes the engine object for it, and puts it in the queue of the scheduler. The engine object is a {{term sequence}}. It is a C++ object (deepinfer._C.engine.Sequence), so the scheduler can read it without Python.

Where the fields come from. The Python call passes flat arguments. make_sequence_init in the binding fills a SequenceInit ({{cite csrc/engine/pybind_sequence.cpp:25-38}}). The constructor reads the sampling values from the Python object once, into SamplingScalars and StoppingCriteria ({{cite csrc/engine/sequence.hpp:276-283}}). add_request sets sampling_params.eos_id = self.eos_id, the tokenizer EOS id ({{cite deepinfer/engine/llm_engine.py:527}}).

The schedulable flag. The binding sets schedulable = multi_modal_data.is_none() ({{cite csrc/engine/pybind_sequence.cpp:35}}). Our request has a multimodal dict, so it starts as not schedulable. The multimodal worker process prepares the request and sends it back through a queue. fetch() then calls scheduler.set_schedulable(id) ({{cite deepinfer/ve/multimodal_processor.py:281-305}}). A text-only model has no multimodal processor, so its sequences are schedulable at once.

Status values. A sequence is WAITING, RUNNING, SWAPPED, or one of seven FINISHED_* values ({{cite csrc/engine/sequence.hpp:30-43}}). Each finished value has a reason string: "stop", "length", "abort", "prompt_length_exceeded", "insufficient_system_resource", "xgrammar runtime errors or timeout", "ve_error" ({{cite csrc/engine/sequence.hpp:45-64}}).

Reserved memory. add_sequence reserves space in the token vector for max_tokens more ids, and in the block table for all blocks the request can need ({{cite csrc/engine/scheduler.hpp:135-142}}, {{cite csrc/engine/scheduler.hpp:190-192}}). For our request: (41 + 128 + 127) // 128 + 1 = 3 block entries.

Structured output. The SO builder is made on first use. It is a ThreadPoolExecutor with one worker per idle CPU ({{cite deepinfer/engine/llm_engine.py:329-342}}). get_idle_cpus returns DEEPINFER_SO_BUILDER_CPUS CPUs (default 4) ({{cite deepinfer/utils.py:154-161}}). submit() starts the build. pump() runs in every step and enqueues the requests whose matcher is ready ({{cite deepinfer/structure_output/so_matcher_builder.py:97-121}}, {{cite deepinfer/engine/llm_engine.py:841-842}}). Our request has no so_args, so this path is not used.

Other admission rules. If DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE is not "off", prompt_logprobs is forced to False with a warning ({{cite deepinfer/engine/llm_engine.py:529-537}}). If the multimodal data has image_bytes=None, the sequence starts as FINISHED_VE_FAILED ({{cite deepinfer/engine/llm_engine.py:547-550}}, {{cite deepinfer/engine/llm_engine.py:603-604}}).

From here, the code runs in every engine step. LLMEngine.step() first asks the C++ {{term scheduler}} for the batch ({{cite deepinfer/engine/llm_engine.py:881-887}}). The scheduler has three queues: waiting, prompted and running ({{cite csrc/engine/scheduler.hpp:1124-1126}}). It makes one decision first: is this step a {{term prefill}} step or a {{term decode}} step? DeepInfer never mixes the two in one batch.

NORMAL engine: decide whether the whole group does prompt or decode in this step. Inside DP the type must be the same; a vote makes it the same. Two kinds of attempt points. ALL point (every prefill_attempt_interval decode steps): do it only if all ranks have prefill work, so that one rank does not work while the others run empty prompt steps. ANY point (every prefill_any_attempt_interval decode steps): do it if one rank has work, as a fallback for an isolated rank. If both points fall on the same step, ANY wins. Second vote: confirm that some rank really scheduled a prefill. "want" only looked at a non-empty waiting queue, but _schedule_prefill can still come back empty (slots full, not enough KV blocks). Some rank in the group does a prompt step: this rank runs an empty prompt step to keep the step type the same.

So a prefill can start only at an attempt point. decode_step counts decode steps since the last prefill step. With the defaults, every 70th decode step is an ALL point and every 100th is an ANY point ({{cite deepinfer/environ.py:174-178}}). The first step has decode_step = 0, which is an ALL point. A rank wants a prefill if its KV cache is at most 90 % full and the first waiting request is schedulable (line 313).

The prefill limits, in order ({{cite csrc/engine/scheduler.hpp:360-546}}):

  1. A request that is already aborted or failed goes to ignored_seqs. It gets an output with its finish reason.
  2. A request that is not schedulable stops the loop (break). The requests behind it also wait.
  3. A prompt longer than prompt_limit becomes FINISHED_IGNORED. prompt_limit is max_model_len with chunked prefill, else min(max_model_len, max_num_batched_tokens) ({{cite csrc/engine/scheduler.hpp:112}}).
  4. The {{term block-manager}} answers OK, LATER or NEVER. NEVER means that the request needs num_blocks or more blocks, so it can never fit, because block 0 is not used ({{cite csrc/engine/block_manager.hpp:128-136}}). LATER stops the loop.
  5. At most max_num_seqs sequences run at the same time (lines 440-442).
  6. The sum of the prompt lengths in one prefill step must stay under DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K. Unset means no limit (lines 444-449).
  7. The chunk may not cut an image in the middle. _adjust_chunk_size moves the cut ({{cite csrc/engine/scheduler.hpp:235-260}}).
  8. In a NORMAL engine, a chunked request is the last one in the step (lines 543-545).

How many blocks. get_num_blocks() is ceil((len + inflight + drafts) / block_size) ({{cite csrc/engine/sequence.hpp:291-293}}). The block size is 128 tokens ({{cite deepinfer/model_executor/model_metadata_utils.py:133-135}}). The free list starts at block 1, because block 0 means "empty" ({{cite csrc/engine/block_manager.hpp:27-35}}). The state manager uses the same class for the per-sequence {{term state-slot | state slots}}. allocate_seq takes the blocks and one state slot ({{cite csrc/engine/block_manager.hpp:207-214}}).

Decode steps. _schedule_decode runs when the step is not a prefill step ({{cite csrc/engine/scheduler.hpp:559-660}}):

  1. It removes finished sequences from running and returns them as finished_seqs.
  2. It sorts running by output length, longest first (lines 624-625).
  3. It takes sequences from the end of the list, so the shortest output comes first. Before each one, the loop checks that at least one block is free. Then _append_slot adds a block only if the sequence needs one ({{cite csrc/engine/scheduler.hpp:628-640}}, {{cite csrc/engine/scheduler.hpp:817-828}}).
  4. If no block is free, it preempts from the front of the list: the sequence with the longest output (lines 630-634).
  5. It sorts the batch by total length and asks MTPVarlen for each seqlen_q (lines 648-652). Without a performance curve, seqlen_q = 1 + number of drafts, so 6 ({{cite csrc/engine/mtp_varlen.hpp:150-158}}).

The comment above _schedule_decode says that the scheduler preempts the sequence with the shortest output ({{cite csrc/engine/scheduler.hpp:556-557}}). The code sorts by output length, longest first, and preempts running[l] from the front (lines 624-634). So the code preempts the longest output. The comment on FINISHED_PREEMPTED is closer to the code. Translated: "the task that uses the most KV cache is stopped" ({{cite csrc/engine/sequence.hpp:55-56}}). But the code sorts by output length only, not by total length with the prompt.

Preemption. _preempt stops the request with FINISHED_PREEMPTED if stop_preempted_request is true, or if the request uses structured output. Else it resets the sequence, frees its blocks and puts it at the front of waiting. The request then runs its prefill again ({{cite csrc/engine/scheduler.hpp:766-790}}). The offline LLM uses the second policy (stop 2).

The vote and the DP group. _dp_allreduce runs an all-reduce on the DP group, also with one DP rank ({{cite csrc/engine/scheduler.hpp:169-182}}). With ZOS on, the group is the CPU (Gloo) DP group ({{cite deepinfer/engine/llm_engine.py:313}}).

A consequence for vision models. Read together, the lines above give the following sequence for one DP rank and the default intervals. This site derived it from the code and did not run it.

  1. Every request starts with schedulable=False, because the engine has a MultimodalProcessor and the request has a multimodal dict (stop 4). Only fetch() sets schedulable ({{cite deepinfer/ve/multimodal_processor.py:281-303}}).
  2. In each step(), schedule() runs first and fetch() runs later ({{cite deepinfer/engine/llm_engine.py:885}}, {{cite deepinfer/engine/llm_engine.py:939-941}}). So in step 1, the first waiting request is not schedulable, and no rank wants a prefill.
  3. Step 1 has decode_step = 0, an ALL point. The vote fails, so step 1 is an empty decode step. schedule() then sets decode_step to 1 ({{cite csrc/engine/scheduler.hpp:676-681}}).
  4. Steps 2 to 70 have decode_step 1 to 69. These are not attempt points, so they are empty decode steps too. Each one runs a placeholder forward pass ({{cite deepinfer/worker/worker.py:125-127}}).
  5. Step 71 has decode_step = 70, the next ALL point. If the multimodal worker answered for the first waiting request before the fetch() of step 70, the prefill runs in step 71.

So step 71 is the earliest prefill step. The code does not show how fast the worker process answers. If it is late, the next attempt points are decode_step 100 (ANY point, step 101) and 140 (ALL point, step 141). With one DP rank, ANY and ALL give the same result. With more DP ranks, the ALL point at 70 needs every rank to be ready. In this release the only model class has a vision part, so every request of a NORMAL engine goes through this wait. A model class without multi_modal_mapper would get no MultimodalProcessor and could prefill in step 1 ({{cite deepinfer/engine/llm_engine.py:210}}).

The output of this part. SchedulerOutputs holds scheduled_seqs, prompt_run, num_batched_tokens, finished_seqs, ignored_seqs, seqlens_q and statistics ({{cite csrc/engine/scheduler.hpp:45-77}}). schedule() checks that num_batched_tokens <= max_num_batched_tokens ({{cite csrc/engine/scheduler.hpp:671-673}}).

The model cannot read C++ sequence objects. It needs flat tensors: one row per query token, for all requests of the batch together. This layout is called varlen (variable length): the requests have different lengths, and offset arrays mark where each request starts. The page {{link concepts/input-metadata}} explains it.

The work has three parts. First, Scheduler::schedule() makes one SequenceMetadata per scheduled sequence. It is a small view of the sequence with the lengths of this step:

Open upper bound of the positions in this step: prefill stops at seqlen_k; decode pads seqlen_q on the GPU to at most max_seqlen_q (as max_k in zos.cpp), and DFlash drafts go nextn further. Buffers indexed by position, such as the RoPE cache, have only runtime_max_model_len rows.

seqlen_q is the number of new tokens of the request in this step. seqlen_k is the number of tokens it can see: the cached ones plus the new ones. For our prefill, both are 41.

Second, the worker turns the list into tensors. ModelRunner._prepare_input_tensors calls the C++ function prepare_prompt_v4 or prepare_decode_v4 through ModelMetadata.prepare_inputmetadata_dict ({{cite deepinfer/model_executor/model_metadata_utils.py:146-188}}). The common part writes the positions and the input ids:

In a prefill step, line 112 copies seqlen_q prompt ids. In a decode step, it copies one id (the last real token), and lines 116-118 add the draft tokens. Third, Python wraps the dict in an InputMetadataV4 (or InputMetadataV4VL for a vision model) and copies it to the device ({{cite deepinfer/worker/model_runner.py:142-146}}, {{cite deepinfer/worker/model_runner.py:192-198}}). In a decode step with a CUDA graph, the function writes into the buffers of the graph instead (deep dive).

Worked example, slot maps. With ratio 2, one block of 128 tokens holds 64 compressed entries. Our 41 tokens make 41 // 2 = 20 entries, at positions 0, 2, ..., 38. With block 2, they go to slots 2 * 64 + 0 to 2 * 64 + 19, so 128 to 147. The sliding-window ring of one slot has swa_block_size rows. The docs give 128 + 6 = 134 for V4.1 ({{cite doc/inference_deployment_qa.md:191}}). The code computes window size plus DEEPINFER_MAX_BACKTRACKING_TOKENS, which is at least nextn + 1 ({{cite deepinfer/worker/cache_engine.py:88-93}}, {{cite deepinfer/environ.py:132}}). A token goes to the ring only if it is one of the last swa_block_size tokens of the chunk. All 41 are, so the slots are 2 * 134 + 0 to 2 * 134 + 40.

Decode with a CUDA graph. In a decode step, the worker selects a captured {{term cuda-graph | CUDA graph}} first. prepare_decode_v4 then writes straight into the input buffers of that graph (out_dict). Placeholder sequences fill the rows up to the graph size ({{cite deepinfer/worker/model_runner.py:184-191}}). With ZOS, the decode path is prepare_decode_v4_zos ({{cite deepinfer/model_executor/model_metadata_utils.py:142-144}}).

Context parallelism. With --cp above 1, only the driver builds the metadata. It sends it to the other {{term context-parallelism | CP}} ranks with broadcast_tensor_dict ({{cite deepinfer/worker/model_runner.py:200-230}}).

The metadata pool. SequenceMetadata objects come from an object pool. The engine gives them back one step later ({{cite deepinfer/engine/llm_engine.py:1013}}, {{cite deepinfer/engine/llm_engine.py:100-104}}).

After the schedule, step() calls the worker through _run_workers("execute_model_step", ...) ({{cite deepinfer/engine/llm_engine.py:961-975}}). The {{term driver-worker | driver worker}} runs in the same process. The function has a fixed order:

3. Sample the current step (first correct the CPU metadata with the seqlens_q copied back from the device). 4. A prompt step, or a non-ZOS configuration: post-process now. A ZOS decode step: keep it for the next step, to overlap with forward.
  1. Line 122: start the forward pass of step N on the device (stop 8). The call returns at once; the device works in the background.
  2. Line 144: post-process step N-1 (stop 12) while the device runs step N.
  3. Line 154: start the sampler of step N (stops 10 and 11).
  4. Line 164: pre_sampler_sync releases old objects and frees the blocks of finished sequences ({{cite deepinfer/engine/llm_engine.py:830-846}}).

ZOS is on by default for the NORMAL engine ({{cite deepinfer/engine/arg_utils.py:51-55}}, {{cite deepinfer/engine/engine_type.py:15-17}}). With ZOS, the CPU and the device work at the same time. The cost: step() returns the tokens of the previous decode step.

The problem. With ZOS, step N+1 is scheduled before step N is post-processed. So the CPU does not yet know how many drafts of step N the sampler accepted. The scheduler assumes the most: it adds nextn + 1 to total_inflight_tokens for each scheduled sequence ({{cite csrc/engine/scheduler.hpp:689}}, {{cite csrc/engine/scheduler.hpp:726}}). seqlen_k includes that number ({{cite csrc/engine/scheduler.hpp:697}}).

The fix on the device. _correct_seqlens_qk matches the sequences of step N+1 with those of step N by seq_id (prepare_zos_inputs, {{cite csrc/engine/zos.cpp:142-196}}). Then a kernel corrects seqlens_k on the device: seqlens_k[i] += seqlens_q[i] - (nextn - accepted[j]) ({{cite deepinfer/model_executor/layers/tilelang_ops/compute_seqlens_k_zos.py:10-31}}). The real input ids come from the sampled tokens of step N, which are still on the device (MetadataZOS, {{cite deepinfer/worker/zos_status.py:23-40}}). With the default settings, this correction needs no CPU-device sync. With DSpark (DEEPINFER_ENABLE_MTP_VARLEN=1), the worker copies the corrected seqlens_q back and waits for that copy before it samples ({{cite deepinfer/worker/worker.py:146-152}}, {{cite deepinfer/worker/worker.py:229-234}}).

No sync rule. execute_main_model and execute_sample run inside forbid_cuda_sync(). Their docstrings say: "This function must NOT contain any cuda synchronize" ({{cite deepinfer/worker/model_runner.py:315-324}}). The main wait of a step is sample_end_evt.synchronize() in _post_process_step, one step later ({{cite deepinfer/worker/worker.py:262-263}}).

Placeholder steps. If the batch is empty, the worker still runs a forward pass on one dummy sequence (_placeholder_seq_metadata, {{cite deepinfer/worker/model_runner.py:386-403}}).

CP workers. run_workers sends the method name to the CP worker processes before it calls the method on the driver ({{cite deepinfer/worker/base.py:290-302}}). The CP workers run the same method in start_slave_worker_loop ({{cite deepinfer/worker/base.py:129-133}}). They get only is_prompt and is_placeholder; the sequence list stays on the driver.

Settings. DEEPINFER_ZERO_OVERHEAD_SCHEDULING=0 turns ZOS off; then each step post-processes itself ({{cite deepinfer/environ.py:179}}). DEEPINFER_GC_INTERVAL_STEP (default 1000) sets how often the worker runs Python garbage collection ({{cite deepinfer/environ.py:185}}, {{cite deepinfer/worker/base.py:153-157}}).

A CUDA graph is a recording of all kernel launches of one forward pass, for one fixed batch size. A replay starts all of them with one call, so the CPU cost is small. The graph sizes for this example are 1, 2, 4, 8, 16 and 24 tokens ({{cite deepinfer/worker/cuda_graph_runner.py:41-51}}). One decode request with 6 tokens uses the graph of size 8 ({{cite deepinfer/worker/cuda_graph_runner.py:143-148}}).

The model object is a DeepseekVLForCausalLM, a subclass of DeepseekForCausalLM. It is the only class that the model registry knows ({{cite deepinfer/model_executor/models/__init__.py:15-17}}).   2. Lines 210-218: each decoder layer runs {{term attention}} and then the MLP or {{term moe | MoE}} block ({{cite deepinfer/model_executor/models/decoder_layer.py:155-173}}). Each layer gets its part of the KV cache, kv_caches[i] (stop 9).

Graph settings. CUDA graphs are off for a PROMPT engine and with DEEPINFER_ENFORCE_EAGER=1. The largest graph has max_num_seqs * (1 + nextn) tokens: 4 * 6 = 24 here ({{cite deepinfer/worker/model_runner.py:73-79}}). DEEPINFER_CUDAGRAPH_BATCH_SIZE_INTERVAL (default 8) sets the step between graph sizes ({{cite deepinfer/environ.py:155}}). A batch larger than the largest graph raises ValueError in select.

Logits are float32. get_logits makes a float32 tensor [rows, vocab_size] and fills it with a BF16 matrix multiply against the LM head weights ({{cite deepinfer/model_executor/layers/sampler_utils.py:20-28}}).

Attention needs the keys and values of all earlier tokens. The {{term kv-cache}} keeps them, so the model does not compute them again in each step. In DeepInfer, the cache for one request has two parts:

  • Paged blocks for the compressed KV entries: one entry for every 1 or 2 tokens ({{term kv-compression}}). The {{term block-table}} of the sequence lists its blocks (stop 5).
  • A state slot for the {{term sliding-window-attention | sliding-window}} KV: a ring with room for the last 134 tokens per layer. The docs say: "The SWA KV cache does not go into paged KV blocks; it lives in the state cache" ({{cite doc/inference_deployment_qa.md:163}}).

The forward pass does the writes. The kernels of each attention layer use the slot maps from stop 6. No Python code runs per token. The block and state ids come from the scheduler; the device only follows them.

Sizes. A compressed entry uses 528 bytes in MXFP8 or 288 bytes in FP4: data plus scale factors ({{cite deepinfer/worker/cache_engine.py:211-213}}). A sliding-window entry uses 528 bytes ({{cite deepinfer/worker/cache_engine.py:216-218}}). The docs give the stored part of one state slot as "20 layers × 134 tokens × 528 B = 1,415,040 B per sequence" ({{cite doc/inference_deployment_qa.md:169}}).

How many slots and blocks. The number of state slots is int(max_num_seqs * DEEPINFER_NUM_STATE_SLOTS_RATIO) + 1: int(4 * 1.2) + 1 = 5 here ({{cite deepinfer/worker/cache_engine.py:201-202}}, {{cite deepinfer/environ.py:162}}). Slot 0 is never given out (stop 5). The memory profile at start-up sets the number of blocks. It takes total memory * gpu_memory_utilization and subtracts the peak use of a test run and two times the state cache. It divides the rest by the size of one block ({{cite deepinfer/worker/base.py:228-245}}). Then all ranks use the same value: the mean over all ranks, rounded down to an even number ({{cite deepinfer/worker/base.py:264-266}}).

A decode step. The 6 query tokens of one request write 6 ring rows. A compressed entry is written only where (position + 1) % ratio == 0; other rows get slot -1 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:70-95}}). The step writes entries for draft tokens too. If the sampler rejects a draft, its entries are wrong. They do no harm: cache.num_tokens counts only accepted tokens (stop 12), and the next step writes over the same rows. The DFlash docstring uses the same argument for its own cache ({{cite deepinfer/model_executor/models/mtp/dflash.py:204-209}}).

A new block. When the sequence grows past the end of its last block, _append_slot adds one block in the next decode schedule ({{cite csrc/engine/scheduler.hpp:817-828}}).

The end. When the request finishes, finalize_seq calls scheduler.free_seq, which frees the blocks and the state slot ({{cite deepinfer/engine/llm_engine.py:804-806}}, {{cite csrc/engine/scheduler.hpp:738-750}}). The pages {{link learn/kv-cache}} and {{link concepts/paged-kv-cache}} explain the cache in full.

A decode step that makes only one token per request is slow, because the whole model runs for one token. DeepInfer adds a small {{term mtp | multi-token prediction}} module, {{term dflash | DFlash}}. The last one gets draft_tok = drafts + 1 and accept_tok = accepted + 1 ({{cite csrc/engine/outputs.hpp:199-294}}). Ignored sequences get one output with their finish reason ({{cite csrc/engine/outputs.hpp:297-304}}). A prefill chunk that is not the last one gets no output. Logprobs below -9999 are clamped to -9999 ({{cite csrc/engine/outputs.hpp:182-192}}).

The output pool. The objects live in a {{term request-output-pool | RequestOutputPool}} with room for 10000 outputs. Python gets only uint64 pointers ({{cite csrc/engine/outputs.hpp:45-81}}). The engine collects the pointers and releases them in the next pre_sampler_sync ({{cite deepinfer/engine/llm_engine.py:92-107}}, {{cite deepinfer/engine/llm_engine.py:830-831}}). A finished request. When _check_stop sets a FINISHED_* status, the sequence stays in running until the next decode schedule. free_finished_seqs then moves it to finished_seqs ({{cite csrc/engine/scheduler.hpp:752-763}}). pre_sampler_sync of that step calls finalize_seq, which frees the blocks ({{cite deepinfer/engine/llm_engine.py:844-846}}).

The last stop is the loop in LLM._run_engine. It calls step() while a request is unfinished, and once more flush_inflight_reqs() at the end:

  1. Line 178: step() while there is work, then one flush_inflight_reqs(). The flush post-processes the last ZOS step, which no later step would do ({{cite deepinfer/engine/llm_engine.py:977-982}}).
  2. Line 181: RequestOutput.clone(ptr) copies the C++ object into a new Python-owned object ({{cite csrc/engine/pybind_output.cpp:17-18}}). This copy is necessary because of the pool rule in stop 12.
  3. Line 187: the results are sorted by request id as an integer, so the order is the order of the prompts.
  4. Lines 189-190: with decode_sequence=True, the token ids become text with tokenizer.decode.

The example uses decode_sequence=False (stop 1). So it gets lists of RequestOutput objects and decodes the text itself ({{cite examples/offline_inference.py:78-81}}).

What the data looks like now (illustrative):

outputs[1]                          # list of RequestOutput, one per token, up to 128
[x.token_id for x in outputs[1]]    # [14200, 41813, 198, 198, 21265, 25, ...]
outputs[1][-1].finished             # True

has_unfinished_requests() asks the scheduler for the number of sequences in waiting, running and prompted, plus requests that wait for an SO matcher ({{cite deepinfer/engine/llm_engine.py:665-679}}, {{cite csrc/engine/scheduler.hpp:165-167}}). With more than one DP rank, it takes the maximum over the DP group. So a rank with no work runs placeholder steps until all ranks finish. This keeps the collective operations of all ranks in the same order.

A finished sequence still counts while it is in running. So the loop runs one more step after the last token: that step frees the blocks (stop 12). The ZOS step that was in flight at that time had our request in its batch. Its result is dropped: process_outputs skips finished sequences ({{cite csrc/engine/scheduler.hpp:905-915}}).

In the example, print_output also computes the acceptance rate from draft_tok and accept_tok, and a perplexity from token_logprobs ({{cite examples/offline_inference.py:79-86}}). llm.close() stops the workers ({{cite examples/offline_inference.py:109}}).

The loop: many steps for one request

Stops 5 to 12 repeat for every engine step. One request sees one prefill step (or more with chunked prefill) and then many decode steps. Each decode step adds 1 to 6 tokens. The diagram shows the steps of request "1" alone. It counts the steps from the first prefill step and leaves out the empty steps before it (stop 5, deep dive).

  • Panel 1. The prefill step returns the first token in the same step. Each decode step returns the tokens of the step before it (stop 7). For 128 output tokens with about 3 tokens per step, the request needs about 40 decode steps.
  • Panel 2. This overlap is the reason for ZOS. The CPU work of the scheduler and of the output assembly hides behind the forward pass on the device.
  • Panel 3. The accepted drafts and the new sample are appended. The KV cache counts only them (stop 12).

The diagram shows one request. In the example, four requests share each step, and the fifth request starts when one of them finishes. In this release, empty steps come before the first prefill, because the model class has a vision part (stop 5, deep dive). With DSpark, a decode step can have fewer than 6 query tokens.

What can go wrong

If you call LLMEngine.step() yourself, the returned pointers are valid only until the next step. Copy them with RequestOutput.clone() first ({{cite deepinfer/engine/llm_engine.py:866-870}}). LLM.generate() does this for you.
  • A request disappears. A token id outside [0, vocab_size) makes add_request drop the request with an info log line, not an error ({{cite deepinfer/engine/llm_engine.py:581-589}}). generate() then returns fewer results than prompts. The example checks this with an assert ({{cite examples/offline_inference.py:102}}).
  • An empty prompt. ValueError("prompt must not be empty") ({{cite deepinfer/engine/llm_engine.py:553-554}}).
  • A prompt that is too long. The request finishes at once with "prompt_length_exceeded" and no tokens ({{cite csrc/engine/scheduler.hpp:377-385}}).
  • The KV cache is full. The scheduler preempts the running request with the longest output. In the offline API, the request runs its prefill again later. A structured-output request stops instead ({{cite csrc/engine/scheduler.hpp:766-790}}).
  • The pool is exhausted. Code that never releases outputs gets RequestOutputPool exhausted (max_size=10000) ({{cite csrc/engine/outputs.hpp:65}}).
  • A hung multimodal worker. If the worker makes no progress for DEEPINFER_MULTI_MODAL_WORKER_TIMEOUT seconds, the engine calls os.abort() ({{cite deepinfer/ve/multimodal_processor.py:264-275}}).
  • Devices set too late. Set CUDA_VISIBLE_DEVICES before you import deepinfer or torch ({{cite examples/_config.py:1-7}}). See {{link concepts/hardware-platforms}}.

Why it matters. The tour shows the full path of the data in one picture. Most questions about DeepInfer behaviour start with "which stop is it?". A slow first token can be a schedule question (stop 5). A wrong token can be a sampler question (stop 10). Lost output can be an output-pool question (stops 12 and 13).

Which function turns the prompt text into token ids, and which id is always first?

LLM._add_request calls self.llm_engine.tokenizer.encode(prompt) ({{cite deepinfer/entrypoints/llm.py:156}}). The release fix-ups turn on add_bos_token and check that BOS has id 0, so the list always starts with 0 ({{cite deepinfer/hugging_face/tokenizer.py:59-69}}).

 In a decode step with the defaults of the example, how many query tokens does one request send, and what are they?

6: the last real token and 5 draft tokens. Without a performance curve, seqlen_q = 1 + number of drafts ({{cite csrc/engine/mtp_varlen.hpp:153-157}}). prepare_common_base copies the last token and then the drafts into input_ids ({{cite csrc/engine/input_metadata/prepare_tensor_input_base.cpp:112-119}}).

 Why does LLM._run_engine call RequestOutput.clone() for every output?

step() returns pointers into a C++ RequestOutputPool. The engine releases them in the next pre_sampler_sync, so the objects become invalid in the next step ({{cite deepinfer/engine/llm_engine.py:100-107}}, {{cite deepinfer/engine/llm_engine.py:830-831}}, {{cite csrc/engine/outputs.hpp:72-80}}). clone makes an independent copy ({{cite csrc/engine/pybind_output.cpp:17-18}}).

 With ZOS on, step N is a decode step. Which tokens does step() return? And why does a request that finished in step N's post-process still appear in the batch of step N+1?

It returns the tokens of step N-1: the worker post-processes the previous step after it starts forward N, and keeps step N for later ({{cite deepinfer/worker/worker.py:143-144}}, {{cite deepinfer/worker/worker.py:182-187}}). Step N+1 is scheduled before the post-process of step N runs, so the scheduler does not know yet that the request is finished. process_outputs later skips the finished sequence, and the result of that extra step is dropped ({{cite csrc/engine/scheduler.hpp:905-915}}).

 The model has a vision part and DP size is 1. You add one text request and call generate(). Why is step 1 not the prefill step? With default settings, which is the earliest step that can be the prefill step?

The sequence starts with schedulable=False, because it has a multimodal dict ({{cite csrc/engine/pybind_sequence.cpp:35}}). set_schedulable runs in fetch(), after schedule() in the same step ({{cite deepinfer/engine/llm_engine.py:885}}, {{cite deepinfer/engine/llm_engine.py:939-941}}). So step 1 is an empty decode step, and decode_step becomes 1. The next prefill attempt point is decode_step = 70, the default DEEPINFER_PREFILL_ATTEMPT_INTERVAL ({{cite csrc/engine/scheduler.hpp:308-319}}, {{cite deepinfer/environ.py:174}}). So step 71 is the earliest prefill step. It is the prefill step only if the multimodal worker answered before the fetch() of step 70. Else the next try is step 101 (decode_step = 100, ANY point).
