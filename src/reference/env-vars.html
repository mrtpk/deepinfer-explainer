What an environment variable is

An {{term environment-variable}} is a named text value that a process gets from its parent when it starts. In a shell, you set one for all later commands with export, or for one command only:

export DEEPINFER_ACCELERATOR=nvidia          # for this shell and all programs it starts
DEEPINFER_ENFORCE_EAGER=1 python3 examples/offline_inference.py   # for one command only

In Python, the process environment is the dict os.environ. os.getenv("NAME") returns the text, or None when the variable is not set. A child process gets a copy of the environment of its parent. A change in the parent after the child starts does not reach the child.

Environment variables are always text. A program must parse the text into a number, a flag or a path. DeepInfer does this in one place, deepinfer/environ.py. The file defines one class, envs, with one attribute for each variable:

The module that defines all environment variables in one place.

Other code reads a value as envs.DEEPINFER_NCCL_NUM_SMS, for example in {{cite deepinfer/platform.py:81}}. The package exports envs at the top level, so from deepinfer import envs works ({{cite deepinfer/__init__.py:6}}).

environ.py declares 59 variables. Comments such as # -- MTP -- put them in 16 groups. This page uses the same groups. Five more DEEPINFER_* names are read directly with os.getenv or std::getenv, outside environ.py. They are in a separate table.

How DeepInfer reads a variable

The EnvVar descriptor

Each attribute of envs is an EnvVar object. EnvVar is a {{term descriptor}}: a Python object in a class that controls what an attribute read returns. When code reads envs.X and X is still a descriptor, Python calls X.__get__. This is the whole mechanism:

  1. Class definition (lines 40-42). Python calls __set_name__ for each attribute when it makes the class envs. The descriptor remembers its name, for example "DEEPINFER_NCCL_NUM_SMS". It also adds itself to the module dict _descriptors.
  2. First read (lines 49-50). envs.DEEPINFER_NCCL_NUM_SMS calls __get__. It reads os.getenv(self.name) and gives the text to its parse function init.
  3. Cache (line 56). setattr(owner, self.name, value) puts the parsed value, for example the int 32, into the class. The descriptor is now gone from the class dict.
  4. Later reads. The attribute is now a plain int. Python returns it directly and does not call any function. So a later change of os.environ has no effect on envs.

So a read after the first one costs the same as a normal class attribute. And the code never parses a variable that no code reads, so a bad value in it gives no error.

"The first read caches the value" is true for each process. DeepInfer starts its extra workers with SpawnProcess ({{cite deepinfer/engine/llm_engine.py:389-395}}, {{cite deepinfer/logger.py:169-170}}). A spawned process is a new Python interpreter, so it has its own envs class and reads the environment again. It reads the environment that it got from its parent at start.

If the exception type cannot take one text argument, the original exception is raised.

When DeepInfer reads a variable

A value is fixed at the first read in each process. So the important question is: when is the first read? There are three cases.

  1. At import time. Some code reads envs.X at the top level of a module, in a class body, or in the default value of a function argument. Python runs this code at {{term import-time | import time}}. The import-time table lists every such read.
  2. At first use. Most reads are inside functions. The first call fixes the value, for example when the engine builds its config or a worker builds the model.
  3. In C++. Two variables are read by the C++ extension with std::getenv, separately from envs: DEEPINFER_USE_NEXTN_DECODE ({{cite csrc/engine/utils.hpp:36-40}}) and DEEPINFER_CPP_LOG_LEVEL ({{cite csrc/utils/log.hpp:19-31}}).

Set variables before you import deepinfer

Set all DEEPINFER_* variables and the visible-device variables before import deepinfer and before import torch. A value that you set later can be ignored without an error.

The example scripts follow this rule. The module docstring of examples/_config.py says so:

Shared config, environment setup and LLM construction for the V4 scripts and the tests/models end-to-end tests. Config and environment setup are closely coupled, so they are in this one module. Note: this module must NOT import deepinfer at the top level. The environment setup must be complete before deepinfer is imported. For this reason, create_llm also imports deepinfer lazily, inside the function.

create_llm sets the environment, then the visible devices, and only then imports torch and DeepInfer:

Build the LLM in the child process: first set CUDA_VISIBLE_DEVICES and the environment, then import deepinfer lazily. llm_kwargs go to LLM unchanged and can replace the common defaults below. profile_init wraps the LLM construction in a temporary profiler to warm up kineto. The caller must not wrap create_llm in a profiler: CUPTI initializes CUDA when it starts, so a CUDA_VISIBLE_DEVICES that is set later has no effect. On Ascend NPU, import torch initializes the ACL environment, so a later ASCEND_RT_VISIBLE_DEVICES setting fails.

There are three reasons for this order:

  • import deepinfer reads DEEPINFER_ACCELERATOR. The package calls _so_platform_tag() at module level to find its compiled extension folder ({{cite deepinfer/__init__.py:15}}, {{cite deepinfer/__init__.py:30-32}}).
  • Device runtimes read the visible devices once. After CUDA or the Ascend runtime starts, a new CUDA_VISIBLE_DEVICES or ASCEND_RT_VISIBLE_DEVICES has no effect. For this reason, import deepinfer sets PYTORCH_NVML_BASED_CUDA_CHECK=1 ({{cite deepinfer/__init__.py:37-39}}), and PLATFORM is made only on first use ({{cite deepinfer/__init__.py:58-59}}).
  • Some modules read variables at import time (next table).

Values that the code changes at run time

Some code changes a value after start-up. It uses one of three methods.

1. os.environ.setdefault plus rearm. EngineArgs chooses a default that depends on the engine type. Then it calls environ.rearm, which puts the descriptor back, so the next read parses the new text:

So DEEPINFER_ZERO_OVERHEAD_SCHEDULING is False in environ.py, but it is on for NORMAL and COMPLETION engines ({{cite deepinfer/engine/engine_type.py:15-17}}). DEEPINFER_USE_MULTIMODAL_POOL is on for all engines except COMPLETION. Your own exported value wins, because setdefault does not overwrite.

2. Direct assignment to envs. envs.X = value replaces the class attribute. The profile run sets DEEPINFER_FORCE_IMBALANCE_RATIO to 1.8 and then back to 0.0 ({{cite deepinfer/worker/model_runner.py:509-512}}). The EP buffer writes the calculated SM count into DEEPINFER_USERBUFFER_COMM_SMS ({{cite deepinfer/model_executor/parallel_utils/userbuffer.py:86-90}}). These assignments do not change os.environ, so child processes and C++ do not see them.

3. Tests. pytest runs many tests in one process. Without help, the first test that reads a variable fixes it for all later tests. An autouse fixture in tests/conftest.py restores os.environ after each test and calls rearm_all():

Some tests change envs directly with the pytest {{term monkeypatch}} fixture. A comment in tests/worker/test_state_cache_ops.py explains a trap: monkeypatch.setattr first reads the old value, and that read replaces the descriptor. So the undo restores a plain value, not the descriptor. The test depends on rearm_all() in the autouse fixture, which runs after the undo ({{cite tests/worker/test_state_cache_ops.py:93-97}}). The same test must also clear an lru_cache that keeps old results ({{cite tests/worker/test_state_cache_ops.py:102-103}}, {{cite deepinfer/worker/cache_engine.py:130-138}}).

Deterministic sampling

DEEPINFER_BATCH_INVARIANT=1 DEEPINFER_ENABLE_MTP_VARLEN=0   # and a fixed seq_seed in SamplingParams

Source: {{cite README.md:28}}. The README does not give the reason for MTP_VARLEN=0. The code shows one batch dependency. With varlen on, the worker shares one budget of query tokens over all sequences of the batch, by confidence rate ({{cite deepinfer/worker/worker.py:218-219}}, {{cite deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py:17-25}}). So the number of tokens that one request verifies depends on the other requests. ENABLE_MTP_VARLEN is already off by default ({{cite deepinfer/environ.py:131}}). The explicit 0 also overrides a value that a script exported.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

This variable sets the maximum number of draft tokens for each request in one {{term decode}} step. A draft token is a guess for a later token. The model checks all guesses in one step (speculative decoding, see {{link concepts/speculative-decoding}}). We follow the value 3 from the shell to every place that uses it. The example uses max_num_seqs = 4, max_model_len = 32768 and ZOS on.

Step 1: the definition.

The maximum number of speculative tokens. Default 5. Set it to 0 explicitly to turn off speculative decoding.
  1. Shell. export DEEPINFER_USE_NEXTN_DECODE=3. The example scripts use os.environ.setdefault(..., "5"), so they keep your value ({{cite examples/_config.py:74-75}}).
  2. import deepinfer. Line 6 of deepinfer/__init__.py imports envs. Python runs the class body. Line 129 makes an EnvVar with the parse function lambda v: _int(v, 5). No value is read yet.
  3. First read. The first code that touches envs.DEEPINFER_USE_NEXTN_DECODE calls __get__. It calls _int("3", 5), gets 3, and stores 3 in the class. If deepinfer.structure_output.matcher is imported first, its module-level line MAX_ROLLBACK_TOKENS = envs.DEEPINFER_USE_NEXTN_DECODE + 2 does this first read ({{cite deepinfer/structure_output/matcher.py:20}}).
  4. All later reads in this process get the plain int 3.

The docstring for DEEPINFER_USE_NEXTN_DECODE (line 130) is in the first deep dive.

In a NORMAL engine with data parallelism, all DP ranks must do the same kind of step: all {{term prefill}} or all decode. The C++ scheduler counts decode steps in decode_step. A prefill step sets it back to 0. At some steps the ranks vote with an all-reduce:

  1. Line 308: an ANY point is each multiple of prefill_any_attempt_interval (default 100), but not step 0.
  2. Line 309: an ALL point is each multiple of prefill_attempt_interval (default 70), and also step 0.
  3. Line 313: a rank "wants" prefill if its KV cache usage is at or below a watermark and a prefill request waits.
  4. Line 316: at an ANY point, one rank that wants prefill is enough. When a step is both an ANY and an ALL point, the ANY rule applies ({{cite csrc/engine/scheduler.hpp:303}}).
  5. Line 318: at an ALL point, every rank must want prefill.

Use the defaults, with no prefill in between. Then the ranks vote at these decode steps: 0 (ALL), 70 (ALL), 100 (ANY), 140 (ALL), 200 (ANY), 210 (ALL), 280 (ALL), 300 (ANY) ... 700 (ANY, also an ALL point). So if only one rank has a request in its queue, that request waits at most 100 decode steps.

Both values are default arguments of SchedulerConfig.__init__ ({{cite deepinfer/config.py:193-194}}). Python computes them when it imports deepinfer.config. A value that you set after that import has no effect, and rearm does not help. Both must be at least 1 ({{cite deepinfer/config.py:213-216}}, {{cite csrc/engine/scheduler.hpp:105-108}}).

A CUDA graph records the kernels of one decode step for one batch size. The engine pads each batch to the next captured size. build_graph_batch_sizes chooses the sizes:

  • Offline example: max_num_seqs = 4 ({{cite examples/offline_inference.py:54}}) and 5 draft tokens give a maximum of 4 * 6 = 24. With the default interval 8: [1, 2, 4, 8, 16, 24].
  • Benchmark: it sets the interval to 32 ({{cite examples/benchmark.py:169}}). Assume a maximum of 384, for example 64 sequences with 5 draft tokens. Then the 17 sizes are 1, 2, 4, 8, 16, 32, 64, ..., 352, 384.
  • DFlash graphs use DEEPINFER_DFLASH_CUDAGRAPH_BATCH_SIZE_INTERVAL with the maximum max_num_seqs ({{cite deepinfer/worker/dflash_cuda_graph_runner.py:36}}).

A smaller interval makes more graphs. Each graph costs capture time and memory, but it gives less padding. DEEPINFER_ENFORCE_EAGER=1 makes no graphs. The PROMPT engine never uses graphs ({{cite deepinfer/worker/model_runner.py:73}}).

Five variables control expert load balancing (EPLB). The example scripts set them as a group ({{cite examples/_config.py:77-83}}):

DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS=32           # setdefault, if set_override_experts
DEEPINFER_EXPERT_COUNT_WINDOW_SIZE=3              # always
DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL=30   # only with EPLB on
DEEPINFER_REARRANGE_AFTER_PREFILL_IN_NORMAL_ENGINE=1   # only with EPLB on
  1. Redundant experts. resolve_num_extra_experts adds padding so that routed plus extra experts divide by the EP size ({{cite deepinfer/model_executor/eplb/__init__.py:21-28}}). Assume 256 routed experts (a number for this example only), 32 extra and EP size 24: -(256 + 32) % 24 = 0, so 32 stays. With EP size 20: -(288) % 20 = 12, so the loader uses 44 and logs a warning ({{cite deepinfer/model_executor/model_loader.py:95-99}}).
  2. Window. The balancer keeps a ring of the last 3 steps of token counts, as an int tensor [window, num_moe_layers, num_local_physical_experts] ({{cite deepinfer/model_executor/eplb/__init__.py:113-119}}). The default 100 needs more memory, which is why the examples use 3.
  3. Interval. With interval 30, the step counter starts at 30 - max(1, 30 // 4) = 23. So the first rearrangement comes after 7 steps, then one every 30 steps ({{cite deepinfer/model_executor/eplb/__init__.py:121-123}}, {{cite deepinfer/model_executor/eplb/__init__.py:161-165}}). The window (3) must be between 1 and the interval (30), or the constructor raises ValueError ({{cite deepinfer/model_executor/eplb/__init__.py:106-111}}).
  4. After prefill. In a NORMAL engine, a prefill step sets the counter to interval - 1. The next decode step reaches the interval and rearranges ({{cite deepinfer/model_executor/eplb/__init__.py:156-159}}).
  5. Statistics. Independent of rearrangement, every 128 steps (DEEPINFER_MOE_LB_STAT_INTERVAL) the EP ranks all-gather an int64 tensor [ep_size, 128, num_moe_layers] and compute mean and maximum tokens per rank ({{cite deepinfer/model_executor/eplb/__init__.py:181-193}}).

With an EP size of 1, step() returns at once, and none of this runs ({{cite deepinfer/model_executor/eplb/__init__.py:133-134}}). See {{link concepts/eplb}}.

With the default 0, the code asks DeepEP for a theoretical SM count. It keeps min(32, device_sms // 4) SMs free for compute, and takes the smaller value. What can go wrong

A bool variable is False only for 0, an empty text, false and False ({{cite deepinfer/environ.py:12-13}}). DEEPINFER_BATCH_INVARIANT=off or =no turns the feature on. Use 0 and 1.
  • The value is set too late. After the first read, a process ignores changes to os.environ ({{cite deepinfer/environ.py:56}}). For import-time reads, the module import is the first read. No error tells you this. Set variables before import deepinfer.
  • Empty text for a number. export DEEPINFER_NCCL_NUM_SMS= gives ValueError, not the default, because only an unset variable uses the default ({{cite deepinfer/environ.py:16-17}}). Use unset to go back to the default.
  • Wrong case for a choice. DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=Compact raises ValueError: ... 'Compact', must be one of ('off', 'mask', 'compact') ({{cite deepinfer/environ.py:90-91}}).
  • YOCO keep tokens too small. With truncation on, KEEP_TOKENS must be above 0 and at least window_size + DEEPINFER_MAX_BACKTRACKING_TOKENS. Otherwise an AssertionError stops start-up ({{cite deepinfer/model_executor/model_metadata_utils.py:92}}, {{cite deepinfer/worker/model_runner.py:110-113}}).
  • Temperature list with the wrong length. The list for DEEPINFER_DFLASH_CONFIDENCE_HEAD_TEMPERATURE must have DEEPINFER_USE_NEXTN_DECODE values ({{cite deepinfer/environ.py:140-141}}).
  • EPLB window larger than the interval. With rearrangement on, DEEPINFER_EXPERT_COUNT_WINDOW_SIZE must be from 1 to the interval. The default window 100 with an interval of 30 raises ValueError ({{cite deepinfer/model_executor/eplb/__init__.py:106-111}}).
  • A change in Python only. envs.X = value does not change os.environ. The C++ scheduler reads DEEPINFER_USE_NEXTN_DECODE from the environment ({{cite csrc/engine/scheduler.hpp:118}}). Spawned workers also read the environment. Change the environment, not envs, if other processes or C++ must see the value.
  • CUDA_VISIBLE_DEVICES not set. The engine reads it with os.environ[...] and stops with KeyError ({{cite deepinfer/engine/llm_engine.py:188}}). The example scripts set it for you ({{cite examples/_config.py:55-63}}).
  • Cached results in tests. get_inference_compress_block_size has an lru_cache. After you change DEEPINFER_MAX_BACKTRACKING_TOKENS, call clear_compress_block_size_cache() ({{cite deepinfer/worker/cache_engine.py:130-138}}).
  • Docs and code differ. examples/README.md says that DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS defaults to 32 ({{cite examples/README.md:63}}). The default in environ.py is 0 ({{cite deepinfer/environ.py:114}}). The value 32 comes from the example scripts, only when the caller passes set_override_experts=True ({{cite examples/_config.py:77-79}}). benchmark.py always passes True ({{cite examples/benchmark.py:161}}). offline_inference.py passes True only with EPLB on ({{cite examples/offline_inference.py:35-40}}). In your own code, the default is 0 redundant experts.

Why it matters. A wrong variable rarely gives an error. It changes speed, memory or results without a message. When a run behaves in an unexpected way, print the values that the process really uses: {k: getattr(envs, k) for k in environ._descriptors}. This forces the first read of every variable in that process, so do it after the start-up code has set the environment.

Still 70. The value is a default argument of SchedulerConfig.__init__ ({{cite deepinfer/config.py:193}}).  You set nothing, and the model uses the default 5 draft tokens. What is envs.DEEPINFER_MAX_BACKTRACKING_TOKENS? Then you export DEEPINFER_USE_NEXTN_DECODE=0 and DEEPINFER_MAX_BACKTRACKING_TOKENS=1. What is it now, and which state ring gets smaller?

With nothing set: max(0, 5 + 1) = 6 ({{cite deepinfer/environ.py:132}}). In the second case: max(1, 0 + 1) = 1. The sliding-window block becomes window_size + 1 instead of window_size + 6 ({{cite deepinfer/worker/cache_engine.py:93}}). The compression ring becomes compress_ratio + 0 instead of compress_ratio + 5 ({{cite deepinfer/worker/cache_engine.py:133}}). The C++ scheduler also reads 0 from the environment and makes no drafts ({{cite csrc/engine/scheduler.hpp:118}}).
