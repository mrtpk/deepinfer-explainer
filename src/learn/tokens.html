The model sees only these ids.

The idea

Why not letters or words?

A neural network works on numbers. So the text must become a list of numbers first. There are three simple choices:

  • One id per letter (or byte). The vocabulary is small, but the lists are very long. The model must then do many steps for each word, and each step costs time.
  • One id per word. The lists are short, but there are millions of words, names and spellings. A word that is not in the list cannot be written.
  • One id per common piece of text. This is the middle way. Frequent words are one piece. Rare words are cut into several pieces. Any text can be written with the pieces.

LLMs use the third choice. Each piece is a {{term token}}. The program that cuts text into tokens is the {{term tokenizer}}. The fixed list of all tokens is the {{term vocabulary}}. As a rough guide, one token of English text is about three quarters of a word. Code, numbers and other languages often need more tokens per word.

How the tokenizer finds the pieces

Most LLM tokenizers use {{term bpe | BPE}} (byte-pair encoding), or a method like it. Training the tokenizer happens once, before the model is trained:

  1. Start with single bytes. Every text can be written as bytes, so no text is "unknown".
  2. Count all pairs of neighbours in a large amount of text.
  3. Merge the most frequent pair into one new piece. Add it to the vocabulary.
  4. Repeat until the vocabulary has the size that you want.

To encode a new text, the tokenizer applies the learned merges in the same order. A frequent word such as " the" ends as one token. A rare word such as "Tokenization" can end as "Token" + "ization".

Special tokens

Some ids are not text. They are {{term special-token | special tokens}} with a control meaning:

  • BOS (begin of sequence) marks the start of the input.
  • EOS (end of sequence) is the token that the model writes to say "I am done". The engine stops the request when it sees EOS ({{term eos-token}}).
  • PAD fills unused places when lists must have the same length.

Chat models use more special tokens, for example to mark where the user text starts. DeepInfer's release tokenizer must put BOS at id 0, EOS at id 1 and PAD at id 2. The section "In DeepInfer" shows the check.

Ids are only names

The number of a token tells the model nothing. Id 15400 is not "more" than id 498. The first layer of the model, the {{term embedding}}, looks up one learned vector for each id. That vector carries the meaning. The page {{link learn/transformer}} continues from there.

An everyday comparison

Think of a box of building bricks. The box has many large bricks for common shapes, and small bricks for everything else. You can build any shape. Common shapes need few bricks, and unusual shapes need many small ones. A tokenizer builds text in the same way.

The comparison stops here: you choose your bricks freely, but a tokenizer has no choice. It applies its fixed rules, so the same text always gives the same tokens. Also, it does not know what the text means.

Deep dive

This is the general algorithm. The deployment notes rely on "how BPE tokenizers work" when they describe the encoding of DeepSeek prompts ({{cite doc/inference_deployment_qa.md:304}}). Its rules are in the Hugging Face file tokenizer.json of the checkpoint. DeepInfer does not change how it cuts text.

Training (done once by the model makers):

  1. Split the training text into words at spaces and punctuation. This "pre-tokenization" keeps merges inside a word. Many tokenizers keep the space at the start of the next word, so " hard" is one piece.
  2. Write each word as a list of bytes. The start vocabulary is the 256 byte values.
  3. Count every pair of neighbours over all words, weighted by how often each word occurs.
  4. Take the most frequent pair (A, B). Add the new piece AB to the vocabulary. Record the merge rule "A B → AB" with its rank (1, 2, 3 ...).
  5. Replace every A B in the words with AB. Go back to step 3.
  6. Stop at the target vocabulary size. Add the special tokens with their own ids.

Worked example (panel 2 of the figure). Corpus: "low", "lower", "lowest".

MergeMost frequent pairCountWords after the merge
start——l o w · l o w e r · l o w e s t
1(l, o)3lo w · lo w e r · lo w e s t
2(lo, w)3low · low e r · low e s t
3(low, e)2low · lowe r · lowe s t

After merge 3, every remaining pair occurs once: (lowe, r), (lowe, s), (s, t). A real run continues with many more words.

Encoding a new word, for example "lowest":

  1. Start with bytes: l o w e s t.
  2. Find the pair with the best (lowest) merge rank in the word. Apply it.
  3. Repeat until no learned merge applies: lo w e s t → low e s t → lowe s t.
  4. Look up the id of each remaining piece.

Decoding is simple: look up the bytes of each id and join them. The text after decoding is the same as the original, because every step only joins bytes.

Real tokenizers add rules for numbers, for some languages, and for the normalization of text. Some use other methods, for example SentencePiece unigram models. The idea of a fixed vocabulary of pieces stays the same.

DeepInfer reads vocab_size from the config.json of the checkpoint ({{cite deepinfer/hugging_face/config.py:276}}). The repository does not contain that file. The tokenizer code requires 21 multimodal tokens at ids 129280 to 129300 and says that their ids are vocab_size + offset ({{cite deepinfer/hugging_face/tokenizer.py:25-30}}, {{cite deepinfer/hugging_face/tokenizer.py:48-56}}). Both rules agree only if vocab_size is 129280. So this site uses V = 129,280 (inferred): text ids 0 to 129,279.

The vocabulary size sets the size of three things:

Embedding table[V, d]illustrative d = 4,096, BF16: 129,280 × 4,096 × 2 B ≈ 1.06 GB{{cite deepinfer/model_executor/models/deepseek.py:144-148}}

The hidden size d also comes from the checkpoint config. The value 4,096 above is only an example.

A larger vocabulary makes texts shorter (fewer steps), but the embedding, the LM head and every logits row grow. With 256 rows to sample in one decode step, the logits alone take 256 × 517 KB ≈ 132 MB.

Which class loads the files: a class from the checkpoint if tokenizer_config.json has an auto_map; AutoTokenizer with the policy "native"; else LlamaTokenizerFast ({{cite deepinfer/hugging_face/tokenizer.py:103-112}}). The policy comes from tokenizer_compatibility in config.json, default "release" ({{cite deepinfer/hugging_face/tokenizer.py:89-94}}). With "native", none of the checks above run ({{cite deepinfer/hugging_face/tokenizer.py:121}}).
  1. Encode. LLM._add_request calls tokenizer.encode(prompt) and converts the result to np.int32 ({{cite deepinfer/entrypoints/llm.py:153-157}}).
  2. Check. LLMEngine.add_request raises ValueError for an empty prompt ({{cite deepinfer/engine/llm_engine.py:553-554}}). It drops a request with an id below 0 or at or above vocab_size (plus the image ids for a multimodal request). It logs this at info level and returns None ({{cite deepinfer/engine/llm_engine.py:580-589}}).
  3. Engram ids. For a model with {{link concepts/engram | Engram}} whose config turns on tokenizer compression, the engine also maps each id to a compressed id with a lookup table ({{cite deepinfer/engine/arg_utils.py:89-90}}, {{cite deepinfer/engine/llm_engine.py:564-567}}, {{cite deepinfer/model_executor/models/v4_modules/engram.py:62-66}}).
  4. Embed. The model looks up one row of the embedding table per id ({{cite deepinfer/model_executor/models/deepseek.py:161-162}}).
  5. Sample. The sampler gives back new ids, one or more per sequence and step.
  6. Decode. At the end, LLM turns the output ids back into text: tokenizer.decode([...]) ({{cite deepinfer/entrypoints/llm.py:189-190}}).

Tokenizer speed in production. The deployment notes describe a separate component, DeepSeek Recipe, for the API-to-token step. It records where special tokens go and encodes the text segments between them in parallel ({{cite doc/inference_deployment_qa.md:304}}). That component is not in this repository. The offline LLM class calls encode() once per prompt.

What can go wrong

  • Missing files. Without tokenizer.json or tokenizer_config.json, start-up raises FileNotFoundError ({{cite deepinfer/hugging_face/tokenizer.py:96-99}}).
  • Another tokenizer. A tokenizer with other special ids stops with ValueError under the default policy ({{cite deepinfer/hugging_face/tokenizer.py:36-41}}). An unknown tokenizer_compatibility value also raises ValueError ({{cite deepinfer/hugging_face/tokenizer.py:93-94}}).
  • Ids without BOS. If you pass prompt_token_ids, DeepInfer does not call the tokenizer ({{cite deepinfer/entrypoints/llm.py:153-156}}). So it does not add BOS for you. Put id 0 first yourself, as encode() does.
  • Special text in user input. A Hugging Face tokenizer can map the text of a special token to its special id. The deployment notes say that their production encoder prevents this, so user text cannot inject control tokens ({{cite doc/inference_deployment_qa.md:300}}). Check prompts that contain such strings.

Why it matters. Every count in an inference engine is in tokens: prompt length, max_tokens, KV cache size, batch size. A text that needs more tokens costs more memory and more steps. The special ids also control when a request ends.

Why do LLMs not use one id per word?

There are too many words, names and spellings. The vocabulary would be very large, and any word that is not in it could not be written. Subword tokens keep the vocabulary at a fixed size and can still write any text.

 What does tokenizer.encode("") return for DeepInfer's release tokenizer?

[0]: only the BOS token. The release policy turns on BOS insertion and checks exactly this ({{cite deepinfer/hugging_face/tokenizer.py:68-69}}).

 A BPE corpus has the words "low", "lower" and "lowest". After the merges (l, o) and (lo, w), which pair comes next, and why?

(low, e). The words are now low, low e r and low e s t. The pair (low, e) occurs 2 times. Every other pair occurs once.

 You call llm.generate(prompt_token_ids=[[15400, 2860]]). Name two ways in which this request differs from a text prompt, from the code.

(1) DeepInfer does not call the tokenizer, so no BOS id 0 is added in front ({{cite deepinfer/entrypoints/llm.py:153-157}}). (2) The ids still go through the range check in add_request. An id below 0, or at or above the limit, drops the request with an info log ({{cite deepinfer/engine/llm_engine.py:580-589}}). The limit is vocab_size + 5. LLM always adds empty multimodal data when the engine has a multimodal processor, so the 5 image ids are also valid ({{cite deepinfer/entrypoints/llm.py:158-159}}, {{cite deepinfer/multimodal_tokens.py:28}}).
