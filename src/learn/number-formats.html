DeepInfer stores weights in FP8 and FP4 with block scales, computes most GEMMs with FP8 inputs, and keeps its KV cache in FP4 or MXFP8. --- A number format decides how many bits each value uses; fewer bits save memory and time, and a shared scale keeps small formats accurate.

The idea

Why fewer bits?

Every weight, activation and KV cache entry is a number in device memory. The {{term dtype}} of a {{term tensor}} sets how many bits each number uses. Fewer bits help in three ways:

  • Memory. A model in 8-bit numbers needs half the memory of the same model in 16-bit numbers.
  • Bandwidth. Decode is {{term memory-bound}} (see {{link learn/gpus-kernels}}). Half the bytes means about half the time.
  • Math. {{term tensor-core | Tensor Cores}} do more FP8 or FP4 operations per second than BF16 operations.

The cost is accuracy. A small format has fewer possible values, so most numbers must be rounded. Engineers make this rounding small with {{term quantization}} methods, mainly with scales.

Sign, exponent and mantissa

A {{term floating-point}} has three bit fields:

value = (−1)^sign × 1.mantissa × 2^(exponent − bias)

sign      1 bit: + or −
exponent  e bits: the power of two (sets the range)
mantissa  m bits: the digits after the binary point (sets the precision)

More exponent bits give a larger range: very large and very small numbers. More {{term mantissa}} bits give finer steps between neighbour values. When the exponent field is 0, the number is subnormal: 0.mantissa × 2^(1 − bias). Subnormals fill the gap between 0 and the smallest normal number.

BF16 has the same exponent as FP32, so it has the same range with less precision. This is why models train and run in BF16 without overflow. FP16 is more precise, but its range ends at 65,504.

FP8 has two common layouts. E4M3 has more precision; E5M2 has more range. Inference engines usually use E4M3 for weights and activations. FP4 E2M1 has only 16 codes. Its positive values are 0, 0.5, 1, 1.5, 2, 3, 4 and 6.

A worked conversion: 0.3

0.3 = 1.2 × 2−2. So the exponent is −2 and the mantissa is 0.2. Each format rounds 0.2 to its mantissa bits:

FormatMantissaBitsStored valueError
BF160.2 × 27 = 25.6 → 260 01111101 0011010 = 0x3E9A(1 + 26/128) × 0.25 = 0.300781250.26 %
FP160.2 × 210 = 204.8 → 2050 01101 0011001101 = 0x34CD0.300048830.016 %
E4M30.2 × 23 = 1.6 → 20 0101 010 = 0x2A(1 + 2/8) × 0.25 = 0.31254.2 %
E2M1(0.3 lies between the codes 0 and 0.5)0 00 10.567 %

The exponent field of E4M3 is −2 + 7 = 5 = 0101. The exponent field of BF16 is −2 + 127 = 125 = 01111101.

Scales: keep small formats accurate

E2M1 cannot store 0.3 well on its own. But if we first divide by a {{term scale-factor}}, the value can land near a code. Divide 0.3 by 0.0625: the result is 4.8, and the nearest code is 4. Then 4 × 0.0625 = 0.25, an error of 17 % instead of 67 %.

The scale must fit the numbers that share it. With one scale for a whole tensor, one large value forces a large scale on all other values. So modern formats use {{term block-scaling}}: a small block of values (for example 16 or 32) shares one scale.

  • {{term mxfp4}}: 32 E2M1 values + 1 UE8M0 scale = 17 bytes, 4.25 bits per value.
  • {{term mxfp8}}: 32 FP8 values + 1 UE8M0 scale = 33 bytes, 8.25 bits per value.
  • FP4 with an E4M3 scale per 16 values: 9 bytes per 16 values, 4.5 bits per value.

A UE8M0 scale holds only a power of two: 2^(code − 127). Multiplying by a power of two changes only the exponent, so it adds no rounding error of its own. An E4M3 scale can be any FP8 value, so it fits the block better, but it costs a few more bits per value.

An everyday comparison

Think of a price list with the header "all prices in thousands of euros". Each row needs only a short number, such as 4 or 1.5, and the header gives the size. A block scale is that header. A list with very different prices (5 euros and 5 million euros) needs several headers, one per small group of rows.

The comparison stops here: a price list can write any short number, but an FP4 row can only write one of 16 codes. And a UE8M0 header can only be a power of two, such as "in units of 4" or "in units of 8".

A power-of-two scale (MXFP4). A common rule: scale = 2^ceil(log2(amax / 6)), so that the largest value fits into the E2M1 maximum. Block (8 of 32 values shown): 0.12, −0.53, 1.70, 0.04, −2.90, 0.88, 0.31, −0.07.

  1. amax = 2.90. 2.90 / 6 = 0.483. log2(0.483) = −1.05, ceil = −1. Scale = 2−1 = 0.5, UE8M0 code 126.
  2. Divide: 0.24, −1.06, 3.4, 0.08, −5.8, 1.76, 0.62, −0.14.
  3. Round to E2M1: 0, −1, 3, 0, −6, 2, 0.5, −0.
  4. Multiply back: 0, −0.5, 1.5, 0, −3.0, 1.0, 0.25, 0. The largest error is 0.20 (for 1.70).

An E4M3 scale per 16 values. DeepInfer's reference code for the FP4 KV cache takes amax / 6 and stores it as E4M3 ({{cite deepinfer/model_executor/layers/tilelang_ops/cache_common.py:339-345}}). For the same 8 values: 2.90 / 6 = 0.483, and the nearest E4M3 value is 0.46875.

  1. Divide: 0.26, −1.13, 3.63, 0.09, −6.19, 1.88, 0.66, −0.15. The value −6.19 is outside the range and becomes −6.
  2. Round to E2M1: 0.5, −1, 4, 0, −6, 2, 0.5, −0.
  3. Multiply back: 0.23, −0.47, 1.88, 0, −2.81, 0.94, 0.23, 0.

The sum of the 8 errors is 0.68, against 0.74 for the power-of-two scale. The finer scale helps a little, and smaller blocks help more.

The power-of-two rule is one common choice; the OCP MX rule uses floor(log2(amax)) − 2 for E2M1. DeepInfer asks its quantize kernels for round_sf=True and packed UE8M0 ({{cite deepinfer/model_executor/layers/linear.py:17-24}}). Those kernels are in tile_kernels and DeepGEMM, which this site does not explain.

Linear layers (FP8). Before loading, DeepInfer turns each FP8 linear weight into float8_e4m3fn and declares a scale tensor with one value per 32 × 32 block. The token embedding, the head and the FP4 experts are skipped ({{cite deepinfer/model_executor/models/v4_modules/containers.py:113-135}}):

weight  W  : float8_e4m3fn  [N, K]
scale   sf : float32        [ceil(N/32), ceil(K/32)]   (one scale per 32 × 32 block)

The loader reads the UE8M0 scale bytes, turns them into FP32 without loss, and then packs them for the GEMM library ({{cite deepinfer/hugging_face/weights.py:418-427}}, {{cite deepinfer/hugging_face/weights.py:13-16}}).

Worked example. W = [4,096, 4,096]. Data: 16 MiB in FP8 (32 MiB in BF16). Scales: 128 × 128 = 16,384 blocks, 16 KiB as UE8M0 bytes.

Routed experts (MXFP4). One parameter holds the experts of one rank as packed FP4 in int8, plus a packed scale tensor of dtype int16 or int32 ({{cite deepinfer/hugging_face/weights.py:304-305}}). The expert GEMM reads one scale per 32 weights ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:118-128}}). Example: one expert linear1 with h_out = 4,096 and h_in = 4,096. Data: 4,096 × 2,048 bytes = 8 MiB. Scales: 4,096 × 128 = 512 KiB. Total 8.5 MiB, which is 4.25 bits per weight.

BF16 parts. The checkpoint must be in BF16 apart from the quantized weights ({{cite deepinfer/hugging_face/config.py:58-59}}). The gate projection stays in BF16 ({{cite deepinfer/model_executor/models/v4_modules/moe.py:66-67}}). The logits come from a BF16 GEMM with an FP32 output ({{cite deepinfer/model_executor/layers/sampler_utils.py:20-28}}).

A ReplicatedLinear with an FP8 weight casts its BF16 input to FP8 on the fly. Each token row gets one scale per 32 values:

The order of the codes inside an int32, and the column-major, TMA-aligned layout of the scale tensor, are set by the GEMM library. The shape above shows only the number of values.

Worked example. A C1 layer stores one entry per token. With FP4: 128 tokens × 288 B = 36,864 B per block and layer. With MXFP8: 128 × 528 = 67,584 B. FP4 saves 45 % of the main cache. In BF16, the same 512 values would need 1,024 B per token.

What can go wrong

  • A checkpoint in another format. The config loader raises ValueError("Unsupported HF ...") if the quantization method, expert dtype, activation scheme, block size or scale format differ ({{cite deepinfer/hugging_face/config.py:254-262}}). A model dtype other than BF16 also raises ({{cite deepinfer/hugging_face/config.py:58-59}}).
  • FP4 experts from a plain FP8 checkpoint. The dummy FP4 path asserts that the FP8 bytes are FP4-compatible: "Only support FP4-QAT checkpoint" ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:60}}). QAT means that training already used FP4.
  • Wrong scale dtype. An FP8 GEMM asserts that both scale tensors have the platform type, int32 or int16 ({{cite deepinfer/model_executor/layers/linear.py:164}}).
  • Overflow and outliers. E4M3 ends at 448 and E2M1 at 6. One very large value in a block makes the scale large, and the small values of the same block round to 0. Block scaling limits this damage to one block.

Why it matters. The format of a tensor sets its memory, its bandwidth and the speed of the math on it. In DeepInfer, FP4 experts need about a quarter of the BF16 memory. FP8 activations halve the GEMM input traffic. The FP4 KV cache lets more sequences run at the same time.

Why can a model run in BF16 without overflow, when FP16 sometimes overflows?

BF16 has 8 exponent bits, like FP32, so its largest value is about 3.4 × 1038. FP16 has only 5 exponent bits and ends at 65,504. BF16 gives up mantissa bits (7 instead of 10) to keep the range.

 Decode the E4M3 byte 0x44.

0x44 = 0 1000 100. Exponent field 8, so 28 − 7 = 2. Mantissa 4/8 = 0.5. Value = 1.5 × 2 = 3.

 An MXFP4 block has amax = 10. Which power-of-two scale does the rule 2^ceil(log2(amax / 6)) give, and what is its UE8M0 code?

10 / 6 = 1.67; log2(1.67) = 0.74; ceil = 1. Scale = 21 = 2, so the largest value becomes 5, a tie between the codes 4 and 6. UE8M0 code = 1 + 127 = 128 = 0x80 (decoded by {{cite deepinfer/hugging_face/weights.py:163-167}}).

 How many bytes does one main KV cache entry take in DeepInfer with the default format, and how is that number made?

288 bytes: 512 FP4 values (256 bytes) plus one E4M3 scale per 16 values (32 bytes) ({{cite deepinfer/model_executor/layers/tilelang_ops/cache_common.py:119-128}}). The default comes from use_fp4_sparse_kv, which is True unless the checkpoint config says otherwise ({{cite deepinfer/hugging_face/config.py:303}}).

 An FP8 GEMM input has M = 512 tokens and K = 7,168. How many UE8M0 codes are there, and how many int32 values hold them on NVIDIA?

One code per 32 values of a row: 7,168 / 32 = 224 codes per token, 512 × 224 = 114,688 codes ({{cite deepinfer/model_executor/layers/linear.py:17-24}}). On NVIDIA, four codes share one int32 ({{cite deepinfer/platform.py:63}}): 114,688 / 4 = 28,672 int32 values, or 56 per token.
