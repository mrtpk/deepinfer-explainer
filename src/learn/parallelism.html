The work can be split by requests (DP), by matrices (TP), by layers (PP), by tokens (CP) or by experts (EP). DeepInfer uses DP for attention, CP for long prefills and EP for the MoE experts. It has no TP and no PP group. --- Parallelism splits the work of one model over many devices; the devices then exchange data with collective operations.

The idea

Why use more than one device?

There are two reasons. First, a large model does not fit in the memory of one device. Second, one device is too slow for the number of requests. So the engine runs on many devices. Each device is driven by one process, the {{term rank}}.

The ranks must then split the work and exchange data. There are five common ways to split the work. Each way splits a different thing, and each way needs a different kind of communication.

Five ways to split the work

NameWhat each rank holdsWhat the ranks exchangeIn DeepInfer
{{term data-parallelism | Data parallel}} (DP)a full copy of the model part; its own requestsnothing in the forward passyes, for attention
{{term tensor-parallelism | Tensor parallel}} (TP)a slice of every weight matrixan {{term all-reduce}} (or {{term all-gather}}) in every layerno
{{term pipeline-parallelism | Pipeline parallel}} (PP)some of the layers (a stage)activations, from one stage to the nextno
{{term context-parallelism | Context parallel}} (CP)a part of the tokens of one long promptkeys and values (all-gather)yes, for prefill
{{term expert-parallelism | Expert parallel}} (EP)some of the experts of each {{term moe}} layertokens to experts and back ({{term all-to-all}})yes, for the experts

Real systems combine them. A common plan for an MoE model is "attention DP, MoE EP". Every rank keeps the full attention weights and its own requests, but holds only some of the experts. This is the plan of DeepInfer ({{cite README.md:12}}).

Collectives, with small numbers

A {{term collective}} is a communication step in which all ranks of a {{term process-group | group}} take part. Every rank calls the same function, and every rank gets a result. Here are the four that this site uses, with three ranks:

CollectiveRank 0 givesRank 1 givesRank 2 givesEach rank gets
{{term all-reduce}} (sum)[1, 2][3, 4][5, 6][9, 12]
{{term all-gather}}[1, 2][3, 4][5, 6][1, 2, 3, 4, 5, 6]
{{term all-to-all}}[1, 2, 3][4, 5, 6][7, 8, 9]rank 0: [1, 4, 7]; rank 1: [2, 5, 8]; rank 2: [3, 6, 9]
{{term broadcast}} from rank 0[1, 2](anything)(anything)[1, 2]

In an all-to-all, rank j gets part j of every rank. That is a transpose of the data over the ranks. MoE uses it: each rank sends each token to the rank that holds its expert.

All-reduce has more than one use. With "sum" it adds partial results, as in TP. With "max" or "min" it works as a vote: all ranks learn the same answer to a yes/no question.

The cost of communication

Communication takes time, and it also uses SMs and memory bandwidth on the device. Links inside one machine or rack ({{term nvlink}} on NVIDIA) are much faster than the network between machines. So the plan tries to keep heavy traffic on fast links. A simple cost rule for a ring all-reduce of S bytes over n ranks: each rank sends and receives 2 × (n − 1) / n × S bytes.

Example: an all-reduce of 16 MiB over 8 ranks. Each rank sends 2 × 7/8 × 16 = 28 MiB. TP does this in every layer, for every step. This is one reason why an MoE engine can prefer DP for attention: DP needs no communication in the attention layers.

Libraries such as {{term nccl}} also use tree and other algorithms. The ring formula is a good first estimate, not an exact cost.

An everyday comparison

Think of a restaurant group with eight kitchens. With DP, each kitchen cooks the full menu for its own guests. With TP, every dish is half-cooked in two kitchens, and the halves are joined before the next step. With PP, each kitchen does one stage of every dish, like an assembly line. With EP, each kitchen has specialist cooks for some dishes, and orders go to the kitchen with the right specialist. With CP, very large orders are shared between kitchens.

The comparison stops here: kitchens can work alone for hours, but ranks must exchange data many times in every step. And in a collective, all ranks wait for the slowest one. So one slow rank slows down the whole group.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Sizes. ParallelConfig gets four sizes ({{cite deepinfer/config.py:150-182}}):

  1. Line 162: if data_parallel_size is 0 (the EngineArgs default, {{cite deepinfer/engine/arg_utils.py:28-31}}), it becomes max(1, ep // cp).
  2. Line 171: model_parallel_size = context_parallel_size.
  3. Lines 172-173: the Engram size defaults to cp × dp. The world size is max(cp × dp, enp).
  4. Lines 177-182: EP must divide cp × dp, and the world size must be a multiple of cp × dp and of enp.

Rank numbers. A rank is engine_rank × cp_size + cp_rank ({{cite deepinfer/worker/base.py:329}}). engine_rank is the DP index of the engine. The CP ranks of one engine are neighbours.

Layouts. create_process_groups uses einops.rearrange on torch.arange(world) ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:80-118}}):

Worked example. Run with --ep 8 --cp 2 and no DP size. Then dp = max(1, 8 // 2) = 4, enp = 2 × 4 = 8, world = 8. The ranks are 0..7, and rank r has engine_rank = r // 2 and cp_rank = r % 2.

  • CP groups: [0, 1], [2, 3], [4, 5], [6, 7]. Each pair runs one engine.
  • DP groups: [0, 2, 4, 6] and [1, 3, 5, 7]. Each group has one rank of each engine with the same cp_rank.
  • EP group: [0..7], the world group. Engram group: [0..7].
  • With --ep 4 instead: EP groups [0, 1, 2, 3] and [4, 5, 6, 7]. Each rank holds 1/4 of the experts.

One group object per layout. _split_group_cached makes a group for every row of the layout on every rank, because torch.distributed.new_group must be called by all ranks. It keeps only the row that contains this rank, and caches the result ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:26-48}}).

The default process group uses gloo, a CPU backend ({{cite deepinfer/worker/base.py:334-340}}). The device groups use the backend of the platform: nccl or hccl ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:82-83}}). See {{link concepts/hardware-platforms}}.

With a CPU default group, the device groups start lazily. So DeepInfer runs one small all-reduce on each device group at start-up:

After the default process group changed to the CPU (gloo) backend, the NCCL/HCCL subgroups lost eager/split start-up. They are all lazy: a collective must run once before the communicator really exists. Single-rank groups must not be skipped either: Engram's deep_ep reuses the communicator made here through backend._comm_ptr(), and a null pointer gives a segmentation fault at once.

The CPU copies of the groups are for small control messages. For example, with {{term zos}} the scheduler votes over the CPU DP group ({{cite deepinfer/engine/llm_engine.py:313}}). The CPU CP group carries the shared-memory message queue that sends method calls from the driver to the other CP ranks ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:122-124}}).

The CP all-gathers go through DeepInfer's own buffer (userbuffer.cp), and the EP exchange goes through {{term deepep}}. This site does not explain the insides of DeepEP.

Worked example: the size of an MoE dispatch. The numbers are illustrative, not from the repo. One rank has 1,536 tokens, top-8 routing, hidden size 4,096 and FP8 tokens (1 byte per value). Each token goes to up to 8 experts. So the rank sends at most 1,536 × 8 × 4,096 B = 48 MiB in the dispatch, plus the small scale factors. The combine brings the same number of BF16 results back, 96 MiB at most. Tokens whose expert is on the same rank do not leave the rank. In a real model, top-k and the hidden size come from the checkpoint config.

The Q&A document describes the production service of DeepSeek V4.1 Flash. It is about the service, not only about this repo:

  • Prefill uses EP2-8 / DP2-8, the smallest size that HBM allows. Decode uses EP64-128 / DP64-128 ("Wide-EP") ({{cite doc/inference_deployment_qa.md:47-49}}).
  • "TP and CP are not used for now" ({{cite doc/inference_deployment_qa.md:53}}). The code supports CP, and the examples show --cp 8 ({{cite examples/README.md:8}}).
  • Wide EP reduces the memory traffic per step in the expert part ({{cite doc/inference_deployment_qa.md:57}}).

Why wide EP helps decode, with numbers. Take 256 experts (illustrative) and 64 ranks: each rank holds 4 experts. With 8 ranks, each rank holds 32 experts. A decode step must read the weights of every expert that gets at least one token. With fewer experts per rank, each rank reads fewer weight bytes per step. Also, each expert gets the tokens of more ranks, so the batch per expert is larger. A larger batch per expert gives the expert GEMMs a higher arithmetic intensity. See {{link learn/gpus-kernels}} and {{link learn/moe}}.

What can go wrong

  • Sizes that do not fit. ParallelConfig asserts that EP divides cp × dp, and that the world size fits CP, DP and Engram ({{cite deepinfer/config.py:176-182}}). A wrong combination stops start-up.
  • Experts that do not divide by EP. The number of physical experts must be a multiple of ep_size. DeepInfer rounds the number of extra (redundant) experts up and logs a warning ({{cite deepinfer/model_executor/model_loader.py:93-100}}, {{cite deepinfer/model_executor/eplb/__init__.py:21-28}}).
  • A hang in a collective. All ranks of a group must call the same collectives in the same order. The scheduler keeps decode_step equal on all ranks for this reason. Translated: "decode_step is the same on all ranks. So the number and meaning of the votes match, and the group does not hang in the allreduce." ({{cite csrc/engine/scheduler.hpp:307}}).
  • A slow rank. In a collective, every rank waits for the slowest one. One rank with too much MoE load slows all EP ranks. This is the job of {{link concepts/eplb}}.
  • A long start-up wait. The CPU group waits up to DEEPINFER_GLOO_TIMEOUT seconds, default 14,400 ({{cite deepinfer/environ.py:110}}, {{cite deepinfer/worker/base.py:334-340}}).

Why it matters. The parallel plan decides how much memory each rank needs, how much it communicates, and which ranks wait for which. When a DeepInfer page says "the DP group" or "the EP group", it means one of the groups on this page.

Three ranks hold [2, 0], [1, 1] and [0, 3]. What does each rank get from an all-reduce (sum)? And from an all-gather?

All-reduce: every rank gets [3, 4]. All-gather: every rank gets [2, 0, 1, 1, 0, 3], in rank order.

 Does DeepInfer split the attention weights over ranks with tensor parallelism? Give evidence from the code.

No. ParallelProcessGroup has no TP group ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:51-65}}). The attention layers use ReplicatedLinear, which keeps the full weight ({{cite deepinfer/model_executor/layers/linear.py:36-45}}). Only the expert weights are split, by expert (EP). Attention uses DP ({{cite doc/inference_deployment_qa.md:33}}).

 In an all-to-all over 4 ranks, rank 2 holds [a, b, c, d]. Which rank gets c?

Rank j gets part j of every rank. c is part 2 of rank 2, so rank 2 keeps it. a goes to rank 0, b to rank 1 and d to rank 3.

 You start DeepInfer with --ep 8 --cp 4 and no DP size. What are dp, the world size, the CP groups and the DP groups?

dp = max(1, 8 // 4) = 2 ({{cite deepinfer/config.py:161-162}}). enp = 4 × 2 = 8, world = 8. CP groups (dp cp) -> dp cp: [0, 1, 2, 3] and [4, 5, 6, 7]. DP groups (replica dp cp) -> (replica cp) dp: [0, 4], [1, 5], [2, 6], [3, 7] ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:92-98}}). The EP group is all 8 ranks.

 Why does init_device_groups run an all-reduce on a zero tensor for every NCCL or HCCL group, also for groups with one rank?

The default group uses gloo, so the device groups start lazily. A collective must run once to make the communicator. Single-rank groups are included because Engram's DeepEP code reuses that communicator, and a null pointer would crash ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:173-187}}).
