A router sends each token to only a few of them. DeepInfer's model uses MoE in every layer, with a top-k gate, shared experts and expert parallelism. --- A Mixture of Experts layer holds many experts but uses only a few of them for each token. So the model is large, but each token is cheap.

The idea

From one FFN to many experts

Each transformer layer has {{term attention}} and then a feed-forward network ({{term ffn}}). The FFN works on each token alone. A common FFN is {{term swiglu}}, with three weight matrices:

h      = hidden size,  m = FFN width
W1, W3 : [h → m]      W2 : [m → h]
FFN(x) = W2 · ( SiLU(W1·x) ⊙ (W3·x) )
FLOPs per token = 2 · 3 · h · m          (three matrix-vector products)

An {{term moe}} layer replaces the one FFN with many smaller FFNs, the {{term expert | experts}}. A small {{term router}} gives each token a score for each expert. With {{term top-k-routing}}, the token goes only to the k experts with the best scores. Their outputs are added with weights that come from the scores.

Many MoE models also have a {{term shared-expert}}. Every token uses it, in addition to its top-k experts. It learns what all tokens need, so the routed experts can specialize.

Why MoE is cheap per token

The weights that a token really uses are its {{term active-parameters}}. In an MoE layer, they are the top-k experts, the shared experts and the router. All other experts stay unused for that token.

A worked example (illustrative numbers). Take h = 4,096, expert width m = 2,048, 64 routed experts, top-6 and 1 shared expert.

  1. One expert: 3 × 4,096 × 2,048 = 25.2 M weights.
  2. Stored in one layer: (64 + 1) × 25.2 M = 1.64 G weights.
  3. Used by one token: (6 + 1) × 25.2 M = 176 M weights, which is 10.8 % of the stored weights.
  4. FLOPs per token: 2 × 176 M = 352 M. A dense FFN with all 1.64 G weights would need 3.3 G FLOPs.

So the model can store much more knowledge without more compute per token. The cost moves to memory: all experts must be in device memory, and the router must send tokens to the right experts.

Load balance and capacity

A router can send many tokens to the same few experts. Then those experts do most of the work, and the others wait. During training, MoE models use a balance rule. Two common rules:

  • An extra loss that punishes uneven use of the experts.
  • A bias per expert that is added to the scores only to choose the top-k (the "auxiliary-loss-free" rule of DeepSeek-V3). The bias goes up for under-used experts and down for over-used ones.

Some systems also set an {{term expert-capacity}}: a maximum number of tokens per expert in one step. Extra tokens are dropped or sent to another expert. This keeps buffers small, but it changes the output.

In inference, {{term load-balance}} matters even more with {{term expert-parallelism}}. Each rank holds some experts. The rank with the most tokens takes the longest, and all other ranks wait for it in the collective step.

Why MoE decode is memory-bound

In a dense layer, all tokens of the batch share the same weights. In an MoE layer, each expert sees only its own tokens. With T tokens, top-k and E experts, an expert gets T × k / E tokens on average.

Example: 1,536 decode tokens, top-6, 64 experts: 1,536 × 6 / 64 = 144 tokens per expert. A BF16 GEMM with 144 rows is still memory-bound on a device with a ridge point of about 281 (see {{link learn/gpus-kernels}}). With 256 tokens, an expert gets only 24. This is why MoE engines want very large decode batches, and why they spread the experts over many ranks.

An everyday comparison

Think of a large hospital. A triage nurse (the router) sees each patient and sends the patient to two specialists out of many (top-2). Every patient also sees the family doctor (the shared expert). The hospital employs many specialists, but each patient costs only three short visits.

The comparison stops here: a specialist in a hospital is an expert in a human topic, but an MoE expert has no clear topic. Training decides what each expert does. And the router decides again for every token, in every layer.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

DeepInfer stores the gate and up projections (W1 and W3) of an expert as one matrix linear1 with 2 × m outputs. linear2 is W2 ({{cite deepinfer/model_executor/models/v4_modules/moe.py:97-108}}). When it loads the checkpoint, it joins w1 and w3 of each expert ({{cite deepinfer/hugging_face/weights.py:285}}).

StepShape for T tokens of one expertSource
input[T, h], FP8 with scales, or BF16{{cite deepinfer/model_executor/models/v4_modules/mlp.py:406-415}}
linear1 (grouped GEMM)[T, 2m] BF16{{cite deepinfer/model_executor/models/v4_modules/mlp.py:417-430}}
SwiGLU with clamp and cast (the kernel also gets topk_weights)[T, m]{{cite deepinfer/model_executor/models/v4_modules/mlp.py:436-442}}
linear2 (grouped GEMM)[T, h] BF16{{cite deepinfer/model_executor/models/v4_modules/mlp.py:444-457}}

The clamp value is swiglu_limit from the checkpoint config ({{cite deepinfer/hugging_face/config.py:282}}). The SwiGLU kernel also receives the top-k weights ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:440}}). A weight before linear2 gives the same result as a weight after it, because linear2 is linear.

Shared experts. With n_shared_experts = s, DeepInfer makes one FFN of width m × s, not s separate FFNs ({{cite deepinfer/model_executor/models/v4_modules/moe.py:24-37}}). The result is the same, because the outputs of shared experts are simply added.

FLOPs. DeepInfer's FLOPs estimator counts, per token and MoE layer ({{cite csrc/engine/flops_estimator.hpp:82-99}}):

FFN:    coef · 3 · h · m · (top_k + n_shared)      coef = 2 (FP8) or 4 (BF16)
router: 4 · h · n_routed_experts                   (BF16 gate GEMM over all logical experts)

The coefficients count FP8-equivalent operations: a BF16 multiply-add counts 4, an FP8 multiply-add counts 2 ({{cite csrc/engine/flops_estimator.hpp:13-20}}). Use the illustrative numbers of "The idea" in FP8. The FFN counts 2 × 3 × 4,096 × 2,048 × 7 = 352 M. The router adds 4 × 4,096 × 64 = 1.0 M. The router is cheap.

Only the memory profile run uses it: it sets the value to 1.8 and then back to 0.0 ({{cite deepinfer/worker/model_runner.py:509-512}}).
  2. Lines 374-377: gate_force_random is a per-token flag in the input metadata. A true flag replaces the gate logits of that token with random values, to balance the MoE load ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:48-50}}). The C++ input builder sets it from a force_load_balance argument ({{cite csrc/engine/input_metadata/prepare_tensor_input_base.cpp:82-85}}).
  3. Lines 381-396: the arguments. bias is the correction bias; image_bias and image_token_mask select the second bias for image tokens. mask is valid_token_mask, which marks the padding tokens. to_physical_map and logical_count come from {{link concepts/eplb | EPLB}}: they map the chosen logical expert to a physical copy.
  4. Lines 397-400: on NVIDIA, deep_gemm.bf16_mega_gate does the gate GEMM and the selection in one kernel. Otherwise the BF16 gate GEMM gives FP32 logits ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:222-227}}), and tile_kernels.moe.moe_topk_gate selects.

The result is topk_idx and topk_weights, both [num_tokens, top_k]. The profiling path shows the same pair from torch.topk ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:335-345}}).

What noaux_tc means. The name comes from DeepSeek-V3: "no auxiliary loss", with a bias per expert. In that design the bias changes only which experts win. The output weights use the scores without the bias, normalized over the chosen experts and multiplied by routed_scaling_factor. DeepInfer passes the bias, the scaling factor and norm_topk_prob to the kernel. The exact kernel math is vendor code, which this site does not explain.

The module docstring defines four counts ({{cite deepinfer/model_executor/models/v4_modules/moe.py:3-7}}):

  • logical = n_routed_experts: what the gate chooses from;
  • extra = n_redundant_experts: extra copies of busy experts;
  • physical = logical + extra, a multiple of ep_size;
  • local = physical / ep_size: the experts on one rank.

The extra count is at least DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS (default 0, {{cite deepinfer/environ.py:114}}). DeepInfer rounds it up until physical is a multiple of ep_size, and logs a warning when it rounds ({{cite deepinfer/model_executor/eplb/__init__.py:21-28}}, {{cite deepinfer/model_executor/model_loader.py:93-100}}). The example scripts set a default of 32 when set_override_experts is on ({{cite examples/_config.py:77-79}}).

Worked example (illustrative expert count). 256 logical experts, extra at least 32, EP = 64.

  1. 256 + 32 = 288. 288 mod 64 = 32, so the padding is 64 − 32 = 32.
  2. extra = 32 + 32 = 64; physical = 320; local = 320 / 64 = 5 experts per rank.
  3. With EP = 8 instead: 288 mod 8 = 0, so extra stays 32, and each rank holds 36 experts.

Memory per rank. The expert weights on one rank are local × (2m·h + m·h) values. With FP4 experts, a value takes half a byte plus a small scale (see {{link learn/number-formats}}). The routed experts in DeepInfer are FP4 ({{cite deepinfer/hugging_face/config.py:256}}, {{cite deepinfer/hugging_face/weights.py:283}}).

Without mega MoE, DeepseekMoE.forward does five steps ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:565-616}}):

  1. Gate: topk_idx, topk_weights (line 574).
  2. Dispatch (DeepEP): each token goes to the ranks that hold its chosen experts. The receiver gets its tokens in one tensor, grouped by local expert, and psum_num_recv_tokens_per_expert, the running sum of tokens per expert (lines 578-585).
  3. Routed experts: two grouped GEMMs over the sorted tokens, with SwiGLU between them (lines 593-598).
  4. Shared expert: runs on the local tokens of this rank, before DeepInfer launches the combine. limit_num_sms makes it leave DEEPINFER_USERBUFFER_COMM_SMS SMs free for DeepEP (lines 601-603).
  5. Combine (DeepEP): each result goes back to the rank of its token. DeepInfer passes the shared-expert output as the bias argument (lines 604-610, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:505}}).

Grouped GEMM. All tokens of all local experts are in one tensor. psum marks where each expert's tokens start, as cu_seqlens does for sequences (see {{link learn/batching}}). One kernel multiplies each group with the weights of its expert ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:109-137}}).

Example: a rank has 4 local experts and receives 10, 0, 7 and 3 tokens. Without padding, the packed tensor has 20 rows and the running sums are 10, 10, 17, 20. Expert 1 has an empty group. DeepInfer also sets an alignment for the groups that the GEMM kernel needs ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:250-252}}).

No capacity per expert. The dispatch gets a maximum number of tokens per rank (the prefill or decode token limit), not per expert ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:476}}). DeepInfer's code sets no capacity per expert.

What can go wrong

  • A checkpoint with another router. DeepInfer asserts sqrtsoftplus, noaux_tc and norm_topk_prob. Another value stops the model build ({{cite deepinfer/model_executor/models/v4_modules/moe.py:58-60}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:164-170}}).
  • An unsupported precision mix. Only FP8 × FP4, FP8 × FP8 and BF16 × BF16 are allowed for activations × expert weights ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:177-182}}). An FP4 path also needs a checkpoint that was trained for FP4 ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:60}}).
  • Experts that do not divide by EP. Physical experts must be a multiple of ep_size ({{cite deepinfer/model_executor/models/v4_modules/moe.py:94-95}}). The loader pads the extra count, so the assert only fails if you bypass the loader.
  • Uneven load. A hot expert makes its rank slow, and all EP ranks wait. EPLB moves and copies experts to fix this; see {{link concepts/eplb}}.
  • A profiling knob that does nothing. DEEPINFER_FORCE_IMBALANCE_RATIO replaces real routing with random choices ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:367-371}}). But the memory profile run sets it to 1.8 and then to 0.0 ({{cite deepinfer/worker/model_runner.py:509-512}}). So a value that you set in the environment never takes effect in normal steps.

Why it matters. MoE decides the shape of a DeepInfer deployment. The experts need memory on many ranks, the tokens need an all-to-all, and the batch per expert decides if the experts are memory-bound. Expert parallelism, EPLB and mega MoE all exist because of MoE.

An MoE layer has 32 routed experts, top-4 and 2 shared experts. How many experts does one token use? What fraction of the expert weights is that?

4 + 2 = 6 experts, out of 32 + 2 = 34 stored: 6 / 34 ≈ 18 % (if all experts have the same size).

 A router gives the top-2 experts the scores 0.6 and 0.2. What are the normalized weights? Why does this matter for the output?

0.6 / 0.8 = 0.75 and 0.2 / 0.8 = 0.25. They sum to 1, so the size of the MoE output does not depend on how high the scores are. DeepInfer asserts norm_topk_prob ({{cite deepinfer/model_executor/models/v4_modules/moe.py:56-60}}); the vendor kernel then also applies routed_scaling_factor.

 Where does DeepInfer get the number of experts and top-k? Are they fixed in the code?

No. They come from the checkpoint config: n_routed_experts, n_shared_experts, num_experts_per_tok and moe_intermediate_size ({{cite deepinfer/hugging_face/config.py:164-174}}). The gate reads num_experts_per_tok as its top-k ({{cite deepinfer/model_executor/models/v4_modules/moe.py:52-53}}).

 A model has 128 logical experts. You run EP = 48 and set DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS=16. How many physical experts are there, and how many on each rank?

128 + 16 = 144. 144 mod 48 = 0, so the padding is 0 ({{cite deepinfer/model_executor/eplb/__init__.py:27-28}}). Physical = 144, local = 144 / 48 = 3 experts per rank.

 A decode step has 512 tokens, top-8 and 256 experts. On average, how many tokens does one expert get, and is its GEMM memory-bound (ridge point about 281)?

512 × 8 / 256 = 16 tokens per expert. The intensity of a BF16 GEMM is about the number of rows, so about 16, far below 281: strongly memory-bound. Larger batches or fewer experts per rank help; see the deep dive "What the deployment notes say" on {{link learn/parallelism}}.
