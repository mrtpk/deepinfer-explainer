It writes text by repeating this, one token at a time.

The idea

Text in, one token out

A large language model ({{term llm | LLM}}) does not work on letters or words. It works on {{term token | tokens}}: small pieces of text, each with an integer id. The page {{link learn/tokens}} shows how text becomes ids.

The model is a mathematical function with a fixed list of inputs and outputs:

  • Input: a list of token ids, for example the ids of "The cat sat on".
  • Output: one probability for each token in the {{term vocabulary}}. The vocabulary is the list of all tokens that the model knows. A modern vocabulary often has between 32,000 and 256,000 tokens.

Take "The cat sat on". The model can give "the" a probability of 0.41, "a" 0.22 and "his" 0.09. Every other token gets a very small probability. These numbers are made up, but real outputs look like this. The model does not give one answer. It gives a probability distribution over all possible next tokens.

Writing text is a loop

To write an answer, an inference engine runs the model in a loop. This kind of generation is {{term autoregressive}}:

  1. Run the model on all tokens so far. Get the probabilities of the next token.
  2. Select one token from these probabilities. This is {{term sampling}}. The page {{link learn/sampling}} explains the rules.
  3. Add the selected token to the end of the input.
  4. Stop if the token is the end-of-sequence token ({{term eos-token | EOS}}), or if the answer has the maximum number of tokens. Else go back to step 1.

So an answer of 200 tokens needs 200 runs of the model. Each run makes exactly one new token. (Speculative decoding can make more than one token per run. DeepInfer uses it, but the idea stays the same.)

Where the knowledge is

The model has billions of learned numbers, the {{term model-weights | weights}}. Training set them: the model read a very large amount of text and learned to predict the next token. All the "knowledge" of the model is in these numbers.

Generation does not change the weights. Each run reads all of them from device memory and uses them for the math. This is why LLM inference needs large and fast {{term accelerator | accelerators}}. It is also why an engine such as DeepInfer uses each read of the weights for many requests at the same time.

An everyday comparison

Think of the word suggestions on a phone keyboard. You type "See you", and the keyboard suggests "soon", "tomorrow" or "later". When you tap one word, the keyboard adds it and suggests the next word. An LLM does the same thing, one token at a time.

The comparison stops here. A keyboard looks at the last few words and shows three choices. An LLM looks at all the text so far, often thousands of tokens. It gives a probability to every token in its vocabulary. Then the sampler, not the user, makes the choice.

What an inference engine adds

The loop above is simple. An engine such as DeepInfer makes it fast for many users at the same time:

  • It keeps the intermediate results of earlier tokens, so each run computes only the new token. This memory is the {{term kv-cache | KV cache}} ({{link learn/kv-cache}}).
  • It splits the work into two phases: {{term prefill}} reads the whole prompt once, and each {{term decode}} step adds one token ({{link learn/prefill-decode}}).
  • It runs the tokens of many requests in one step, so one read of the weights serves all of them ({{link learn/batching}}).
  • A {{term scheduler}} decides in each step which requests run.

Deep dive

The sections below give the full detail. Open them one at a time.

Write the tokens of a text as x1, x2, …, xn. An LLM gives the probability of the whole text as a product of next-token probabilities (the chain rule of probability):

P(x1, x2, ..., xn) = P(x1) · P(x2 | x1) · P(x3 | x1, x2) · ... · P(xn | x1 ... xn-1)

The model computes each factor P(xt+1 | x1 … xt) in the same way:

  1. Input: token ids, an integer tensor of shape [T].
  2. The layers of the model make one {{term hidden-state}} vector per token: shape [T, d], where d is the hidden size.
  3. The output head multiplies each hidden state by a matrix of shape [d, V], where V is the vocabulary size. The result is the {{term logits}}: shape [T, V], one raw score per token.
  4. {{term softmax | Softmax}} turns the logits of one row into probabilities: pi = exp(zi) / Σj exp(zj).

Row t of the logits predicts token t + 1. During training, the model uses all rows: every position predicts its next token. During generation, only the last row matters, because only that row predicts a token that does not exist yet.

DeepInfer uses this fact. In a prefill step, the sampler selects only the last row of each sequence ({{cite csrc/engine/prepare_sample.cpp:197}}). The sampler then computes the logits only for the selected rows, in float32 ({{cite deepinfer/model_executor/layers/sampler.py:140-142}}, {{cite deepinfer/model_executor/layers/sampler_utils.py:25}}). A request with prompt logprobs is an exception: it also needs the other rows. For a prompt of 1,000 tokens and V = 129,280 (inferred, see {{link learn/tokens}}), this saves 999 × 129,280 ≈ 129 million logits per sequence.

Worked example. These probabilities are made up. Take P("The") = 0.02, P("cat" | "The") = 0.01, P("sat" | "The cat") = 0.10, P("on" | "The cat sat") = 0.50:

P("The cat sat on") = 0.02 × 0.01 × 0.10 × 0.50 = 0.00001
log P               = ln 0.02 + ln 0.01 + ln 0.10 + ln 0.50
                    = −3.912 − 4.605 − 2.303 − 0.693 = −11.513

Products of many small numbers become too small for floating point. So engines work with the sum of log probabilities. One such value per token is a {{term logprob}}. DeepInfer can return the logprob of each output token and of the best alternatives (top_logprobs, {{cite deepinfer/sampling_params.py:31-33}}).

A common rule of thumb: one forward pass costs about 2 × N floating-point operations (FLOPs) per token. N is the number of weights that the token uses. Each weight takes part in one multiply and one add.

The rule leaves out attention. Attention grows with the length of the text. For long texts it adds a large part of the work. The page {{link learn/attention}} gives its cost.

Illustrative example (not a DeepInfer model): a dense model with 10 billion weights and 2-byte numbers.

  1. Compute per token: 2 × 10 × 109 = 2 × 1010 FLOPs.
  2. Weights to read per step: 10 × 109 × 2 bytes = 20 GB.
  3. An answer of 500 tokens needs 500 steps. Each step reads the 20 GB again, if the engine runs this one request alone.

So the engine reads the same weights again and again. If 64 requests share each step, one read of 20 GB serves 64 tokens. This is the main reason for {{link learn/batching | batching}}.

Mixture of experts. A {{term moe | MoE}} model has many more weights than one token uses. A router selects a few experts per token. So N in the rule is the number of active weights per token, not all weights. DeepSeek V4.1, the model of DeepInfer, is an MoE model ({{link learn/moe}}).

The step results. Each step() returns output objects. The loop clones each one, because the engine reuses their memory in the next step ({{cite deepinfer/entrypoints/llm.py:179-182}}). With zero-overhead scheduling ({{term zos | ZOS}}), a step returns the results of the previous step. So after the last step, the loop calls flush_inflight_reqs() once to collect the last results ({{cite deepinfer/entrypoints/llm.py:178}}). The page {{link concepts/zero-overhead-scheduling}} explains why.

Edge cases:

  • max_tokens=0 becomes 1 ({{cite deepinfer/sampling_params.py:70-71}}). A negative value raises ValueError ({{cite deepinfer/sampling_params.py:100-101}}).
  • first_n_token_no_eos=1 forbids EOS as the first output token. The sampler sets the EOS logit to −∞ in the prefill step ({{cite deepinfer/model_executor/layers/sampler.py:183-185}}). The engine always sets the EOS id of the request to the EOS id of the tokenizer ({{cite deepinfer/engine/llm_engine.py:527}}).
  • A prompt that is longer than the prompt limit never runs. It ends with the reason "prompt_length_exceeded" ({{cite csrc/engine/scheduler.hpp:377-384}}, {{cite csrc/engine/sequence.hpp:53-54}}).

What can go wrong

  • Very short answers. The default max_tokens is 16 ({{cite deepinfer/sampling_params.py:53}}). Set a larger value for real answers.
  • Answers that never end early. With ignore_eos=True, every request runs to max_tokens. Benchmarks use this on purpose; normal use does not.
  • An empty prompt. add_request raises ValueError("prompt must not be empty") ({{cite deepinfer/engine/llm_engine.py:553-554}}).
  • A bad token id. If you pass a token id below 0, or at or above the valid limit, add_request logs an info message and returns None. It does not raise ({{cite deepinfer/engine/llm_engine.py:580-589}}). The limit is vocab_size, plus 5 image ids if the request has multimodal data ({{cite deepinfer/multimodal_tokens.py:28}}).

Why it matters. Every later page builds on this loop. Prefill and decode are the first run and the later runs. The KV cache saves the work of earlier tokens. Batching and the scheduler decide which loops share a step. Sampling is step 2 of the loop.

An LLM gets the tokens of "The cat sat on". What does one run of the model give back?

One probability for every token of the vocabulary: the chance that this token comes next. The model does not give one word. A separate sampling step selects one token from these probabilities.

 An answer has 300 tokens. How many runs of the model does the plain loop need, without speculative decoding?

300. Each run makes exactly one new token, which becomes part of the input of the next run.

 You call llm.generate("Hello") with no sampling parameters. Why is the answer so short?

generate() uses SamplingParams() ({{cite deepinfer/entrypoints/llm.py:125-127}}). Its default max_tokens is 16 ({{cite deepinfer/sampling_params.py:53}}). The scheduler stops the request with the reason "length" after 16 output tokens ({{cite csrc/engine/scheduler.hpp:1048-1051}}).

 A prompt has 2,000 tokens, and the vocabulary has 129,280 tokens (inferred). How many logits does the DeepInfer sampler compute for this sequence in its prefill step, and why not 2,000 rows?

One row: 129,280 logits. Only the last row predicts a new token. The sampler input selects only the last token row of each prefill sequence ({{cite csrc/engine/prepare_sample.cpp:197}}). Sampler.forward gathers these rows and only then computes the logits ({{cite deepinfer/model_executor/layers/sampler.py:140-142}}). The other 1,999 rows would need 1,999 × 129,280 ≈ 258 million float32 values. (This assumes that the request asks for no prompt logprobs.)
