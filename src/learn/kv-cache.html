DeepInfer stores the cache in blocks of 128 tokens. scripts: viz/kv_allocator.js --- The KV cache keeps the keys and values of earlier tokens in device memory, so the model computes them only once for each token.

The idea

Why keep keys and values?

An {{term llm | LLM}} writes text one {{term token}} at a time. For each new token, every {{term attention}} layer compares the query of the new token with the keys of all earlier tokens. Then it mixes the values of those tokens ({{term query-key-value}}). The page {{link learn/attention}} shows this step by step.

The keys and values of an earlier token never change. A token looks only at itself and at the tokens before it, so a later token cannot change them. Thus the model can compute them once and keep them. The device memory that keeps them is the {{term kv-cache}}.

  • Without a cache, the model must compute the keys and values of the whole text again for each new token.
  • With a cache, the model computes keys and values only for the new token. It reads the old ones from memory and adds the new ones at the end.

The {{term prefill}} step fills the cache for all prompt tokens. Each {{term decode}} step then adds one token. The page {{link learn/prefill-decode}} explains the two phases.

A worked example

Take a prompt of 3 tokens, and let the model write 5 new tokens. The table counts how many key and value rows one layer computes in each step.

StepTokens in the textRows computed, no cacheRows computed, with cache
prefill (writes token 4)333
decode 1 (writes token 5)441
decode 2 (writes token 6)551
decode 3 (writes token 7)661
decode 4 (writes token 8)771
Total257

For a prompt of p tokens and n new tokens, the totals are:

no cache:    n·p + n·(n − 1)/2
with cache:  p + (n − 1)

p = n = 1,000:
no cache:    1,499,500 rows
with cache:      1,999 rows

That is about 750 times less work for the keys and values, in every layer. The work without a cache grows with the square of the length.

What the cache holds. Here is one layer and one head, with vectors of 2 numbers. The prompt is "The cat sat". The next token is "on", and its query is q = (1, 2). The score of a row is q·k.

Cache rowTokenKeyValueScore q·k
1The(1, 0)(2, 0)1·1 + 2·0 = 1
2cat(0, 1)(0, 2)1·0 + 2·1 = 2
3sat(1, 1)(1, 1)1·1 + 2·1 = 3
4 (new)on(2, 1)(0, 3)1·2 + 2·1 = 4

In the decode step for "on", the model computes only row 4. It reads rows 1 to 3 from the cache. Softmax turns the four scores into weights, and the weights mix the four values. Rows 1 to 3 stay the same in every later step.

The numbers are made up, and a real head has 64 to 512 numbers per vector. A real model also scales the scores before softmax. The page {{link learn/attention}} shows the full calculation.

An everyday comparison

Think of a long meeting with a secretary who writes the minutes. Before each new speaker talks, the speaker reads the minutes. Nobody repeats what they said before. The secretary only adds the new speech at the end. The minutes are the KV cache.

The comparison stops here: minutes are a summary, but the KV cache is not. It keeps one entry for every token, in every layer. So it grows with the text, and each step still reads all of it.

How much memory does it use?

For standard multi-head attention, one layer stores one key and one value for each token and each {{term attention-head | KV head}}:

bytes per token per layer = 2 × n_kv_heads × head_dim × bytes_per_number
bytes for one sequence    = bytes per token per layer × n_layers × n_tokens

The 2 counts one key and one value. Here is a worked example for a generic model, not DeepInfer: 32 layers, 32 KV heads, head_dim 128, BF16 numbers (2 bytes).

  1. One token, one layer: 2 × 32 × 128 × 2 = 16,384 bytes = 16 KiB.
  2. One token, 32 layers: 16 KiB × 32 = 512 KiB.
  3. One sequence of 4,096 tokens: 512 KiB × 4,096 = 2 GiB.
  4. 64 such sequences: 128 GiB. That is more than the memory of one 80 GB GPU.

So device memory, not compute, often limits how many sequences can run at the same time. This is why engines save cache memory in many ways.

DeepInfer's model has one KV head ({{cite deepinfer/worker/cache_engine.py:624}}). It stores one entry of 512 numbers for each token, or for each 2 tokens, per layer. One entry takes 528 bytes in 8-bit format or 288 bytes in 4-bit format ({{cite deepinfer/model_executor/layers/tilelang_ops/cache_common.py:109-128}}). The Hugging Face loader uses the 4-bit format by default ({{cite deepinfer/hugging_face/config.py:302-303}}). See the deep dive and {{link concepts/kv-compression}}.

Blocks and block tables

The engine does not know how long a sequence becomes. One simple plan is to reserve the maximum length for each sequence. But most sequences are shorter, so most of the reserved memory stays empty.

A {{term paged-kv-cache}} solves this. It splits the cache memory into {{term kv-block | blocks}} of a fixed number of tokens. A sequence gets one block at a time, when it needs one. The block can be anywhere in the pool. A {{term block-table}} per sequence records which physical block holds which part of the sequence:

logical block = position // block_size
offset        = position %  block_size
slot          = block_table[logical block] × block_size + offset

This gives two advantages:

  • Only the last block of a sequence can be partly empty. The waste is less than one block per sequence. This waste is called internal {{term fragmentation}}.
  • Any free block fits any sequence. So there are no free gaps that are too small to use.

Operating systems use the same idea for virtual memory: a page table maps virtual pages to physical pages.

When the blocks run out: preemption

In each decode step, a sequence with a full last block needs one new block. If the pool has no free block, the scheduler must take blocks away from a running sequence. This is {{term preemption}}. The engine then has two choices for that sequence:

  • Stop it. The request ends early, with an error reason.
  • Recompute it later. The sequence goes back to the waiting queue. Later, a new prefill computes the keys and values of all its tokens again. The output stays correct, but the request takes more time.

DeepInfer can do both. A configuration flag selects the behavior. The deep dive below shows which sequence DeepInfer selects, and the defaults.

The simulator copies these DeepInfer rules:

  • Block 0 is never used.
  • A new block comes from the front of the free list. Freed blocks go to the back.
  • A prefill reserves all blocks of the prompt at once.

The simulator leaves out: speculative (draft) tokens, in-flight tokens of zero-overhead scheduling, state slots, shared prefix blocks, the limits on batch size, and data parallelism. In DeepInfer a step is a prefill step or a decode step. In the toy, waiting requests start when you add or finish a request, and at the start of each decode step.

In the code

This is a basics page, so this part is short. The pages {{link concepts/paged-kv-cache}} and {{link concepts/scheduler}} go further.

Step 1: one block holds 128 tokens

The block size is fixed in the model metadata. It is not a command-line choice:

The deployment notes use the same number: the prefix-cache hit length is "a multiple of the 128-token block size" ({{cite doc/inference_deployment_qa.md:191}}).

Step 2: the BlockManager hands out blocks

The C++ {{term block-manager}} keeps the free blocks in a linked list. allocate() takes the first free block. free() puts a block back when no sequence uses it:

Each {{term sequence}} keeps its block table as a std::vector<int> ({{cite csrc/engine/sequence.hpp:200-207}}). The number of blocks that a sequence needs is a round-up division by the block size ({{cite csrc/engine/sequence.hpp:291-293}}).

Step 3: the cache has several parts

CacheEngine allocates the memory. Then it gives each attention layer a KVCache object with views into that memory:

  • ca_cache: the main compressed cache. It is paged: one row per block.
  • ica_cache: the keys of the indexer, for sparse layers. It is paged in the same blocks.
  • swa_cache: the {{term sliding-window-attention}} cache. It is not paged. Each sequence has a fixed ring of recent tokens in its {{term state-slot}}.
  • ca_state: per-sequence float32 state for compression with ratio 2. It is also in the state slot.
  • ica_state: float32 state for an indexer without use_kproj ({{cite deepinfer/worker/cache_engine.py:123-127}}). The Hugging Face loader always sets use_kproj=True ({{cite deepinfer/hugging_face/config.py:122}}). So in practice ica_state is None.

So DeepInfer has two pools: paged KV blocks, and one state slot per running sequence. It makes one BlockManager for each pool ({{cite deepinfer/engine/llm_engine.py:265-266}}).

Step 4: the cache size comes from a memory profile

At start-up, each rank runs the model once on dummy inputs and measures the peak memory. The rest of the memory budget becomes KV blocks:

Subtract the reserved state cache, which has a fixed size. State store and copy buffer, so it needs twice the size.

Compare this with 16,384 bytes per token and layer in the generic example. FP4 uses about 57 times less, and MXFP8 about 31 times less.

Indexer keys. A sparse layer (index_topk > 0) also stores FP4 indexer keys: index_head_dim / 2 + index_head_dim / 32 bytes per entry, with the same 128 // n entries per block ({{cite deepinfer/worker/cache_engine.py:73-80}}, {{cite deepinfer/worker/cache_engine.py:428-439}}). A layer can reuse the indexer keys or the main cache of an earlier layer. Then it adds no bytes ({{cite deepinfer/worker/cache_engine.py:429-431}}, {{cite deepinfer/worker/cache_engine.py:448-449}}); see {{link concepts/cross-layer-kv-sharing}}.

Sliding-window ring. Per sequence and SWA layer: (window + backtracking) × 528 bytes, a fixed size, padded to 32 bytes ({{cite deepinfer/worker/cache_engine.py:88-93}}, {{cite deepinfer/worker/cache_engine.py:274-275}}). The backtracking value is at least DEEPINFER_USE_NEXTN_DECODE + 1 = 6 ({{cite deepinfer/environ.py:129-132}}). If DEEPINFER_PREFILL_STORE_EXTRA_STATE is on (default off), the ring in the state slot is longer by DEEPINFER_PREFILL_STORE_EXTRA_SIZE tokens, default 128 ({{cite deepinfer/worker/cache_engine.py:101-110}}). The deployment notes give 134 = 128 (window) + 6 (backtracking) ({{cite doc/inference_deployment_qa.md:191}}), and the stored total: 20 layers × 134 tokens × 528 B = 1,415,040 B per sequence ({{cite doc/inference_deployment_qa.md:169}}).

Before each step, the engine computes for each new token where the kernels must write its cache entry. For a prefill step, and for a decode step without ZOS, C++ code does this. ZOS is on by default in the NORMAL engine ({{cite deepinfer/engine/arg_utils.py:51-55}}). With ZOS, a decode step uses a different function: the kernel prepare_v4_decode_metadata computes the decode slot mapping on the device ({{cite deepinfer/model_executor/model_metadata_utils.py:143-144}}, {{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:336-367}}). The C++ rules below show the arithmetic. For compressed layers:

  1. Line 42: compressed_block_size = block_size / n, the entries per block (128 or 64).
  2. Line 58: in a prefill, entry index j runs over the new compressed entries. Entry j covers tokens j·n to j·n + n − 1.
  3. Line 60: slot = block_table[j / compressed_block_size] × compressed_block_size + j % compressed_block_size. This is the rule from "Blocks and block tables", in units of entries.

In a decode step, a C2 layer writes a new entry only when (position + 1) % n == 0. Then the 2-token group is complete. Other tokens get slot -1 (no write) ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:80-91}}).

Worked example. Position 1,000 in a C2 layer, with block_table[7] = 42:

  1. (1,000 + 1) % 2 = 1, so a decode step writes nothing for this token. Position 1,001 completes the group.
  2. Entry index: 1,001 // 2 = 500. Entries per block: 128 / 2 = 64.
  3. Logical block: 500 // 64 = 7. Offset: 500 % 64 = 52.
  4. Slot: 42 × 64 + 52 = 2,740. The row is ca_cache[42, 52].

Sliding-window ring. The SWA slot uses the state slot, not the block table:

Example: state_id 3, ring size 134, position 1,000: 3 × 134 + (1,000 % 134) = 402 + 62 = 464. Line 103 writes only the last 134 tokens of a long prefill. Older tokens fall out of the window, so the code does not write them.

How many blocks. get_num_blocks() is ceil((len + in-flight tokens + draft tokens) / 128) ({{cite csrc/engine/sequence.hpp:291-293}}). A prompt of 1,000 tokens with 5 draft tokens needs ceil(1,005 / 128) = 8 blocks: 1,024 token positions, 19 of them empty.

The free list is a doubly linked list inside a std::vector. Index 0 is the "no block" marker, so block 0 is never given out:

NOTE: GPU block 0 is not used, so 0 here means "empty". "Too few GPU blocks: ".
  • Usable blocks = num_gpu_blocks − 1. The stats logger also subtracts 1 ({{cite deepinfer/engine/stats_logger.py:410}}).
  • Order. allocate() pops the head; free() pushes the block to the tail (lines 82-103 above). free_blocks_nolock frees the block table in reverse order ({{cite csrc/engine/block_manager.hpp:147-149}}). So the first block of the table goes to the very back of the free list.
  • Reference counts. A block can belong to more than one sequence. A forked sequence pins the blocks of its parent: ref_count goes up ({{cite csrc/engine/block_manager.hpp:88-93}}, {{cite csrc/engine/scheduler.hpp:1108-1114}}). A block goes back to the free list only at ref_count == 0.
  • Can it fit? can_allocate_nolock(n) returns NEVER if n >= num_blocks, OK if enough blocks are free, else LATER ({{cite csrc/engine/block_manager.hpp:128-136}}).
  • Two managers. The engine makes one BlockManager for KV blocks and one for state slots ({{cite deepinfer/engine/llm_engine.py:265-266}}). A sequence needs a block budget and a free state slot: if the slot pool is empty, the block check also gives LATER ({{cite csrc/engine/scheduler.hpp:194-201}}).
  • Locks. BlockManagerMutexAcquire locks the state manager first, then the block manager, and unlocks in the opposite order ({{cite csrc/engine/block_manager.hpp:189-204}}).

When does a sequence get blocks?

  1. Prefill: the first chunk of a prompt reserves blocks for the whole sequence at once with allocate_seq ({{cite csrc/engine/scheduler.hpp:516-520}}, {{cite csrc/engine/block_manager.hpp:207-214}}).
  2. Decode: _append_slot adds one block when get_num_blocks() grows. It frees extra blocks when the count goes down, for example when the number of draft tokens goes down ({{cite csrc/engine/scheduler.hpp:816-828}}).
  3. End: finalize_seq calls scheduler.free_seq, which frees the state slot and all blocks ({{cite deepinfer/engine/llm_engine.py:804-806}}, {{cite csrc/engine/scheduler.hpp:738-744}}).

Preemption happens only in a decode step, in _schedule_decode:

  1. Lines 624-625: sort running by the number of output tokens, the most first.
  2. Line 629: take sequences from the end of the list: the sequence with the fewest output tokens goes first.
  3. Lines 630-634: if the pool has no free block, the scheduler preempts sequences from the front of the list (the most output tokens). It stops when one block is free. The check runs before each sequence, also when that sequence does not need a new block.
  4. Lines 635-637: if a block is free, _append_slot gives the sequence its block (if it needs one), and the sequence runs in this step.
  5. Lines 638-640: if only this sequence is left and there is still no free block, the scheduler preempts this sequence.

The comment above the function says that the scheduler preempts the sequence with the shortest output (translated, {{cite csrc/engine/scheduler.hpp:557}}). The code preempts from the front of a list sorted with the longest output first. This page describes the code. The comment in sequence.hpp agrees with the code. Translated: "If the KV cache is about to overflow, we stop the task that uses the most KV cache." ({{cite csrc/engine/sequence.hpp:56}}).

What happens to the victim:

COMPLETION together with !stop_preempted_request is already rejected in the constructor. Preempted structured-output requests do not support recompute yet; they stop. Reset the state of the sequence that changes in each step (cache.num_tokens, in-flight counts, MTP state); the list is in Sequence::reset_for_recompute.
  • Stop (stop_preempted_request is true, or the structured-output status is not 0): status FINISHED_PREEMPTED, finish reason "insufficient_system_resource" ({{cite csrc/engine/sequence.hpp:55-56}}).
  • Recompute: the sequence keeps its tokens (prompt and output so far), goes to the front of the waiting queue, and frees all blocks. The next prefill computes the cache for all its tokens again.
  • DeepInfer has no swap to CPU memory here. The status SWAPPED exists in the enum ({{cite csrc/engine/sequence.hpp:33}}), but _preempt never sets it.

A watermark protects decode. A NORMAL engine starts a new prefill only when cache usage is 90 % or less ({{cite csrc/engine/scheduler.hpp:80}}, {{cite csrc/engine/scheduler.hpp:313}}). Usage is (num_blocks − free) / num_blocks, so reserved block 0 counts as used ({{cite csrc/engine/scheduler.hpp:830-835}}).

Worked example. The pool has 0 free blocks. Three sequences run: R1 with 50 output tokens, R2 with 3, R3 with 20. The sorted list is [R1, R3, R2]. R2 goes first. No block is free, so the scheduler preempts R1. R1 frees its blocks. Then R2 and R3 run. With the offline LLM class, R1 waits at the front of the queue for a new prefill.

  2. Line 225: profile_run runs one forward pass with max_num_seqs dummy sequences and a temporary KV cache ({{cite deepinfer/worker/model_runner.py:444-511}}).
  3. Lines 228-234: peak = peak PyTorch memory + device memory that PyTorch does not manage.

  5. Lines 237-244: subtract two copies of the state buffer (store buffer and copy buffer).

The docstring of _init_cache says that the engine takes the minimum number of blocks over all workers ({{cite deepinfer/engine/llm_engine.py:426-428}}). The code takes the sum divided by the world size, which is the average.

Worked example. The numbers are made up, not measured. The device has 80 GiB, utilization is 0.90 and the peak is 52 GiB. One block takes 2 MiB, one state slot takes 1.5 MiB, and max_num_seqs is 256.

  1. Budget: 80 × 0.90 − 52 = 20 GiB = 20,480 MiB.
  2. State slots: int(256 × 1.2) + 1 = 308 ({{cite deepinfer/worker/cache_engine.py:201-202}}). Two copies: 2 × 308 × 1.5 MiB = 924 MiB.
  3. Blocks: (20,480 − 924) / 2 = 9,778 blocks, or 9,778 × 128 = 1,251,584 token positions.
  4. Check: the engine stops if runtime_max_model_len is more than 0.8 × 1,251,584 = 1,001,267 tokens ({{cite deepinfer/engine/llm_engine.py:445-451}}).

Allocation. CacheEngine.allocate_gpu_cache then makes two raw uint8 buffers with cuda_utils.alloc_tensor: gpu_blocks with shape [num_gpu_blocks, bytes_per_block] and gpu_states with shape [num_state_slots, state_bytes] ({{cite deepinfer/worker/cache_engine.py:910-916}}, {{cite deepinfer/worker/cache_engine.py:937-958}}). The comment on line 936 shows a 6-D shape. It does not describe this layout. Each layer then gets strided views into one row per block, so one block id serves all layers ({{cite deepinfer/worker/cache_engine.py:452-458}}). The row length is padded to lcm(128, bytes_per_token) ({{cite deepinfer/worker/cache_engine.py:479-484}}).

What can go wrong

  • No memory for the cache. If the profile leaves no budget, start-up stops with "No available memory for the cache blocks" ({{cite deepinfer/engine/llm_engine.py:441-444}}). Increase gpu_memory_utilization or decrease max_num_seqs.
  • Cache too small for the context length. Start-up stops if runtime_max_model_len is more than 80 % of all block tokens ({{cite deepinfer/engine/llm_engine.py:445-451}}).
  • A prompt that can never fit. If a prompt needs num_gpu_blocks blocks or more, the scheduler logs "exceeds the capacity of block_manager" and ends the request as ignored ({{cite csrc/engine/scheduler.hpp:386-396}}).
  • Preempted requests. With stop_preempted_request on, a long request can end early with the reason insufficient_system_resource. With recompute, it gets a new prefill, so its latency goes up. Structured-output requests with a status that is not 0 always stop ({{cite csrc/engine/scheduler.hpp:770-779}}).
  • Free blocks, but the request still waits. A new request also needs a free state slot, and a prefill starts only at 90 % cache usage or less ({{cite csrc/engine/scheduler.hpp:194-201}}, {{cite csrc/engine/scheduler.hpp:313}}).

Why it matters. The KV cache decides how many requests can run at the same time, and how long they can be. Most memory settings of an inference engine are really KV cache settings. When you read about compression, sliding windows or the scheduler, ask: how does this change the bytes per token, or the number of free blocks?

Why can the model keep the keys and values of earlier tokens? Why does it not compute them again?

A token looks only at itself and at earlier tokens. A later token cannot change the keys and values of an earlier token. So they stay correct, and the model can compute them once and keep them in the KV cache.

 A generic model (not DeepInfer) has 40 layers, 8 KV heads, head_dim 128 and FP16 numbers. How much KV cache does one sequence of 8,192 tokens need?

Per token and layer: 2 × 8 × 128 × 2 = 4,096 bytes. Per token: 4,096 × 40 = 163,840 bytes = 160 KiB. For 8,192 tokens: 160 KiB × 8,192 = 1,310,720 KiB = 1.25 GiB.

 In DeepInfer, a C1 layer must write the cache entry of the token at position 1,000. The block table of the sequence has block_table[7] = 42. Which slot does the entry go to?

Block size 128, ratio 1, so 128 entries per block. Logical block 1,000 // 128 = 7, offset 1,000 % 128 = 104. Slot = 42 × 128 + 104 = 5,480 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:85-86}}).

 A decode step starts with 0 free blocks. Three sequences run: R1 has 50 output tokens, R2 has 3, R3 has 20. Which sequence does DeepInfer preempt, and what happens to it in the offline LLM class?

The scheduler sorts by output length, longest first: [R1, R3, R2]. It serves R2 first. No block is free, so it preempts from the front: R1 ({{cite csrc/engine/scheduler.hpp:624-634}}). The offline LLM class sets stop_preempted_request=False ({{cite deepinfer/entrypoints/llm.py:68}}). So R1 frees its blocks and goes to the front of the waiting queue, and a later prefill recomputes its cache ({{cite csrc/engine/scheduler.hpp:781-787}}).

 The pool has many free KV blocks, but a new request does not start. Give two reasons from the DeepInfer code.

(1) The request also needs a free state slot. If the state pool is empty, the scheduler treats the block check as LATER ({{cite csrc/engine/scheduler.hpp:194-201}}). (2) A NORMAL engine starts a prefill only when cache usage is 90 % or less ({{cite csrc/engine/scheduler.hpp:313}}). Other limits also apply, for example max_num_seqs.
