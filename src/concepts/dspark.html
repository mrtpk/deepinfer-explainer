With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time. --- DFlash drafts 5 tokens and predicts the chance that each one passes. DSpark then checks only the drafts that are worth their cost.

The idea

{{term dspark}} is the name of the {{term speculative-decoding}} design of DeepInfer ({{cite README.md:13}}, {{cite README.md:24}}). It has two parts:

  1. The draft model DFlash. {{term dflash | DFlash}} is a small model with its own decoder layers. It reads hidden states of the main model and makes 5 {{term draft-token | draft tokens}} per request in one pass. It also has a {{term confidence-head}} that predicts, for each draft, the chance that the main model accepts it.
  2. Confidence-scheduled verification. Without it, every request sends all 5 drafts to the next step. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler uses the confidences to choose the {{term verification-length}} of each request. A draft that will probably fail costs device time and gives nothing.

The deployment Q&A gives the reason: "fixed-length verification wastes verification compute on low-probability tokens" ({{cite doc/inference_deployment_qa.md:243}}). On EP64/DP64 benchmark data, DSpark checks about 30 % fewer drafts per step (5.00 → 3.2–4.4). The accepted length stays almost the same (3.29 compared with 3.20). The estimated gain is +4–7 % throughput at about 60 sequences per rank ({{cite doc/inference_deployment_qa.md:247}}).

An everyday comparison. Think of a cashier with a queue of customers. Each customer hands over 5 coupons in a fixed order. A coupon counts only if all coupons before it were valid. Each check takes time. The cashier knows from experience how likely each coupon is to be valid. To give the most value per minute, the cashier checks the coupons that will probably count and hands the others back unchecked. The comparison stops being true in two places. The "experience" is a neural network head, not memory. And the time per check comes from a curve that DeepInfer measures on the real hardware.

In the code

Step 1: DFlash is built from extra layers of the checkpoint

The checkpoint has more layers than the main model. DFlash takes the layers after the main layers, the embedding layer and the LM head layer, and checks that each one is a DFlash block:

Main model layers + embedding layer + LM head layer. The model has no MTP layers, or the wrong number of layers. Number of proposals that each sequence makes. Dimension of the predicted logprobs. With force_topk, only force_topk values, plus their index. The DFlash module should have nextn_predict layers.

DFlash shares the embedding and the LM head of the main model ({{cite deepinfer/model_executor/models/deepseek.py:300-302}}). Its number of layers comes from num_nextn_predict_layers in the checkpoint config. The number of drafts comes from DEEPINFER_USE_NEXTN_DECODE (line 103). A comment says that the two numbers are independent ({{cite deepinfer/model_executor/models/deepseek.py:301}}).

Step 2: the main forward pass writes the draft model's keys

Some main layers, listed in dspark_target_layer_ids, copy their residual stream into one buffer dflash_input [total_q, hidden × n_target] ({{cite deepinfer/model_executor/models/deepseek.py:172-174}}, {{cite deepinfer/model_executor/models/decoder_layer.py:144-145}}). After the last layer, update_main_cache turns these features into keys:

The row layout of input_metadata must match dflash_input (the consumer view with YOCO compaction). In decode it replays with the main model CUDA graph. The accept results do not exist yet, so all tokens are written with slot_mapping_store_swa. The rejected draft positions are exactly the positions where forward_drafts later writes draft keys, and they are overwritten before any read, so no mask by accept result is needed. With prefill CP > 1, dflash_input has the per-rank mirror layout; each layer all-gathers and writes in the original varlen order.
  1. Line 219: a linear projection from hidden × n_target to hidden, then an RMSNorm.
  2. Line 220: main_kv_proj makes one key of head_dim values per DFlash layer: [total_q, n_layers, head_dim].
  3. Lines 221-228: each DFlash layer writes its key into its own sliding-window cache, with the same slot map as the main model.

Step 3: one draft pass after the verification

The sampler calls decode_forward after the verification ({{cite deepinfer/model_executor/layers/sampler.py:236-251}}). It replays a CUDA graph, or runs run_drafts directly:

  1. Line 365: with context parallelism, the driver broadcasts last_valid_offset and golden_tokens to the other ranks.
  2. Lines 367-372: build_dflash_input makes the metadata of a block of 5 positions per request. The block starts after the last accepted position: a + 1 … a + 5, with a = positions[ftp] + last_valid_offset ({{cite deepinfer/model_executor/layers/tilelang_ops/get_kv_index.py:168-174}}).
  3. Line 373: forward_drafts embeds [golden, noise, noise, noise, noise] and runs the DFlash layers ({{cite deepinfer/model_executor/models/mtp/dflash.py:230-256}}). The golden token is the token that the sampler just made. The noise token id comes from the checkpoint config ({{cite deepinfer/hugging_face/config.py:186}}).
  4. Line 376: only the driver samples.

Every draft row attends to the same keys: the last window_size main positions up to a (128 in the docs), plus the 5 draft positions ({{cite deepinfer/model_executor/layers/tilelang_ops/get_kv_index.py:183-197}}). So the 5 rows see each other, and they all come from one pass.

Step 4: per-step heads: Markov correction and confidence

  1. Line 309: row step_i of every request. The rows of one request are 5 apart.
  2. Lines 311-312: the Markov term. markov_w1 embeds the previous token into a small vector (dspark_markov_rank values). markov_w2 maps that vector to one score per vocabulary token and adds the scores to the logits (out_acc). For step 0 the previous token is the golden token; then it is the draft of the step before ({{cite deepinfer/model_executor/models/mtp/dflash.py:296}}).
  3. Lines 316-321: the confidence head computes sigmoid([h, markov_emb] · w / T) for this step ({{cite deepinfer/model_executor/layers/tilelang_ops/dflash.py:10-28}}).
  4. Lines 322-330: process_sampling with the request's temperature, top-p and top-k, and the seed namespace "mtp". The processed logprobs go straight into next_n_token_logprobs[:, step_i]. The verification needs them in the next step.

Lines 336-344 then store the drafts, the logprobs and the confidences in the {{term mtp-info-pool}}, and return token_ids [req, 5] and confidence_rates [req, 5].

Step 5: confidences become accept rates in C++

After the step, process_MTPInfo copies the drafts and the confidences into each sequence. It stores the running product of the confidences:

build output reads confidence_raw before this update (the value just moved into prev_confidence_raw), so processMTP must run before build output. The confidence rate from modeling is independent per token; multiply them before use.

The running product is the estimated chance that drafts 1 to j all pass. Only then does draft j count. The rate never grows with j, so a sort by rate keeps the drafts of each request in order.

Step 6: MTPVarlen::schedule chooses the lengths

The decode scheduler sorts the batch and asks MTPVarlen for one seqlen_q per sequence ({{cite csrc/engine/scheduler.hpp:648-652}}). Without a performance curve, the answer is always 1 + 5 ({{cite csrc/engine/mtp_varlen.hpp:153-158}}). The curve exists only with DEEPINFER_ENABLE_MTP_VARLEN=1 ({{cite deepinfer/worker/base.py:280-281}}). Then:

  1. Lines 231-232: start with one row per sequence. Each sequence surely gives one token, so the expected count starts at num_seqs.
  2. Lines 243-244: the time of a step with cur_bsz rows has three parts. They are the measured time of the smallest CUDA graph that fits, a slope term and the sampler time.
  3. Lines 254-258: add the drafts one by one, best rate first. Each draft adds its rate to the expected tokens and one row to the batch. Keep the size with the best expected / time.
  4. Lines 263-266: give the best_bsz − num_seqs best drafts to their sequences. Each won draft adds 1 to that sequence's seqlen_q.

In the worked example of the figure, 12 rows give 8.59 expected tokens in 11.6 ms. All 18 rows would give 9.05 tokens in 13.2 ms. 12 rows are faster per token.

Step 7: with ZOS, the GPU splits the budget

With {{term zos | ZOS}}, the CPU schedules step N+1 before the confidences of step N reach the CPU. The Q&A explains the solution: "CPU scheduling only fixes the total budget; the per-request lengths are recomputed on the GPU by a TileLang kernel" ({{cite doc/inference_deployment_qa.md:264}}). In the worker:

The kernel uses the confidences of step N, which are still on the device. It computes the running products, sorts all drafts of the batch and gives each request its share of the same total_q ({{cite deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py:51-98}}). The new lengths go back to pinned CPU memory. Before it samples, the worker waits for this copy with d2h_evt ({{cite deepinfer/worker/worker.py:146-152}}). This wait exists only with DSpark.

Worked example. Two requests. Request 0 had input positions 49 to 54 and accepted 2 drafts. Request 1 had positions 200 to 205 and accepted 5 drafts. So ftp = [0, 6] and last_valid_offset = [2, 5].

accepted_pos     = [49 + 2, 200 + 5]      = [51, 205]
draft positions  = [[52, 53, 54, 55, 56],  # request 0: row 0 holds its golden token at 52
                    [206, 207, 208, 209, 210]]
kv_len           = 128 + 5 = 133 → padded to 192 columns
keys of request 0 = positions 51 − 127 = −76 … 56 → negative positions become −1 (invalid)
                    so it sees positions 0 … 51 (main keys) and 52 … 56 (draft keys)
store slot       = state_offset + pos % 134    # same ring as the main SWA cache

The reference implementation gives these values ({{cite deepinfer/model_executor/layers/tilelang_ops/get_kv_index.py:166-197}}). The SWA ring has 134 rows per state slot with default settings ({{cite deepinfer/worker/cache_engine.py:88-110}}).

Markov head. The checkpoint stores it as markov_head.embed and markov_head.head ({{cite deepinfer/hugging_face/names.py:92-93}}). The class docstring says: "Final DFlash head with a first-order Markov correction to logits" ({{cite deepinfer/model_executor/models/v4_modules/heads.py:26-34}}). For step i with previous token x:

w1       = markov_w1[x]                    # [R, markov_rank], an embedding lookup
logits_i = lm_head(post_norm(h_i)) + w1 @ markov_w2.T    # [R, V], float32 output (out_acc)

So the draft of step i depends on the sampled draft of step i − 1, through a rank-markov_rank table. This is cheap: the expensive layers run once for all 5 steps.

Confidence head. It is one linear layer from H + markov_rank inputs to 1 output (AcceptRatePredictor, {{cite deepinfer/model_executor/models/v4_modules/heads.py:37-42}}). The fused kernel computes:

c_i = sigmoid( concat(h_i, w1) @ w / T_i )   # h_i: hidden state before the final norm, bf16

The reference clamps the scaled value to [−60, 60] before the sigmoid ({{cite deepinfer/model_executor/layers/tilelang_ops/dflash.py:49-51}}). T_i comes from DEEPINFER_DFLASH_CONFIDENCE_HEAD_TEMPERATURE: one value for all steps (default 1.0), or a comma list with exactly nextn values ({{cite deepinfer/environ.py:134-143}}). Values below 1e-5 become 1e-5 ({{cite deepinfer/model_executor/models/mtp/dflash.py:62-64}}).

Accuracy of the confidence. The verification computes an estimate of the accept chance of each row, accept_probs = max(1 − Σ residual, 0). Because of the α penalty, it is a little lower than the exact chance Σ min(p, q) ({{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:232-234}}). finalize_verification adds |accept_prob − confidence| over all verify rows into batch_confidence_error ({{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:584-589}}). The statistics logger divides the sum by the number of verified drafts ({{cite deepinfer/engine/stats_logger.py:236}}).

After a stop token. If a request emits EOS in this step, the sampler sets all its new confidences to 0 ({{cite deepinfer/model_executor/layers/sampler.py:252-254}}). The scheduler then gives it no drafts.

The C++ comment explains a timing problem ({{cite csrc/engine/mtp_varlen.hpp:160-168}}). Translated:

"Make sure that confidence_{i+1..nextn} does not decide whether draft_token_i is verified. In round N, we use the accept rates of round N−2 to compute best_bsz (total_q). We use the accept rates of round N−1 to give each request its seqlen_q (non-ZOS here; ZOS corrects it on the GPU). Each request keeps two counters, schedule_cnt and process_cnt. If they are equal, accept_rates is from round N−1 and prev_accept_rates from N−2. If schedule_cnt = process_cnt + 1 (as with ZOS), accept_rates is from N−2 and prev_accept_rates from N−3."

So the code fills two queues ({{cite csrc/engine/mtp_varlen.hpp:191-208}}):

  • acc_queue_for_bsz: prev_accept_rates if the counters are paired, else accept_rates. This decides the total.
  • acc_queue_for_seqs_q: always accept_rates. This decides the split.

No rates yet. A sequence with an empty rate list gets the value 1.0 for each draft if it has drafts, else 0.0 ({{cite csrc/engine/mtp_varlen.hpp:173-178}}). A request that the CPU schedules ahead of its post-processing always counts as "has drafts" ({{cite csrc/engine/mtp_varlen.hpp:200-201}}).

Sort order. Higher rate first; for equal rates, the lower sequence index first ({{cite csrc/engine/mtp_varlen.hpp:210-214}}). The scheduler sorted the batch by length, longest first, just before ({{cite csrc/engine/scheduler.hpp:648-649}}).

Checks. TORCH_CHECK(best_bsz >= num_seqs) ({{cite csrc/engine/mtp_varlen.hpp:260}}), and the counters must satisfy process_cnt ≤ schedule_cnt ≤ process_cnt + 1 ({{cite csrc/engine/mtp_varlen.hpp:195-196}}). A preempted request resets both counters ({{cite csrc/engine/sequence.hpp:133-142}}).

Start-up curve. After the CUDA graph capture, profile_decode_perf replays the decode graph of every captured batch size. It does 1 warm-up and 5 timed runs, drops the fastest and the slowest run, and takes the mean. Then it averages over the expert-parallel group ({{cite deepinfer/worker/model_runner.py:586-623}}). The result is a list of (graph_size, ms) pairs, cached on disk by DecodePerfCache ({{cite deepinfer/worker/model_runner.py:570-579}}). The engine gives it to the C++ scheduler ({{cite deepinfer/engine/llm_engine.py:268}}). Without CUDA graphs, the curve is empty ({{cite deepinfer/worker/model_runner.py:563-564}}), and DSpark falls back to 1 + 5.

Runtime feedback. After each decode step, the engine passes the measured forward and sampler times ({{cite deepinfer/engine/llm_engine.py:995-1002}}). update_runtime keeps two estimators ({{cite csrc/engine/mtp_varlen.hpp:139-148}}):

  • Sampler time. The median of the last 9 samples, used after at least 5 samples. There is one estimator per batch size (num_seqs) and one global fall-back ({{cite csrc/engine/mtp_varlen.hpp:20-42}}, {{cite csrc/engine/mtp_varlen.hpp:216-223}}).
  • Forward slope. For each step, (forward_ms − curve_ms) / graph_size. The estimator keeps the last 5000 steps. It takes the median per graph size (only sizes with 10 or more samples), then the median of these medians ({{cite csrc/engine/mtp_varlen.hpp:44-131}}). The slope is clamped to at least 0 ({{cite csrc/engine/mtp_varlen.hpp:226}}).

The time model is then baseline_ms(graph) + slope_ms × graph_size + sampler_ms ({{cite csrc/engine/mtp_varlen.hpp:242-244}}). The comment at line 44 gives the reason for the slope: the start-up curve does not include the effect of the context length.

The lengths depend on measured times, so two runs can choose different lengths and batch shapes. The README asks for DEEPINFER_ENABLE_MTP_VARLEN=0 for deterministic sampling ({{cite README.md:28}}).

compute_seqlens_q_by_confidence_rates(total_q, remap, prev_confidence_rates, seqlens_q) works in two phases ({{cite deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py:35-98}}):

  1. Gather and multiply. remap[i] is the row of sequence i in the previous batch, or -1 for a new sequence. A new sequence gets rates of 0. The running product goes along the 5 drafts.
  2. Rank. Sort all num_seqs × 5 rates (higher first, lower flat index first on ties). The first total_q − num_seqs win. Each sequence gets 1 + wins.

Two differences from the CPU split: the GPU uses the newest confidences (step N), and a new sequence gets the rate 0. So its drafts come after all drafts with a rate above 0. The sum of the lengths stays total_q, so the CUDA graph that the CPU chose still fits. On Ascend the kernel asserts num_seqs × nextn × 4 ≤ 32 KB of on-chip buffer ({{cite deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py:30-31}}).

After the kernel, the CPU copy of the lengths updates each SequenceMetadata and the scheduler outputs before the sampler runs ({{cite csrc/engine/zos.cpp:279-305}}). cu_seqlens_q is also recomputed on the device ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:92-95}}).

What can go wrong

  • DSpark has no effect. Without CUDA graphs, the cost curve is empty and every request sends 1 + 5 tokens ({{cite deepinfer/worker/model_runner.py:563-564}}, {{cite csrc/engine/mtp_varlen.hpp:153-158}}).
  • Different results in two runs. The chosen lengths depend on measured times. Turn DSpark off for deterministic sampling ({{cite README.md:28}}).
  • Small batches. At 16 sequences per rank the Q&A measured −1.5 % ({{cite doc/inference_deployment_qa.md:251}}).
  • A sync point. With DSpark and ZOS, the worker waits for d2h_evt before each decode sample ({{cite deepinfer/worker/worker.py:147-149}}).
  • Wrong temperature list. A comma list with a length other than nextn raises ValueError ({{cite deepinfer/environ.py:140-141}}).
  • Counter mismatch. If the schedule and process counters drift apart, MTPVarlen::schedule stops with a check failure. A C++ comment notes that a preempted sequence must skip its MTP update for this reason ({{cite csrc/engine/scheduler.hpp:1214-1219}}).

Why it matters. Speculative decoding gives more tokens per step only when the drafts pass. DSpark spends the verification rows where they most likely pay off, and the gain grows with the batch size.

Which environment variable turns on confidence-scheduled verification, and what is its default?

DEEPINFER_ENABLE_MTP_VARLEN; it is off by default ({{cite deepinfer/environ.py:131}}, {{cite README.md:24}}).

 The confidences of one request are 0.9, 0.5, 0.8. What accept rates does C++ store?

The running products: 0.9, 0.45, 0.36 ({{cite csrc/engine/scheduler.hpp:1243-1249}}).

 DFlash makes 5 drafts. Does it run its decoder layers 5 times?

No. It runs them once on a block of 5 positions: the golden token and 4 noise tokens ({{cite deepinfer/model_executor/models/mtp/dflash.py:230-256}}). Only the per-step heads and the small Markov term run 5 times ({{cite deepinfer/model_executor/models/mtp/dflash.py:308-334}}).

 The draft keys of DFlash: from which data does DFlash compute the keys of the main tokens?

From the residual streams of the target layers of the main model (dspark_target_layer_ids), concatenated, projected, normalized and passed through main_kv_proj ({{cite deepinfer/model_executor/models/mtp/dflash.py:219-228}}).

 With ZOS and DSpark on, the CPU scheduled step N+1 with total_q = 40 for 10 sequences. Which confidences decide how the 30 draft rows are shared, and who computes the split?

The confidences of step N, still on the device. A TileLang kernel computes the running products, ranks all 50 rates, and gives each sequence 1 + its wins among the best 30 ({{cite deepinfer/worker/worker.py:218-219}}, {{cite deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py:67-98}}). The CPU only fixed total_q. Step N was not post-processed yet, so the CPU used the rates of step N−1, one round older ({{cite csrc/engine/mtp_varlen.hpp:160-168}}, {{cite csrc/engine/mtp_varlen.hpp:203-204}}). This is in the deep dives on MTPVarlen and the GPU split.
