In decode steps it also verifies the draft tokens. --- After each forward pass, the sampler makes float32 logits for the rows that need a token. Then it filters them and draws each token with a seed.

The idea

The model does not output a token. For each position, it outputs a {{term hidden-state}}. The sampler turns that vector into one score per vocabulary token: the {{term logits}}. Then it turns the scores into probabilities and selects one token. The page {{link learn/sampling}} explains the basic steps.

Each request carries its own settings in {{term sampling-params | SamplingParams}}:

  • {{term temperature}} divides the logits before softmax. A low value makes the best token more likely.
  • {{term top-p}} and {{term top-k}} remove unlikely tokens. Their probability becomes zero.
  • {{term seq-seed | seq_seed}} fixes the random numbers of the request. The same seed and the same inputs give the same tokens.

The DeepInfer sampler has two more jobs. In a {{term decode}} step, it checks the {{term draft-token | draft tokens}} of the previous step and keeps a prefix of them. This is {{term speculative-decoding}}. After the check, it calls the draft model {{term dflash | DFlash}}, which proposes the drafts for the next step.

An everyday comparison. Think of a raffle drum. Each token has tickets in proportion to its probability. Temperature gives the favourite tokens more or fewer tickets. Top-p and top-k take the tickets of unlikely tokens out of the drum. Then a hand picks one ticket. The comparison stops being true at the last step. DeepInfer does not pick by chance in the usual sense. It computes a number u from the seed and the position. Then it walks the running sum of the probabilities until the sum is larger than u. So the same seed and position always give the same ticket.

In the code

Step 1: who calls the sampler

The worker runs the sampler right after the forward pass. ModelRunner.execute_sample builds the sampler inputs and calls DeepseekForCausalLM.sample ({{cite deepinfer/worker/model_runner.py:337-367}}). That method passes the LM head weight as embedding and the draft module as mtp_module:

The sampler inputs come from C++. prepare_sampler_inputs fills pinned CPU arrays and starts non-blocking copies to the device ({{cite csrc/engine/prepare_sample.cpp:40-284}}). The arrays of temperature, top-p, top-k, seed and sample position have one entry per sequence, not per row ({{cite csrc/engine/prepare_sample.cpp:82-88}}).

Step 2: select rows, then make logits

In a prefill step, the selected row is the last token of each prompt ({{cite csrc/engine/prepare_sample.cpp:197}}). In a decode step, all seqlen_q rows of each request are selected, because each row checks one draft ({{cite csrc/engine/prepare_sample.cpp:202-205}}). Then get_logits makes a float32 tensor and fills it with a BF16 matrix multiply:

Step 3: masks before the sampling

Three masks can set logits to minus infinity. A token with a logit of minus infinity has probability zero.

  1. Token blacklist. DEEPINFER_DECODE_TOKEN_BLACKLIST lists token ids, for example 0..3,7 ({{cite deepinfer/model_executor/utils.py:29-35}}). The sampler fills them with minus infinity in all rows ({{cite deepinfer/model_executor/layers/sampler.py:167-169}}).
  2. EOS suppression. With first_n_token_no_eos=1, the first output token cannot be EOS ({{cite deepinfer/model_executor/layers/sampler.py:183-185}}).
  3. Structured output. A grammar matcher fills a bit mask for each request that has a {{term structured-output}} grammar ({{cite deepinfer/model_executor/layers/sampler.py:187-188}}). In decode, there is one mask per draft step ({{cite deepinfer/model_executor/layers/sampler.py:433-437}}).

The name says "DECODE", but line 169 runs before the split into prefill and decode at line 171. So the blacklist also applies to the first token of each request.

Step 4: one kernel for temperature, top-p, top-k and the draw

process_sampling prepares the inputs. Then it calls fused_sample, a {{term tilelang}} kernel that does all per-row work in one launch ({{cite deepinfer/model_executor/layers/sampler_utils.py:162-196}}). The reference code in the same file shows the order of the operations:

  1. Line 209: each row is divided by its temperature.
  2. Line 210: top-p, then top-k, set removed tokens to minus infinity ({{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:121-150}}).
  3. Line 211: log_softmax gives the logprobs of the filtered distribution.
  4. Lines 223-225: the draw uses the seed and the sample position of the row.

The same file also holds the tests. They run the same checks on the TileLang kernel and on this reference ({{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:738-750}}).

Step 5: the seeded draw

The draw does not use a global random generator. It hashes the seed and the position into one number u in [0, 1). Then it walks the running sum of the probabilities until the sum is larger than u times the row sum (line 83):

The docstring states the property that matters: the result depends only on the seed, the position and the case. It does not depend on the batch size or on the row order ({{cite deepinfer/model_executor/layers/tilelang_ops/random_sampling.py:17-21}}). The deep dive Seeds and positions lists all three cases.

Step 6: prefill output

In a prefill step, _prefill_golden_gen runs process_sampling, then adds the extras: the top logprobs, the {{term golden-tokens | golden-token}} override and sum_smaller_probs ({{cite deepinfer/model_executor/layers/sampler.py:597-634}}). The result has one token per request. The sampler starts the copies to the CPU and returns ({{cite deepinfer/model_executor/layers/sampler.py:190-211}}).

Step 7: decode output

In a decode step, the sampler calls _verification with the drafts of the previous step ({{cite deepinfer/model_executor/layers/sampler.py:213-233}}). The result is one sampled token per request, plus the accepted drafts. Then DFlash makes the next drafts from the sampled token ({{cite deepinfer/model_executor/layers/sampler.py:235-251}}). The page {{link concepts/speculative-decoding}} explains the verification.

The sampler never waits for the device. execute_sample runs inside forbid_cuda_sync() ({{cite deepinfer/worker/model_runner.py:356-360}}). The CPU reads the results later, after the event sample_end_evt ({{cite deepinfer/worker/worker.py:167-168}}). Work that needs CPU values goes into post_funcs, for example the counters of a decode step ({{cite deepinfer/model_executor/layers/sampler.py:293-298}}).

Worked example (prefill). Two prompts of 41 and 100 tokens are in one prefill step. The model output has 141 rows. selected_token_indices = [40, 140], so R = 2 ({{cite csrc/engine/prepare_sample.cpp:197-199}}). sample_positions = [41, 100], the seqlen_k of each prompt ({{cite csrc/engine/prepare_sample.cpp:198}}). The logits use 2 × V × 4 bytes. With the inferred V = 129280, that is 1,034,240 bytes, about 1 MB.

Worked example (decode). Three requests have seqlen_q = 6, 6, 4. Then R = total_q = 16 and mtp_first_token_positions = [0, 6, 12] ({{cite csrc/engine/prepare_sample.cpp:152-153}}). prepare_verification_metadata makes three tensors of shape [16]:

The reference implementation shows the rule ({{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:13-25}}). expand_sampling_params then copies the per-sequence parameters to the 16 rows ({{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:56-66}}). The logits use 16 × 129280 × 4 bytes, about 8.3 MB.

Every random number of the sampler comes from a hash of two values: the 64-bit seq_seed of the request and a 64-bit sequence number. The hash is SplitMix64, and the result is a float64 in [0, 1) ({{cite deepinfer/model_executor/layers/tilelang_ops/random_sampling.py:58-67}}). The sequence number is 3 × position + case:

CaseUseSource
0A fresh sample (prefill token, bonus token, draft token){{cite deepinfer/model_executor/layers/tilelang_ops/random_sampling.py:78}}
1A sample from the {{term residual-distribution}} after a rejected draft (is_nextn_predict=True){{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:245}}
2The number U that decides accept or reject{{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:239-242}}

Which position.

  • Prefill: sample_position = seqlen_k, the prompt length after this chunk ({{cite csrc/engine/prepare_sample.cpp:198}}).
  • Decode: sample_position = seqlen_k - seqlen_q + 1 per request ({{cite csrc/engine/prepare_sample.cpp:206}}). Row j of the request uses sample_position + j × 10000019, so every row has its own stream ({{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:65}}, {{cite deepinfer/model_executor/layers/tilelang_ops/common.py:52}}).
  • Draft model: the seed gets an offset of 1000000007 (tag "mtp"), so drafts and target use different streams ({{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:15}}, {{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:93}}). Draft i (1 to 5) uses position sample_position + last_valid_offset + i ({{cite deepinfer/model_executor/models/mtp/dflash.py:290-294}}).

Worked example. Request "1" of the tour {{link tours/life-of-a-request}} has seq_seed = 1 and a 41-token prompt. Its prefill token uses position 41, case 0. In a decode step with input positions 49 to 54, seqlen_k = 55 and seqlen_q = 6, so sample_position = 50. Row 2 then uses position 50 + 2 × 10000019 = 20000088.

No seed given. SamplingParams takes 64 random bits from Python's random module ({{cite deepinfer/sampling_params.py:85-91}}). So two runs differ, unless you pass seq_seed. The README gives the full recipe for equal outputs: DEEPINFER_BATCH_INVARIANT=1 DEEPINFER_ENABLE_MTP_VARLEN=0 and a fixed seq_seed, on NVIDIA only ({{cite README.md:28}}). See {{link concepts/determinism}}.

Parameter checks. SamplingParams raises ValueError for a negative temperature, for top_p outside (0, 1], and for top_k that is 0, below -1 or above the int32 maximum ({{cite deepinfer/sampling_params.py:93-99}}). A temperature below SAMPLING_EPS = 1e-5 becomes 1e-5, and top-p and top-k are then turned off ({{cite deepinfer/sampling_params.py:76-79}}). So "temperature 0" is very close to greedy, but it is still a seeded draw.

Order. The reference applies top-p first and top-k second. Both use a stable sort, so equal values keep their token order ({{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:121-150}}):

  1. Sort the probabilities in descending order.
  2. Remove a token if the sum of the probabilities before it is larger than top_p (line 139). So the kept set is the shortest prefix whose sum is larger than top_p, or the full row.
  3. On the remaining logits, remove every token with rank ≥ top_k (lines 145-150). top_k = -1 removes nothing.
  4. log_softmax normalizes the kept tokens again.

Worked example. After temperature, five tokens have probabilities [0.50, 0.25, 0.15, 0.06, 0.04]. With top_p = 0.8, the sums before each token are [0, 0.50, 0.75, 0.90, 0.96]. Tokens 4 and 5 have sums above 0.8, so they go. With top_k = 2, token 3 also goes. The result is [0.667, 0.333, 0, 0, 0].

The logprobs are of the filtered distribution. All later values use these processed logprobs: the token logprob, the top logprobs and the prompt logprobs. A token that top-p removed has logprob minus infinity.

A full row has about 129280 floats (vocabulary size inferred). Sorting it for top-p is expensive. With {{term force-topk}}, the sampler first keeps only the N largest logits of each row, with their ids, and does all later work on N columns:

  1. Line 167: topk(..., sorted=False) returns float32 values [R, N] and int32 token_index [R, N]. The function comes from the vendor library DeepSelect. On Ascend, an import hook replaces it ({{link concepts/hardware-platforms}}).
  2. Lines 172-180: the drafts of the previous step live in the top-N space of the draft model. remap_draft_topk moves them into the top-N space of the target row ({{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:165-203}}). A draft token that is not in the target top-N gets id -1, and -1 forces a reject ({{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:221-222}}, {{cite deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:46-48}}).
  3. After the kernel, map_lookup turns column indices back into vocabulary ids ({{cite deepinfer/model_executor/layers/sampler.py:460-467}}).

What it changes. A token outside the top N can never be sampled, and its logprob is minus infinity. A script that needs full-vocabulary logprobs sets sampler_force_topk=0 for this reason ({{cite examples/yoco/yoco_equiv.py:559}}).

Memory. The draft logprobs live in the {{term mtp-info-pool}}, with (max_num_seqs + 1) × nextn rows of N floats, plus N int32 ids with force top-k ({{cite deepinfer/model_executor/layers/mtp_info_pool.py:20-23}}). Example with max_num_seqs = 64 and nextn = 5: 325 rows. With N = V = 129280, the pool needs 325 × 129280 × 4 bytes, about 168 MB. With N = 4096, it needs 325 × 4096 × 8 bytes, about 10.6 MB.

Limits and settings. remap_draft_topk asserts N ≤ 16384 on NVIDIA and N ≤ 4096 on Ascend ({{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:189}}). The code default is 0, off ({{cite deepinfer/environ.py:150}}). examples/offline_inference.py uses 4096 ({{cite examples/offline_inference.py:17}}), and examples/benchmark.py uses 1024 ({{cite examples/benchmark.py:54}}).

Token logprob. For each sampled token, the sampler looks up its processed {{term logprob}} with map_lookup ({{cite deepinfer/model_executor/layers/sampler.py:494-499}}).

Top logprobs. _prepare_top_info takes the k largest logprobs of each row, sorted ({{cite deepinfer/model_executor/layers/sampler.py:636-648}}). k is the largest top_logprobs of all requests in the batch ({{cite csrc/engine/prepare_sample.cpp:157}}). So the tensor has the same width for all rows.

sum_smaller_probs. With DEEPINFER_COMPUTE_SUM_SMALLER_PROBS=1, the sampler also returns one more value per row. It is the probability sum of all tokens that are less likely than the sampled token, plus the sampled token itself. Equal probabilities are ordered by column index:

{{term prompt-logprobs | Prompt logprobs}}. With SamplingParams(prompt_logprobs=True), a prefill step also returns the logprob of each prompt token, given the tokens before it:

  1. C++ selects every row of the chunk except the last row of the last chunk, and stores the next prompt token as the target ({{cite csrc/engine/prepare_sample.cpp:12-18}}, {{cite csrc/engine/prepare_sample.cpp:181-189}}).
  2. compute_prompt_logprobs works in chunks of 8192 rows, so the float32 logits never exceed 8192 × V ({{cite deepinfer/model_executor/layers/sampler_utils.py:17}}, {{cite deepinfer/model_executor/layers/sampler_utils.py:93-110}}).
  3. Each chunk runs fused_sample without a draw, with the temperature, top-p and top-k of the request ({{cite deepinfer/model_executor/layers/sampler_utils.py:69-78}}).
  4. A post function splits the flat result back into one list per request ({{cite deepinfer/model_executor/layers/sampler.py:205-210}}).

Example: a 41-token prompt in one chunk gives 40 prompt logprobs. With 8192 × 129280 × 4 bytes, one chunk of logits needs about 4.2 GB. YOCO truncation turns prompt logprobs off ({{cite deepinfer/engine/llm_engine.py:529-537}}).

The docstring of the class names this feature "golden teacher forcing" ({{cite deepinfer/model_executor/layers/sampler.py:92}}). A request can pass golden_token_ids, a list of output tokens ({{cite deepinfer/sampling_params.py:60}}). The sampler then outputs these tokens instead of its own samples, while it still computes all logprobs.

  1. The C++ sequence stores the list ({{cite csrc/engine/pybind_sequence.cpp:36}}). At each step, next_golden_tokens returns 2 × nextn + 1 values from the current output length, padded with -1 ({{cite csrc/engine/sequence.hpp:155-165}}).
  2. prepare_sampler_inputs writes up to min(seqlen_q, nextn + 1) of them into golden_output, one per row; other rows get -1 ({{cite csrc/engine/prepare_sample.cpp:229-248}}).
  3. Prefill: _update_golden_tokens replaces the sample where golden_output != -1, and looks up the logprob of the golden token ({{cite deepinfer/model_executor/layers/sampler.py:665-677}}).
  4. Decode: a row with a golden token accepts its draft only if the draft equals the golden token, and outputs the golden token ({{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:239-242}}).

Result: the request follows the golden text exactly. The logprobs show how likely the model finds that text, and the accept counts show how well the drafts match it.

_get_so_mask runs on the CPU while the device computes the logits ({{cite deepinfer/model_executor/layers/sampler.py:135-138}}). It returns nothing when no request in the batch has a grammar ({{cite deepinfer/model_executor/layers/sampler.py:318-319}}).

  • Layout. One pinned int32 bit mask [batch, ceil(V / 32)] per step: max_MTP_value + 1 masks, so 6 by default ({{cite deepinfer/model_executor/layers/sampler.py:323-327}}). Mask 0 is for row 0, whose input is the last real token. Mask j (1 to 5) is for row j, whose input is draft j.
  • Drafts. The matcher accepts the drafts one by one and fills one mask per accepted draft. It stops at the first draft that the grammar forbids. Then rollback undoes the trial ({{cite deepinfer/model_executor/layers/sampler.py:366-376}}).
  • Copy. A side stream copies the masks to the device and records an event. The main stream waits for that event before it applies the masks ({{cite deepinfer/model_executor/layers/sampler.py:391-404}}, {{cite deepinfer/model_executor/layers/sampler.py:163-164}}).
  • Errors. A matcher error kills only its own request (so_status = -1). A comment explains why: an exception here would stop all requests and time out the NCCL barrier ({{cite deepinfer/model_executor/layers/sampler.py:377-386}}).

The page {{link concepts/structured-outputs}} explains the grammar matcher.

With context parallelism, only the driver rank samples. On a follower rank, sampler_inputs.driver is None ({{cite deepinfer/model_executor/layers/sampler.py:136-137}}). The follower still does two things, because they contain collective operations ({{cite deepinfer/model_executor/layers/sampler.py:145-161}}):

  • It runs compute_prompt_logprobs. Translated comment: "The result is valid only on the driver; the follower only takes part in the collective communication of the embedding gather."
  • In a decode step, it runs DFlash.decode_forward without a driver input. It gets the sampled tokens of the driver by a broadcast ({{cite deepinfer/model_executor/models/mtp/dflash.py:358-365}}).

Then it returns an empty SamplerOutput.

What can go wrong

  • Bad parameters. SamplingParams raises ValueError, for example for top_k=0 or top_p=0 ({{cite deepinfer/sampling_params.py:93-105}}). Use top_k=-1 to turn top-k off.
  • Bad blacklist. A wrong format or an id outside the vocabulary raises ValueError when the sampler is made ({{cite deepinfer/model_executor/utils.py:37-38}}). The engine does not start.
  • Unexpected logprobs. The returned logprobs come from the filtered distribution, and with force top-k from N columns only. They are not the raw model probabilities.
  • Different outputs in two runs. Without a fixed seq_seed, every request gets a new random seed ({{cite deepinfer/sampling_params.py:87-88}}).
  • Mixed batch. prepare_sampler_inputs stops with a check failure if one batch mixes prefill and decode sequences ({{cite csrc/engine/prepare_sample.cpp:61}}). The scheduler never makes such a batch.
  • Grammar failure. A matcher error ends only that request with so_status = -1 ({{cite deepinfer/model_executor/layers/sampler.py:377-386}}).

Why it matters. The sampler decides every output token. Its float32 logits for only the needed rows keep memory small. Its seeded hash makes the output repeatable. Its verification turns the drafts into extra tokens per step.

A prefill step has 3 prompts of 10, 20 and 30 tokens. How many rows of logits does the sampler make, and of what dtype?

3 rows, one for the last token of each prompt, in float32 ({{cite csrc/engine/prepare_sample.cpp:197}}, {{cite deepinfer/model_executor/layers/sampler_utils.py:25}}). The selected_token_indices are [9, 29, 59].

 A request sets temperature=0. What does DeepInfer do with this value?

It replaces it with SAMPLING_EPS = 1e-5 and sets top_p=1.0 and top_k=-1 ({{cite deepinfer/sampling_params.py:76-79}}). The draw is then almost always the most likely token.

 Two runs use the same prompt and the same seq_seed, but the second run has more requests in the batch. Why can the sampler still give the same token?

The draw hashes only the seed, the sample position and the case. It does not use the batch size or the row order ({{cite deepinfer/model_executor/layers/tilelang_ops/random_sampling.py:17-21}}). For fully equal outputs, the logits must also be equal, so the README also asks for DEEPINFER_BATCH_INVARIANT=1 and DEEPINFER_ENABLE_MTP_VARLEN=0 ({{cite README.md:28}}).

 You set DEEPINFER_DECODE_TOKEN_BLACKLIST=5. Can token 5 be the first token after the prompt?

No. The blacklist fill at line 169 runs before the prefill and decode split at line 171, so it applies to prefill rows too ({{cite deepinfer/model_executor/layers/sampler.py:167-171}}).

 With DEEPINFER_SAMPLER_FORCE_TOPK=4096, a request asks for prompt logprobs. One prompt token is the 5000th most likely token at its position. What logprob does it get, and why?

Minus infinity. Each chunk keeps only the 4096 largest logits and their ids, then looks up the prompt token by key; a missing key gives minus infinity ({{cite deepinfer/model_executor/layers/sampler_utils.py:67-78}}, {{cite deepinfer/model_executor/layers/tilelang_ops/sampler.py:149-152}}). This is in the deep dive "Force top-k".
