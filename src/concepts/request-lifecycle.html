The idea

A user sends a request: a prompt and its {{term sampling-params | sampling settings}}. Inside the engine, the request becomes a {{term sequence}}. The sequence is a C++ object. It holds the token ids, the settings, the KV {{term block-table | block table}}, the draft tokens, and a status.

The status tells where the sequence is in its life ({{cite csrc/engine/sequence.hpp:30-41}}):

  • WAITING: in the waiting queue. The sequence waits for its {{term prefill}}, or for the next chunk of it.
  • RUNNING: the prompt is in the KV cache. Each {{term decode}} step adds one or more tokens.
  • FINISHED_*: seven final values. Each one has a {{term finish-reason | finish reason}}, for example "stop" for the end-of-sequence token or "length" for the token limit.

Two more things can happen on the way. A sequence can wait at the start, until the image worker marks it {{term schedulable}}. And when the KV cache is full, the scheduler can {{term preemption | preempt}} it. The sequence then stops, or it goes back to the queue and computes its KV cache again ({{term recompute}}).

An everyday comparison. Think of a passenger at an airport. Check-in makes a boarding pass (the sequence). The passenger waits at the gate until the gate opens (schedulable, attempt point). Boarding is the prefill; the flight is the decode. The trip ends with a reason: arrived, cancelled, or bumped. A bumped passenger can get a seat on a later flight at the front of the line. The comparison stops being true here. A recomputed sequence keeps every token that it already made, but it must read all of them again in a new prefill.

In the code

Step 1: the engine makes the Sequence

LLMEngine.add_request checks the prompt and makes the C++ object ({{cite deepinfer/engine/llm_engine.py:580-604}}). The binding fills a SequenceInit from the flat Python arguments:

Line 35 is important. A sequence with multimodal data starts as not schedulable. The offline LLM gives every request a multimodal dict when the engine has an image processor, also for text-only prompts ({{cite deepinfer/entrypoints/llm.py:158-159}}). The constructor then copies the sampling values and the stop values out of the Python object once ({{cite csrc/engine/sequence.hpp:276-283}}).

Two error cases give a sequence a final status before it enters a queue. Image bytes set to None give FINISHED_VE_FAILED ({{cite deepinfer/engine/llm_engine.py:603-604}}). An aborted grammar build gives FINISHED_SO_FAILED ({{cite deepinfer/engine/llm_engine.py:621-622}}).

Step 2: the sequence enters the waiting queue

add_sequence sets the arrival time in milliseconds (the Python value is replaced). For a NORMAL engine it also reserves memory for max_tokens more token ids. It also reserves room in the block table for all blocks that the sequence can need ({{cite csrc/engine/scheduler.hpp:190-192}}). Then the sequence goes to the end of waiting. With an image processor, the engine also sends the multimodal dict to the image worker ({{cite deepinfer/engine/llm_engine.py:624-625}}).

Step 3: the image worker makes it schedulable

The image worker runs in other processes. In every engine step, fetch() collects its results:

A failed result (None) goes to a list; the engine then aborts that request ({{cite deepinfer/engine/llm_engine.py:942-945}}). A sequence that is not schedulable stops the prefill loop when it is at the front of the queue ({{cite csrc/engine/scheduler.hpp:369-371}}).

Step 4: the prefill makes it RUNNING

At an {{term attempt-point}}, the scheduler takes the sequence from the front of waiting. The first chunk takes the KV blocks and one {{term state-slot}} for the whole prompt. Only the last chunk changes the status:

After the step, process_outputs moves the cache counter forward by the chunk length. Then it decides:

  • The whole prompt is in the cache: the sequence goes into running, and the sampled token becomes its first output token ({{cite csrc/engine/scheduler.hpp:937-953}}, {{cite csrc/engine/scheduler.hpp:969-990}}).
  • More prompt is left: the sequence goes back to the front of waiting, with no output ({{cite csrc/engine/scheduler.hpp:1011-1020}}).

Step 5: decode steps add tokens

In each decode step, a running sequence sends its last token plus its draft tokens. After the step, the accepted drafts and the new sampled token are appended one by one. The stop check runs after each token:

So there are three stop conditions: the EOS token (unless ignore_eos), a length above max_model_len, and max_tokens output tokens. The EOS id is the tokenizer EOS that the engine gives to the scheduler ({{cite deepinfer/engine/llm_engine.py:312}}). SamplingParams has no stop strings and no list of stop ids ({{cite deepinfer/sampling_params.py:47-62}}).

Step 6: preemption: stop or recompute

If a decode step finds no free block, the scheduler preempts the running sequence with the most output tokens ({{link concepts/scheduler}}). _preempt has two policies:

  • Stop. Status FINISHED_PREEMPTED, reason "insufficient_system_resource". This is the EngineArgs default ({{cite deepinfer/engine/arg_utils.py:40}}). A sequence with a structured-output status other than 0 always stops, because the code cannot recompute the grammar state ({{cite csrc/engine/scheduler.hpp:770-771}}).
  • Recompute. The sequence keeps all its tokens, prompt and output. It loses its blocks, gets status WAITING, and goes to the front of the queue. Its next prefill reads the prompt and the outputs so far. The offline LLM uses this policy ({{cite deepinfer/entrypoints/llm.py:68}}).

reset_for_recompute resets the cache counters, the in-flight counters and the draft state ({{cite csrc/engine/sequence.hpp:307-311}}).

Step 7: a finished sequence leaves the engine

A sequence that finishes in a decode step stays in running until the next decode schedule. Then free_finished_seqs takes it out. It also gives back the draft-info slot, if process_outputs did not give it back already ({{cite csrc/engine/scheduler.hpp:992-994}}):

The finished list goes out with that step. In pre_sampler_sync, the engine calls finalize_seq for each one, which frees the KV blocks and the state slot ({{cite deepinfer/engine/llm_engine.py:844-846}}, {{cite deepinfer/engine/llm_engine.py:804-806}}, {{cite csrc/engine/scheduler.hpp:738-745}}).

Step 8: the user sees RequestOutput objects

For every new token, build_request_outputs makes one {{term request-output | RequestOutput}}:

finish_reason comes from the status ({{cite csrc/engine/sequence.hpp:45-64}}). It is an empty string while the sequence runs. Only the last output of a finished request has finished=True ({{cite csrc/engine/outputs.hpp:247-251}}). An ignored sequence (too long, aborted in the queue, failed, or preempted with stop) gets one output with its last token id and its reason ({{cite csrc/engine/outputs.hpp:297-304}}).

is_finished is a comparison: every status from FINISHED_STOPPED on counts as finished ({{cite csrc/engine/sequence.hpp:43}}). Translated, the comment on the preempted reason says: "if the KV cache is about to overflow, stop the task with the most KV cache" ({{cite csrc/engine/sequence.hpp:56}}). The code picks by output length, not by total KV use ({{cite csrc/engine/scheduler.hpp:624-625}}).

An abort of a running sequence makes no output. abort_sequence only sets the status. The in-flight step skips the sequence because it is finished ({{cite csrc/engine/scheduler.hpp:905-915}}). The next decode schedule puts it into finished_seqs, and build_request_outputs makes outputs only for scheduled and ignored sequences ({{cite csrc/engine/outputs.hpp:194-304}}). So the caller does not get an output with "abort" for it. A sequence aborted in waiting leaves as an ignored sequence and gets one. This site derived this from the code and did not run it.

Cost. The new prefill reads len - 0 tokens: the whole prompt and all outputs ({{cite csrc/engine/scheduler.hpp:372}}). A sequence with a 20000-token prompt and 900 outputs reads 20900 tokens again. Its first new output comes from that prefill, so the output list continues without a gap.

Preempted while in flight. With ZOS, the scheduler can preempt a sequence whose previous decode step is still on the device. When that step is processed later, the sequence has status WAITING. process_outputs and process_MTPInfo skip it, so the old tokens do not move the counters ({{cite csrc/engine/scheduler.hpp:917-925}}, {{cite csrc/engine/scheduler.hpp:1214-1219}}).

ZOS async: a seq that _preempt preempted for recompute while this step was still in flight (only in decode steps; in-flight seqs of a prompt step are not in running, so they cannot be preempted). _preempt already reset its counters and put it at the head of waiting. The output of this step is void: skip all bookkeeping, to avoid a second enqueue and a wrong advance of cache.num_tokens.
  1. EOS. token_id == eos_token_id and not ignore_eos gives "stop" ({{cite csrc/engine/scheduler.hpp:1038-1041}}). eos_token_id is the tokenizer EOS, given to the scheduler at start-up ({{cite deepinfer/engine/llm_engine.py:312}}). In the default "release" mode, the tokenizer loader accepts only a tokenizer whose EOS has id 1 ({{cite deepinfer/hugging_face/tokenizer.py:38}}, {{cite deepinfer/hugging_face/tokenizer.py:121}}).
  2. Model length. More than max_model_len tokens in the sequence (prompt + output) gives "length" ({{cite csrc/engine/scheduler.hpp:1043-1046}}).
  3. Output length. get_output_len() == max_tokens gives "length" ({{cite csrc/engine/scheduler.hpp:1048-1051}}). max_tokens defaults to 16, and 0 becomes 1 ({{cite deepinfer/sampling_params.py:53}}, {{cite deepinfer/sampling_params.py:69-71}}).

Where the EOS id is also used. add_request writes the same id into SamplingParams.eos_id ({{cite deepinfer/engine/llm_engine.py:527}}). The sampler uses it in two places: to forbid EOS as the first token when first_n_token_no_eos == 1 ({{cite csrc/engine/prepare_sample.cpp:20-22}}, {{cite csrc/engine/prepare_sample.cpp:192-195}}), and as the stop token during draft verification ({{cite csrc/engine/prepare_sample.cpp:217-218}}).

No stop strings. SamplingParams.__init__ has no stop or stop_token_ids argument ({{cite deepinfer/sampling_params.py:47-62}}). To stop on other text, a caller must check the outputs and call abort_request.

Order. The checks run after every appended token, in the order EOS, model length, output length. With 2 accepted drafts, the sequence gets up to 3 tokens. If the first draft is EOS, the loop stops there, and the other 2 tokens are not appended ({{cite csrc/engine/scheduler.hpp:982-990}}). The output objects follow: pushed_tokens_before_finish limits them to the appended tokens ({{cite csrc/engine/outputs.hpp:232-234}}).

Grammar failure. If the structured-output state is -1, the sequence gets FINISHED_SO_FAILED and one token with id 0 ({{cite csrc/engine/scheduler.hpp:976-980}}).

What can go wrong

In this release, the engine always has an image processor, so the offline API gives every request a multimodal dict ({{cite deepinfer/entrypoints/llm.py:158-159}}). Every sequence starts as not schedulable, and it waits for one round trip through the image worker ({{cite csrc/engine/pybind_sequence.cpp:35}}).
  • Short outputs. The default max_tokens is 16 ({{cite deepinfer/sampling_params.py:53}}). generate() with no sampling_params uses this default.
  • No stop strings. A stop word in the prompt template does not end the request. Only EOS and the two length limits do.
  • Preempted requests that stop. With EngineArgs defaults, a preempted request ends with "insufficient_system_resource". A request with a structured-output status other than 0 ends this way with any setting ({{cite csrc/engine/scheduler.hpp:770-780}}).
  • Recompute cost. A recomputed sequence reads all its tokens again. Many preemptions of long sequences can cost more device time than they save.
  • Prompt too long. The request ends at its first prefill attempt with "prompt_length_exceeded" ({{cite csrc/engine/scheduler.hpp:377-385}}).
  • No final output after an abort. A running sequence that is aborted gets no output with "abort" (deep dive "Every status").

Why it matters. The status and the finish reason are the only things that tell a user why a request ended. To read the logs, the metrics and the outputs, you must know which code path sets each value.

Which three conditions end a running request normally?

The EOS token (unless ignore_eos), a length above max_model_len, and max_tokens output tokens. _check_stop tests them after each appended token ({{cite csrc/engine/scheduler.hpp:1035-1052}}).

 What does a preempted sequence keep when the offline LLM recomputes it?

All its token ids, prompt and output, and its settings. It loses its KV blocks, its state slot and its draft state, and goes to the front of waiting ({{cite csrc/engine/scheduler.hpp:782-787}}, {{cite csrc/engine/sequence.hpp:307-311}}).

 A request has a 300-token prompt, and the budget of the step is 256 with chunked prefill. What is its status after the first prefill step, and where is it?

WAITING, at the front of waiting. Only the last chunk sets RUNNING ({{cite csrc/engine/scheduler.hpp:522-526}}). After the step, process_outputs sees 256 < 300 cached tokens and puts it back at the front ({{cite csrc/engine/scheduler.hpp:1011-1020}}). It already holds 3 blocks for the whole prompt.

 A decode step accepts 3 drafts, and the second accepted draft is the EOS token. How many tokens are appended, and what is the finish reason?

Two: the first draft and the EOS draft. _check_stop sets FINISHED_STOPPED after the EOS token, and the loop breaks ({{cite csrc/engine/scheduler.hpp:982-990}}). The reason is "stop".

 The user aborts a request while it is in running, with ZOS on. Does the user get a RequestOutput with finish_reason == "abort"?

No. The abort only sets the status ({{cite csrc/engine/scheduler.hpp:152}}). The in-flight step skips finished sequences ({{cite csrc/engine/scheduler.hpp:905-915}}). The next decode schedule moves the sequence to finished_seqs, and build_request_outputs makes outputs only for scheduled and ignored sequences ({{cite csrc/engine/outputs.hpp:194-304}}). A request aborted in waiting does get one, as an ignored sequence. See the deep dive "Every status".
