DeepEP dispatch sends each token to the ranks of its experts, DeepGEMM runs grouped GEMMs there, and DeepEP combine brings the results back. --- Each EP rank holds an equal part of the expert slots. DeepEP sends every token to the ranks of its k experts and then brings the results back.

The idea

An MoE layer has many {{term routed-expert | routed experts}}. With {{term expert-parallelism}} (EP), each {{term rank}} of the EP group holds only some of them. The other parts of the model are on every rank. Attention uses {{term data-parallelism}}: each rank has its own requests. The docs say "attention uses data parallelism (#DP = #EP)" ({{cite doc/inference_deployment_qa.md:33}}).

So the tokens of a rank need experts that are on other ranks. One MoE layer has three parts:

  1. Dispatch. Each rank sends one copy of each token to every rank that holds one of its k experts. This is an all-to-all {{term collective}}.
  2. Expert compute. Each rank now has rows from many ranks, sorted by local expert. One {{term grouped-gemm}} computes all local experts at once.
  3. Combine. The results go back to the rank of the token. There, the k results of each token are added with their routing weights. The output of the {{term shared-expert}} is also added.

DeepInfer uses {{term deepep | DeepEP}} for dispatch and combine, and DeepGEMM for the grouped GEMMs. Both are {{term vendor-library | vendor libraries}}. This page explains only how DeepInfer calls them.

Why do this? The docs give the reason: EP "increases batch size and GPU matrix-multiplication efficiency, and therefore throughput" ({{cite doc/inference_deployment_qa.md:29}}). Each expert gets the tokens of all ranks, so its GEMM has more rows.

An everyday comparison. Think of a food court with several kitchens. Each kitchen cooks only some dishes. A waiter takes the order of a table and sends each dish to the kitchen that cooks it (dispatch). Each kitchen cooks all its orders for the same dish together (grouped GEMM). Then the waiter collects the plates for his table (combine). The comparison stops here: in DeepInfer, every "waiter" is also a "kitchen". Each rank does attention for its own requests and also holds experts.

In the code

Step 1: the EP group

EP groups are blocks of ep_size neighbouring ranks. If the EP size equals the world size, the EP group is the world group:

The example script sets the EP size with --ep (default 8). By default it starts one data-parallel rank per EP rank: dp_size = ep_size // cp_size ({{cite examples/offline_inference.py:13-28}}).

Step 2: each rank holds an equal number of slots

Slots are numbered globally. Rank r holds slots r × n_local to (r + 1) × n_local − 1. At start-up, the loader reads the checkpoint weights of exactly those slots ({{cite deepinfer/hugging_face/weights.py:264-267}}). Extra slots hold copies of other experts. The page {{link concepts/eplb}} explains them.

Step 3: one EP buffer per process

Before the first step, every MoE layer asks for its communication buffer. On the DeepEP path, this is a DeepEP EPBuffer:

All layers share one buffer. The first call makes it, and later calls only check that it is large enough ({{cite deepinfer/model_executor/parallel_utils/userbuffer.py:81-85}}). The page {{link code/userbuffer}} explains the buffer manager.

Step 4: dispatch

  • Line 471: dispatch and combine use DEEPINFER_USERBUFFER_COMM_SMS {{term sm | SMs}}.
  • Line 474: DeepEP adds the received token counts into the EPLB counter of this layer.
  • Line 476: the buffer limit differs for prefill and decode steps.
  • Line 477: DeepGEMM gives the row alignment of each expert group.
  • Line 486: do_expand=True. The receiver gets one row per (token, expert) pair, not one row per token.

The layer waits for the result and gets four values: the received rows, their expert ids and weights, and a handle ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:585}}). handle.psum_num_recv_tokens_per_expert tells the grouped GEMM where each local expert group ends.

Step 5: the grouped GEMMs

  1. The first grouped GEMM computes the gate and up halves of all local experts at once. The output is BF16.
  2. swiglu_forward_and_per_token_cast does the {{term swiglu | SwiGLU}} activation. It also gets the routing weights (line 440) and casts the result to FP8.
  3. The second grouped GEMM (down) gives one BF16 row of the hidden size for each received row.

With FP8 activations, the GEMM is m_grouped_fp8_fp4_gemm_nt_contiguous, with blocks of 32 on both sides ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:118-128}}). Lines 431-434 free the received rows after the first GEMM, to save memory.

Step 6: shared expert and combine

The code captures an event after the routed experts (line 601). Then it starts the shared expert inside limit_num_sms on GPU, which gives the shared expert fewer SMs. Then it calls combine, with the event as previous_event and the shared output as bias ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:501-509}}). The event comes from before the shared expert, so it covers only the routed experts. When the combine transfer runs on the device, and when DeepEP adds the bias, is decided inside DeepEP. The result is BF16 [T, hidden] for the own tokens of this rank.

Step 7: prefill and decode

The same code runs for prefill and decode. Two arguments of dispatch change ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:476}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:485}}):

The steps on this page are the DeepEP path. Inside one {{term nvlink-domain}}, DeepInfer uses mega-MoE instead: one DeepGEMM call does all seven steps. With the released checkpoint format, GPU layers use mega-MoE when the EP group fits in the NVLink domain. Ascend layers always use it. See {{link concepts/mega-moe}}.

A worked example with the settings of examples/offline_inference.py: max_num_seqs=4, max_num_batched_tokens=32768, --ep 8 ({{cite examples/offline_inference.py:13}}, {{cite examples/offline_inference.py:52-54}}), and the default nextn = 5.

  1. A decode step has at most 4 × (1 + 5) = 24 tokens per rank. So num_max_tokens_per_rank = 24 in decode.
  2. A prefill step has at most 32768 // 1 = 32768 tokens per rank.
  3. With a toy k = 8 and 8 ranks, dispatch on each rank makes 24 × 8 = 192 rows in a full decode step. Rows for local experts stay on the rank. On average each rank also receives 192 rows, but a rank with hot experts receives more.

The real k, H and I are in the checkpoint config.json, not in the repository.
  • Size. The buffer is sized for max_num_tokens per rank. For a NORMAL engine, this is the prefill limit, because the engine does both prefill and decode. Only a COMPLETION engine uses the decode limit ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:175}}).
  • FP8 dispatch. use_fp8_dispatch is true with FP8 activations. Then dispatch sends FP8 rows and their scales.
  • Batch invariance. With DEEPINFER_BATCH_INVARIANT on and EPLB rearrangement on, DeepInfer passes allow_multiple_reduction=False (line 79).
  • SM count. With DEEPINFER_USERBUFFER_COMM_SMS=0 (the default), lines 86-90 compute a value and write it back into envs.

An example for a GPU with 148 SMs: compute_num_sms = min(32, 148 // 4) = 32. The communication SMs are min(theoretical, 148 − 32) = min(theoretical, 116). DeepEP gives the theoretical value from the expert count and k.

The shared expert runs inside limit_num_sms, which sets DeepGEMM and tile_kernels to current DeepGEMM SM count − comm SMs and restores the old value after ({{cite deepinfer/model_executor/parallel_utils/userbuffer.py:39-51}}).

Dispatch and combine are collectives over the EP group. Every EP rank must call them in every MoE layer of every step, also with no tokens. A rank with no work runs a placeholder step for this reason ({{cite deepinfer/worker/worker.py:125-127}}). The page {{link concepts/dp-step-votes}} explains how the data-parallel ranks agree on the step type.

A rank with zero received rows is valid. The code notes it: "num_expanded_tokens can be 0" ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:413-415}}).

The DFlash draft layers of speculative decoding also have MoE layers. They use the same DeepseekMoE class ({{cite deepinfer/model_executor/models/mtp/dflash.py:389-392}}), but the expert count and k come from other config fields: dspark_n_routed_experts and dspark_num_experts_per_tok ({{cite deepinfer/hugging_face/config.py:187-190}}). The loader rounds their extra experts separately ({{cite deepinfer/model_executor/model_loader.py:102-106}}). They share the one EPBuffer with the main layers ({{cite deepinfer/model_executor/models/deepseek.py:422-428}}).

What can go wrong

  • Slots do not divide by the EP size. DeepseekMoE asserts it ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:203-205}}). The loader prevents it: it rounds the extra experts up so that the total divides by ep_size ({{cite deepinfer/model_executor/eplb/__init__.py:21-28}}).
  • A hot expert. The rank of a busy expert receives more rows and finishes last. All ranks wait for it at combine. See {{link concepts/eplb}}.
  • A rank that skips a step. Dispatch is a collective. If one EP rank does not run the layer, the others wait. This is why placeholder steps exist.
  • Memory. In a NORMAL engine, the EP buffer is sized for the prefill token limit. A large max_num_batched_tokens makes a large buffer on every rank.
  • CPU sync in prefill. do_cpu_sync is true for prefill. The TODO comment says that it makes YOCO compaction a CPU bottleneck, so compact mode turns it off ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:482-485}}).

Why it matters. Expert parallelism lets many devices share the expert weights and gives each expert large GEMMs. The cost is two all-to-all collectives per MoE layer, and the slowest rank sets the speed of all ranks.

What are the three parts of an MoE layer with expert parallelism?

Dispatch: DeepEP sends tokens to the ranks of their experts. Expert compute: grouped GEMMs on each rank. Combine: DeepEP returns the results and adds them ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:576-610}}).

 How many expert slots does each rank hold?

num_physical_experts // ep_size, where physical = routed + extra ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:199-201}}).

 Where does the shared expert output join the routed outputs on the DeepEP path?

In combine. DeepInfer passes it as bias=shared_hidden_states to EPBuffer.combine ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:505}}). The shared expert runs on the own tokens of the rank and does not travel.

 A NORMAL engine runs with max_num_seqs=4, max_num_batched_tokens=32768, CP size 1 and nextn = 5. Which num_max_tokens_per_rank does dispatch get in a decode step, and which size is the EP buffer made for?

Dispatch gets max_num_decoding_tokens = 4 × (1 + 5) = 24 ({{cite deepinfer/model_executor/model_loader.py:119}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:476}}). The buffer is made for max_num_tokens, which is the prefill limit 32768 for a NORMAL engine ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:175}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:317-320}}).
