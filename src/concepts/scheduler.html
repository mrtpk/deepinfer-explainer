It starts prefills only at attempt points, cuts long prompts into chunks, gives KV blocks, and preempts sequences when the blocks run out. --- In each engine step, the C++ {{term scheduler}} picks a {{term prefill}} batch or a {{term decode}} batch, never both, and gives each sequence its KV blocks.

The idea

The engine works in {{term engine-step | steps}}. Before each step, LLMEngine.step() asks the scheduler for a batch ({{cite deepinfer/engine/llm_engine.py:885-887}}). The scheduler answers three questions:

  1. Is this step a prefill step or a decode step?
  2. Which {{term sequence | sequences}} run, and how many query tokens does each one send?
  3. Which {{term kv-block | KV blocks}} does each sequence get?

DeepInfer never puts prefill and decode work into the same step. A prefill step reads new prompts and writes their KV cache. A decode step adds new tokens to the sequences that already run. While a prefill step runs, the running sequences make no progress. So the scheduler does not start a prefill in every step. It tries only at fixed points.

The main rules are short:

  • {{term attempt-point | Attempt points}}. A prefill can start only when the decode counter decode_step is a multiple of 70 (an ALL point) or of 100 (an ANY point). A prefill step sets the counter back to 0, which is again an attempt point.
  • {{term token-budget | Token budget}}. One step has at most max_num_batched_tokens query tokens. With {{term chunked-prefill}}, the scheduler cuts a long prompt to fit.
  • {{term cache-watermark | Watermark}}. A new prefill starts only if 90 % or less of the KV blocks are in use.
  • Slots. At most max_num_seqs sequences hold a place in the running set.
  • Decode order. A decode step serves the sequences with the fewest output tokens first. If no block is free, it {{term preemption | preempts}} the sequence with the most output tokens.

An everyday comparison. Think of a bus on a loop route. Most of the time the bus drives, and every passenger moves on (decode). At fixed stops, the bus stops to let new passengers in (prefill). While it stops, the passengers inside do not move. If the bus is full, the driver asks one passenger to leave. The comparison stops being true here. That passenger keeps a record of the trip so far, but must ride the whole route again from the start (recompute).

The simulator is a small model, not the real engine. It keeps these rules from the code:

  • attempt points and the counter reset ({{cite csrc/engine/scheduler.hpp:308-322}}, {{cite csrc/engine/scheduler.hpp:676-681}});
  • the 90 % watermark, the prefill limits and the chunks ({{cite csrc/engine/scheduler.hpp:360-546}});
  • the decode order and preemption ({{cite csrc/engine/scheduler.hpp:622-645}});
  • the late release of the blocks of finished sequences.

It leaves out these parts:

  • Real blocks hold 128 tokens, and a real cache has thousands of blocks.
  • A real decode step sends 1 + 5 draft tokens per sequence and reserves blocks for them. The toy sends 1 token.
  • The toy runs with ZOS off and one data-parallel rank, so the two votes always agree with the local answer.
  • Every toy request is schedulable at once. In this release, each request first waits for the multimodal worker ({{link concepts/request-lifecycle}}).
  • The toy has no EOS token. Every request runs until it has max_tokens output tokens.
  • When two sequences have the same output length, the toy takes the lower request number first. std::sort in the code does not fix this order.
  • With chunked prefill off, the toy accepts a budget below max_model_len. The real SchedulerConfig refuses that combination ({{cite deepinfer/config.py:209-212}}).

In the code

Step 1: one call per engine step

Python calls Scheduler.schedule(pool) once per step. It runs _schedule(), then turns the result into one {{term sequence-metadata | SequenceMetadata}} per sequence ({{cite csrc/engine/scheduler.hpp:667-736}}). _schedule() first releases the Python lock and takes the locks of both block managers:

The SchedulerOutputs of the previous step borrows the storage of these three vectors (see the pybind properties clone_states/clone_blocks/zero_states). Python must use them before the next schedule; here they are cleared and used again. A PROMPT engine only does prefill. It returns an (empty) prefill result, also if no request was scheduled. A COMPLETION engine only does decode.

The offline LLM makes a NORMAL engine, because that is the EngineArgs default ({{cite deepinfer/engine/arg_utils.py:41}}). The rest of this page is about the NORMAL case.

Step 2: prefill step or decode step

A prompt step sets decode_step to 0 (see schedule()). So the step right after a prefill has decode_step == 0 and is again an ALL point: to prefill again, every rank must have work. decode_step is the same on every rank, so the number and the meaning of the votes match in the group, and the all-reduce does not hang. ANY: the prefill starts if any rank wants it. ALL: the prefill starts only if all ranks want it. Second vote: confirm that some rank really scheduled a prefill. "want" only looked at the waiting queue, but _schedule_prefill can still come back empty (slots full, not enough KV blocks). If the whole group comes back empty, the step must be a decode step. A forced empty prompt step would set decode_step to 0; the next step would vote and come back empty again, and with running full and waiting not empty this is an endless loop. Some rank in the group does a prompt step: this rank runs an empty prompt step with it, to keep the step type the same.
  1. Lines 308-311: no attempt point, so this is a decode step. No vote runs.
  2. Line 313: this rank wants a prefill if the cache usage is 0.9 or less and the first waiting sequence is {{term schedulable}}. The watermark is the constant GPU_CACHE_PREFILL_WATERMARK = 0.9f ({{cite csrc/engine/scheduler.hpp:80}}).
  3. Lines 315-319: the first vote. Both cases use an all-reduce MIN. At an ANY point each rank sends 0 if it wants, so the MIN is 0 if one rank wants. At an ALL point each rank sends 1 if it wants, so the MIN is 1 only if all ranks want.
  4. Lines 324-326: only a rank that wants a prefill runs _schedule_prefill.
  5. Line 332: the second vote. If no rank got a batch, the step becomes a decode step.
  6. Line 340: a rank with no batch runs an empty prefill step, so that all ranks run the same kind of step.

The defaults are DEEPINFER_PREFILL_ATTEMPT_INTERVAL = 70 and DEEPINFER_PREFILL_ANY_ATTEMPT_INTERVAL = 100 ({{cite deepinfer/environ.py:174-178}}). The page {{link concepts/dp-step-votes}} explains why all data-parallel ranks must run the same kind of step.

Step 3: the prefill batch

_schedule_prefill looks at the waiting queue from the front. It stops at the first sequence that cannot start, so a later, smaller request cannot pass it.

A sequence that was already dead before it entered the queue does not run a prefill. It goes into ignored_seqs and returns with its finish_reason.
  1. Lines 363-367: a sequence that is aborted, or failed in the image or grammar step, leaves the queue as an ignored sequence.
  2. Lines 369-371: a sequence that is not schedulable stops the loop.
  3. Lines 374-385: a new sequence (no block table yet) longer than prompt_limit ends as FINISHED_IGNORED. prompt_limit is max_model_len with chunked prefill, else min(max_model_len, max_num_batched_tokens) ({{cite csrc/engine/scheduler.hpp:112}}).
  4. Lines 386-396: the block check. LATER (not enough free blocks now) stops the loop. NEVER (more blocks than the whole cache) ends the sequence as FINISHED_IGNORED.

Lines 398-438 handle a forked sequence, whose branch_id starts with _. Only Scheduler.fork_seq makes such sequences ({{cite csrc/engine/pybind_scheduler.cpp:123-124}}). No file in the deepinfer package calls it. Only examples/benchmark.py uses it, to copy one cached prompt to a whole batch ({{cite examples/benchmark.py:331-352}}). Two more limits follow:

Line 440: the running sequences count against max_num_seqs (max_num_prompts is the same value, {{cite csrc/engine/scheduler.hpp:114}}). Lines 444-449: the sum of the full lengths in one prefill step must stay under DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K. If the variable is not set, the limit is 2**30 ({{cite deepinfer/environ.py:9}}, {{cite deepinfer/engine/llm_engine.py:317}}).

Step 4: the chunk size

The scheduler first compares the prompt with the rest of the token budget:

The first workload. It decides if the prompt is chunked. The workload after all limits. Cut the prompt (to the base length) only if this condition is true: with this prompt, the step goes over the base length. Note: count the CP padding when you compute the tokens that are left.

So the chunk is simply "all the budget that is left", rounded down to a multiple of cp_align. cp_align is 1 without {{term context-parallelism}}, and 2 × cp_size with it ({{cite csrc/engine/scheduler.hpp:90}}). Then two adjustments can make the chunk shorter or longer:

Adjust the cut position for multimodal input. A request waits in the queue but cannot be scheduled; this must not happen (post_adjust). All other limits are hard limits. Here, only check that seqlen_q meets the minimum. If not, do not schedule.
  1. Lines 477-486: a caller can give chunk checkpoints, positions where a chunk must end. The chunk ends at the next checkpoint if it would pass it. In this release, add_request(chunk_checkpoints=...) can set them ({{cite deepinfer/engine/llm_engine.py:615-616}}), and examples/benchmark.py sets one to stop a prefill at an exact length ({{cite examples/benchmark.py:364-370}}).
  2. Lines 488-493: the chunk must not end inside an image. For the first sequence of the batch, _adjust_chunk_size first tries to make the chunk longer. If that breaks the budget, it makes the chunk shorter.
  3. Lines 504-507: a cut prompt with chunked prefill off stops the loop. The request waits for a later step.
  4. Lines 509-511: a chunk must have at least max(lookahead_tokens, 1) tokens.

Step 5: the side effects

The scheduler decided to schedule this seq: all operations with side effects come below.
  1. Line 515: the chunk length goes into the budget, rounded up to cp_align.
  2. Lines 518-520: the first chunk takes the blocks and one {{term state-slot}} for the whole prompt, through allocate_seq ({{cite csrc/engine/block_manager.hpp:207-214}}). Later chunks need no new blocks.
  3. Lines 522-526: only a full prompt, or the last chunk, makes the sequence RUNNING and gives it an {{term mtp}} info slot.
  4. Lines 533-537: a chunk records the rest in chunked_rest_len.
  5. Lines 543-545: in a NORMAL engine, a chunk ends the batch.

After the step, process_outputs moves a sequence with a complete prompt into running and appends its first token. An unfinished chunk goes back to the front of waiting ({{cite csrc/engine/scheduler.hpp:951-953}}, {{cite csrc/engine/scheduler.hpp:1011-1020}}). So the next attempt continues the same prompt first.

Step 6: the decode batch

LCFS (last come, first served). decode: running still has queued seqs; N are scheduled and M are left; this must not happen.
  1. Lines 624-625: sort running by output length, the longest output first.
  2. Lines 628-629: take sequences from the end of the list, so the shortest output comes first. The comment calls this LCFS: the newest sequences usually have the shortest outputs.
  3. Lines 630-634: while no block is free and more than one sequence is left, preempt from the front: the longest output.
  4. Lines 635-640: if a block is free, _append_slot gives the sequence one more block when it needs one ({{cite csrc/engine/scheduler.hpp:817-828}}). If not, the sequence itself is preempted.
  5. Lines 648-652: the batch is sorted by total length. MTPVarlen sets the query tokens per sequence: 1 plus the number of draft tokens, so 6 with the defaults ({{cite csrc/engine/mtp_varlen.hpp:153-157}}).

Before this loop, the decode branch does two clean-ups. It removes finished sequences from running ({{cite csrc/engine/scheduler.hpp:562}}). It also removes finished sequences from anywhere in waiting ({{cite csrc/engine/scheduler.hpp:569-577}}). Both go out with the step result.

Step 7: preemption

The comment above _schedule_decode says, translated: "when blocks are not enough, preempt the seq with the shortest output" ({{cite csrc/engine/scheduler.hpp:556-557}}). The code sorts the longest output to the front and preempts from the front ({{cite csrc/engine/scheduler.hpp:624-634}}). This site describes the code.

 COMPLETION with !stop_preempted_request was already blocked in the constructor. SO requests cannot be recomputed after preemption yet; they end at once. Reset the rolling state of the seq (cache.num_tokens, in-flight counters, MTP state). The list is in Sequence::reset_for_recompute.

There is no swap to CPU memory. A preempted sequence can stop with FINISHED_PREEMPTED. Or it keeps its tokens, loses its blocks, and waits at the front of the queue for a new prefill ({{term recompute}}). EngineArgs has stop_preempted_request=True ({{cite deepinfer/engine/arg_utils.py:40}}). The offline LLM sets it to False ({{cite deepinfer/entrypoints/llm.py:68}}).

Step 8: after the decision

A prefill step sets decode_step to 0. A decode step stores its batch as the new running list and adds 1 to decode_step. An empty decode step also counts. Then the loop in lines 692-729 makes one SequenceMetadata per sequence. It holds seqlen_q (query tokens) and seqlen_k (cached + in flight + query). The loop also reserves max_seqlen_q = nextn + 1 in-flight tokens on the sequence ({{cite csrc/engine/scheduler.hpp:689}}, {{cite csrc/engine/scheduler.hpp:696-697}}, {{cite csrc/engine/scheduler.hpp:726}}).

The result is a {{term scheduler-outputs | SchedulerOutputs}}: scheduled_seqs, prompt_run, num_batched_tokens, finished_seqs, ignored_seqs, seqlens_q, statistics, and the clone lists ({{cite csrc/engine/scheduler.hpp:45-77}}).

This is Scheduler::schedule for a NORMAL engine, with the line of each statement. Variables keep their C++ names.

def schedule(pool):                                         # 667
    clone_states, zero_states, clone_blocks = [], [], []    # 282-284
    ds = decode_step
    is_any = ds != 0 and ds % prefill_any_attempt_interval == 0   # 308
    is_all = ds % prefill_attempt_interval == 0                   # 309
    if not (is_any or is_all):
        out = schedule_decode()                             # 310-311
    else:
        want = cache_usage() <= 0.9 and waiting and waiting[0].schedulable  # 273, 313
        if is_any:  ok = allreduce_min(0 if want else 1) == 0   # 315-316 (ANY wins)
        else:       ok = allreduce_min(1 if want else 0) == 1   # 317-318
        if not ok:
            out = schedule_decode()                         # 320-321
        else:
            out = schedule_prefill() if want else None      # 324-326
            if allreduce_min(0 if out else 1) != 0:         # 332
                out = schedule_decode()                     # 333-334
            elif out is None:
                out = empty_prompt_step()                   # 340
    assert out.num_batched_tokens <= max_num_batched_tokens  # 671-673
    if out.prompt_run: decode_step = 0                      # 676-677
    else:              running = out.scheduled_seqs; decode_step += 1   # 679-680
    for seq, q in zip(out.scheduled_seqs, out.seqlens_q):   # 692-729
        k = seq.cache.num_tokens + seq.total_inflight_tokens + q
        assert position_end <= runtime_max_model_len        # 700-705
        metadata.append(pool.allocate(seq, out.prompt_run, q, k, golden))
        seq.start_inflight_step(nextn + 1)                  # 726
    return metadata, out

def schedule_prefill():                                     # 351
    scheduled, ignored, n_curr, tokens = [], [], len(running), 0
    while waiting:
        seq = waiting[0]
        if seq.status in (ABORTED, VE_FAILED, SO_FAILED): ignore(seq); continue  # 363-368
        if not seq.schedulable: break                       # 369-371
        if not seq.block_table:                             # 374
            if seq.len > prompt_limit: ignore(seq, IGNORED); continue          # 377-385
            st = can_allocate(blocks_for(seq)) and a state slot                  # 386
            if st == LATER: break                           # 387-388
            if st == NEVER: ignore(seq, IGNORED); continue  # 389-396
        if n_curr + 1 > max_num_seqs: break                 # 440-442
        if sum_k_left < seq.len: break                      # 444-446
        work = seq.len - seq.cache.num_tokens
        q = min(work, (budget - tokens) // cp_align * cp_align)                # 470-475
        q = cut at the next chunk checkpoint                # 477-486
        q = adjust so that no image is cut                  # 488-493
        if q == 0: break                                    # 494-502
        if q < work and not chunked_prefill: break         # 504-507
        if q < max(lookahead_tokens, 1): break              # 509-511
        tokens += round_up(q, cp_align)                     # 515
        if not seq.block_table: allocate blocks + state slot   # 518-520
        if q == work: n_curr += 1; seq.status = RUNNING; give MTP slot   # 522-526
        scheduled.append(seq); waiting.popleft()            # 528, 541
        if q < work: break                                  # 543-545
    return outputs(prompt_run=True) if scheduled or ignored else None     # 548-553

def schedule_decode():                                      # 559
    finished = [s for s in running if s.finished]; remove them    # 562
    ignored = [s for s in waiting if s.finished]; remove them     # 569-577
    move forked seqs from prompted to running               # 595-620 (unused here)
    running.sort(key=output_len, reverse=True)              # 624-625
    l, r, batch = 0, len(running), []
    while l < r and len(batch) < max_num_seqs:             # 628
        seq = running[r - 1]
        while no free block and r - l > 1:                  # 630
            preempt(running[l]); l += 1                     # 631-633
        if a block is free: append_slot(seq); batch.append(seq)   # 635-637
        else: preempt(seq)                                  # 638-639
        r -= 1
    batch.sort(key=total_len, reverse=True)                 # 648-649
    seqlens_q = mtp_varlen.schedule(batch)                  # 652
    return outputs(prompt_run=False, batch, finished, ignored)

Two details are easy to miss. First, a sequence that finished in step N still counts in running during a prefill step, because only the decode branch removes it. So it still takes one of the max_num_seqs slots. Second, its blocks go back to the free list in pre_sampler_sync of the decode step that removed it ({{cite deepinfer/engine/llm_engine.py:844-846}}). That step's own block checks still see the blocks as used.

The settings come from the offline example: max_num_batched_tokens=32768, max_model_len=32768, max_num_seqs=4 ({{cite examples/offline_inference.py:52-54}}), and chunked prefill on ({{cite examples/_config.py:120}}). The block size is 128 tokens ({{cite deepinfer/model_executor/model_metadata_utils.py:133-135}}). Assume 1000 KV blocks, one DP rank, and five schedulable requests in waiting: A (41 prompt tokens), B (20000), C (15000), D (300), E (50).

Step 1. decode_step = 0, an ALL point. Usage is 1/1000 (block 0 counts as used), so the rank wants a prefill.

  1. A: ceil(41/128) = 1 block. 41 tokens fit. Budget used: 41.
  2. B: ceil(20000/128) = 157 blocks. 20000 tokens fit in the 32727 that are left. Budget used: 20041.
  3. C: ceil(15000/128) = 118 blocks, all taken now. Only 12727 tokens are left, so C sends a chunk of 12727. chunked_rest_len = 2273. The chunk ends the batch.

Result: seqlens_q = [41, 20000, 12727], num_batched_tokens = 32768. After the step, A and B are in running with one output token each. C is at the front of waiting: [C, D, E]. 276 blocks are in use.

Step 2. decode_step is 0 again, an ALL point. C sends its last 2273 tokens and becomes RUNNING. D needs 3 blocks and sends 300 tokens. E: running.size() = 2, plus C and D, makes 4, so 4 + 1 > 4 stops the loop. Budget used: 2573.

Step 3. Again an ALL point. E is schedulable, so the rank wants a prefill. _schedule_prefill returns nothing, because 4 sequences hold slots. The second vote turns the step into a decode step. A, B, C and D each send 1 token plus 5 placeholder drafts: seqlens_q = [6, 6, 6, 6], 24 tokens. decode_step becomes 1.

Later. Steps 4 to 72 (decode_step 1 to 69) are decode steps with no vote. Suppose A finishes in step 20. Its slot is free after the next decode step, but E still waits for the next attempt point: decode_step = 70 (ALL), in step 73. If the cache is then above 90 %, the next try is at 100 (ANY).

Blocks in decode. A sequence needs ceil((len + total_inflight_tokens + drafts) / 128) blocks ({{cite csrc/engine/sequence.hpp:291-293}}). For B after 300 output tokens with ZOS: len = 20300, 6 tokens of the previous step are still in flight, and 5 drafts. ceil(20311/128) = 159 blocks.

The base cut. q = min(work, (budget - used) / cp_align * cp_align) ({{cite csrc/engine/scheduler.hpp:470-472}}). With context parallelism of size 4, cp_align = 8. Example: 1000 tokens of budget are left and the prompt has 5000 tokens left: q = 1000 / 8 * 8 = 1000. With 1005 left: q = 1000. The budget then grows by ceil(q / 8) * 8 ({{cite csrc/engine/scheduler.hpp:515}}).

Image tokens. In the token list, an image is one MM_TOKEN_IMAGE followed by N MM_TOKEN_IMAGE_PAD tokens. Both ids are above the vocabulary: vocab_size + 2 and vocab_size + 1 ({{cite csrc/engine/sequence.hpp:21-28}}, {{cite csrc/engine/scheduler.hpp:91-92}}).

Adjust the chunk size so that multimodal input is not cut in the middle of an image. In token_ids an image is MM_TOKEN_IMAGE + MM_TOKEN_IMAGE_PAD*N (the IMAGE_START/NEW_LINE/END structure is only in mm_token_type). Protect each image unit. A cut between two images (at an MM_TOKEN_IMAGE) is allowed. Extend forward: skip all IMAGE_PAD (stop at the next MM_TOKEN_IMAGE or at a non-image token). Shrink backward: skip all IMAGE_PAD and the MM_TOKEN_IMAGE (the whole image unit moves to the next chunk). Not inside an image: no change.

Worked example. A prompt has 100 text tokens (positions 0-99), an image at position 100 with 256 pad tokens (101-356), then text. The cache holds 0 tokens, and the budget allows q = 200, so the cut is at k_len = 200.

  1. token_ids[200] is a pad token, and a backward search finds MM_TOKEN_IMAGE at 100. So the cut is inside an image ({{cite csrc/engine/scheduler.hpp:217-230}}).
  2. The sequence is the first of the batch, so the scheduler tries to grow: k_len moves to 357, so q = 357. That is more than the budget (line 489), so it tries again with make_larger = false.
  3. Shrink: k_len moves back over the pads to 101, then over the image token to 100. q = 100. The image goes into the next chunk as one unit.

A cut exactly at an MM_TOKEN_IMAGE is allowed (lines 214-216 say so). So two images next to each other can go into different chunks.

Chunk checkpoints. chunk_checkpoints is a deque of positions. Checkpoints at or before the cached length are dropped. If the chunk would reach or pass the next checkpoint, it ends exactly there, and that checkpoint is removed ({{cite csrc/engine/scheduler.hpp:477-486}}).

The scheduler owns three kinds of slots. Each kind is limited, and each kind has a reserved slot 0.

LATER and NEVER. can_allocate_nolock(n) returns NEVER if n >= num_blocks, OK if n blocks are free, else LATER ({{cite csrc/engine/block_manager.hpp:128-136}}). _can_allocate_with_state also turns OK into LATER when no state slot is free ({{cite csrc/engine/scheduler.hpp:195-201}}).

The watermark in numbers. get_gpu_cache_usage() is (num_blocks - free) / num_blocks ({{cite csrc/engine/scheduler.hpp:830-835}}). Block 0 is never free, so it counts as used. With 1000 blocks, a prefill is possible only with 100 or more free blocks: (1000 - 100) / 1000 = 0.9. With 99 free blocks, usage is 0.901 and no prefill starts.

Shrinking block tables. _append_slot can also free blocks. If the block table is longer than get_num_blocks(), it frees the extra blocks (lines 821-825). This happens when the reserve for drafts and in-flight tokens gets smaller.

The decode check is "one free block". The loop asks can_allocate_single_nolock() before each sequence, also for a sequence that needs no new block ({{cite csrc/engine/scheduler.hpp:630}}, {{cite csrc/engine/scheduler.hpp:635}}). So with 0 free blocks, the scheduler preempts even if the current sequence still has room in its last block.

A decode step sends the last sampled token plus the draft tokens of {{link concepts/speculative-decoding | speculative decoding}}. MTPVarlen::schedule sets seqlen_q per sequence:

  • No performance curve (the default): seqlen_q = 1 + len(draft_tokens) ({{cite csrc/engine/mtp_varlen.hpp:153-157}}). After a prefill, the draft list holds 5 placeholder ids, so the first decode step already sends 6 tokens ({{cite deepinfer/engine/llm_engine.py:706-711}}).
  • With a curve (DSpark): the curve exists only if CUDA graphs are on and DEEPINFER_ENABLE_MTP_VARLEN is set ({{cite deepinfer/worker/base.py:274-281}}). The scheduler sorts all drafts of the batch by their estimated accept rate. Then it picks the total best_bsz with the most expected tokens per millisecond ({{cite csrc/engine/mtp_varlen.hpp:228-258}}). Each sequence gets 1 plus its share of the best drafts (lines 263-266). The page {{link concepts/dspark}} explains the estimates.

Budget. SchedulerConfig makes sure that a full decode batch fits: max_num_batched_tokens >= max_num_seqs × (1 + nextn) ({{cite deepinfer/config.py:224-227}}). With 256 sequences and 5 drafts that is 1536 tokens.

Reserved positions. Each scheduled sequence reserves nextn + 1 in-flight tokens until its result is processed ({{cite csrc/engine/scheduler.hpp:726}}, {{cite csrc/engine/sequence.hpp:244-256}}). With ZOS, the scheduler plans step N+1 before step N is processed, so up to two reserves exist at the same time. This is why runtime_max_model_len adds nextn + (nextn + 1) plus nextn positions to max_model_len ({{cite deepinfer/config.py:11-16}}).

 Run one all-reduce inside dp and return the result (also with dp_size == 1; the caller can skip it).

The tensor is one int32 value. With ZOS, the group is the CPU Gloo group, so the tensor is on the CPU ({{cite csrc/engine/scheduler.hpp:109}}, {{cite deepinfer/engine/llm_engine.py:313}}). Without ZOS, the tensor is on the device.

Example with 4 ranks at decode_step = 70 (ALL): ranks 0-2 want, rank 3 has an empty queue. MIN of [1, 1, 1, 0] is 0, so no prefill. At decode_step = 100 (ANY): MIN of [0, 0, 0, 1] is 0, so all ranks prefill, and rank 3 runs an empty prefill step. The comments give the reason for the two kinds ({{cite csrc/engine/scheduler.hpp:1184-1193}}). ALL points prevent steps in which one rank works and the others run empty prompt steps. ANY points make sure that the prefill of an isolated rank waits at most about 100 decode steps.

Why the decode branch cleans waiting. The comment at lines 564-568 says, translated: "Finished seqs in waiting (aborted, or failed in the image step) can only be removed by the scheduler. _schedule_prefill used to clean them up. Now prefill runs only when want is true on this rank. A rank whose waiting queue holds only such seqs never wants a prefill, so they stay forever. Then has_unfinished stays true and keeps the whole group in empty steps. This rank also blocks every ALL vote. So the decode branch cleans them up too, and scans the whole queue."

What can go wrong

The prefill loop stops at the first sequence that cannot start: not schedulable, not enough blocks (LATER), no slot, or no budget ({{cite csrc/engine/scheduler.hpp:369-371}}, {{cite csrc/engine/scheduler.hpp:387-388}}, {{cite csrc/engine/scheduler.hpp:440-442}}). A small request behind a large one waits too.
  • Long waits for new requests. A request waits for the next attempt point after it becomes schedulable. With one rank, up to 69 more decode steps can run before its prefill. With several DP ranks, an ALL vote fails if one rank has no work, so up to 99 decode steps can run first. In this release, a request first waits for the image worker too ({{link tours/life-of-a-request}}, stop 5).
  • Prompt too long. A prompt above prompt_limit, or one that needs num_blocks or more blocks, ends as FINISHED_IGNORED with a warning in the log ({{cite csrc/engine/scheduler.hpp:377-396}}).
  • Budget below max_model_len. Without chunked prefill, SchedulerConfig raises ValueError ({{cite deepinfer/config.py:209-212}}).
  • Requests stop with insufficient_system_resource. With the EngineArgs default, a preempted request ends. Requests with a structured-output status other than 0 always end when preempted ({{cite csrc/engine/scheduler.hpp:770-780}}).
  • An image larger than the budget. Suppose that the next chunk of the first sequence starts with an image unit that is longer than the budget. Then the shrink gives 0 tokens, and the check at lines 495-500 stops the process. This site derived this case from the code and did not run it.
  • Position limit. schedule() checks every position against runtime_max_model_len and raises if a sequence goes past it ({{cite csrc/engine/scheduler.hpp:700-705}}).
  • Wrong engine combination. A COMPLETION engine with stop_preempted_request=False fails at start-up ({{cite csrc/engine/scheduler.hpp:101-104}}).

Why it matters. The scheduler sets the latency and the throughput of the engine. The attempt interval trades the time to the first token of new requests against the decode speed of the running ones. The watermark and the preemption policy decide how much work is lost when the KV cache is full.

Can one engine step contain both prefill tokens and decode tokens?

No. _schedule returns either the result of _schedule_prefill or of _schedule_decode, and prompt_run marks which one ({{cite csrc/engine/scheduler.hpp:305-341}}). While a prefill step runs, the running sequences wait.

 A decode step has no free KV block. Which running sequence does the scheduler preempt first?

The one with the most output tokens. The list is sorted with the longest output first, and the loop preempts from the front ({{cite csrc/engine/scheduler.hpp:624-634}}). The comment at line 557 says "shortest", but the code does the opposite.

 The token budget is 32768 and 20041 tokens are already in the batch. The next request has a 15000-token prompt and chunked prefill is on. How many tokens does it send, and does the scheduler look at the request behind it?

It sends a chunk of 32768 − 20041 = 12727 tokens ({{cite csrc/engine/scheduler.hpp:470-472}}). The scheduler does not look further: in a NORMAL engine a chunk ends the batch ({{cite csrc/engine/scheduler.hpp:543-545}}). After the step, the request goes back to the front of waiting.

 With the default intervals and one DP rank, the last prefill step was 30 steps ago, and all steps since then were decode steps. A new request arrives now. When is the earliest step in which it can start its prefill?

The next schedule sees decode_step = 30. After 40 more decode steps (decode_step 30 to 69), the step with decode_step = 70 is an ALL point. The prefill starts there if the request is schedulable by then, the cache usage is 0.9 or less, and a slot is free ({{cite csrc/engine/scheduler.hpp:308-313}}, {{cite csrc/engine/scheduler.hpp:440-442}}). If one of these tests fails, the next points are 100 (ANY) and 140 (ALL). In this release, the request also waits for the image worker before it becomes schedulable.

 The cache has 1000 blocks and 99 are free. A short request waits, and the step is an ALL point. Does a prefill start? What changes if one running sequence finishes in this step?

No. Usage is (1000 − 99) / 1000 = 0.901, above the 0.9 watermark, so the rank does not want a prefill ({{cite csrc/engine/scheduler.hpp:313}}, {{cite csrc/engine/scheduler.hpp:830-835}}). A sequence that finishes in this step gives its blocks back only later. The next decode step removes it from running, and pre_sampler_sync of that step frees the blocks ({{cite csrc/engine/scheduler.hpp:562}}, {{cite deepinfer/engine/llm_engine.py:844-846}}). Then the request still waits for the next attempt point. See the deep dives "Blocks, state slots and MTP info slots" and "The whole algorithm in pseudocode".
