This page explains the build, the three submodules, the GIL and lock rules, and the memory that crosses the boundary. --- DeepInfer runs the scheduler and the step bookkeeping in C++. Python reaches that code through one compiled {{term pybind11}} module, deepinfer._C.

The idea

Most of DeepInfer is Python. The entry point, the engine, the workers and the model forward pass are Python code that calls PyTorch and device {{term kernel | kernels}}. One part is C++: the code that decides what each engine {{term engine-step | step}} does, and the code that prepares the inputs for that step. This C++ code is in the folder csrc/.

The C++ code is compiled into one {{term extension-module}}: a .so file that Python imports like a normal module. Its name is deepinfer._C ({{cite setup.py:59-60}}). It has three submodules:

  • _C.engine: the {{term scheduler}}, the {{term block-manager | block managers}}, sequences, output objects, and the functions that prepare model and sampler inputs. This is the largest part: 34 names.
  • _C.cuda_utils: three functions for raw device memory and for memory that another process opens.
  • _C.graph_timer: three classes that time regions inside a captured {{term cuda-graph}}.

Why C++? The code and the docs do not give a direct reason. The deployment doc gives the context: in a decode step, schedule and post-process are "pure CPU logic", and the device sits idle while they run ({{cite doc/inference_deployment_qa.md:270}}). {{term zos | Zero-overhead scheduling}} hides this CPU time behind device work ({{cite doc/inference_deployment_qa.md:274}}). So the CPU time of each step matters. This site does not claim more than that.

An everyday comparison. Think of a shop with a front desk and a stock room. Customers talk only to the front desk (Python). The stock room (C++) keeps the stock lists and counts fast. Items go between the two through one window (the pybind11 module). The comparison stops here: sometimes the stock room lends its own shelf to the front desk instead of a copy of the items. The front desk must finish with that shelf before the next step, because the stock room then uses it again. On this page, such a shelf is a {{term borrowed-view}}.

Step 5: memory that crosses the boundary

Data can cross the boundary in three ways. Each way has a different owner.

C++ lends memory to Python. Some results are borrowed views. The property clone_blocks makes a NumPy array on the scheduler's own vector, with an empty capsule as owner:

[n, 2] int32 (src, dst) block clone pairs; dst = 0 means only give back src, with no copy. Zero-copy borrow of the Scheduler's internal storage. The next schedule() clears it and uses it again: use it up before that, never keep it across steps.

Python gives data to C++. The Sequence constructor copies the prompt token ids into C++ storage. The binding accepts only a C-contiguous int32 NumPy array, with no conversion ({{cite csrc/engine/pybind_sequence.cpp:93-105}}). Its docstring says, translated: "The caller guarantees that the token ids are valid; this constructor only copies the data."

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Two kinds of lock meet at the boundary: the Python {{term gil}} and the C++ mutex of each BlockManager. The base class Lockable has one strict rule:

Holding the GIL when you call this function is forbidden, to avoid a deadlock! Fast path.
  1. Line 16: if the calling thread holds the GIL, TORCH_CHECK fails. Python sees a RuntimeError.
  2. Line 17: the fast path tries the lock without a wait.
  3. Lines 20-27: else it waits for at most 20 seconds (CLOCK_MONOTONIC). After that, TORCH_CHECK fails with "failed to lock mutex".
  4. Line 35: the mutex is an error-check mutex. A second lock from the same thread gives an error, not a hang.

Why no GIL while you lock. The code comment gives only "to avoid a deadlock". The general case is this: thread A holds the GIL and waits for the mutex. Thread B holds the mutex and waits for the GIL. Neither can continue. When every caller first releases the GIL, this cannot happen.

Lock order. BlockManagerMutexAcquire locks the state manager first, then the block manager. It unlocks in the opposite order ({{cite csrc/engine/block_manager.hpp:189-204}}). A fixed order prevents a second kind of deadlock between two threads that both want both locks.

How the code releases the GIL. There are three patterns:

  • Inside the C++ function: py::gil_scoped_release as the first line, as in _schedule ({{cite csrc/engine/scheduler.hpp:276}}) and prepare_sampler_inputs ({{cite csrc/engine/prepare_sample.cpp:42}}).
  • In the binding: py::call_guard<py::gil_scoped_release>(), for example for BlockManager.lock and free_seq ({{cite csrc/engine/pybind_scheduler.cpp:67-71}}, {{cite csrc/engine/pybind_scheduler.cpp:100-102}}).
  • Release, work, then get the GIL again to build a Python result. build_request_outputs reads its NumPy input pointers first, releases the GIL ({{cite csrc/engine/outputs.hpp:102-104}}), and gets it back before it makes the result array ({{cite csrc/engine/outputs.hpp:306-307}}).

One call must keep the GIL: update_metadata_for_sampling_zos assigns a Python object ({{cite csrc/engine/pybind_scheduler.cpp:51-53}}). The page {{link code/engine-pyi}} lists every call that releases the GIL.

Which other Python threads run. The released GIL helps these threads in the engine process:

  • the structured-output compile pool ({{cite deepinfer/structure_output/so_matcher_builder.py:45}});
  • the statistics log thread ({{cite deepinfer/engine/stats_logger.py:186}});
  • the image-processing pool of the VL model ({{cite deepinfer/model_executor/models/deepseek_vl.py:84}});
  • the optional profiling HTTP server ({{cite deepinfer/engine/profile_server.py:157}}).

Worked example: one borrowed array. A forked sequence moves into the running queue. It has 300 tokens. The block size is 128 ({{cite deepinfer/model_executor/model_metadata_utils.py:133-135}}), so it uses 3 KV blocks. The scheduler gives it one new block for its last, part-full block and pushes the pair (old last block, new block) ({{cite csrc/engine/scheduler.hpp:606-611}}). Each extra block after the last used block adds a pair (block, 0), which gives the block back with no copy (lines 612-615). Here there is no extra block, so clone_blocks holds 2 ints. The property returns a NumPy array of shape (1, 2). Its strides are (8, 4) bytes, that is 2 × sizeof(int) and sizeof(int). Its data pointer is clone_blocks.data() ({{cite csrc/engine/pybind_scheduler.cpp:46-47}}). The empty capsule py::capsule([]() {}) tells NumPy that it does not own the memory. When the next schedule() calls clone_blocks.clear(), the array points at stale or reused memory. With no fork, the property returns a new empty array of shape (0, 2) (line 45). The engine does not keep the three arrays. It uses them at once, in the same step. It gives them to the worker, which clones and zeroes the blocks and states on the device ({{cite deepinfer/engine/llm_engine.py:889-903}}).

The device buffer. alloc_tensor rounds the size up to a multiple of 4096 bytes for cuMemAlloc, but the tensor shape keeps the requested size ({{cite csrc/cuda_utils.cpp:24-27}}, {{cite csrc/cuda_utils.cpp:79-82}}). If the allocation fails, the function logs an error and returns None. The cache engine asserts the type and stops with a message ({{cite deepinfer/worker/cache_engine.py:914-915}}).

IPC handles. export_ipc_tensor(ptr, nbytes) returns a byte string that holds a cudaIpcMemHandle_t and the size. import_ipc_tensor opens it in another process ({{cite csrc/cuda_utils.cpp:43-47}}). The deleter of the tensor closes the handle when the tensor dies ({{cite csrc/cuda_utils.cpp:15-22}}). In the package, only utils.CudaIPCWrapper uses these calls ({{cite deepinfer/utils.py:52-69}}), and only a test uses that class ({{cite tests/distributed/test_expert_shuffle.py:89}}). On Ascend, the export needs a 2 MB-aligned address:

ACL needs the exported address to be 2 MB aligned. Else aclrtIpcMemGetExportKey returns ACL_ERROR_RT_DRV_INTERNAL_ERROR (507899); it checks only the address, not the size. In production the KV cache is one large allocation and is aligned. This explicit check makes the cause easy to find. By default the export has a PID allow-list check, and a cross-process import fails at once (507899).

Config objects. The Scheduler constructor takes scheduler_config as a plain py::object. It reads nine attributes by name, once, and keeps C++ copies ({{cite csrc/engine/scheduler.hpp:94-108}}). A later change to the Python object has no effect on the scheduler. A missing attribute raises an error at construction.

Process groups. The scheduler gets the data-parallel group as a c10d::ProcessGroup and runs its all-reduce votes from C++ ({{cite csrc/engine/scheduler.hpp:169-182}}). A Gloo group keeps the vote tensor on the CPU; any other backend puts it on the device ({{cite csrc/engine/scheduler.hpp:109}}).

What can go wrong

Copy clone_states, clone_blocks, zero_states and the result of process_outputs before the next call (for example with np.array(x)). A saved view shows the data of a later step, or freed memory. Nothing raises an error.
  • Import order. If deepinfer._C loads before torch, the import fails. A script comment says, translated: "Load libtorch first, or deepinfer._C reports libc10.so not found" ({{cite examples/yoco/yoco_equiv.py:200}}).
  • Wrong .so folder. If the tag at run time differs from the tag at build time, the import finds no module or an old one. See the deep dive "Build and import".
  • Lock with the GIL held. New C++ code that locks a block manager without releasing the GIL fails the check in Lockable::lock_ ({{cite csrc/utils/lockable.hpp:16}}).
  • Lock time-out. If another thread holds a block manager for more than 20 seconds, the call fails with "failed to lock mutex" ({{cite csrc/utils/lockable.hpp:25-27}}).
  • Wrong argument type. Sequence(...) with a Python list for prompt_token_ids raises TypeError, because of noconvert() ({{cite csrc/engine/pybind_sequence.cpp:103}}).
  • Old stub. After a binding change, the .pyi files are wrong until you run make stubgen.
  • Default drift. C++ has its own default for DEEPINFER_USE_NEXTN_DECODE (5). A change in environ.py alone makes the two sides disagree ({{cite csrc/engine/utils.hpp:38-39}}).

Why it matters. The scheduler, the block managers and the input preparation run in C++. So many engine bugs show up at this boundary. Examples are data that a later step changed, a lock that waits, and a module from the wrong build. When you know who owns each buffer and which call releases the GIL, you can find these bugs fast.

How many submodules does deepinfer._C have, and what are their names?

Three: cuda_utils, engine and graph_timer. csrc/pybind.cpp makes them with def_submodule ({{cite csrc/pybind.cpp:9-16}}).

 Does the repository say why the scheduler is in C++?

No. The deployment doc only says that schedule and post-process are pure CPU work and that the device is idle during them without asynchronous scheduling ({{cite doc/inference_deployment_qa.md:270}}). The code gives no reason.

 On an NVIDIA x86 machine, you run make build-nvidia. Where does the .so go, and how does import deepinfer._C find it?

The build writes to build/nvidia-x86_64 and links each .so into deepinfer/_so/nvidia-x86_64/ ({{cite scripts/build.sh:12-14}}, {{cite scripts/build.sh:23-26}}). deepinfer/__init__.py computes the same tag and appends that folder to the package __path__ ({{cite deepinfer/__init__.py:30-32}}).

 A new Python thread calls scheduler.try_allocate_seq(seq) while the main thread is inside schedule(). What happens?

The binding releases the GIL and then waits for the block-manager locks ({{cite csrc/engine/pybind_scheduler.cpp:87-90}}). The main thread holds them during _schedule(), so the new thread waits. If it waits more than 20 seconds, the lock fails with "failed to lock mutex" ({{cite csrc/utils/lockable.hpp:25-27}}).

 Why does Lockable::lock_ refuse to run when the thread holds the GIL, and why does BlockManagerMutexAcquire always lock the state manager first?

Both rules prevent deadlocks. A thread can hold the GIL and wait for a mutex. If the mutex holder needs the GIL to finish, both threads stop. So the check at {{cite csrc/utils/lockable.hpp:16}} makes every caller release the GIL first. A fixed lock order (state manager, then block manager; {{cite csrc/engine/block_manager.hpp:190-196}}) prevents two threads from each holding one lock and waiting for the other. This is the deep dive "The GIL and the block-manager locks".
