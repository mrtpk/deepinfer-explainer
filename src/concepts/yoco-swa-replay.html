Consumer layers project their compressed KV from one shared hidden state. With the optional prefill truncation (README feature "Decoder SWA bounded replay"), a prefill computes the consumer layers only for the last KEEP_TOKENS prompt tokens (140 in the README), with the window cut at that range. Only their compressed KV still covers every token. --- Consumer layers take their compressed KV from one shared hidden state, so a prefill can run them only for the last 140 tokens.

The idea

{{term yoco}} splits the N main layers at n_prefill_layer, the first layer with {{term compress-ratio}} 1:

  • Producer layers [0, n_prefill_layer) work as usual. The deployment notes call them "encoder layers".
  • Consumer layers [n_prefill_layer, N) make their compressed KV from one {{term shared-hidden}}, not from their own input. The notes call them "decoder layers" ({{cite doc/inference_deployment_qa.md:187}}).

This changes what a long prefill must compute. The compressed KV of every consumer layer depends only on the shared hidden state, and that comes from the producer layers. So the consumer layers do not need to run attention and MoE on the full prompt to fill their compressed caches. They need the full prompt for two things only: the output of the last token, and their {{link concepts/sliding-window-attention | sliding-window}} KV.

{{term swa-bounded-replay | SWA bounded replay}} uses this. With DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact, a prefill runs the consumer layers only for the last DEEPINFER_YOCO_PREFILL_KEEP_TOKENS tokens of the prompt. The README gives 140 as the V4.1 setting ({{cite README.md:25}}). The window of these tokens is cut at the start of the kept range. The consumer-layer SWA KV that results is then approximate. This is a deduction from the visibility rule. The deployment notes also call the replay result approximate, for use in decode only ({{cite doc/inference_deployment_qa.md:183}}, {{cite doc/inference_deployment_qa.md:187}}).

The truncation is off by default ({{cite deepinfer/environ.py:188}}). Without it, every layer computes every prompt token, and the shared hidden state only changes where the compressed KV comes from.

An everyday comparison. Think of a long meeting with a written summary. Late participants read the summary (the compressed KV from the shared state) and listen only to the last ten minutes (the kept tokens). They can then follow the next discussion well. The comparison stops here: their notes about those ten minutes differ a little from the notes of a full listener. The engine accepts that difference.

The repo does not expand the name. In the research literature, YOCO ("You Only Cache Once") is a decoder-decoder design with a similar split. This site uses the name only as the code uses it.

Step 3: the settings and the guard

YoCo consumer prefill truncation mode: off turns it off; mask keeps every query and only narrows the SWA visible range; compact really removes the truncated queries, to reduce the work of the consumer layers. Number of last query tokens kept when YoCo consumer prefill truncation is on. In both mask and compact, the SWA visible range is the intersection of the original window and the rectangle of the last KEEP_TOKENS. KEEP_TOKENS must be >= window_size + DEEPINFER_MAX_BACKTRACKING_TOKENS; the default is 0, so set it explicitly when truncation is on.

The model runner checks the minimum at start-up:

Keep the three-state mode, to check later whether truncation is on and whether it uses the compact layout. ModelMetadata already makes sure that the model has YoCo consumer layers when truncation is on. The truncation length must be at least window_size + backtracking, so that after a rollback the decoder still gets a full window of SWA.

With the defaults, the minimum is 128 + 6 = 134, so the README value 140 passes. Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Settings: compact, KEEP_TOKENS = 140, window 128 (the docs value), ring 134, one sequence, one prefill chunk (q_start = 0, q_len = data_len = 1,000), no context parallelism.

  1. Producer layers. All 1,000 rows, as without YOCO.
  2. Clip. clip_prefix = clamp(1,000 − 140 − 0, 0, 999) = 860 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:225}}). The kept rows are 860 … 999: yoco_consumer_total_q = 140, yoco_consumer_query_indices = [860 … 999] ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:261-265}}).
  3. Boundary. At layer n_prefill_layer, the hidden states shrink from [1000, hc, hidden] to [140, hc, hidden], by a gather with the query indices ({{cite deepinfer/model_executor/models/v4_modules/yoco.py:65-67}}).
  4. Compressed KV. Each KV-source consumer layer writes entries for all 1,000 positions: 1,000 in a C1 layer, 500 in a C2 layer. Index keys likewise ({{cite deepinfer/model_executor/models/v4_modules/attn.py:692-721}}).
  5. Window. For a kept query at pos, the oldest visible key is max(pos − 127, 860) ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:155}}). Query 860 sees 1 key; query 900 sees 41; queries 987 … 999 see 128.
  6. Ring. A kept row writes the ring only if it is among the last 134 rows of the chunk: rows 866 … 999 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:267-271}}). Rows 860 … 865 are computed but not stored.
  7. Top-k. The indexer selects keys only for the 140 kept queries. Each kept query reads (pos + 1) / ratio compressed entries, as without truncation ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:292-301}}).
  8. First decode step. The query at 1,000 reads ring positions 873 … 1,000. All of them were written: 873 … 999 by the prefill, 1,000 by the step itself.

Work. Each consumer layer runs its query projection, attention and MoE on 140 rows instead of 1,000. Only the KV path stays at full length. Each KV-source consumer layer projects, compresses and stores the KV of all 1,000 positions. It also stores their index keys. The deployment notes report "nearly halving total prefill computation" for V4.1 ({{cite doc/inference_deployment_qa.md:187}}).

The first consumer layer gets exact inputs for every kept row: they come from the producer layers, which saw the whole prompt. Its SWA KV is exact. But its attention output for rows 860 … 986 used a cut window. So the next consumer layer gets slightly different inputs for those rows, and stores slightly different SWA KV. The difference moves forward one window per layer. This is a deduction from the visibility rule ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:149-168}}).

The deployment notes agree. An exact rebuild "would require running the last 2,560 tokens through 20 decoder layers" (128 × 20). The replay result "is used for decode only and never enters the prefix cache" ({{cite doc/inference_deployment_qa.md:187}}). The numbers 20 and 2,560 come from the docs.

The cache layout follows the same rule. The SWA rings of consumer layers are in the "dropped" part of the state slot, which never goes to the external KV store ({{cite deepinfer/worker/cache_engine.py:113-116}}, {{cite deepinfer/worker/cache_engine.py:221-235}}). The compressed KV of consumer layers is exact, because it comes from the full shared hidden state.

Why KEEP_TOKENS ≥ window + backtracking. The translated comment says: after a rollback, the decoder must still get a full window of SWA ({{cite deepinfer/worker/model_runner.py:108}}). With 134 kept rows, the ring holds every position that the first decode step can read. The README value 140 is 6 rows above this minimum; the repo does not say why.

The predicates test which field set exists ({{cite deepinfer/model_executor/input_metadata/yoco.py:66-84}}). The two views are shallow copies:

yoco decoder truncation changes only the mask; it does not really truncate. Make a compact shallow copy of the metadata for the first YoCo consumer layer. Switch the query-aligned fields and the SWA visible range to the compact layout, and clear the expanded attention fields so that they are rebuilt. With CP > 1, also redo the zigzag split and build the layer-boundary redistribution index. Fields that are not rewritten share tensors with the original metadata; do not change them in place. Swap the SWA visible range for the compact yoco pivots: the consumer layer reads kv_swa_full_index(_pivots) as usual and gets the truncation semantics. Fields expanded during the forward are set to None; compute_attn_info expands them again from the compact metadata. input_ids is used only in the embedding before the layer loop, so keep the original varlen tensor. gate_force_random is gathered from the global full layout to the compact layout.

Both modes use the same visibility function in C++, so the kept rows get the same numbers ({{cite deepinfer/model_executor/input_metadata/yoco.py:1-6}}). The checker in examples/yoco uses mask as the reference for compact ({{cite examples/yoco/README.md:3}}). One more rule applies to chunks. When a whole chunk is before the kept range, compact mode keeps the last row of the chunk as a placeholder ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:222-225}}). That row writes no ring slot ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:266-271}}).

  3. Lines 692-709. A KV source projects consumer_full_hidden with shared_hidden_kv_proj only. It skips the merged projection, so it does not compute unused index weights. Then it stores the main KV for all rows and keeps pre_rope_kv.

Cross-layer sharing must not cross the boundary: the first consumer layer must be a KV source ({{cite deepinfer/model_executor/models/v4_modules/cross_layer.py:114-116}}). At the boundary, compact_yoco_boundary also compacts a top-k list that a producer layer shares with consumer layers ({{cite deepinfer/model_executor/models/v4_modules/yoco.py:116-122}}).
  • CP. Compact mode cuts first and then splits for CP again. Each rank selects its kept rows, all ranks all-gather them, and each rank takes its new rows ({{cite deepinfer/model_executor/models/v4_modules/yoco.py:55-76}}). The view rebuilds the mirror index with prepare_cp_mirror ({{cite deepinfer/model_executor/input_metadata/yoco.py:130-182}}). The userbuffer grows to carry the mHC residual ({{cite deepinfer/model_executor/models/deepseek.py:417-420}}).
  • DFlash. The DFlash target layers must be all producers or all consumers ({{cite deepinfer/model_executor/models/deepseek.py:128-135}}). If they are consumers, dflash_input shrinks to the kept rows ({{cite deepinfer/model_executor/models/deepseek.py:199-205}}).
  • Engram. Engram layers must be producers in compact mode ({{cite deepinfer/model_executor/models/deepseek.py:136-138}}, {{cite deepinfer/model_executor/models/decoder_layer.py:136}}).
  • Cost estimate. The engine gives the mode and KEEP_TOKENS to the FlopsEstimator ({{cite deepinfer/engine/llm_engine.py:318-322}}). It counts the consumer rows from the cut-off, and keeps the last row of a fully cut chunk ({{cite csrc/engine/flops_estimator.hpp:259-278}}).
  • truncate_len. The engine passes KEEP_TOKENS to the C++ scheduler only in compact mode, else 0 ({{cite deepinfer/engine/llm_engine.py:260}}, {{cite deepinfer/engine/llm_engine.py:315}}). In this release, scheduler.hpp only stores the value ({{cite csrc/engine/scheduler.hpp:88}}, {{cite csrc/engine/scheduler.hpp:1167}}).
  • Hit policy (docs only). The deployment notes give two rules. First: "under the YOCO truncation requirement, the maximum hit length for an input of length L is at most L − 134". Second: "If an SWA KV cache exists in the range L1 − 128 to L1, the hit length is L1; otherwise it is L1 − 128" ({{cite doc/inference_deployment_qa.md:191}}). L1 is the hit length from the block KV cache, and 134 is "128-token window + 6 tokens of speculative backtracking". The KV cache system is not in this release ({{cite README.md:40}}).

The folder examples/yoco/ has an equivalence checker with two levels ({{cite examples/yoco/README.md:5-8}}):

  • L1 (mask-compact, one device, no weights). It compares the SWA pivots, the visible keys, the store slots and the compressed key ranges of both modes. The reference is: visible = window ∩ [N − KEEP_TOKENS, N) ({{cite examples/yoco/yoco_equiv.py:116-118}}). The cases cover a prompt shorter than, equal to and longer than KEEP_TOKENS, and chunks before, across and inside the range ({{cite examples/yoco/yoco_equiv.py:79-99}}).
  • L2 (logp + compare, 8 devices, a V4.1 checkpoint). It runs mask and then compact on a fixed trajectory. Then it compares logprobs and top-K element by element ({{cite examples/yoco/run_yoco_equiv_l2.sh:9-11}}).
python examples/yoco/yoco_equiv.py mask-compact --keep-tokens 140 --window 128
examples/yoco/run_yoco_equiv_l2.sh --model_name /path/to/compatible-v41-hf

The checker compares compact with mask, not with "off". It checks that compaction removes rows without other changes. It does not measure the approximation itself.

What can go wrong

Set DEEPINFER_YOCO_PREFILL_KEEP_TOKENS when you set the mode. Its default is 0, and any mode other than off then fails an assert ({{cite deepinfer/model_executor/model_metadata_utils.py:90-92}}).
  • Too few kept tokens. A value below window + backtracking (134 with the defaults) fails at start-up ({{cite deepinfer/worker/model_runner.py:110-113}}). More draft tokens raise the minimum.
  • A model without consumer layers. The mode needs n_prefill_layer < N and above 0 ({{cite deepinfer/model_executor/model_metadata_utils.py:90-91}}).
  • Engram or split DFlash targets in compact mode. Asserts at model build ({{cite deepinfer/model_executor/models/deepseek.py:128-138}}).
  • Small differences in the output. With truncation on, the consumer-layer SWA KV of the last prompt tokens is approximate (a deduction from the visibility rule; the deployment notes agree). To compare with a reference run, set the mode to off.

Why it matters. With compaction on, the consumer half of the model costs much less in a long prefill. Only its KV path runs on every token. The price is an approximation in the consumer-layer SWA KV of the last prompt tokens, which the first decode tokens read. The attention and MoE work of the consumer layers does not grow with the prompt length.

What is the default of DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE, and which values does it accept?

off; it accepts off, mask and compact ({{cite deepinfer/environ.py:188}}).

 With a window of 128 and the default 5 draft tokens, what is the smallest valid KEEP_TOKENS?

128 + 6 = 134. The backtracking count is at least nextn + 1 = 6 ({{cite deepinfer/environ.py:132}}), and the runner asserts window + backtracking ≤ KEEP_TOKENS ({{cite deepinfer/worker/model_runner.py:110}}).

 In compact mode, why can the consumer layers skip most prompt rows but still have a complete compressed cache?

Their compressed KV comes from the shared hidden state ({{cite deepinfer/model_executor/models/v4_modules/attn.py:345-352}}). The first consumer layer saves the full attention-norm output as consumer_full_hidden before the rows shrink ({{cite deepinfer/model_executor/models/decoder_layer.py:137-140}}), and _store_yoco_full_kv writes the KV of all positions from it ({{cite deepinfer/model_executor/models/v4_modules/attn.py:692-709}}).

 A 1,000-token prompt, compact, KEEP_TOKENS = 140, window 128. How many SWA keys does the consumer-layer query at position 900 see, and which kept rows write the ring?

41 keys (860 … 900): the oldest visible key is max(900 − 127, 1,000 − 140) = 860 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:155}}). Rows 866 … 999 write the ring, because a row must be in the kept range and among the last 134 rows ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:267-271}}). See the deep dive "Worked example".

 The deployment notes say the replay result "never enters the prefix cache". Where does the code put the consumer-layer SWA rings to match this?

In the "dropped" region of the state slot, after the stored SWA rings of the producer layers. Only the stored region goes to the store ({{cite deepinfer/worker/cache_engine.py:113-116}}, {{cite deepinfer/worker/cache_engine.py:221-235}}, {{cite deepinfer/worker/cache_engine.py:306}}).
