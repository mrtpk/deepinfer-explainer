This page shows the ring, the decode and prefill index paths, and how the window joins the compressed keys. --- Each layer reads the last 128 tokens exactly, from a per-sequence ring of 134 slots; compressed layers add selected older keys.

The idea

In normal {{term attention}}, a new token reads the keys of all earlier tokens. The cost and the {{term kv-cache}} then grow with the length of the sequence. {{term sliding-window-attention | Sliding-window attention}} (SWA) reads only the last W tokens: the window. Its cache has a fixed size for each sequence, whatever the length.

In DeepInfer every attention layer has a window. The config key sliding_window gives W ({{cite deepinfer/hugging_face/config.py:284}}). The repo does not contain the value; the deployment notes use 128 ({{cite doc/inference_deployment_qa.md:191}}). This page uses 128 as the example value.

A window alone forgets old tokens. So most layers also read {{link concepts/kv-compression | compressed keys}} that cover the whole history. A layer with {{term compress-ratio}} 0 is "SWA only": it reads the window and nothing else.

The window lives in a {{term ring-buffer}} of 134 slots per sequence and layer: 128 for the window plus 6 {{term backtracking-tokens}}. Position p always goes to slot p % 134. A new token replaces the token that is 134 positions older.

An everyday comparison. Think of a round table with 134 numbered seats. Guest number p sits on seat p % 134 and sends the earlier guest on that seat away. To talk to "the last 128 guests", you walk around the table from one seat. The comparison stops here: a real guest leaves for ever, but a compressed copy of each token stays in the main cache.

In the code

Step 1: every layer gets a ring

The Hugging Face loader gives every layer kind sink_mode="swa": the SWA-only spec, the compressed spec and the DFlash spec ({{cite deepinfer/hugging_face/config.py:99-108}}, {{cite deepinfer/hugging_face/config.py:111-116}}, {{cite deepinfer/hugging_face/config.py:136-143}}). The cache engine allocates a ring for each layer with that mode:

Intentionally does not check use_swa: a use_swa=False layer (packed-KV / YoCo consumer) also takes an SWA slot that is never read or written.

With the default settings, the ring size is the window plus the backtracking count:

swa_block_size is window_size plus the part stored extra for rollback. If window_size < 0 in the config, the model has no SWA layer: return 0. NextN must roll back n tokens. A maximum rollback count can also be set directly.

DEEPINFER_MAX_BACKTRACKING_TOKENS is never below DEEPINFER_USE_NEXTN_DECODE + 1 ({{cite deepinfer/environ.py:132}}). The default draft count is 5 ({{cite deepinfer/environ.py:129}}), so the ring has 128 + 6 = 134 slots. Each slot holds one {{term latent-kv}} vector of 512 values in FP8 with one UE8M0 scale per 32 values: 512 + 16 = 528 bytes ({{cite deepinfer/worker/cache_engine.py:261-263}}, {{cite deepinfer/model_executor/layers/tilelang_ops/cache_common.py:109-118}}). The ring is in the sequence's {{term state-slot}}, not in the paged blocks.

The slot is state_id × 134 + position % 134. In decode, every query token gets a slot. In a prefill, only the last 134 tokens of the chunk get one. Older tokens get −1 (no write), because no window can reach them again. Prefill always uses C++.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

A decode step writes all its new SWA vectors first, then runs attention. With the default 5 draft tokens, one step has 6 query tokens per sequence: positions p to p + 5 (see {{link concepts/speculative-decoding}}). The rule is in {{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:103-104}} and {{cite deepinfer/model_executor/models/v4_modules/attn.py:421-432}}.

  1. The first query (position p) needs positions p − 127 to p.
  2. The step also writes positions p + 1 to p + 5.
  3. So the ring must hold positions p − 127 to p + 5 at the same time: 133 positions.
  4. With 128 slots, the draft at p + 1 would overwrite position p − 127, which the first query still reads.

The code reserves DEEPINFER_USE_NEXTN_DECODE + 1 = 6 extra slots, so the ring has 134 slots: one more than this count needs. The docs give two reasons for the extra slots. The hit policy calls them "6 tokens of speculative backtracking" ({{cite doc/inference_deployment_qa.md:191}}). The store copy "can overshoot the boundary by at most 5 tokens, which is absorbed by the 6 extra positions" ({{cite doc/inference_deployment_qa.md:165}}).

Rejected drafts. A rejected draft is never deleted. The next step starts at the first rejected position and writes the same positions again, into the same slots. Then the ring holds the correct tokens again.

The compression state uses the same rule with its own numbers: its ring must hold ratio + tokens per step − 1 entries ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:98-100}}). See {{link concepts/kv-compression}}.

Bytes. One ring per layer and sequence: 134 × 528 B = 70,752 B. The code pads each layer to 32 bytes; 70,752 is already a multiple of 32 ({{cite deepinfer/worker/cache_engine.py:274-277}}). The SWA format is always MXFP8, also when the main cache uses FP4: use_fp4=False for SWA ({{cite deepinfer/worker/cache_engine.py:261-263}}).

Tensor view. swa_cache is uint8 [num_state_slots, 134, 1, 528]. The row stride is the size of the whole state slot, so one row index (state_id) selects one sequence ({{cite deepinfer/worker/cache_engine.py:419-422}}, {{cite deepinfer/worker/cache_engine.py:216-218}}).

Where in the slot. The slot starts with the "stored" SWA rings of the producer layers. Then come the "dropped" SWA rings of the YOCO consumer layers, and the compression state ({{cite deepinfer/worker/cache_engine.py:221-241}}). Only the stored part goes to the external KV store. The deployment notes give its size: "20 layers × 134 tokens × 528 B = 1,415,040 B per sequence" ({{cite doc/inference_deployment_qa.md:169}}). The number 20 comes from the docs, not from the code. See {{link concepts/yoco-swa-replay}}.

Sequence with state_id 3, decode query at position 1,000, window 128, ring 134 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:644-649}}):

  1. real_window_size = min(1,000 + 1, 128) = 128.
  2. The oldest key is 1,000 − 128 + 1 = 873. 873 % 134 = 69, so offset = 3 × 134 + 69 = 471.
  3. The kernel makes 128 slots: 402 + (69 + j) % 134 for j = 0 … 127 ({{cite deepinfer/model_executor/layers/tilelang_ops/get_kv_index.py:91}}).
  4. j = 0 … 64 give slots 471 … 535 (positions 873 … 937). j = 65 … 127 wrap and give slots 402 … 464 (positions 938 … 1,000).
  5. Slot 464 = 3 × 134 + 1,000 % 134 = 402 + 62: the query's own key, written in the same step ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:104}}).

A short sequence at position 50 gets real_window_size = 51, so columns 51 … 127 are −1.

Shapes: kv_swa_index_offset_len int32 [T, 2]; kv_swa_index int32 [T, 128] ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:313-317}}). With zero-overhead scheduling, the device kernel prepare_v4_decode_metadata builds the offsets ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:326-367}}).

The load plan. C++ copies each sequence's history window from its ring into the first section of the buffer:

  1. Lines 378-379. The history window is positions q_start − W to q_start − 1: the W tokens before the chunk.
  2. Lines 380-382. Positions before 0 (or before swa_valid_start) become zero rows: a segment with src_block_id = −1.
  3. Line 383. The rest is a ring range. The builder splits it where the ring wraps, so one sequence has at most three segments ({{cite csrc/engine/input_metadata/block_load_plan.cpp:37-46}}, {{cite deepinfer/model_executor/input_metadata/input_metadata.py:268-271}}).
  4. Line 387. The section always has num_seqs × W rows.

Example: 2,048 cached tokens, so the history is 1,920 … 2,047. 1,920 % 134 = 44. The plan has two segments: ring rows 44 … 133 (90 tokens), then rows 0 … 37 (38 tokens). A new prompt (q_start = 0) gets one zero segment of 128 rows.

The pivots.

Zero-state recompute: the SWA state of [0, valid_start) is cleared, so the left edge of the visible window is clamped to valid_start, to avoid attention to cleared slots. With valid_start = 0 (normal path) this is the same as the original start_in_win = min(W, max(j+1, W − q_start)). The code below assumes valid_start <= q_start. The visible range is always larger than the input range. Lower bound of the absolute position of a visible key: the max of the window bound and the valid-state bound, clamped to >= 0. Section 1 (history, read from the state buffer): visible range [min(abs_lo, q_start), q_start). Section 2 (new in this chunk): visible range [max(abs_lo, q_start), pos].
  1. Line 507. The oldest visible key is pos − W + 1, not below valid_start and 0.
  2. Lines 512-517. Section 1: the history part. start_slot is the first visible row of this sequence's 128 history rows; the length is W − start_slot.
  3. Lines 520-523. Section 2: the new part, from k_lo to the query itself.

Example, same sequence (2,048 cached, 300 new). Query j = 0 (position 2,048): abs_lo = 1,921, start_slot = 1, so 127 history keys and 1 new key. Query j = 200 (position 2,248): abs_lo = 2,121, start_slot = 128 (empty history part), k_lo = 73, so 128 new keys.

The store. After the load, store_kv_cache writes the last 134 new vectors into the ring ({{cite deepinfer/model_executor/models/v4_modules/attn.py:855}}). The prefill vectors went through an FP8 round trip (cast_back=True). So attention in the prefill sees the same numbers that decode later reads from the ring ({{cite deepinfer/model_executor/models/v4_modules/attn.py:412-419}}).

Each sequence has a field swa_valid_start ({{cite csrc/engine/sequence.hpp:205}}). The C++ code treats ring positions before it as missing: the load plan zero-fills them and the pivots do not point at them ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:380-382}}, {{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:501-509}}).

In this release, no code sets the field above 0. reset_for_recompute sets it to 0 ({{cite csrc/engine/sequence.hpp:223-227}}), and pybind exposes it to Python as a read-write property ({{cite csrc/engine/pybind_sequence.cpp:132}}), but no Python code writes it. The field is a hook for the "encoder SWA bounded replay" of the docs. After a prefix-cache hit without SWA state, that design recomputes only the last 128 tokens ({{cite doc/inference_deployment_qa.md:183-185}}). The KV cache system that would use it is not in this release ({{cite README.md:40}}).

What can go wrong

  • A layer with another window. V4Attention asserts that the layer window equals the model window, and names the layer ({{cite deepinfer/model_executor/models/v4_modules/attn.py:243}}).
  • A sparse layer without SWA. use_swa=False with an indexer fails an assert ({{cite deepinfer/model_executor/models/v4_modules/attn.py:95-96}}).
  • Ring smaller than the window. The C++ load plan checks swa_block_size ≥ window_size ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:369}}).
  • A query with no visible key. A swa_valid_start that is too large makes section 2 empty. C++ stops with "query token sees nothing" ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:521}}).
  • A low backtracking value has no effect. A value below DEEPINFER_USE_NEXTN_DECODE + 1 is raised with no message ({{cite deepinfer/environ.py:132}}). A higher value makes every ring larger.
  • Memory per sequence. The ring is per layer and per sequence, also for short requests. With N main layers, a sequence always takes at least N × 70,752 B of state, whatever its length.

Why it matters. The window gives every layer exact attention to recent tokens, with a cache whose size does not grow. Most memory questions about long sequences then go to the compressed cache. Most correctness questions about speculative decoding go to the ring: the 6 extra slots make draft tokens safe.

Where does DeepInfer store the sliding-window KV: in the paged KV blocks or somewhere else?

In the sequence's state slot, as a ring of 134 slots per layer. The paged blocks hold only the compressed KV and the indexer keys ({{cite deepinfer/worker/cache_engine.py:406-422}}, {{cite deepinfer/worker/cache_engine.py:216-218}}).

 A sequence has state_id 3. In which slot of swa_cache does the token at position 1,000 go?

3 × 134 + 1,000 % 134 = 402 + 62 = 464 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:104}}).

 A prefill chunk has 1,000 new tokens. How many of them does the code write into the ring, and why not all?

The last 134. Line 103 gives −1 to every token with seqlen_q − j > swa_block_size ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:103-106}}). Older tokens are outside every future window, and the ring would overwrite them anyway.

 Why does a ring of exactly 128 slots fail when DEEPINFER_USE_NEXTN_DECODE is 5?

A decode step writes the SWA KV of positions p … p + 5 before attention ({{cite deepinfer/model_executor/models/v4_modules/attn.py:421-432}}). The query at p still needs p − 127. With 128 slots, position p + 1 goes to the slot of p − 127 and destroys it. The code adds at least nextn + 1 = 6 slots ({{cite deepinfer/environ.py:132}}, {{cite deepinfer/worker/cache_engine.py:93}}). See the deep dive "Why 134 slots, not 128".

 In a prefill with 2,048 cached tokens, how many history keys and how many new keys does the query at position 2,048 read?

127 history keys (1,921 … 2,047) and 1 new key (itself). abs_lo = 2,048 − 127 = 1,921, so start_slot = 1,921 − 1,920 = 1 and the section-1 length is 127 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:507-523}}).
