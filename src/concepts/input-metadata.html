The idea

The scheduler gives the worker a list of sequences. The sequences have different lengths. A prefill chunk can have thousands of new tokens, and a decode sequence has 1 + 5 tokens. The kernels on the device cannot read C++ sequence objects. They need flat {{term tensor | tensors}} of numbers.

So DeepInfer puts the new tokens of all sequences end to end, with no gaps. This is a {{term packed-batch | packed (varlen) batch}}. Each new token is one row. Then DeepInfer computes small index tensors for these rows. Together they are the {{term input-metadata}}:

  • Where each sequence starts. Offset arrays such as {{term cu-seqlens}}.
  • Where each token is in its sequence. The position of each row.
  • Where to write. A {{term slot-mapping}} gives the cache row for each new cache entry.
  • What to read. {{term block-table | Block tables}}, window descriptions and key ranges tell attention which earlier entries each row sees.

In a prefill step, C++ code computes these tensors on the CPU. In a decode step with {{term zos}} (the default), C++ packs only per-sequence values and a device kernel computes the per-row tensors (deep dive). Python wraps the tensors in one object of the class InputMetadataV4, or of its subclass InputMetadataV4VL for a vision model ({{cite deepinfer/model_executor/model_metadata_utils.py:142-144}}). Every layer of the model reads this object.

An everyday comparison. Think of a delivery truck. The parcels of many customers go into the truck end to end, with no gaps. A packing list says where the parcels of each customer start. It also gives, for each parcel, the shelf in the warehouse where it goes. The kernels are the warehouse workers: they read only the list, not the customer files.

The comparison stops at two points. First, in a decode step with a {{term cuda-graph}}, the truck has a fixed size, so DeepInfer adds empty parcels ({{term graph-padding | padding rows}}). Second, some list entries are short descriptions that the device expands later into full index tables.

In the code

Step 1: the scheduler gives one SequenceMetadata per sequence

The C++ scheduler makes one {{term sequence-metadata}} object for each scheduled sequence. It has two lengths: seqlen_q (the new tokens of this step) and seqlen_k (all tokens that the step can see) ({{cite csrc/engine/scheduler.hpp:696-697}}). A step is a prefill step or a decode step, never both. The sampler preparation checks this: "Mixed prefill and decode batches are unsupported" ({{cite csrc/engine/prepare_sample.cpp:61}}).

In a NORMAL engine, the scheduler stops the prefill batch right after it cuts a prompt ({{cite csrc/engine/scheduler.hpp:543-545}}). So a batch has at most one cut chunk, at the end. A continued chunk (like A) can come earlier.

In a prefill step, line 112 copies the seqlen_q prompt ids. In a decode step, it copies one id, the last real token. Lines 116-118 then add the {{term draft-token | draft tokens}}. So a decode sequence sends 1 + 5 rows with the default settings.

Step 4: where the new cache entries go

DeepInfer has two kinds of cache for attention. The compressed cache is paged in blocks of 128 tokens. The {{term sliding-window-attention}} (SWA) cache is a ring per sequence in a {{term state-slot}} ({{link concepts/paged-kv-cache}}). update_common_v4 writes one slot map for each:

The dict slot_mapping_store_ca has one tensor per compress ratio, with keys such as "1" and "2". The model accepts only ratios 0, 1 and 2 ({{cite deepinfer/model_executor/model_metadata_utils.py:52-53}}). The SWA ring has swa_block_size rows: the window plus the backtracking tokens ({{cite deepinfer/worker/cache_engine.py:88-93}}, {{cite deepinfer/environ.py:132}}). The window size comes from the checkpoint config. The docs give 128 + 6 = 134 for V4.1 ({{cite doc/inference_deployment_qa.md:191}}), and this page uses these example values.

Step 5: what each row reads

Prefill and decode read the cache in different ways.

  • Prefill gathers the history of all sequences into one flat buffer first. A {{term load-plan}} (load_segments_swa, load_segments_ca) says which cache rows to copy ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:461-476}}). Then each row gets a short description of its window in that buffer: kv_swa_full_index_pivots ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:478-527}}).
  • Decode reads the paged cache in place. Each row gets a copy of its sequence's block table (block_tables), its visible length (context_lens) and an [offset, length] pair for its window ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:585-652}}).

The device expands the short descriptions into full index tables at the start of the forward pass. Each attention layer calls compute_attn_info, and the first call does the work ({{cite deepinfer/model_executor/models/v4_modules/attn.py:765}}, {{cite deepinfer/model_executor/input_metadata/input_metadata.py:343-389}}).

Step 6: decode with a CUDA graph

A decode step usually replays a captured CUDA graph ({{link concepts/cuda-graphs}}). The graph has fixed input buffers. So the model runner adds padding sequences up to the graph size, and C++ writes straight into the graph's buffers:

The second figure shows a decode step of two sequences with 6 rows each, padded to 16 rows.

Step 7: views for special features

Three features change the metadata during the forward pass. The deep dive explains each one.

  • Context parallelism. With CP above 1, the model reorders the prefill rows for each rank: prepare_for_mirror_cp ({{cite deepinfer/model_executor/models/deepseek.py:168-170}}).
  • YOCO prefill truncation. At the first consumer layer, the model switches to a different view of the metadata: fewer rows in compact mode, narrower windows in mask mode ({{cite deepinfer/model_executor/models/deepseek.py:190-207}}).
  • DFlash drafts. The draft model gets its own fixed-stride view: build_dflash_input ({{cite deepinfer/model_executor/models/mtp/dflash.py:367-372}}).

Fields that the device computes. kv_swa_full_index, kv_ca_index, kv_ca_index_len, compressed_batch_mapping, kv_swa_index and the scheduling metadata of the attention libraries start as None. compute_attn_info fills them in the first attention layer ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:343-389}}). The width of kv_ca_index is max_model_len / N, rounded up to a multiple of 128: the comment says that the sparse-attention kernel needs this ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:362}}).

The size of a decode block table. max_num_blocks is the block count of runtime_max_model_len, rounded up to a multiple of 64 ({{cite deepinfer/worker/model_runner.py:114-115}}). With runtime_max_model_len = 32784 (max_model_len 32768 plus 16 extra positions with nextn 5 and ZOS on, {{cite deepinfer/config.py:11-16}}): 257 blocks, rounded up to 320. So 16 rows of block tables take 16 × 320 × 4 = 20,480 bytes. C++ copies only the blocks that the row needs; the rest of the row is not written ({{cite csrc/engine/input_metadata/prepare_tensor_input_base.cpp:207}}).

Why padding is safe. Block 0 and state slot 0 are never given to a real sequence: the free list starts at 1 ({{cite csrc/engine/block_manager.hpp:27-30}}). So padding rows write only to these two places. The MoE gate gets valid_token_mask as its mask ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:387}}), and the sampler does not read them (see {{link code/prepare-sample-cpp}}).

{{term zos | Zero-overhead scheduling}} is on by default. Then the CPU does not know the real seqlen_k of a sequence: the previous step is still on the device. So the decode path splits the work ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:307-382}}):

  1. C++ prepare_decode_zos_inputs packs only per-sequence values: lengths, state ids, a flat block table with offsets, and the token ids of fresh sequences ({{cite csrc/engine/zos.cpp:198-277}}).
  2. The worker corrects seqlens_k on the device from the accepted-token counts of the previous step. With {{term dspark}} (DEEPINFER_ENABLE_MTP_VARLEN), it also sets seqlens_q from the confidence rates ({{cite deepinfer/worker/worker.py:191-245}}).
  3. The kernel prepare_v4_decode_metadata computes all per-row fields on the device: positions, masks, slot maps, block tables, offset pairs ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:336-367}}).
  4. gather_input_ids_zos takes the token ids of continuing sequences from the previous step's device tensors, so no copy to the CPU is necessary ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:235-244}}).

With ZOS, the output buffers are device tensors (get_or_create uses device="cuda", {{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:113-117}}). The kernel writes several ratio buckets in one launch, through equally spaced row views of one allocation (get_or_create_stacked, {{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:120-159}}).

A {{term yoco}} model has consumer layers after layer n_prefill_layer ({{cite deepinfer/model_executor/model_metadata_utils.py:87-88}}). With {{term swa-bounded-replay | YOCO prefill truncation}}, the prefill step needs the consumer layers only for the last KEEP_TOKENS tokens of the prompt. C++ computes the extra fields when the mode is not off ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:349-360}}):

  • mask: only yoco_mask_swa_index_pivots. The layout stays full; the windows of rows before the kept range are empty ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:155}}, {{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:285-289}}).
  • compact: yoco_consumer_* fields in a smaller layout: query_indices (which full rows stay), cu_seqlens_q, total_q, positions, pivots, ks/ke, offset pairs and the SWA slot map ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:334-342}}).

The rows to drop: clip_prefix = clamp(data_len − keep_tokens − q_start, 0, q_len − 1) ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:225}}). The upper limit q_len − 1 keeps at least one row, because the sampler always reads the last row of a chunk. Example with KEEP_TOKENS = 140: A (data_len 260, q_start 200) keeps all 60 rows. B (data_len 400, q_start 0) has clip_prefix = 199 and keeps 1 row. The compact batch has cu = [0, 60, 61].

At the first consumer layer, DeepseekModel.forward calls get_consumer_view() (compact) or get_mask_view() (mask) ({{cite deepinfer/model_executor/models/deepseek.py:191-207}}). Each view is a shallow copy. It sets the derived fields to None, so that compute_attn_info expands them again for the new pivots or layout ({{cite deepinfer/model_executor/input_metadata/yoco.py:86-128}}). The page {{link concepts/yoco-swa-replay}} explains the model side.

With CP above 1, only the driver rank builds the metadata. For an eager step it sends all fields with broadcast_tensor_dict. Dict fields are flattened to keys such as "slot_mapping_store_ca.2", because the broadcast handles one level only ({{cite deepinfer/worker/model_runner.py:200-212}}, {{cite deepinfer/model_executor/input_metadata/input_metadata.py:391-413}}).

In a prefill step, each rank then works on its own part of the rows: the {{term cp-mirror}}. prepare_for_mirror_cp computes mirror_cp_index and new ks/ke on the device. It reorders positions and ngram_token_ids. gate_force_random keeps the full layout; a reordered copy goes to gate_force_random_cp. It sets valid_token_mask to mirror_cp_index != -1 ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:170-208}}). input_ids keeps the full layout, because the embedding runs before the reorder ({{cite deepinfer/model_executor/models/deepseek.py:161-170}}).

The length per rank is cp_mirror_len = 2 × Σ ⌈seqlen_q / (2 × cp)⌉ ({{cite csrc/engine/input_metadata/prepare_tensor_input_base.cpp:147-155}}). Example: our prefill batch with cp = 2: 2 × (⌈60/4⌉ + ⌈200/4⌉) = 2 × (15 + 50) = 130 rows per rank.

The DFlash draft model runs after the main model in a decode step. Its attention needs one block of draft rows per request, not the varlen rows of the main model. build_dflash_input makes a shallow copy and replaces six fields with one fused kernel: dflash_newx_slot_mapping_store, positions, input_ids, valid_token_mask, gate_force_random and dflash_kv_index ({{cite deepinfer/model_executor/input_metadata/dflash.py:36-84}}).

  • dflash_newx_slot_mapping_store: [real_cnt × dflash_block_size], SWA slots for the draft-token KV.
  • dflash_kv_index: [real_cnt × dflash_block_size, pad64(window_size + dflash_block_size)], the SWA slots that each draft row reads ({{cite deepinfer/model_executor/input_metadata/dflash.py:30-34}}).

The module docstring says, translated: the C++ prepare does not make these fields. With the DFlash CUDA graph, the graph captures and replays them ({{cite deepinfer/model_executor/input_metadata/dflash.py:1-8}}). See {{link code/dflash}}.

What can go wrong

The C++ builder checks its inputs with TORCH_CHECK. A failed check raises a Python RuntimeError and stops the step.

  • YOCO keep length too small. KEEP_TOKENS must be at least window_size + DEEPINFER_MAX_BACKTRACKING_TOKENS (134 with the defaults). The model runner checks this at load time with an assert ({{cite deepinfer/worker/model_runner.py:107-113}}), and C++ checks it again in each prefill ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:355-357}}).
  • Block table too short. In a decode step, a row needs more blocks than max_num_blocks or than the sequence has ({{cite csrc/engine/input_metadata/prepare_tensor_input_base.cpp:223}}).
  • Index overflow. The decode offset total_q × max_num_blocks × (128/N) must fit in int32 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:615-616}}).
  • Wrong buffer size. On the graph path, each existing buffer must have exactly the expected shape and dtype ({{cite csrc/engine/input_metadata/prepare_tensor_input_base.cpp:41-43}}).
  • Unsupported compression. Ratios other than 0 (no compression), 1 and 2 stop the model load with ValueError ({{cite deepinfer/model_executor/model_metadata_utils.py:52-53}}).

Why it matters. Every attention kernel trusts these numbers. A wrong slot writes a token into the cache of another sequence, and no error appears. The checks above catch only shape errors. So when you change the scheduler or the cache layout, test the slot maps with a small example like the one on this page.

A prefill batch has two chunks with seqlen_q 60 and 200 and seqlen_k 260 and 200. What are cu_seqlens_q and cu_seqlens_k?

cu_seqlens_q = [0, 60, 260] and cu_seqlens_k = [0, 260, 460]. Both are running sums that start at 0, with n_seq + 1 values ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:407-418}}).

 Which function turns the list of SequenceMetadata into an InputMetadataV4 object, and where do the tensors live after it returns on the eager path?

ModelRunner._prepare_input_tensors ({{cite deepinfer/worker/model_runner.py:120-146}}). In a prefill step, C++ makes the tensors in pinned CPU memory (also in a decode step without ZOS). _prepare_input_driver then copies them to the device with .cuda(non_blocking=True) ({{cite deepinfer/worker/model_runner.py:198}}).

 A prefill chunk has 200 rows, state slot 1, and the ring has 134 rows. Which rows get -1 in slot_mapping_store_swa, and why?

Rows 0-65. Only rows with seqlen_q − j ≤ swa_block_size write, so only the last 134 rows ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:103-106}}). Older rows would be overwritten in the ring by later rows of the same chunk.

 In a decode step, a padding row has positions = 0, state_block_idx = 0 and slot_mapping_store_swa = 0. Why does its write not damage a real sequence?

Slot 0 and block 0 are never given to a sequence: the block lists start at 1 ({{cite csrc/engine/block_manager.hpp:27-30}}). The placeholder uses block table [0] ({{cite deepinfer/worker/model_runner.py:386-403}}) and the default state slot 0 ({{cite csrc/engine/pybind_sequence.cpp:152}}). valid_token_mask is False for it, and the sampler skips it. This is in the deep dive "Worked example: the decode step".

 With DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact and KEEP_TOKENS=140, a new 400-token prompt is cut into a first chunk of 200 tokens. How many rows does this chunk have in the consumer layers, and why not zero?

One row. clip_prefix = clamp(400 − 140 − 0, 0, 200 − 1) = 199, so keep_len = 1 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:225-229}}). The upper limit q_len − 1 keeps one row because every prefill chunk sends its last row through the sampler ({{cite csrc/engine/prepare_sample.cpp:173-180}}). This is in the deep dive "YOCO prefill truncation".
