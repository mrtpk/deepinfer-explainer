This page shows the layer kinds, the optional parts and the file that holds each part. --- DeepInfer runs one model, DeepSeek-V4.1-Flash: an embedding, N decoder layers of attention and MoE with mHC mixing, and a final norm.

The idea

DeepSeek-V4.1-Flash is a {{term llm}} with the usual transformer plan (see {{link learn/transformer}}). The {{term embedding}} turns each token id into a {{term hidden-state}}. Then N {{term decoder-layer | decoder layers}} change the hidden states one after the other. A final norm ends the forward. The {{term lm-head}} turns the last hidden state into {{term logits}}. In DeepInfer the sampler applies the lm head, not the forward.

Each decoder layer has two sub-layers:

  1. Attention. The token looks at earlier tokens. V4.1 uses {{link concepts/mla-attention | MLA attention}}: one 512-value vector per token is both key and value. A layer can read keys from two sources. The first source is a {{link concepts/sliding-window-attention | sliding window}} of recent tokens. The second source is {{link concepts/kv-compression | compressed keys}}: one per token or per 2 tokens. In sparse layers, an {{link concepts/sparse-attention-indexer | indexer}} selects only some of the compressed keys.
  2. MoE. A {{term moe}} block sends each token to a few experts. See {{link concepts/moe-routing}} and {{link concepts/mega-moe}}.

Between the sub-layers, V4.1 does not use a plain residual sum. It keeps hc_mult parallel copies of the residual stream and mixes them before and after each sub-layer. This is {{link concepts/mhc-residual | mHC}}.

Some features change the plan:

  • Layer kinds. The config gives each layer a {{term compress-ratio}}: 0 (sliding window only), 1 (C1) or 2 (C2).
  • {{link concepts/yoco-swa-replay | YOCO}}. The layers from the first C1 layer to the end are "consumer" layers. Their compressed KV comes from one shared hidden state. When YOCO prefill truncation is on (default off), a long prefill computes only the last tokens in these layers.
  • {{link concepts/cross-layer-kv-sharing | Cross-layer sharing}}. A layer can reuse the compressed KV, the index keys or the top-k list of an earlier layer.
  • Optional parts. A DFlash draft head for {{link concepts/speculative-decoding | speculative decoding}}, {{link concepts/engram | Engram}} n-gram memory in some layers, and the {{link concepts/vision-encoder | vision encoder}} for images.

An everyday comparison. Think of an assembly line with N stations. Each product (a token) passes every station in the same order. Each station has two machines: one compares the product with earlier products (attention), one sends it to a few specialists (MoE). The comparison stops here: in a real line, products do not look at each other. Also, here the product travels with several copies of itself (mHC), and a station can borrow a machine setting from an earlier station (sharing).

In the code

Step 1: from config.json to the layer list

The model loader reads the Hugging Face config.json. load_hf_model_config checks the architecture and the number formats, then builds the inference config gpt ({{cite deepinfer/hugging_face/config.py:237-311}}). The per-layer list comes from the config key compress_ratios:

  1. Line 152: ratio 0 gives a sliding-window spec; ratio 1 or 2 gives a compressed spec with an indexer config.
  2. Line 153: the lm head takes one entry, with no attention.
  3. Line 154: one spec for each DFlash layer.
  4. Line 161: n_prefill_layer is the index of the first ratio-1 layer. It is the first YOCO consumer layer (deep dive "YOCO producer and consumer layers").

V41Builder then makes the parameter containers in this order: the embedding, the N blocks, the main head, and the DFlash heads ({{cite deepinfer/model_executor/models/v4_modules/builder.py:105-125}}).

Step 2: three model classes

The only registered architecture is DeepseekV41ForCausalLM. It maps to DeepseekVLForCausalLM ({{cite deepinfer/model_executor/models/__init__.py:15-17}}). The classes nest like this:

  • DeepseekVLForCausalLM (deepseek_vl.py) adds the vision path. In every prefill (also text-only) it computes the input embeddings itself, adds image features when the batch has images, and passes them on ({{cite deepinfer/model_executor/models/deepseek_vl.py:226-234}}).
  • DeepseekForCausalLM (deepseek.py) holds the inner model, the lm head, the sampler, the DFlash module and the expert load balancer ({{cite deepinfer/model_executor/models/deepseek.py:251-321}}).
  • DeepseekModel (deepseek.py) holds the embedding, the N layers and the final norm ({{cite deepinfer/model_executor/models/deepseek.py:59-116}}), and runs the forward ({{cite deepinfer/model_executor/models/deepseek.py:154-248}}).

Step 3: the forward loop

Without input hidden states, the forward starts with the embedding. One CrossLayerRuntime object goes through all layers. A source layer writes shared values into it, and later layers read them ({{cite deepinfer/model_executor/models/v4_modules/cross_layer.py:276-308}}). Then the loop runs the layers:

YOCO truncation: the metadata layout switches from full to compact; the hidden states switch inside the first YOCO consumer layer. Rule: what must be computed to the end (compact) becomes input_metadata; the full metadata goes to the full-source path through the cross-layer runtime. NOTE: when the metadata switches to compact, the hidden states passed in are still the original ones. All DFlash target layers are on the consumer side: dflash_input switches to the compact row count together with the hidden states (cp_mirror_len under CP, else total_q), so that the rows of dflash_input_store match the consumer layer's hidden states.

Lines 191-207 run only in a prefill with YOCO truncation, at the first consumer layer. Lines 210-218 call one layer with its own slice of the KV cache, kv_caches[i]. Each layer returns the new hidden states and the residual data for mHC.

Step 4: one decoder layer

DeepseekDecoderLayer.forward is short. Without the timers and the YOCO boundary, it is four calls:

  1. Line 143: attn_norm_forward finishes the mHC post mix of the previous sub-layer, mixes the copies into one attention input, and normalizes it. It returns FP8 values and a BF16 copy.
  2. Lines 155-161: V4Attention ({{link concepts/mla-attention}}).
  3. Line 162: ffn_norm_forward does the same mHC work around the MoE input.
  4. Lines 169-173: DeepseekMoE ({{link concepts/moe-routing}}).

The page {{link code/decoder-layer}} reads the file line by line, and the tour {{link tours/decoder-layer}} follows one token through it.

Step 5: the end of the forward

The last layer leaves the residual stream as hc_mult copies. Line 227 does the last mHC post mix. With hc_shifted (the HF default is True, {{cite deepinfer/hugging_face/config.py:295}}), line 230 mixes the copies into one. Without it, the HCHead does this (line 238). Line 239 is the final {{term rmsnorm}}. The forward returns these hidden states. The sampler applies lm_head.weight later, only to the rows that it samples ({{cite deepinfer/model_executor/models/deepseek.py:391-400}}).

Step 6: where each piece lives

The file v4_modules/__init__.py sorts the model files into four roles: parameter containers, runtime adapters, tensor operators, and topology ({{cite deepinfer/model_executor/models/v4_modules/__init__.py:6-20}}). This table maps each part of the model to its concept page and its files:

YOCO splits the main layers into two halves:

The HF loader sets n_prefill_layer to the index of the first layer with ratio 1 ({{cite deepinfer/hugging_face/config.py:158-161}}). By line 21, that layer is the first consumer. V4Attention agrees: is_first_yoco_consumer_layer is true when layer_idx == n_prefill_layer ({{cite deepinfer/model_executor/models/v4_modules/attn.py:247}}).

The docstring of _n_prefill_layer says: "it and everything before it form the prefill side, the layers after it are yoco consumer layers" ({{cite deepinfer/hugging_face/config.py:159}}). The code treats that layer as a consumer. This site describes the code.

What changes in a consumer layer. In a KV-source consumer layer, the compressed KV is projected from the shared hidden state, not from the layer's own hidden state ({{cite deepinfer/model_executor/models/v4_modules/attn.py:345-352}}). The shared hidden state is the attention-norm output of the first consumer layer ({{cite deepinfer/model_executor/models/decoder_layer.py:146-152}}). The deployment notes describe the same design: "the decoder layers' block KV cache is projected from the last encoder layer's hidden state" ({{cite doc/inference_deployment_qa.md:187}}).

With DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE set to mask or compact (default off, {{cite deepinfer/environ.py:188}}), a prefill keeps only the last DEEPINFER_YOCO_PREFILL_KEEP_TOKENS query tokens in the consumer layers. The README uses 140 ({{cite README.md:25}}). The page {{link concepts/yoco-swa-replay}} explains this.

The config lists the source layers. _source_map maps every layer from the first source onward to the nearest source at or before it:

Worked example. kv_source_layer_ids = [2, 5] and N = 8 give {2: 2, 3: 2, 4: 2, 5: 5, 6: 5, 7: 5}. Layers 0 and 1 are not in the map, so they use their own KV. Layers 3 and 4 reuse the compressed KV of layer 2; the cache engine gives them the same ca_cache view ({{cite deepinfer/worker/cache_engine.py:448-449}}).

SharedLayerTopology checks the maps at start-up: segments must be contiguous, index-topk segments must lie inside index-K segments, and those inside KV segments ({{cite deepinfer/model_executor/models/v4_modules/cross_layer.py:36-47}}). Share-KV must not cross the YOCO boundary ({{cite deepinfer/model_executor/models/v4_modules/cross_layer.py:114-116}}). The page {{link concepts/cross-layer-kv-sharing}} explains the maps.

DFlash draft head. DeepseekForCausalLM builds DFlash when DEEPINFER_USE_NEXTN_DECODE is not 0 (default 5) ({{cite deepinfer/model_executor/models/deepseek.py:276}}, {{cite deepinfer/model_executor/models/deepseek.py:300-306}}). The DFlash layers come after the lm head in the module list ({{cite deepinfer/model_executor/models/mtp/dflash.py:92-95}}). In the main forward, the layers in dspark_target_layer_ids write a feature row into dflash_input ({{cite deepinfer/model_executor/models/decoder_layer.py:144-145}}). After the loop, update_main_cache turns these features into the DFlash KV. The sampler then runs the drafts. See {{link concepts/speculative-decoding}}.

Engram. The layers in engram_layer_ids get an Engram module ({{cite deepinfer/model_executor/models/decoder_layer.py:80-83}}). It works as a hook inside the attention norm step: after the mHC post mix, it changes the residual stream ({{cite deepinfer/model_executor/models/decoder_layer.py:111-118}}). Engram tables can live in CPU memory: DEEPINFER_ENGRAM_FORCE_GPU_STORAGE moves them to the device, and it is always on with DEEPINFER_ACCELERATOR=ascend ({{cite deepinfer/environ.py:147}}, {{cite deepinfer/model_executor/models/deepseek.py:473-477}}). See {{link concepts/engram}}.

Vision. In a prefill with images, get_input_embeddings embeds the ids and lets the vision-language tuner put image features into the image-token rows ({{cite deepinfer/model_executor/models/deepseek_vl.py:194-224}}). Decode never runs the vision encoder. See {{link concepts/vision-encoder}}.

EPLB. The constructor puts the MoE layers of the main model and of DFlash into groups with the same weight layout. It makes one expert load balancer per group ({{cite deepinfer/model_executor/models/deepseek.py:310-317}}, {{cite deepinfer/model_executor/models/deepseek.py:331-364}}). See {{link concepts/eplb}}.

What can go wrong

  • Wrong checkpoint. The loader accepts one architecture name, model_type == "deepseek_v41", BF16 parameters, FP8 weights with 32 × 32 blocks and FP4 experts. Anything else raises ValueError ({{cite deepinfer/hugging_face/config.py:241-262}}).
  • No vision config. Only multimodal HF models are supported; the loader asserts vl_aligner ({{cite deepinfer/model_config_loader.py:21-22}}).
  • Unsupported ratio. A compress ratio other than 0, 1 or 2 raises ValueError ({{cite deepinfer/model_executor/model_metadata_utils.py:52-53}}).
  • No C1 layer. _n_prefill_layer uses next(...) with no default, so a config without a ratio-1 layer raises StopIteration ({{cite deepinfer/hugging_face/config.py:160-161}}).
  • Bad sharing maps. SharedLayerTopology asserts at start-up. A consumer layer without layer_info_shared_cfg fails on purpose: without the check, it would silently read a cache that nobody writes ({{cite deepinfer/model_executor/models/v4_modules/cross_layer.py:106-112}}).
  • YOCO truncation on a model without consumers. With the mode not off, ModelMetadata asserts that YOCO is on and that the keep-token count is above 0 ({{cite deepinfer/model_executor/model_metadata_utils.py:90-92}}).
  • DFlash and the drafts disagree. The forward asserts that a DFlash module exists exactly when target layers are set ({{cite deepinfer/model_executor/models/deepseek.py:173}}).

Why it matters. The model map tells you which page to read for a question. A question about memory leads to the layer kinds and the caches. A question about speed in long prompts leads to the indexer and YOCO. A question about a wrong output leads to the config checks above.

Which two sub-layers does each decoder layer run, and in which order?

Attention (V4Attention), then MoE (DeepseekMoE). mHC mixing and a norm come before each one ({{cite deepinfer/model_executor/models/decoder_layer.py:143-173}}).

 Does DeepseekForCausalLM.forward return logits?

No. It returns hidden states in CausalLMForwardOutput ({{cite deepinfer/model_executor/models/deepseek.py:246-248}}). The sampler applies lm_head.weight in sample() ({{cite deepinfer/model_executor/models/deepseek.py:392-400}}).

 The config has compress_ratios = [0, 0, 2, 2, 1, 2, 1, 2] for 8 main layers (no draft layers). What is n_prefill_layer, and which layers are YOCO consumers?

The first ratio-1 layer is layer 4, so n_prefill_layer = 4 ({{cite deepinfer/hugging_face/config.py:158-161}}). Consumers are layers 4 to 7: n_prefill_layer ≤ i < N ({{cite deepinfer/model_executor/models/v4_modules/yoco.py:19-21}}). Layer 4 itself is the first consumer, although the docstring says otherwise.

 Which file allocates the attention weights, and which file runs the attention? Why are they separate?

mla_attn.py allocates them (a parameter container); attn.py runs the forward (a runtime adapter). Containers keep the Hugging Face names, shapes and dtypes for loading; runtime files convert them to the layout that the kernels need ({{cite deepinfer/model_executor/models/v4_modules/__init__.py:6-15}}).

 With kv_source_layer_ids = [1, 4] and N = 6, which layers have their own compressed KV cache? Which layers write to the cache of layer 1?

_source_map gives {1: 1, 2: 1, 3: 1, 4: 4, 5: 4} ({{cite deepinfer/hugging_face/config.py:62-65}}). Layer 0 is not in the map, so it is its own source. Own caches: layers 1 and 4, and also layer 0 if layer 0 is a compressed layer (a ratio-0 layer has no compressed cache). Layers 2 and 3 get the ca_cache view of layer 1 ({{cite deepinfer/worker/cache_engine.py:448-449}}), but only the source layer 1 writes it: a consumer has no PackedWkv ({{cite deepinfer/model_executor/models/v4_modules/mla_attn.py:252-269}}). This is in the deep dive "Cross-layer sharing maps".
