The idea

A model is mostly {{term model-weights | weights}}: large tables of numbers. DeepInfer reads them from a {{term hf-checkpoint}}. That is a folder with three kinds of file:

  • config.json: the sizes and settings of the model, for example the number of layers.
  • model.safetensors.index.json: a map from each tensor name to the file that holds it ({{cite deepinfer/hugging_face/weights.py:40}}).
  • The {{term checkpoint-shard | shards}}: many {{term safetensors}} files with the tensor bytes.

DeepInfer does four jobs with this folder. Every {{term rank}} does them itself:

  1. Read the config. Parse config.json, refuse formats that the runtime cannot run, and make the model config.
  2. Draw the plan. Build the whole model on the {{term meta-device}}. This gives the name, shape and dtype of every parameter, but uses no memory.
  3. Match names. Map each checkpoint tensor name to a parameter name. This map is the {{term weight-coverage | coverage}}. If a parameter has no source, stop.
  4. Copy bytes. Give each parameter real memory and copy the bytes into it. Convert the {{term scale-factor | scales}} of {{term fp8}} weights. Each {{term expert-parallelism | EP}} rank reads only its own experts.

An everyday comparison. Think of a move to a new house. First you draw a plan with a label on each room (the meta model). Then you take each box from the truck and read its label (the tensor name). The label tells you the room (the parameter). An empty room stops the move: the house cannot work without it. A box with no room stays on the truck, and nobody complains. The comparison stops here. In DeepInfer, each rank is its own house with its own small set of expert rooms. So each rank opens only some of the expert boxes.

Step 1: config.json becomes model_cfg

load_hf_model_config reads config.json. It accepts only one model family and one number format:

The result is an {{term attrdict}}: a dict that also allows cfg.gpt.hidden_size. Other code adds fields to it. ModelConfig copies four runtime values into model_cfg.gpt ({{cite deepinfer/config.py:82-94}}). Inside the worker, finalize_model_config adds the token limits and the number of extra experts ({{cite deepinfer/model_executor/model_loader.py:116-125}}). Many parts then make a {{term model-metadata}} object from model_cfg.gpt, for example the KV cache manager in cache_engine.py ({{cite deepinfer/worker/cache_engine.py:320}}).

Step 2: check the files and plan the coverage

prepare_hf_coverage runs before the model is built. It reads only the index and the shard headers:

  1. Lines 34-38: read the index. If a shard file does not exist, raise FileNotFoundError.
  2. Lines 40-41: refuse separate HC norm tensors. The runtime needs them folded into the HC matrices.
  3. Lines 42-43: refuse an index where a name occurs with and without the prefix model..
  4. Lines 45-59: open each shard and make sure that it holds every tensor that the index names.
  5. Line 61: build_coverage maps the names and groups them into three channels: ordinary parameters, routed experts and Engram tables.

Step 4: build on meta, tie, then give memory

The builder makes every parameter on the meta device ({{cite deepinfer/model_executor/model_loader.py:128-133}}). Then cover_tied_parameters marks the embedding and output head of each MTP layer as {{term tied-parameter | tied}} to the backbone ({{cite deepinfer/hugging_face/loading.py:69-83}}). When the loader gives memory, a tied parameter gets the storage of its source:

Engram tables stay in CPU memory unless DEEPINFER_ENGRAM_FORCE_GPU_STORAGE is on ({{cite deepinfer/model_executor/models/deepseek.py:473}}). On Ascend the variable is always on ({{cite deepinfer/environ.py:147}}). All other parameters go to the device.

The loader stops only when a model parameter has no source. It does not stop when a checkpoint tensor has no parameter. Such a tensor is not read. So a successful load does not prove that the checkpoint and the model match tensor for tensor.

Step 5: check coverage and shapes, then load

HF checkpoint {hf_dir} does not cover {len(missing)} model parameters: {missing} HF load done: all {len(params)} model parameters come from {hf_dir}
  1. Line 147: missing is the set of model parameters minus the names in the coverage. Only this direction is checked.
  2. Line 150: validate_hf_shapes compares shapes and dtypes of the ordinary parameters and the tied aliases. It does not check experts, Engram tables or .scale tensors. It reads only the safetensors headers ({{cite deepinfer/hugging_face/loading.py:86-121}}).
  3. Lines 151-152: load_covered_params copies the bytes, under a 30-minute watchdog.

An example script uses the one-way rule on purpose. It builds a model with only the vision parameters and loads them from the full checkpoint. Its docstring says, translated: "a parameter tree with only ViT/aligner and the three image_* parameters reads only those 266 tensors" ({{cite examples/_ve_helper.py:32-33}}).

Step 6: read the bytes and convert the scales

DeepInfer has its own safetensors reader. It reads one byte range per tensor with plain file reads, not with a memory map ({{cite deepinfer/hugging_face/weights.py:182-188}}). The ordinary and expert channels use this reader; the Engram channel reads slices with safe_open ({{cite deepinfer/hugging_face/weights.py:358-362}}). For an FP8 weight, it also reads the .scale tensor next to it. The checkpoint stores scales as {{term ue8m0}} bytes. The loader decodes them to FP32 with no loss:

The ordinary channel stores the FP32 scales as param.sf ({{cite deepinfer/hugging_face/weights.py:418-421}}). Routed experts are different: the loader copies their scale bytes without a decode, into the packed layout of the platform ({{cite deepinfer/hugging_face/weights.py:318-323}}).

Step 7: each EP rank reads only its experts

Each EP rank holds a slice of the physical expert slots. The loader takes the slice of the initial slot map:

Take the number of redundant experts that is at least the lower limit and makes num_physical_experts divisible by ep_size. Initial layout: [original routed experts, copied routed experts].

With 8 experts (an example value), EP size 3 and no lower limit, the padding is -(8 + 0) % 3 = 1. So there are 9 slots and 3 per rank. Rank 2 holds slots 6-8. Slot 8 is the first extra slot (extra index 0), so it holds a copy of expert 0 % 8 = 0. Rank 2 reads expert 0 from the checkpoint too. The page {{link concepts/eplb}} explains how these copies move later.

Rules of hf_to_model ({{cite deepinfer/hugging_face/names.py:147-179}}):

  1. Remove a leading model..
  2. Try the vision names. vision_pipeline.aligner.visual_encoder. becomes vision., with renames such as .attn.wqkv. to .attn.qkv. ({{cite deepinfer/hugging_face/names.py:99-129}}).
  3. Try the global embedding names, then the global head names.
  4. For layers.{L}.suffix: module L + 1 and the suffix from the table. An unknown suffix passes through unchanged. The comment says that "the actual parameter container decides whether to load them".
  5. For mtp.{i}.suffix: embed.weight and head.weight give None (tied). MTP-only parts such as markov_head and confidence_head have their own table ({{cite deepinfer/hugging_face/names.py:87-97}}). All others go under block..
  6. Any other name gives None and is not loaded.

Two checkpoint tensors, one parameter. The shared expert's w1 and w3 map to the same linear1. The loader concatenates them along dim 0, in name order (w1 before w3) ({{cite deepinfer/hugging_face/weights.py:93-107}}). If only one of the two exists, the parameter has no coverage.

Scale names. The scale of X.weight is X.scale ({{cite deepinfer/hugging_face/names.py:182-184}}). Scale names are never mapped as parameters (line 95 of weights.py).

The numbers below use example sizes, not values from the repo: hidden size 4096, expert intermediate size 2048.

An ordinary FP8 linear weight with shape [1024, 4096] (E4M3, 4 MiB):

  1. On meta, prepare_meta_fp8 declares an FP32 scale of shape [ceil(1024/32), ceil(4096/32)] = [32, 128] ({{cite deepinfer/model_executor/models/v4_modules/containers.py:128-135}}).
  2. The checkpoint has X.scale: 32 × 128 = 4096 UE8M0 bytes.
  3. The loader copies the weight, decodes the scale to FP32 (16 KiB) and sets param.sf ({{cite deepinfer/hugging_face/weights.py:414-421}}). It does not compare the scale shape with the meta shape; it replaces sf ({{cite deepinfer/model_executor/models/v4_modules/containers.py:100-101}}, {{cite deepinfer/hugging_face/weights.py:420}}).
  4. set_ue8m0_sf packs the FP32 scales again into param.ue8m0_sf ({{cite deepinfer/hugging_face/parameters.py:59-70}}).
  5. The runtime layer converts sf into the GEMM layout when its dtype is not PLATFORM.fp8_sf_type ({{cite deepinfer/model_executor/layers/linear.py:67-76}}).

Only set_ue8m0_sf touches param.ue8m0_sf. It writes the attribute ({{cite deepinfer/hugging_face/parameters.py:70}}). It also reads it in two places, but only for its own work. Line 52 asserts that a CPU scale has no old ue8m0_sf. Line 67 reuses an existing ue8m0_sf as the output buffer. No other code in the repo reads it. The runtime layer copies only sf into its new parameter ({{cite deepinfer/model_executor/utils.py:22-26}}) and converts sf itself. So step 4 seems to do work that the runtime does not use.

The runtime shapes come from materialize_hf_parameter. The weight is int8 (n_experts, h_out, h_in // 2). The scales are (n_experts, h_in // (32 × itemsize), h_out), transposed, so column-major inside each expert ({{cite deepinfer/model_executor/models/v4_modules/containers.py:76-87}}). The loader views the row-major scale bytes as int32 or int16 and copies them in. The asserts check every shape ({{cite deepinfer/hugging_face/weights.py:314-323}}). linear2 works the same way with w2 alone: [4096, 1024] bytes and int32 scales [4096, 16].

Which checkpoint experts a rank reads. For each MoE layer, sorted by layer_id, _local_expert_ids takes physical_to_logical[n_local × ep_rank : n_local × (ep_rank + 1)] ({{cite deepinfer/hugging_face/weights.py:248-272}}). Every MoE layer with the same expert count starts with the same initial map. In the 256 / 20 example, rank 19 holds slots 285-299. Slots 285-299 are copies of experts (285 − 256) to (299 − 256), that is experts 29 to 43. So rank 19 reads no expert that is new to it: it reads 15 experts that other ranks also read.

MTP layers. The expert channel expects dflash_cfg.moe.n_routed_experts experts for an mtp.* prefix, and the main count for layers.* ({{cite deepinfer/hugging_face/weights.py:140-145}}). A layer with a different count is skipped, so its parameter has no coverage and the load stops.

Engram rows. An Engram table is split by rows over the Engram group. Each rank holds num_per_part rows, from row_start = rank × num_per_part. The total is padded up to a multiple of lcm(256, group size) ({{cite deepinfer/model_executor/models/v4_modules/engram_parameters.py:19-40}}). The loader reads the rank's rows in chunks of about 256 MiB (1 << 28 bytes) ({{cite deepinfer/hugging_face/weights.py:345-378}}):

  1. rows_per_chunk = max(1, 2**28 // width). With a width of 1024 bytes, that is 262,144 rows per chunk.
  2. For each chunk, copy the FP8 rows and decode the UE8M0 scale rows to FP32 on the scale's device.
  3. The padded rows past the end of the checkpoint table get weight 0 and scale 1 (lines 379-382).

The table stays in CPU memory unless DEEPINFER_ENGRAM_FORCE_GPU_STORAGE is on. On Ascend that variable is always on ({{cite deepinfer/environ.py:147}}). The scale tensor is always on the device, because gather_sf uses device collectives ({{cite deepinfer/model_executor/models/v4_modules/containers.py:96-98}}).

Tied parameters. cover_tied_parameters adds an alias for each MTP module (number above n_layer + 1) that has emb.tok_emb.weight or shared_head.head.weight. The source is the embedding of module 0 or the head of module n_layer + 1 ({{cite deepinfer/hugging_face/loading.py:72-82}}). validate_hf_shapes checks that each alias has the shape and dtype of its source ({{cite deepinfer/hugging_face/loading.py:119-121}}). The comment in the loader: "MTP never allocates another vocabulary matrix" ({{cite deepinfer/model_executor/models/deepseek.py:483-485}}).

Each rank loads by itself. There is no broadcast of weights between ranks.

  • DP ranks are separate processes, each with its own engine ({{cite examples/_launch.py:35-44}}).
  • CP followers get the method name load_model from the driver by a CPU broadcast, and then run it themselves ({{cite deepinfer/worker/base.py:296-302}}).
  • Each worker parses config.json again (deep dive on config.json).
  • Every rank reads all ordinary parameters, because the dense layers are replicated. It reads only its own experts and its own Engram rows.
  • Each rank opens the shard files itself and keeps one file handle per shard while a reader is open ({{cite deepinfer/hugging_face/weights.py:210-220}}).
  • Each rank has its own watchdog. If load_covered_params takes more than 30 minutes, the process calls os.abort() ({{cite deepinfer/model_executor/model_loader.py:47-62}}).

The log. log_load_phase writes one line per phase, with device memory: plan_build, materialize, engram_preallocate, checkpoint, runtime_adapt and total ({{cite deepinfer/model_executor/models/deepseek.py:470-517}}). Inside checkpoint there are three more: ordinary, experts, engram ({{cite deepinfer/hugging_face/weights.py:429-434}}).

Dummy weights. With load_format="dummy", the engine passes skip_load=True ({{cite deepinfer/engine/llm_engine.py:241}}). The loader then reads no file and makes dummy values ({{cite deepinfer/model_executor/models/deepseek.py:488-494}}). The page {{link concepts/low-precision-formats}} describes them.

What can go wrong

The coverage check is one-way. If a new checkpoint has a tensor that the model does not define, the tensor is not read and no error occurs ({{cite deepinfer/model_executor/model_loader.py:147}}). Compare the log line "HF weight coverage: N tensors" with the number of tensors you expect ({{cite deepinfer/hugging_face/loading.py:62-65}}).
  • Wrong format. A checkpoint with BF16 experts, E4M3 scales or 128 × 128 blocks stops at the config check. DeepInfer has no conversion path.
  • Unfolded HC norms. A checkpoint with separate hc_*_norm.weight tensors stops with "HF requires folded HC weights" ({{cite deepinfer/hugging_face/loading.py:40-41}}).
  • A missing .scale of an ordinary FP8 weight is found only during the copy, after the earlier checks pass and some weights are already loaded. (For experts and Engram tables, a missing .scale removes the coverage, so the coverage check stops the load.)
  • Unexpected extra experts. The lower limit is rounded up, so the memory for experts can be larger than you set. Look for the rounding warning.
  • Slow storage. Every rank reads all dense weights. On a shared file system, many ranks read the same bytes at the same time. If one rank takes more than 30 minutes, it aborts.
  • Engram in host memory. On NVIDIA without DEEPINFER_ENGRAM_FORCE_GPU_STORAGE, the Engram tables use CPU memory. Size the host memory for them.

Why it matters. Weight loading decides what the model computes. Most mistakes stop the start-up with a clear error. The one-way coverage check is the exception, so check the log when you use a new checkpoint.

Which file tells the loader which shard holds a tensor?

model.safetensors.index.json. Its weight_map maps each tensor name to a shard file ({{cite deepinfer/hugging_face/weights.py:40}}, {{cite deepinfer/hugging_face/loading.py:34-35}}).

 A checkpoint has one tensor that the model does not use. Does the load fail?

No. The loader checks only that every model parameter has a source ({{cite deepinfer/model_executor/model_loader.py:147-149}}). An unused tensor is not read.

 What model parameter does layers.0.attn_norm.weight fill?

module.module.1.norm1.weight. Layer 0 is module 1, because module 0 is the embedding, and the suffix attn_norm.weight maps to norm1.weight ({{cite deepinfer/hugging_face/names.py:58}}, {{cite deepinfer/hugging_face/names.py:164-167}}).

 A checkpoint scale byte has the value 130. What FP32 scale does the loader make?

2 ** (130 − 127) = 8.0. _ue8m0_to_fp32 subtracts 127 and calls torch.ldexp(1, e) ({{cite deepinfer/hugging_face/weights.py:163-167}}).

 256 logical experts (example), EP size 20, DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS=32. How many expert slots does each rank hold, and which checkpoint experts does rank 19 read?

The padding is -(256 + 32) % 20 = 12, so there are 44 extra experts, 300 slots and 15 per rank ({{cite deepinfer/model_executor/eplb/__init__.py:27-28}}). Rank 19 holds slots 285-299. The initial map gives slot p ≥ 256 the expert (p − 256) % 256, so rank 19 reads experts 29 to 43 ({{cite deepinfer/model_executor/eplb/__init__.py:36-39}}, {{cite deepinfer/hugging_face/weights.py:265-267}}).
