The idea

DeepInfer uses {{term data-parallelism}} (DP) for attention. One DP replica is one engine: one Python process with its own LLMEngine, its own scheduler, its own requests and its own KV cache. Replicas do not share requests. The docs say "attention uses data parallelism (#DP = #EP)" ({{cite doc/inference_deployment_qa.md:33}}).

The replicas are not independent, because of the MoE layers. With {{term expert-parallelism}}, each rank holds only some experts. In each MoE layer, DeepEP sends tokens to the ranks of their experts and back. These are {{term collective | collectives}}: every rank of the EP group must call them, also a rank with no tokens.

So the replicas must keep in step. Three rules make this true:

  1. The same number of steps. A replica keeps calling step() while any replica has work.
  2. The same kind of step. At a prefill {{term attempt-point | attempt point}}, the replicas vote. Then all run a prefill step, or all run a decode step.
  3. A step with no work is still a step. A replica with nothing to do runs a {{term placeholder-step | placeholder step}}: the model runs on one dummy sequence.

Each vote is an {{term all-reduce}} over the DP group. We call it a {{term step-vote | step vote}}.

An everyday comparison. Think of rowers in one boat. Each rower has an own oar and own strength, like a replica with its own requests. The boat moves well only if all rowers pull at the same time. Before a change of stroke, the crew agrees on the new stroke. A rower with no strength left still moves the oar with the others. The analogy stops at the vote: DeepInfer replicas do not vote before every step, only at attempt points. Between attempt points, all replicas run decode steps without a vote.

In the code

Step 1: one process per replica

The example launcher starts one process per DP rank. It uses the spawn method and waits for all of them:

Each process makes its own LLM with engine_rank = dp_rank ({{cite examples/offline_inference.py:45-51}}, {{cite examples/_config.py:113-117}}). ParallelConfig stores data_parallel_rank = engine_rank % data_parallel_size ({{cite deepinfer/config.py:167}}). The {{term engine-rank | engine rank}} also sets the global rank: engine_rank × cp_size + cp_rank ({{cite deepinfer/worker/base.py:329}}).

The example gives the replicas different work on purpose: replica r gets r + 1 copies of the test prompts ({{cite examples/_prompts.py:100}}). So replica 0 finishes first and then runs placeholder steps until the last replica is done.

Step 2: the DP group

create_process_groups makes the DP group and a Gloo (CPU) copy of it:

The rearrange puts ranks with the same cp_rank into one group. With CP size 1, the DP group is all engines. With CP size 2 and 4 engines, the DP groups are [0, 2, 4, 6] and [1, 3, 5, 7]. The scheduler runs only in the engine process (CP rank 0), so only the group [0, 2, 4, 6] votes.

The engine gives the scheduler the Gloo copy when {{term zos}} is on (the default for a NORMAL engine), else the device group ({{cite deepinfer/engine/llm_engine.py:313}}). The scheduler stores the choice and puts its vote tensor on the CPU or on the device ({{cite csrc/engine/scheduler.hpp:109-111}}, {{cite csrc/engine/scheduler.hpp:170-182}}).

Step 3: the same number of steps

LLM._run_engine calls step() while has_unfinished_requests() is true ({{cite deepinfer/entrypoints/llm.py:176-178}}). That function takes the maximum over the DP group:

So the loop ends on all replicas in the same call. A replica with no requests keeps calling step() until the busiest replica is done.

Step 4: the same kind of step

The C++ scheduler makes the decision in _schedule, in the branch for the NORMAL engine:

NORMAL engine: decide whether the whole group runs a prompt step or a decode step in this step. Inside DP, the type must be the same; a vote makes it the same. ALL point (every prefill_attempt_interval decode steps): prefill only if all ranks have prefill work. This prevents steps where one rank works and the other ranks run empty prompt steps with it. ANY point (every prefill_any_attempt_interval decode steps): prefill together if one rank has work. This is the safety net for an isolated rank: its prefill waits at most this many decode steps. If both kinds of point fall on the same step, it counts as ANY. A prompt step sets decode_step to 0 (see schedule()). So the step right after a prefill has decode_step == 0 and is an ALL point again: to prefill again, all ranks must have work. decode_step is the same on every rank, so the number and the meaning of the votes match in the group, and the all-reduce does not hang. Second vote: confirm that some rank really scheduled a prefill. "want" looked only at a non-empty waiting queue, but _schedule_prefill can still come back empty (slots full, not enough KV blocks). If the whole group comes back empty, the step must be a decode step. A forced empty prompt step would set decode_step to 0; the next step would vote and come back empty again; with running full and waiting not empty, this is an endless loop. Some rank in the group really runs a prompt step: this rank runs an empty prompt step with it, so that the step type stays the same.
  1. Lines 308-312: if decode_step is not an attempt point, the step is a decode step. No vote runs.
  2. Line 313: this replica "wants" a prefill if the KV cache use is 90 % or less and the front of waiting is schedulable.
  3. Lines 315-319: vote 1, an all-reduce MIN. The encoding makes MIN mean "any" at an ANY point and "all" at an ALL point.
  4. Lines 324-326: only a replica that wants a prefill tries to schedule one.
  5. Line 332: vote 2. If no replica got a batch, all run a decode step.
  6. Line 340: a replica with no batch returns an empty prompt step. The engine turns it into a placeholder step.

decode_step is set to 0 after a prompt step and goes up by 1 after a decode step ({{cite csrc/engine/scheduler.hpp:676-680}}). All replicas run the same step types, so the counter has the same value on all of them. The page {{link concepts/scheduler}} explains the intervals and the watermark in full.

Step 5: placeholder steps

The engine marks a step with no scheduled sequence as a placeholder ({{cite deepinfer/engine/llm_engine.py:972}}). The worker then runs the model on one dummy sequence:

The dummy sequence has one token with id 0, block table [0] and greedy sampling ({{cite deepinfer/worker/model_runner.py:386-403}}). The free list of the block manager starts at block 1, so block 0 is never given to a real sequence ({{cite csrc/engine/block_manager.hpp:27-30}}). So the dummy step does not change the data of real sequences. The model still runs every layer, so every MoE collective runs. The engine ignores the sampler output of a placeholder step ({{cite deepinfer/engine/llm_engine.py:987}}).

Step 6: why one step type

The source comment states the rule (line 296 above) but not the reason. The code shows these collectives in a step:

  • MoE dispatch and combine over the EP group, in every MoE layer ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:565-616}}). The EP group is a block of ep_size neighbour ranks, or the world group ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:101-106}}). So it holds the ranks of several replicas. The dispatch passes a different token limit in a prefill step and in a decode step ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:476}}).
  • The draft model runs only in decode steps, and its layers have MoE blocks ({{cite deepinfer/model_executor/layers/sampler.py:236-248}}, {{cite deepinfer/model_executor/models/mtp/dflash.py:389-392}}).
  • CP all-gathers run only in prefill steps ({{cite deepinfer/model_executor/models/v4_modules/attn.py:766}}).
  • The EPLB statistics run an all-gather over the EP group once every 128 steps (DEEPINFER_MOE_LB_STAT_INTERVAL, {{cite deepinfer/environ.py:118}}, {{cite deepinfer/model_executor/eplb/__init__.py:167-190}}). This needs the same number of steps on all ranks.

A collective finishes only when every rank of the group calls it. If two ranks call different collectives, or the same collective with different arguments, they can wait for each other with no end. (This is general behaviour of collectives, not a DeepInfer rule.)

So a normal decode step has one all-reduce: the loop check. An attempt point has two or three. The vote tensors are one int32 value ({{cite csrc/engine/scheduler.hpp:170-182}}). The loop check uses one int64 value ({{cite deepinfer/engine/llm_engine.py:676}}).

Device or CPU. With ZOS on, both use the Gloo group and CPU tensors ({{cite deepinfer/engine/llm_engine.py:667-669}}, {{cite deepinfer/engine/llm_engine.py:313}}). A device all-reduce followed by .item() waits for the device. A CPU vote does not. With ZOS off, both use the device group.

A detail with one replica. The comment above _dp_allreduce says that it communicates also when dp_size == 1, and the caller must skip it ({{cite csrc/engine/scheduler.hpp:169}}). _schedule does not skip it. With one replica, the vote is an all-reduce over a group of one rank. The loop check in Python does skip it ({{cite deepinfer/engine/llm_engine.py:675}}).

Setting: --ep 4, so 4 replicas and an EP group of 4 ranks ({{cite examples/offline_inference.py:24-28}}). Default intervals: ALL every 70, ANY every 100 ({{cite deepinfer/environ.py:174-177}}). Replicas 0-2 have running sequences. Replica 3 has none.

  1. decode_step 1 to 69: decode steps, no vote. Replica 3 runs placeholder decode steps.
  2. decode_step = 70 (ALL): one new request has arrived at each of replicas 0, 1 and 2. Vote 1: MIN(1, 1, 1, 0) = 0. No prefill. All decode.
  3. 71 to 99: decode steps, no vote. The new requests wait.
  4. 100 (ANY): vote 1: MIN(0, 0, 0, 1) = 0, so a prefill step. Replicas 0-2 schedule their prompts. Vote 2: MIN(0, 0, 0, 1) = 0. Replica 3 returns an empty prompt step and runs a placeholder prefill. decode_step becomes 0 on all replicas.
  5. Next step, decode_step = 0 (ALL): replica 0 has a second chunk to prefill. Replica 3 has nothing, so vote 1 fails. All decode, and decode_step becomes 1. The second chunk waits until step 70 (ALL, fails again if replica 3 is still empty) or step 100 (ANY).

The result: the new requests waited 30 decode steps for their first prefill. Without the idle replica 3, they would have started at step 70. The ANY points bound the wait: a prefill waits at most about 100 decode steps, the comment says ({{cite csrc/engine/scheduler.hpp:301-302}}).

Where the 90 % watermark comes in: a replica with a full KV cache does not want a prefill (line 313). At an ALL point it blocks the others. At an ANY point the others prefill without it.

In this release, nothing moves requests between replicas. Each process gets its own requests from its caller. The README lists "Load balancing across data-parallel replicas for both prefill and decode" under "Required for a complete inference service (not included in this release)" ({{cite README.md:38-42}}).

The deployment Q&A describes the production balancers in its section "Data-parallel load balancing" ({{cite doc/inference_deployment_qa.md:105-127}}):

  • Prefill. Requests go into 4 tiers by total context length: under 16K, 16-64K, 64-256K and 256K or more. Engines pull work by their remaining compute quota. Inside a DP group, each request goes to the DP rank with the lowest quota load ({{cite doc/inference_deployment_qa.md:109-113}}).
  • Inside one GPU. FIFO, with a chunk size from a time budget and a fitted quadratic cost model, at most 32,768 tokens. "The budget itself is further reduced by an all-reduce MIN within the DP group" ({{cite doc/inference_deployment_qa.md:115}}).
  • Decode. Uniform routing over all GPUs of all decode instances, which balances the request count and the total KV length ({{cite doc/inference_deployment_qa.md:119}}).
  • Result. "roughly 80% of a perfectly balanced offline benchmark" ({{cite doc/inference_deployment_qa.md:127}}).

The code of this release does not have the compute quota or the cost model in its scheduler. The step votes are the only coordination between replicas in this release.

The DP rearrange is "(replica dp cp) -> (replica cp) dp" ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:92}}). What can go wrong

Every replica must call step() the same number of times. LLM.generate does this with the MAX vote. Code that drives the engine directly, such as a benchmark, must keep this rule too. A replica that stops early leaves the others waiting in a collective.
  • Slow first tokens with uneven load. One replica with no waiting request makes every ALL vote fail. New requests on the other replicas then wait for the next ANY point, up to about 100 decode steps ({{cite csrc/engine/scheduler.hpp:301-302}}).
  • Wasted device time. A replica with no work runs placeholder steps, each with a full pass through all layers. The example launcher makes this visible: replica 0 has the fewest prompts ({{cite examples/_prompts.py:100}}).
  • Finished requests in the queue. Without a clean-up, an aborted request that stays in waiting would block the ALL votes of the group for ever. The source comment gives this reason, and the decode branch removes such requests ({{cite csrc/engine/scheduler.hpp:564-577}}).
  • A hang, not an error. If the replicas disagree on a collective, nothing raises at once. The ranks wait. DEEPINFER_GLOO_TIMEOUT (4 hours) applies only to the default group ({{cite deepinfer/worker/base.py:334-340}}). The DP groups come from new_group with no time-out argument, so the PyTorch default applies ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:34}}).

Why it matters. DP for attention needs no communication in the attention layers, but MoE with EP ties all replicas together. The votes are the price: one replica with no work, or with a full cache, can delay the prefills of all replicas. A production system needs a load balancer in front of the replicas. This release does not have one.

Is one DP replica a thread, a process or a device group?

A process. run_dp starts one process per DP rank with the spawn method ({{cite examples/_launch.py:35-44}}). Each process makes its own LLM and engine. With CP above 1, the replica also starts CP follower processes.

 Replica 2 has no requests, but replica 0 still has three. Does replica 2 call step()?

Yes. has_unfinished_requests() takes the MAX over the DP group, so it is true on every replica ({{cite deepinfer/engine/llm_engine.py:673-678}}). Replica 2 runs placeholder steps ({{cite deepinfer/worker/worker.py:125-127}}).

 At an ANY point, replica 1 wants a prefill, but its _schedule_prefill returns nothing because all slots are full. The other replicas do not want a prefill. What kind of step runs?

A decode step on all replicas. Vote 1 passes (replica 1 sent 0). Vote 2 fails: every replica sends 1 because no replica has a batch, and MIN = 1 ({{cite csrc/engine/scheduler.hpp:332-335}}). The comment explains why: an empty prompt step would reset decode_step and could loop for ever.

 Why does the vote use MIN for both ALL and ANY points?

Only the encoding changes. For ALL, "wants" is 1, so MIN is 1 only if all send 1. For ANY, "wants" is 0, so MIN is 0 if one sends 0 ({{cite csrc/engine/scheduler.hpp:315-319}}). One reduce op serves both.

 You run --ep 2 --dp 8. Replicas 0 and 1 share an EP group. Could replicas 0-1 and replicas 2-3 safely run different step types? What does the code do?

From the MoE side, perhaps: their EP groups are disjoint ([0,1] and [2,3], {{cite deepinfer/model_executor/parallel_utils/parallel_state.py:101-106}}). But the code does not make this choice. The scheduler votes over the whole DP group of 8 replicas ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:91-93}}, {{cite csrc/engine/scheduler.hpp:170-182}}). So all 8 run the same step type. One empty replica can make the ALL votes of all 8 fail.
