C2 mixes the two tokens with a learned softmax gate and keeps the score and latent of the most recent tokens in a small fp32 state ring. Entries are FP4 (288 B) by default, or FP8 (528 B). --- A C2 layer mixes each pair of tokens into one cache entry; a C1 layer keeps one entry per token. Both cover the whole history.

The idea

The {{link concepts/sliding-window-attention | sliding window}} gives exact keys for the last 128 tokens only. To see older tokens, a layer needs keys for the whole history. {{term kv-compression | KV compression}} keeps those keys small in two ways.

  1. Fewer entries. The {{term compress-ratio}} n of a layer is 1 or 2. The code calls the two kinds C1 and C2 ({{cite deepinfer/model_executor/models/v4_modules/compress.py:75-76}}). A C1 layer stores one {{term compressed-entry}} per token. A C2 layer stores one entry per 2 tokens.
  2. Fewer bytes per entry. Each entry has 512 values in {{term fp4}} with scales: 288 bytes. The FP8 option uses 528 bytes.

A C2 entry is not the average of two tokens. A second projection, the gate, gives each value of each token a score. A {{term softmax}} over the 2 tokens turns the scores into weights, value by value. The entry is the weighted sum of the two token vectors. So the model learns which token is more important for each value.

The cache entries live in the paged cache ca_cache, in blocks of 128 tokens. A C1 layer has 128 entries per block, a C2 layer 64. A C2 layer also needs a little {{term compression-state}} per sequence, because the first token of a pair must wait for the second.

An everyday comparison. Think of a photo album where you keep one photo for every two days. For each part of the picture (sky, faces, background), you choose the share of each day. Then you blend the two photos. The comparison stops here: the "parts" are 512 numbers, and the model learned the blend rule in training.

In the code

Step 1: the projection

The weights are in PackedWkv, an object of class SoftmaxAPEGatedColumnParallelLora:

Line 66 explains why C1 has no gate: "the single-token softmax of C1 is always 1". V4Attention merges [Gate, A] into one GEMM over the BF16 hidden state. The output is fp32 for C2 and bf16 for C1 ({{cite deepinfer/model_executor/models/v4_modules/attn.py:345-371}}). Only a KV-source layer has these weights; see {{link concepts/cross-layer-kv-sharing}}.

Step 2: C1 passes through, C2 mixes

  1. Lines 89-93: C1. The projected vector is the entry. With context parallelism, a gather puts the rows back in sequence order.
  2. Line 96: C2. The fp32 output splits into score (gate part) and latent (A part), each [T, 512].
  3. Lines 97-109: prefill. One kernel makes all new entries of the chunk and updates the state.
  4. Lines 111-119: decode. Another kernel writes each token into the state ring and makes an entry where a pair ends. max_seqlen_q is 1 + 5 = 6 with the default drafts.

The TileLang kernel does the mix value by value. It computes the softmax weights over the 2 tokens, then the weighted sum of the latents ({{cite deepinfer/model_executor/layers/tilelang_ops/cuda/compress.py:120-132}}). The reference code says the same in one line: (latent_slice * score_slice.softmax(dim=0)).sum(dim=0) ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:199}}).

Step 3: norm, RoPE, cast and store in one kernel

One fused kernel does RMSNorm, {{term rope}} on the last 64 values, the cast to the cache format, and the store at slot_mapping_store_ca. With out_stage="norm" it also returns the vector after the norm and before RoPE (pre_rope_kv). The {{link concepts/sparse-attention-indexer | indexer}} projects its keys from that vector ({{cite deepinfer/model_executor/models/v4_modules/compress.py:1-6}}). get_kv_cache_format finds the format from the last dimension of the cache: 288 or 528 bytes ({{cite deepinfer/model_executor/layers/tilelang_ops/cache_common.py:171-187}}).

Step 4: which position does an entry have?

Before the step, the input preparation computes the position and the cache slot of each new entry. For prefill this is C++; for decode with zero-overhead scheduling (the default) a device kernel does the same work ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:336-367}}). The C++ prefill code:

Entry j covers tokens j·n … j·n + n − 1. Its RoPE position is j·n, the position of its first token (line 59). A prefill makes an entry only for complete pairs: j runs from (k − q) / n to k / n − 1, with each division rounded down. The slot uses the block table: 64 entries per block for C2 (line 60). A sequence with no complete pair still gets one pad row with slot −1 (lines 63-66).

Step 5: where the entries go, and the state ring

Whether the main (compressed) KV is reused depends only on the KV map, not on the index map. All compress ratios (C1/C2) are handled the same way.

Each block row of gpu_blocks has a byte range for this layer: 128 // ratio entries of 288 or 528 bytes. Only C2 gets a state, of get_inference_compress_block_size(2) tokens:

With the default backtracking count 6, the ring has 2 + 5 = 7 tokens. _alloc_state views it as fp32 [num_state_slots, 7, 2, 512]: index 0 is the score, index 1 is the latent ({{cite deepinfer/worker/cache_engine.py:367-374}}, {{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:208-209}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

A new prompt of 1,000 tokens (seqlen_k = seqlen_q = 1,000), one C2 layer, FP4 entries, block size 128.

  1. Entries. j = 0 … 499: 500 entries ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:47-49}}). Entry 499 covers tokens 998 and 999; its RoPE position is 998.
  2. Blocks. The sequence has 8 blocks (1,000 / 128, rounded up). Entry j goes to block block_table[j / 64], row j % 64. Entries 448 … 499 fill 52 of the 64 rows of the eighth block.
  3. Bytes. 500 × 288 B = 144,000 B of entries in this layer. The 8 blocks reserve 8 × 64 × 288 B = 147,456 B.
  4. State after the prefill. The kernel stores the score and latent of the last min(1,000, 7) tokens: positions 993 … 999 go to ring slots pos % 7 ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:201-209}}).
  5. First decode step. Positions 1,000 … 1,005. Each token writes slot (context_len − 1) % 7. Positions 1,001, 1,003 and 1,005 end a pair, so they make entries 500, 501 and 502 ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:227-248}}, {{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:79-91}}). The other three tokens get slot −1.

An odd prompt. With 1,001 tokens, the prefill still makes 500 entries. Token 1,000 exists only in the state ring and in the sliding window. The first decode token (position 1,001) reads token 1,000 from the ring and makes entry 500.

What a query sees. A query at position p reads (p + 1) / n entries, rounded down ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:449}}, {{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:598}}). At p = 1,000 in a C2 layer that is 500 entries (tokens 0 … 999). Token 1,000 itself is in the window.

The decode kernel asserts that the ring holds one compression window plus the tokens of one step:

  1. A step brings at most max_seqlen_q = 6 tokens per sequence ({{cite deepinfer/model_executor/models/v4_modules/compress.py:117}}).
  2. The first token of the step can be the second half of a pair whose first half came in the step before. So the ring must keep 1 older token plus 6 new ones: 2 + 6 − 1 = 7.
  3. get_inference_compress_block_size gives ratio + max(0, backtracking − 1) = 2 + 5 = 7 ({{cite deepinfer/worker/cache_engine.py:130-133}}).

The function is cached with lru_cache. After a change of DEEPINFER_MAX_BACKTRACKING_TOKENS in the same process, call clear_compress_block_size_cache() ({{cite deepinfer/worker/cache_engine.py:136-138}}).

Not stored. The compression state is in the "dropped" part of the state slot. The docs say that compression windows end at multiples of the 128-token store grain, so the state has no dependency across a store boundary ({{cite doc/inference_deployment_qa.md:163}}, {{cite deepinfer/worker/cache_engine.py:285}}).

  • Choice. use_fp4_sparse_kv selects FP4 for ca_cache. The HF loader sets it to True unless config.json says otherwise ({{cite deepinfer/hugging_face/config.py:302-303}}). The scale group size follows: 16 for FP4, 32 for FP8 and for SWA ({{cite deepinfer/model_executor/model_metadata_utils.py:37-39}}).
  • The 512 values. kv_lora_rank + qk_rope_head_dim must equal 512 ({{cite deepinfer/worker/cache_engine.py:53-54}}). RoPE goes on the last 64 values (offset = 512 − rotary_dim, {{cite deepinfer/model_executor/models/v4_modules/compress.py:156}}).
  • Block row. A C2 layer adds 64 × 288 = 18,432 B to each block row; a C1 layer adds 128 × 288 = 36,864 B ({{cite deepinfer/worker/cache_engine.py:452-461}}). The whole row is padded to lcm(128, bytes_per_token) ({{cite deepinfer/worker/cache_engine.py:481-484}}).

Per token and layer, with FP4: C1 288 B, C2 144 B. The indexer keys of a sparse layer come on top ({{link concepts/sparse-attention-indexer}}).
  • Prefill. The entries are stored first. Then load_paged_kv_cache converts the entries of each sequence to BF16 and appends them to the gathered buffer, after the SWA rows ({{cite deepinfer/model_executor/models/v4_modules/attn.py:833-839}}). A query's compressed indices point into that buffer.
  • Decode. The kernel reads ca_cache directly. The indices are physical slots: block_table[pos // tpb] × tpb + pos % tpb, with tpb = 64 for C2 ({{cite deepinfer/model_executor/layers/tilelang_ops/get_kv_index.py:41-57}}).
  • Sparse or dense. In a sparse layer the indexer selects index_topk entries. A dense compressed layer reads all (p + 1) / n entries; in prefill, its index row has width pad128(max_model_len / n) ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:358-363}}).

What can go wrong

  • Another ratio. Ratio 4 or 128 in config.json raises ValueError "C4 and C128 have been removed" ({{cite deepinfer/model_executor/model_metadata_utils.py:52-53}}).
  • A config without use_ape. Outside the HF loader, a missing use_ape key counts as True. If the model has a compressed layer, this raises ValueError ({{cite deepinfer/model_executor/model_metadata_utils.py:57-58}}).
  • A state ring that is too small. The decode kernel asserts state size ≥ ratio + max_seqlen_q − 1 ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:98-100}}). This can happen if the ring size is cached and the backtracking value changes later ({{cite deepinfer/worker/cache_engine.py:130-138}}).
  • Wrong dtype into the compressor. C1 must get bf16 and no state; C2 must get fp32 and a state. Both are asserts ({{cite deepinfer/model_executor/models/v4_modules/compress.py:90}}, {{cite deepinfer/model_executor/models/v4_modules/compress.py:95}}).
  • Block size. C++ checks that the block size divides by every ratio ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:3-9}}).
  • Precision. FP4 keeps 16 values per scale. If the outputs drift, compare with use_fp4_sparse_kv=false in config.json (528-byte entries).

Why it matters. The compressed cache is the part of the KV cache that grows with the sequence. Its size per token decides how many long requests fit on a device. A C2 FP4 layer needs 144 bytes per token. A classic BF16 layer with 64 heads and separate K and V of 512 values each needs 131,072 (see {{link concepts/mla-attention}}).

How many compressed entries does a C2 layer store for a 1,000-token prompt, and how many bytes in FP4?

500 entries ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:47-49}}), 500 × 288 B = 144,000 B ({{cite deepinfer/model_executor/layers/tilelang_ops/cache_common.py:119-128}}).

 Why does a C1 layer have no Gate weight?

A softmax over a single token is always 1, so the weight would not change anything ({{cite deepinfer/model_executor/models/v4_modules/mla_attn.py:66}}, {{cite deepinfer/model_executor/models/v4_modules/mla_attn.py:86-95}}).

 Which RoPE position does the C2 entry of tokens 998 and 999 get?

998: p_pos[i_cq] = j * n with j = 499 and n = 2 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:59}}). The fused kernel applies RoPE at positions_c ({{cite deepinfer/model_executor/models/v4_modules/compress.py:144}}, {{cite deepinfer/model_executor/models/v4_modules/compress.py:151-157}}).

 With the default settings, why does ca_state have 7 token slots, and what is in each slot?

A decode step brings up to 6 tokens, and the first can close a pair opened in the step before: 2 + 6 − 1 = 7 ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:98-100}}, {{cite deepinfer/worker/cache_engine.py:130-133}}). Each slot holds the fp32 score (index 0) and latent (index 1) of one token, 512 values each ({{cite deepinfer/worker/cache_engine.py:367-374}}, {{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:208-209}}). See the deep dive "Why 7 state slots".

 A prompt has 1,001 tokens. Where is token 1,000 after the prefill, and when does it enter ca_cache?

The prefill makes only complete pairs, so token 1,000 has no entry yet ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:58}}). Its score and latent are in the state ring (the prefill stores the last 7 tokens, {{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:201-209}}), and its SWA KV is in the window. The first decode token, position 1,001, closes the pair and makes entry 500 ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:237-248}}).
