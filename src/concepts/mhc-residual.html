Before each sub-layer, learned weights mix the streams into one input. After it, the output goes back into all streams. The model ends with one fold. --- mHC keeps hc_mult copies of the residual stream and mixes them, with weights per token, before and after each sub-layer.

The idea

A normal transformer layer has a {{term residual-stream}}. Each {{term sub-layer}} (attention or the feed-forward part) reads the stream, computes a change, and adds the change back: x_next = x + F(norm(x)). The addition has a fixed weight of 1. The stream is one vector of H numbers per token.

DeepSeek-V4.1 replaces this with {{term mhc}}. The residual stream becomes hc_mult parallel streams per token. The code calls them the {{term mhc-trunk | trunk}}: a tensor [T, hc_mult, H] ({{cite deepinfer/model_executor/models/v4_modules/hc.py:58}}). Around each sub-layer, three sets of weights act on the trunk:

  1. The {{term pre-mix}} makes one sub-layer input from the streams: a weighted sum, one weight per stream.
  2. The sub-layer runs on this one input, as in a normal model.
  3. The {{term post-mix}} says how much of the output each stream gets. The {{term comb-mix | residual mix}} (an hc_mult × hc_mult matrix) mixes the old streams into the new streams.

The model computes these weights again for each token and each sub-layer, from the trunk itself. At the end of the model, one last mix folds the streams back into one hidden state. The final norm and the sampler then see a normal [T, H] tensor.

An everyday comparison. Think of a meeting room with four whiteboards and a row of speakers. Before each speaker talks, an assistant writes one summary sheet from the boards: much of board 1, a little of board 3. The speaker reads only this sheet. After the talk, the assistant copies the speaker's notes onto every board, with a different strength for each board. The assistant also moves some old text between the boards. The comparison stops here: the "boards" are vectors, and the assistant computes new strengths for every token and every speaker.

The repo never spells out "mHC". Outside the repo, DeepSeek published a design with the name mHC: Manifold-Constrained Hyper-Connections. It extends hyper-connections, an earlier design with several residual streams and learned mixes. The "constraint" in that design keeps the residual mix doubly stochastic (rows and columns sum to 1), with Sinkhorn normalization. The code shows this part: it applies Sinkhorn normalization to the residual mix ({{cite deepinfer/model_executor/models/v4_modules/hc.py:358}}). This site describes only what the code does.

In the code

Five files hold the work ({{cite deepinfer/model_executor/models/v4_modules/__init__.py:16-17}}, {{cite deepinfer/model_executor/models/v4_modules/__init__.py:27}}). hc_blocks.py holds the weights, and hc.py runs the forward. mhc_ops.py and mhc_modeling.py call the kernels. hc_lazy.py holds one small data class. The page {{link code/v4-hc}} reads these files line by line.

Step 1: the weights of one layer

Each decoder block has one set of mHC weights for attention and one for the MoE. With m = hc_mult:

  1. Line 23: each weight set makes (2 + m) × m values per token: m pre values, m post values, and m × m residual-mix values. For m = 4 that is 24.
  2. Lines 34-35: hc_attn and hc_ffn are the "base" vectors: one bias per mix value.
  3. Lines 38 and 40: fn is a float32 matrix [(2 + m) × m, m × H]. It maps the whole flattened trunk of a token to the mix values.
  4. Lines 39 and 41: scale has 3 values, one for each group (pre, post, residual mix).

The container is built on the meta device ({{cite deepinfer/model_executor/model_loader.py:132-133}}), so the start values on lines 25-41 never reach the device. The checkpoint gives all values. The HF checkpoint must have the norm weights already folded into fn: a separate HC norm tensor raises ValueError ({{cite deepinfer/hugging_face/loading.py:39-41}}). The folded matrices must stay float32 ({{cite deepinfer/hugging_face/loading.py:112-116}}).

Step 2: the first layer makes the trunk

The embedding gives one vector per token, [T, H]. The first decoder layer gets residual = None ({{cite deepinfer/model_executor/models/deepseek.py:164}}). In that case _hc_fused_post_pre makes the trunk:

expand_to_mhc makes a [T, m, H] tensor from the [T, H] embedding output ({{cite deepinfer/model_executor/models/v4_modules/mhc_ops.py:25-28}}). The comment on line 205 calls the input "the un-broadcast trunk", so each stream starts as the same vector. With {{term hc-shifted | shifted mHC}}, line 208 also makes a one-hot pre mix. Its docstring says it is "equivalent to pre reading only main path 0" ({{cite deepinfer/model_executor/models/v4_modules/hc.py:45-49}}).

Step 3: pre — from many streams to one input

_hc_pre computes the mixes and the sub-layer input. Without hc_shifted, one fused operator does all of it:

  1. Lines 329-339 (not shifted): mhc_pre_big_fuse returns the post mix, the residual mix and the layer input. Its docstring lists the parts: "prenorm GEMM + reduce/rmsnorm + split mixes + sinkhorn + apply mix" ({{cite deepinfer/model_executor/models/v4_modules/mhc_modeling.py:84-88}}).
  2. Line 343 (shifted): the input uses the pre mix of the previous sub-layer.
  3. Lines 344-358 (shifted): the same mix computation as separate operators. mhc_pre_norm_fn gives [T, 2m + m²] raw values. mhc_pre_split_mixes splits them into pre [T, m, 1], post [T, m, 1] and residual mix [T, m, m] ({{cite deepinfer/model_executor/models/v4_modules/mhc_ops.py:88-92}}). sinkhorn_normalize normalizes the residual mix.
  4. Lines 359-363: the sub-layer's own {{term rmsnorm}} (attn_layernorm or ffn_layernorm) normalizes the input. It gives FP8 values with scales, and a BF16 copy.
  5. Line 364: the trunk and the mixes go into an {{term hc-lazy-post-data}} object. The post mix uses them later.

Step 4: post — the output goes back into the trunk

After the sub-layer, its output x [T, H] must go back into the trunk. DeepInfer does not do this at once. It waits until the next sub-layer starts, and then does the post and the next pre together ({{cite deepinfer/model_executor/models/v4_modules/hc.py:62-64}}):

mhc_post takes the output, the old trunk, the post mix and the residual mix, and returns the new trunk [T, m, H]. The kernel is not in the repo. The FLOP counter of the engine counts a post term of m × (m + 1) × H per token, times a fixed cost factor ({{cite csrc/engine/flops_estimator.hpp:111}}). That is m + 1 scaled vectors of length H for each new stream. It fits the simplified model R_new = comb @ R + post × x (see the deep dive "A worked example with numbers").

The fused path needs a GPU, hc_mult = 4 and H a multiple of 1024. Then one call to deep_gemm.mega_mhc does four things: the previous post, this pre, the RMSNorm and the FP8 cast ({{cite deepinfer/model_executor/models/v4_modules/hc.py:97-101}}, {{cite deepinfer/model_executor/models/v4_modules/hc.py:236-238}}). This is {{term mega-mhc}}. Two boundaries do not use it. The first boundary of the model has no post data yet. At the attention boundary of an Engram layer, the Engram hook must run between the post and the pre ({{cite deepinfer/model_executor/models/v4_modules/hc.py:184-202}}).

Step 5: the fold at the end of the model

The last layer returns the MoE output [T, H] and the lazy data. DeepseekModel.forward finishes the work:

  1. Line 227: the last post mix. The result is the full trunk [T, m, H].
  2. Line 230 (shifted): the last pre mix makes one stream: mhc_pre_apply_mix returns [T, H] in BF16 ({{cite deepinfer/model_executor/models/v4_modules/mhc_ops.py:40-45}}).
  3. Lines 232 and 237-238 (not shifted): the trunk is flattened and then unflattened again, and the {{term hc-head}} mixes it into [T, H].
  4. Line 239: the final RMSNorm.

The HF loader sets hc_shifted to True when config.json has no value ({{cite deepinfer/hugging_face/config.py:295}}). A shifted checkpoint has no head parameters, and HCHead asserts that it is not built for one ({{cite deepinfer/model_executor/models/v4_modules/hc.py:372-373}}). The DFlash draft model ends in the same way ({{cite deepinfer/model_executor/models/mtp/dflash.py:258-264}}).

Memory. The trunk needs m × H × 2 bytes per token: 32 KiB in the example, four times a plain BF16 residual. The code uses the same count for the context-parallel buffer in YOCO compact mode ({{cite deepinfer/model_executor/models/deepseek.py:418-420}}).

The pre, post and residual-mix values below are toy values. The exact formulas that make them (sigmoid, scale, eps, Sinkhorn) run inside tile_kernels and DeepGEMM kernels, which are not in the repo. The form R_new = comb @ R + post × y is a model that fits the kernel names, the arguments and the FLOP count ({{cite csrc/engine/flops_estimator.hpp:107-111}}).

Take m = 2 streams and H = 3, and one token.

The model computes 2m + m² = 8 numbers from the trunk. Say they give the mixes in the block below. Each row and each column of comb sums to 1. Sinkhorn normalization makes this approximately true. Then the steps are:

R0, R1 = [1, 2, 3], [3, 0, -1]                  # the trunk of one token
pre  = [0.75, 0.25]
post = [1.2, 0.8]
comb = [[0.9, 0.1], [0.1, 0.9]]

# 1. pre apply
x_in = 0.75*R0 + 0.25*R1 = [1.5, 1.5, 2.0]
# 2. norm (weight 1): rms = sqrt((2.25 + 2.25 + 4) / 3) = 1.683
norm(x_in) = [0.891, 0.891, 1.188]
# 3. sub-layer (toy output)
y = [0.2, -0.4, 0.6]
# 4. post
R0' = 0.9*R0 + 0.1*R1 + 1.2*y = [1.2, 1.8, 2.6] + [0.24, -0.48, 0.72] = [1.44, 1.32, 3.32]
R1' = 0.1*R0 + 0.9*R1 + 0.8*y = [2.8, 0.2, -0.6] + [0.16, -0.32, 0.48] = [2.96, -0.12, -0.12]

What the column sums do. Before the step, R0 + R1 = [4, 2, 2]. The comb part alone gives [1.2, 1.8, 2.6] + [2.8, 0.2, −0.6] = [4, 2, 2]. So the residual mix moves content between streams, but it does not make the sum larger or smaller. Only the sub-layer output adds new content.

The plain residual is a special case. With m = 1, pre = 1, post = 1 and comb = [[1]], the step is R' = R + F(norm(R)). That is the normal transformer layer.

The DFlash feature of this token. A DFlash target layer stores the mean of the streams ({{cite deepinfer/model_executor/layers/tilelang_ops/dflash.py:134-139}}). Here that is ([1, 2, 3] + [3, 0, −1]) / 2 = [2, 1, 1]. See {{link tours/decoder-layer}}, stop 5.

With hc_shifted, "the pre mix is offset by half a layer" ({{cite deepinfer/model_executor/models/v4_modules/hc.py:64-67}}). Number the sub-layers 0, 1, 2, … (two per decoder layer). Then:

  1. Sub-layer 0 (attention of layer 0) applies a one-hot pre mix: it reads only stream 0 ({{cite deepinfer/model_executor/models/v4_modules/hc.py:207-208}}). Because all streams start equal, this is the embedding output.
  2. Sub-layer s computes its mixes from its own trunk R_s: pre p_s, post and residual mix ({{cite deepinfer/model_executor/models/v4_modules/hc.py:344-358}}).
  3. Sub-layer s uses its post and residual mix for its own post, but it applies p_(s−1) to make its input (line 343).
  4. p_s goes to sub-layer s + 1 in HCLazyPostData.pre_layer_mix ({{cite deepinfer/model_executor/models/v4_modules/hc.py:223}}).
  5. After the last sub-layer, the model applies the last pre mix to the final trunk ({{cite deepinfer/model_executor/models/deepseek.py:229-230}}). No HCHead exists ({{cite deepinfer/model_executor/models/deepseek.py:107}}).

The Chinese docstring in ModelMetadata says the same. Translated: "hc pre mix half-layer offset: each sub-layer applies the mix that the previous sub-layer computed, and there is no hc head (see hc.py)" ({{cite deepinfer/model_executor/model_metadata_utils.py:47-48}}). The code does not say why the training used this offset.

The engine's FLOP counter shows the effect on cost. With shifted mHC, it subtracts one mix term from the total. The end of the model then counts only the final mix, not the head projection ({{cite csrc/engine/flops_estimator.hpp:113-120}}). The code still runs mhc_pre_apply_mix with the one-hot mix at the first pre (line 343).

Limit. Shifted mHC does not support a full trunk as layer input (the old NextN path). The assert says "hc_shifted does not support nextn, please use DFlash" ({{cite deepinfer/model_executor/models/v4_modules/hc.py:211}}).

mhc_ops.py and mhc_modeling.py have no parameters ({{cite deepinfer/model_executor/models/v4_modules/__init__.py:16-17}}). They allocate output tensors and call kernels from tile_kernels (installed with pip) and DeepGEMM. This site does not describe the inside of these kernels.

The fields hc_pre_init_value, hc_res_init_value, hc_post_init_value and hc_dynamic_scale only set the start values of the containers (Step 1). The checkpoint replaces them. No environment variable changes mHC.

The code explains what mHC does, not why. The module docstring says only: "mix the hc_mult-way residual trunk around every sub-layer, then fold it back" ({{cite deepinfer/model_executor/models/v4_modules/hc.py:1}}). These facts in the code are about cost and speed:

  • The sub-layers stay the same size. Attention and the MoE see one [T, H] input and give one [T, H] output. Only the trunk is m times wider.
  • The extra work is small. Per sub-layer and token, the counter adds one m·H × (2m + m²) GEMM and the mixes ({{cite csrc/engine/flops_estimator.hpp:107-112}}). For m = 4 that is a 16384 × 24 product, much smaller than the projections of attention.
  • The post and the next pre are joined. They run back to back in one function ({{cite deepinfer/model_executor/models/v4_modules/hc.py:62-64}}), and on a GPU in one kernel call (mega_mhc, {{cite deepinfer/model_executor/models/v4_modules/hc.py:236-238}}). The code does not say how much memory traffic this saves.

Outside background (not in the repo). The hyper-connection papers give two reasons for several streams. The network can learn how strongly each layer connects to earlier layers. A wider residual stream also holds more information. The mHC design adds the doubly stochastic constraint, so that the residual mix does not make the signal grow or shrink over many layers. The worked example above shows this property of the column sums.

What can go wrong

  • Unfolded HC norms in the checkpoint. A checkpoint with separate hc_*_norm.weight tensors raises ValueError: "HF requires folded HC weights" ({{cite deepinfer/hugging_face/loading.py:39-41}}).
  • HC weights not in FP32. A cast would change the folded values, so the loader raises ValueError ({{cite deepinfer/hugging_face/loading.py:112-116}}).
  • Attention and MoE weights of different width. HCLayerMixin asserts "attn/ffn must use the same fn hidden" ({{cite deepinfer/model_executor/models/v4_modules/hc.py:96}}).
  • Shifted mHC with the NextN path. Assert "hc_shifted does not support nextn, please use DFlash" ({{cite deepinfer/model_executor/models/v4_modules/hc.py:211}}).
  • Wrong dtypes in the fused path. mhc_pre_big_fuse asserts a BF16 trunk and FP32 fn, scale and base ({{cite deepinfer/model_executor/models/v4_modules/mhc_modeling.py:90-93}}).
  • No fused path. On Ascend, or with hc_mult other than 4, or with H not a multiple of 1024, mega_mhc is off ({{cite deepinfer/model_executor/models/v4_modules/hc.py:99-101}}). Then each boundary uses separate kernel calls: hc_post, then the kernels of _hc_pre.

Why it matters. The trunk is four times wider than the hidden state in the example, and two mHC boundaries run in every layer. A checkpoint problem shows up at load time, but a slow path shows up only in the speed. The DFlash draft head also reads the trunk (stop 5 of {{link tours/decoder-layer}}).

What is the shape of the mHC trunk, and what shape does attention see?

The trunk is [T, hc_mult, H] in BF16 ({{cite deepinfer/model_executor/models/v4_modules/hc.py:58}}, {{cite deepinfer/model_executor/models/v4_modules/hc.py:252}}). Attention sees one [T, H] input: the pre mix makes it from the streams, and the RMSNorm normalizes it ({{cite deepinfer/model_executor/models/v4_modules/hc.py:359-363}}).

 Where does the post mix of the MoE sub-layer of layer 5 run?

At the start of layer 6, in attn_norm_forward, together with the attention pre mix of layer 6. One mega_mhc call does both when the fused path is on; else hc_post runs first ({{cite deepinfer/model_executor/models/v4_modules/hc.py:195-202}}, {{cite deepinfer/model_executor/models/v4_modules/hc.py:220-227}}). After the last layer, it runs in DeepseekModel.forward ({{cite deepinfer/model_executor/models/deepseek.py:226-227}}).

 With hc_mult = 4, how many mix values does one sub-layer compute per token, and how do they split?

2m + m² = 24: 4 pre values, 4 post values and a 4 × 4 residual mix ({{cite deepinfer/model_executor/models/v4_modules/mhc_ops.py:68-76}}, {{cite deepinfer/model_executor/models/v4_modules/hc_blocks.py:23}}).

 A config.json has no hc_shifted key. Does the model build an HCHead?

No. The loader sets hc_shifted=True ({{cite deepinfer/hugging_face/config.py:295}}), and DeepseekModel builds HCHead only when hc_shifted is off ({{cite deepinfer/model_executor/models/deepseek.py:107}}). The end of the model applies the last pre mix instead ({{cite deepinfer/model_executor/models/deepseek.py:229-230}}).

 In the toy example, the residual mix is [[0.9, 0.1], [0.1, 0.9]]. Show that the comb part keeps the sum of the streams. What property of the matrix gives this, and which operator makes it?

0.9·R0 + 0.1·R1 + 0.1·R0 + 0.9·R1 = R0 + R1, because each column sums to 1. sinkhorn_normalize applies Sinkhorn normalization to the residual mix. In general, this method scales rows and columns so that they sum to about 1; the kernel itself is not in the repo ({{cite deepinfer/model_executor/models/v4_modules/hc.py:358}}, {{cite deepinfer/model_executor/models/v4_modules/mhc_ops.py:95-99}}). See the deep dive "A worked example with numbers".
