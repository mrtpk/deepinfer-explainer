All shared code reads its hardware choices from that object.

The idea

DeepInfer supports two kinds of {{term accelerator | accelerators}}: NVIDIA SM100 {{term gpu | GPUs}} and Huawei Ascend 950 {{term npu | NPUs}} ({{cite README.md:33-36}}). The two chips need different software:

  • NVIDIA uses {{term cuda}}. Ascend uses {{term cann}} and the PyTorch plug-in {{term torch-npu}}.
  • NVIDIA GPUs talk to each other with {{term nccl}}. Ascend NPUs use {{term hccl}}.
  • Each chip needs its own {{term kernel | kernels}}: the small programs that do the math on the device.

Most of DeepInfer is the same for both chips: the scheduler, the model code, the sampler and the engine loop. Only a small number of places are different. DeepInfer collects those places in one object, the Platform object, in deepinfer/platform.py.

An everyday comparison. Think of a travel plug adapter. Your laptop is the same in every country. Only the adapter changes. You choose the adapter once, when you arrive, and not each time you use the laptop. In DeepInfer, the shared code is the laptop. The Platform object is the adapter. DeepInfer chooses it once per process, at start-up.

The work has three steps:

  1. Detect. The deep_cluster package looks for device files such as /dev/davinci0 or /dev/nvidia0. It does not import PyTorch.
  2. Choose. get_platform() makes a PlatformNPU on Ascend and a PlatformGPU in all other cases.
  3. Use. Shared code reads names such as PLATFORM.distributed_backend. A kernel dispatcher loads the kernel folder for the chosen hardware.

One process uses one platform. One deployment uses one hardware type. The last part of this page explains why DeepInfer is therefore not an {{term afd | AFD}} system.

DeepInfer keeps a large shared-memory buffer for data that goes from the CPU to the device. The buffer is pinned so that copies can use DMA:

The real large shared-memory block. SharedMemory makes it shared across processes. Then it is pinned as host pinned memory to speed up H2D copies (GPU: cudaHostRegister; NPU: aclrtHostRegisterV2, see platform.py). "Allocated: is_shared=…, is_pinned=…"

NVIDIA. cudaHostRegister(ptr, nbytes, 0) through torch.cuda.cudart() ({{cite deepinfer/platform.py:65-73}}).

Ascend. torch_npu has no such call, so DeepInfer loads libascendcl.so with ctypes:

  • The flag _ACL_HOST_REG_PINNED = 0x10000000 asks for pinned memory (line 158).
  • Error 507910 (already registered) on pin and 507911 (not registered) on unpin are ignored. All other errors give a warning, not an exception (lines 202-207 here; {{cite deepinfer/platform.py:215-219}} for unpin). The copy then uses the slow pageable path.
  • The ACL device context is per thread. Without it, a bare register call fails with error 107002. So each call first runs torch.npu.set_device(torch.npu.current_device()) (lines 186-193).
  • If the driver is too old and the functions are missing, start-up stops with RuntimeError (lines 169-178).

The base class has empty pin_host_memory and unpin_host_memory methods. A future platform that cannot pin memory still works, with slower copies ({{cite deepinfer/platform.py:37-49}}).

NCCL options. PlatformGPU.get_distributed_options() sets config.max_ctas and config.min_ctas to DEEPINFER_NCCL_NUM_SMS ({{cite deepinfer/platform.py:75-83}}). The default is 32 ({{cite deepinfer/environ.py:108}}). A CTA is one thread block, and one CTA runs on one {{term sm | SM}}. So this value sets how many SMs an NCCL operation uses. "Vector core" and "on-chip buffer" are short names for Ascend hardware parts. The page {{link concepts/tilelang-kernels}} explains TileLang on both platforms.

DeepInfer stores many weights and activations in {{term fp8 | FP8}}. Each block of FP8 values has a {{term scale-factor}}. One common scale format is UE8M0: an 8-bit exponent with no sign and no mantissa, so one scale uses one byte. DeepInfer packs several one-byte scales into one integer. The integer type is PLATFORM.fp8_sf_type:

So on NVIDIA one int32 holds 4 scales. On Ascend one int16 holds 2 scales. The pack factor is simply fp8_sf_type.itemsize:

Allocate the scale factors (sf) for an FP8 cast. Returns (external view, kernel argument). The layout matches tile_kernels.quant. row-major: float32 (B, M, d_scale), contiguous. row-major packed ue8m0 (the mega-MoE x_sf layout): fp8_sf_type (B, M, d_scale/pack_factor), contiguous. Each element packs pack_factor consecutive ue8m0 values along k. The kernel writes them byte by byte through a uint8 (B, M, d_scale) view. col-major (TMA aligned): float32 (B, M, d_scale), column-major view. Each column is padded to align(M, 4). col-major packed ue8m0: fp8_sf_type (B, M, ceil(d_scale/pack_factor)), column-major view. The kernel writes byte by byte through a uint8 (B, M, packs, pack_factor) view.

A worked example: a row has d_scale = 8 scales. On NVIDIA, the packed row-major tensor has shape (B, M, 2) in int32. On Ascend, it has shape (B, M, 4) in int16. Both use 8 bytes per row. Line 51 shows one more difference. On NVIDIA, the column-major layout pads M up to a multiple of 4. On Ascend, it does not pad.

Other code checks the type directly. The FP8 linear layer converts loaded weight scales if their type is not fp8_sf_type ({{cite deepinfer/model_executor/layers/linear.py:67-70}}). It asserts the type before each FP8 GEMM ({{cite deepinfer/model_executor/layers/linear.py:164}}). The KV cache sizes its scale tensor with the same type ({{cite deepinfer/model_executor/layers/tilelang_ops/cache_common.py:244-248}}). The page {{link concepts/low-precision-formats}} explains the formats.

patch_imports() replaces the built-in builtins.__import__ with its own function. It changes only statements of the form from X import a, b.

Only handle from name import a, b (not *). fromlist can be None. Get the original target module. Imports inside it are still patched. When the source module itself imports the matching target, give it the original object.

Step by step, for from deep_select.interface import topk on Ascend:

  1. Python calls _hooked_import("deep_select.interface", ..., fromlist=("topk",), level=0).
  2. _patch_map has {"deep_select.interface": {"topk": "deepinfer.npu_ops.deep_select.topk"}}, so the name is patched.
  3. The hook returns a new, empty module object. Its topk is a Lazy wrapper ({{cite deepinfer/npu_ops/patch_imports.py:33-52}}). The real NPU function loads only on the first call.
  4. Exception: deepinfer/npu_ops/deep_select.py itself imports topk from deep_select.interface. Because the caller is the source module, it gets the original vendor function (lines 86-89). Without this rule, the NPU version would call itself.
  5. Other names of the module go to the real module through the fake module's __getattr__ (line 92).

The hook does not change sys.modules, and patch_imports() can run only once ({{cite deepinfer/npu_ops/patch_imports.py:114-116}}). Its docstring is in Chinese. Translated: "Replace from dst.mod import name with a lazy src.mod.name. Only from-imports are intercepted; sys.modules is not faked. src loads only when the patched object is first used." ({{cite deepinfer/npu_ops/patch_imports.py:97-111}}).

Is DeepInfer AFD (Attention-FFN Disaggregation)?

No. {{term afd | AFD}} runs the attention layers on one group of devices and the FFN or expert layers on another group. In every layer, hidden states go from the attention group to the FFN group and back. DeepInfer does not do this. There are four reasons in the code and docs.

  1. One hardware type per deployment. Each process makes its platform from its own device files. Every device process group then uses PLATFORM.distributed_backend, which is "nccl" or "hccl" ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:82-117}}). NCCL and HCCL are different libraries, and the code has no path that connects an NCCL group to an HCCL group. So all ranks of one job use the same hardware type.
  2. Attention and MoE run in the same layer, on the same device. DeepseekDecoderLayer.forward calls attention and then the MoE block, one after the other:
  3. MoE uses expert parallelism, not a separate pool. With {{term expert-parallelism}}, each device holds a part of the experts. {{term deepep | DeepEP}} dispatch sends each token to the devices of its experts, and combine sends the results back ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:461-511}}). Every one of these devices also runs attention, with {{term data-parallelism}}: "attention uses data parallelism (#DP = #EP)" ({{cite doc/inference_deployment_qa.md:33}}).
  4. The only split in the docs is E/P/D, and it is not in this release. The docs describe separate vision-encoder, prefill and decode instances ({{cite doc/inference_deployment_qa.md:31}}, {{cite doc/inference_deployment_qa.md:41-63}}). Each prefill or decode instance runs the whole language model, attention and MoE. A VE instance runs only the vision encoder, on one GPU ({{cite doc/inference_deployment_qa.md:51}}). The README lists "VE/Prefill/Decode disaggregation" under "not included in this release" ({{cite README.md:38-41}}). See {{term epd}}.

Point 1 is about one job. The docs say DeepInfer "runs on both NVIDIA and Huawei Ascend platforms" ({{cite doc/inference_deployment_qa.md:19}}). That means two separate deployments, one per hardware type, not one mixed job.

What can go wrong

If CUDA_VISIBLE_DEVICES is set and is not equal to ASCEND_RT_VISIBLE_DEVICES, start-up stops with RuntimeError ({{cite deepinfer/platform.py:101-102}}). This also happens when only CUDA_VISIBLE_DEVICES is set. Set both to the same value, or set only ASCEND_RT_VISIBLE_DEVICES.
  • Wrong .so folder. If DEEPINFER_ACCELERATOR is not exported on Ascend, the package looks in _so/nvidia-<arch>/. The import of deepinfer._C can then fail or find the wrong build. See the deep dive on the _so folder.
  • Platform made too early. On Ascend, the first access to PLATFORM starts the device runtime. It must happen after ASCEND_RT_VISIBLE_DEVICES is set ({{cite deepinfer/__init__.py:58-59}}). Do not touch deepinfer.PLATFORM in code that runs before the worker sets its devices.
  • torch in deepinfer/__init__.py. The package rule forbids it, because it breaks child processes ({{cite deepinfer/__init__.py:1}}).
  • Missing kernel on one platform. A call to a factory that the backend does not have raises KernelUnavailableError ({{cite deepinfer/model_executor/layers/tilelang_ops/ops.py:31-32}}).
  • Old Ascend driver. If libascendcl.so has no aclrtHostRegisterV2, start-up stops with RuntimeError ({{cite deepinfer/platform.py:169-178}}).
  • Slow copies, no error. A failed pin only gives a warning. Copies from shared memory then use the slow pageable path ({{cite deepinfer/platform.py:202-207}}). Look for "aclrtHostRegisterV2 ... failed" in the logs.
  • No accelerator. On a machine with no device files, DeepInfer still makes a PlatformGPU. The error comes later, at the first CUDA call.

Why it matters. The Platform object keeps vendor checks out of most of the code. To read the model or the scheduler, you can ignore the hardware. A third hardware type needs a Platform subclass, a kernel folder next to cuda/ and asc/, and a build branch in setup.py.

Which function decides between NVIDIA and Ascend? Does it import PyTorch?

accelerator_kind() in deep_cluster/hardware/device.py. It does not import PyTorch. It only checks device files, such as /dev/davinci_manager and /proc/driver/nvidia/gpus.

 What is the value of PLATFORM.distributed_backend in an Ascend process?

"hccl" ({{cite deepinfer/platform.py:89}}). On NVIDIA it is "nccl".

 An interface file calls ops.expand_swa_index_tl(width). On Ascend, which file has the kernel code? Which file makes that choice?

The code is in tilelang_ops/asc/swa_index.py. The choice is in tilelang_ops/ops.py, line 15: it imports the subpackage named by PLATFORM.tilelang_ops_backend, which is "asc". (tilelang_ops/__init__.py is empty.)

 On an Ascend host, CUDA_VISIBLE_DEVICES=0,1 is set and ASCEND_RT_VISIBLE_DEVICES is not set. What happens when the process makes the platform?

RuntimeError. The first branch needs CUDA_VISIBLE_DEVICES to be unset. The second branch compares "0,1" with None, and they are not equal ({{cite deepinfer/platform.py:94-102}}).

 Can one DeepInfer job use 8 NVIDIA GPUs for attention and 8 Ascend NPUs for the MoE experts? Give two reasons from the code.

No. (1) All device process groups use one backend from PLATFORM.distributed_backend, NCCL or HCCL, and the code cannot connect the two. (2) DeepseekDecoderLayer.forward runs attention and the MoE block one after the other on the same device. Expert parallelism moves tokens between devices that all run attention too. It does not put the experts on a separate pool. (Also: E/P/D disaggregation is not in this release.)
