It also defines SchedulerOutputs and three free functions. ---

Purpose

scheduler.hpp decides, for every engine step, which sequences run and with how many tokens, and then records the tokens that the step produced.

Where it sits

The scheduler is a passive object. It has no thread and no loop of its own. LLMEngine makes it once and calls its methods from step() and from the post-process callback. The page {{link concepts/scheduler}} explains the policy with diagrams; this page walks through the code.

Who calls it

  • Construction. LLMEngine._create_scheduler passes 14 arguments ({{cite deepinfer/engine/llm_engine.py:307-327}}). Then the engine sets decode_perf_curve and gives the scheduler to the image processor ({{cite deepinfer/engine/llm_engine.py:267-270}}).
  • Admission. _enqueue calls add_sequence ({{cite deepinfer/engine/llm_engine.py:623}}). abort_request calls abort_sequence ({{cite deepinfer/engine/llm_engine.py:651}}).
  • Every step. step() calls schedule(pool) ({{cite deepinfer/engine/llm_engine.py:885-887}}). The Worker runs clone_and_zero_states_and_blocks when the scheduler asks for copies ({{cite deepinfer/worker/base.py:160-168}}).
  • After a step. _process_model_outputs calls process_MTPInfo, process_outputs and get_finished_seqs_info ({{cite deepinfer/engine/llm_engine.py:717-738}}). post_process calls update_mtp_runtime ({{cite deepinfer/engine/llm_engine.py:995-1002}}). finalize_seq calls free_seq ({{cite deepinfer/engine/llm_engine.py:804-806}}).
  • Loop tests. has_unfinished_seqs and get_num_unfinished_seqs ({{cite deepinfer/engine/llm_engine.py:660}}, {{cite deepinfer/engine/llm_engine.py:673}}).
  • Images. MultimodalProcessor.fetch calls set_schedulable(id) ({{cite deepinfer/ve/multimodal_processor.py:303}}).
  • Statistics. StatsLogger reads the free blocks, the queue sizes and the preempted and aborted counts ({{cite deepinfer/engine/stats_logger.py:411-423}}).
  • Benchmark. examples/benchmark.py calls try_allocate_seq, fork_seq, and sets decode_step = 0 to force an attempt point ({{cite examples/benchmark.py:314-317}}, {{cite examples/benchmark.py:337-350}}).

What it calls

  • Blocks and state slots. BlockManager and BlockManagerMutexAcquire ({{cite csrc/engine/block_manager.hpp:119-243}}). The scheduler holds two managers: one for KV blocks and one (optional) for state slots.
  • Sequences. The fields of Sequence and the constructor of SequenceMetadata ({{cite csrc/engine/sequence.hpp:275-321}}, {{cite csrc/engine/sequence.hpp:374-389}}).
  • Draft lengths. MTPVarlen::schedule sets seqlen_q in decode ({{cite csrc/engine/mtp_varlen.hpp:150-267}}).
  • Statistics. FlopsEstimator::calc_flops, only with log_stats ({{cite csrc/engine/scheduler.hpp:712-719}}).
  • Votes. dp_group->allreduce in _dp_allreduce ({{cite csrc/engine/scheduler.hpp:170-182}}).
  • Device copies. deepinfer::cuda::utils::cuda_copy_async in clone_and_zero_states_and_blocks ({{cite csrc/engine/scheduler.hpp:1283}}, {{cite csrc/engine/scheduler.hpp:1297}}).

Walk through the main methods

The constructor

A COMPLETION engine has no prefill path, so it cannot recompute preempted requests. Block this configuration at start-up.
  1. Lines 94-100: copy seven values from the Python SchedulerConfig.
  2. Lines 101-104: a COMPLETION engine must stop preempted requests.
  3. Lines 105-108: both attempt intervals must be 1 or more.
  4. Line 109: a Gloo group means "do the votes on the CPU".
  5. Line 112: prompt_limit: max_model_len with chunked prefill, else min(max_model_len, max_num_batched_tokens).
  6. Line 116: the budget must hold at least one block.
  7. Line 118: nextn comes from the environment variable DEEPINFER_USE_NEXTN_DECODE, read with getenv (default 5, {{cite csrc/engine/utils.hpp:36-40}}).
  8. Lines 120-121: the prefill sum limit must be at least prompt_limit.
  9. Lines 126-128: MTP slots max_num_seqs … 1 go into a stack, so slot 1 comes out first. Slot 0 is padding.
  10. Lines 130-132: reserve the clone vectors for the worst case.

add_sequence and abort_sequence

A seq whose multimodal processing failed stays in waiting with schedule.schedulable = false, so scan both queues.
  1. Line 136: the arrival time is set here, in milliseconds since the epoch ({{cite csrc/engine/block_manager.hpp:20-25}}). This value goes into the time-to-first-token statistic (line 1009).
  2. Lines 138-139: reserve token ids for max_tokens outputs and block-table entries for ceil((len + max_tokens) / block_size) + 1 blocks.
  3. Lines 147-157: only an unfinished sequence with the same id is marked. The function returns the list of the aborted sequences.
  4. Lines 158-161: prompted is not scanned. That queue only holds forked sequences.

_schedule: the step type

The concept page shows the voting code line by line ({{link concepts/scheduler}}, step 2). The structure is:

  1. Line 276: release the Python GIL. Other Python threads, such as the grammar builders, can run during scheduling.
  2. Line 277: lock the block manager and the state manager. Lockable::lock_ refuses to run while the GIL is held, and gives up after 20 seconds ({{cite csrc/utils/lockable.hpp:16-28}}).
  3. Lines 282-284: clear the clone vectors of the previous step. The previous SchedulerOutputs borrowed them.
  4. Lines 288-294: PROMPT and COMPLETION engines skip the vote.

_schedule_prefill: the loop, part 1

The doc comment says, translated: "Prefill (prompt) scheduling: pick runnable prompts from the waiting queue. For a NORMAL engine, return nullptr if this round scheduled no prompt (scheduled and ignored both empty); _schedule then decides whether to switch to decode. Other engine types always return SchedulerOutputs." ({{cite csrc/engine/scheduler.hpp:347-349}}).

A seq that was already dead before it entered the queue does not run a prefill. It goes into ignored_seqs and returns with its finish_reason.
  1. Line 355: num_curr_seqs starts at the size of running, so finished but not yet removed sequences also count.
  2. Line 372: the work of this sequence is its full length minus the cached tokens. For a recompute, that includes its earlier outputs.
  3. Line 374: an empty block table means "first chunk". The local name prefix_caching_hit is set to true here. It only switches off the lookahead check at line 454.
  4. Lines 386-396: get_num_blocks() of a new sequence is ceil(len / block_size), because it has no drafts and no in-flight tokens yet.

_schedule_prefill: forked prompts

Release the parent's blocks and state that the fork pinned. There is a tail: it needs a copy.
  1. Line 398: a forked sequence has a branch_id that starts with _ and a block table that it shares with its parent.
  2. Lines 413-415: it keeps the full blocks of the shared prefix, and needs new blocks for the rest.
  3. Lines 425-430: it gets its own state slot (a copy) and a copy of the half-full last block.
  4. Lines 431-437: the other parent blocks are only unpinned (pair (block, 0)), then the table gets the new blocks.

The pairs go to clone_states and clone_blocks. LLMEngine.step() sends them to the Worker in the same step ({{cite deepinfer/engine/llm_engine.py:889-905}}).

_schedule_prefill: the loop, part 2

  1. Lines 440-442: the slot limit.
  2. Lines 444-449: the sum limit counts the full length of each sequence, not the chunk.
  3. Lines 451-458: a sequence that is neither new nor forked (a later chunk) must have num_tokens == 0 or at least lookahead_tokens cached tokens. The comment says that the block size is assumed to be larger than nextn.
  4. Line 464: the work must be at least lookahead_tokens.
  5. Lines 470-475: the chunk cut (see the concept page).

Lines 477-511 adjust the chunk for checkpoints and images, and lines 513-546 commit the side effects. The concept page explains both parts. _make_outputs (lines 263-268) wraps the result and adds references to the clone vectors.

_adjust_chunk_size

The doc comment of the first helper says, translated: "Check whether position k_len is inside an image of the form MM_TOKEN_IMAGE + MM_TOKEN_IMAGE_PAD*N. True only if token_ids[k_len] == IMAGE_PAD and an MM_TOKEN_IMAGE comes before it. If token_ids[k_len] == MM_TOKEN_IMAGE, the cut is exactly at the start of an image: allowed, return false." ({{cite csrc/engine/scheduler.hpp:214-216}}).

Extend forward: skip all IMAGE_PAD (stop at the next MM_TOKEN_IMAGE or at a non-image token). Shrink backward: skip all IMAGE_PAD and the MM_TOKEN_IMAGE (the whole image unit moves to the next chunk).
  1. Line 218: a cut position that is not a pad token is never inside an image.
  2. Lines 221-228: walk back over pad tokens. Reaching the image token means "inside". Any other token means "not inside".
  3. Lines 237-239: a cut at or after the end of the sequence needs no change.
  4. Lines 244-246: grow until the first non-pad token.
  5. Lines 249-254: shrink over the pads and the image token, but not below the cached length.

_schedule_decode: clean-up and forked admission

The doc comment says, translated: "Decode (completion) scheduling: first move the seqs from the prompted queue into running, then pick the seqs of this round in LCFS order; when blocks are not enough, preempt the seq with the shortest output." ({{cite csrc/engine/scheduler.hpp:556-557}}). The last part is wrong (see the warning below).

Finished seqs in waiting (aborted, or failed in the image step) can only be removed by the scheduler. Only _schedule_prefill removed them before. Now prefill runs only when want is true on this rank, so such seqs could stay forever, keep has_unfinished true and block every ALL vote. So clean them up here, and scan the whole queue, because an abort can hit the middle of it. Move the seqs at the head of the prompted queue into running (finished ones into finished). A forked seq must first clone its state and its last (maybe half-written) block. Aborted before it entered the completion engine.
  1. Line 562: finished sequences leave running. Their MTP slots go back now, if process_outputs did not give them back already (line 993). Their blocks go back later, in finalize_seq.
  2. Lines 569-577: finished sequences anywhere in waiting go to ignored_seqs.
  3. Lines 595-620: forked sequences in prompted join running, as long as there is room and a free block and state slot. The comment above line 556 is wrong about the preemption order (see below).

_schedule_decode: the decode loop

decode: running still has queued seqs; N are scheduled and M are left; this must not happen.
  1. Lines 624-625: std::sort with "more output first". std::sort is not stable, so the order of equal lengths is not fixed.
  2. Line 629: take running[r - 1], the fewest outputs among the sequences left.
  3. Lines 630-634: while the free list is empty and two or more sequences are left, preempt running[l], the most outputs.
  4. Lines 635-640: with a free block, call _append_slot; without one (only the current sequence is left), preempt it.
  5. Line 645: every sequence is either scheduled or preempted. A sequence that does not fit because of max_seqs would fail this check.
  6. Line 646: running is cleared. schedule() sets it to the batch (line 679).
  7. Lines 648-652: sort the batch by length, then MTPVarlen gives seqlens_q.

The comment says that the scheduler preempts the sequence with the shortest output (lines 556-557). The code preempts from the front of a list sorted with the longest output first. This site describes the code.

schedule: the public entry

Open upper bound of the positions in this step. Prefill ends at seqlen_k. In decode, seqlen_q on the GPU is padded to at most max_seqlen_q (same as max_k in zos.cpp), and the DFlash draft goes nextn further. Buffers indexed by position, such as the RoPE cache, have only runtime_max_model_len rows.
  1. Line 689: max_seqlen_q = nextn + 1.
  2. Line 694: count one more schedule for the MTP bookkeeping.
  3. Line 695: the "golden" tokens: an optional list of reference tokens from SamplingParams.golden_token_ids ({{cite deepinfer/engine/llm_engine.py:562}}, {{cite csrc/engine/sequence.hpp:155-165}}). The YOCO equivalence example sets them ({{cite examples/yoco/yoco_equiv.py:682}}).
  4. Line 697: seqlen_k = cached + in flight + seqlen_q.
  5. Lines 700-705: the highest position must stay below runtime_max_model_len, or the call fails.
  6. Lines 706-707: one SequenceMetadata from the pool. It holds references into the Sequence, not copies.
  7. Line 726: reserve nextn + 1 in-flight tokens on the sequence.

_preempt, _append_slot and the free functions

free_seq_nolock gives back the MTP slot, the state slot and all blocks. BlockManager::free_blocks_nolock frees the table in reverse order, and a block whose reference count reaches 0 goes to the tail of the free list ({{cite csrc/engine/block_manager.hpp:95-103}}, {{cite csrc/engine/block_manager.hpp:147-149}}). free_finished_seqs gives back only the MTP slot. _preempt calls free_seq_nolock in both of its paths ({{cite csrc/engine/scheduler.hpp:779}}, {{cite csrc/engine/scheduler.hpp:787}}).

Line 820 adds at most one block per call; the check at line 826 fails if one block is not enough. Lines 821-825 free extra blocks when the reserve shrinks.

process_outputs: after the step

[total_q] flat: each request has seqlens_q[i] positions. The first seqlens_q[i]-1 are draft tokens (-1 = not accepted); the last one is the main token position (not used). With MTP = 0, or in prefill, an empty 1-D tensor (numel() == 0). Tokens that have not been forwarded yet, but are already accepted. The returned numpy arrays borrow this storage (empty capsule). The caller must use them before the next process_outputs. Counts the tokens pushed before the finish.

For each scheduled sequence, in order:

  1. finish_inflight_step() (line 903).
  2. Finished already (an abort while in flight): skip, give back the MTP slot; in a prompt step, put it into running so that the next decode removes it (lines 906-915).
  3. Preempted while in flight (decode step, status WAITING): skip all bookkeeping (lines 920-925).
  4. advance_optimistically(seqlen_q) and the structured-output status (lines 927-929).
  5. Prompt complete or decode: read the accepted drafts, append them and the sampled token with _check_stop after each one, then commit_processed_tokens in decode (lines 940-1000).
  6. Prompt not complete: back to the front of waiting (lines 1011-1020).

It returns two arrays: the time to the first token for sequences with exactly 1 output, and the number of tokens pushed per sequence (lines 1030-1032). Both borrow static buffers.

fork_seq

A fork copies the tokens of a sequence that already has a cached prefix, shares its blocks and its state slot (with pin), and puts the new sequence either at the front of waiting (prompt not complete) or into prompted ({{cite csrc/engine/scheduler.hpp:1108-1120}}). No file in the deepinfer package calls it. examples/benchmark.py uses it to copy one cached prompt to a batch ({{cite examples/benchmark.py:331-352}}).

process_MTPInfo

A comment at the top of the loop says, translated: "ZOS async: a seq that _preempt preempted for recompute while this step was in flight already had all its MTP counters reset; drop this step's bookkeeping too (same test as in process_outputs). Else process_cnt would run ahead of schedule_cnt, and the pairing check in MTPVarlen::schedule would fail." ({{cite csrc/engine/scheduler.hpp:1214-1216}}).

Only the chunked prefill case must be excluded here. Note: seqlen_q can now be smaller than 1 + nextn, so the old test does not hold. If seqlen_q < 1 + nextn: decode always has nextn > 0, and prefill always has nextn = 0. A chunked prefill makes no real nextn information. build output reads the confidence values from before this update (moved into prev_confidence_raw above), so process_MTPInfo must be called before build output. The confidence rate from the model is per token and independent; multiply them before use.
  1. Line 1220: process_cnt counts processed steps; schedule() counts scheduled steps (line 694). MTPVarlen uses the difference to know which round an accept rate belongs to ({{cite csrc/engine/mtp_varlen.hpp:195-201}}).
  2. Lines 1235-1238: the new drafts replace the old ones.
  3. Lines 1246-1251: accept_rates[j] is the product of the first j + 1 confidence values. Example: confidences [0.9, 0.8, 0.5] give accept rates [0.9, 0.72, 0.36].
  4. Lines 1253-1256: in a decode step, mark that the new draft info is in the MTP pool and not yet read.

clone_and_zero_states_and_blocks

Line 1267 says, translated: "The returned numpy arrays borrow this storage (empty capsule). The caller must use them before the next call." The storage is the function-level static vectors of line 1268.

Each pair (src, dst) copies one state row or one block row on the current stream; dst = 0 skips the copy. Every src is returned for unpinning. The engine unpins them after a CUDA event, in the pre_sampler_sync of the same step ({{cite deepinfer/engine/llm_engine.py:109-116}}).

A worked example of the flat layout. A decode step has two sequences with seqlens_q = [6, 6], so total_q = 12. The sampler returns accepted_token_ids = [a, b, -1, -1, -1, *, c, -1, -1, -1, -1, *] and output_token_ids = [x, y]. The * slots are the main token positions and are not read.

  1. Sequence 0: drafts a, b accepted, then x. token_cnt = 3. With num_tokens = 100 before the step: advance_optimistically(6) gives 106, commit_processed_tokens(3) gives 103.
  2. Sequence 1: draft c accepted, then y. token_cnt = 2.
  3. flat_offset moves by 6 after each sequence (line 1022). pushed_tokens_before_finish = [3, 2].
  • GIL. _schedule releases the GIL for its whole run (line 276). It must, because Lockable::lock_ fails if the caller holds the GIL. Translated: "Holding the GIL when you call this function is forbidden, to avoid deadlock!" ({{cite csrc/utils/lockable.hpp:16}}). fork_seq and free_seq release it too ({{cite csrc/engine/scheduler.hpp:1109}}, {{cite csrc/engine/pybind_scheduler.cpp:100-102}}).
  • Lock order. BlockManagerMutexAcquire locks the state manager first, then the block manager, and unlocks in the opposite order ({{cite csrc/engine/block_manager.hpp:189-204}}).
  • Lock timeout. A lock that is not free after 20 seconds fails with "failed to lock mutex" ({{cite csrc/utils/lockable.hpp:22-27}}).
  • One caller thread. The queues have no lock of their own. The engine calls the scheduler from its main thread only.
  • Static buffers. process_outputs (lines 880-881, 896-897) and clone_and_zero_states_and_blocks (line 1268) keep function-level static vectors. They are shared by all Scheduler objects in the process, and the results of one call are overwritten by the next.
  • Object pool. SequenceMetadataPool::allocate reuses a released object with placement new, or makes a new one ({{cite csrc/utils/object_pool.hpp:21-32}}). release destroys and keeps only objects that came from the pool ({{cite csrc/utils/object_pool.hpp:34-42}}).

The members are listed at {{cite csrc/engine/scheduler.hpp:1124-1193}}. num_cached_tokens_gpu in SchedulerOutputs is always 0: every _make_outputs call passes 0 (lines 340, 549, 658-659).

With ZOS, schedule() for step N+1 runs before process_outputs for step N. Four parts of this file handle that order:

  1. In-flight tokens. start_inflight_step(nextn + 1) at schedule time and finish_inflight_step() at process time ({{cite csrc/engine/scheduler.hpp:726}}, {{cite csrc/engine/scheduler.hpp:903}}). Example: after step N is scheduled, total_inflight_tokens = 6. After step N+1 is scheduled, it is 12. When step N is processed, total == last is false, so it becomes last = 6 ({{cite csrc/engine/sequence.hpp:249-256}}).
  2. Optimistic counters. process_outputs first adds the whole seqlen_q to num_tokens, then sets it to the old value plus the accepted tokens ({{cite csrc/engine/scheduler.hpp:927}}, {{cite csrc/engine/scheduler.hpp:999}}).
  3. Preempted in flight. Skipped in process_outputs and in process_MTPInfo (lines 920-925, 1217-1219).
  4. Device corrections. The CPU seqlen_q and seqlen_k are estimates. The Worker corrects them on the device, and update_metadata_for_sampling_zos writes the final values back into the metadata and into scheduler_outputs.seqlens_q ({{cite csrc/engine/zos.cpp:279-305}}).

The MTP counters. MTPVarlen::schedule checks that process_cnt <= schedule_cnt <= process_cnt + 1 for every sequence ({{cite csrc/engine/mtp_varlen.hpp:195-196}}). The scheduler increments schedule_cnt in schedule() and process_MTPInfo increments process_cnt, so at most one step can be in flight per sequence.

One sequence, prompt 300 tokens, budget 32768, block size 128, nextn = 5, ZOS on, one DP rank, 100 KV blocks, a state manager.

Usage 1/100 ≤ 0.9. _can_allocate_with_state(3) → OK. seqlen_q = 300, num_batched_tokens = 300. allocate_seq: blocks [1, 2, 3] (head of a fresh free list), state slot 1. Status RUNNING, MTP slot 1. schedule(): decode_step = 0, seqlen_k = 0 + 0 + 300 = 300, schedule_cnt = 1, in-flight 6.
  2. Process. In-flight back to 0. num_tokens = 300 = len → into running. process_MTPInfo: 5 placeholder drafts, process_cnt = 1. One token appended: len = 301. Output length 1, so the time to the first token is recorded.
  3. Decode. decode_step = 0 → ALL point, but waiting is empty → want = false → vote fails → decode. Sort, serve; _append_slot: ceil((301 + 0 + 5) / 128) = 3 blocks, no change. seqlens_q = [6], 6 tokens. decode_step = 1. seqlen_k = 300 + 0 + 6 = 306; position end 306 − 6 + 6 + 5 = 311 must be ≤ runtime_max_model_len.

Which method does LLMEngine.step() call on the scheduler, and what does it return?

schedule(sequence_metadata_pool). It returns a tuple: a list of SequenceMetadata objects from the pool, and a SchedulerOutputs object ({{cite csrc/engine/scheduler.hpp:667}}, {{cite csrc/engine/scheduler.hpp:735}}).

 Why does _schedule release the GIL before it locks the block managers?

Lockable::lock_ fails if the caller holds the GIL, to avoid a deadlock ({{cite csrc/utils/lockable.hpp:16}}). Releasing the GIL also lets other Python threads, such as the grammar builders, run during scheduling ({{cite csrc/engine/scheduler.hpp:276}}).

 In process_outputs, a decode sequence has num_tokens = 100 and seqlen_q = 6, and the sampler accepts 2 drafts. What is num_tokens after the call, and why not 106?

103. advance_optimistically(6) first sets it to 106, then commit_processed_tokens(3) sets it to 100 + 3 ({{cite csrc/engine/scheduler.hpp:927}}, {{cite csrc/engine/scheduler.hpp:999}}). Rejected drafts take no KV cache.

 The confidence head gives [0.9, 0.8, 0.5, 0.5, 0.2] for one sequence. What does process_MTPInfo store in accept_rates, and which earlier values does build_request_outputs see?

The running products: [0.9, 0.72, 0.36, 0.18, 0.036] ({{cite csrc/engine/scheduler.hpp:1246-1251}}). The raw values go to confidence_raw, and the old raw values move to prev_confidence_raw first (line 1241). build_request_outputs reads prev_confidence_raw, so process_MTPInfo must run before it ({{cite csrc/engine/scheduler.hpp:1244-1245}}, {{cite csrc/engine/outputs.hpp:291-293}}).

 Which members of Scheduler are written but never read, and what does that tell you about DEEPINFER_YOCO_PREFILL_KEEP_TOKENS?

truncate_len, dp_size, dp_rank, schedule_counter, last_step_num_batched_tokens, last_step_cached_tokens and tokens_chunked_prefill_remaining (see the deep dive "Member variables"). The engine passes the YOCO keep length as truncate_len ({{cite deepinfer/engine/llm_engine.py:315}}), but the scheduler does not use it in this release. Only the FLOP estimate that the scheduler calls gets the value, through a separate argument ({{cite deepinfer/engine/llm_engine.py:318-322}}).
