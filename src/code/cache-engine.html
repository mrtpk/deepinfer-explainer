Purpose

CacheEngine allocates the two cache buffers of a rank and gives every attention layer a KVCache object with views into them. The page {{link learn/kv-cache}} explains the layout in simple terms; this page reads the code.

Who calls it

  • WorkerBase.init_cache_engine makes the real cache ({{cite deepinfer/worker/base.py:270-272}}). The engine calls it on every rank after the profile ({{cite deepinfer/engine/llm_engine.py:453}}).
  • WorkerBase.profile_num_available_blocks calls the static methods get_cache_block_size and get_state_shape ({{cite deepinfer/worker/base.py:237-242}}).
  • ModelRunner.profile_run makes a temporary CacheEngine with only the blocks of the dummy sequences ({{cite deepinfer/worker/model_runner.py:504-507}}).
  • The model reads one KVCache per layer: kv_caches[i] ({{cite deepinfer/model_executor/models/deepseek.py:212}}), for example kv_cache.ca_cache and kv_cache.swa_cache in the attention module ({{cite deepinfer/model_executor/models/v4_modules/attn.py:519-520}}, {{cite deepinfer/model_executor/models/v4_modules/attn.py:642-644}}).
  • The engine reads gpu_states and gpu_blocks for clones ({{cite deepinfer/worker/base.py:166-168}}) and the unused state copy ({{cite deepinfer/engine/llm_engine.py:797}}).

What it calls

  • cuda_utils.alloc_tensor(size): "Allocate a 1D byte tensor by calling cuMemAlloc directly, bypassing torch's caching allocator" ({{cite csrc/cuda_utils.cpp:77-89}}, {{cite csrc/cuda_utils.cpp:99-102}}).
  • ModelMetadata(cfg) for the alignment and the FP4 flag ({{cite deepinfer/worker/cache_engine.py:320-332}}).
  • iter_runtime_attn_modules, which skips the LM-head entry of the attention list ({{cite deepinfer/model_executor/layer_utils.py:6-16}}).

Walk through the main methods

allocate_gpu_cache: two buffers

The lengths of the layers already include their 32-byte padding; their sum is the row size before finalize().
  1. Line 919: the row size of one block comes from a layout pass without memory.
  2. Lines 937-938: one {{term gpu-blocks}} buffer, uint8 [num_gpu_blocks, bytes_per_block]. The comment on line 936 shows a 6-D shape from vLLM. It does not describe this layout.
  3. Lines 948-951: the state shape is (num_state_slots, bytes_per_slot). Three sizes go into the shared cache_config; the engine reads them to make the two block managers ({{cite deepinfer/engine/llm_engine.py:262-266}}).
  4. Lines 955-958: the {{term gpu-states}} buffer. A model with no state gets an empty tensor.
  5. Lines 960-965: GPUCacheInterface runs the layout again, now with the buffers, and keeps the per-layer views.

alloc_tensor calls cuMemAlloc and rounds the size up to a page ({{cite csrc/cuda_utils.cpp:77-82}}). So the cache does not appear in torch.cuda.memory_allocated(). On Ascend, asc_utils.cpp has its own alloc_tensor ({{cite csrc/asc_utils.cpp:88}}).

KVCacheManager.process: one layer

  1. SWA. A layer with sink_mode == "swa" gets a ring of swa_block_size entries in the state row. A YOCO consumer layer puts its ring into the "dropped" part ({{cite deepinfer/worker/cache_engine.py:113-116}}). The view [slots, ring, 1, bytes_per_token] uses the full slot stride.
  2. Indexer keys. A sparse layer (index_topk > 0) gets block_size // ratio FP4 keys per block. A layer that reuses the keys of an earlier layer takes that view and adds no bytes.
  3. Main cache. A layer with ratio > 0 gets block_size // ratio entries per block. A ratio above 1 (for example 2) also gets fp32 compression state in the state row ({{cite deepinfer/worker/cache_engine.py:119-120}}).
  4. Each block-row part and each SWA ring is padded to 32 bytes; the fp32 compression state is not padded. A full-attention layer (ratio 0 and no SWA) raises AssertionError ({{cite deepinfer/worker/cache_engine.py:466-468}}).

finalize: the row size

The row is padded to lcm(128, bytes_per_token): 1,152 bytes for FP4 entries and 4,224 bytes for MXFP8 entries. The comment gives the reasons: DeepGEMM needs a block stride that is a multiple of 128 bytes, and the main attention needs a multiple of the entry size.

StateBlock: one state slot

The physical layout of one seq in the state cache. States that must be stored go first, in the stored region. States that are not stored but that the run still needs go after it, in the dropped region. PE→CE transfers both parts; to disk only the first state_size_to_disk bytes of the inference layout, so a length cut excludes the whole dropped region. With extra state on, the kvstore ring is first reordered into the inference window; with it off, the code can cut the original buffer directly. Layout from low to high address: [stored region: SWA] [dropped region: YOCO consumer SWA | compression state]. Each sub-region is in runtime layer order; each SWA layer is aligned to 32 B. With SWA, the whole block is aligned to lcm(32, SWA bytes per token), else to align_to.

PE and CE mean the prefill engine and the completion engine of a disaggregated deployment, which is not in this release. The offline engine uses only the inference sizes.

  2. Indexer key. 128 / 2 + 128 / 32 = 68 B ({{cite deepinfer/worker/cache_engine.py:76-78}}); 128 × 68 = 8,704, a multiple of 32.
  3. Compression state for ratio 2: ring 2 + max(0, 6 − 1) = 7 tokens ({{cite deepinfer/worker/cache_engine.py:131-133}}); fp32 [7, 2, 512] = 7 × 2 × 512 × 4 = 28,672 B ({{cite deepinfer/worker/cache_engine.py:41-43}}). The view is [slots, 7, 2, 512] float32 ({{cite deepinfer/worker/cache_engine.py:367-374}}).
  4. Block row. The offset ends at 64,000. lcm(128, 288) = 1,152; ceil(64,000 / 1,152) × 1,152 = 56 × 1,152 = 64,512 B per block.
  5. State row. The offset ends at 240,928. With SWA, the slot is aligned to lcm(32, 528) = 528: 457 × 528 = 241,296 B ({{cite deepinfer/worker/cache_engine.py:301-305}}).
  6. Slots. int(4 × 1.2) + 1 = 5 ({{cite deepinfer/worker/cache_engine.py:201-202}}), so gpu_states is uint8 [5, 241,296]. Slot 0 is never handed out ({{cite csrc/engine/block_manager.hpp:27-35}}).

Views share one row. ca_cache of L1 is gpu_blocks[:, 8704:45568] seen as [num_blocks, 128, 1, 288] with stride (64,512, 288, 288, 1) ({{cite deepinfer/worker/cache_engine.py:455-458}}). So block id b means row b for every layer.

 Run the profile with a small real KV cache, so that the memory of the cache read and write kernels counts. The allocation uses cuMemAlloc, is not in the torch statistics, and is freed when this function returns, so it does not change the count of profile_num_available_blocks. Zero it because the full gather of chunked prefill reads cache areas that nothing wrote, and the values must be finite. NOTE allocate_gpu_cache also writes bytes_per_block / num_state_seqs / bytes_of_state_per_seqs into cache_config, with the same values as the real allocation later (only num_gpu_blocks differs).
  1. The dummy sequences use blocks 0, 1, 2, ... in order, so num_blocks is the sum of their block counts ({{cite deepinfer/worker/model_runner.py:476-495}}).
  2. The constructor argument num_gpu_blocks overrides cache_config.num_gpu_blocks, which is still None at this time ({{cite deepinfer/worker/cache_engine.py:869}}, {{cite deepinfer/worker/cache_engine.py:882}}, {{cite deepinfer/config.py:137}}).
  3. The profile sets DEEPINFER_FORCE_IMBALANCE_RATIO = 1.8 for the run and sets it back to 0 after ({{cite deepinfer/worker/model_runner.py:510-512}}). The comment says only "MoE simulated imbalance enabled"; this site infers that the aim is a high MoE memory peak.
  4. After the run, profile_num_available_blocks subtracts 2 × prod(state_shape) bytes and divides by get_cache_block_size ({{cite deepinfer/worker/base.py:237-245}}). With the toy config: 2 × 5 × 241,296 = 2,412,960 B for state, then free // 64,512 blocks.

clone_and_zero_states_and_blocks copies whole rows on the current stream with cudaMemcpyAsync ({{cite csrc/engine/scheduler.hpp:1273-1301}}). One state copy is states[0].nbytes(), one block copy is blocks[0].nbytes(): a full row each. A block pair with dst = 0 is not copied; only its source is returned for release ({{cite csrc/engine/scheduler.hpp:1296-1299}}). zero_states clears whole state rows ({{cite csrc/engine/scheduler.hpp:1303-1309}}).

The engine's do_copy_state copies one state row into copy_state for KV saving ({{cite deepinfer/engine/llm_engine.py:787-798}}). copy_state is None in this release, so this does nothing.

How many device buffers does CacheEngine allocate for the cache, and what are their shapes?

Two: gpu_blocks, uint8 [num_gpu_blocks, bytes_per_block], and gpu_states, uint8 [num_state_slots, bytes_per_slot] ({{cite deepinfer/worker/cache_engine.py:937-938}}, {{cite deepinfer/worker/cache_engine.py:948-958}}). Every layer gets views into them.

 Does the SWA cache of a layer use KV blocks? Where is it?

No. It is a ring in the state slot of the sequence, cut from the state row ({{cite deepinfer/worker/cache_engine.py:406-422}}). A layer with only SWA has kv_length = 0 and is not in the block layout ({{cite deepinfer/worker/cache_engine.py:640-642}}).

 Why does the profile run zero its temporary cache?

The comment says that the full gather of chunked prefill reads cache areas that nothing wrote, and the values must be finite ({{cite deepinfer/worker/model_runner.py:498-507}}).

 In the toy config, a layer has ratio 2 and is dense. How many bytes does it take in one block row and in one state slot, without SWA?

Block row: 128 // 2 = 64 entries of 288 B = 18,432 B ({{cite deepinfer/worker/cache_engine.py:452-453}}). State: a ring of 2 + 6 − 1 = 7 tokens of fp32 [2, 512] = 28,672 B ({{cite deepinfer/worker/cache_engine.py:131-133}}, {{cite deepinfer/worker/cache_engine.py:41-43}}). See the deep dive "process() on a toy config".
