It converts the moe.py containers into the runtime layout, runs the gate, and then either DeepEP dispatch, grouped GEMMs and combine, or one mega-MoE call. ---

Purpose

DeepseekMoE runs one MoE layer: it scores the experts for each token, sends the tokens to the expert slots, computes the routed and shared experts, and returns one hidden vector per token.

Where it sits

Who calls it

  • Build. _build_mlp_and_layernorms makes a DeepseekMoE for every MoeDecoderBlockHC ({{cite deepinfer/model_executor/models/decoder_layer.py:38-45}}). DFlash layers use the same function with their own MoE config ({{cite deepinfer/model_executor/models/decoder_layer.py:198-200}}).
  • Forward. DeepseekDecoderLayer.forward calls self.mlp(hidden_states, hidden_states_bf16, input_metadata) after the FFN norm ({{cite deepinfer/model_executor/models/decoder_layer.py:169-173}}). The DFlash layer does the same ({{cite deepinfer/model_executor/models/decoder_layer.py:238}}).
  • Fused cast. The FFN norm asks the layer for fused_norm_cast_kwargs ({{cite deepinfer/model_executor/models/v4_modules/hc.py:52-54}}, {{cite deepinfer/model_executor/models/v4_modules/hc.py:146}}).
  • Set-up. DeepseekForCausalLM.__init__ collects all MoE layers, builds the EPLB balancers from their weights, and calls allocate_userbuffer on each ({{cite deepinfer/model_executor/models/deepseek.py:308-321}}, {{cite deepinfer/model_executor/models/deepseek.py:422-428}}).
  • Dummy weights. With load_format="dummy", process_moe_weight(..., use_fp4=True) converts synthetic expert weights ({{cite deepinfer/model_executor/models/deepseek.py:494}}).

What it calls

  • DeepGEMM (import deep_gemm, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:14}}): the mega gate, the mega-MoE kernels, the grouped GEMMs, the weight and scale layout transforms.
  • DeepEP types (EPBuffer, EPHandle, EventHandle, EventOverlap, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:17}}). The buffer itself comes from userbuffer ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:34}}).
  • tile_kernels: moe_topk_gate and swiglu_forward_and_per_token_cast ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:18-19}}), and quant.per_token_cast for FP4.
  • EPLB: eplb.current().layer(self.layer_idx) ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:326-327}}).

Walk through the main methods

The containers in moe.py

  1. Line 77-78: logical experts come from n_routed_experts; physical = logical + n_redundant_experts, which the loader writes ({{cite deepinfer/model_executor/model_loader.py:102}}).
  2. Lines 91-95: each rank holds physical // ep_size experts; the division must be exact.
  3. Lines 97-108: linear1 has width 2 × moe_intermediate_size (gate and up), linear2 goes back to the hidden size. Both hold only the local experts.
  4. Line 110: the gate container (see {{link concepts/moe-routing}}).

__init__: counts, types and the mega decision

  1. Lines 161-162: routed = logical experts; extra = physical − logical.
  2. Line 175: max_num_tokens is the decode limit for a COMPLETION engine and the prefill limit for all others. It sizes the buffers.
  3. Lines 177-182: mma_type is "fp8xfp4" for the released checkpoint format.
  4. Lines 184-188: the mega decision ({{link concepts/mega-moe}}).
  5. Lines 199-205: physical slots split evenly over the EP ranks.
  6. Lines 207-213: FP4 weights are already in the runtime layout; other types go through process_moe_weight.

The rest of __init__ builds the gate and the biases ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:221-238}}), the shared expert as two ReplicatedLinear ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:240-248}}), and sets the DeepGEMM row alignment for the contiguous layout in DeepGEMM and tile_kernels ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:250-252}}). Mega layers then convert their weights (lines 254-257).

forward

  1. Lines 571-572: mega layers return from mega_moe_forward.
  2. Line 574: the gate uses the BF16 hidden states.
  3. Lines 578-585: dispatch, then wait on the compute stream. The handle carries psum_num_recv_tokens_per_expert.
  4. Lines 593-598: the routed experts on the received rows.
  5. Lines 601-610: event, shared expert with fewer SMs, combine with the shared output as bias, wait.

The page {{link concepts/expert-parallelism}} reads dispatch, routed_experts_forward and combine in detail.

mega_moe_forward

The gate writes into the buffer (lines 537-541). With FP8, the norm already wrote x and x_sf (lines 543-544). One call does the rest. The page {{link concepts/mega-moe}} reads it in detail.

process_moe_weight

  1. Lines 47-48: the source weight is 2-D, [E·k, n]. view(E, -1, n).mT makes a contiguous [E, n, k]. Then the source storage is freed.
  2. Line 49-50: BF16 stops here.
  3. Lines 52-57: the FP8 scales, one per 32 × 32 block, get the same transpose.
  4. Lines 59-71: dummy FP4 path. The assert at line 60 checks that each FP8 byte has two zero low bits ("Only support FP4-QAT checkpoint"). per_token_cast to "e2m1" with 32 values per scale and packed UE8M0 scales.
  5. Lines 73-81: FP8 path: DeepGEMM puts the scales into its required layout.
  6. Lines 84-88: the scales hang on the parameter as .sf; FP4 also gets .mxfp4 = True.

The FP4 layout is from the loader docstring ({{cite deepinfer/hugging_face/weights.py:283}}). The GEMM recipes use blocks of 32 for activations and for FP4 weights ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:118-128}}).
  • DeepEP calls use async_with_compute_stream=True. current_stream_wait() makes the compute stream wait for the communication ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:479}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:585}}).
  • allocate_on_comm_stream is true only with a previous event. Dispatch passes None, so it is false there. Combine passes the captured event, so it is true there ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:480}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:508}}).
  • Both calls set defer_epilogue=True ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:488}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:509}}).
  • Decode steps run in CUDA graphs. The routed-expert timer works only on layer 1 in decode, with cuda_graph_timer ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:588-592}}).
  • dispatch uses do_cpu_sync only in prefill and not in YOCO compact mode ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:482-485}}).
  • gate_forward passes logical_to_physical_map and logical_count of the layer to the gate kernel ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:392-393}}).
  • Dispatch and the mega call add the received rows into expert_count ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:474}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:555}}).
  • _init_eplb gives the balancer the weights to move: gate_up_proj_weight, down_proj_weight, and their .sf for one-byte types. Transposed views go back to the stored order before the move ({{cite deepinfer/model_executor/models/deepseek.py:324-329}}).
  • forward reads eplb.current() in every call ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:326-327}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:591}}). The model always makes the EPLB manager when it has MoE layers, also with EP size 1 ({{cite deepinfer/model_executor/models/deepseek.py:310-317}}).

Settings of examples/offline_inference.py: --ep 8, max_num_seqs=4, nextn = 5. Toy model values: 64 logical experts, k = 4, 32 extra slots (the example lower limit).

  1. Slots: 64 + 32 = 96, divisible by 8, so 12 slots per rank (resolve_num_extra_experts adds no padding).
  2. The decode step has at most 4 × 6 = 24 tokens on this rank. topk_idx is [24, 4].
  3. If the EP group fits in the NVLink domain (GPU) or on Ascend: one mega call. In a NORMAL engine with CP size 1, the buffer has num_max_tokens_per_rank = the prefill limit 32768.
  4. Else: dispatch sends 24 × 4 = 96 rows. If the experts are balanced, the rank receives about 96 rows in 12 groups. Grouped GEMM 1 makes bf16 [96, 2I], grouped GEMM 2 makes bf16 [96, H], and combine returns bf16 [24, H].

Which method decides between the mega path and the DeepEP path at run time?

None at run time. __init__ sets use_mega_moe once ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:184-188}}). forward only reads it ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:571}}).

 Why does forward get two hidden-state inputs?

The experts take FP8 rows with scales, but the gate needs BF16. The FFN norm returns both ({{cite deepinfer/model_executor/models/v4_modules/hc.py:155-161}}), and forward gives the BF16 copy to gate_forward ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:574}}).

 With FP4 expert weights, does __init__ call process_moe_weight?

No. FP4 weights are already in the packed runtime layout, so __init__ only calls reconstruct_param ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:207-210}}). process_moe_weight(..., use_fp4=True) runs only for dummy weights ({{cite deepinfer/model_executor/models/deepseek.py:494}}).

 A COMPLETION engine and a NORMAL engine use the same settings. Which one gets the smaller EP or symmetric buffer, and why?

The COMPLETION engine. Its max_num_tokens is max_num_decoding_tokens, while all other engine types use max_num_prefilling_tokens ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:175}}). Both buffers are sized with max_num_tokens ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:305-324}}).
