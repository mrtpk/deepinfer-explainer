Purpose

This C++ file computes the V4 part of the {{term input-metadata}}: for each row of the packed batch, where its cache entries go and which cache entries it reads.

Walk through the main methods

The two modes of every field

Every function can make its tensors or fill existing ones. The comment at the top of update_common_v4 says, translated: "1. args.out has a value: the tensors are already allocated in result; only fill them. 2. Else: build the tensors from zero and write them into result." ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:20-25}}).

update_common_v4: where new entries go

Pad to at least 1 element for each sequence. Decode: shape [total_q]; only query tokens that make a new compressed token have a value, the others are padding. Makes a new compressed token. Padding: no new compressed token.
  1. Lines 47-49 (prefill): the new compressed entries of a sequence are seqlen_k/n − (seqlen_k − seqlen_q)/n, at least 1.
  2. Lines 58-61: entry j has position j × n and slot block_table[j / cbs] × cbs + j % cbs, with cbs = 128 / n.
  3. Lines 63-67: a sequence with no new entry gets one dummy entry with slot -1, so every sequence has at least one row in the compressor.
  4. Lines 80-91 (decode): one value per row. Only a row at position p with (p + 1) % n == 0 ends an entry.

Lines 103-106: the SWA slot. Only the last swa_block_size rows of a sequence write to the ring; older rows of a long chunk would be overwritten anyway. Lines 111-123: state_block_idx has one value per sequence in prefill and one per row in decode.

prepare_prompt_v4: the prefill fields

For the compressor.

Then the function adds, in this order:

  1. cu_compressed_seqlens_q per ratio, with at least 1 per sequence ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:420-432}}).
  2. ks and ke per sparse ratio. A row at position j sees (j + 1) / r compressed keys from the start of its sequence in the gathered buffer ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:434-459}}).
  3. The SWA load plan and the compressed load plans ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:461-476}}).
  4. kv_swa_full_index_pivots (next section).
  5. The YOCO fields, when the mode is not off ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:532}}).
  6. kv_ca_index_offset_len per dense ratio ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:534-557}}).

The SWA history and the pivots

Each sequence gets exactly window_size history rows. Rows before position 0, or before swa_valid_start, are zero-filled (src_block_id = -1). The rest comes from the sequence's ring, in at most two pieces because the ring wraps.

Index of each query token in the gathered SWA buffer, new tokens included. With X = kv_swa_full_index[i_q], P = kv_swa_full_index_pivots[i_q], W = window_size, the device computes: X[0 : P[1]] = P[0] + arange(P[1]); X[P[1] : P[1] + P[3]] = P[2] + arange(P[3]); X[P[1] + P[3] : W] = -1. Zero-state recompute: the SWA state in [0, valid_start) is cleared, so the left edge of the visible window is clamped to valid_start. With valid_start = 0 (the normal path) this is the same as the old formula. The code below assumes valid_start <= q_start. At present the visible range is always larger than the input range. Lower bound of the visible keys: the larger of the window bound and the valid start, at least 0. Section 1 (history, from the state buffer): visible range [min(abs_lo, q_start), q_start). Section 2 (new in this chunk): visible range [max(abs_lo, q_start), pos].
  1. Lines 493-494: the gathered buffer has all histories first (window_size rows each), then all new rows.
  2. Lines 507-509: the oldest visible position is pos − window + 1, but not before swa_valid_start or 0.
  3. Lines 512-517: section 1 is a range of the sequence's history block.
  4. Lines 520-523: section 2 is a range of the sequence's new rows, up to the row itself (causal).

prepare_decode_v4: the decode fields

The base already checks that seq_metadata_list is not empty. klen: the number of compressed keys that each query token needs, per sparse ratio (mixed ratios are supported). Offset and length of each query token's KV index, per dense ratio. Layers without index attention still call the sparse-attention kernel, so the full index set is made in advance. Only offset and length are computed here, to keep the CPU cost low. The device then computes pos = offset + arange(len), kv_ca_index[i, :len] = block_tables[pos // tpb] * tpb + pos % tpb, and -1 after len. The KV of the current 1 or 2 tokens is already written to the SWA state through slot_mapping_store_swa; here it is read back from the SWA cache with the other tokens. Only offset and length are computed, to keep the CPU cost low. The length is window_size, but not more than the available tokens.

The decode block table of a row uses the smallest ratio of the model (line 566, line 586). The offset of row i is i × max_num_blocks × tpb: it points at row i of the flat block_tables tensor in "compressed token" units.

All tensors are int32 except the bool masks. A dict key is the ratio as a string, for example "2". The page {{link concepts/input-metadata}} computes every field for a two-chunk prefill and a padded decode step.
  1. Lines 9-12: a segment records its destination offset, which is the running total total_k_.
  2. Lines 14-21: a zero fill is cut into pieces of at most one source block.
  3. Lines 23-35: a paged range walks the block table. Each segment stays inside one block.

append_ring_range does the same for a ring: the source block id stays the state slot, and the position wraps with % source_block_size ({{cite csrc/engine/input_metadata/block_load_plan.cpp:37-46}}). The compressed plan of a sequence covers entries 0 to seqlen_k / n; a sequence with 0 entries gets a one-entry zero fill, "on par with" the max(1, …) in ks ({{cite csrc/engine/input_metadata/prepare_tensor_input_base.cpp:51-63}}, {{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:451-452}}).

Example (sequence A of the figure, ratio 2, block table [7, 2, 9], seqlen_k = 260): 130 entries, 64 per block: [7,0,64,0], [2,0,64,64], [9,0,2,128].

 Combined lower bound (position in the sequence): the max of the window bound, the rectangle bound and the state valid bound, clamped to [0, pos + 1]; abs_lo == pos + 1 means an empty visible range (the token is fully outside the rectangle). The right edge of section 1 is q_start. q_start - window_size: the sequence position of the start of the original SWA range. The left edge of section 2 is q_start; j is the offset of the token in section 2, k_lo the offset of the start.

The "rectangle" is the kept range [data_len − keep_tokens, data_len). Rows outside it see nothing in mask mode. In compact mode they are dropped, but a chunk always keeps at least its last row as a placeholder ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:222-225}}). In compact mode, a kept row writes to the ring only if it is in the rectangle and among the last swa_block_size rows of the chunk ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:266-271}}).

With CP above 1, fill_yoco_consumer_cp_scalars computes two lengths for the device: the compact mirror length Σ 2 × ⌈keep_len / (2·cp)⌉ and the largest number of kept rows on one rank ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:173-201}}). Rank r holds parts r and 2·cp − 1 − r of each sequence (line 187), the {{term cp-mirror}}.

With ZOS on (the default), does prepare_decode_v4 run in a decode step?

No. ModelMetadata picks prepare_decode_v4_zos when DEEPINFER_ZERO_OVERHEAD_SCHEDULING is on ({{cite deepinfer/model_executor/model_metadata_utils.py:143}}). Then a device kernel computes the decode fields.

 A decode row is at position 305 and the model has ratio-2 layers. Does it end a compressed entry, and which entry?

Yes: (305 + 1) % 2 == 0. The entry is 305 / 2 = 152, with positions_c = 304 ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:80-86}}).

 A prefill chunk has q_start = 200 and a window of 128. What are the pivots of its first row (position 200), if it is the first sequence of a batch of two?

abs_lo = 73, so section 1 starts at slot 73 − (200 − 128) = 1 with 127 rows, and section 2 has 1 row at 2 × 128 + 0 = 256. Pivots: [1, 127, 256, 1] ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:493-523}}). This matches the deep dive of {{link concepts/input-metadata}}.
