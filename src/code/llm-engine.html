Purpose

LLMEngine turns requests into engine steps: it starts the workers and the KV cache, puts each request into the C++ scheduler, and runs one step per call to step().

The docstring says that the class "receives requests from clients and generates texts". It also says: "This release does not include an online-serving wrapper" ({{cite deepinfer/engine/llm_engine.py:140-141}}). So in this release, the only caller in the package is the offline class LLM.

Where it sits

Read the diagram from left to right. Blue is Python in the engine process. Violet is C++ code that the engine calls. Green is the Worker, which launches the device work. The dashed arrow is the only way back from the Worker into the engine.

Who calls it

  • LLM.__init__ makes the engine with LLMEngine.from_engine_args(engine_args) ({{cite deepinfer/entrypoints/llm.py:84}}).
  • LLM._add_request tokenizes the prompt and calls add_request with an int32 NumPy array ({{cite deepinfer/entrypoints/llm.py:153-166}}).
  • LLM._run_engine calls step() while has_unfinished_requests() is true. At the end it calls flush_inflight_reqs() once ({{cite deepinfer/entrypoints/llm.py:176-186}}).
  • LLM.close calls close() ({{cite deepinfer/entrypoints/llm.py:197-198}}).
  • Benchmarks call llm.llm_engine.step() directly and read llm.llm_engine.scheduler ({{cite examples/benchmark.py:230-231}}, {{cite examples/benchmark.py:252-253}}).

One process holds one engine. For data parallelism, examples/_launch.py starts one process per data-parallel rank with the spawn method ({{cite examples/_launch.py:35-44}}). Each process makes its own LLM ({{cite examples/_config.py:106-117}}).

What it calls

  • The C++ engine. BlockManager, Scheduler, RequestOutputPool, SequenceMetadataPool and four functions come from deepinfer._C.engine ({{cite deepinfer/engine/llm_engine.py:19-31}}). The {{term pybind11}} sources are in csrc/engine/.
  • The driver Worker. Every call to the Worker goes through _run_workers, which calls driver_worker.run_workers ({{cite deepinfer/engine/llm_engine.py:1017-1025}}).
  • Helpers. The Hugging Face tokenizer ({{cite deepinfer/engine/llm_engine.py:200-205}}), the MultimodalProcessor ({{cite deepinfer/engine/llm_engine.py:209-221}}), the SOMatcherBuilder for structured outputs ({{cite deepinfer/engine/llm_engine.py:329-342}}), StatsLogger ({{cite deepinfer/engine/llm_engine.py:298-305}}) and an optional ProfileManager ({{cite deepinfer/engine/llm_engine.py:236-239}}).

Walk through the main methods

Start-up: __init__

The constructor does the work in a fixed order. The order matters: the KV cache size depends on the memory that the weights leave free.

  1. Read the first device id from CUDA_VISIBLE_DEVICES ({{cite deepinfer/engine/llm_engine.py:188-189}}).
  2. Load the tokenizer ({{cite deepinfer/engine/llm_engine.py:200-205}}).
  3. Make a MultimodalProcessor if the model class has multi_modal_mapper and the engine type is not COMPLETION ({{cite deepinfer/engine/llm_engine.py:209-221}}). The only registered architecture maps to DeepseekVLForCausalLM ({{cite deepinfer/model_executor/models/__init__.py:15-17}}), which has this method ({{cite deepinfer/model_executor/models/deepseek_vl.py:105}}).
  4. Make the RequestOutputPool, then start the workers with _init_workers().
  5. Load the weights on all ranks: _run_workers("load_model"). With load_format="dummy" the load is skipped.
  6. Size and make the KV cache with _init_cache().
  7. Make the two block managers and the scheduler (below).
  8. Make the StatsLogger. Its peak speed is two times the BF16 peak, as an FP8-equivalent value ({{cite deepinfer/engine/llm_engine.py:304}}).

The C++ Scheduler gets 14 arguments ({{cite deepinfer/engine/llm_engine.py:307-327}}). Three of them depend on settings: the data-parallel group (the CPU Gloo group when ZOS is on), the YOCO truncation length, and the prefill limit DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K.

_init_workers: processes for context parallelism

  1. Line 371 counts the visible devices.
  2. Lines 377-395 start one process for each context-parallel rank 1 … cp_size − 1. Each process runs _spawn_worker, which makes a Worker with is_driver_worker=False. That Worker never returns: it waits in a loop for method calls ({{cite deepinfer/worker/base.py:120-123}}, {{cite deepinfer/worker/base.py:129-133}}).
  3. Line 384 sets the local device of the follower to cp_rank % ngpus.
  4. Lines 398-413 make the driver Worker in this process, with local_rank=0 and cp_rank=0. The engine gives it two {{term engine-callbacks}}.

_init_workers starts processes only for context parallelism. With cp_size = 1 it starts no process at all. Data-parallel ranks come from the launcher script, one engine per process.

_init_cache: how many KV blocks

  1. Line 437: every rank runs a {{term memory-profiling}} pass. The driver Worker writes the result into cache_config.num_gpu_blocks ({{cite deepinfer/worker/base.py:267}}). The engine shares this cache_config object with the driver Worker, so line 438 can read it. The method's return value is not used.
  2. Line 441: zero blocks stop start-up with ValueError.
  3. Lines 445-446: the cache must hold the longest sequence, with 20 % spare. See the deep dive for the numbers.
  4. Line 453: every rank makes its CacheEngine.
  5. Line 457: warm_up_model captures the CUDA graphs ({{cite deepinfer/worker/base.py:274-288}}).

The docstring says that the engine takes "the minimum number of blocks across all workers" ({{cite deepinfer/engine/llm_engine.py:426-428}}). The code takes the mean: an all-reduce SUM over the world group, then a division by the group size, rounded down to an even number ({{cite deepinfer/worker/base.py:264-266}}). This site describes the code.

add_request: from token ids to a sequence

The caller gives a 1-D np.int32 array of token ids. The engine does not tokenize ({{cite deepinfer/engine/llm_engine.py:493-494}}).

Check the token values.

A token id outside [0, max_valid_token_id) does not raise an error. The engine writes a log line and returns None. With image data, the upper limit grows by ImageTokenOffset.NUM_SPECIAL, because image tokens use ids above the vocabulary.

The caller manages scheduling itself and cannot re-enter through pump, so build synchronously.
  1. Without structured output, _enqueue runs at once and adds the {{term sequence}} to the scheduler's waiting queue.
  2. With structured output and enqueue=True, the grammar compiles on a thread pool. _enqueue runs later, when pump() finds the result ready ({{cite deepinfer/engine/llm_engine.py:841-842}}).
  3. With enqueue=False, the engine builds the grammar matcher now and blocks until it is ready. The caller adds the sequence itself.

step: one engine step

The engine part of step() is short. It schedules, does a few checks, and hands the batch to the Worker:

  1. Lines 885-887: the C++ scheduler picks the sequences for this step. It returns a list of SequenceMetadata from the pool, and a SchedulerOutputs object.
  2. Lines 889-905: sometimes the scheduler asks to copy state slots and KV blocks. This happens for a forked sequence, which starts from the cache of another sequence ({{cite csrc/engine/scheduler.hpp:420-437}}, {{cite csrc/engine/scheduler.hpp:602-618}}). Only the binding Scheduler.fork_seq makes forked sequences, and no Python file in this release calls it ({{cite csrc/engine/pybind_scheduler.cpp:123}}). In this release no scheduler code fills zero_states. Only when a list is not empty does the engine call the Worker. The returned ids are unpinned in this step's pre_sampler_sync.
  3. Line 908: post_schedule is an empty hook in this release.

A step with no sequences still runs: is_placeholder is then true, and the Worker runs the model on a placeholder sequence ({{cite deepinfer/worker/worker.py:125-127}}). The schedulers of all data-parallel ranks vote with an all-reduce during scheduling ({{cite csrc/engine/scheduler.hpp:316-332}}). So every rank must call step() the same number of times, also a rank with no work. The page {{link concepts/dp-step-votes}} explains the votes.

post_process and _process_model_outputs

The Worker calls post_process when the sampled tokens of a step are on the CPU ({{cite deepinfer/worker/worker.py:262-271}}).

_process_model_outputs does three C++ calls in order:

  1. process_MTPInfo copies the new draft tokens of {{link concepts/speculative-decoding | speculative decoding}}, and their confidence values, into each scheduled sequence ({{cite csrc/engine/scheduler.hpp:1196-1250}}).
  2. scheduler.process_outputs appends the accepted tokens to each sequence and checks if the sequence is finished ({{cite csrc/engine/scheduler.hpp:955-992}}).
  3. build_request_outputs makes the RequestOutput objects in the {{term request-output-pool}} and returns their handles ({{cite deepinfer/engine/llm_engine.py:743-761}}). One request can get more than one output in a step, one for each accepted token ({{cite csrc/engine/outputs.hpp:83-85}}).

The order is fixed. A C++ comment says, translated: "build output reads the confidence values from before this update, so process_MTPInfo must be called before build output" ({{cite csrc/engine/scheduler.hpp:1244-1245}}).

If statistics are on, the method also returns a function that logs a StepStats record. post_process calls it, and an error there only writes a log line ({{cite deepinfer/engine/llm_engine.py:1004-1008}}).

pre_sampler_sync and DeferredRelease

The Worker calls pre_sampler_sync right after it launches the sampling kernels ({{cite deepinfer/worker/worker.py:154-164}}). The CPU work in this callback overlaps with the device work.

Release the resources that a step made one step later, so that the caller has finished reading them. Collect the resources to release. Release them at the next pre_sampler_sync, overlapped with GPU computation.

Three kinds of objects wait in DeferredRelease: the SequenceMetadata list of a step, the RequestOutput handles of a step, and the state and block ids from a clone. For the clone ids, release() first waits for a CUDA event that marks the end of the clone ({{cite deepinfer/engine/llm_engine.py:109-116}}).

The small methods

  • has_unfinished_requests() combines the local answer of all data-parallel ranks with an all-reduce MAX. With ZOS it uses the CPU group, else the device group ({{cite deepinfer/engine/llm_engine.py:665-679}}). So every rank keeps calling step() until all ranks are done.
  • flush_inflight_reqs() asks the Worker for the outputs of the step that it still holds ({{cite deepinfer/engine/llm_engine.py:977-982}}, {{cite deepinfer/worker/worker.py:274-283}}).
  • abort_request() takes one id or many ids and returns the number of aborted sequences and their total length ({{cite deepinfer/engine/llm_engine.py:648-656}}).
  • close() runs once. It calls stop on all workers ({{cite deepinfer/engine/llm_engine.py:350-366}}). __del__ also calls it ({{cite deepinfer/engine/llm_engine.py:347-348}}).

How the followers get their work. run_workers first broadcasts (method, kwargs) to the context-parallel group, then calls the method on the driver ({{cite deepinfer/worker/base.py:290-302}}). The followers run the same method with the same kwargs. Only the driver gets driver_kwargs, so only the driver sees seq_metadata_list and scheduler_outputs. The followers get the prepared input tensors from the driver by a tensor broadcast inside the model runner ({{cite deepinfer/worker/model_runner.py:201-213}}, {{cite deepinfer/worker/model_runner.py:216-217}}).

What happens when the parent dies. A follower asks the Linux kernel for SIGKILL when its parent process dies ({{cite deepinfer/worker/base.py:42-46}}, {{cite deepinfer/worker/base.py:130}}). A crash in a follower prints a crash header first ({{cite deepinfer/logger.py:148-166}}).

Thread rule for structured outputs. Translated comment: "submit and pump are both called on the main thread; worker threads only fill the future and do not touch the scheduling of sequences." ({{cite deepinfer/structure_output/so_matcher_builder.py:50}}). So the scheduler is used from one thread only.

ZOS lets the CPU prepare step N+1 while the device still computes step N. The page {{link concepts/zero-overhead-scheduling}} explains the idea. This section lists what changes in llm_engine.py.

  1. The default. EngineArgs.__post_init__ sets DEEPINFER_ZERO_OVERHEAD_SCHEDULING to 1 for NORMAL and COMPLETION engines, if you did not set it ({{cite deepinfer/engine/arg_utils.py:51-55}}, {{cite deepinfer/engine/engine_type.py:15-17}}). A PROMPT engine gets 0.
  2. The scheduler's data-parallel group. With ZOS, the scheduler gets the CPU (Gloo) group ({{cite deepinfer/engine/llm_engine.py:313}}). The C++ code sees the backend name "gloo" and puts its all-reduce tensors on the CPU ({{cite csrc/engine/scheduler.hpp:109}}, {{cite csrc/engine/scheduler.hpp:170-180}}).
  3. has_unfinished_requests uses the same CPU group ({{cite deepinfer/engine/llm_engine.py:667-672}}).
  4. Outputs come one step late. For a decode step, the Worker keeps the step state and post-processes it in the next call ({{cite deepinfer/worker/worker.py:182-187}}). So step() number N returns the tokens of step N−1. The hook docstring says the same: with ZOS, process_output handles the tokens of the previous step ({{cite deepinfer/engine/llm_engine.py:824-828}}).
  5. The last step. When no work is left, LLM calls flush_inflight_reqs() to get the last outputs ({{cite deepinfer/entrypoints/llm.py:177-178}}).
  6. Buffers live one step longer. DeferredRelease keeps the buffers of step N−1 until the pre_sampler_sync of step N.
  7. The length limit grows. With ZOS the runtime limit adds nextn + 1 more positions ({{cite deepinfer/config.py:11-16}}). This value goes into the KV cache check in _init_cache.

A handle from step() points into the pool. The pool gets the object back at the next pre_sampler_sync. Clone the output first, as LLM does.

Step 1: free memory per rank. profile_num_available_blocks runs a profiling forward pass and computes ({{cite deepinfer/worker/base.py:228-245}}):

peak    = peak_torch_allocated + max(non_torch_allocated, 0)
kv_mem  = total_gpu_memory * gpu_memory_utilization - peak
kv_mem -= 2 * state_size        # "state store & copy buffer"
blocks  = max(int(kv_mem // cache_block_size), 0)

Step 2: one value for all ranks. All ranks add their blocks with an all-reduce SUM. Each rank then takes sum // world_size // 2 * 2: the mean, rounded down to an even number ({{cite deepinfer/worker/base.py:264-266}}).

Step 3: the engine check. The block size is 128 tokens for this model ({{cite deepinfer/model_executor/model_metadata_utils.py:133-135}}). The engine needs runtime_max_model_len ≤ int(128 × num_gpu_blocks × 0.8) ({{cite deepinfer/engine/llm_engine.py:445-446}}).

A worked example with the settings of examples/offline_inference.py: max_model_len=32768 ({{cite examples/offline_inference.py:53}}), the default nextn = 5 and ZOS on.

  1. runtime_max_model_len = 32768 + 5 + (5 + 1) + 5 = 32784 ({{cite deepinfer/config.py:11-16}}).
  2. The check needs 128 × blocks × 0.8 ≥ 32784, so blocks ≥ 320.16. At least 321 blocks are necessary.
  3. With 320 blocks, int(128 × 320 × 0.8) = 32768 < 32784, and start-up stops with ValueError.

After the check. CacheEngine writes num_state_seqs, bytes_of_state_per_seqs and bytes_per_block into the shared cache_config ({{cite deepinfer/worker/cache_engine.py:949-951}}). The engine reads them at line 263 for a log line and at line 266 for the state manager.

Which class calls LLMEngine.step() in normal offline use, and what does step() return?

LLM._run_engine in deepinfer/entrypoints/llm.py ({{cite deepinfer/entrypoints/llm.py:176-178}}). step() returns a NumPy array of uint64 handles to RequestOutput objects in the RequestOutputPool. LLM clones each one before the next step.

 You run with context_parallel_size = 1. How many worker processes does _init_workers start?

None. The loop for cp_rank in range(1, cp_size) is empty ({{cite deepinfer/engine/llm_engine.py:377}}). The driver Worker runs inside the engine process.

 A request has the token id -1 in its prompt. What does add_request do? Does it raise?

It does not raise. It writes an info log line "Drop request ... due to invalid token" and returns None ({{cite deepinfer/engine/llm_engine.py:582-589}}). Only an empty prompt raises ValueError.

 With ZOS on, a sequence is in a decode step. In which call of step() does the caller get the token of that step?

In the next call. The Worker keeps the state of a ZOS decode step in prev_step_state and post-processes it during the next execute_model_step ({{cite deepinfer/worker/worker.py:143-144}}, {{cite deepinfer/worker/worker.py:182-187}}). For the last step, flush_inflight_reqs() gets it.

 You set max_model_len=32768, keep DEEPINFER_USE_NEXTN_DECODE=5 and ZOS on. Profiling gives each of 8 ranks 400, 400, 400, 400, 300, 300, 300 and 301 blocks. Does start-up pass the KV cache check?

The sum is 2801. 2801 // 8 = 350, and 350 // 2 * 2 = 350 ({{cite deepinfer/worker/base.py:264-266}}). The check needs int(128 × 350 × 0.8) = 35840 ≥ 32784 ({{cite deepinfer/engine/llm_engine.py:445-446}}, {{cite deepinfer/config.py:11-16}}). So it passes, although some ranks measured only 300 blocks. The docstring says "minimum", but the code uses the mean. This is the deep dive "Sizing the KV cache".
