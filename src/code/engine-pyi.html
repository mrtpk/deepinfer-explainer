Where it sits

The groups follow the job of each name, not the binding file. pybind_output.cpp binds three groups: outputs, input metadata and sampler inputs.

Who reads it

  • Editors and type checkers. The Python imports carry # pyright: ignore[reportMissingModuleSource], because pyright finds the stub but not the compiled source ({{cite deepinfer/engine/llm_engine.py:19}}).
  • You. The stub is the shortest way to learn the C++ API: argument names, types and the docstrings, which are in Chinese. This page translates them.

Walk through the main methods

A stub has no method bodies. This part reads the stub lines that matter most, and the rules that the docstrings state.

The header and __all__

Line 8 lists all exported names. The script that makes the stub then replaces typing.Sequence with Sequence in this file ({{cite scripts/gen_stub.sh:17-18}}). Note the name clash: Sequence is also the engine class at line 421. In argument types, collections.abc.Sequence means "a list or tuple".

Scheduler: the constructor and two docstrings

Commit this step's model output. Returns (first_token_latencies float64[n], pushed_tokens_before_finish int32[n]). Both arrays borrow a process-wide static buffer without a copy; the next process_outputs overwrites it. Use them up before that; never keep them across steps. Schedule one step. Returns (seq_metadata_list, scheduler_outputs). The SequenceMetadata objects in seq_metadata_list come from the pool; return them with pool.release after use.
  1. Line 310: the constructor takes 14 arguments. LLMEngine._create_scheduler passes them in this order ({{cite deepinfer/engine/llm_engine.py:307-327}}). scheduler_config is typing.Any: C++ reads its attributes by name, for example max_num_seqs ({{cite csrc/engine/scheduler.hpp:94-100}}).
  2. Line 316: fork_seq takes 9 arguments. In this release only examples/benchmark.py calls it ({{cite examples/benchmark.py:337-347}}).
  3. Lines 336-343: the two docstrings give the borrow rules. The deep dive "Borrowed memory" lists all of them.

BlockManager.unpin_blocks (stub line 24) has no C++ method of that name. The binding maps it to BlockManager::free_blocks ({{cite csrc/engine/pybind_scheduler.cpp:68}}). To unpin and to free are the same operation.

SchedulerOutputs: views into scheduler memory

[n, 2] int32 (src, dst) block clone pairs; dst = 0 means: only give back src, do not copy. Borrows the Scheduler's internal storage without a copy; the next schedule() clears and reuses it. Use it up before that; never keep it across steps. [n, 2] int32 (src, dst) state clone pairs. Same borrow rule.

The binding builds these NumPy arrays on the scheduler's own vector, with an empty capsule as owner ({{cite csrc/engine/pybind_scheduler.cpp:41-48}}). So the array is valid only until the next schedule() clears that vector ({{cite csrc/engine/scheduler.hpp:282-284}}).

RequestOutput: properties and raw-pointer readers

Every field except max_num_batched_tokens has a property and a static get_<field>(ptr) that reads the field at an {{term output-handle}} without a copy ({{cite csrc/engine/pybind_output.cpp:12-14}}, {{cite csrc/engine/pybind_output.cpp:24}}). max_num_batched_tokens has only the property. clone(ptr) makes a Python-owned copy. The page {{link code/outputs-hpp}} explains why a handle is valid for about one step.

Sequence and SequenceMetadata: what Python can change

Sequence token constructor: the caller guarantees that the token_ids are valid; this constructor only copies the data.
  • Lines 422-430: plain attributes, so Python can read and write them, for example status and so_matcher. They are properties in C++ that point into the nested state structs ({{cite csrc/engine/pybind_sequence.cpp:109-137}}).
  • prompt_token_ids must be an int32 C-contiguous NumPy array: the binding uses noconvert() ({{cite csrc/engine/pybind_sequence.cpp:103}}). A Python list or an int64 array raises TypeError. This is why LLM._add_request converts with np.asarray(..., dtype=np.int32) ({{cite deepinfer/entrypoints/llm.py:157}}).
  • SequenceMetadata is almost read-only. Only so_status has a setter (stub lines 582-587; {{cite csrc/engine/pybind_sequence.cpp:167}}).

The functions with Chinese docstrings

Runs the clone and zeroing of states and blocks on the current CUDA stream. Returns two int32 arrays (to_release_states, to_release_blocks). Both borrow a process-wide static buffer without a copy; the next call overwrites it. Use them up before that; never keep them across steps. Engram compression mapping: lookup_table[t] when 0 <= t < len(lookup_table); otherwise (also for negative and out-of-table ids) sentinel.

The engine follows these rules. It copies the clone ids into DeferredRelease before the next schedule, and it releases metadata and outputs one step later ({{cite deepinfer/engine/llm_engine.py:889-905}}, {{cite deepinfer/engine/llm_engine.py:1013}}).

The opposite case: copies. A C++ std::vector field becomes a new Python list on every access. For example, Sequence.chunk_checkpoints or RequestOutput.top_logprobs. A change to that list does not change the C++ object. The module docstring of sampling_inputs.py states this rule ({{cite deepinfer/model_executor/sampling_inputs.py:7-9}}). To change a vector field, assign a new list, as LLMEngine.add_request does with seq.chunk_checkpoints = ... ({{cite deepinfer/engine/llm_engine.py:615-616}}).

One call must keep the GIL: SchedulerOutputs.update_metadata_for_sampling_zos. A comment says why: it assigns a Python object (so_matcher) ({{cite csrc/engine/pybind_scheduler.cpp:51-53}}).
  • typing.SupportsInt | typing.SupportsIndex is how pybind11-stubgen writes a C++ int argument. A Python int or a NumPy integer works.
  • typing.Any marks a C++ py::object: the C++ code reads attributes by name. Examples: scheduler_config, sampling_params, so_matcher ({{cite deepinfer/_C/engine.pyi:310}}, {{cite deepinfer/_C/engine.pyi:431}}). The stub cannot check these. For sampling_params, C++ reads nine attributes once ({{cite csrc/engine/sequence.hpp:103-115}}).
  • Return widths. get_finished_seqs_info returns tuple[int, int, int, int] in the stub; in C++ the last value is int64_t ({{cite csrc/engine/scheduler.hpp:1315}}). Python int has no width, so nothing is lost.
  • 13-tuple. prepare_decode_zos_inputs returns 13 values with no names (stub line 721). The only caller unpacks them by position ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:49-69}}).
  • Enums. SequenceStatus and YocoPrefillTruncationMode are pybind11 enums: they compare with ==, convert with int(), and have .name and .value (stub lines 593-653, 667-706).
  1. Build the extension for your platform: make build-nvidia or make build-ascend ({{cite Makefile:3-11}}).
  2. Run make stubgen. The script preloads the CUDA stub library libcuda.so from CUDA_HOME/lib64/stubs, if that file exists ({{cite scripts/gen_stub.sh:6-10}}).
  3. pybind11-stubgen imports deepinfer._C and writes deepinfer/_C/*.pyi ({{cite scripts/gen_stub.sh:11-13}}).
  4. The script replaces typing.Sequence with Sequence in engine.pyi ({{cite scripts/gen_stub.sh:17-18}}).

Nothing in the build checks that the stub matches the compiled module. If you change a binding and do not run make stubgen, the stub is wrong. We compared the names in the stub with the three binding files at commit 9bd9cf2 and found no difference.

LLMEngine.step() calls self.scheduler.schedule(self.sequence_metadata_pool) ({{cite deepinfer/engine/llm_engine.py:885-887}}). The stub tells you:

  1. Line 340: schedule(self, sequence_metadata_pool: SequenceMetadataPool) -> tuple. The return type is a plain tuple; the docstring (translated above) says it holds (seq_metadata_list, scheduler_outputs).
  2. Lines 537-587: each SequenceMetadata has seqlen_q, seqlen_k, is_prompt and more.
  3. Lines 371-420: SchedulerOutputs has scheduled_seqs, prompt_run, num_batched_tokens and the three borrowed arrays.
  4. Then grep -n "\"schedule\"" csrc/engine/pybind_*.cpp finds the binding: &Scheduler::schedule ({{cite csrc/engine/pybind_scheduler.cpp:97-99}}), and the C++ body is at {{cite csrc/engine/scheduler.hpp:667-736}}.

Example values for a decode step with 4 sequences and nextn = 5:

  • 4 metadata objects with seqlen_q = 6 each, or less with variable draft lengths.
  • prompt_run = False and num_batched_tokens = 24 at most.
  • clone_blocks with shape [0, 2] when there is no fork ({{cite csrc/engine/pybind_scheduler.cpp:44-45}}).

Does Python import engine.pyi at run time?

No. A .pyi file is only for editors and type checkers. At run time Python loads the compiled deepinfer._C from deepinfer/_so/<tag>/, which deepinfer/__init__.py adds to the package path ({{cite deepinfer/__init__.py:28-32}}).

 Which C++ file binds prepare_sampler_inputs, and which file implements it?

pybind_output.cpp binds it ({{cite csrc/engine/pybind_output.cpp:133-135}}). prepare_sample.cpp implements it ({{cite csrc/engine/prepare_sample.cpp:40}}).

 You call Sequence(seq_id=0, prompt_token_ids=[1, 2, 3], ...) with a Python list. What happens, and why?

A TypeError: the binding declares prompt_token_ids with noconvert() and type py::array_t<int32_t, c_style>, so pybind11 does not convert a list ({{cite csrc/engine/pybind_sequence.cpp:93}}, {{cite csrc/engine/pybind_sequence.cpp:103}}). Pass np.asarray(ids, dtype=np.int32).

 A script saves outs.clone_blocks in a list after each schedule() and reads the list after 10 steps. What does it read, and why?

Wrong data. The array is a view on the scheduler's vector with an empty capsule as owner ({{cite csrc/engine/pybind_scheduler.cpp:41-48}}). Each schedule() clears and refills that vector ({{cite csrc/engine/scheduler.hpp:282-284}}), so all saved arrays show the storage of the latest step (or freed memory). Copy with np.array(outs.clone_blocks) instead. This is the deep dive "Borrowed memory".
