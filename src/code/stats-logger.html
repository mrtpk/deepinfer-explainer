Purpose

StatsLogger turns per-step numbers into a periodic log line, so that you can see the speed and the health of a running engine.

Filedeepinfer/engine/stats_logger.py, 477 lines. Also on this page: deepinfer/timer.py (295 lines) and deepinfer/engine/profile_server.py (320 lines).

Where it sits

Read panel 1 from left to right. Blue work happens in every step, green work only in a logging step, and the amber thread does the slow logging call. Panel 2 shows three formulas from the code with small invented numbers.

Who calls it

  • LLMEngine.__init__ passes itself, three configs and the device peak: tflops_limit = get_bf16_tflops_limit() × 2, an FP8-equivalent peak ({{cite deepinfer/engine/llm_engine.py:298-305}}).
  • _process_model_outputs makes a StepStats record and returns a function that calls log_step, only when statistics are on ({{cite deepinfer/engine/llm_engine.py:763-785}}). post_process calls it and only logs an error if it fails ({{cite deepinfer/engine/llm_engine.py:1004-1008}}).
  • step() calls log_nccl_memory() in every step with statistics on ({{cite deepinfer/engine/llm_engine.py:954-955}}).
  • close() stops the log thread ({{cite deepinfer/engine/llm_engine.py:355-356}}).

Statistics are on when disable_log_stats is false. LLM turns them off by default; the example scripts turn them on ({{cite deepinfer/entrypoints/llm.py:67}}, {{cite examples/_config.py:122}}).

What it calls

  • Scheduler counters: free blocks, running and chunked prompt counts, preempted and aborted counts ({{cite deepinfer/engine/stats_logger.py:410-423}}).
  • cpu_timer and the two device timers, through get_timers() ({{cite deepinfer/timer.py:293-295}}).
  • A daemon thread stats_log_worker with a queue.SimpleQueue ({{cite deepinfer/engine/stats_logger.py:185-187}}).

Walk through the main methods

log_step: once per step

  1. Line 449: _record appends the step to the {{term stats-window | windows}}. A prefill step goes into the prompt window; a decode step into three windows for generated tokens, verified tokens and confidence errors. Every step goes into the FLOP window, and into the moe_lb window when it has a value ({{cite deepinfer/engine/stats_logger.py:359-377}}).
  2. Line 452: a log line is due at step 0 and then every DEEPINFER_LOGGING_INTERVAL_STEP steps. A PROMPT engine logs five times as often ({{cite deepinfer/engine/stats_logger.py:381-390}}).
  3. Lines 453-458: on a logging step, each window keeps only the entries that are at most interval steps old (so interval + 1 steps). The moe_lb window keeps at least DEEPINFER_MOE_LB_STAT_INTERVAL steps (default 128), because a new value comes only that often.
  4. Line 459: _collect computes the values. Cheap values are computed in every step; the expensive ones only on a logging step.
  5. Lines 462-467: the message goes to the queue, not to the logger. The main thread never waits for log I/O ({{cite deepinfer/engine/stats_logger.py:342-344}}).
  6. Lines 470-474: on a logging step, all timers are cleared, so each line shows the time since the last line.

DEEPINFER_LOGGING_INTERVAL_STEP=0 turns the line off. The condition on line 453 is then true in every step, so every window except the moe_lb window is trimmed to age 0 in every step (line 456). The benchmark script uses this to turn the log off in parts of its run ({{cite examples/README.md:49}}).

Throughput and MFU

Convention: the first entry is only the start of the window (its value is not counted); the denominator goes to now, including the empty time after the last sample, so the value decays when the window stops getting entries (compare _mfu). Convention: the first entry is only the start of the interval (its value is not counted); the denominator is the time between the first and the last sample, not up to now (compare _throughput; _tflops gets an entry in every step, so in practice the last time stamp is now).

MFU divides by model_parallel_size, which is the CP size ({{cite deepinfer/config.py:171}}). The code does not say why. The peak tflops_limit is two times the BF16 peak of deep_cluster: 2 × 2250 on x86_64 SM100, 2 × 2500 on ARM, 2 × 432 on Ascend ({{cite deep_cluster/hardware/device.py:151-156}}).

Draft accept rates

The sampler reports two lists per decode step: num_generated_tokens and num_verified_tokens. Item 0 is the request count; item i is the count for draft position i ({{cite deepinfer/sequence.py:242-246}}, {{cite deepinfer/model_executor/layers/sampler.py:294-295}}). So nextn_rates[i-1] is the accept rate of draft i among the drafts that were verified. avg_verified_len is the mean number of drafts sent per request; it is lower than 5 only with DSpark.

moe_lb: sum of maxima over sum of means

No data: assume perfect balance.

Each payload is (mean, max). The EPLB code makes it every DEEPINFER_MOE_LB_STAT_INTERVAL steps: it gathers the token counts of every EP rank, takes the mean and the maximum over ranks for each step and MoE layer, and sums each over all steps and layers ({{cite deepinfer/model_executor/eplb/__init__.py:180-193}}). The logger then divides the sum of maxima by the sum of means. 1.0 is perfect balance.

The deployment Q&A calls moe_lb "slowest rank / mean" ({{cite doc/inference_deployment_qa.md:99}}). The code takes the maximum per step and layer first, then sums. So the busiest rank can change from layer to layer, and the result is never smaller than the ratio of the total of the busiest rank to the mean. The page {{link concepts/eplb}} explains the counting.

The record is built in _process_model_outputs ({{cite deepinfer/engine/llm_engine.py:765-780}}). With ZOS, this runs one step late, so a log line at step N describes steps up to N−1.

Invented numbers: one DP rank, --cp 1, x86_64 SM100 (tflops_limit = 4500), interval 10. Steps 110 to 120 are decode steps, 10 ms apart, each with 4 sequences and 24 query tokens.

  1. completion_TPS. The generated-token window has 11 entries. Each counts sum(gen_tokens): for example 4 + 3 + 3 + 2 + 2 + 1 = 15 tokens (4 sampled tokens and 11 accepted drafts). The first entry only marks the start. 10 × 15 / 0.1 s = 1500 tokens per second.
  2. MFU. Each step reports 0.9 TFLOP. (11 × 0.9 − 0.9) / 0.1 s / 1 / 4500 = 0.02.
  3. Accept rate of draft 1. 4 drafts verified per step at position 1, and 3 accepted. All 11 entries count here: 33 / 44 = 75 %.
  4. avg_verified_len. sum(verified[1:]) / sum(num_seqs) = 11 × 20 / 44 = 5.0 with fixed 5 drafts.
  5. KV_cache_usage. (num_gpu_blocks − 1 − free) / (num_gpu_blocks − 1); block 0 is not counted ({{cite deepinfer/engine/stats_logger.py:410-411}}).
  6. cur_SPS. With ZOS, 1 / last_step_interval, the time between two step() calls ({{cite deepinfer/engine/stats_logger.py:405-406}}): 1 / 0.010 = 100.

The log thread sleeps (rank % 8) × 5 ms before it writes, but only when no backlog waits in the queue ({{cite deepinfer/engine/stats_logger.py:116-126}}). So the 8 ranks of one host do not all write at the same moment. close() puts None on the queue and joins the thread, so queued lines are written before the engine stops ({{cite deepinfer/engine/stats_logger.py:346-349}}).

The CPU split prefill/decode comes from two extra timer names. _record adds the time since the last step to engine_step:prefill or engine_step:decode, but not for empty steps ({{cite deepinfer/engine/stats_logger.py:362-372}}).

With DEEPINFER_PROFILE_HTTP_ENABLE=1, the engine starts a small HTTP server in a daemon thread ({{cite deepinfer/engine/llm_engine.py:235-239}}). It listens on port DEEPINFER_PROFILE_HTTP_PORT_BASE + driver_gpu_id, default 6070 + gpu ({{cite deepinfer/engine/profile_server.py:117}}).

  1. A client sends POST /profile (or GET) with num_steps (1 to 50, default 20) and an optional output_dir ({{cite deepinfer/engine/profile_server.py:167-205}}).
  2. The engine thread picks the request up at the start of the next step() and starts torch.profiler ({{cite deepinfer/engine/profile_server.py:256-295}}, {{cite deepinfer/engine/llm_engine.py:878-879}}).
  3. After num_steps steps it stops the profiler. A worker thread writes the {{term profiler-trace}} to profile-<ip>-gpu<id>-rank<rank>-<time>.json ({{cite deepinfer/engine/profile_server.py:311-320}}, {{cite deepinfer/engine/profile_server.py:224-226}}).
  4. The HTTP reply holds the file path. A second request during a run gets 409; a request that the engine does not pick up in 30 s gets 503 ({{cite deepinfer/engine/profile_server.py:216-252}}, {{cite deepinfer/engine/profile_server.py:277-278}}).

Only the driver device is traced, because the profiler works in one process; CP followers are not in the trace (Translated, {{cite deepinfer/engine/profile_server.py:7-8}}). A comment gives a measured size of about 4.9 MB per step (Translated, {{cite deepinfer/engine/profile_server.py:45}}). Missing fastapi or uvicorn, or a busy port, only turns the endpoint off with an error log ({{cite deepinfer/engine/profile_server.py:140-152}}).

You use LLM(...) and see no [stats] lines. Why?

LLM.__init__ sets disable_log_stats=True unless you pass it ({{cite deepinfer/entrypoints/llm.py:67}}). Then _process_model_outputs returns an empty function ({{cite deepinfer/engine/llm_engine.py:782-783}}). Pass disable_log_stats=False, as create_llm does ({{cite examples/_config.py:122}}).

 Two windows give moe_lb payloads (mean, max) = (100, 120) and (100, 150). What does the log show? What would "slowest rank / mean" of each payload give?

The code: (120 + 150) / (100 + 100) = 1.35 ({{cite deepinfer/engine/stats_logger.py:238-241}}). Per payload: 1.2 and 1.5, with a mean of 1.35 here only because both means are equal. With different means, the two methods give different numbers; the code weights each payload by its mean.

 A decode run stops getting new steps. Why does completion_TPS go down, but MFU stays the same, in the next log line?

_throughput divides by now − t_first, so empty time after the last sample counts. _mfu divides by t_last − t_first ({{cite deepinfer/engine/stats_logger.py:199-209}}). The translated comments state this difference.

 On x86_64 SM100 with --cp 2, the FLOP window has 11 entries of 18 TFLOP each, 0.1 s from first to last. What MFU does the logger print?

(11 × 18 − 18) / 0.1 = 1800 TFLOP/s. Divide by model_parallel_size = 2 and by tflops_limit = 2 × 2250 = 4500: 1800 / 2 / 4500 = 0.2 ({{cite deepinfer/engine/stats_logger.py:208-209}}, {{cite deepinfer/engine/llm_engine.py:304}}, {{cite deep_cluster/hardware/device.py:155}}).
