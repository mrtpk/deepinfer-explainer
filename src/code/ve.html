Purpose

deepinfer/ve/ does all image work on the CPU: it plans how many tokens each image takes, prepares the pixels in a separate process, and gives each prefill chunk the image data that it needs.

Walk through the main methods

overwrite_prompt

"Found N image_token_id but only M images; the extra image_token_id stay plain tokens!" Inference does not use the text token content (the engine has input_ids): TextLengthInput carries only the length.
  1. Lines 118-124: extra placeholders stay as text, with an error log.
  2. Line 145: the token count comes from the declared size, without a decode.
  3. Lines 146-148: the first token is vocab_size + 2, the others vocab_size + 1. The span (start, count) goes into image_spans.
  4. Lines 158-162: the dict gets segment_input and loses image_sizes and image_bytes (the bytes now live in the segments). The function always returns a new array.

_processor: the worker loop

Bind to the NUMA node of this engine's GPU (index 0 of the visible list). Every VE deployment uses one device per process. "multimodal processor NUMA/CPU binding failed; continue without binding"

Before the loop, the worker binds to the NUMA node of the engine's first visible device. With 2-way SMT, it uses the sibling hyperthreads of that device's cores, to stay off the main process's cores. It uses 2 torch threads. A binding failure only logs a warning. On NPU, it first resets SIGTERM to the default, because torch_npu's fork path ignores the signal ({{cite deepinfer/ve/multimodal_processor.py:165-171}}). The loop itself is in {{link concepts/vision-encoder}} (step 3).

fetch

  1. Lines 287-289: any result, also a failure, proves that the worker is alive and resets the hang clock.
  2. Lines 290-292: a failure goes to to_abort_ids; the engine aborts it in the same step.
  3. Lines 293-295: a result for an aborted request frees its pool blocks.
  4. Lines 296-299: with the pool, each handle becomes a tensor view of the shared pool. The "handle" key stays in the dict and marks pool ownership.
  5. Lines 301-303: the original dict object, which the C++ sequence also holds, is updated in place. Then the sequence becomes schedulable.

compute_image_layout

Clamp the width of a very wide image to height × max_wh_ratio; that image is then stretched, not fitted with the same aspect ratio. Resize to a multiple of patch_size within max_n_token, with the same aspect ratio, and count the LLM tokens. Any-resolution images still add image_newline: the ViT features have 2-D information, but the LLM still uses 1-D RoPE.
  1. Lines 166-167: a very wide image is clamped to max_wh_ratio.
  2. Lines 170-173: a small image is scaled up to min_pixels.
  3. Lines 178-179: round both sides up to a multiple of the patch size.
  4. Lines 180-188: safe_resize keeps that size if the token count fits, else solve_resize_ratio solves h × (w + 1) = max_n_token − 2 with the aspect ratio ({{cite deepinfer/ve/processor/image_processor.py:95-127}}).

_chunk_mm_metadata

  1. Lines 36-37: cut the per-token keys to the chunk.
  2. Lines 43-47: binary search for the first image that ends after the chunk start and the first image that starts at or after the chunk end.
  3. Lines 50-52: no overlap: all image keys become None.
  4. Lines 55-73: cut the per-image keys, the raw bytes and the patch positions to the overlapping images, and shift the running sums to start at 0.

After batching, prepare_input_metadata_vl adds cu_seqlens_vit (int32 [num_valid_images + 1]), max_seqlen_vit, num_downsampled_patch, vit_attn_cu_seqlens (NPU only), image_raw_sizes, cu_raw_bytes (rebuilt for the whole batch, int64) and total_image_patches ({{cite deepinfer/ve/prepare_tensor_input_vl.py:123-163}}). Zero-crop rows (cached images) are removed before the ViT ({{cite deepinfer/ve/prepare_tensor_input_vl.py:99-111}}).
  • Processes. The engine passes no num_workers, so the default of 1 applies: one worker process per engine (per DP rank) ({{cite deepinfer/ve/multimodal_processor.py:36}}, {{cite deepinfer/engine/llm_engine.py:213-219}}). The worker is a daemon ForkProcessWithCrashHeader ({{cite deepinfer/ve/multimodal_processor.py:99-101}}).
  • Queues. input_queue has no limit. output_queue holds at most DEEPINFER_MULTI_MODAL_BUFFER_SIZE results; a full queue blocks the worker, which gives back-pressure.
  • Pool. With DEEPINFER_USE_MULTIMODAL_POOL, the worker copies each non-empty tensor into a SharedTorchMemoryPool block and sends (handle, shape, dtype) ({{cite deepinfer/ve/multimodal_processor.py:202-211}}). The pool is one multiprocessing.shared_memory block, pinned for fast copies to the device ({{cite deepinfer/shared_memory.py:80-84}}, {{cite deepinfer/shared_memory.py:114-120}}).
  • Pool lifetime. When a prefill covers all tokens of a sequence, defer_expiring_pool_handles takes the blocks and records an event after the host-to-device copy is queued. free_deferred_pool_handles waits for that event and frees the blocks in pre_sampler_sync of the same step ({{cite deepinfer/ve/schema.py:53-77}}).
  • Shutdown. stop terminates the workers, joins them when the pool is on, and closes the pool ({{cite deepinfer/ve/multimodal_processor.py:317-326}}).

Prompt: 40 text tokens, image A (206 tokens), 10 text tokens, image B (206 tokens), 30 text tokens. Total 492. Image spans: A = (40, 206), B = (256, 206). Assume a token budget of 300 and chunked prefill on.

  1. Chunk 1 would be tokens 0-299. Position 300 is inside B (B covers 256-461), so the scheduler must move the end. This is the first sequence of the batch, so it tries to grow to 462. 462 tokens exceed the budget, so it shrinks to the start of B: chunk 1 is tokens 0-255 ({{cite csrc/engine/scheduler.hpp:487-493}}).
  2. _chunk_mm_metadata(0, 256): ends = [246, 462], bisect_right(ends, 0) = 0; starts = [40, 256], bisect_left(starts, 256) = 1. So only image A is in chunk 1.
  3. Chunk 2 starts at 256, the first token of B, which is an IMAGE id. Its 236 tokens fit the budget. bisect_right(ends, 256) = 1, bisect_left(starts, 492) = 2: only image B.

So each image goes to the ViT exactly once, in the chunk that holds all its tokens. The slicing code also handles the theoretical case that a chunk cuts an image, but the scheduler rule prevents it.

Which process decodes the JPEG bytes of an image?

The forked multimodal worker. The image processor returns a lazy ImageTensorLoader, and the mapper calls load() in the worker ({{cite deepinfer/ve/processor/image_processor.py:292-302}}, {{cite deepinfer/model_executor/models/deepseek_vl.py:81-89}}).

 What does TextLengthInput carry, and why not the text tokens?

Only a length. The engine already has the ids; the processor only needs to make mm_token_type zeros of that length ({{cite deepinfer/ve/processor/common.py:24-27}}, {{cite deepinfer/ve/processor/text_processor.py:10-13}}).

 When are the pool blocks of a request freed in the normal case?

In the step whose prefill covers all tokens of the sequence. defer_expiring_pool_handles takes them during preparation, and free_deferred_pool_handles frees them in pre_sampler_sync after the copy event ({{cite deepinfer/ve/schema.py:53-77}}, {{cite deepinfer/engine/llm_engine.py:118-119}}).

 In the worked example, why does chunk 1 end at token 255 and not at 299?

Position 300 is inside image B. The first sequence of a batch may grow to the image end (462), but that exceeds the budget of 300, so _adjust_chunk_size shrinks the chunk to the start of B at 256 ({{cite csrc/engine/scheduler.hpp:235-260}}, {{cite csrc/engine/scheduler.hpp:487-493}}).
