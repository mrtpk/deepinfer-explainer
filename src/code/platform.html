Purpose

platform.py holds every hardware choice in one object, and get_platform() makes the object for NVIDIA or Ascend once per process.

Filedeepinfer/platform.py, 227 lines of Python. It imports PyTorch only inside methods, never at the top ({{cite deepinfer/platform.py:1-11}}).
Main classesPlatform ({{cite deepinfer/platform.py:19}}), PlatformGPU ({{cite deepinfer/platform.py:55}}), PlatformNPU ({{cite deepinfer/platform.py:86}}). Also PlatformEnum and the function get_platform.
Runs inEvery process that reads deepinfer.PLATFORM: the engine process, context-parallel followers, image workers. One object per process.
Called byOnly deepinfer/__init__.py calls get_platform(). All other code reads from deepinfer import PLATFORM: 27 files at this commit.
Callsdeep_cluster.hardware.accelerator_kind, PyTorch, and on Ascend torch_npu, deepinfer.npu_ops and libascendcl.so through ctypes.
Not in this fileThe device detection ({{link code/deep-cluster}}), the kernel dispatch (tilelang_ops/ops.py), the import patches ({{link code/npu-ops}}), and the C++ build switch (setup.py).

The page {{link concepts/hardware-platforms}} explains the idea, the constructor of PlatformNPU line by line, and host-memory pinning. This page maps the file and its users.

Where it sits

Who calls it

  • deepinfer/__init__.py makes the object on the first read of deepinfer.PLATFORM, with a module-level __getattr__, and stores it as a module global ({{cite deepinfer/__init__.py:53-64}}).
  • Readers of PLATFORM. 27 files import it. The deep dive "Who reads which name" counts the uses. Examples: the kernel dispatcher ({{cite deepinfer/model_executor/layers/tilelang_ops/ops.py:15}}), the process groups ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:82-83}}), and the pinned buffer ({{cite deepinfer/shared_memory.py:119}}).

What it calls

  • accelerator_kind(), which reads device files and does not import PyTorch ({{cite deepinfer/platform.py:224-226}}).
  • On NVIDIA: torch.cuda.cudart() for cudaHostRegister, and dist.ProcessGroupNCCL.Options ({{cite deepinfer/platform.py:65-83}}).
  • On Ascend: torch_npu, torch_npu.contrib.transfer_to_npu, import deepinfer.npu_ops, and two ACL functions from libascendcl.so ({{cite deepinfer/platform.py:120-143}}, {{cite deepinfer/platform.py:169-184}}).

Walk through the main methods

The base class

  1. Lines 20-27: four names that each platform must set. Three are class attributes; fp8_sf_type is set in the constructor, because it needs PyTorch.
  2. Lines 29-35: is_gpu and is_npu compare the enum. Together, these two properties have the most reads (47 of 76; see the deep dive "Who reads which name").
  3. Lines 37-49: pinning is a no-op in the base class. The docstring says a platform without host-register support "falls back to pageable copies".
  4. Lines 51-52: get_distributed_options must be overridden.

PlatformGPU

  1. Lines 57-58: kernel folder cuda, backend nccl.
  2. Line 63: one int32 holds four UE8M0 scales.
  3. Lines 65-73: pin with cudaHostRegister(ptr, nbytes, 0). The return code is not checked.
  4. Lines 75-83: every NCCL group gets min_ctas = max_ctas = DEEPINFER_NCCL_NUM_SMS (default 32, {{cite deepinfer/environ.py:108}}).

The constructor does not check for a GPU. On a machine with no accelerator, get_platform() still makes a PlatformGPU, and the first CUDA call fails later.

On Ascend, the constructor imports torch_npu and patches PyTorch. The package comment says it "must happen only after ASCEND_RT_VISIBLE_DEVICES has been configured" ({{cite deepinfer/__init__.py:58-59}}). Set the visible devices before you import the engine.

PlatformNPU.__init__ (the end)

  1. Lines 130-131: two torch_npu settings.
  2. Line 136: NPU streams get a cuda_stream property, so CUDA-style code that reads stream.cuda_stream works.
  3. Line 138: one int16 holds two UE8M0 scales.
  4. Line 141: the import installs the import hook of {{link code/npu-ops}}.
  5. Line 143: load the ACL pin functions. A missing library or function stops start-up with RuntimeError.

Lines 92-128 set the visible devices and nine environment variables. The page {{link concepts/hardware-platforms#npu-init}} reads them one by one.

get_platform

@functools.cache makes the function return the same object on each call. The package also stores the object in its globals, so deepinfer.PLATFORM calls __getattr__ only once ({{cite deepinfer/__init__.py:62-64}}).

The TileLang kernel folder name is the only string that selects code by name. The page {{link concepts/tilelang-kernels}} will cover the kernels; in short, ops.py imports the subpackage cuda or asc from this name.

The platform is made at the first read of deepinfer.PLATFORM. Many modules read it at import time, with from deepinfer import PLATFORM at the top. One chain at engine import time: entrypoints/llm.py imports engine/llm_engine.py, which imports engine/profile_server.py ({{cite deepinfer/engine/llm_engine.py:35}}). That imports utils.py ({{cite deepinfer/engine/profile_server.py:33}}), which imports timer.py ({{cite deepinfer/utils.py:22}}), which reads PLATFORM ({{cite deepinfer/timer.py:13}}). We found this order by a static read of the import statements; we did not run it.

So in practice, import deepinfer.entrypoints.llm makes the platform. import deepinfer alone does not: the package file has no PyTorch import and makes no platform ({{cite deepinfer/__init__.py:1}}). The example scripts follow this rule. Their config module says, translated: "This module must not import deepinfer at the top level. The env setup must finish before deepinfer is imported, so create_llm imports deepinfer lazily inside the function" ({{cite examples/_config.py:5-6}}). They set the visible devices first, then import LLM ({{cite examples/_config.py:107-110}}).

The import hook depends on the same order. On Ascend, the constructor installs the npu_ops hook. A module that ran from deep_select.interface import topk before that keeps the vendor function. In the chain above, timer.py makes the platform before the model modules load. Nothing in the code checks this order. See {{link code/npu-ops}}.

What is PLATFORM.fp8_sf_type on NVIDIA and on Ascend?

torch.int32 on NVIDIA and torch.int16 on Ascend ({{cite deepinfer/platform.py:63}}, {{cite deepinfer/platform.py:138}}).

 Does import deepinfer make the platform?

No. The package makes it on the first read of deepinfer.PLATFORM, through __getattr__ ({{cite deepinfer/__init__.py:53-64}}).

 A machine has no GPU and no NPU. Which class does get_platform() return, and where does the first error come from?

accelerator_kind() returns "cpu", so get_platform() returns PlatformGPU ({{cite deepinfer/platform.py:226}}). Its constructor only sets the scale type, so no error comes from it. The first error comes later, from the first CUDA call.

 On Ascend, a script runs from deepinfer.model_executor.layers.sampler import Sampler as its first DeepInfer import. Which topk does the sampler module get, and why?

The vendor topk. sampler.py imports deep_select.interface.topk on line 12, before any line that reads PLATFORM. The first read comes later, through the import on line 16 ({{cite deepinfer/model_executor/layers/sampler.py:12-16}}). The hook is installed only in PlatformNPU.__init__ ({{cite deepinfer/platform.py:140-141}}), so it does not exist yet. In the normal engine start, timer.py makes the platform first ({{cite deepinfer/timer.py:13}}). This is the deep dive "When the platform is made".
