--- title: layers/sampler.py: the Sampler class nav_title: sampler.py level: Intermediate prerequisites: concepts/sampler, concepts/speculative-decoding related: concepts/sampler, concepts/speculative-decoding, concepts/dspark, concepts/structured-outputs, code/dflash, code/prepare-sample-cpp, code/model-runner, code/tilelang-ops, tours/spec-decode-round summary: sampler.py holds the Sampler module. It turns selected hidden states into float32 logits, samples prefill tokens, verifies draft tokens in decode steps and calls DFlash. sampler_utils.py holds the logits, sampling and prompt-logprob helpers. ---

Purpose

Sampler turns the hidden states of one engine step into new tokens: one per request in prefill, and an accepted draft prefix plus one token per request in decode.

The class docstring is in Chinese. It lists the core flow (translated): take the hidden states that need sampling, compute the logits, apply the logits processors, temperature and top-k/top-p, sample the output token, and optionally predict draft tokens with the nextn module for the next decode step ({{cite deepinfer/model_executor/layers/sampler.py:60-67}}).

Where it sits

Who calls it

  • ModelRunner.execute_sample builds SamplerInputs and calls model.sample inside forbid_cuda_sync() ({{cite deepinfer/worker/model_runner.py:348-365}}).
  • DeepseekForCausalLM.sample calls the sampler with the DFlash module, the LM head weight as embedding, and the KV caches for DFlash ({{cite deepinfer/model_executor/models/deepseek.py:391-399}}).
  • Worker.execute_model_step calls execute_sample after the forward pass and before pre_sampler_sync ({{cite deepinfer/worker/worker.py:154-164}}).

What it calls

  • Kernels and wrappers in tilelang_ops/: gather, prepare_verification_metadata, get_accept_result, finalize_verification, map_lookup, apply_token_bitmask_by_step_inplace, get_sum_smaller_probs ({{cite deepinfer/model_executor/layers/sampler.py:24-32}}). Through sampler_utils: fused_sample, expand_sampling_params, remap_draft_topk ({{cite deepinfer/model_executor/layers/sampler_utils.py:6-8}}).
  • Vendor code: topk from deep_select.interface ({{cite deepinfer/model_executor/layers/sampler.py:12}}), and the BF16 GEMM bf16_gemm_nt ({{cite deepinfer/model_executor/layers/sampler_utils.py:6}}).
  • Structured outputs: XGrammarUtils and allocate_vocab_mask ({{cite deepinfer/model_executor/layers/sampler.py:49}}).
  • The draft model: mtp_module.decode_forward ({{cite deepinfer/model_executor/layers/sampler.py:237-251}}). See {{link code/dflash}}.

forward, part 3: the decode path

The request met EOS; set the confidence of its next-round draft tokens to 0.
  1. Lines 225-233: _verification returns 8 values. The DFlash pool is passed in, because the verification reads the drafts of the previous step from it.
  2. Line 235: golden_tokens is the new token of each request (residual sample or bonus token).
  3. Lines 236-251: if the step has drafts, DFlash makes the next drafts. It starts after last_valid_offset accepted drafts.
  4. Lines 252-254: a request that emitted a stop token gets zero confidence for its next drafts.

Lines 258-299 start the CPU copies, keep device copies for ZOS, and build the SamplerOutput. The counters num_generated_tokens and num_verified_tokens are filled later by _decode_post_func, when the CPU values are ready ({{cite deepinfer/model_executor/layers/sampler.py:293-298}}).

_verification: sample, verify, finalize

The page {{link concepts/speculative-decoding}} reads lines 423-491 line by line. The second half collects the extra outputs and packs the results:

  3. Lines 511-515: the top logprobs of every row.
  4. Lines 519-536: finalize_verification makes the request results. The confidence inputs are passed only if the pool has confidences.

Without drafts (nextn = 0), lines 567-583 return the fresh samples directly, and last_valid_offset is all zeros.

The SamplerOutput fields are documented in {{cite deepinfer/sequence.py:171-269}}.
  • Main stream. All sampler kernels and the DFlash pass run on the current stream. A note in the docstring says that the MTP info pool has a read-after-write dependency across steps: the verification of step N reads what the DFlash graph wrote in step N−1, and the shared stream keeps the order ({{cite deepinfer/model_executor/layers/sampler.py:85}}).
  • Mask copy stream. _get_so_mask records an event on the main stream, makes the copy stream wait for it, copies the pinned masks, and records so_mask_ready. Then record_stream tells the allocator that the main stream uses these tensors ({{cite deepinfer/model_executor/layers/sampler.py:391-407}}).
  • No CPU wait. All copies to the CPU are non_blocking. The worker reads the values after sample_end_evt in a later call ({{cite deepinfer/worker/worker.py:167-168}}). The function execute_sample must not contain a CUDA synchronize ({{cite deepinfer/worker/model_runner.py:344-347}}).

Two requests, nextn = 5, force top-k 4096, no grammar, no golden tokens. Request 0 has seqlen_q = 6, request 1 has seqlen_q = 4 (DSpark cut it). Request 1 has top_logprobs = 4, request 0 has 0.

  1. total_q = R = 10. logits float32 [10, V]: with the inferred V = 129280, 5.17 MB.
  2. prepare_verification_metadata: row_to_req = [0×6, 1×4], is_verify false at rows 5 and 9.
  3. process_sampling: topk gives values [10, 4096] and token_index int32 [10, 4096]. The draft rows are remapped. fused_sample returns logprobs [10, 4096] and four tensors of shape [10].
  4. map_lookup turns the 10 column indices into vocabulary ids.
  5. get_accept_result: request 0 accepts 2 drafts, request 1 accepts 3 (all). is_final is true at rows 2 and 9.
  6. _prepare_top_info with k = max(0, 4) = 4: [10, 4] for every row, also for request 0.
  7. finalize_verification: last_valid_offset = [2, 3], sampled_token_ids [2], verified_token_ids [10] with 5 real ids and 5 times -1.
  8. DFlash: drafts [2, 5] and confidences [2, 5].

The CPU later appends 3 tokens to request 0 and 4 tokens to request 1.

In which two files is the sampler code, and which one holds the fused_sample call?

layers/sampler.py (the Sampler class) and layers/sampler_utils.py. process_sampling in sampler_utils.py calls fused_sample ({{cite deepinfer/model_executor/layers/sampler_utils.py:185-194}}).

 A follower rank of context parallelism calls Sampler.forward in a decode step. What does it run, and what does it return?

It gathers its rows and computes the logits, but does not use them. Then it runs DFlash.decode_forward without a driver input, and returns SamplerOutput(post_funcs=[]) ({{cite deepinfer/model_executor/layers/sampler.py:141-161}}). Inside DFlash, it gets the driver's new tokens by a broadcast ({{cite deepinfer/model_executor/models/mtp/dflash.py:358-365}}).

 Why does the decode path keep sampled_token_ids_gpu and num_accepted_tokens_gpu on the device?

With ZOS, the next step is scheduled before the CPU sees these values. The worker uses the device copies to fix the next step's inputs and seqlens_k without a sync ({{cite deepinfer/model_executor/layers/sampler.py:258-291}}, {{cite deepinfer/worker/worker.py:220-243}}).

 In the worked example, request 0 has top_logprobs = 0. Why does its row still get a top-logprob tensor of width 4?

max_top_logprobs is the maximum over all requests of the batch ({{cite csrc/engine/prepare_sample.cpp:157}}), and _prepare_top_info uses that one width for all rows ({{cite deepinfer/model_executor/layers/sampler.py:642-643}}). This is in the deep dive "Worked example".
