It makes one LLMEngine, adds every prompt as a request, calls step() until no data-parallel rank has work, clones the outputs, and returns token lists or decoded text. ---

Purpose

LLM is the class that a user script calls. It turns a list of prompts into a list of results, and hides the engine step loop.

Filedeepinfer/entrypoints/llm.py, 198 lines. The header says "Derived from vLLM; modified by DeepSeek." ({{cite deepinfer/entrypoints/llm.py:2}})
Main classLLM ({{cite deepinfer/entrypoints/llm.py:23}}). It is the only class in the file.
Runs inThe user's process. That process is also the engine process of one data-parallel rank, with the {{term driver-worker}} in it. The step loop runs on the calling thread, and generate() blocks until all requests end.
Called byUser scripts, examples/_config.py (create_llm), eval/run_eval.py.
CallsEngineArgs, LLMEngine, the Hugging Face tokenizer, RequestOutput.clone, tqdm.
Not in this fileBatching, scheduling, sampling (all in the engine). No streaming, no abort, no online server: the engine docstring says that this release has no online-serving wrapper ({{cite deepinfer/engine/llm_engine.py:140-141}}).

Where it sits

Panel 1 runs once per prompt and does no device work. Panel 2 is the loop. The flush runs only once, at the end.

Who calls it

  • The examples make the object in create_llm, with trust_remote_code=True, chunked_prefill=True, decode_sequence=False and statistics on ({{cite examples/_config.py:110-125}}). examples/offline_inference.py then calls generate ({{cite examples/offline_inference.py:95}}).
  • The eval script uses decode_sequence=False and passes token ids ({{cite eval/run_eval.py:189}}).
  • The benchmark uses the private method llm._add_request and then calls llm.llm_engine.step() itself ({{cite examples/benchmark.py:304-309}}, {{cite examples/benchmark.py:369}}).

What it calls

  • EngineArgs(...) and LLMEngine.from_engine_args ({{cite deepinfer/entrypoints/llm.py:70-84}}). See {{link code/llm-engine}}.
  • tokenizer.encode and tokenizer.decode ({{cite deepinfer/entrypoints/llm.py:156}}, {{cite deepinfer/entrypoints/llm.py:190}}).
  • LLMEngine.add_request, has_unfinished_requests, step, flush_inflight_reqs, get_num_unfinished_requests and close.
  • RequestOutput.clone from the C++ extension ({{cite deepinfer/entrypoints/llm.py:15}}). See {{link code/outputs-hpp}}.

Walk through the main methods

__init__: defaults that differ from the engine

  1. Lines 56-64: nine named arguments. All other arguments go through **kwargs to EngineArgs, for example max_model_len, max_num_seqs or chunked_prefill. An unknown name raises TypeError, because EngineArgs is a dataclass.
  2. Line 67: statistics logging is off, unless you pass disable_log_stats=False.
  3. Line 68: stop_preempted_request=False. The EngineArgs default is True ({{cite deepinfer/engine/arg_utils.py:40}}). So with LLM, a preempted request is computed again, not stopped (see {{link learn/kv-cache}}).
  4. Line 69: TOKENIZERS_PARALLELISM=false, unless the variable is already set.
  5. Line 79: offline_inference=True. The engine stores it ({{cite deepinfer/engine/llm_engine.py:195}}); no other line in the release reads it.
  6. Line 82: decode_sequence chooses the result type of generate() (text or outputs).

The docstring has a note in Chinese. Translated: "With CUDA graphs on, the error 'CUDA error: an illegal memory access was encountered' can mean that the CUDA graph ran out of memory. Lower gpu_memory_utilization and try again." ({{cite deepinfer/entrypoints/llm.py:50-51}}).

generate: the input rules

  1. Lines 117-118: you must give prompts, prompt_token_ids, or both.
  2. Lines 119-122: one string becomes a list of one. multi_modal_data is wrapped too, so pass one dict for one string.
  3. Lines 123-124: if you give both lists, they must have the same length. Then the token ids win; _add_request tokenizes only when the ids are None ({{cite deepinfer/entrypoints/llm.py:153-156}}).
  4. Lines 125-127: no settings means one SamplingParams() for all requests: temperature 1.0, 16 tokens ({{cite deepinfer/sampling_params.py:49-53}}).
  5. Line 138: one object for all, or a list with one object per prompt. The comment says, translated: "when the same SamplingParams is shared, no copy is needed here: _add_request does a deepcopy" (line 137).

_add_request: one request

HACK: add some user_id.
  1. Line 151: a deep copy, because the engine changes the object (it sets eos_id, see {{link code/sampling-params}}).
  2. Line 152: the request id is the next value of a counter that starts at 0, as a string. The counter lives in the LLM object, so a second generate() call goes on from the last id.
  3. Line 156: text goes through tokenizer.encode(prompt). With token ids, DeepInfer uses them as they are and adds no BOS token.
  4. Line 157: the engine needs a 1-D np.int32 array; the C++ Sequence refuses other types (see {{link code/engine-pyi}}).
  5. Lines 158-159: if the engine has an image processor and you gave no image data, the request gets an empty image dict. The only registered model is a vision-language model, so the NORMAL engine always has that processor ({{cite deepinfer/model_executor/models/__init__.py:15-17}}, {{cite deepinfer/engine/llm_engine.py:209-221}}).
  6. Line 160: the return value is a Sequence, or None for a dropped request. generate() ignores it.

_run_engine: the loop

Clone step_outputs, because step_outputs will be released in the next step.
  1. Line 171: the progress bar counts local unfinished requests at the start.
  2. Line 177: has_unfinished_requests() asks all data-parallel ranks with an all-reduce MAX, when there is more than one rank ({{cite deepinfer/engine/llm_engine.py:665-679}}). So this rank goes on while any rank has work.
  3. Line 178: work left: one engine step. No work left: one flush, which returns the outputs that the Worker still holds from the last ZOS decode step ({{cite deepinfer/worker/worker.py:274-283}}).
  4. Lines 179-182: every handle is cloned at once. The engine releases the pool objects at the next pre_sampler_sync ({{cite deepinfer/engine/llm_engine.py:830-831}}).
  5. Lines 185-186: the loop ends after the flush.
  6. Line 187: the request ids are sorted as integers, so "10" comes after "9".
  7. Lines 189-190: with decode_sequence=True, each request becomes one string: the decode of all its output token ids.

The result list has one entry per request id that produced an output (line 188). add_request drops a request with a bad token id and returns None ({{cite deepinfer/engine/llm_engine.py:582-589}}). That request gets no output, so the list is shorter, and later results move up by one. The docstring promises "the same order as the input prompts" (lines 113-115). Check that len(results) == len(prompts).

One output per token. Each RequestOutput holds one token ({{term request-output}}). A decode step with accepted drafts gives several outputs for one request (see {{link code/outputs-hpp}}). To get the token ids of request i: [o.token_id for o in results[i]], as line 190 does.

The table assumes one data-parallel rank and a multimodal worker that answers before the fetch() of call 70; else the prefill comes at call 101 (the ANY point). Real runs accept some drafts, so a decode step can give up to nextn + 1 = 6 tokens per request. The pattern stays: with ZOS, decode tokens arrive one call late, and the run ends with one or two calls that return nothing.

There are two seeds, and they do different things.

  • LLM(seed=0) goes to ModelConfig.seed. The Worker calls set_random_seed(seed + global_rank) for Python random, NumPy and PyTorch, at start-up and again after the memory profile and graph capture ({{cite deepinfer/worker/base.py:170-172}}, {{cite deepinfer/worker/base.py:194}}, {{cite deepinfer/worker/base.py:286-288}}, {{cite deepinfer/model_executor/utils.py:13-18}}).
  • SamplingParams(seq_seed=...) is the seed that the sampling kernels use for that request. Without it, the constructor takes 64 bits from Python random ({{cite deepinfer/sampling_params.py:86-88}}). The Worker runs in the same process, so a SamplingParams object made after LLM(...) takes its bits from the state that LLM(seed) set.

The seed is made in the constructor, and _add_request copies the object with copy.deepcopy, which does not run the constructor again (line 151). So if you pass one object (or none: then generate() makes one), every request gets the same seq_seed. Two requests with the same prompt then get the same random numbers, and they can give the same text. Pass a list of objects with different seeds if you need different samples, as eval/run_eval.py does ({{cite eval/run_eval.py:225-234}}).
  • One process per data-parallel rank. Each rank makes its own LLM. examples/_launch.py starts the processes ({{cite examples/_launch.py:35-44}}).
  • All ranks loop together. has_unfinished_requests() and the scheduler's votes are collective calls ({{cite deepinfer/engine/llm_engine.py:675-678}}). So a rank with no prompts also calls generate(), and runs empty steps until all ranks are done.
  • Context-parallel ranks are follower processes that the engine starts; LLM does not see them ({{cite deepinfer/engine/llm_engine.py:377-395}}).
  • Threads. generate() is not thread-safe: two threads would share one engine and one counter. Tokenization runs on the calling thread; TOKENIZERS_PARALLELISM=false turns off the tokenizer's own thread pool (line 69).

What does generate() return with the default decode_sequence=True, and with False?

True: one string per request, the decode of its output token ids. False: one list[RequestOutput] per request, one object per token ({{cite deepinfer/entrypoints/llm.py:187-190}}).

 Which defaults does LLM change compared with EngineArgs, and what is the effect of the second one?

disable_log_stats=True and stop_preempted_request=False ({{cite deepinfer/entrypoints/llm.py:67-68}}). With the second one, a preempted request goes back to the waiting queue and is computed again, instead of an early stop with insufficient_system_resource ({{cite csrc/engine/scheduler.hpp:771-788}}).

 Why does _run_engine call flush_inflight_reqs() after the last step()?

With ZOS, the Worker post-processes a decode step during the next call. When no work is left, the outputs of the last step are still in the Worker; the flush post-processes them ({{cite deepinfer/worker/worker.py:182-187}}, {{cite deepinfer/worker/worker.py:274-283}}).

 You call llm.generate(["Hi"] * 4) with no sampling parameters. Why can all four texts be the same?

generate() makes one SamplingParams(), which draws one random seq_seed in its constructor ({{cite deepinfer/entrypoints/llm.py:125-127}}, {{cite deepinfer/sampling_params.py:74}}). _add_request deep-copies that object for each request, so all four copies have the same seed (line 151). The sampler draws its random numbers from the seed and the position, so all four requests get the same numbers. If their logits are also equal, they get the same tokens. This is the deep dive "Seeds".
