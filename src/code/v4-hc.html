Purpose

These four files compute the {{term mhc}} mixes: they turn the [T, hc_mult, H] {{term mhc-trunk | trunk}} into one input for each {{term sub-layer}}, and write the sub-layer output back into the trunk.

Filesdeepinfer/model_executor/models/v4_modules/hc.py (397 lines), mhc_ops.py (148 lines), mhc_modeling.py (142 lines), hc_lazy.py (35 lines). Written for DeepInfer; no "Derived from vLLM" header. The weights are in hc_blocks.py (109 lines, a parameter container).
Main classesHCLayerMixin ({{cite deepinfer/model_executor/models/v4_modules/hc.py:57}}), HCHead ({{cite deepinfer/model_executor/models/v4_modules/hc.py:367}}), HCLazyPostData ({{cite deepinfer/model_executor/models/v4_modules/hc_lazy.py:15}}).
Runs inEvery worker process. All work is device kernels on the current stream. In decode it runs inside the CUDA graph of the model.
Called byDeepseekDecoderLayer and DFlashDecoderLayer (subclasses), DeepseekModel.forward and DFlash.forward_drafts (final post and fold), yoco.py (copies the lazy data).
Callstile_kernels.mhc.* kernels, deep_gemm.tf32_hc_prenorm_gemm, deep_gemm.mega_mhc, the sub-layer's RMSNorm, per_token_cast.
Not in these filesThe kernel code (pip packages and vendor libraries), the weight containers (hc_blocks.py, heads.py), the Engram hook body (engram.py), the layer body (decoder_layer.py).

Where it sits

Who calls it

  • The decoder layers. DeepseekDecoderLayer and DFlashDecoderLayer inherit from HCLayerMixin ({{cite deepinfer/model_executor/models/decoder_layer.py:48}}, {{cite deepinfer/model_executor/models/decoder_layer.py:178}}). Their forward calls attn_norm_forward and ffn_norm_forward ({{cite deepinfer/model_executor/models/decoder_layer.py:143}}, {{cite deepinfer/model_executor/models/decoder_layer.py:162}}).
  • The end of the model. DeepseekModel.forward calls the static HCLayerMixin.hc_post, then mhc_pre_apply_mix or HCHead ({{cite deepinfer/model_executor/models/deepseek.py:225-238}}). The DFlash draft model does the same ({{cite deepinfer/model_executor/models/mtp/dflash.py:258-264}}).
  • YOCO. gather_hc_lazy makes a compact copy of the lazy data at the compaction boundary ({{cite deepinfer/model_executor/models/v4_modules/yoco.py:79-90}}). This is why hc_lazy.py has no imports from the forward path ({{cite deepinfer/model_executor/models/v4_modules/hc_lazy.py:1-5}}).

What it calls

  • tile_kernels (a pip package): expand, post, apply mix, head mix, split mixes, Sinkhorn, the norm epilogues and the big fused pre ({{cite deepinfer/model_executor/models/v4_modules/mhc_ops.py:7-14}}, {{cite deepinfer/model_executor/models/v4_modules/mhc_modeling.py:11}}).
  • DeepGEMM (a vendor library): tf32_hc_prenorm_gemm ({{cite deepinfer/model_executor/models/v4_modules/mhc_ops.py:6}}) and mega_mhc ({{cite deepinfer/model_executor/models/v4_modules/hc.py:270}}).
  • The sub-layer norm. hc_modules.layer_norm is the RMSNorm of attention or of the MoE ({{cite deepinfer/model_executor/models/v4_modules/hc.py:359-363}}).

Walk through the main methods

HCLayerMixin.__init__

  1. Lines 73-74: a block without hc_mult is not an mHC model; the method returns early. In this release every block is a MoeDecoderBlockHC ({{cite deepinfer/model_executor/models/v4_modules/builder.py:63}}), which has hc_mult ({{cite deepinfer/model_executor/models/v4_modules/hc_blocks.py:86}}).
  2. Lines 83-88: reconstruct_param takes over the six float32 tensors of the container. The comment on line 90 says "Transfer ownership of HF's effective FP32 fn matrices bit-for-bit".
  3. Lines 91-92: the norm epsilon of the mix computation must be the same for attention and MoE.
  4. Line 94: hc_shifted comes from the block (see {{link concepts/mhc-residual}}, deep dive "Shifted mHC").
  5. Lines 99-101: the fused path needs a GPU, hc_mult == 4, and an fn width (4 × H) that is a multiple of 4 × 1024. So H must be a multiple of 1024.

attn_norm_forward and ffn_norm_forward

  1. Lines 125-131: with mHC on, the attention entry calls _hc_fused_post_pre with the attention weights and the optional Engram hook.
  2. Lines 133-139: without mHC, it is a plain pre-norm residual: the first layer keeps the input as the residual; later layers do "add + RMSNorm" in one call.
  3. Line 146: the FFN entry asks the MoE for cast arguments. A mega-MoE layer with FP8 activations returns its symmetric buffer, so the norm writes its FP8 output straight into that buffer ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:274-301}}). Other layers return {}.
  4. Lines 147-153: the FFN entry has no Engram hook.

All three return values are the same in both paths: the normed input (FP8 with scales, or BF16), a BF16 copy, and the new residual object.

_hc_fused_post_pre: five cases

  1. Lines 195-202 (case A): the fused path. It needs no Engram hook, a 2-D output of the previous sub-layer, and lazy data that still has its post mix.
  2. Lines 203-208 (case B): the first layer. expand_to_mhc makes the trunk from the embedding output; with hc_shifted a one-hot pre mix is added.
  3. Lines 209-212 (case C): the input is already a full trunk. The comment calls it "the nextn input". Shifted mHC does not allow it.
  4. Lines 213-219 (case D): the comment says a DFlash target layer "has already run post ahead of time and saved the full trunk". No code in this commit reaches this case: clear_post is never called, and every layer returns a 2-D output. See the deep dive "Lifetime of the lazy data".
  5. Lines 220-224 (case E): the normal case. Post first, then keep the pre mix of the previous sub-layer (only set when shifted), then release the old lazy data.
  6. Lines 225-227: the Engram hook changes the trunk after the post and before the pre. Then _hc_pre.

_hc_pre

  1. Line 324: the pre mix of the previous sub-layer must exist exactly when hc_shifted is on.
  2. Line 326: the kernels need a batch dim, so the trunk becomes [1, T, m, H].
  3. Lines 329-339: not shifted. One call to mhc_pre_big_fuse returns post [1, T, m, 1], residual mix [1, T, m, m] and the input [1, T, H]. No pre mix is kept (pre_layer_mix = None).
  4. Lines 343-358: shifted. Apply the old pre mix; compute the new mixes; split them; normalize the residual mix with Sinkhorn. The comment on line 347 says the HF fn "includes the norm weight", so the norm weight argument is None.
  5. Lines 359-363: the sub-layer's RMSNorm, with the cast arguments from ffn_norm_forward.
  6. Line 364: the new HCLazyPostData keeps the trunk before the sub-layer, plus the mixes. The next boundary uses it for the post.

_mega_mhc: one call for post + pre + norm

  1. Lines 246-250: unpack the lazy data (drop the batch dim) and release it.
  2. Lines 252-256: new outputs: trunk bf16 [T, m, H], pre mix (only when shifted) and post mix fp32 [T, m, 1], residual mix fp32 [T, m, m], input bf16 [T, H].
  3. Lines 259-263: mega-MoE: the FP8 output and its scales go into the MoE buffer. The shared-expert scales get their own layout.
  4. Lines 264-268: other FP8 consumers get a TMA column-major scale tensor. Line 267 pads the column length to a multiple of 4 int32 values (16 bytes).

Lines 270-298 pass all inputs, all weights (fn, mix_scales, mix_bases), all eps values, the Sinkhorn rounds and the RMSNorm weight to deep_gemm.mega_mhc. Lines 300-315 wrap the outputs as _hc_pre does.

HCHead and mhc_head

  1. Lines 56-59: the head fn has only m rows. It is padded with zero rows to m × (2 + m) "to reuse the pre_norm_fn kernel" (docstring, line 39).
  2. Line 61: the same GEMM + RMS epilogue as a sub-layer.
  3. Line 63: only the first m values are used.
  4. Line 67: mhc_head_compute_mix turns them into the fold weights, with scale [1] and base [m].
  5. Line 69: the weighted sum of the streams: [T, H].

HCHead.forward only adds and removes the batch dim around this call ({{cite deepinfer/model_executor/models/v4_modules/hc.py:386-397}}). HCHead refuses a shifted checkpoint ({{cite deepinfer/model_executor/models/v4_modules/hc.py:372-373}}).

mhc_pre_big_fuse

  1. Lines 90-104: the checks: BF16 trunk; FP32 fn [2m + m², m × H], scale [3], base [2m + m²].
  2. Lines 111-113: the outputs: post and residual mix in FP32, the layer input in BF16.
  3. Line 115: the prenorm GEMM with S split-K parts (16 on CUDA, 1 on Ascend).
  4. Lines 121-136: one kernel does the rest: add the parts, RMS, split, Sinkhorn, apply the pre mix.

  1. _hc_pre (or _mega_mhc) makes a new HCLazyPostData for each sub-layer. The decoder layer keeps it in the variable residual ({{cite deepinfer/model_executor/models/decoder_layer.py:143}}).
  2. The next boundary reads it and calls clear(), which sets all four fields to None ({{cite deepinfer/model_executor/models/v4_modules/hc.py:219}}, {{cite deepinfer/model_executor/models/v4_modules/hc.py:224}}, {{cite deepinfer/model_executor/models/v4_modules/hc.py:250}}). The comment says "To reduce memory footprint". After the call, the old object no longer holds the old trunk or the old mixes.
  3. After the last layer, hc_post reads it and does not clear it. With hc_shifted, the fold then reads its pre_layer_mix ({{cite deepinfer/model_executor/models/deepseek.py:227-230}}).

clear_post() keeps the pre mix and clears the rest ({{cite deepinfer/model_executor/models/v4_modules/hc_lazy.py:27-31}}). A search of the repo finds no call to it outside clear(). So case D of _hc_fused_post_pre (residual None, layer output 3-D) has no producer in this commit. The YOCO compaction asserts that "engram-cleared lazy data must not reach the compaction boundary" ({{cite deepinfer/model_executor/models/v4_modules/yoco.py:108}}), so the design expects such objects in some form.

Example sizes (not in the repo): T = 192, H = 4096, m = 4. The FLOP counter of the engine gives the terms ({{cite csrc/engine/flops_estimator.hpp:107-111}}):

PartPer tokenFor 192 tokens
prenorm GEMM [1, m·H] × [m·H, m(m+2)]16384 × 24 = 393,216 multiply-adds75.5 M
pre apply (m · H)16,3843.1 M
post (m · (m+1) · H)81,92015.7 M

Each layer has two boundaries. Memory: the input trunk is 192 × 4 × 4096 × 2 bytes = 6 MiB, and the post writes a new trunk of the same size. The mixes are small: 192 × 24 × 4 bytes = 18 KiB. So the boundary reads and writes mostly the trunk. The code joins the post and the next pre ({{cite deepinfer/model_executor/models/v4_modules/hc.py:62-64}}), but it does not say why. In the separate-kernel path, hc_post writes the new trunk and the kernels of _hc_pre read it again. mega_mhc gets the old trunk and returns the new trunk and the input in one call (lines 270-298). How the kernel reads memory is inside DeepGEMM, which is not in the repo.

The counter is an accounting model. It counts FP32 work with the TF32 weight: "Accounting reference, not actual kernel precision" ({{cite csrc/engine/flops_estimator.hpp:19}}).

Which method writes the output of the MoE sub-layer of layer 3 into the trunk?

_hc_fused_post_pre of layer 4 (case E calls hc_post, or case A calls mega_mhc) ({{cite deepinfer/model_executor/models/v4_modules/hc.py:195-202}}, {{cite deepinfer/model_executor/models/v4_modules/hc.py:220-224}}).

 A GPU model has hc_mult = 4 and H = 3072. Does it use mega_mhc?

Yes: fn has 4 × 3072 = 12288 columns, and 12288 % (4 × 1024) = 0 ({{cite deepinfer/model_executor/models/v4_modules/hc.py:99-101}}). The first layer still uses the separate kernels (case B), and an Engram layer uses them at its attention boundary.

 Why does the shifted path pass None as the norm weight to mhc_pre_norm_fn?

The HF fn already includes the norm weight ({{cite deepinfer/model_executor/models/v4_modules/hc.py:347}}). The loader even rejects a checkpoint with separate HC norm tensors ({{cite deepinfer/hugging_face/loading.py:39-41}}).

 How many bytes does one boundary read for the trunk with T = 192, H = 4096, m = 4, and why does the code join the post with the next pre?

6 MiB (192 × 4 × 4096 × 2). The code does not state the reason. The comment says only that the previous post and the next pre run back to back ({{cite deepinfer/model_executor/models/v4_modules/hc.py:62-64}}). On a GPU this lets one mega_mhc call do the post, the pre and the norm ({{cite deepinfer/model_executor/models/v4_modules/hc.py:236-238}}), so the new trunk does not go to a separate pre kernel. See the deep dive "Worked example: the work at one boundary".

 In this commit, which FP8 branch of _mega_mhc never runs, and why?

The branch for a 128 granularity (lines 311-314). get_fp8_casting_granularity() always returns 32 ({{cite deepinfer/model_executor/layers/linear.py:13-14}}), so an FP8 norm always takes the MXFP8 branch ({{cite deepinfer/model_executor/models/v4_modules/hc.py:264-268}}).
