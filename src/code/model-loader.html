Purpose

model_loader.py is the entry point for model loading. It finds the model class, completes the config, and guards the checkpoint load with checks and a watchdog.

Where it sits

The file has two roles. get_model is the top of the call chain. The other public functions are building blocks that DeepseekForCausalLM.load_model calls in a fixed order ({{cite deepinfer/model_executor/models/deepseek.py:457-510}}).

Who calls it

  • ModelRunner.load_model calls get_model(self.model_config, skip_load) ({{cite deepinfer/worker/model_runner.py:96-97}}). The engine starts this on all ranks with _run_workers("load_model", skip_load=load_format == "dummy") ({{cite deepinfer/engine/llm_engine.py:241}}).
  • DeepseekForCausalLM.load_model imports build_model_on_meta, finalize_model_config and load_hf_checkpoint ({{cite deepinfer/model_executor/models/deepseek.py:22-26}}).
  • LLMEngine.__init__ and MultimodalProcessor call the private _get_model_architecture to look at the model class ({{cite deepinfer/engine/llm_engine.py:209}}, {{cite deepinfer/ve/multimodal_processor.py:68}}).
  • examples/_ve_helper.py calls load_hf_checkpoint on a tree with only vision parameters ({{cite examples/_ve_helper.py:58-60}}).

What it calls

  • ModelRegistry.load_model_cls, which imports the module of the one registered architecture ({{cite deepinfer/model_executor/models/__init__.py:15-28}}).
  • resolve_num_extra_experts from eplb ({{cite deepinfer/model_executor/model_loader.py:19}}).
  • PG.expert_parallel_group() and PG.context_parallel_group() for the group sizes ({{cite deepinfer/model_executor/model_loader.py:116-120}}).
  • V41Builder and the HF functions model_params, validate_hf_shapes, load_covered_params. It imports them inside the functions ({{cite deepinfer/model_executor/model_loader.py:130}}, {{cite deepinfer/model_executor/model_loader.py:143}}).

get_model

  1. Line 69: find the class. With the only registered architecture, it is DeepseekVLForCausalLM.
  2. Line 70: two context managers. The default dtype becomes model_config.dtype, which is always torch.bfloat16 ({{cite deepinfer/config.py:75}}). New tensors go to "cuda" unless code names another device.
  3. Lines 71-75: the class method load_model does the real work.
  4. Lines 76-79: every parameter and every sf scale tensor of the result must be on the device. An AssertionError names the first one that is not.
  5. Line 80: eval mode, no gradients.

finalize_model_config and _configure_moe_redundancy

Set up the runtime environment that model construction needs, and write the parallel and runtime fields for inference into the loaded model_cfg. model_cfg was loaded by ModelConfig through load_model_config (HF config.json). Some runtime fields (runtime_max_model_len / max_num_seqs / max_num_batched_tokens / engine_type) were already written into model_cfg.gpt by ModelConfig; this function uses the inference process groups to complete the expert layout and the derived token limits.
  1. Line 117: the EP size is 1 if no EP group exists.
  2. Line 119: max_num_decoding_tokens = max_num_seqs × (1 + DEEPINFER_USE_NEXTN_DECODE). A decode step sends one new token and the drafts for each sequence.
  3. Line 120: max_num_prefilling_tokens = max_num_batched_tokens // cp_size. Context parallelism splits a prefill over the CP ranks.
  4. Lines 122-123: the extra-expert lower limit comes from the environment. _configure_moe_redundancy rounds it up.
{layout} DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS={min} was rounded up to {extra}, so that num_routed_experts={n} + num_extra_experts divides by ep_size={ep_size}.
  1. Lines 89-91: a model with no moe block keeps no extra experts. In this release, ModelMetadata requires the MoE block anyway ({{cite deepinfer/model_executor/model_metadata_utils.py:96-97}}).
  2. Line 94: resolve_num_extra_experts returns the smallest value at or above the limit that makes routed + extra divide by the EP size ({{cite deepinfer/model_executor/eplb/__init__.py:21-28}}).
  3. Lines 95-99: a warning if the value went up.
  4. Line 102: the result goes to moe.n_redundant_experts. FusedExperts reads it to size its slots ({{cite deepinfer/model_executor/models/v4_modules/moe.py:77-95}}).
  5. Lines 103-106: DFlash can have its own MoE settings. The function merges them over the main settings with the {{term attrdict}} + operator, so the count of DFlash experts decides the padding. The result goes into the DFlash override.

build_model_on_meta

Build the language parameter containers of the HF model on the meta device.

Inside torch.device("meta"), a new tensor gets a shape and a dtype but no memory. One exception: the vision encoder builds its RoPE tables on the device, because its constructor is not meta-safe ({{cite deepinfer/model_executor/models/v4_modules/containers.py:50-54}}).

Line 147 subtracts the coverage from the model parameters. It never subtracts the parameters from the checkpoint. A checkpoint tensor that the model does not use is not reported.

load_hf_checkpoint

HF checkpoint {hf_dir} does not cover {len(missing)} model parameters: {missing} HF load done: all {len(params)} model parameters come from {hf_dir}
  1. Line 145: model_params lists every parameter and every persistent buffer by its path ({{cite deepinfer/hugging_face/parameters.py:14-27}}).
  2. Lines 147-149: any parameter with no source stops the load with RuntimeError. The message lists all of them, sorted.
  3. Line 150: shapes and dtypes are compared with the safetensors headers only.
  4. Lines 151-152: the load itself runs under the watchdog.
  5. Line 153: the log line counts the model parameters, not the checkpoint tensors.

checkpoint_load_watchdog

Time-out protection for checkpoint loading. If the load does not finish within the given time, abort the process.

The watchdog thread waits on an Event. The finally block sets the event, so the thread also ends after an exception. If the wait times out, the thread logs an error and calls os.abort(). That kills the whole process with SIGABRT: no Python exception, no clean-up.

The token limits size buffers in the model: the MoE layer and Engram choose their maximum token count from them ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:173-175}}, {{cite deepinfer/model_executor/models/v4_modules/engram.py:94}}).

Assume max_num_seqs = 256, max_num_batched_tokens = 32768, CP size 2 and EP size 16. Also assume the default DEEPINFER_USE_NEXTN_DECODE = 5 ({{cite deepinfer/environ.py:129}}), 256 routed experts and a DFlash override with 64 routed experts. The expert counts and the batch values are examples, not values from the repo.

  1. max_num_decoding_tokens = 256 × (1 + 5) = 1536.
  2. max_num_prefilling_tokens = 32768 // 2 = 16384.
  3. With DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS=32: main -(256 + 32) % 16 = 0, so 32 extra, 288 slots, 18 per rank. DFlash -(64 + 32) % 16 = 0, so 32 extra, 96 slots, 6 per rank. No warning.
  4. With the variable not set (0): main 0 extra and 16 per rank; DFlash 0 extra and 4 per rank.
  5. With EP size 24 and the limit 32: main -(288) % 24 = 0, so 32; DFlash -(96) % 24 = 0, so 32. With EP size 20: main 44 (warning), DFlash -(96) % 20 = 4, so 36 (warning).
  • Each data-parallel rank is its own process with its own engine, and each one calls get_model.
  • Each context-parallel follower gets load_model from the driver by a CPU broadcast and runs it too ({{cite deepinfer/worker/base.py:296-302}}).
  • finalize_model_config reads the EP and CP group sizes (lines 116-120), so it must run after the worker makes the process groups in init_dist ({{cite deepinfer/worker/base.py:196}}). Its docstring says that it uses the inference process groups (lines 110-114). This explains why it runs in the worker and not in ModelConfig.
  • The watchdog is a daemon thread. It does not stop the process from exiting. It ends when the load ends or fails ({{cite deepinfer/model_executor/model_loader.py:57-62}}).
  • The watchdog covers only load_covered_params. The earlier steps, for example opening every shard in prepare_hf_coverage, have no time-out.

Which function in this file raises when a model parameter has no checkpoint tensor?

load_hf_checkpoint, with RuntimeError ({{cite deepinfer/model_executor/model_loader.py:147-149}}).

 What happens if loading the weights takes 31 minutes?

The watchdog thread logs an error and calls os.abort(), so the process stops at once ({{cite deepinfer/model_executor/model_loader.py:53-55}}).

 Why does finalize_model_config run inside the worker, and not when ModelConfig parses config.json?

It needs the sizes of the EP and CP process groups ({{cite deepinfer/model_executor/model_loader.py:116-120}}). These groups exist only after the worker starts the distributed environment.

 EP size 20, 256 main experts, 64 DFlash experts, DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS=32 (example values). How many expert slots does each rank hold for the main layers and for the DFlash layers, and how many warnings appear?

Main: -(256 + 32) % 20 = 12, so 44 extra, 300 slots, 15 per rank. DFlash: -(64 + 32) % 20 = 4, so 36 extra, 100 slots, 5 per rank. Both values are above 32, so two warnings appear, one for "backbone" and one for "DFlash" ({{cite deepinfer/model_executor/model_loader.py:93-106}}). This is the deep dive "Worked example".
