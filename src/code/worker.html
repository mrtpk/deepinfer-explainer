Purpose

Worker runs the device work of one engine step on one rank, in the order forward, post-process of the previous step, sample. With ZOS it keeps a decode step for the next call.

Filedeepinfer/worker/worker.py, 283 lines, and deepinfer/worker/zos_status.py, 40 lines. The header of worker.py says "Derived from vLLM; modified by DeepSeek." ({{cite deepinfer/worker/worker.py:2}})
Main classWorker(WorkerBase) ({{cite deepinfer/worker/worker.py:51}}). Also EngineCallbacks ({{cite deepinfer/worker/worker.py:43-48}}), _SeqlensCorrection ({{cite deepinfer/worker/worker.py:34-40}}), and in zos_status.py the dataclasses WorkerStepState and MetadataZOS.
Runs inThe driver worker runs in the engine process, in the main thread. Context-parallel followers run the same methods in their own processes.
Called byLLMEngine through run_workers: execute_model_step every step, flush_inflight_reqs at the end ({{cite deepinfer/engine/llm_engine.py:965-973}}, {{cite deepinfer/engine/llm_engine.py:979}}).
CallsModelRunner (forward, sample, post-process), the C++ functions prepare_zos_inputs and SchedulerOutputs.update_metadata_for_sampling_zos, two TileLang kernels, and the two engine callbacks.
Not in this fileStart-up, the model load and the KV cache: they are in the base class ({{link code/worker-base}}). Input tensors and the model call: {{link code/model-runner}}.

The class docstring gives the rule: "Every step runs the Forward-Post_process-Sample round in execute_model_step; under ZOS the post-process of a decode step is deferred to overlap with the next forward" ({{cite deepinfer/worker/worker.py:52-55}}).

Where it sits

The figure on {{link tours/engine-step}} shows the phases of one call in code order. This section lists the neighbours.

Who calls it

  • LLMEngine._init_workers makes the driver Worker with is_driver_worker=True and an EngineCallbacks object that holds post_process and pre_sampler_sync ({{cite deepinfer/engine/llm_engine.py:398-413}}).
  • _spawn_worker makes a follower Worker in each context-parallel process ({{cite deepinfer/engine/llm_engine.py:122-127}}). Its constructor never returns: it ends in the call loop of the base class ({{cite deepinfer/worker/base.py:120-123}}).
  • LLMEngine._execute_model_async_step calls execute_model_step every step ({{cite deepinfer/engine/llm_engine.py:961-975}}).
  • LLMEngine.flush_inflight_reqs calls flush_inflight_reqs ({{cite deepinfer/engine/llm_engine.py:977-982}}).

What it calls

  • ModelRunner.execute_main_model, execute_sample, post_process and _placeholder_seq_metadata ({{cite deepinfer/worker/worker.py:122-127}}, {{cite deepinfer/worker/worker.py:154-159}}, {{cite deepinfer/worker/worker.py:268}}).
  • C++: prepare_zos_inputs ({{cite deepinfer/worker/worker.py:209-211}}) and update_metadata_for_sampling_zos ({{cite deepinfer/worker/worker.py:150-152}}). See {{link code/zos-cpp}}.

Walk through the main methods

execute_model_step, part 1: correct and forward

  1. Lines 116-118: only the driver, and only for a real batch, computes total_q and the correction. A prefill sums seqlen_q; a decode step reads num_batched_tokens from the scheduler.
  2. Lines 121-124: launch the forward pass of step N. execute_main_model must not sync (its docstring, {{cite deepinfer/worker/model_runner.py:315-318}}).
  3. Lines 125-127: an empty batch still runs the model on one placeholder sequence (a {{term placeholder-step}}). The code gives no reason. This site infers that every rank must join the collective calls of the model.
  4. Lines 130-138: with DSpark, the driver keeps the timing events of the forward pass for the cost model of a decode step.
  5. Line 140: Movable wraps the model output, so that the sampler can take it and free it early.

execute_model_step, part 2: post-process N−1, sample N, keep N

3. Sample the current step (first correct the CPU metadata with the seqlens_q copied back from the device). 4. A prompt step, or a non-ZOS configuration: post-process at once. A ZOS decode step: keep it for the next step (to overlap with forward).
  1. Line 144: post-process the kept step. With no kept step, this returns an empty array.
  2. Lines 147-152: with a correction, wait for the copy event if there is one (DSpark only), then update the CPU metadata of step N.
  3. Line 154: launch the sampler of step N.
  4. Lines 162-165: the pre_sampler_sync callback (driver only) and the garbage collector run while the device samples.
  5. Lines 167-168: record sample_end_evt. It marks the end of all work queued so far in the stream.
  6. Lines 183-187: a prefill step, or any step with ZOS off, is post-processed at once and its outputs are added. A ZOS decode step is kept in prev_step_state.

With ZOS, an empty decode step is also kept. Its post-process passes no sampler output to the engine ({{cite deepinfer/engine/llm_engine.py:987}}), and the next correction skips it ({{cite deepinfer/worker/worker.py:199-200}}).

_correct_seqlens_qk

With ZOS, the CPU seqlens_q/k are one step behind: if the batch overlaps the previous batch, correct them on the GPU with the sampling results of the previous step.
  1. Lines 199-200: no kept step, or a kept placeholder: return None.
  2. Lines 203-207: the arrays need one row per CUDA graph padding row. Example: 3 sequences with 6 tokens each use the graph of 24, so n_seq_with_padding = 3 + 24 − 18 = 9.
  3. Lines 209-213: C++ builds the remap and the CPU lengths. No overlap: return None.
  4. Lines 214-216: non-blocking copies to the device. The source is {{term pinned-memory}}.
  5. Lines 218-219: DSpark only. A kernel splits the verification budget with the newest confidences of the kept step (see {{link concepts/dspark}}).
  6. Lines 220-227: the length kernel. It needs drafts, so it runs only with nextn > 0.
  7. Lines 230-234: DSpark only. Copy the new seqlens_q back into the same pinned array and record d2h_evt.
  8. Lines 236-244: the result for the input preparation of the model runner.

_post_process_step and flush_inflight_reqs

  1. Line 263: the wait for the end of the sampler of that step. With ZOS this is the event of step N−1.
  2. Line 266: the CUDA graph timer reads the times of finished graphs. The comment says that this does not touch the running graph.
  3. Line 268: ModelRunner.post_process runs the sampler's post_funcs and, for a prefill, the prompt log-probabilities ({{cite deepinfer/worker/model_runner.py:370-384}}).
  4. Lines 270-271: only the driver calls the engine. A follower returns an empty array.
  5. Lines 281-282: the flush post-processes the kept step and clears it. The docstring warns: "It may cause CPU-GPU synchronization" ({{cite deepinfer/worker/worker.py:276}}).

In which order does execute_model_step do its three main parts?

Forward of the current step, post-process of the previous step, sample of the current step ({{cite deepinfer/worker/worker.py:96-102}}).

 Why does Worker.__init__ set prev_step_state before it calls super().__init__()?

A follower worker enters start_slave_worker_loop inside the base constructor and never returns ({{cite deepinfer/worker/base.py:120-123}}). The loop calls methods such as execute_model_step, which read prev_step_state and nextn. The comment says so ({{cite deepinfer/worker/worker.py:70-74}}).

 A prefill step runs with ZOS on. Is it kept for the next call?

No. Line 183 post-processes a prompt step at once and sets prev_step_state = None ({{cite deepinfer/worker/worker.py:183-185}}). Only ZOS decode steps are kept.

 Three sequences with 6 query tokens each run with CUDA graphs of sizes 1, 2, 4, 8, 16, 24. How many rows do remap, seqlens_q and seqlens_k have, and which rows does the length kernel get?

total_q = 18, the selected graph has 24 tokens, so n_seq_with_padding = 3 + 24 − 18 = 9 ({{cite deepinfer/worker/worker.py:203-205}}). The kernel gets only the first n_seq = 3 rows ({{cite deepinfer/worker/worker.py:221-227}}); the 6 padding rows keep length 1 ({{cite csrc/engine/zos.cpp:190-194}}). See the deep dive "Data flow".
