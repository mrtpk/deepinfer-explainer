Purpose

parallel_state.py makes the {{term process-group | process groups}} of one {{term rank}} and keeps them in the global object PG, which all other code reads.

Where it sits

Panel 2 is the result of create_process_groups for dp_size = 4, cp_size = 2, ep_size = 8. The rest of this page shows how the file computes those lists.

Who calls it

  • _init_distributed_environment joins all ranks with a Gloo default group, then calls init_parallel_groups(dp_size, ep_size=..., cp_size=..., enp_size=...) ({{cite deepinfer/worker/base.py:315-344}}). Each Worker runs it in init_dist ({{cite deepinfer/worker/base.py:196-201}}).
  • Readers of PG. The engine reads the DP group for the votes ({{cite deepinfer/engine/llm_engine.py:313}}, {{cite deepinfer/engine/llm_engine.py:665-679}}). The model reads the CP group for mirror CP ({{cite deepinfer/model_executor/models/deepseek.py:168}}) and the EP group for MoE ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:192-194}}). The worker reads the world group to agree on the KV block count ({{cite deepinfer/worker/base.py:265-266}}) and the CPU CP group to send method calls ({{cite deepinfer/worker/base.py:298-300}}).
  • cp_broadcast_object is used by the worker loop ({{cite deepinfer/worker/base.py:132}}), broadcast_tensor_dict ({{cite deepinfer/model_executor/parallel_utils/communication_op.py:72-75}}) and InputMetadata.broadcast ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:153-156}}).
  • PG_dict is read by the NCCL memory statistics, which label each communicator with its group name ({{cite deepinfer/model_executor/parallel_utils/nccl_memory.py:26-34}}).

Walk through the main methods

create_process_groups: the rank lists

  1. Line 80: the rank list is 0 … max(enp_size, dp_size × cp_size) − 1. It is the world of this job.
  2. Lines 86-89: world is one group of all ranks. local has one group per rank (each rank alone).
  3. Line 92: DP groups. The pattern "(replica dp cp) -> (replica cp) dp" makes one group for each (replica, cp_rank) pair. Its members are the ranks with that cp_rank in each engine.
  4. Line 97: CP groups are blocks of cp_size neighbour ranks: the ranks of one engine.
  5. Lines 102-106: EP groups are blocks of ep_size neighbour ranks. If ep_size is the world size, the code reuses the world group object.
  6. Line 109: Engram groups are blocks of enp_size neighbour ranks.
  7. Lines 113-118: EP-in-DP groups use the same block rule as EP. With ep_size = 1, the code reuses local.
  8. Lines 94, 99, 118: Gloo copies of the DP, CP and EP-in-DP groups, for CPU tensors.
  9. Lines 123-124: with more than one CP rank, the CPU CP group gets a shared-memory queue: chunks of 1 << 20 bytes (1 MiB), 10 chunks.
  10. Line 126: start the device communicators (next section).

_split_group_cached calls dist.new_group for every rank list, also for lists that do not contain this rank ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:33-36}}). PyTorch requires that all processes call new_group for each group, in the same order. So all ranks must call create_process_groups with the same sizes.

_split_group_cached: one group per rank list, made once

The cache key is (rank lists, backend, options). The caller turns the lists into tuples, because the cache needs hashable keys (line 45). Inside one call of create_process_groups, the options object is the same for all device groups (line 83). So two splits with the same rank lists return the same group object. The deep dive shows where this happens.

cp_broadcast_object: objects from the CP driver

The writer of the queue is CP rank 0 (the default writer_rank, {{cite deepinfer/distributed/shm_broadcast.py:432-437}}). On rank 0, the function puts the object into the queue and returns it. On the other ranks, it waits for the next object and returns it. The call order must be the same on all CP ranks: the k-th call on a follower returns the object of the k-th call on the driver.

init_device_groups: start the communicators

After the default process group changed to the CPU (gloo) backend, the NCCL/HCCL subgroups lost their eager/split initialization. All of them are lazy: a collective must run once before the communicator really exists. Single-rank groups cannot be skipped either: Engram's deep_ep reuses the communicator made here through backend._comm_ptr(), and a null pointer gives a segmentation fault at once.
  1. Line 179: walk all attributes of the object, in the order of __init__: dp, cp, ep, ep_in_dp, enp, world, local, then the rest.
  2. Lines 180-184: skip everything that is not a NCCL or HCCL process group (the Gloo copies, the tag, the queue).
  3. Lines 185-187: run one all-reduce of a one-element tensor on each group object once. A group object that two attributes share runs once (the id check).

All ranks walk the same attribute order, so the collectives match.

init_parallel_groups: the entry point

The function makes a new object, stores it in PG_dict[tag], and for the default tag copies all its attributes into the global PG (line 227). Modules that ran from ... import PG before this call see the new groups, because PG is the same object. The log line lists the ranks, for example RANK 3, DP 1/4, CP 1/2, EP 3/8 (ep_in_dp:3), ENP 3/8, WORLD 3/8, GPU 1 for --ep 8 --cp 2 (lines 214-229). The ENP part appears because enp_size defaults to 8 here.

The small methods

  • is_within_nvl_domain(group): True on NPU. On GPU, True for a group of one rank, or if the group size is at most the NVLink domain size that DeepEP reports ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:130-134}}). The MoE layer uses it to choose mega-MoE ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:184-188}}).
  • cleanup_shm_broadcast(): closes the shared memory of the queue, and unlinks it on the rank that made it. The docstring gives the reason: "so that the resource_tracker won't report leaked shared_memory warnings" ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:161-169}}). WorkerBase.stop calls it ({{cite deepinfer/worker/base.py:147}}).

A search of the repository for ep_in_dp and cpu_ep_in_dp outside this file finds no reader. The NCCL memory statistics see them only as names of groups.

dp = max(1, 8 // 2) = 4 ({{cite deepinfer/config.py:161-162}}). enp defaults to cp × dp = 8 ({{cite deepinfer/config.py:172}}). So ranks = [0 … 7], and rank r is engine r // 2, CP rank r % 2.

So init_device_groups runs only four all-reduces on rank 3: dp, cp, W and local. The Gloo copies are three more splits (DP, CP and EP-in-DP), with backend="gloo" and no options. Each split calls new_group once per rank list.

With --ep 2 --dp 8: ep is [[0,1],[2,3],[4,5],[6,7]], and ep_in_dp has the same lists. The cache returns the ep object for ep_in_dp, because the key (lists, backend, options) is the same.

With a larger Engram group (for example dp = 2, cp = 1, enp = 4): the world has 4 ranks, and replica = 2. The DP groups are [0, 1] and [2, 3]: two separate DP worlds that share one Engram group [0..3].
  • Who runs it. Every rank process, once. In a CP engine, the driver and each follower run it inside their own Worker.__init__ ({{cite deepinfer/worker/base.py:114-118}}).
  • Order of collectives. Each new_group call, the queue handshake and the warm-up all-reduces are collectives. They run in program order, the same on all ranks.
  • The queue handshake. create_from_process_group broadcasts a handle object over the Gloo CP group and then waits until all readers connected ({{cite deepinfer/distributed/shm_broadcast.py:446-461}}).
  • The device tensor. The warm-up uses torch.zeros(1).cuda() ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:187}}). On Ascend, torch.cuda is mapped to torch.npu ({{link concepts/hardware-platforms}}).
  • Several tags. init_parallel_groups can make extra group sets with another tag. Only the default tag goes into PG. In this release, only the worker calls it, with the default tag ({{cite deepinfer/worker/base.py:343}}).

Does DeepInfer have a tensor-parallel group?

No. ParallelProcessGroup has dp, cp, ep, ep_in_dp, enp, world and local, and three Gloo copies ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:52-65}}). There is no TP or PP group.

 Which backend do the CPU groups use, and which group carries the method calls from the CP driver?

Gloo. The method calls go through the shared-memory queue that is set up on cpu_cp_group ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:99}}, {{cite deepinfer/model_executor/parallel_utils/parallel_state.py:123-124}}).

 With dp_size = 2 and cp_size = 4, what are the DP groups and the CP groups?

Ranks 0..7. CP: (dp cp) -> dp cp gives [0, 1, 2, 3] and [4, 5, 6, 7]. DP: (replica dp cp) -> (replica cp) dp gives [0, 4], [1, 5], [2, 6] and [3, 7] ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:92-98}}).

 Why does init_device_groups run an all-reduce on the local group, which has only one rank?

The default process group is Gloo, so the NCCL/HCCL subgroups start lazily; a collective must run once to make the communicator. The translated docstring says that single-rank groups cannot be skipped: Engram's deep_ep reuses the communicator through backend._comm_ptr(), and a null pointer gives a segmentation fault ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:174-176}}).

 In a run with --ep 8 --cp 1 (8 ranks), are PG.ep, PG.enp and PG.world three groups or one?

One object. ep_size equals the rank count, so ep = world (line 103). enp_size defaults to 8, so the Engram split is [[0..7]] with the same backend and options as the world split, and _split_group_cached returns the cached world group ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:26-37}}, {{cite deepinfer/config.py:172}}). init_device_groups warms it up once, because of the id check.
