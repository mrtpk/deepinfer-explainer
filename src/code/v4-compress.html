Compressor turns the projected KV of a C1 or C2 layer into compressed entries, stores them in ca_cache and returns the pre-RoPE vector for the indexer. KProject is the indexer's key projection of that vector. ---

Purpose

compress.py makes the compressed cache entries of one layer: it mixes the token pairs of a C2 layer, then normalizes, rotates, casts and stores each entry.

Where it sits

Who calls it

  • V4Attention._init_compressor_and_indexer makes one Compressor per KV-source layer with compressed KV, from the container attn_module.PackedWkv ({{cite deepinfer/model_executor/models/v4_modules/attn.py:345-347}}).
  • V4Attention._store_main_kv calls forward_store_kv_cache with the projected KV, ca_cache and ca_state. It asks for pre_rope_kv only when the layer has its own indexer ({{cite deepinfer/model_executor/models/v4_modules/attn.py:509-523}}). This happens in the normal path and in the YOCO full-KV path ({{cite deepinfer/model_executor/models/v4_modules/attn.py:546}}, {{cite deepinfer/model_executor/models/v4_modules/attn.py:584}}, {{cite deepinfer/model_executor/models/v4_modules/attn.py:708}}).
  • MQA.__init__ makes a KProject in index-K source layers ({{cite deepinfer/model_executor/models/v4_modules/index_attn.py:91-94}}). MQA.store_index_kv calls forward_pre_norm and reads norm ({{cite deepinfer/model_executor/models/v4_modules/index_attn.py:144-145}}).

No code in the repo calls Compressor.forward or KProject.forward; the callers use the other methods.

What it calls

  • Compression kernels in layers/tilelang_ops/compress.py: one for prefill, one for decode ({{cite deepinfer/model_executor/models/v4_modules/compress.py:16-19}}). ops.py picks the CUDA or Ascend version.
  • The fused transform fused_norm_rope_hadamard_cast_store_kvcache ({{cite deepinfer/model_executor/models/v4_modules/compress.py:20-26}}). This file passes no Hadamard arguments.
  • Helpers: gather for the CP reorder, get_kv_cache_format, convert_rmsnorm, ReplicatedLinear ({{cite deepinfer/model_executor/models/v4_modules/compress.py:11-29}}).

In decode, pre_rope_kv has one row per query token; rows where no entry ends are zero rows. The index-K store sends them to slot −1, so nothing is written for them.

One sequence at positions 1,000 … 1,005 (1 token + 5 drafts), FP4 cache, state_id 7.

  1. projected_kv is fp32 [6, 1024]; score and latent are [6, 512].
  2. The decode kernel writes each token into state slot (context_len − 1) % 7: positions 1,000 … 1,005 go to slots 6, 0, 1, 2, 3, 4 ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:227-232}}).
  3. Positions 1,001, 1,003 and 1,005 end a pair. Their rows of kv_compressed get the mix of (1,000, 1,001), (1,002, 1,003) and (1,004, 1,005); the other rows are zero ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:236-248}}).
  4. C++ (or the ZOS device kernel) gave positions_c = [0, 1000, 0, 1002, 0, 1004] and slots −1 for the even positions ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:79-91}}).
  5. The fused kernel writes 3 entries of 288 B: entries 500, 501 and 502 of the sequence, at block_table[500 / 64] × 64 + 500 % 64 and the next two rows.

Which layers have a Compressor?

Layers with compressed KV that are KV sources ({{cite deepinfer/model_executor/models/v4_modules/attn.py:345-346}}). SWA-only layers and share-KV consumers have none.

 What is pre_rope_kv, and who asks for it?

The entry after the RMSNorm and before RoPE, bf16 [rows, 512] ({{cite deepinfer/model_executor/models/v4_modules/compress.py:159-167}}). A layer with its own indexer asks for it (return_pre_rope_kv=self.has_local_index, {{cite deepinfer/model_executor/models/v4_modules/attn.py:522}}); KProject projects it to the index keys.

 How does forward_store_kv_cache know whether to write FP4 or FP8 entries?

It does not get a flag. get_kv_cache_format reads the last dimension of ca_cache: 288 means FP4, 528 means FP8 ({{cite deepinfer/model_executor/models/v4_modules/compress.py:147}}, {{cite deepinfer/model_executor/layers/tilelang_ops/cache_common.py:171-187}}).

 In a decode step at positions 1,000 … 1,005, which rows of kv_compressed are not zero, and what are the matching positions_c?

The rows of positions 1,001, 1,003 and 1,005, because they end a pair ({{cite deepinfer/model_executor/layers/tilelang_ops/compress.py:236-248}}). Their positions_c are 1,000, 1,002 and 1,004: the first token of each pair ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:82-86}}). See the deep dive "Worked example".
