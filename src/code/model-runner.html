It builds the input metadata, runs the forward pass (eager or as a CUDA graph replay), prepares the sampler inputs, runs the memory profile and captures the graphs. ---

Purpose

ModelRunner is the layer between the Worker and the model: for each step it turns the scheduled sequences into device inputs, starts the forward pass and the sampler, and it does the start-up work for memory profiling and {{term cuda-graph}} capture.

Who calls it

  • WorkerBase.__init__ makes the runner with the block size of the cache ({{cite deepinfer/worker/base.py:90-96}}).
  • Start-up: load_model ({{cite deepinfer/worker/base.py:207}}), profile_run inside profile_num_available_blocks ({{cite deepinfer/worker/base.py:222-225}}), then capture_model, profile_decode_perf and capture_dflash_model inside warm_up_model ({{cite deepinfer/worker/base.py:274-285}}).
  • Each step: Worker.execute_model_step calls execute_main_model and execute_sample ({{cite deepinfer/worker/worker.py:121-159}}), and later post_process ({{cite deepinfer/worker/worker.py:268}}). For a {{term placeholder-step}} it first asks for _placeholder_seq_metadata ({{cite deepinfer/worker/worker.py:126-127}}).
  • Shutdown: WorkerBase.stop calls destroy_cuda_graphs ({{cite deepinfer/worker/base.py:142-146}}).

Walk through the main methods

__init__: graphs on or off

  1. Line 73: graphs are on unless DEEPINFER_ENFORCE_EAGER is set or the engine is a PROMPT engine.
  2. Line 77: the largest graph has max_num_seqs × (1 + nextn) rows.
  3. Line 78: with {{term zos}}, the graph inputs live on the device.
  4. Lines 80-85: DFlash graphs need main graphs, nextn > 0, a dflash_cfg and no DEEPINFER_DFLASH_ENFORCE_EAGER.

load_model: sizes and the YOCO keep guard

With YOCO truncation on, start-up stops with AssertionError unless window_size + DEEPINFER_MAX_BACKTRACKING_TOKENS ≤ DEEPINFER_YOCO_PREFILL_KEEP_TOKENS. With a window of 128 and 6 backtracking tokens, the minimum is 134. The README value is 140 ({{cite README.md:25}}).

 Models without a window size can have (-1, -1) here. Keep the three-state mode; later code checks separately if truncation is on and if the compact layout is used. ModelMetadata already makes sure that the model has YoCo consumer layers when truncation is on. The truncation length must be at least window_size + backtracking, so that after a rollback the decoder still has a full window of SWA. The 64 here is an alignment requirement. self.block_size is the token count before compression.
  1. Lines 98-99: only the driver of a non-PROMPT engine makes the {{term mtp-info-pool}} of the draft model.
  2. Lines 101-102: the window size comes from the model config. The ring size is window + DEEPINFER_MAX_BACKTRACKING_TOKENS, plus extra rows when DEEPINFER_PREFILL_STORE_EXTRA_STATE is on ({{cite deepinfer/worker/cache_engine.py:88-110}}).
  3. Lines 107-113: the YOCO guard. C++ checks the same rule again in each prefill ({{cite csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:355-357}}).
  4. Line 115: the width of a decode block table. With runtime_max_model_len = 32784: ⌈32784 / 128⌉ = 257, rounded up to 320.

_prepare_input_tensors

The dict from C++ becomes the keyword arguments of the metadata class: InputMetadataV4, or InputMetadataV4VL for a vision model ({{cite deepinfer/model_executor/model_metadata_utils.py:142-144}}). num_reqs is the number of sequences, with padding when the caller added it. On the graph path the caller passes out_dict, and the function returns None.

_prepare_input_driver: graph or eager

The helper _graph_input_metadata sets the real request count. Its comment says, translated: "The real request count, without padding. It must match the sampler inputs, which have no padding. It is in input_metadata because with CP only the driver has the sampling inputs." ({{cite deepinfer/worker/model_runner.py:164-169}}).

  1. Line 180: total_q is the sum of seqlen_q, unless the Worker passes it. For a decode step the driver Worker passes scheduler_outputs.num_batched_tokens ({{cite deepinfer/worker/worker.py:117}}).
  2. Line 182: a graph runs for a decode step when graphs are on and captured.
  3. Lines 185-191: select the graph, add graph_size − total_q padding sequences, and let the builder write into the graph's source buffers. Then set the real request count on the device object.
  4. Lines 194-198: the eager path builds a new object and copies every tensor to the device without a wait.
  5. Lines 200-212: with CP above 1, broadcast a small dict. Only an eager step also sends all tensor fields, flattened to one dict level.

_prepare_input_follower

Pop only the keys that are not InputMetadata fields; is_prompt, total_q and num_reqs are fields themselves and stay for from_flatten_dict.

A follower selects the same graph from total_q. The tensor values reach its graph buffers inside the replay: the recorded InputMetadata.broadcast() copies them from rank 0 ({{cite deepinfer/worker/cuda_graph_runner.py:64-65}}).

execute_main_model

  1. Line 319: build the input (driver) or receive it (follower).
  2. Lines 321-325: two timers and the {{term sync-guard}}. The CPU timer name contains the request count and the row count, for example launch_forward_N2_B12.
  3. Lines 326-329: replay or eager call. Both return at once; the device works in the background.

prepare_sampler_inputs and execute_sample

Compact mode computes the prefill sample positions from the truncated output size; mask and off keep the full layout. The sampler runs after CP, so CP is invisible to it. Decode always uses the full layout, so it passes off.

The driver passes the real sequence list, without graph padding. So the sampler reads only real rows. With CP, the followers get the row indices and build a SamplerInputs without the driver part ({{cite deepinfer/worker/model_runner.py:260-275}}). execute_sample then calls self.model.sample(...) inside the sync guard. It passes kv_caches only when nextn > 0, because the draft model needs the cache ({{cite deepinfer/worker/model_runner.py:348-365}}).

post_process

The sampler leaves work that needs finished device results in post_funcs. The Worker calls post_process after it waits for the sample event ({{cite deepinfer/worker/worker.py:262-268}}). For a prefill step, the driver converts the prompt log-probabilities in C++ (update_prompt_logprobs).

profile_run: the memory profile

Engram's compressed tokenizer cannot handle meaningless tokens; the valid range is [0, len(tokenizer)). Run the profile on a small real KV cache, to count the memory of the cache read and write kernels. The allocation uses cuMemAlloc, which torch does not count, and it is freed when the function returns, so it does not change the block count of profile_num_available_blocks. It is zeroed because the full gather of chunked prefill reads cache areas that nobody wrote; zeros make sure the values read are finite. allocate_gpu_cache also writes bytes_per_block, num_state_seqs and bytes_of_state_per_seqs into cache_config, with the same values as the real allocation (only num_gpu_blocks is different).
  1. Line 448: a NORMAL engine profiles a prefill batch; only a COMPLETION engine profiles a decode batch.
  2. Line 452: the lengths come from _build_prompt_profile_seq_lens (deep dive).
  3. Line 476: each sequence gets its own blocks, in order, so the profile cache has exactly the blocks it needs.
  4. Lines 505-507: a temporary CacheEngine with these blocks, filled with zeros.
  5. Lines 510-512: the run uses a forced MoE imbalance of 1.8, so the profile sees a bad expert load. Then the value goes back to 0.0.

Capture and destroy

capture_model passes _prepare_input_tensors and a decode placeholder to the graph runner ({{cite deepinfer/worker/model_runner.py:514-529}}). capture_dflash_model needs the main graphs and reuses their pool and stream ({{cite deepinfer/worker/model_runner.py:538-549}}). destroy_cuda_graphs frees both runners; its docstring explains that NCCL inside graphs holds extra resources that block the destruction of the process group ({{cite deepinfer/worker/model_runner.py:633-644}}). The page {{link code/cuda-graph-runner}} reads the runners line by line.

 If DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K is set, run the profile with sum seqlen_k as close as possible to it.
  1. Lines 407-409: split max_num_batched_tokens evenly over max_num_seqs sequences for seqlen_q.
  2. Line 414: the first sequence gets the longest possible seqlen_k, runtime_max_model_len.
  3. Lines 417-439: with DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K set, the other sequences grow until the sum of seqlen_k hits the limit (clamped between the minimum and max_num_seqs × runtime_max_model_len).

Example A, the settings of examples/offline_inference.py (max_num_seqs=4, max_num_batched_tokens=32768, {{cite examples/offline_inference.py:52-54}}) and runtime_max_model_len = 32784: seqlen_q = [8192, 8192, 8192, 8192], seqlen_k = [32784, 8192, 8192, 8192]. Blocks: ⌈32784/128⌉ + 3 × 64 = 257 + 192 = 449.

Example B, the same with DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K=65536: the minimum sum is 57360, so 8176 tokens remain. The loop adds 2726, 2725 and 2725: seqlen_k = [32784, 10918, 10917, 10917], sum 65536.

The prefill sequences use top_p=0.99 and top_logprobs=20 ({{cite deepinfer/worker/model_runner.py:484}}), so the profile also counts the memory of the log-probability path. Each sequence gets its own MTP write slot seq_id + 1, unlike padding, which uses slot 0 ({{cite deepinfer/worker/model_runner.py:491-492}}).

Which method of ModelRunner does the Worker call to start the forward pass, and does it wait for the device?

execute_main_model ({{cite deepinfer/worker/worker.py:122}}). It does not wait: the docstring says it "must NOT contain any cuda synchronize", and the launch runs inside forbid_cuda_sync() ({{cite deepinfer/worker/model_runner.py:315-324}}).

 You set DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact and DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=128, with a window of 128 and the default backtracking. What happens?

Start-up stops in load_model with AssertionError: 128 + 6 = 134 > 128 ({{cite deepinfer/worker/model_runner.py:107-113}}). The default backtracking is at least nextn + 1 = 6 ({{cite deepinfer/environ.py:132}}).

 On the graph path, the device buffers have 16 rows but only 2 real sequences. Where does the model find the real count, and why is it stored in the input metadata?

_graph_input_metadata sets input_metadata.num_reqs to the real count ({{cite deepinfer/worker/model_runner.py:164-169}}). The comment says that with CP only the driver has the sampling inputs, so the count must travel in the metadata.

 With max_num_seqs=4, max_num_batched_tokens=32768, runtime_max_model_len=32784 and DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K=65536, what seqlen_k values does the profile batch use, and how many KV blocks does the temporary cache get?

[32784, 10918, 10917, 10917] (deep dive "The profile batch"; {{cite deepinfer/worker/model_runner.py:405-441}}). Blocks: ⌈32784/128⌉ + ⌈10918/128⌉ + 2 × ⌈10917/128⌉ = 257 + 86 + 86 + 86 = 515 ({{cite deepinfer/worker/model_runner.py:476}}).
