--- title: v4_modules/attn.py: the MLA attention runtime nav_title: v4_modules/attn.py level: Advanced prerequisites: concepts/mla-attention, concepts/sparse-attention-indexer related: concepts/mla-attention, concepts/sparse-attention-indexer, concepts/sliding-window-attention, concepts/kv-compression, concepts/cross-layer-kv-sharing, concepts/yoco-swa-replay, code/v4-mla-attn, code/v4-index-attn, code/v4-compress, code/decoder-layer summary: attn.py turns the MLA weight container into runtime weights and runs one attention layer per call: projections, sliding-window and compressed KV stores, the indexer, the FlashMLA kernel and the output projection. It also holds the DFlash draft attention. ---

Purpose

attn.py runs one attention layer: it makes Q and the KV vectors, writes them to the caches, gets the key list, calls FlashMLA, and projects the result back to the hidden size.

The module docstring sums it up: V4AttentionBase holds the shared projection, norm and RoPE plumbing; V4Attention adds compressed KV, sparse index, sliding window, YOCO and cross-layer paths; DFlashAttention serves the draft model ({{cite deepinfer/model_executor/models/v4_modules/attn.py:1-7}}).

Where it sits

Who calls it

  • DeepseekDecoderLayer.__init__ makes one V4Attention per main layer ({{cite deepinfer/model_executor/models/decoder_layer.py:85}}). Its forward calls it with the FP8 and BF16 hidden states and the cross-layer runtime ({{cite deepinfer/model_executor/models/decoder_layer.py:154-161}}).
  • DFlashDecoderLayer makes a DFlashAttention and calls update_main_cache and forward_drafts ({{cite deepinfer/model_executor/models/decoder_layer.py:190-195}}, {{cite deepinfer/model_executor/models/decoder_layer.py:216-236}}).
  • DeepseekForCausalLM.allocate_userbuffer asks each layer for get_max_ag_bytes_per_token() ({{cite deepinfer/model_executor/models/deepseek.py:429-430}}).

What it calls

  • Attention kernels: prefill_attn_varlen_sparse and decode_mla_mqa_sparse ({{cite deepinfer/model_executor/models/v4_modules/attn.py:20-23}}), which call FlashMLA. The fused FlashMLA module fused_norm_rope_attn_rope_cast also permutes weights at start-up ({{cite deepinfer/model_executor/models/v4_modules/attn.py:14}}).
  • GEMMs: ReplicatedLinear for the projections; deep_gemm.fp8_einsum for the grouped Wv ({{cite deepinfer/model_executor/models/v4_modules/attn.py:215-221}}).
  • TileLang interface kernels: fused_norm_rope_hadamard_cast_store_kvcache, gather, kv_index_cat, load_paged_kv_cache, store_kv_cache ({{cite deepinfer/model_executor/models/v4_modules/attn.py:29-39}}). None of the calls here passes Hadamard arguments.
  • Sub-modules: Compressor ({{cite deepinfer/model_executor/models/v4_modules/attn.py:346}}) and MQA ({{cite deepinfer/model_executor/models/v4_modules/attn.py:355-362}}).

Walk through the main methods

V4AttentionBase.__init__: the flags

  1. Line 85: a layer is sparse when its config has index_topk above 0.
  2. Line 86: has_packed_kv: the layer has compressed KV (ratio 1 or 2).
  3. Lines 87-92: the fused FlashMLA path. The comment says it is "disabled in dense packed-KV decoding".
  4. Lines 93-96: a layer needs the sliding window, or compressed KV, or both. A sparse layer needs the window.

_init_compressor_and_indexer: who owns what

  1. Only a KV-source layer has a Compressor (line 346). In a YOCO consumer, its weights go into a separate projection of the shared hidden state (lines 349-350).
  2. Only a layer with its own indexer has an MQA (line 355). Its weights_proj joins the projection of the current hidden state (line 364).
  3. Lines 368-371: the joined projection gives fp32 output for C2 and bf16 for C1. The Compressor asserts these dtypes ({{cite deepinfer/model_executor/models/v4_modules/compress.py:89-95}}).

forward, part 1: inputs and projections

  1. Lines 764-765: compute_attn_info expands compact index fields of the metadata into the index lists that the kernels need. It does nothing when they exist already.
  2. Line 768: one GEMM for the compressor input and the indexer weights.
  3. Lines 769-780: YOCO paths: in compact prefill, the full-context KV is written first (line 774); else a YOCO KV source projects the shared hidden state (line 780).
  4. Line 785: with CP, the all-gather of the compressor input starts now and overlaps with the Q projection.
  5. Lines 787-799: Q, the SWA vector, its FP8 store or cast, and the query up-projection.
  6. Lines 802-809: store the compressed KV and get the compressed-key list (next method).

_compute_kv_ca_index: three sources of the key list

  1. Lines 553-567: the layer has its own indexer: call MQA, which returns [T, index_topk].
  2. Lines 568-578: a sparse layer that shares the indexer of an earlier layer reuses cross_layer_runtime.topk_indices.
  3. Line 580: a dense compressed layer reads all its compressed keys: input_metadata.kv_ca_index[ratio].
  4. Lines 583-584: without a local indexer, the compressed KV is stored late, to overlap with the CP all-gather. With an indexer it was stored earlier (line 546), because the indexer needs pre_rope_kv.

forward, part 2: the prefill buffer

  1. Lines 814-818: the buffer sizes. total_k_swa = number of sequences × window ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:272-273}}).
  2. Lines 825-830: copy the current SWA vectors into the middle part (with CP: gather them into it).
  3. Lines 834-842: load the compressed KV from ca_cache as BF16 into the last part. A share-KV consumer skips the load and reuses the buffer of its source.
  4. Lines 847-855: load the SWA history into the first part, then store the new SWA vectors. The comment explains the order: the store slots can overlap the loaded range.

forward, part 3: kernel and output

_prefill_attention joins the SWA index and the compressed-key list with kv_index_cat and calls prefill_attn_varlen_sparse ({{cite deepinfer/model_executor/models/v4_modules/attn.py:603-625}}). _decode_attention passes swa_cache and ca_cache with their index lists to decode_mla_mqa_sparse ({{cite deepinfer/model_executor/models/v4_modules/attn.py:640-669}}). The page {{link concepts/mla-attention}} reads these calls in detail.

DFlashAttention.forward_drafts

The draft attention has no compressed KV and no indexer. It writes the draft keys into its own swa_cache slots. The comment says they "live for one decode step and are overwritten by the next step" (line 975). Then it calls the decode kernel with dflash_kv_index and the scheduler metadata key "DFlash". See {{link code/dflash}}.

A prefill step with two sequences in a C2 layer. The window is 128 (the value in the deployment notes, {{cite doc/inference_deployment_qa.md:191}}; the code reads it from the config).

  • Sequence A: a new prompt of 1,000 tokens.
  • Sequence B: a later chunk of 300 tokens, after 2,048 cached tokens.
  1. total_k_swa_cached = 2 × 128 = 256 rows. A has no history, so its rows are zeros (src_block_id = −1 zero-fills, {{cite deepinfer/model_executor/input_metadata/input_metadata.py:268-271}}).
  2. total_k_swa_cur = 1,000 + 300 = 1,300 rows.
  3. total_k_compressed["2"] ≈ 1,000 / 2 + 2,348 / 2 = 500 + 1,174 = 1,674 rows. The new entries are stored before the load, so the load includes them. The real value can be a little larger: it includes padding ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:278-279}}).
  4. total_kv ≈ 256 + 1,300 + 1,674 = 3,230 rows. In BF16: 3,230 × 512 × 2 B ≈ 3.3 MB.

A query of B reads its row of kv_index: 128 window positions, then up to topk positions in the compressed part. kv_index_cat adds total_k_swa_cached + total_k_swa_cur = 1,556 to each compressed index ({{cite deepinfer/model_executor/layers/tilelang_ops/kv_index_cat.py:24}}).

Which two FlashMLA wrappers does V4Attention call, and when?

prefill_attn_varlen_sparse in prefill and decode_mla_mqa_sparse in decode ({{cite deepinfer/model_executor/models/v4_modules/attn.py:859-877}}).

 A sparse layer shares the indexer of an earlier layer. Which code path gives it its key list?

has_local_index is false and is_sparse is true, so _compute_kv_ca_index takes cross_layer_runtime.topk_indices, written by the index source ({{cite deepinfer/model_executor/models/v4_modules/attn.py:568-570}}, {{cite deepinfer/model_executor/models/v4_modules/attn.py:585-586}}).

 In prefill, why does the code store the new SWA vectors only after it loads the SWA history?

The store slots of the ring can overlap the range that the load reads. A store first would overwrite history that the prefill still needs ({{cite deepinfer/model_executor/models/v4_modules/attn.py:854-855}}).

 Two sequences in a C2 prefill: 1,000 new tokens, and 300 new tokens after 2,048 cached ones. Window 128. About how many rows does the buffer kv have, and what offset does kv_index_cat add to a compressed index?

256 SWA history rows + 1,300 current rows + about 1,674 compressed rows ≈ 3,230. The offset is 256 + 1,300 = 1,556 ({{cite deepinfer/model_executor/models/v4_modules/attn.py:814-818}}, {{cite deepinfer/model_executor/layers/tilelang_ops/kv_index_cat.py:24}}).
