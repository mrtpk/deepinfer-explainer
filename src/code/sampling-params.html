Purpose

SamplingParams holds the settings of one request: how to choose each token, when to stop, and which extra values to return.

Where it sits

Who calls it

  • User scripts make one object per request, or one for all. Example: the eval script sets temperature, top-p, max_tokens and a fixed seq_seed per sample ({{cite eval/run_eval.py:225-234}}).
  • LLM.generate makes SamplingParams() when you pass none ({{cite deepinfer/entrypoints/llm.py:125-127}}). _add_request deep-copies the object for each request ({{cite deepinfer/entrypoints/llm.py:151}}).
  • LLMEngine.add_request also accepts a dict. It drops keys with the value None and calls the constructor ({{cite deepinfer/engine/llm_engine.py:521-526}}).
  • The model runner uses SamplingParams(temperature=0.0) for placeholder metadata and SamplingParams(top_p=0.99, top_logprobs=20) in the profile run ({{cite deepinfer/worker/model_runner.py:396}}, {{cite deepinfer/worker/model_runner.py:484}}).

Who reads the values

  • The C++ Sequence constructor copies 9 values into SamplingScalars and 2 into StoppingCriteria ({{cite csrc/engine/sequence.hpp:280-281}}).
  • LLMEngine.add_request reads golden_token_ids, so_args and prompt_logprobs in Python ({{cite deepinfer/engine/llm_engine.py:529-537}}, {{cite deepinfer/engine/llm_engine.py:562}}, {{cite deepinfer/engine/llm_engine.py:607}}).

Order of the work in __init__

  1. Line 63: drop logprobs.
  2. Lines 65-73: store the values; a max_tokens of 0 becomes 1.
  3. Line 74: make the seed (see below).
  4. Line 75: _verify_args() checks the ranges. It runs before the temperature clamp, so it sees the values that you gave.
  5. Lines 76-79: a temperature below SAMPLING_EPS becomes 1e-5, and top_p = 1.0, top_k = -1.
  6. Lines 80-83: store the four fields that have no check.

The engine has no separate greedy path. Temperature 0 becomes 1e-5. The sampler still makes a seeded draw from a very sharp distribution (see {{link concepts/sampler}}). Your top_p and top_k are replaced, but they must still pass the checks: SamplingParams(temperature=0, top_k=0) raises.

_make_seed: the seed rules

  1. Line 88: no seed gives 64 random bits from Python's random module. So two runs give different tokens, unless you pass a seed or seed the random module.
  2. Line 90: an int is masked to 64 bits. A negative seed is valid: -1 becomes 18,446,744,073,709,551,615. True is an int in Python, so it gives seed 1.
  3. Line 91: any other type raises TypeError() with an empty message. A NumPy integer is not a Python int, so np.int64(7) raises too.

Because of the mask, the range check on seq_seed at lines 104-105 can never fail.

so_args: the grammar dict

The docstring describes the keys in Chinese ({{cite deepinfer/sampling_params.py:39-43}}). Translated and split into a list:

  • "schema_type" and "schema": the grammar.
  • Optional "trigger_token_ids" (one list[int]): the token sequence that turns the grammar on. Before the full sequence appears, the output is free.
  • Optional "bound_token_id": a non-negative integer; 0 is valid. Missing or None means no bound. A list is not valid. It needs a non-empty trigger_token_ids.
  • When the bound is active, free tokens are no longer allowed. The output first follows the trigger sequence token by token, then enters the grammar.

The class does not check the dict. The grammar builder checks it in build(), and then compiles the grammar on a thread pool ({{cite deepinfer/structure_output/so_matcher_builder.py:58-95}}):

  • "serialized" raises ValueError (offline use needs schema_type and schema). "bound_token_ids" (plural) raises ValueError ({{cite deepinfer/structure_output/so_matcher_builder.py:60-63}}).
  • A bad trigger or bound does not raise: the builder returns an aborted matcher ({{cite deepinfer/structure_output/so_matcher_builder.py:71-76}}). When the request goes into the queue, it gets the status FINISHED_SO_FAILED ({{cite deepinfer/engine/llm_engine.py:620-623}}), and the scheduler ends it without a prefill ({{cite csrc/engine/scheduler.hpp:363-367}}).

The page {{link concepts/structured-outputs}} explains the grammar matcher. examples/benchmark.py shows a regex example: {"schema_type": "regex", "schema": r"Hello, my name is [a-z]+"} ({{cite examples/benchmark.py:280}}).

What the engine changes after the constructor

  1. Line 527: eos_id always becomes the tokenizer's EOS id. The docstring calls the field a "HACK" with default 0 "only for warm up phase" ({{cite deepinfer/sampling_params.py:36-38}}). So a value that you set has no effect through add_request.
  2. Lines 529-537: with DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE not off, prompt_logprobs becomes False, with a warning in the log.

The engine changes the object that it gets. LLM passes a deep copy, so your object stays as it was. A direct caller of LLMEngine.add_request sees its own object change.

__repr__

The text form shows 9 of the 13 fields ({{cite deepinfer/sampling_params.py:107-119}}). It leaves out first_n_token_no_eos, eos_id and golden_token_ids. logprobs is not stored, so it cannot show.

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

  1. Once, in the Sequence constructor. C++ reads attributes by name from the Python object: and max_tokens and ignore_eos into StoppingCriteria ({{cite csrc/engine/sequence.hpp:181-190}}). The Python object stays in the sequence as generation.params, but C++ never reads these numbers from it again.
  2. Each step, in the metadata. Each SequenceMetadata copies the SamplingScalars struct ({{cite csrc/engine/sequence.hpp:380}}).
  3. Each step, in prepare_sampler_inputs. The function fills one entry per sequence in pinned CPU tensors: temperatures and top_ps as float32, top_ks as int32, seq_seeds as uint64 ({{cite csrc/engine/prepare_sample.cpp:82-88}}, {{cite csrc/engine/prepare_sample.cpp:157-161}}). max_top_logprobs is the largest top_logprobs of the batch (line 157).
  4. EOS rules. In a prefill, a sequence with first_n_token_no_eos == 1 in its last prompt chunk adds a row and its eos_id to the suppression list ({{cite csrc/engine/prepare_sample.cpp:20-22}}, {{cite csrc/engine/prepare_sample.cpp:192-195}}). In a decode with drafts, stop_token_ids[i] = [eos_id, -1], or [-1, -1] with ignore_eos ({{cite csrc/engine/prepare_sample.cpp:217-219}}).
  5. Prompt logprobs. With prompt_logprobs, the prompt rows get the same temperature, top-p and top-k ({{cite csrc/engine/prepare_sample.cpp:181-189}}).
  6. To the device. All arrays go to the device with non_blocking=True ({{cite csrc/engine/prepare_sample.cpp:257-264}}).
  7. Stop check. After the step, the scheduler stops a sequence on EOS (unless ignore_eos), at max_model_len, or at max_tokens output tokens ({{cite csrc/engine/scheduler.hpp:1035-1052}}).

Worked example. R1 has temperature=0.6, top_p=0.95, seq_seed=7. R2 has temperature=0 and no seed. In one decode step: temperatures = [0.6, 1e-5], top_ps = [0.95, 1.0], top_ks = [-1, -1], seq_seeds = [7, <64 random bits>]. Note that 0.6 as float32 is 0.60000002384.
  • Memory reserve. add_sequence reserves room in the token vector for max_tokens more tokens ({{cite csrc/engine/sequence.hpp:286-289}}, {{cite csrc/engine/scheduler.hpp:135-141}}). It also reserves the block table for (len + max_tokens) / 128 + 1 blocks ({{cite csrc/engine/scheduler.hpp:189-192}}). These are host-memory reserves, not KV blocks.
  • Batch planning. The default of 16 tokens is short. Benchmarks set max_tokens=1 for prefill-only requests ({{cite examples/benchmark.py:283}}).
  • The other limit. max_model_len also stops a sequence, with the same reason "length" ({{cite csrc/engine/scheduler.hpp:1043-1045}}, {{cite csrc/engine/sequence.hpp:49-50}}).

What are the defaults of temperature, top_p, top_k and max_tokens?

1.0, 1.0, -1 (off) and 16 ({{cite deepinfer/sampling_params.py:49-53}}).

 You write SamplingParams(temperature=0, top_p=0.5, top_k=40). Which values does the sampler get?

Temperature 1e-5, top-p 1.0, top-k -1. The checks pass first (0 ≥ 0, 0.5 in range, 40 in range), then lines 76-79 replace the three values ({{cite deepinfer/sampling_params.py:75-79}}).

 You set eos_id=42 and call LLM.generate. Which EOS id does the request use?

The tokenizer's EOS id. add_request sets sampling_params.eos_id = self.eos_id for every request ({{cite deepinfer/engine/llm_engine.py:527}}, {{cite deepinfer/engine/llm_engine.py:225}}).

 After add_request, a script sets seq.sampling_params.temperature = 2.0. Does the next step sample with temperature 2.0?

No. The C++ Sequence copied the value into SamplingScalars in its constructor ({{cite csrc/engine/sequence.hpp:280}}, {{cite csrc/engine/sequence.hpp:105}}). SequenceMetadata and prepare_sampler_inputs read that copy ({{cite csrc/engine/sequence.hpp:380}}, {{cite csrc/engine/prepare_sample.cpp:158}}).
