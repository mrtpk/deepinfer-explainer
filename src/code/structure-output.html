XGrammarCompiler compiles a grammar, XGrammarMatcher follows one request with trigger, bound and rollback, SOMatcherBuilder compiles on a pinned thread pool, and mask.py connects the sampler to the TileLang bitmask kernel. ---

Purpose

The package turns so_args into a {{term grammar-matcher}} for each request, and gives the sampler the functions that make and apply {{term token-bitmask | token bitmasks}}.

Where it sits

Who calls it

  • LLMEngine.so_matcher_builder, a property, makes the builder on first use with the tokenizer, the vocabulary size, the EOS id and the pinned cores ({{cite deepinfer/engine/llm_engine.py:329-342}}).
  • LLMEngine.add_request calls submit, or build(...).result() when enqueue=False ({{cite deepinfer/engine/llm_engine.py:606-630}}).
  • LLMEngine.pre_sampler_sync calls pump() once per step ({{cite deepinfer/engine/llm_engine.py:841-842}}). get_num_unfinished_requests and has_unfinished_requests count pending builds ({{cite deepinfer/engine/llm_engine.py:658-663}}, {{cite deepinfer/engine/llm_engine.py:673-674}}). close() calls shutdown() ({{cite deepinfer/engine/llm_engine.py:357-361}}).
  • Sampler imports XGrammarUtils and allocate_vocab_mask ({{cite deepinfer/model_executor/layers/sampler.py:49}}) and calls accept_token, constrained, fill_vocab_mask, rollback and set_aborted on the matcher ({{cite deepinfer/model_executor/layers/sampler.py:347-386}}).
  • C++ Scheduler::fork_seq calls copy_without_status() through pybind11 ({{cite csrc/engine/scheduler.hpp:1097-1100}}).
  • examples/benchmark.py calls pump() in a loop until no build is pending ({{cite examples/benchmark.py:311-313}}).

What it calls

  • xgrammar. TokenizerInfo.from_huggingface ({{cite deepinfer/structure_output/so_matcher_builder.py:29}}), GrammarCompiler and its three compile functions ({{cite deepinfer/structure_output/compiler.py:34-39}}, {{cite deepinfer/structure_output/compiler.py:56-61}}), GrammarMatcher ({{cite deepinfer/structure_output/matcher.py:83}}), and get_bitmask_shape, bitmask_dtype, _FULL_MASK ({{cite deepinfer/structure_output/matcher.py:14}}). This site does not explain xgrammar internals.
  • The TileLang kernel through apply_token_bitmask_by_step_inplace ({{cite deepinfer/structure_output/mask.py:5-7}}, {{cite deepinfer/structure_output/mask.py:33}}).
  • The OS. os.sched_setaffinity pins each pool thread ({{cite deepinfer/structure_output/so_matcher_builder.py:40}}).

Walk through the main methods

XGrammarCompiler.__init__: the cache

  1. Line 17 (comment): xgrammar 0.1.x and older had production incidents with the cache on; the variable stays as a kill switch.
  2. Lines 18-19: two settings from the environment: DEEPINFER_XGRAMMAR_DISABLE_CACHE and DEEPINFER_XGRAMMAR_CACHE_LIMIT_BYTES (default 10 GiB, {{cite deepinfer/environ.py:169-170}}).
  3. Lines 23-29: for a limit of 0 or less, the code logs a warning: the cache then has no size limit and can grow with many schemas.
  4. Lines 34-39: the xgrammar compiler gets the tokenizer info, the cache settings and max_threads (2, from the builder).

SOMatcherBuilder.build: checks, then a task

  1. Lines 60-63: "serialized" and "bound_token_ids" raise ValueError on the engine thread. The caller of add_request sees it.
  2. Line 64: a missing "schema" key raises KeyError here, too.
  3. Lines 71-76: a bad trigger or bound does not raise. A finished Future holds an aborted matcher.
  4. Lines 78-92: the task, which runs on a pool thread: compile, make the matcher, then replay old tokens. No caller in this release passes replay_tokens.
  5. Line 79: schema_type is read only inside the task, so a missing schema_type gives an aborted matcher, not an exception. Line 94 submits the task to the pool.

SOMatcherBuilder.pump: hand over ready matchers

Poll the pending list. Take each sequence whose matcher is compiled out of the list, and put it into scheduling with on_ready. Non-blocking. On timeout it returns an aborted matcher.
  1. Line 111: an empty list returns at once. This is the common case.
  2. Lines 115-118: try_result() returns None while the build runs; the entry stays.
  3. Lines 119-120: a matcher (good or aborted) goes to the sequence, and on_ready runs. In the engine, on_ready is _enqueue ({{cite deepinfer/engine/llm_engine.py:620-625}}).

XGrammarMatcher.accept_token: three phases

  1. Lines 135-153: the trigger is not complete. With a fired bound (lines 136-140), only the next trigger token is accepted. Without a bound (lines 141-148), every token is accepted and KMP updates the progress. Lines 149-152 count tokens after the bound, or start the count at the bound token.
  2. Lines 154-156: after EOS every token is accepted. This happens when a draft is EOS: the sampler still accepts the later drafts to fill their masks ({{cite deepinfer/model_executor/layers/sampler.py:367-373}}).
  3. Lines 158-168: the grammar phase. xgrammar decides. An accepted EOS starts tokens_after_eos; the assert at line 166 guards against a second EOS.
  4. Lines 170-174: an xgrammar error that mentions "regarded as a special token" means "reject"; other errors are logged and raised again. The sampler catches them ({{cite deepinfer/model_executor/layers/sampler.py:377-386}}).

XGrammarMatcher.fill_vocab_mask and rollback

  1. Lines 183-187: forced phase. The row is set to zero, and only the bit of the expected trigger token is set: word expected >> 5, bit expected & 31.
  2. Lines 189-191: after EOS, the row is the full mask.
  3. Line 193: else xgrammar fills the row.
  4. Lines 196-199: the error !IsStopTokenAccepted() returns False. The sampler asserts on False ({{cite deepinfer/model_executor/layers/sampler.py:362-363}}).
  5. Lines 207-216: rollback removes tokens after EOS first.
  6. Lines 218-221: then tokens in xgrammar, at most tokens_in_matcher.
  7. Lines 223-230: then the trigger progress from the history. Too deep a rollback raises RuntimeError.

XGrammarMatcherFuture.try_result: the timeout

  1. Line 325: the task finished. _resolve reads the result; an exception in the task becomes an aborted matcher (lines 328-331).
  2. Lines 332-335: the task still runs, but the time from the creation of the future is above DEEPINFER_XGRAMMAR_TIMEOUT (default 20 s, {{cite deepinfer/environ.py:168}}). The result is an aborted matcher. The task keeps its thread until it ends.
  3. Line 337: _log_abort logs the message once, at debug level ({{cite deepinfer/structure_output/matcher.py:288-291}}).

mask.py: a thin layer for the sampler

Lazy import: this module is in the import closure of the sampler. A top-level import would pull xgrammar into deployments that do not use SO. A so_status check comes before every real call, so only SO requests trigger it.

Line 32 asserts that the index tensor is on the logits device and is int32. The kernel itself is described on {{link concepts/structured-outputs}}.

mask_after_eos costs one mask row per request: with V = 129,280 (the kernel benchmark value, {{cite deepinfer/model_executor/layers/tilelang_ops/structure_output.py:106}}), 4,040 int32 = 16,160 bytes.
  • Pool threads. max_workers = len(idle_cpus), which is DEEPINFER_SO_BUILDER_CPUS (default 4) ({{cite deepinfer/engine/llm_engine.py:334-340}}, {{cite deepinfer/utils.py:154-161}}). The initializer pins each thread with sched_setaffinity(0, …); 0 means the calling thread ({{cite deepinfer/structure_output/so_matcher_builder.py:37-41}}).
  • The compiler is made on a pool thread with num_threads=2, and the engine waits for it once ({{cite deepinfer/structure_output/so_matcher_builder.py:49}}).
  • The engine thread calls submit and pump. Translated comment: "submit and pump are both called on the main thread; the worker thread only fills the future and does not touch the seq or the scheduling logic" ({{cite deepinfer/structure_output/so_matcher_builder.py:50}}).
  • The matcher is used only on the engine thread of CP rank 0, inside the sampler. The sampler fills the masks before it calls get_logits ({{cite deepinfer/model_executor/layers/sampler.py:135-142}}).
  • Shutdown. close() stops the pool and the compiler on purpose. Translated: "Shut down the thread pool and the compiler actively; with only GC, nanobind reports a leak at atexit" ({{cite deepinfer/engine/llm_engine.py:357-361}}).
  1. Step 0: add_request(so_args={"schema_type": "regex", "schema": "[A-Z]{2}-[0-9]{3}"}). submit adds a pending entry. The scheduler does not know the request yet.
  2. The pool thread compiles the regex and makes the matcher.
  3. Each step, pump() runs in pre_sampler_sync. The first pump() after the build ends calls _enqueue: the sequence enters the waiting queue with so_status = 0.
  4. At a prefill attempt point, the prompt runs. On the last prompt chunk the engine sets so_status = 1 ({{cite deepinfer/engine/llm_engine.py:913-915}}).
  5. The sampler sees status 1: no token to accept. It sets status 2 and fills mask 0 from the start state. Only tokens whose text can start the pattern are allowed, for example A or AB.
  6. The mask kernel changes the logits row of the prefill, so the first output token fits the start of the pattern. process_outputs stores status 2 ({{cite csrc/engine/scheduler.hpp:928-929}}).
  7. Next decode step: the matcher accepts that token, fills mask 0 for the next part of the pattern and masks for the drafts, then rolls back.

On which thread does a grammar compile, and on which thread does pump() run?

The compile runs on a builder pool thread ({{cite deepinfer/structure_output/so_matcher_builder.py:94}}). pump() runs on the engine thread, in pre_sampler_sync ({{cite deepinfer/engine/llm_engine.py:841-842}}).

 A caller passes {"schema": "...", "bound_token_ids": [5]}. What happens, and how is it different from {"schema": "...", "schema_type": "regex", "bound_token_id": 5} without a trigger?

The first raises ValueError from add_request ({{cite deepinfer/structure_output/so_matcher_builder.py:62-63}}). The second passes the key checks but fails validate_trigger_bound ("bound_token_id requires non-empty trigger_token_ids"), so the request gets an aborted matcher and ends with FINISHED_SO_FAILED without a prefill ({{cite deepinfer/structure_output/matcher.py:54-55}}, {{cite deepinfer/structure_output/so_matcher_builder.py:71-76}}).

 In the forced phase, the expected trigger token is 70. Which word and bit of the mask row does fill_vocab_mask set?

Word 70 >> 5 = 2, bit 70 & 31 = 6; all other bits are 0 ({{cite deepinfer/structure_output/matcher.py:185-186}}).

 The trigger is [9, 4] with no bound. The matcher has accepted 9, 4, x (x accepted by the grammar). The sampler now calls rollback(2). What are tokens_in_matcher and trigger_progress after it?

Before the rollback: tokens_in_matcher = 1 (only x went to xgrammar), and the history holds the progress values recorded before each token: [0, 1, 2] ({{cite deepinfer/structure_output/matcher.py:127-132}}). rollback(2) rolls back min(2, 1) = 1 token in xgrammar, so tokens_in_matcher = 0. Then trigger_progress = history[-2] = 1, and the history becomes [0] ({{cite deepinfer/structure_output/matcher.py:218-230}}). The matcher is back after token 9, with the trigger half matched.
