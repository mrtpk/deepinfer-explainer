Purpose

block_manager.hpp counts and hands out numbered entries of a pool: KV blocks, or state slots. It does not decide who gets them; the scheduler does.

Where it sits

The figure shows the only data structure of the file. Each entry has three integers. The value 0 means "no block", so entry 0 is never given out. The page {{link concepts/paged-kv-cache}} shows how the scheduler uses these calls during a run.

Who calls it

  • The engine makes two managers: one for KV blocks and, if the model has per-sequence state, one for {{term state-slot | state slots}} ({{cite deepinfer/engine/llm_engine.py:265-266}}).
  • The scheduler holds both managers as shared_ptr ({{cite csrc/engine/scheduler.hpp:1164-1165}}). It locks them for each schedule() ({{cite csrc/engine/scheduler.hpp:277}}), checks space ({{cite csrc/engine/scheduler.hpp:195-201}}), allocates ({{cite csrc/engine/scheduler.hpp:519}}, {{cite csrc/engine/scheduler.hpp:820}}), pins for forks ({{cite csrc/engine/scheduler.hpp:1110-1113}}) and frees ({{cite csrc/engine/scheduler.hpp:738-745}}).
  • DeferredRelease in Python calls unpin_blocks after a fork copy ({{cite deepinfer/engine/llm_engine.py:113-116}}).
  • Statistics read the free counts of both pools ({{cite deepinfer/engine/stats_logger.py:410-414}}).
  • examples/benchmark.py calls Scheduler.try_allocate_seq to give blocks to its requests before the first step ({{cite examples/benchmark.py:314-315}}).

What it calls

  • lock_() and unlock_() of Lockable: a POSIX error-check mutex with a 20-second wait limit ({{cite csrc/utils/lockable.hpp:15-35}}).
  • Sequence::get_num_blocks() and the fields seq.cache.block_table and seq.cache.state_id ({{cite csrc/engine/sequence.hpp:200-207}}, {{cite csrc/engine/sequence.hpp:291-293}}).

Walk through the main methods

The constructor: a list in a vector

NOTE: GPU block 0 is not used, so 0 here means "empty". "Too few GPU blocks: ".
  1. Line 28: the vector has n entries. The head is 1, the tail is n − 1, and the size is n − 1.
  2. Line 29: n must be 2 or more. With n = 1 the pool would be empty.
  3. Lines 30-34: entry i points back to i − 1 and forward to i + 1. The last entry points forward to 0, the "none" value. Entry 1 points back to 0.

The list costs no extra memory per operation. Each entry is a struct of three int fields ({{cite csrc/engine/block_manager.hpp:105-111}}): 12 bytes. A pool of 9,778 blocks needs about 117 KB of host memory for its list.

The list operations

  1. Lines 39-52, _push_back: the entry must not be linked (line 42) and must have no owner (line 43). It becomes the new tail. If the list was empty, it also becomes the head (line 48).
  2. Lines 54-71, _erase: unlink an entry from anywhere in the list, in constant time. Lines 68-69 set its links to 0, which line 42 later checks.
  3. Lines 73-78, _pop_front: erase the head. It raises if the list is empty.

allocate() does not check if the list has an entry. It relies on _pop_front, which raises "list is empty, but pop_front is called" (line 74). Always call can_allocate_nolock or can_allocate_single_nolock first, as the scheduler does.

allocate, pin_block and free

_erase has already checked ref_count == 0.
  1. Line 84: a new block has exactly one owner.
  2. Line 92: pin_block adds an owner. Line 91 refuses to pin a free block, because a free block is still in the list.
  3. Lines 98-102: free removes one owner. Only the last owner puts the block back. So "free" and "unpin" are the same operation; the Python binding unpin_blocks calls free_blocks ({{cite csrc/engine/pybind_scheduler.cpp:68}}).

Only forks make a {{term ref-count}} larger than 1 (deep dive "Reference counts in the scheduler").

BlockManager: the space check and the list calls

  1. Lines 129-131: NEVER if the request is for num_blocks entries or more. The usable maximum is num_blocks − 1, because of entry 0. So the check is exact.
  2. Lines 132-135: OK if enough entries are free now, else LATER.
  3. Lines 138-145: allocate_nolock pops n heads in order. The result is the new block table.
  4. Line 148: free_blocks_nolock walks the list backwards. The last block of a table is freed first, so the first block of the table ends at the tail.

Methods with _nolock expect that the caller holds the lock. free_blocks, pin_blocks, pin_block and reset take the lock themselves ({{cite csrc/engine/block_manager.hpp:122-126}}, {{cite csrc/engine/block_manager.hpp:151-173}}).

BlockManagerMutexAcquire: two locks and one sequence

The caller must make sure that there are enough resources. Try to allocate blocks and state at the same time. If it can never be allocated in the future either, raise an error now.
  1. Lines 190-196: the constructor locks the state manager (if it exists), then the block manager. Lines 199-204: the destructor unlocks in the opposite order. A fixed order prevents a deadlock between two threads.
  2. Lines 197-198: the object cannot be copied or moved, so it cannot unlock twice.
  3. Lines 207-214, allocate_seq: takes get_num_blocks() blocks and, if there is a state manager, one state slot. It does not check space.
  4. Lines 217-239, try_allocate_seq: checks that the sequence is WAITING, has no blocks and no slot (lines 218-222). Then it checks blocks and slot together. On NEVER it raises (line 232). On LATER it returns false. On OK it allocates.

The scheduler uses allocate_seq directly, after its own check ({{cite csrc/engine/scheduler.hpp:386-397}}, {{cite csrc/engine/scheduler.hpp:518-520}}). Only the Python binding Scheduler.try_allocate_seq uses try_allocate_seq ({{cite csrc/engine/pybind_scheduler.cpp:85-92}}).

Complexity. Every list operation is O(1). allocate_nolock(n) and free_blocks_nolock are O(n). Nothing scans the pool.

Python surface. The binding exposes pin_blocks, unpin_blocks, lock, unlock, reset, allocate_nolock and get_num_free_blocks ({{cite csrc/engine/pybind_scheduler.cpp:65-73}}). The stub file lists the same eight names with the constructor ({{cite deepinfer/_C/engine.pyi:9-25}}). The page {{link code/engine-pyi}} maps all bindings.

lock() refuses to run while the thread holds the Python {{term gil}}: TORCH_CHECK(PyGILState_Check() == 0, ...) ({{cite csrc/utils/lockable.hpp:16}}). The reason: the scheduler releases the GIL while it holds the block locks ({{cite csrc/engine/scheduler.hpp:276-277}}). If a second thread held the GIL and waited for a block lock, and the first thread needed the GIL, both would wait forever.

So every binding that can lock releases the GIL first: pin_blocks, unpin_blocks, lock, reset ({{cite csrc/engine/pybind_scheduler.cpp:67-71}}), Scheduler.try_allocate_seq and Scheduler.free_seq ({{cite csrc/engine/pybind_scheduler.cpp:88}}, {{cite csrc/engine/pybind_scheduler.cpp:100-102}}). unlock keeps the GIL; it never waits.

The wait has a limit of 20 seconds (pthread_mutex_clocklock with CLOCK_MONOTONIC). After that, lock() raises with the text of the error code ({{cite csrc/utils/lockable.hpp:20-27}}). The mutex type PTHREAD_ERRORCHECK_MUTEX_INITIALIZER_NP makes a second lock from the same thread fail with an error, not hang ({{cite csrc/utils/lockable.hpp:35}}).

The scheduler raises a count above 1 in one place only: fork_seq pins the whole parent table and the parent's state slot ({{cite csrc/engine/scheduler.hpp:1108-1114}}). Before the fork runs, the scheduler gives it a new state slot and a copy of the partly written last block. It also lists the old ids for release ({{cite csrc/engine/scheduler.hpp:602-618}}). After the device copy, Python unpins the old ids ({{cite deepinfer/engine/llm_engine.py:109-116}}).

Worked example. Parent table [5, 6, 7], 300 cached tokens.

  1. fork_seq: pin_blocks([5, 6, 7]). All three counts become 2.
  2. Admission: ceil(300 / 128) = 3, so block 7 (index 2) is the last used block. A new block, for example 9, gets a copy of block 7. The fork's table becomes [5, 6, 9].
  3. unpin_blocks([7]): block 7 goes back to count 1.
  4. The parent ends: free_blocks([5, 6, 7]). Block 7 reaches 0 and goes to the list. Blocks 6 and 5 go to 1.
  5. The fork ends: free_blocks([5, 6, 9]). Blocks 9, 6, 5 reach 0, in this order, and go to the list.

In this release, only examples/benchmark.py calls fork_seq ({{cite examples/benchmark.py:337-347}}). The page {{link concepts/paged-kv-cache}} has a longer example.

Why is block 0 never given out?

The free list uses 0 as the "none" value for next, prev, _head and _tail ({{cite csrc/engine/block_manager.hpp:27}}). So index 0 cannot also be a real block. The constructor links only 1 … n−1 ({{cite csrc/engine/block_manager.hpp:30-34}}).

 A pool has num_blocks = 100 and all blocks are free. What does can_allocate_nolock return for 99 and for 100?

99: OK, because 99 entries (1 … 99) are free. 100: NEVER, because 100 ≥ num_blocks ({{cite csrc/engine/block_manager.hpp:129-134}}).

 The free list is 8 → 9. A sequence with the table [2, 5, 7] ends. What is the list after free_blocks_nolock?

8 → 9 → 7 → 5 → 2. The table is freed in reverse order, and each block goes to the tail ({{cite csrc/engine/block_manager.hpp:148}}, {{cite csrc/engine/block_manager.hpp:44-50}}).

 Block 7 has ref_count = 2 because of a fork. The parent calls free(7). Is block 7 in the free list now? What happens if code calls free(7) two more times?

No: the count goes to 1, and only a count of 0 puts the block back ({{cite csrc/engine/block_manager.hpp:98-102}}). The next free(7) puts it at the tail. The one after that makes the count −1 and raises "ref_count corrupted" (line 99). This needs the deep dive "Reference counts in the scheduler".

 Python code calls block_manager.lock(). Why does the binding release the GIL first?

Lockable::lock_() raises if the thread holds the GIL ({{cite csrc/utils/lockable.hpp:16}}). The binding uses py::call_guard<py::gil_scoped_release> ({{cite csrc/engine/pybind_scheduler.cpp:69}}). This rule prevents a deadlock with the scheduler, which holds the block locks without the GIL ({{cite csrc/engine/scheduler.hpp:276-277}}).
