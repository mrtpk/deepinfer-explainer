It also limits the SMs of compute kernels while DeepEP runs. ---

Purpose

userbuffer.py makes each large communication buffer once per process, gives the same buffer to every layer that asks, and frees all of them at shutdown.

Where it sits

Who calls it

  • MoE layers. DeepseekMoE.allocate_userbuffer calls allocate_sym_buffer on the mega path, else allocate_ep ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:303-324}}). The DeepEP path runs the shared expert inside limit_num_sms ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:602-603}}).
  • The model. DeepseekForCausalLM.allocate_userbuffer asks every MoE layer for its buffer, then calls allocate_cp with the largest all-gather size of all attention layers ({{cite deepinfer/model_executor/models/deepseek.py:412-442}}). The constructor calls it after torch.cuda.empty_cache() ({{cite deepinfer/model_executor/models/deepseek.py:319-321}}).
  • Context parallelism. Attention, YOCO and the model use userbuffer.cp_session() and userbuffer.cp.all_gather (for example {{cite deepinfer/model_executor/models/deepseek.py:242-243}}, {{cite deepinfer/model_executor/models/v4_modules/yoco.py:71-73}}).
  • Engram. EngramRuntime.allocate calls allocate_engram, and the runtime reads userbuffer.engram ({{cite deepinfer/model_executor/models/v4_modules/engram.py:166-189}}).
  • Shutdown. Worker.stop calls userbuffer.close() between two barriers ({{cite deepinfer/worker/base.py:135-140}}).

What it calls

  • DeepEP: EPBuffer, EngramBuffer, and the alignment helpers get_num_rdma_alignment and get_num_allocation_alignment ({{cite deepinfer/model_executor/parallel_utils/userbuffer.py:7}}, {{cite deepinfer/model_executor/parallel_utils/userbuffer.py:12}}, {{cite deepinfer/model_executor/parallel_utils/userbuffer.py:108-109}}).
  • CPManager, which wraps a DeepEP BucketBuffer ({{cite deepinfer/model_executor/parallel_utils/cp.py:16-17}}).
  • DeepGEMM: SymmBuffer, get_num_sms, set_num_sms; tile_kernels: set_num_sms.

Key classes and functions

The file is short, so this part walks through every method.

limit_num_sms

  1. Lines 41-43: with enabled=False (Ascend, in the only caller), nothing changes.
  2. Lines 44-46: DeepGEMM and tile_kernels may use prev_sms − num_sms, where prev_sms is the current SM count of DeepGEMM. The SMs that DeepEP uses stay free.
  3. Lines 49-51: the old value comes back, also after an exception.

allocate_ep: the DeepEP buffer

  1. Lines 72-80: the buffer arguments. allow_hybrid_mode=True. allow_multiple_reduction is false only with batch invariance and EPLB rearrangement both on.
  2. Lines 81-83: a second call returns the same buffer. It only asserts that the buffer is large enough for the new arguments. So all MoE layers, also the DFlash layers, share one EPBuffer.
  3. Line 85: explicitly_destroy=True: close() must free it.
  4. Lines 86-90: with DEEPINFER_USERBUFFER_COMM_SMS = 0, DeepInfer computes the SM count once and writes it back into envs.

allocate_cp and cp_session

  1. Lines 104-106: with CP size 1 there is no CP buffer; cp_session then does nothing (lines 121-123).
  2. Lines 107-110: size = tokens × bytes per token × CP size, plus room for 8 all-gathers of RDMA alignment, rounded up to the allocation alignment.
  3. Lines 111-113: a later call only checks the size.

CPManager notes: "Gathered tensors alias the buffer storage, which is reused by the next session" ({{cite deepinfer/model_executor/parallel_utils/cp.py:10-14}}). The page {{link concepts/context-parallelism}} explains CP.

allocate_engram

EP traffic goes over NVLink. Here the Engram SL keeps the default sl3 (sl2 is kept for the isolation of KV-cache traffic).

Only one Engram buffer can exist (line 137). The table storage is on the CPU (RDMA) unless DEEPINFER_ENGRAM_FORCE_GPU_STORAGE is on (line 148). On Ascend that variable is always on ({{cite deepinfer/environ.py:147}}). The page {{link concepts/engram}} explains Engram.

allocate_sym_buffer: DeepGEMM symmetric buffers

  1. Line 195: the first spec must be the largest. It owns the memory; later specs are views of it.
  2. Lines 210-212: an equal spec returns the cached buffer. The docstring says that this is safe, because a SymmBuffer never changes after it is made.
  3. Lines 215-220: before the first buffer on GPU, DeepInfer starts DeepGEMM's SM locality probe if DeepGEMM has it. The comment: the probe synchronizes, so it must run "before guarded forward and CUDA graph capture".
  4. Line 221: base=base makes a view for every spec after the first.

close

The EP, CP and Engram buffers are destroyed first. Then the symmetric buffers, in reverse order, so views go before their base. vars(buffer).clear() drops the tensor references of each buffer. A second call does nothing. The unit test checks the order and the second call ({{cite tests/worker/test_userbuffer.py:76-92}}).

Walk through the main methods

The previous part covers every method. One order matters at start-up:

  1. The model is built, and the MoE layers convert their weights ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:254-257}}).
  2. _init_eplb makes the balancers ({{cite deepinfer/model_executor/models/deepseek.py:310-317}}).
  3. torch.cuda.empty_cache(), then allocate_userbuffer() ({{cite deepinfer/model_executor/models/deepseek.py:319-321}}). The main layers come first in the list, then the DFlash layers ({{cite deepinfer/model_executor/models/deepseek.py:423-425}}). So the first SymmBuffer spec is a main layer.
  4. After the weights load, the engine measures the KV-cache size, with these buffers already in memory ({{cite deepinfer/engine/llm_engine.py:241-244}}).

A DeepEP or DeepGEMM buffer is large and needs all ranks of its group to take part. One manager makes each buffer once, shares it between layers, and frees everything in a fixed order at shutdown. The comment in Worker.stop gives one reason for the explicit close: os._exit(0) skips destructors, "which would leave the driver worker's UB stuck at its destructor barrier" ({{cite deepinfer/worker/base.py:136-137}}).

CP buffer. Toy values: hidden size 4096, CP size 2, max_num_batched_tokens = 32768. Then max_num_prefilling_tokens = 32768 // 2 = 16384 ({{cite deepinfer/model_executor/model_loader.py:120}}). The smallest bytes per token is hidden × 2 = 8192 ({{cite deepinfer/model_executor/models/deepseek.py:415}}); attention layers can raise it.

  1. 16384 × 8192 × 2 = 268,435,456 bytes (256 MiB).
  2. Plus 8 × get_num_rdma_alignment().
  3. Round up to a multiple of get_num_allocation_alignment(). DeepEP gives both alignment values; the repository does not show them.

SM count. For a GPU with 148 SMs and DEEPINFER_USERBUFFER_COMM_SMS=0:

  1. compute_num_sms = min(32, 148 // 4) = 32.
  2. The comm SMs are min(theoretical, 148 − 32). DeepEP computes theoretical from the expert count and k.
  3. If DeepEP gives 24, dispatch and combine use 24 SMs. If DeepGEMM uses all 148 SMs before, the shared expert runs with 148 − 24 = 124 SMs inside limit_num_sms.

How many DeepEP EPBuffer objects does one process have when 40 MoE layers use the DeepEP path?

One. The first allocate_ep makes it; later calls return the same object after a size check ({{cite deepinfer/model_executor/parallel_utils/userbuffer.py:81-85}}).

 What does limit_num_sms(24) do on a GPU with 148 SMs, and when is it off?

If DeepGEMM uses all 148 SMs before the call, it sets DeepGEMM and tile_kernels to 124 SMs and restores 148 at the end ({{cite deepinfer/model_executor/parallel_utils/userbuffer.py:44-51}}). The MoE layer passes enabled=PLATFORM.is_gpu, so it is off on Ascend ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:602}}).

 Which buffers does a CP-size-1 deployment on Ascend have, with the released checkpoint and no Engram?

Only DeepGEMM symmetric buffers. On Ascend, every fp8xfp4 MoE layer uses mega-MoE, so no EPBuffer is made ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:184-188}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:303-315}}). allocate_cp returns None for CP size 1 ({{cite deepinfer/model_executor/parallel_utils/userbuffer.py:104-106}}).

 Why does close() destroy the symmetric buffers in reverse order?

Later buffers are views of the first buffer, which owns the memory ({{cite deepinfer/model_executor/parallel_utils/userbuffer.py:195}}, {{cite deepinfer/model_executor/parallel_utils/userbuffer.py:221}}). Reverse order destroys the views before their base. The test expects [view, base] ({{cite tests/worker/test_userbuffer.py:86}}).
