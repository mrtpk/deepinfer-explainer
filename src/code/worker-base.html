Purpose

WorkerBase owns the resources of one worker: the device, the process groups, the model, the KV cache and the CUDA graphs. The per-step code lives in the subclass Worker.

Walk through the main methods

__init__

  1. Lines 90-96: make the ModelRunner. The model is loaded later, in load_model.
  2. Lines 102-106: turn off Python's automatic garbage collector. The worker collects by hand every DEEPINFER_GC_INTERVAL_STEP steps (default 1000), and ten times less often in a COMPLETION engine.
  3. Line 108: _init_torch turns off reduced-precision reductions in FP16 and BF16 matrix multiplies, turns on expandable memory segments, and sets 8 CPU threads ({{cite deepinfer/worker/base.py:174-180}}).
  4. Line 114: init_model sets environment variables for the kernel libraries, binds the NUMA node, selects the device, binds the CPU cores and sets the seed ({{cite deepinfer/worker/base.py:182-194}}).
  5. Line 117: init_dist makes the process groups.
  6. Lines 120-123: a follower freezes the current objects for the garbage collector and enters its loop. The constructor never returns.

start_slave_worker_loop and run_workers

The driver puts (method, kwargs) into a shared-memory message queue of the context-parallel group, and each follower reads it ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:17-23}}). The driver then calls the same method with driver_kwargs as well. So the followers run the same sequence of methods as the driver, with fewer arguments. With one context-parallel rank, nothing is sent.

profile_num_available_blocks: the memory profile

Subtract the reserved state cache, which has a fixed size. State store and copy buffer, so it needs twice the size.
  1. Lines 217-220: empty the PyTorch cache, reset the peak counter, and read free and total device memory.
  2. Line 225: profile_run runs one full step on dummy sequences with a small temporary cache (see {{link code/cache-engine}}).
  3. Lines 228-234: peak = peak PyTorch memory + device memory that PyTorch does not manage.
  4. Line 235: budget = total × gpu_memory_utilization − peak.
  5. Lines 237-245: subtract two copies of the state buffer, then divide by the bytes of one block row.

Line 266 divides the sum by the world size and rounds down to an even number: the mean, not the minimum. The engine docstring says "minimum" ({{cite deepinfer/engine/llm_engine.py:426-428}}). This site describes the code. A rank that measured fewer blocks than the mean gets the mean anyway.

init_cache_engine and warm_up_model

  1. Lines 271-272: make the CacheEngine with the agreed block count from cache_config, and keep the per-layer view object gpu_cache.
  2. Line 279: capture the CUDA graphs of the main model with the real cache.
  3. Lines 280-281: with DSpark, measure the decode time per batch size for the cost model ({{cite deepinfer/worker/model_runner.py:562}}).
  4. Line 285: capture the DFlash graphs, if DFlash has graphs.
  5. Line 288: reset the seed, so that profiling and capture do not change the random state of the run.

stop

The comment explains the order: the follower ends with os._exit(0), which skips destructors, so the userbuffer must close between two barriers. CUDA graphs must go before the process groups, because NCCL inside graphs holds extra dependencies (the comment links PyTorch issue 115388).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

  • Line 329: the global rank is engine_rank × cp_size + cp_rank. The same formula sets self.global_rank ({{cite deepinfer/worker/base.py:79}}).
  • Lines 334-340: the default process group uses the CPU backend "gloo", with the timeout DEEPINFER_GLOO_TIMEOUT (default 14,400 s, {{cite deepinfer/environ.py:110}}). Only this default group uses the timeout. The groups from new_group get no timeout argument, so the PyTorch default applies to them ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:34}}).
  • Line 343: init_parallel_groups splits the world into data-parallel, expert-parallel, context-parallel and engram groups. It also makes CPU groups, such as cpu_cp_group for the message queue ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:99}}, {{cite deepinfer/model_executor/parallel_utils/parallel_state.py:124}}), and then the device groups ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:126}}).

The CPU data-parallel group is the group that the engine uses with ZOS (see {{link concepts/zero-overhead-scheduling}}).
  • NUMA. _bind_numa binds the process and its memory to the NUMA node of the device. A failure only logs a warning. Translated: "NUMA binding failed; memory placement falls back to first-touch, which can slow down H2D copies" ({{cite deepinfer/worker/base.py:347-357}}).
  • CPU cores. bind_cpu gives each device an equal share of the physical cores: device i gets cores i·k to (i+1)·k − 1, with k = physical cores // devices ({{cite deepinfer/utils.py:143-148}}).
  • Environment. configure_worker_environment sets EP_AVOID_RECORD_STREAM=1, removes NCCL_NVLS_ENABLE, sets NCCL variables on NVIDIA, and sets the JIT cache folders if DEEPINFER_JIT_CACHE_DIR is set ({{cite deepinfer/worker/runtime_config.py:29-51}}).
  • Kernels. configure_worker_kernels turns on PDL for DeepGEMM and TileKernels on NVIDIA, and deterministic algorithms with DEEPINFER_BATCH_INVARIANT or on Ascend ({{cite deepinfer/worker/runtime_config.py:54-69}}).
  • Seed. Each rank uses seed + global_rank, so ranks draw different random numbers, for example for simulated MoE imbalance ({{cite deepinfer/worker/base.py:170-172}}).

Example values (not measured): 8 ranks, an 80 GiB device, gpu_memory_utilization = 0.85 (the value of examples/offline_inference.py), a peak of 50 GiB, a block row of 2 MiB and a state buffer of 0.5 GiB.

  1. Budget: 80 × 0.85 − 50 = 18 GiB = 18,432 MiB.
  2. State: 2 × 512 MiB = 1,024 MiB; left: 17,408 MiB.
  3. Blocks on this rank: 17,408 // 2 = 8,704.
  4. If the 8 ranks measure 8,704, 8,704, 8,704, 8,704, 8,600, 8,600, 8,600 and 8,601 blocks, the sum is 69,217. Each rank uses 69,217 // 8 = 8,652, then 8,652 // 2 × 2 = 8,652.

The second state copy is the store buffer copy_state of the KV-saving hooks ({{cite deepinfer/engine/llm_engine.py:787-798}}). In this release copy_state stays None ({{cite deepinfer/engine/llm_engine.py:284}}), but the profile still reserves the memory. The page {{link learn/kv-cache}} has a second worked example in its deep dive "Where the memory comes from".

Which four WorkerBase methods does the engine call at start-up, in order?

load_model, profile_num_available_blocks, init_cache_engine and warm_up_model ({{cite deepinfer/engine/llm_engine.py:241}}, {{cite deepinfer/engine/llm_engine.py:437}}, {{cite deepinfer/engine/llm_engine.py:453}}, {{cite deepinfer/engine/llm_engine.py:457}}).

 How does a follower worker learn which method to run?

It waits in start_slave_worker_loop for a (method, kwargs) object from cp_broadcast_object ({{cite deepinfer/worker/base.py:129-133}}). The driver sends it in run_workers before it runs the method itself ({{cite deepinfer/worker/base.py:298-302}}).

 Why does the worker turn off Python's automatic garbage collector?

It calls gc.disable() and collects by hand every DEEPINFER_GC_INTERVAL_STEP steps, next to the pre_sampler_sync callback ({{cite deepinfer/worker/base.py:102-106}}, {{cite deepinfer/worker/base.py:153-157}}, {{cite deepinfer/worker/worker.py:165}}). So a collection runs at a known point, while the device samples, and not at a random point in the step. (The code gives no comment on the reason; this is the effect.)

 4 ranks measure 1,001, 1,001, 1,000 and 990 blocks. How many blocks does each rank use? Does the docstring of _init_cache give the same answer?

Sum 3,992; 3,992 // 4 = 998; 998 // 2 × 2 = 998 ({{cite deepinfer/worker/base.py:264-266}}). The docstring says the minimum, which would be 990 ({{cite deepinfer/engine/llm_engine.py:426-428}}). So the rank that measured 990 gets 8 blocks more than it measured. See the deep dive "The memory profile with numbers".
