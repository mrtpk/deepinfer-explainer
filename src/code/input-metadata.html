Purpose

This folder defines the object that every layer of the model reads in a step, the {{term input-metadata}}, and the device-side builder of the decode metadata for {{term zos}}.

Filesinput_metadata.py (490 lines): the classes. yoco.py (182 lines) and dflash.py (84 lines): two mixins. prepare_tensor_input_zos.py (382 lines): the ZOS decode builder. __init__.py (13 lines): exports four classes ({{cite deepinfer/model_executor/input_metadata/__init__.py:1-13}}).
Main classInputMetadataV4 ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:218}}), with the base InputMetadata ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:27}}) and the vision classes InputMetadataVL and InputMetadataV4VL.
Runs inEvery worker process. The object is built on the driver; its tensors live on the device during the forward pass.
Called byModelRunner (construction), ModelMetadata (the ZOS builder), the model (compute_attn_info, the views), CudaGraphRunner (recursive_fn, broadcast).
CallsTileLang kernels for gathers and index expansion (get_kv_index, swa_index, prepare_cp_mirror, prepare_v4_decode_metadata, …), CP collectives, C++ prepare_decode_zos_inputs.
Not in this fileThe CPU computation of prefill fields and of non-ZOS decode fields (C++, {{link code/prepare-tensor-input-v4}}). The image fields come from deepinfer/ve/prepare_tensor_input_vl.py.

Where it sits

Who calls it

  • ModelRunner._prepare_input_tensors builds the object from the dict of the builder ({{cite deepinfer/worker/model_runner.py:142-146}}).
  • ModelMetadata selects the class and the ZOS builder ({{cite deepinfer/model_executor/model_metadata_utils.py:142-144}}).
  • Each attention layer calls compute_attn_info ({{cite deepinfer/model_executor/models/v4_modules/attn.py:765}}).
  • DeepseekModel.forward calls prepare_for_mirror_cp, get_consumer_view and get_mask_view ({{cite deepinfer/model_executor/models/deepseek.py:168-207}}).
  • The DFlash model calls build_dflash_input ({{cite deepinfer/model_executor/models/mtp/dflash.py:367-372}}).
  • CudaGraphRunner calls recursive_fn, get_clean_list, recursive_copy_ and broadcast ({{cite deepinfer/worker/cuda_graph_runner.py:62-65}}, {{cite deepinfer/worker/cuda_graph_runner.py:95}}, {{cite deepinfer/worker/cuda_graph_runner.py:117-119}}).

What it calls

  • Index kernels: get_kv_ca_index_prefill, get_kv_ca_index_decode, get_kv_swa_index_decode, expand_swa_index, gather, prepare_cp_mirror ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:13-20}}).
  • CP collectives: cp_broadcast_object and cp_broadcast_multi_tensor ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:21-22}}).
  • ZOS: C++ prepare_decode_zos_inputs and the kernels gather_input_ids_zos, gather_engram_tokens_zos, prepare_v4_decode_metadata ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:7-10}}).

Walk through the main methods

The dataclass and its field layout

The YoCo truncation fields and views, and the DFlash fields and construction, are in the mixins of yoco.py and dflash.py.

Every field has a docstring with its shape. The fields fall in three groups: prefill and decode (lines 225-252), prefill only (lines 256-298), decode only (lines 300-322). The page {{link concepts/input-metadata}} has the full table. The class docstring says "Zero-length tensors are padded to length 1": this is the max(1, …) rule of the C++ builder.

compute_attn_info: expansion on the device

Expand the SWA visible range of the current object (the original metadata or a consumer view). On the original metadata the pivots are the full sliding window; on a consumer view get_consumer_view has replaced them with compact YOCO pivots. The expansion is the same.
  1. Lines 345-352 (prefill): compressed_batch_mapping gives the sequence index of each new compressed entry, from cu_compressed_seqlens_q. A scatter_add_ marks the sequence ends and a cumsum_ counts them.
  2. Lines 353-357: kv_swa_full_index from the pivots ([total_q, window_size]).
  3. Lines 358-363: kv_ca_index from the offset pairs. The width is max_model_len / N rounded up to 128.
  4. Lines 371-376 (decode): kv_swa_index from the offset pairs, with the ring size.
  5. Lines 377-383: kv_ca_index through the block tables, but only when the layer passes block_size. The indexer of a sparse layer makes its own top-k indices.

Each step is guarded by is None. So the first attention layer does the work, and later layers reuse it. This is also why get_clean_list exists: a graph capture must see these fields as None.

broadcast: one call for the whole object

  1. Lines 126-149: walk the object. Tensors go into a list, also the tensors inside dict fields such as slot_mapping_store_ca["2"]. Other values go into a dict by path, for example "num_reqs". All tensors must be on the device.
  2. Lines 151-164: rank 0 sends the dict with cp_broadcast_object; the other ranks write the values back by path.
  3. Lines 166-167: one multi-tensor broadcast fills all tensors in place. Because the addresses do not change, this call works inside a CUDA graph.

prepare_for_mirror_cp

Dense-only models have an empty ks dict; the kernel needs at least one ratio to compute the mirror index, so it falls back to 1.

The kernel prepare_cp_mirror returns the mirror index, its inverse, and new ks/ke for the reordered rows. The function then reorders positions and ngram_token_ids with gather, and writes a reordered copy of gate_force_random to gate_force_random_cp. input_ids and gate_force_random keep the full layout. The docstring explains why rebinding the fields is safe: "prefill runs without cudagraph" ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:171-177}}).

The YOCO views

YOCO decoder truncation (mask mode) changes only the mask; it does not cut rows. Make a compact shallow copy of the metadata for the first YoCo consumer layer: switch the query-aligned fields and the SWA visible range to the compact layout, and clear the attention expansions so that they are made again. With CP > 1, also redo the zigzag split and make the redistribution index at the layer boundary. Fields that are not rewritten share tensors with the original metadata; do not change them in place. Switch the SWA visible range to the compact YOCO pivots; consumer layers read kv_swa_full_index(_pivots) as usual and get the truncated meaning. Set the fields expanded in forward to None; compute_attn_info expands them again from the compact metadata. input_ids is used only by the embedding before the layer loop, so it keeps the original varlen tensor. gate_force_random is gathered from the full layout to the compact layout.

The two properties yoco_compaction_enabled and yoco_mask_enabled test which fields C++ made; the two modes never exist together ({{cite deepinfer/model_executor/input_metadata/yoco.py:66-84}}). With CP above 1, get_consumer_view also runs prepare_cp_mirror on the compact lengths and builds the redistribution index for the layer boundary ({{cite deepinfer/model_executor/input_metadata/yoco.py:130-182}}).

The ZOS decode builder

  1. Line 317: prepare_common_decode_buffers_zos calls C++ prepare_decode_zos_inputs for per-sequence values, copies them to the device, and gets or makes the per-row buffers ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:162-178}}).
  2. Lines 322-334: one stacked buffer per dict field, so one kernel launch fills all ratios.

The kernel reads the corrected seqlens_q and seqlens_k from metadata_zos, which the Worker made on the device ({{cite deepinfer/worker/worker.py:236-245}}). finalize_decode_outputs_zos then fills input_ids: a copy from the CPU for fresh sequences, and a device gather from the previous step's sampled and draft tokens for continuing ones ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:181-244}}). With a graph, it returns the graph's out dict ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:286-287}}).

Deep dive

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

The kernel prepare_v4_decode_metadata writes, for example, positions_c for all ratios in one launch. It needs one 2-D buffer [len(keys), q_stride]. The dict of the metadata needs one 1-D tensor per ratio. get_or_create_stacked gives both ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:120-159}}):

  1. No keys: a dummy one-row buffer that the kernel does not write, and an empty dict.
  2. Eager (no buffer yet): a new [n, total_q, …] tensor; the dict values are its rows.
  3. Graph: the existing per-ratio buffers are row views of one allocation from the capture. The function checks that they are equally spaced views of one storage, then rebuilds the 2-D view with as_strided. The row stride can be larger than total_q, because a small graph uses the first rows of the size-max buffer.

Translated assert message: "the existing buffers of {outer} are not equally spaced row views (was the capture flow changed?)". So a change to the capture flow that breaks this zero-copy rule fails at once.

Example. Sizes [1, …, 24], ratios "1" and "2", a step with 16 rows. The capture made positions_c as one [2, 24] tensor with rows ["1"] and ["2"]; the size-16 graph has views [:16] of each row. stride_elems = 24, q_stride = 24, and the kernel output is a [2, 24] view; the kernel writes the first 16 values of each row.

With Engram, each row needs the compressed ids of its last max_ngram_size tokens. Under ZOS some of them are still on the device. The docstring of prepare_token_ids_zos defines a virtual sequence: the compressed sequence data, then the in-flight draft tokens of the previous step, then the current tokens ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:186-209}}). The window has nextn + max_ngram_size − 1 tokens. For lookback r of row j: if j ≥ r, the id is a current token; else it comes from the window, shifted by the number of rejected drafts, which the kernel computes.

Which method turns the offset pairs of a decode step into the full index table kv_swa_index, and when does it run?

InputMetadataV4.compute_attn_info ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:371-376}}). Each attention layer calls it at the start of its forward ({{cite deepinfer/model_executor/models/v4_modules/attn.py:765}}); only the first call does the work.

 Why does get_consumer_view set kv_swa_full_index and kv_ca_index to None?

The view has a new, compact row layout. With None, the next compute_attn_info call expands them again from the compact pivots and offsets ({{cite deepinfer/model_executor/input_metadata/yoco.py:113-118}}).

 Under ZOS with a graph of size 16 and two compress ratios, how can one kernel launch write both positions_c["1"] and positions_c["2"] without a copy?

The capture made both as rows of one [2, 24] tensor. get_or_create_stacked checks that the two size-16 views are equally spaced in one storage and builds a strided [2, 24] view for the kernel ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:141-159}}). This is in the deep dive "get_or_create_stacked".
