Purpose

These two files turn a Hugging Face folder into filled parameters. loading.py checks and plans. weights.py reads the bytes and copies them into the model.

Filesdeepinfer/hugging_face/weights.py (436 lines) and deepinfer/hugging_face/loading.py (121 lines). Helpers in the same package: names.py (the {{term hf-name-map}}, 184 lines) and parameters.py (70 lines).
Main typesHFCoverage, a frozen dataclass ({{cite deepinfer/hugging_face/weights.py:58-71}}), and _TensorReader, a safetensors reader ({{cite deepinfer/hugging_face/weights.py:182}}).
Runs inEvery worker process, main thread, once at start-up. File reads are on the CPU; the copies go to the device.
Called byDeepseekForCausalLM.load_model and load_hf_checkpoint in model_loader.py, through the lazy package API ({{cite deepinfer/hugging_face/__init__.py:23-45}}).
Callssafetensors.safe_open, the EPLB slot map, the EP group, and tile_kernels.quant.batched_transpose_weight_sf.
Not in these filesThe parsing of config.json (hugging_face/config.py, see {{link concepts/weight-loading}}), the load order (deepseek.py), and the tokenizer.

The module docstring of weights.py is the best summary. It names the three channels and the scale rule of each ({{cite deepinfer/hugging_face/weights.py:1-17}}). None of these files reads an environment variable.

Where it sits

Who calls it

  • DeepseekForCausalLM.load_model calls prepare_hf_coverage, then cover_tied_parameters after the meta build, and log_load_phase after each phase ({{cite deepinfer/model_executor/models/deepseek.py:463-470}}).
  • load_hf_checkpoint calls model_params, validate_hf_shapes and load_covered_params ({{cite deepinfer/model_executor/model_loader.py:143-152}}).
  • examples/_ve_helper.py calls prepare_hf_coverage, empties the expert and Engram maps, and loads only the vision parameters ({{cite examples/_ve_helper.py:58-60}}).

What it calls

  • safe_open from the safetensors package, to list keys and read headers ({{cite deepinfer/hugging_face/loading.py:48}}, {{cite deepinfer/hugging_face/loading.py:98-103}}). The ordinary and expert channels read the bytes with their own reader instead.
  • get_initial_global_physical_to_logical_map and PG.expert_parallel_group().rank(), to find the local experts ({{cite deepinfer/hugging_face/weights.py:254-265}}).
  • tile_kernels.quant.batched_transpose_weight_sf, a pip package kernel, to pack FP8 scales ({{cite deepinfer/hugging_face/parameters.py:58-70}}).

Walk through the main methods

build_coverage: three channels

  1. Line 95: scales, per-expert tensors and Engram tables do not go into the ordinary map.
  2. Lines 97-98: every other name that maps to a parameter goes into tensors. Two names can map to one parameter.
  3. Line 106: the shared expert's linear1 is kept only if both w1 and w3 exist. Else the parameter has no coverage, and the load stops later.
  4. Lines 108-109: the other two channels have their own scans.

_scan_expert_coverage: complete layers only

A layer is covered only when all of these are true. If one is false, the layer is skipped, and its parameter has no coverage:

  1. Each expert tensor has its .scale (line 128).
  2. The expert numbers are 0 … n−1 with no gap (line 135). This case also logs a warning.
  3. Each expert has w1, w2 and w3 (line 138).
  4. The count equals n_routed_experts, or the DFlash count for mtp.* layers (lines 140-145).

The result has one entry for linear1 with pairs (w1, w3) and one for linear2 with (w2,), in expert order (lines 147-148). The plan holds every expert. Each rank picks its own experts later.

validate_hf_shapes: headers before bytes

  1. Lines 106-109: for two sources (for example w1 and w3), all dims except dim 0 must agree. The expected shape adds the dim-0 sizes.
  2. Lines 110-111: the result must equal the parameter shape.
  3. Lines 113-116: HC matrices and attention sinks must be FP32 in the model and in the file. The comment: "a cast would defeat exact folded-value loading".
  4. Lines 117-118: the file dtype must equal the parameter dtype. There is no cast.
  5. Lines 119-121: each tied alias must have the shape and dtype of its source.

This function checks only the ordinary channel and the aliases (line 92). Experts and Engram tables get their checks during the copy.

_TensorReader.read: one byte range

  1. Lines 212-220: open each shard once and parse its header. The first 8 bytes are the header length, little-endian. The length must be above 0 and at most 100,000,000 bytes and must fit in the file.
  2. Lines 222-226: find the entry (with or without model.) and check the byte range: inside the file, and exactly prod(shape) × itemsize bytes.
  3. Lines 229-237: read the range into a bytearray with readinto, in a loop. A short read raises EOFError.
  4. Lines 238-240: make a CPU tensor on the same bytes, then copy it to the target device.

The class docstring gives the reason for plain reads. It says: "Reuse file handles and stage only requested byte ranges to bound memory and avoid mmap page faults" ({{cite deepinfer/hugging_face/weights.py:185-187}}).

load_covered_params: the ordinary channel

  1. Line 403: only plan entries that are parameters of this model. Other entries are not read.
  2. Lines 411-413: Engram and MXFP4 expert parameters must not reach this channel.
  3. Lines 414-417: read (and concatenate), check the shape again, and copy.
  4. Lines 418-421: a 1-byte parameter is FP8. Its .scale is read, decoded to FP32 and set as param.sf.
  5. Lines 426-427: all FP8 parameters go to set_ue8m0_sf in one batch.
  6. Lines 431 and 433: then the expert channel and the Engram channel. Each phase is logged.

set_ue8m0_sf writes param.ue8m0_sf ({{cite deepinfer/hugging_face/parameters.py:69-70}}). Only the same function reads it: an assert for CPU scales ({{cite deepinfer/hugging_face/parameters.py:52}}) and the reuse of an existing buffer as the output ({{cite deepinfer/hugging_face/parameters.py:67}}). No other code in the repo reads it. The runtime linear layer copies only sf ({{cite deepinfer/model_executor/utils.py:22-26}}) and converts it with deep_gemm.transform_sf_into_required_layout ({{cite deepinfer/model_executor/layers/linear.py:67-76}}).

_load_expert_params: local experts only

  1. Lines 299-301: a plan entry with no model parameter is counted as skipped. No error.
  2. Lines 302-303: a parameter with no local expert list is a RuntimeError.
  3. Lines 304-307: the parameter must be 3D int8 with int16 or int32 scales and one slot per local id. The checkpoint must have each needed expert.
  4. Lines 312-315: for each local slot, read [w1; w3] (or w2) and the matching scales.
  5. Lines 319-323: view the UE8M0 bytes as the platform's packed type and copy them. The values do not change.
  6. Line 325: mxfp4 = True keeps this parameter out of the generic FP8 path.

_load_engram_tables: this rank's rows

  1. Line 357: the first row of this rank, set by the container ({{cite deepinfer/model_executor/models/v4_modules/engram_parameters.py:31}}).
  2. Lines 367-369: copy at most the rows that exist in the file, in chunks of about 228 bytes.
  3. Lines 370-378: copy the FP8 rows. Decode the scale rows on the scale's device; the weight slice stays on the CPU.
  4. Lines 379-382: rows past the end of the file get weight 0 and scale 1.

cover_tied_parameters

Only modules after the main head (number above n_layer + 1) can get an alias, and only for two names. The alias is added only if the source has a checkpoint tensor and exists in the model (line 81).

The expert layout comes from {{cite deepinfer/model_executor/models/v4_modules/containers.py:72-87}}. The page {{link concepts/low-precision-formats}} explains the packed scale types.

Suppose a shard has a header of 40,000 bytes (an example). Its JSON has this entry:

"layers.3.attn.wq_a.weight": {"dtype": "F8_E4M3", "shape": [1024, 4096], "data_offsets": [0, 4194304]}
  1. Bytes 0-7 of the file hold 40,000 as a little-endian integer. data_start = 8 + 40000 = 40008 (line 220).
  2. The dtype maps to torch.float8_e4m3fn, 1 byte (line 194).
  3. Check: 4194304 − 0 = 1024 × 4096 × 1, and the range ends inside the file (line 225).
  4. Seek to byte 40008 and read 4,194,304 bytes into a new bytearray (lines 229-237).
  5. torch.frombuffer(...).reshape([1024, 4096]) on the CPU, then .to("cuda:N") (lines 238-240).
  6. Then the scale layers.3.attn.wq_a.scale: F8_E8M0 [32, 128], 4,096 bytes, read the same way (lines 418-419).

Memory. The reader holds at most one CPU staging buffer at a time: each read copies its bytes to the device and then drops the buffer. For a concatenation, the device parts stay until torch.cat ends (line 245). The loop deletes the device copies of the weight and the scale after each parameter (lines 422-423). A header above 100 MB is refused, so a broken header cannot make the reader allocate a huge buffer.

Which experts. _local_expert_ids sorts all FusedExperts modules by layer_id. For each, it takes the slots [n_local × ep_rank, n_local × (ep_rank + 1)) of the initial slot map ({{cite deepinfer/hugging_face/weights.py:260-271}}). The docstring: "redundant experts reuse the same HF weights" (line 252). So one EP rank can read the same checkpoint expert twice, once for its own slot and once for a copy slot. This needs a small EP size, for example EP size 1 with extra slots, so that the copies wrap round onto the same rank.

Layout. The runtime weight is int8 (n_local, h_out, h_in // 2): two {{term fp4}} values per byte. The docstring says that the checkpoint scale is "F8_E8M0 row-major bytes (the inverse of the exporter's .contiguous().view(F8_E8M0))" ({{cite deepinfer/hugging_face/weights.py:283-288}}). So a view to int32 or int16 groups 4 or 2 neighbouring scales of one row. Then copy_ into the column-major sf slot moves them into place.

File handles. Each expert parameter gets its own _TensorReader. The comment: "Expert halves and scales may span shards; the reader reuses handles without retaining tensors" ({{cite deepinfer/hugging_face/weights.py:309-311}}).

Return value. A dict with expert_params, experts (slots filled) and expert_skipped. load_covered_params merges it into the final log line "HF weights loaded: {...}" ({{cite deepinfer/hugging_face/weights.py:328}}, {{cite deepinfer/hugging_face/weights.py:435}}).
  • Everything here runs in the calling thread. There is no thread pool and no parallel read. The only extra thread is the watchdog in model_loader.py.
  • Each process opens the shard files itself. _TensorReader is an ExitStack, so the with block closes every file it opened ({{cite deepinfer/hugging_face/weights.py:182}}, {{cite deepinfer/hugging_face/weights.py:407}}).
  • log_load_phase calls torch.cuda.synchronize() when CUDA is initialized. So the logged time includes queued device copies ({{cite deepinfer/hugging_face/weights.py:43-55}}).
  • The package __init__.py imports each function on first use, with a module-level __getattr__. The docstring: "Callers outside this package import from here; package internals import directly from their sibling modules" ({{cite deepinfer/hugging_face/__init__.py:1-5}}, {{cite deepinfer/hugging_face/__init__.py:40-45}}).

Which three channels does load_covered_params run, and in which order?

Ordinary parameters, then routed experts, then Engram tables ({{cite deepinfer/hugging_face/weights.py:407-434}}).

 A checkpoint layer has 255 of 256 routed experts. What happens?

_scan_expert_coverage skips the layer. If expert 255 is the missing one, the numbers have no gap, but the count is not n_routed_experts ({{cite deepinfer/hugging_face/weights.py:144-145}}). If an expert in the middle is missing, the gap check skips the layer first and logs a warning ({{cite deepinfer/hugging_face/weights.py:135-137}}). Its linear1 and linear2 then have no coverage, and load_hf_checkpoint raises RuntimeError ({{cite deepinfer/model_executor/model_loader.py:147-149}}).

 Why does the expert channel not decode the UE8M0 scales to FP32, as the ordinary channel does?

The runtime expert parameter keeps its scales as packed UE8M0 bytes in an int32 or int16 slot, not as FP32 ({{cite deepinfer/model_executor/models/v4_modules/containers.py:78-87}}). The loader views the row-major bytes as int32 or int16 and copies them into the column-major sf slot, "without changing the values or requantizing" ({{cite deepinfer/hugging_face/weights.py:286-288}}, {{cite deepinfer/hugging_face/weights.py:319-323}}).

 The first 8 bytes of a shard encode 40,000. A tensor entry has "data_offsets": [4194304, 4198400]. At which file offset does _TensorReader start to read, and how many bytes does it read?

The data starts after the 8-byte length and the header: 8 + 40000 = 40008 ({{cite deepinfer/hugging_face/weights.py:215-220}}). The reader seeks to 40008 + 4194304 = 4234312 and reads 4198400 − 4194304 = 4096 bytes ({{cite deepinfer/hugging_face/weights.py:224-237}}). This is the deep dive "Worked example: reading one tensor".

 An Engram table in the checkpoint has 1,000,000 rows of 1,024 bytes. The Engram group has 2 ranks (example values). How many rows does rank 1 copy, in how many chunks, and what happens to the other rows of its parameter?

The alignment is lcm(256, 2) = 256, so the padded table has ceil(1000000 / 256) × 256 = 1000192 rows. Each rank holds num_per_part = 500096 rows, and rank 1 starts at row_start = 500096 ({{cite deepinfer/model_executor/models/v4_modules/engram_parameters.py:27-31}}). valid_rows = min(500096, 1000000 − 500096) = 499904 ({{cite deepinfer/hugging_face/weights.py:367}}). rows_per_chunk = 2**28 // 1024 = 262144, so there are 2 chunks: 262,144 rows, then 237,760 rows (lines 369-378). The last 192 rows of the parameter (499,904 to 500,095) are past the end of the file: weight 0 and scale 1 (lines 379-382).
