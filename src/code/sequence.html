Purpose

deepinfer/sequence.py gives Python one import place for the C++ sequence classes, and defines SamplerOutput: the object that carries the sampler results of one step to the engine.

Filedeepinfer/sequence.py, 281 lines of Python. The header says "Derived from vLLM; modified by DeepSeek." ({{cite deepinfer/sequence.py:2}}). Many docstrings are in Chinese.
Main classSamplerOutput ({{cite deepinfer/sequence.py:172}}). Also SampledInfo, MTPPredictInfo, DeepInferTopkInfo and the helper _where_update.
Runs inThe process of the driver Worker, which is also the engine process. The tensors start on the device and move to the CPU at the end of sampling.
Called byThe sampler and DFlash (they make the objects), the model runner and the Worker (they finish and keep them), and LLMEngine._process_model_outputs (it reads them).
CallsOnly PyTorch, and the import of deepinfer._C.engine.
Not in this fileThe Sequence class itself: it is C++ ({{link code/sequence-hpp}}). The sampling math: it is in layers/sampler.py.

In vLLM, sequence.py defines the sequence classes in Python. In DeepInfer those classes moved to C++. This file now only re-exports them and holds the sampler result types.

Where it sits

Who calls it

  • The sampler makes SampledInfo, DeepInferTopkInfo and SamplerOutput ({{cite deepinfer/model_executor/layers/sampler.py:555-560}}, {{cite deepinfer/model_executor/layers/sampler.py:626-630}}). A prefill step fills sampled_token only ({{cite deepinfer/model_executor/layers/sampler.py:198-203}}). A decode step fills the verified tokens, the drafts and the ZOS fields ({{cite deepinfer/model_executor/layers/sampler.py:277-291}}).
  • DFlash makes MTPPredictInfo with the new drafts ({{cite deepinfer/model_executor/models/mtp/dflash.py:338}}). Its CUDA-graph runner uses narrow and copy_ ({{cite deepinfer/worker/dflash_cuda_graph_runner.py:60-71}}, {{cite deepinfer/worker/dflash_cuda_graph_runner.py:91}}).
  • The model adds a post function that fills moe_load_balance_ratio ({{cite deepinfer/model_executor/models/deepseek.py:403-409}}).
  • The model runner runs the post functions after the step is on the CPU ({{cite deepinfer/worker/model_runner.py:369-378}}).
  • The Worker reads the ZOS fields of the previous step to correct the next one ({{cite deepinfer/worker/worker.py:219-243}}).
  • The engine reads the tokens, log-probabilities and drafts ({{cite deepinfer/engine/llm_engine.py:693-761}}).
  • Imports of the C++ classes. llm.py, llm_engine.py, worker.py, model_runner.py, the CUDA-graph runners and zos_status.py import Sequence, SequenceMetadata or SequenceData from here.

What it calls

Only torch for tensor work, and deepinfer._C.engine for the re-exported names.

Walk through the main methods

Imports and re-exports

The C++ classes have no Python source. Their stubs are in deepinfer/_C/engine.pyi. A Sequence made in Python is the same object that the scheduler holds: the binding wraps a std::shared_ptr<Sequence> ({{cite csrc/engine/pybind_sequence.cpp:91}}).

_where_update and DeepInferTopkInfo

Where is_final is True, overwrite current with candidate. If current is None, clone candidate. shape [num_token, topk], dtype torch.float. logps first, then tokens, the same order as deep_select. Make a DeepInferTopkInfo from the request count and topk. With topk = 0, all members are None. Final step before the sampler returns: move the results to the CPU. NOTE: call this before the last sync of the sampler. Where is_final is True, overwrite the current values with candidate.
  1. Lines 31-35: None means "no data". A None candidate keeps the current value.
  2. Lines 55-61: with topk = 0, no tensors are made. Else logps is float32 [req_cnt, topk] (zeros) and tokens is int32 [req_cnt, topk] (not set).
  3. Lines 63-68: sampler_epilogue starts the copies to the CPU with non_blocking=True. The values are valid only after the sampler's last sync.

MTPPredictInfo: the new drafts

Information of the MTP prediction. If the current step needs no MTP, every member is None; parts of the framework test this None to know if MTP exists. token_ids and confidence_rates move to the CPU for the scheduler. The logprobs and their indices go straight from the sampling path of the MTP module into the MTP info pool on the GPU; they are not part of the prediction result. The accept rate of each draft token, predicted by the confidence head. shape [bs, nextn], values in [0, 1]. None if there is no confidence head.
  1. Lines 88-91: token_ids [bs, nextn], and an optional confidence_rates [bs, nextn].
  2. Lines 93-98: narrow(req_cnt) drops the padding rows of a CUDA graph. It asserts 0 < req_cnt <= bs.
  3. Lines 100-104: copy_ copies in place; both objects must agree on the confidence tensor.
  4. Lines 106-110: the CPU copy is int32 for the ids.

The engine passes token_ids to process_MTPInfo, which stores them as the drafts of each sequence ({{cite deepinfer/engine/llm_engine.py:713-723}}, {{cite csrc/engine/scheduler.hpp:1235-1238}}).

SampledInfo: one kind of tokens

Information about returned tokens. One class can mean the sampled token (is_verified_token = False) or the verified tokens (is_verified_token = True). Is it a verified token? This is different from the one token that each step samples. The number of verified tokens is not fixed; the upper limit is nextn. The token sampled in this step. The ids and logp of the top-k tokens that SamplingParams asks for. shape [bs*num_top] or [bs*nextn*num_top]; logically [bs, num_top] or [bs, nextn, num_top]. shape [bs] or [bs*nextn]. Only when DEEPINFER_COMPUTE_SUM_SMALLER_PROBS is on. Final step before the sampler returns: move the results to the CPU. NOTE: call this before the last sync of the sampler. Where is_final (a [bs] or [bs*nextn] bool tensor) is True, overwrite with candidate.
  1. Lines 117-128: one SampledInfo holds either the sampled token of each request ([bs]) or the verified draft tokens (flat, [total_q] in decode).
  2. Lines 130-139: the CPU copy of token_ids becomes int32.
  3. Lines 141-151 (update) and 153-168 (from_reqcnt): no code outside this file calls them in this release. A search for from_reqcnt( and for .update(is_final finds only this file.

SamplerOutput: the result of one step

The properties give old flat names to the nested fields: token_ids is sampled_token.token_ids, and accepted_token_ids is verified_tokens.token_ids. token_ids and token_logprobs return an empty tensor instead of None (lines 181-183, 187-189). So the engine can read output.token_ids.size(0) also for a placeholder output ({{cite deepinfer/engine/llm_engine.py:693-695}}).

shape [total_q]. The last logprobs of each verify position. Only when DEEPINFER_COMPUTE_SUM_SMALLER_PROBS is on. shape [req_cnt], CPU int32. Offset of the first token of each req in the [total_q] flat tensor. Lets later code index [total_q]-shaped tensors such as verified_tokens. The accept rate of each draft token, predicted by the confidence head. shape [bs, nextn]. Log-probabilities of the prompt tokens. Only when SamplingParams.prompt_logprobs=True and the step is a prompt step.
  1. Line 226: first_token_positions is the key to the flat layout. Request i owns positions ftp[i] … ftp[i+1] − 1 of every [total_q] tensor.
  2. Line 230: predict_tokens holds the drafts for the next step.
  3. Lines 242-246: two statistics lists. The decode post function fills them as [req_cnt] + counts ({{cite deepinfer/model_executor/layers/sampler.py:293-296}}).
  4. Lines 254-255: so_status per request: -1 (aborted), 0 (no grammar), 1 (just started), 2 (started).
  5. Lines 259-269: four GPU tensors for ZOS. The next step reads them on the device to correct its seqlen_q and seqlen_k without a CPU sync ({{cite deepinfer/worker/worker.py:219-243}}).

post_funcs (line 177) is a list of functions that fill fields after the CPU copies are done. The model runner calls them once and clears the list ({{cite deepinfer/worker/model_runner.py:376-378}}).

Writers: {{cite deepinfer/model_executor/layers/sampler.py:198-210}} (prefill) and {{cite deepinfer/model_executor/layers/sampler.py:256-298}} (decode). On a follower rank of context parallelism, the sampler returns an empty SamplerOutput(post_funcs=[]) ({{cite deepinfer/model_executor/layers/sampler.py:145-161}}).

Two requests, nextn = 5, both send 1 + 5 tokens, so total_q = 12. Request 0 gets 2 drafts accepted, request 1 gets 0. Illustrative values:

out.first_token_positions          # tensor([0, 6], dtype=torch.int32), CPU
out.accepted_token_ids             # shape [12]: [t1, t2, -1, -1, -1, *, -1, -1, -1, -1, -1, *]
out.token_ids                      # shape [2]: [s0, s1]  (the new sampled token of each request)
out.next_n_token_ids               # shape [2, 5]: new drafts for the next step
out.next_n_token_confidence_rates  # shape [2, 5] or None
out.num_accepted_tokens_gpu        # device, [2]: [2, 0]

The engine passes accepted_token_ids to C++ without a copy, because first_token_positions is set ({{cite deepinfer/engine/llm_engine.py:698-702}}). process_outputs walks the flat array with seqlens_q: request 0 appends t1, t2, s0; request 1 appends s1. The * slots are the main token positions and are not read ({{cite csrc/engine/scheduler.hpp:873-875}}). build_request_outputs uses first_token_positions to find each request's slice ({{cite csrc/engine/outputs.hpp:203-213}}).

A prefill step has only sampled_token. next_n_token_ids is None, so a NORMAL engine pads it with vocab_size − 1 ids, shape [bs, 5] ({{cite deepinfer/engine/llm_engine.py:706-711}}).
  1. The sampler calls sampler_epilogue() on each SampledInfo and MTPPredictInfo ({{cite deepinfer/model_executor/layers/sampler.py:259-264}}). Each one starts .to("cpu", non_blocking=True).
  2. The Worker records sample_end_evt after sampling ({{cite deepinfer/worker/worker.py:167-168}}).
  3. Before the post-process, the Worker waits for that event ({{cite deepinfer/worker/worker.py:262-263}}). Only now are the CPU tensors valid.
  4. The model runner calls the post functions: the prefill one splits the prompt log-probabilities per request; the decode one turns the device counters into lists ({{cite deepinfer/model_executor/layers/sampler.py:205-210}}, {{cite deepinfer/model_executor/layers/sampler.py:293-298}}).
  5. The engine reads the fields in _process_model_outputs.

A field that sampler_epilogue moved holds a CPU tensor at once, but its values arrive later. Code that reads it before sample_end_evt.synchronize() can read old memory. The comment says the same: "call this before the last sync of the sampler" (translated, {{cite deepinfer/sequence.py:64}}).
  • SampledInfo.update, SampledInfo.from_reqcnt, DeepInferTopkInfo.update, DeepInferTopkInfo.from_reqcnt_topk and _where_update call each other, but no other file calls them.
  • is_verified_token is set to True for verified tokens ({{cite deepinfer/model_executor/layers/sampler.py:555-557}}), but no code reads it.
  • nextn on SampledInfo is read only by update (line 145).

These helpers look like the tools for a merge of two sampler passes by a mask, but the release does not use them. This site describes them, and does not guess their future use.

Where is the Sequence class defined, and why does from deepinfer.sequence import Sequence work?

In C++, in csrc/engine/sequence.hpp. sequence.py imports it from deepinfer._C.engine and lists it in __all__ ({{cite deepinfer/sequence.py:14-20}}, {{cite deepinfer/sequence.py:272-281}}).

 Why does SamplerOutput.token_ids return an empty tensor and not None when no token was sampled?

The property makes an empty IntTensor on first access ({{cite deepinfer/sequence.py:179-183}}). The engine reads output.token_ids.size(0) for every step, also for a placeholder step whose output is a fresh SamplerOutput() ({{cite deepinfer/engine/llm_engine.py:693-695}}).

 In a decode step, request 2 has first_token_positions[2] = 12 and request 3 has first_token_positions[3] = 18. Which positions of accepted_token_ids belong to request 2, and which one is not read?

Positions 12 to 17. Positions 12 to 16 are the 5 draft results; position 17 is the main token position, which process_outputs does not read ({{cite csrc/engine/scheduler.hpp:873-875}}, {{cite deepinfer/sequence.py:226-228}}).

 Which four fields of SamplerOutput stay on the device, and which component reads them? Why are they not copied to the CPU?

sampled_token_ids_gpu, predict_token_ids_gpu, num_accepted_tokens_gpu and confidence_rates_gpu ({{cite deepinfer/sequence.py:259-269}}). With ZOS, the Worker of the next step reads them on the device to correct seqlen_q and seqlen_k before the CPU has the results ({{cite deepinfer/worker/worker.py:214-243}}). A CPU copy would need a sync and would stop the overlap. See the deep dive "Every field of SamplerOutput".
