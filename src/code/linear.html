--- title: linear.py: ReplicatedLinear and the FP8 GEMM path nav_title: linear.py level: Intermediate prerequisites: learn/number-formats, concepts/low-precision-formats related: concepts/low-precision-formats, concepts/weight-loading, code/hf-weights, code/v4-mlp, code/v4-attn, concepts/mega-moe, concepts/expert-parallelism summary: Two files share the name linear.py. v4_modules/linear.py describes checkpoint weights (ReplicatedLinear and ParallelRoutedLinear containers). layers/linear.py holds the runtime ReplicatedLinear, which runs a BF16 GEMM or casts its input to FP8 and runs DeepGEMM's FP8 GEMM, plus the FP8 cast parameters that the whole model shares. ---

Purpose

layers/linear.py runs the dense, non-expert linear layers of the model and the logits {{term gemm}} on DeepGEMM, in BF16 or FP8; v4_modules/linear.py only describes the shapes of the checkpoint weights.

Where it sits

Who calls it

  • Attention makes runtime layers from merged container weights, for example q_a_kv_swa_proj and q_b_proj ({{cite deepinfer/model_executor/models/v4_modules/attn.py:284-304}}) and out_proj ({{cite deepinfer/model_executor/models/v4_modules/attn.py:152-156}}). It calls them in the forward pass ({{cite deepinfer/model_executor/models/v4_modules/attn.py:394}}, {{cite deepinfer/model_executor/models/v4_modules/attn.py:458}}, {{cite deepinfer/model_executor/models/v4_modules/attn.py:225}}).
  • Packed-KV projections use use_fp32_output where needed ({{cite deepinfer/model_executor/models/v4_modules/attn.py:337-343}}). The compressor wraps its key projection ({{cite deepinfer/model_executor/models/v4_modules/compress.py:42-46}}).
  • MoE. The gate is a BF16 runtime layer with FP32 output ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:222-227}}). The shared expert uses _replicated_linear ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:144-145}}, {{cite deepinfer/model_executor/models/v4_modules/mlp.py:244-245}}) and adds its output into the MoE output with out_acc ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:561-562}}).
  • DFlash, the draft model, makes four runtime layers ({{cite deepinfer/model_executor/models/mtp/dflash.py:57}}, {{cite deepinfer/model_executor/models/mtp/dflash.py:119}}, {{cite deepinfer/model_executor/models/mtp/dflash.py:148}}, {{cite deepinfer/model_executor/models/mtp/dflash.py:171}}).
  • The sampler computes the logits with bf16_gemm_nt into an FP32 tensor ({{cite deepinfer/model_executor/layers/sampler_utils.py:20-28}}).
  • FP8 producers share get_fp8_cast_params: RMSNorm ({{cite deepinfer/model_executor/layers/layernorm.py:50}}), the attention output ({{cite deepinfer/model_executor/models/v4_modules/attn.py:200}}), and the SwiGLU of the experts ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:140-141}}). mHC also calls it, but only in a branch for a group size other than 32, which does not run in this release ({{cite deepinfer/model_executor/models/v4_modules/hc.py:311-313}}).
  • Containers. The MoE container uses ParallelRoutedLinear for the routed experts and the container ReplicatedLinear for the gate ({{cite deepinfer/model_executor/models/v4_modules/moe.py:67}}, {{cite deepinfer/model_executor/models/v4_modules/moe.py:97-108}}). prepare_meta_fp8 reads use_fp8_gemm ({{cite deepinfer/model_executor/models/v4_modules/containers.py:128}}).

What it calls

Walk through the main methods

The two containers

  1. Lines 8-20: an ordinary nn.Linear with weight [out, in], plus use_fp8_gemm. The model is built on the meta device, so no memory is used yet ({{cite deepinfer/model_executor/models/v4_modules/containers.py:1-5}}).
  2. Line 31: nn.Linear(h_out, h_in * n_local_experts) has the weight shape [h_in · n_local, h_out]: the experts are stacked along the first axis. The docstring calls this the "expert-major" 2-D metadata.
  3. Line 34: the weight carries n_experts. The loader needs it to allocate the packed FP4 layout int8 [n_local, h_out, h_in / 2] ({{cite deepinfer/model_executor/models/v4_modules/containers.py:72-87}}).

Each rank holds only its own experts, so the split is by expert, not inside one matrix. n_local = n_physical / ep_size ({{cite deepinfer/model_executor/models/v4_modules/moe.py:94-95}}).

Runtime __init__: prepare the scales once

  1. Lines 61-62: use_fp32_output is allowed only for a BF16 weight.
  2. Line 65: the weight must be [output_size, input_size].
  3. Line 66: reconstruct_param makes a new parameter on the same data and keeps sf ({{cite deepinfer/model_executor/utils.py:22-26}}).
  4. Lines 67-76: a one-byte weight is FP8. If its scale is not yet in the platform dtype (int32 on NVIDIA, int16 on Ascend), DeepGEMM transforms it once, with the recipe (1, 32, 32). A loaded weight arrives with FP32 scales, one per 32 × 32 block ({{cite deepinfer/hugging_face/weights.py:418-420}}), so this transform runs at model build.

apply_weight_fp8: cast, check, multiply

  1. Line 146: FP8 layers have no bias.
  2. Lines 148-150: a BF16 input must be 2-D and is cast here: one E4M3 row per token and one UE8M0 scale per 32 values. An input that is already a tuple (fp8, sf) skips the cast. For example, the attention gives q_b_proj the FP8 output of its norm ({{cite deepinfer/model_executor/models/v4_modules/attn.py:458}}, {{cite deepinfer/model_executor/layers/layernorm.py:49-50}}).
  3. Lines 154-162: the output is BF16. With out_acc, the GEMM writes into that tensor.
  4. Line 164: the scales of the input and of the weight must both have the platform dtype.
  5. Line 165: out_acc is also passed as the accumulator argument c. The MoE uses this to add the shared expert to the routed output in one GEMM ({{cite deepinfer/model_executor/models/v4_modules/mlp.py:526}}).

apply_weight_bf16 and apply_weight

  1. Line 127: the output dtype is FP32 with use_fp32_output, else the input dtype.
  2. Line 135: the GEMM sees a 2-D view [m, k] of the input and a 2-D view of the output.
  3. Lines 136-137: the bias, if any, is added after the GEMM with a normal tensor add.

apply_weight selects the path: BF16 weight → line 175; one-byte weight → line 177; anything else → TypeError ({{cite deepinfer/model_executor/layers/linear.py:168-178}}).

Output allocation and the 32-byte row stride

The output row stride must be a multiple of 32 bytes. _allocate_output rounds the physical row length up and returns a narrower view. The GEMM paths assert the stride before they run ({{cite deepinfer/model_executor/layers/linear.py:134}}, {{cite deepinfer/model_executor/layers/linear.py:163}}).

Worked example (example sizes, not from the repository). An FP8 layer with N = 1,000, K = 7,168, and M = 256 tokens:

  • Weight: 7,168,000 bytes. Load-time scales: ceil(1,000/32) × 224 = 32 × 224 = 7,168 FP32 values.
  • Input cast: 256 × 7,168 bytes of E4M3, and 256 × 224 scale bytes = 256 × 56 int32 on NVIDIA.
  • Output: BF16, 16 values per 32 bytes, so the physical row is ceil(1,000 / 16) × 16 = 1,008 values. The tensor is [256, 1008], and the layer returns the view [256, 1000] with a row stride of 2,016 bytes.
  • The same layer with use_fp32_output (BF16 weight only): 8 values per 32 bytes; 1,000 is a multiple of 8, so there is no padding.

Attention merges several container weights into one runtime layer, for example Wq.A and Wkv.A into q_a_kv_swa_proj ({{cite deepinfer/model_executor/models/v4_modules/attn.py:281-288}}). merge_linear_weights concatenates the weights and their scales along the output axis, and frees the parts:

Line 55: every part except the last must have a multiple of 128 rows. Because 128 is a multiple of 32, each part then starts on a new 32-row scale block, so the concatenated scales (line 56) still belong to the right rows. The comment on line 54 says only that the last weight need not be a multiple of 128; the code does not say why the limit is 128 and not 32.

These files read no environment variable. The FP8 group size is a constant: get_fp8_casting_granularity() returns 32 ({{cite deepinfer/model_executor/layers/linear.py:13-14}}). Other code asserts this value, for example the packed FP4 expert layout ({{cite deepinfer/model_executor/models/v4_modules/containers.py:82}}). The platform scale dtype comes from PLATFORM.fp8_sf_type ({{cite deepinfer/platform.py:63}}, {{cite deepinfer/platform.py:138}}). Whether a layer is FP8 comes from the checkpoint, through use_fp8_gemm on the container.

Which DeepGEMM function does the runtime ReplicatedLinear call for an FP8 weight, and with which recipe?

deep_gemm.fp8_fp4_gemm_nt(x, weight, out, out_acc, recipe=(1, 1, 32)) ({{cite deepinfer/model_executor/layers/linear.py:165}}).

 What is the weight shape of ParallelRoutedLinear(h_in=7168, h_out=4096, n_local_experts=8) on meta?

nn.Linear(4096, 7168 × 8) gives the weight [57344, 4096]: the 8 experts are stacked along the first axis ({{cite deepinfer/model_executor/models/v4_modules/linear.py:31}}).

 When does apply_weight_fp8 skip per_token_cast, and why is that useful?

When the input is already a tuple (fp8, sf) ({{cite deepinfer/model_executor/layers/linear.py:148-150}}). A kernel that runs just before the GEMM, such as an FP8 RMSNorm, can write FP8 output directly, so the layer does not read the BF16 data again ({{cite deepinfer/model_executor/layers/layernorm.py:49-50}}).

 A BF16 layer has output_size = 1000 and returns BF16. What is the physical row length of its output, and what row stride does the returned view have?

32 bytes hold 16 BF16 values, so the row is rounded up to 1,008 values ({{cite deepinfer/model_executor/layers/linear.py:90-95}}). The view has 1,000 columns and a row stride of 1,008 elements = 2,016 bytes, which is a multiple of 32.
