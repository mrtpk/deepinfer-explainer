Purpose

These two small files hold the {{term cuda-graph}} logic: they build the list of sizes, record one graph per size at start-up, pick the right graph for a step, replay it, and free it at shutdown.

Walk through the main methods

build_graph_batch_sizes

  1. Line 43: the interval cannot be larger than the maximum.
  2. Lines 46-48: powers of two below the interval.
  3. Line 49: multiples of the interval below the maximum.
  4. Line 50: the maximum itself, always last.

Examples with interval 8: maximum 24 gives [1, 2, 4, 8, 16, 24]; maximum 6 gives [1, 2, 4, 6]; maximum 1536 gives 195 sizes.

_run_model

This function runs in the warm-up and inside the recording. With ZOS off (copy_inputs true), rank 0 copies the pinned CPU inputs to the device first, so the copy is part of the graph. With CP above 1, broadcast() sends the device tensors from rank 0 to the other ranks, also inside the graph ({{cite deepinfer/model_executor/input_metadata/input_metadata.py:120-167}}).

capture

keep_graph=True keeps the raw cudaGraph_t, so the graph timer can find its event-record nodes for the ping-pong buffer. The NPU has only an instantiated graph and does not support keep_graph.
  1. Line 89: a new capture first destroys the old graphs.
  2. Lines 93-96: max_batch_size placeholder sequences give one input object; .cuda(non_blocking=True) gives the device object. With ZOS the input builder already makes device tensors, so both objects share memory.
  3. Line 102: largest size first.
  4. Lines 104-110: _cut takes the first bs rows of every tensor. The assert makes sure that every tensor has max_batch_size rows. This is true for decode metadata, where every field is per row.
  5. Lines 113-115: the warm-up on the side stream.
  6. Lines 117-119: fields from get_clean_list() go back to None, on both objects, so the recording computes them.
  7. Lines 124-127: the recording, with the shared pool and the side stream. capture_error_mode="thread_local" limits capture errors to this thread.
  8. Lines 130-137: instantiate (NVIDIA), register with the timer, and let the default stream wait for the side stream.
  9. Lines 139-141: keep the pool of the first graph; store the graph.

select, replay and destroy

select raises ValueError when total_q is larger than the largest size. replay returns the stored output object: its tensors have graph_size rows and are the same memory in every replay of this graph. So the caller must read the result before the next replay of a graph that shares this memory. destroy also unbinds the timer.

The DFlash runner

  1. Lines 52-54: two padding inputs: one for the graph, one kept as the fill value for unused rows.
  2. Lines 58-59: sizes are numbers of sequences; each graph cuts its views with cut(num_seqs).
  3. Lines 62-71: warm-up and recording of run_drafts, with the pool and stream of the main runner. Only the driver (do_sample) copies a sampled output.
  4. Lines 84-91: replay selects by the request count, copies the real decode input into the graph's buffers (copy_dflash_decode_input, which uses the padding for the rest), replays, and cuts the output to the real count.

run_drafts reads main_input_metadata: the device object of the largest main graph ({{cite deepinfer/worker/model_runner.py:546}}). This works for every step because the input fields of all main graphs are views of the same buffers: a smaller graph writes the first rows of the same memory. (The derived fields, such as kv_swa_index, are not shared: each graph computes its own.)

The docstring explains why the two metadata objects stay separate: "Metadata objects stay separate because forward populates derived fields" ({{cite deepinfer/worker/cuda_graph_runner.py:31}}). The forward pass writes fields such as kv_swa_index into the device object only.

Example sizes. With max_num_seqs=4 and nextn=5: max_batch_size = 24, sizes [1, 2, 4, 8, 16, 24]; the decode block tables of all graphs are views of one int32 [24, 320] tensor (max_num_blocks = 320 for runtime_max_model_len = 32784). DFlash sizes: [1, 2, 4].

On NVIDIA the capture keeps the raw graph (keep_graph=True) and wraps it in a C++ GraphHandle. The handle reads the raw graph and the executable graph from raw_cuda_graph() and raw_cuda_graph_exec() ({{cite csrc/graph_timer/graph_timer_cuda.cpp:62-65}}). get_event_record_nodes walks the graph nodes and keeps the event-record nodes ({{cite csrc/graph_timer/graph_timer_cuda.cpp:67-85}}). Before each replay, flip_event_buffer swaps the events of these nodes with cudaGraphExecEventRecordNodeSetEvent ({{cite csrc/graph_timer/graph_timer_cuda.cpp:57-60}}, {{cite deepinfer/timer.py:169-187}}). The page {{link concepts/cuda-graphs}} explains why two sets of events are necessary.

On Ascend, cuda_graph_timer.supported() is false ({{cite deepinfer/timer.py:94-98}}), so the runner makes no handle. The capture logs "cuda_graph_timer probes not supported on this platform." ({{cite deepinfer/worker/cuda_graph_runner.py:90-91}}).

In which order does capture record the graph sizes, and why?

Largest first (reversed(self.batch_sizes), {{cite deepinfer/worker/cuda_graph_runner.py:102}}). The first graph sets the memory pool, and the smaller graphs reuse it ({{cite deepinfer/worker/cuda_graph_runner.py:139-140}}).

 What does select(9) return when the sizes are [1, 2, 4, 8, 16, 24]?

Size 16 and its CudaGraphData. bisect_left gives the index of the first size that is not less than 9 ({{cite deepinfer/worker/cuda_graph_runner.py:143-148}}).

 The DFlash graphs read the input metadata of the largest main graph. Why is that correct in a step that replays the size-8 main graph?

All main graphs use views of the same size-max buffers (_cut, {{cite deepinfer/worker/cuda_graph_runner.py:104-109}}). The size-8 step writes rows 0-7 of the same memory that the largest object sees, and the comment in profile_decode_perf says the buffers are shared ({{cite deepinfer/worker/model_runner.py:581}}). This is in the deep dive "Data flow".
