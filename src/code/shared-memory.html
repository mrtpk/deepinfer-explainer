The image worker writes preprocessed image tensors into it, and the engine copies them to the device with no extra copy. The file also has an unused SharedMemory class. ---

Purpose

shared_memory.py gives the image worker process and the engine process one shared block of {{term pinned-memory | pinned}} host memory, with a small allocator, so that preprocessed image tensors go from the worker to the device without a pickle and without a second copy.

The name is general, but in this release the pool has one user: images. get_multi_modal_pool() is the only factory, and it reads DEEPINFER_USE_MULTIMODAL_POOL and DEEPINFER_MULTIMODAL_POOL_SIZE_GB ({{cite deepinfer/shared_memory.py:359-363}}).

Where it sits

Who calls it

  • The engine process makes the pool. MultimodalProcessor._start_workers calls get_multi_modal_pool() and passes the pool to the worker process, which it starts with fork ({{cite deepinfer/ve/multimodal_processor.py:93-104}}). The pool is made before the fork, so the child inherits the mapping, the shared metadata and the lock.
  • The image worker allocates and writes. For each tensor of a preprocessed image, it calls alloc_tensor, copies the tensor in, stores (handle, shape, dtype) and sets the dict value to None ({{cite deepinfer/ve/multimodal_processor.py:202-211}}). Only the small handles go back over the mp.Queue.
  • The engine reads. fetch() turns each handle back into a tensor view with get_tensor ({{cite deepinfer/ve/multimodal_processor.py:296-299}}).
  • The engine frees. In the input preparation of the step whose prefill reaches the last image token, defer_expiring_pool_handles takes the handles and records a device event ({{cite deepinfer/ve/schema.py:53-65}}, called at {{cite deepinfer/ve/prepare_tensor_input_vl.py:124}}). free_deferred_pool_handles waits for that event and frees the blocks, in pre_sampler_sync of the same step ({{cite deepinfer/ve/schema.py:68-77}}, {{cite deepinfer/engine/llm_engine.py:118-119}}). Aborts free at once ({{cite deepinfer/engine/llm_engine.py:654-655}}, {{cite deepinfer/ve/multimodal_processor.py:293-295}}).
  • Shut-down. MultimodalProcessor.stop stops the workers, clears the factory cache and calls close() ({{cite deepinfer/ve/multimodal_processor.py:317-326}}).

What it calls

  • shared_memory.SharedMemory(create=True, size=...) for the data block ({{cite deepinfer/shared_memory.py:116}}).
  • PLATFORM.pin_host_memory(self.buffer): cudaHostRegister on NVIDIA, aclrtHostRegisterV2 on Ascend ({{cite deepinfer/shared_memory.py:119}}). See {{link concepts/hardware-platforms}}.
  • torch.full(...).share_memory_().numpy() for the metadata arrays ({{cite deepinfer/shared_memory.py:75-77}}).

Walk through the main methods

__init__: one pinned block and shared metadata

Multi-process shared-memory pool. The whole block self.buffer comes from multiprocessing.shared_memory, with a torch view, and is pinned. The metadata is torch storage after share_memory_(), read and written through NumPy views (shared only, not pinned). A multiprocessing.Lock makes concurrent use safe. Only CPU tensors are supported. The real large shared-memory block. SharedMemory makes it shared across processes; then it is pinned as host pinned memory to make H2D copies faster (GPU: cudaHostRegister; NPU: aclrtHostRegisterV2, see platform.py). Metadata: all shared. Head of the free-block list. Head of the free list of metadata nodes (1..max_blocks-1 can be reused). Lock: multi-process synchronization.
  1. Lines 102-107: the size must be positive, max_blocks at least 2, and align a power of two.
  2. Lines 116-119: make the block, wrap it as a uint8 tensor, pin it.
  3. Lines 123-126: four arrays of max_blocks entries (default 4096): start, size, next node and state of each node.
  4. Lines 129-132: two list heads, each a one-element shared array.
  5. Line 135: the lock. A multiprocessing.Lock works across fork, because the child inherits it.

alloc: first fit, then wait

Case 1: the same size. Turn this free node into an allocated node. Case 2: cut a piece off. This needs a new metadata node for the allocated part. The free node shrinks from the front. "Shared-memory pool short of {need} bytes, waiting for release"
  1. Line 174: round the size up to a multiple of align (64).
  2. Lines 177-212: under the lock, walk the free list from its head. The list is sorted by address, so this is first fit by address.
  3. Lines 187-195: an exact fit takes the free node itself.
  4. Lines 198-209: a larger block gives its first need bytes to a new node and keeps the rest.
  5. Lines 214-215: if no block fits, log a warning, sleep 10 ms (outside the lock) and try again. There is no time-out.

free: back in address order, then merge

Free a block, and try to merge it with free neighbours. Put it back in the free list in address order. Try to merge with the next block. Try to merge with the previous block.

A double free raises ValueError (lines 230-231). Each merge returns one node to the list of unused metadata nodes (_push_meta_node, {{cite deepinfer/shared_memory.py:160-165}}).

get_tensor and alloc_tensor: typed views

Interpret the block as a tensor view of the given dtype and shape, with no copy. Needs: the shape and dtype that were used at alloc time (rounded up; padding at the end of the block is allowed), and an offset that is aligned for the dtype (align ≥ 64 is enough for common types).

The view is a narrow of the pinned uint8 buffer, then a view(dtype) and a view(*shape). So the device copy of this tensor is a DMA from pinned memory. alloc_tensor frees the block again if the view fails (lines 306-310).

close: unpin, release, unlink

Give up ownership of the mmap: the last live view (or the exit of the process) frees the mapping. Free the large shared-memory block: remove the pinned registration, give up the mapping, unlink the name.

If a tensor view is still alive, SharedMemory.close() raises BufferError. The code then drops its own references to the mapping instead (lines 340-343) and unlinks the name anyway. The memory stays until the last view is gone.

Node ids move: after the last merge, node 0 is unused and node 1 holds the whole pool. Each free region and each allocated block uses one of the max_blocks nodes, so together they can use at most 4096 nodes. When alloc must cut a block and no unused node is left, _pop_meta_node raises MemoryError ({{cite deepinfer/shared_memory.py:152-158}}, {{cite deepinfer/shared_memory.py:197-198}}). An exact fit needs no new node (lines 187-195).

Sizes in practice. The default pool is 8 GiB = 8,589,934,592 bytes ({{cite deepinfer/environ.py:208}}). The log line counts it per rank: on a host with 8 devices it gives "expected resident 64GB" for the host (translated, {{cite deepinfer/ve/multimodal_processor.py:49-56}}).
  • The pool is made in the engine process, then the image worker is forked ({{cite deepinfer/ve/multimodal_processor.py:97-104}}). A fork copies normal memory lazily (copy-on-write). A write in one process is then not seen in the other. So the metadata must be in shared memory: share_memory_() moves each tensor storage there before the fork ({{cite deepinfer/shared_memory.py:75-77}}).
  • The data block comes from multiprocessing.shared_memory, which is shared by name and by mapping.
  • The worker calls alloc, the engine calls free, both under the same mp.Lock. get_tensor and _validate_handle read the metadata without the lock.
  • The engine starts one image worker: num_workers defaults to 1, and the engine does not pass it ({{cite deepinfer/ve/multimodal_processor.py:36}}, {{cite deepinfer/engine/llm_engine.py:213-219}}).
  • Only the process with rank <= 0 logs the pool size ({{cite deepinfer/ve/multimodal_processor.py:49}}). Each DP replica has its own engine, so each has its own pool.

This class wraps posix_ipc.SharedMemory: a named POSIX object, made with O_CREX (fail if it exists) and mode 0o777, sized with ftruncate, and mapped with mmap on the first access of buf. Its __reduce__ pickles only the name, so another process opens it by name. A search of the repository finds no import of it; the package posix_ipc==1.3.2 is in requirements.txt only for this file ({{cite requirements.txt:7}}). The pool above uses the standard multiprocessing.shared_memory instead.

Which two processes share the pool, and which one allocates?

The engine process and the forked image worker. The image worker allocates and writes the tensors ({{cite deepinfer/ve/multimodal_processor.py:205-211}}). The engine reads them and frees the blocks ({{cite deepinfer/ve/schema.py:68-77}}).

 Why is the data block pinned?

So that the copy to the device is a fast DMA from page-locked memory. The comment says so, translated: "pinned as host pinned memory to make H2D copies faster" ({{cite deepinfer/shared_memory.py:114-115}}, {{cite deepinfer/shared_memory.py:119}}).

 The pool has align = 64. A tensor of shape [3, 5] in float32 is allocated. How many bytes does the block have, and does get_tensor(handle, (3, 5), torch.float32) work?

3 × 5 × 4 = 60 bytes, rounded up to 64. get_tensor checks align_up(60) == 64 == handle.nbytes, so yes; it views only the first 60 bytes ({{cite deepinfer/shared_memory.py:285-294}}).

 Why does free_deferred_pool_handles synchronize on an event before it frees, and what could go wrong without it?

The device copy from the pool is asynchronous. Without the wait, the engine could free a block, the image worker could allocate it for a new image and overwrite it, while the old copy is still in flight. The event was recorded after the copies were issued ({{cite deepinfer/ve/schema.py:53-77}}).

 The pool is made in the engine process. Why are the metadata arrays made with share_memory_() and not as plain NumPy arrays?

The image worker is forked after the pool exists ({{cite deepinfer/ve/multimodal_processor.py:97-104}}). Plain memory is copy-on-write after a fork: the worker's alloc would change only its own copy, and the engine's free would not see it. Shared storage makes both processes see one set of metadata ({{cite deepinfer/shared_memory.py:75-77}}).
