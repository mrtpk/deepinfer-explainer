It writes draft keys from main-model features during the forward pass, makes 5 drafts per request in one pass after the verification, and stores drafts, logprobs and confidences in the MTP info pool. ---

Purpose

DFlash proposes the draft tokens of the next decode step, with their logprobs and their predicted accept chances, from the hidden states of the main model.

Where it sits

Who calls it

  • DeepseekForCausalLM.__init__ makes it when DEEPINFER_USE_NEXTN_DECODE > 0, with the main model's embedding and LM head ({{cite deepinfer/model_executor/models/deepseek.py:300-306}}).
  • DeepseekModel.forward calls update_main_cache after the last main layer, in prefill and in decode ({{cite deepinfer/model_executor/models/deepseek.py:220-223}}).
  • Sampler.forward calls decode_forward in decode steps: on the driver after the verification, on followers with no driver input ({{cite deepinfer/model_executor/layers/sampler.py:155-160}}, {{cite deepinfer/model_executor/layers/sampler.py:236-251}}).
  • ModelRunner makes the pool on the driver of non-PROMPT engines and captures the DFlash CUDA graphs after the main graphs ({{cite deepinfer/worker/model_runner.py:97-99}}, {{cite deepinfer/worker/model_runner.py:532-550}}).

  • InputMetadataV4.build_dflash_input for the fixed-stride metadata of the draft block ({{cite deepinfer/model_executor/input_metadata/dflash.py:36-84}}).
  • get_logits and process_sampling ({{cite deepinfer/model_executor/models/mtp/dflash.py:14}}), confidence_head_fused ({{cite deepinfer/model_executor/models/mtp/dflash.py:15}}).

Walk through the main methods

__init__, part 1: layers and the main-key projection

DFlash prefill_only mode: load only the parameters of the main-cache path. The main and draft projections need different contiguous layouts; the KV weights are kept twice, so memory grows a little. The number of main model layers; used to give the MTP layers their layer ids. The DFlash window_size must equal the main model's, or it cannot use the same SWA cache layout.
  1. Lines 112-114: a PROMPT engine (prefill only) needs only the main-key path. It skips the MLP, the layer norms of the DFlash layers and the heads ({{cite deepinfer/model_executor/models/decoder_layer.py:197-200}}, {{cite deepinfer/model_executor/models/mtp/dflash.py:162}}).
  2. Lines 117-123: main_kv_proj joins the KV-A weights of all DFlash layers into one linear layer with L × head_dim outputs. One matrix multiply then makes the keys of all layers.
  3. Lines 126-136: one DFlashDecoderLayer per checkpoint block. Their layer ids follow the main layers, so the KV cache has an entry for each of them.
  4. Lines 139-141: the noise token id and the window come from the checkpoint config. The block size is the number of drafts, not a config value.
  5. Lines 146-152: projection maps H × T concatenated features to H.

__init__, part 2: the heads

The HF DFlash always contains a confidence head.
  1. Lines 155-156: the Markov term exists only if dspark_markov_rank > 0.
  2. Line 159: enable_confidence is always True.
  3. Lines 165-176: markov_w1 is an embedding table [V, rank]; markov_w2 is a linear layer rank → V with float32 output.
  4. Lines 180-186: the confidence head weight is cast to BF16.

update_main_cache: keys from the target layers

  1. Lines 213-217: without prefill context parallelism, there is one feature row per query token. With it, the rows are in the mirror layout of the rank, and the positions come from positions_cp.
  2. Line 219: [rows, H × T] → [rows, H], then RMSNorm.
  3. Line 220: [rows, H] → [rows, L, head_dim].
  4. Lines 221-228: each layer normalizes, applies RoPE, casts to FP8 (e4m3 with ue8m0 scales) and writes its key into its SWA cache ({{cite deepinfer/model_executor/models/v4_modules/attn.py:928-961}}).

In decode, this method replays inside the main CUDA graph. The verification has not run yet, so it also writes keys for drafts that the sampler will reject. The docstring explains why this is safe: the next draft block writes its keys at exactly those positions, before any read ({{cite deepinfer/model_executor/models/mtp/dflash.py:204-209}}).

forward_drafts: one pass over the draft block

  1. Lines 232-239: an int tensor [R, 5], all noise ids, then column 0 = the golden token. It is flattened to [R × 5] and embedded.
  2. Lines 250-256: every DFlash layer runs on the block. Each layer writes the 5 draft keys into its cache, then attends to the main-key window (128 tokens in the docs) plus the 5 draft keys ({{cite deepinfer/model_executor/models/v4_modules/attn.py:963-1008}}).
  3. Lines 258-267: with hyper-connections, the residual streams are mixed back into one hidden state; else the residual is added.

sample_drafts: 5 drafts, one step at a time

  1. Lines 288-289: final norm, then logits for all R × 5 rows at once: float32 [R × 5, V].
  2. Lines 290-294: the sample positions of the drafts: sample_position + last_valid_offset + (1 … 5), int32 [5, R].
  3. Lines 298-306: output buffers. The logprobs have width V, or force_topk with force top-k.

The loop over the 5 steps (lines 308-334) is explained on {{link concepts/dspark}}, Step 4. After the loop:

The pool store skips requests whose write slot is 0, so the placeholder slot keeps its padding ({{cite deepinfer/model_executor/layers/mtp_info_pool.py:61-66}}).

run_drafts and decode_forward

  1. Lines 353-357: the docstring. With the DFlash CUDA graph, the broadcast, the metadata, the layers and the sampling (with the pool write) are all one graph.
  2. Line 362: a rank without driver input must be a context-parallel follower, else an assertion fails.
  3. Line 365: cp_broadcast_multi_tensor sends last_valid_offset and golden_tokens from the driver.
  4. Lines 374-376: followers stop after the layers and return None.
  5. Lines 385-387: if a graph runner exists, replay; else run eagerly.

The pool is device memory that keeps the draft data from one step to the next ({{cite deepinfer/model_executor/layers/mtp_info_pool.py:14-52}}):

  • token_ids int32 [pool_rows], logprobs float32 [pool_rows, N or V], confidence float32 [pool_rows] (initialized to 1), and logprobs_index int32 [pool_rows, N] with force top-k.
  • pool_rows = (max_num_seqs + 1) × nextn. The scheduler gives each running sequence one slot ({{cite csrc/engine/scheduler.hpp:792-800}}).
  • Slot 0: token V − 1 with logprob 0 (probability 1). With force top-k, column 0 holds id V − 1.

Worked example. max_num_seqs = 64, nextn = 5, force top-k 4096: 325 rows. Token ids 1.3 KB, logprobs 5.3 MB, index 5.3 MB, confidence 1.3 KB. Without force top-k and with the inferred V = 129280, the logprobs need 168 MB.

Who reads which slot. A sequence reads its own slot only if it has unread draft info; else it reads slot 0 ({{cite csrc/engine/sequence.hpp:149-153}}). It always writes its own slot ({{cite csrc/engine/sequence.hpp:409-413}}). The verification of step N reads what DFlash wrote in step N−1, and DFlash then writes the slot again in step N. A docstring note says that both run on the same stream, so the stream keeps this order ({{cite deepinfer/model_executor/layers/sampler.py:85}}).

DFlashCudaGraphRunner captures one graph per batch size. The sizes come from build_graph_batch_sizes(max_num_seqs, DEEPINFER_DFLASH_CUDAGRAPH_BATCH_SIZE_INTERVAL), with the default step 8 ({{cite deepinfer/worker/dflash_cuda_graph_runner.py:32-40}}).

  • Capture. Largest size first, with a warm-up run, on the graph stream and memory pool of the main graphs. The inputs are padding buffers with the noise token as golden token ({{cite deepinfer/worker/dflash_cuda_graph_runner.py:42-75}}). The main graphs must exist first ({{cite deepinfer/worker/model_runner.py:539}}).
  • Replay. Pick the smallest captured size that fits, copy the real inputs into the graph buffers, replay, and cut the output to the real request count ({{cite deepinfer/worker/dflash_cuda_graph_runner.py:77-91}}).
  • Too many requests. A batch larger than the largest size raises ValueError("No DFlash CUDA graph for ...") ({{cite deepinfer/worker/dflash_cuda_graph_runner.py:79-80}}).
  • Off switch. DEEPINFER_DFLASH_ENFORCE_EAGER=1, or no CUDA graphs at all ({{cite deepinfer/worker/model_runner.py:80-85}}).

Which two methods of DFlash run in every decode step, and who calls them?

update_main_cache, called by DeepseekModel.forward ({{cite deepinfer/model_executor/models/deepseek.py:220-223}}), and decode_forward, called by Sampler.forward ({{cite deepinfer/model_executor/layers/sampler.py:236-251}}).

 Why does DFlash keep a second copy of the KV-A weights of its layers?

The main-key projection joins the weights of all layers into one matrix, and needs another contiguous layout than the draft projection. The comment says that the KV weights are kept twice and memory grows a little ({{cite deepinfer/model_executor/models/mtp/dflash.py:117-123}}).

 A request accepted 2 drafts at input positions 49 to 54. At which positions does DFlash place its draft block, and what is the input token at the first position?

Positions 52 to 56 (a = 49 + 2 = 51, block a + 1 … a + 5) ({{cite deepinfer/model_executor/layers/tilelang_ops/get_kv_index.py:168-174}}). The first input is the golden token, the token that the sampler just made; the others are the noise token ({{cite deepinfer/model_executor/models/mtp/dflash.py:230-239}}).

 With max_num_seqs = 64 and no force top-k, how much memory do the draft logprobs of the pool use, and why so much?

325 rows × 129280 × 4 bytes ≈ 168 MB (vocabulary size inferred). The pool keeps a full row of logprobs for every draft of every slot, because the verification needs p for every token to build the residual ({{cite deepinfer/model_executor/layers/mtp_info_pool.py:20-37}}). This is in the deep dive "The MTP info pool".
