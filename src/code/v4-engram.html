--- title: v4_modules/engram.py and engram_metadata.py: the Engram runtime nav_title: v4_modules/engram.py level: Advanced prerequisites: concepts/engram, concepts/model-map related: concepts/engram, code/deepseek, code/userbuffer, code/decoder-layer, code/v4-hc, code/parallel-state, concepts/zero-overhead-scheduling summary: engram.py maps token ids to compressed ids, holds the sharded n-gram tables in a DeepEP EngramBuffer, and gates the fetched rows into the mHC trunk. engram_metadata.py builds the compressed vocabulary, the prime table sizes and the hash multipliers. ---

Purpose

These two files give a decoder layer its {{term engram | Engram}} lookup: engram_metadata.py computes the static layout once, and engram.py stores the tables and applies the rows in every forward step.

Filesdeepinfer/model_executor/models/v4_modules/engram.py (219 lines) and engram_metadata.py (116 lines), Python. The parameter containers are in engram_parameters.py (64 lines).

Where it sits

Who calls it

  • Start-up. Worker.init_engram calls CompressedTokenizer.initialize and gives the table to C++ ({{cite deepinfer/worker/base.py:304-312}}). load_model calls EngramRuntime.preallocate before the checkpoint load ({{cite deepinfer/model_executor/models/deepseek.py:502-506}}). allocate_userbuffer calls engram_runtime.initialize() ({{cite deepinfer/model_executor/models/deepseek.py:438-440}}).
  • Model build. DeepseekModel.__init__ makes NgramHashMapping and EngramRuntime ({{cite deepinfer/model_executor/models/deepseek.py:83-90}}, {{cite deepinfer/model_executor/models/deepseek.py:112-114}}). Each Engram layer makes its Engram ({{cite deepinfer/model_executor/models/decoder_layer.py:80-83}}).
  • Every request. LLMEngine.add_request calls CompressedTokenizer.encode ({{cite deepinfer/engine/llm_engine.py:564-567}}).
  • Every forward. DeepseekModel.forward calls fetch ({{cite deepinfer/model_executor/models/deepseek.py:188}}). The layer calls Engram.forward from its mHC hook ({{cite deepinfer/model_executor/models/decoder_layer.py:114-116}}).
  • ZOS decode. The input preparation reads CompressedTokenizer.lookup_table_gpu and IMAGE_SENTINEL ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:255-272}}).

What it calls

  • encode_compressed from deepinfer._C.engine ({{cite deepinfer/model_executor/models/v4_modules/engram.py:18}}); its C++ body is {{cite csrc/engine/pybind_sequence.cpp:40-46}}.
  • userbuffer.allocate_engram and the EngramBuffer methods write and fetch ({{cite deepinfer/model_executor/models/v4_modules/engram.py:181-189}}, {{cite deepinfer/model_executor/models/v4_modules/engram.py:210}}, {{cite deepinfer/model_executor/models/v4_modules/engram.py:215-218}}).
  • dist.all_gather_into_tensor on the {{term enp-group | enp group}} for the FP8 scales ({{cite deepinfer/model_executor/models/v4_modules/engram.py:96-101}}).

Walk through the main methods

CompressedTokenizer: one class, three copies of the table

  1. Line 42: before initialize, the pad id is the raw DEEPINFER_ENGRAM_PAD_TOKEN (default 2). Line 53 replaces it with the compressed id.
  2. Line 43: IMAGE_SENTINEL = -1 marks every id outside the table, which includes the image ids.
  3. Lines 49-52: a Python list (for the C++ scheduler and the C++ prepare code), a NumPy int32 array (for encode) and a device int32 tensor (for the ZOS kernel).
  4. Line 66: the C++ loop runs without the GIL.

CompressedTokenizer keeps its table in class attributes. The engine and the driver Worker share one process, so add_request sees the table that Worker.init_engram built ({{cite deepinfer/worker/base.py:309}}). release() resets it ({{cite deepinfer/model_executor/models/v4_modules/engram.py:56-60}}).

NgramEmbedding.__init__: the local shard

  1. Lines 79-83: the group is PG.engram_parallel_group(). The parameter container must have been built for the same group size and rank.
  2. Lines 86-89: weight is this rank's [num_per_part, head_dim] part. sf exists for an FP8 table.
  3. Line 93: entries per token = the number of sub-tables = (n-gram sizes) × heads.
  4. Line 94: the buffer must hold the rows for the largest batch: the decode token limit for a COMPLETION engine, else the prefill token limit.

Engram: build and forward

  1. Lines 127-131: fused_kv_projection maps sum(n_embed_per_ngram) inputs to hidden × (hc_mult + 1) outputs. The weight is the loaded one.
  2. Lines 133-137: the two gate weights, each [hc_mult, hidden], are fused once at start-up. Translated comment: "weight_hidden / weight_embed stay constant during inference, so fuse them once up front".
  3. Line 149: embed_hook() returns the fetched rows of this layer. The projection output is unflattened to [T, hc_mult + 1, hidden].
  4. Lines 151-160: engram_gate_fwd gets the trunk [T, hc_mult, hidden], kv, the fused weight, the RMS-norm eps and clamp_value = 1e-6 ({{cite deepinfer/model_executor/models/v4_modules/engram_parameters.py:55-56}}). It writes in place and gets the image mask.

EngramRuntime: one buffer for all Engram layers

  1. Lines 174-180: for FP8, head_dim must be a multiple of 32; each 32 values have one scale; the scales are packed per fp8_sf_type.
  2. Line 187: the table dtype is float8_e4m3fn or bfloat16.
  3. Lines 191-193: preallocate makes the buffer before the checkpoint load, with temporary NgramEmbedding objects. __init__ then reuses userbuffer.engram (line 168).
  4. Lines 197-203: on GPU, a CPU shard gets a "CUDA-tagged" view of the same memory, because the DeepEP write expects one.
  5. Lines 208-212: write all shards (and the all-gathered scales), then release the per-layer tensors.
  6. Lines 215-219: one fetch for all layers. The buffer returns one hook per layer, in layer order.

engram_metadata.py: layout and hash inputs

  1. Lines 70-76: at least 2-grams; all n-gram sizes have the same head count and head width.
  2. Lines 78-94: for each layer, n-gram size and head, take the next prime above vocab_size − 1 that no earlier sub-table uses. The comment says the primes are unique across all layers and heads, in config order.
  1. Lines 104-106: the hash range uses the compressed vocabulary size when compression is on.
  2. Line 109: bound = (int64 max // vocab_size) // 2, so a multiplier times an id stays inside int64.
  3. Lines 112-113: one NumPy generator per layer, seeded with seed + 10007 × layer_id; max_ngram_size odd multipliers (2k + 1). The comment warns that a change to the generator or the bound changes the table ids, so the values must match training.
  4. Line 116: the offsets come from tile_kernels.torch.engram.make_offsets.

The shape of the hashes tensor and of the fetched rows is not in this repo: both come from external kernels.

Toy config (not from a checkpoint): engram_vocab_size = 1000, 2 heads, max_ngram_size = 3, engram_head_dim = 64, hidden 4096, hc_mult = 4, enp 8.

  • Sub-tables per layer: 2 n-gram sizes × 2 heads = 4. num_entries_per_token = 4.
  • Primes for the first layer: 1009, 1013, 1019, 1021; sum 4062. Padded to 4096 (lcm(256, 8) = 256); 512 rows per rank ({{cite deepinfer/model_executor/models/v4_modules/engram_parameters.py:26-31}}).
  • One shard in FP8: 512 × 64 = 32768 bytes, plus 2 one-byte scales per row (64 / 32). Line 177 asserts groups % itemsize == 0. On Ascend (int16, itemsize 2) the 2 scales fill one pack. On NVIDIA (int32, itemsize 4) the assert fails. So on NVIDIA an FP8 table needs a head_dim that is a multiple of 128 ({{cite deepinfer/model_executor/models/v4_modules/engram.py:174-178}}).
  • fused_kv_projection: 2 × 2 × 64 = 256 inputs → 4096 × 5 = 20480 outputs.
  • Multipliers: bound = (2^63 − 1) // V // 2 for the compressed vocabulary size V.
  • All of this runs in the rank process. There is no Engram thread.
  • fetch starts the transfer early (once per forward, before the layer loop). Each layer calls its hook later ({{cite deepinfer/model_executor/models/deepseek.py:177-188}}, {{cite deepinfer/model_executor/models/v4_modules/engram.py:149}}). How DeepEP overlaps the transfer is not in this repo.
  • The shard is on the CPU unless DEEPINFER_ENGRAM_FORCE_GPU_STORAGE is on ({{cite deepinfer/model_executor/models/deepseek.py:473-477}}). The buffer reads host storage over RDMA (use_cpu_rdma_storage, {{cite deepinfer/model_executor/parallel_utils/userbuffer.py:148}}).
  • The single-rank enp group must still have a NCCL/HCCL communicator, because DeepEP reuses it. The translated comment says a null pointer would cause a segmentation fault ({{cite deepinfer/model_executor/parallel_utils/parallel_state.py:176}}).

How many EngramBuffer objects does one process make for a model with 3 Engram layers?

One. allocate passes the row counts of all layers as a list, and allocate_engram asserts that it runs only once ({{cite deepinfer/model_executor/models/v4_modules/engram.py:181-189}}, {{cite deepinfer/model_executor/parallel_utils/userbuffer.py:137}}).

 Why does CompressedTokenizer keep a device copy of the table, when add_request already compresses the prompt on the CPU?

Under ZOS the newest sampled and draft tokens of a running sequence are only on the device. gather_engram_tokens_zos must compress them there, with lookup_table_gpu ({{cite deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:255-272}}).

 What makes the hash multipliers the same on every rank and in every run?

Each layer uses np.random.default_rng(seed + 10007 × layer_id) with seed = 0 by default ({{cite deepinfer/model_executor/models/v4_modules/engram_metadata.py:101}}, {{cite deepinfer/model_executor/models/v4_modules/engram_metadata.py:111-113}}). The comment warns that a change to the generator or the bound changes the table ids.

 In the toy example of the deep dive, why does head_dim = 64 fail on NVIDIA but not on Ascend?

FP8 tables have one scale per 32 values, so 64 values give 2 scale groups. The scales are packed into fp8_sf_type: int32 (4 per pack) on NVIDIA and int16 (2 per pack) on Ascend ({{cite deepinfer/platform.py:63}}, {{cite deepinfer/platform.py:138}}). Line 177 asserts groups % itemsize == 0: 2 % 4 ≠ 0 fails, 2 % 2 = 0 passes ({{cite deepinfer/model_executor/models/v4_modules/engram.py:175-178}}).
