It also defines the status enum, the finish reasons and the image token offsets. ---

Purpose

sequence.hpp defines the record that the engine keeps for each request, and the small view of it that each step sends to the model and the sampler.

Filecsrc/engine/sequence.hpp, 419 lines of C++ in one header. Most comments are in Chinese.
Main classesstruct Sequence ({{cite csrc/engine/sequence.hpp:275}}) and struct SequenceMetadata ({{cite csrc/engine/sequence.hpp:325}}). Also the enums MMTokenOffset and SequenceStatus, and eleven helper structs (from SequenceData to SequenceInit).
Runs inCPU memory of the engine process. A Sequence lives in a std::shared_ptr; the scheduler queues and Python share it. No device code.
Used byscheduler.hpp, block_manager.hpp, mtp_varlen.hpp, outputs.hpp, prepare_sample.hpp, process_output.hpp, input_metadata/prepare_tensor_input.hpp, zos.cpp, and the bindings in pybind_sequence.cpp.
CallsOnly Python attribute reads: the constructor copies values out of the SamplingParams object ({{cite csrc/engine/sequence.hpp:103-115}}, {{cite csrc/engine/sequence.hpp:185-190}}).
Not in this fileThe queue logic (scheduler.hpp), the block allocator (block_manager.hpp), and the Python names of the fields (pybind_sequence.cpp).

Where it sits

Who uses it

  • Python makes a Sequence through the binding constructor, which builds a SequenceInit ({{cite csrc/engine/pybind_sequence.cpp:93-102}}). LLMEngine.add_request calls it ({{cite deepinfer/engine/llm_engine.py:594-598}}). Scheduler::fork_seq makes one in C++ ({{cite csrc/engine/scheduler.hpp:1074-1101}}).
  • The scheduler reads and writes almost every field (the page {{link code/scheduler-hpp}}).
  • The block manager fills cache.block_table and cache.state_id ({{cite csrc/engine/block_manager.hpp:207-214}}).
  • The schedule step makes one SequenceMetadata per scheduled sequence from the object pool ({{cite csrc/engine/scheduler.hpp:706-707}}).
  • The sampler preparation and the ZOS code read SequenceMetadata fields and call is_last_prompt_chunk and refresh_for_sampling ({{cite csrc/engine/prepare_sample.cpp:20-22}}, {{cite csrc/engine/zos.cpp:293-303}}).
  • The output builder reads the status, the lengths and the MTP values ({{cite csrc/engine/outputs.hpp:194-294}}).
  • Python imports the classes from deepinfer._C.engine through deepinfer/sequence.py ({{cite deepinfer/sequence.py:14-20}}).

What it calls

Nothing outside the file, except py::object::attr for the sampling values and deepinfer::EnableObjectPool, the base class that marks pool objects ({{cite csrc/utils/object_pool.hpp:12-15}}).

Walk through the main methods

Image tokens, statuses and reasons

Offset of the special image tokens above vocab_size. The real token_id = vocab_size + offset. Python: deepinfer.multimodal_tokens.ImageTokenOffset. <image>, the real image token Number of special image tokens (IMAGE_START to IMAGE_END, 5 in total)
  1. Lines 21-28: five ids above the vocabulary. Only IMAGE (+2) and IMAGE_PAD (+1) appear in token lists ({{cite csrc/engine/scheduler.hpp:233-234}}); the scheduler uses them to protect image units in chunks ({{cite csrc/engine/scheduler.hpp:91-92}}).
  2. Lines 30-41: ten status values. SWAPPED exists, but no code sets it.
  3. Line 43: "finished" is an order test, so every value after FINISHED_STOPPED counts.
If the KV cache is about to overflow, we stop the task that uses the most KV cache by force.

The comment at line 56 describes the intent. The scheduler picks the victim by output length only ({{cite csrc/engine/scheduler.hpp:624-625}}).

SequenceData: the token list

  1. Lines 70-78: the Python path copies a C-contiguous int32 NumPy array with one memcpy. No value check happens here. add_request checks the ids before ({{cite deepinfer/engine/llm_engine.py:581-589}}).
  2. Line 83: the output length is computed, not stored: len − prompt_len. After a recompute, the prompt length does not change, so the old outputs still count as outputs.
  3. Line 85: get_last_token_id reads back(). On an empty list this is undefined behaviour; add_request refuses empty prompts ({{cite deepinfer/engine/llm_engine.py:553-554}}).

SamplingScalars and StoppingCriteria

Sampler inputs that are copied into SequenceMetadata in every step.

The constructor of Sequence calls capture once ({{cite csrc/engine/sequence.hpp:280-281}}). So a later change to the Python SamplingParams object does not reach the C++ copy. A missing attribute raises a Python error (AttributeError) when the sequence is made. StoppingCriteria copies only max_tokens and ignore_eos ({{cite csrc/engine/sequence.hpp:181-191}}).

MtpState: draft tokens

Reference token list, read by output length. The last token output in the previous round, which is the golden token of this round. Tokens verified in the previous round (the SO matcher needs them to update its automaton). Draft tokens made in the previous round. Estimated accept rates of the previous round's drafts (after the running product). If empty, the scheduler pads 1.0 when drafts exist, else 0.0. accept_rates of the round before; process_MTPInfo shifts it from accept_rates every round. Estimated accept rates of the previous round's drafts (before the product). If empty, SequenceMetadata shows an empty tensor. confidence_raw of the round before; only metrics read it (see outputs.hpp). Request slot in the global MTP info pool; 0 = padding / not allocated. Is there draft info that the sampler has not read yet? Number of rounds that finished process_MTPInfo (aborted ones also count, like schedule_cnt). Number of rounds scheduled (prompt and decode). The difference to process_cnt tells which round accept_rates belongs to; see MTPVarlen::schedule. Keep accepted_tokens (the SO matcher still needs them after a recompute) and prev_confidence_raw (only for metrics).
  1. Lines 127-128: info_slot is the row of this sequence in the device-side MTP pool. The scheduler gives slots 1 … max_num_seqs ({{cite csrc/engine/scheduler.hpp:792-800}}).
  2. Lines 134-142: a recompute clears the draft state and both counters.
  3. Lines 149-153: take_draft_info_slot returns the slot only once per new draft info, then clears the flag. A second read in the same round gets slot 0 (padding).

next_golden_tokens returns 2 × nextn + 1 reference tokens, from position output_len on, padded with -1. Example: 10 golden tokens, output length 7, nextn = 5: positions 7 … 17, so [g7, g8, g9, -1, -1, -1, -1, -1, -1, -1, -1]. With no golden tokens, or output length 10 or more, it returns nothing.

KvCacheState: the cache counters

When a hit count comes from outside, set the base for the increment at the same time.
  1. Line 203: num_tokens is the number of tokens whose KV entries are written (Python: num_cached_tokens).
  2. Line 206: block_table lists physical block ids. A real sequence never gets block 0 ({{cite csrc/engine/block_manager.hpp:27-35}}); only the placeholder step uses it.
  3. Line 207: state_id = -1 means "no state slot".
  4. Lines 216-219: advance_optimistically(n) remembers the old value and adds n.
  5. Line 221: commit_processed_tokens(n) sets the value to the old one plus n. Together, the two calls first assume that all query tokens are kept, then correct the value.

hit_tokens only goes from a parent to a fork ({{cite csrc/engine/scheduler.hpp:1086}}), and swa_valid_start is only reset to 0 in this file. No code in this release sets a value other than 0 for it, but the flop estimate and the tensor preparation read it.

SequenceScheduleState: status and in-flight tokens

0: not started; 1: just started (at the boundary); 2: started; -1: aborted.
  1. Line 237: schedulable defaults to false here, but the binding sets it from the multimodal data ({{cite csrc/engine/pybind_sequence.cpp:35}}).
  2. Line 238: branch_id is "default". A fork waits with a _ prefix until its prefill is set up ({{cite csrc/engine/scheduler.hpp:398}}, {{cite csrc/engine/scheduler.hpp:423}}).
  3. Lines 244-247: schedule() adds nextn + 1 in-flight tokens for each scheduled step.
  4. Lines 249-256: process_outputs removes one step. If only one step was in flight, both counters go to 0. If two were in flight (ZOS), the total becomes the size of the last one.

Sequence: the record

  1. Lines 280-281: copy the sampling and stop values once.
  2. Line 282: the first "last output token" is the last prompt token.
  3. Lines 286-289: reserve room for max_tokens more ids in both token lists.
  4. Lines 291-293: the number of blocks: ceil((len + total_inflight_tokens + drafts) / block_size). This is the core of all block decisions.
  5. Lines 307-311: a recompute resets the cache, schedule and MTP parts. The tokens stay.

SequenceMetadata: the per-step view

A dummy that Python makes (empty placeholder run / profile / CUDA graph padding) has no host Sequence. Its borrowed members point to this self-owned storage instead; on the pool path this is always nullptr.
  1. Lines 342 and 349: request_id and block_table are C++ references into the Sequence. A block added to the sequence later is visible through the metadata.
  2. Lines 346-348: pointers to the token lists; prompt_tokens is set only for prefill.
  3. Line 354: sampling is a copy, so the sampler reads plain numbers.
  4. Lines 357-358: seqlen_q (query tokens of this step) and seqlen_k (tokens after this step, including in-flight ones).
  5. Lines 363-365: the last output token and the two MTP pool slots (read and write).
  6. Line 371: prompt_logprobs is a reference, so prompt log-probabilities of several chunks add up in the Sequence ({{cite csrc/engine/process_output.hpp:23-27}}).
A prefill chunk that is not the last one makes no token in this step; the sampler uses -1 to skip the SO update.

Line 382 calls take_draft_info_slot(), so building the metadata also clears has_draft_info. Lines 392-404 are a second constructor for Python dummies: the borrowed members point into owned, and the object never goes back to a pool. is_placeholder is true when the id is "placeholder" ({{cite csrc/engine/sequence.hpp:398}}).

  1. Line 406: the last prompt chunk is the one that reaches the full length.
  2. Lines 408-418: with ZOS, the metadata was made before the previous step was processed. refresh_for_sampling copies the newest values just before sampling ({{cite csrc/engine/zos.cpp:300-302}}). It keeps the old write slot if the sequence already gave back its slot.

The Python names come from {{cite csrc/engine/pybind_sequence.cpp:109-137}}. Most bindings are read-write, through a helper that returns a reference to the field ({{cite csrc/engine/pybind_sequence.cpp:13-18}}).
  • Sequence. Held by std::shared_ptr (SequencePtr, {{cite csrc/engine/scheduler.hpp:34}}). The scheduler queues, SchedulerOutputs lists and Python handles share it. It dies when the last holder lets go.
  • SequenceMetadata from the pool. It holds references into its Sequence (request_id, block_table, mtp, prompt_logprobs) and raw pointers to the token lists. It must not outlive the Sequence. The engine keeps the step's SchedulerOutputs (and so the shared_ptrs) alive in the step state while the metadata is in use, and gives the metadata back one step later ({{cite deepinfer/engine/llm_engine.py:1013}}).
  • SequenceMetadata from Python. The second constructor owns its strings and vectors in owned, and the binding keeps seq_data and compressed_seq_data alive with keep_alive ({{cite csrc/engine/pybind_sequence.cpp:149-153}}).
  • Pool reuse. The pool destroys a released object and builds the next one in the same memory with placement new ({{cite csrc/utils/object_pool.hpp:26-31}}, {{cite csrc/utils/object_pool.hpp:34-41}}). So a Python reference to an old metadata object sees the new contents after reuse.

Which status values count as finished?

Every value from FINISHED_STOPPED on: is_finished is the test status >= FINISHED_STOPPED ({{cite csrc/engine/sequence.hpp:43}}). That is seven values.

 A sequence has 260 tokens, 6 tokens in flight and 5 drafts. The block size is 128. How many blocks does it need?

ceil((260 + 6 + 5) / 128) = ceil(271/128) = 3 ({{cite csrc/engine/sequence.hpp:291-293}}).

 The scheduler adds a block to a sequence after its SequenceMetadata was made. Does the metadata see the new block?

Yes. block_table in SequenceMetadata is a reference to seq->cache.block_table, not a copy ({{cite csrc/engine/sequence.hpp:349}}, {{cite csrc/engine/sequence.hpp:379}}).

 With ZOS, two steps of a sequence are in flight: total_inflight_tokens = 12, last_inflight_tokens = 6. The older step is processed with 1 accepted draft, and num_tokens was 500. What are the three counters after process_outputs?

finish_inflight_step sees 12 != 6, so total_inflight_tokens = 6 and last_inflight_tokens stays 6 ({{cite csrc/engine/sequence.hpp:249-256}}). advance_optimistically(6) gives 506, then commit_processed_tokens(2) gives num_tokens = 502 ({{cite csrc/engine/sequence.hpp:216-221}}).
