GPUs, kernels, and speed

BeginnerLearn the basicsabout 9 min read + 7 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

In one sentence

A GPU runs kernels on many compute units at the same time. A kernel is fast only when it does not wait for memory or for the CPU.

The idea#

What is inside a GPU?#

A GPU is a chip with many small compute units. NVIDIA calls one unit a Streaming Multiprocessor (SM). A data-center GPU has more than 100 SMs. Each SM runs many threads at the same time, and has Tensor Cores that multiply small matrix tiles in one instruction.

The memory has levels. Far memory is large and slow. Near memory is small and fast:

LevelWhereSize (rounded)Who uses it
HBM (device memory)next to the chip80-192 GB, 3-8 TB/severything: weights, KV cache, activations
L2 cacheon the chiptens of MBall SMs (shared)
shared memory (SMEM)in each SMup to about 228 KiBthe threads of one thread block
registersin each SM256 KiB per SMone thread each

Simplified

The numbers are rounded values for recent NVIDIA data-center GPUs. For example, an H100 has 132 SMs, 80 GB of HBM and a 50 MB L2 cache. Each GPU model has its own exact values. This site does not depend on them.

Kernels and launches#

A kernel is one program that runs on the device. The CPU starts it with a kernel launch. The launch gives a grid of thread blocks. Each block runs on one SM, and all its threads run the same code on different data.

A typical kernel has three phases:

  1. Load a tile of data from HBM into shared memory or registers.
  2. Compute on the tile.
  3. Write the result back to HBM.

A model forward pass is a long list of kernels: matrix multiplies (GEMMs), attention, norms, activations and communication. One launch costs a few microseconds of CPU time.

Memory-bound and compute-bound#

A kernel waits for one of two things: bytes from memory, or math. The arithmetic intensity of a kernel tells which one:

arithmetic intensity = FLOPs / bytes moved        (FLOP per byte)
attainable FLOP/s    = min(peak FLOP/s, bandwidth × intensity)
ridge point          = peak FLOP/s / bandwidth

This is the roofline model. A kernel with an intensity below the ridge point is memory-bound. A kernel above it is compute-bound.

A worked example. Take a BF16 peak of 2,250 TFLOP/s. DeepInfer uses this value for NVIDIA SM100 on x86 (see "In DeepInfer"). Take an illustrative HBM bandwidth of 8 TB/s. The ridge point is 2,250 / 8 ≈ 281 FLOP per byte.

  • Element-wise add of two BF16 vectors. 1 FLOP per element; 6 bytes per element (read 2 + 2, write 2). Intensity 1/6. Always memory-bound.
  • Decode GEMM, 1 token. Weight [4,096, 4,096] BF16. About 2 FLOPs per weight, 2 bytes per weight. Intensity about 1. Memory-bound: 4.2 µs to read 33.6 MB, but only 0.015 µs of math.
  • Prefill GEMM, 4,096 tokens. Same weight. Intensity about 4,096 / 3 ≈ 1,365. Compute-bound.

For a GEMM with a small batch, the intensity is about the batch size (deep dive "The roofline, with formulas"). So a memory-bound GEMM gets more tokens almost for free. The page Batching uses this result.

Streams and events#

The CPU does not wait for each kernel. It puts kernels into a stream, a queue that the device runs in order. Kernels in two different streams can run at the same time. For example, a communication kernel can run next to a compute kernel.

An event is a marker in a stream. The CPU can record an event and later wait for it. Another stream can also wait for it. Events let the CPU continue with useful work and stop only at the point where it needs a result.

CUDA graphs: why launch overhead matters#

A decode step has small kernels. Many of them finish in a few microseconds, which is about the time that the CPU needs to launch one kernel. Then the device waits for the CPU between kernels.

A CUDA graph solves this. The engine runs the forward pass once in capture mode: the driver records every launch and does not run it. Later, one replay() call starts the whole list. The CPU cost is one call instead of hundreds.

A graph records fixed addresses and fixed shapes. So the engine captures one graph per batch size, and pads a batch up to the next captured size.

A worked example (illustrative). A decode step has 800 kernels. Each launch takes 4 µs of CPU time, and the kernels take 6 ms of device time in total. Eager launches need 800 × 4 µs = 3.2 ms of CPU time. That is about half of the device time, and any CPU delay adds to the step. With a graph, the CPU needs one call, and the kernels start one after the other with no gaps.

NPUs in brief#

An NPU is Huawei's Ascend AI chip. The same ideas apply: device memory (HBM), compute units, kernels, streams, events and graphs. The compute unit is the AI Core, with a Cube unit for matrix math and a Vector unit for other math. The software stack is CANN, and PyTorch reaches it through torch_npu.

Simplified

This is only an outline of the Ascend design. The page Hardware platforms: NVIDIA and Ascend explains what DeepInfer changes on Ascend.

An everyday comparison#

Think of a large kitchen. The storeroom (HBM) holds all food, but it is far away. Each cook (SM) has a small worktop (shared memory) and two hands (registers). A cook carries food to the worktop, cooks it, and carries the dish back. If a dish needs little cooking, the cooks spend most of their time walking: the kitchen is memory-bound. The head chef (CPU) gives orders one at a time. A CUDA graph is a printed list of all orders for the evening.

The comparison stops here: real cooks do different tasks, but all threads of a GPU block do the same instruction on different data. And the device does not get tired: speed depends only on bytes, FLOPs and launches.

The picture#

Read panel 2 from left to right. A kernel moves right when it does more math per byte, for example with a larger batch. Below the ridge, the kernel goes as fast as memory allows. Above the ridge, it goes as fast as the math units allow.

Deep dive

The roofline, with formulas and worked numbers

GEMM. For C[M, N] = A[M, K] × B[K, N], with b bytes per value:

FLOPs = 2·M·N·K                         (one multiply and one add per term)
bytes = b·(M·K + K·N + M·N)             (read A, read B, write C, once each)
intensity = 2·M·N·K / (b·(M·K + K·N + M·N))

In decode, M (tokens) is small and N, K (weight size) are large. Then K·N dominates the bytes, and intensity ≈ 2·M / b. For BF16 (b = 2) that is about M. For FP8 weights (b = 1 for the weight) it is about 2·M: smaller weights also make a GEMM less memory-bound. See Number formats: BF16, FP8, FP4.

Worked numbers. N = K = 4,096, BF16, peak 2,250 TFLOP/s, bandwidth 8 TB/s. Time = max(bytes / bandwidth, FLOPs / peak).

MFLOPsBytesIntensityMemory timeMath timeBound by
133.6 M33.6 MB1.04.2 µs0.015 µsmemory
642.15 G34.6 MB624.3 µs0.95 µsmemory
2819.4 G38.2 MB2474.8 µs4.2 µsmemory (close)
51217.2 G42.0 MB4095.2 µs7.6 µsmath
4,096137 G101 MB1,36512.6 µs61 µsmath

From M = 1 to M = 64, the work grows 64 times, but the time grows only from 4.2 µs to 4.3 µs.

Attention in decode. Attention reads the KV cache of each sequence once per step. Its intensity does not grow with the batch, because each sequence has its own cache. With classic multi-head attention, it does only a few FLOPs per byte, so decode attention stays memory-bound. In DeepInfer, all query heads share one KV head, and a decode step sends 6 tokens per sequence. Both give more FLOPs per cache byte, but the intensity still does not grow with the batch. In DeepInfer, one main cache entry (one token, or one compressed group of tokens) is 528 bytes (FP8) or 288 bytes (FP4) per layer (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:109-128). Smaller entries mean less to read; see The KV cache.

Simplified

Real kernels do not reach the full peak, caches can serve some reads, and many kernels overlap. The roofline gives an upper limit and the right intuition, not an exact time.

Deep dive

Grids, blocks and threads: one DeepInfer kernel

The gather kernel copies rows of a table: y[i] = x[index[i]]. The embedding layer uses it to look up token vectors (deepinfer/model_executor/layers/vocab_parallel_embedding.py:22-24). It is short, so it shows the parts of a kernel well:

  1. Lines 14-20: gather_tl is a kernel factory. Its arguments are compile-time values: row width D in bytes, dtypes, stride, and 256 threads per block. TileLang compiles one kernel per set of values.
  2. Lines 24-41: the factory picks a tile. BD bytes of a row and BM rows go to one block. nbd × nbm is the number of blocks.
  3. Line 49: T.Kernel(nbd * nbm, threads=threads) is the launch grid: one dimension of blocks, 256 threads each.
  4. Lines 52-53: T.alloc_fragment makes buffers in registers, spread over the threads of the block.
  5. Lines 58-67: each block loads its index values and reads the rows from HBM into registers. An index out of range gives zeros. Then the block copies the rows to the output in HBM.

Worked example. The interface views every tensor as int8 bytes (deepinfer/model_executor/layers/tilelang_ops/gather.py:56-59). A BF16 row of 4,096 values is 8,192 bytes, so D = 8,192. Take 1,536 tokens.

  1. D > 128, so C = 16,384 and reg_buf_size = 4,096 (lines 30-34).
  2. BD = min(next power of 2 of 8,192, 16,384) = 8,192. BM = 16,384 / 8,192 = 2 rows per block.
  3. buf_n = 4,096 bytes; buf_m = min(2, 4,096 / 4,096) = 1. One pass moves 4,096 bytes with 256 threads: 16 bytes per thread, one vector load. The comment on line 31 gives this aim.
  4. nbd = 1 and nbm = ceil(1,536 / 2) = 768. The grid has 768 blocks of 256 threads.

The kernel does no math at all: it reads 12.6 MB and writes 12.6 MB. It is fully memory-bound, so its only aim is wide, aligned memory access.

Deep dive

Streams, events and SMs for communication in DeepInfer

Events mark the end of a step. After the sampler is launched, the worker records sample_end_evt (deepinfer/worker/worker.py:167-168). The CPU waits on it in the post-processing of that step (deepinfer/worker/worker.py:262-263). With ZOS, the worker post-processes a decode step one step later, so in between the CPU prepares the next step. A prefill step, or a run without ZOS, is post-processed at once (deepinfer/worker/worker.py:182-187). See Zero-overhead scheduling (ZOS).

No hidden synchronization. The forward launch runs inside forbid_cuda_sync() (deepinfer/worker/model_runner.py:321-329). The guard raises on any blocking copy or stream synchronize in that scope. Event waits are not covered, so planned sync points still work (deepinfer/utils.py:119-132).

A side stream for capture. The CUDA graph runner warms up and captures on its own graph_stream. It first waits for the current stream, and at the end the current stream waits for it (deepinfer/worker/cuda_graph_runner.py:113-115, deepinfer/worker/cuda_graph_runner.py:137).

Communication takes SMs. A communication kernel runs on SMs too. DeepInfer limits the SMs that each library may use:

  • NCCL groups get max_ctas = min_ctas = DEEPINFER_NCCL_NUM_SMS, default 32 (deepinfer/platform.py:75-83, deepinfer/environ.py:108).
  • For the MoE buffer, if DEEPINFER_USERBUFFER_COMM_SMS is 0 (the default), DeepInfer asks DeepEP for the SMs it needs. It always keeps min(32, SMs / 4) SMs for compute (deepinfer/model_executor/parallel_utils/userbuffer.py:86-90).
  • While the shared expert runs, limit_num_sms tells the GEMM libraries to leave DEEPINFER_USERBUFFER_COMM_SMS SMs free for the MoE communication (deepinfer/model_executor/parallel_utils/userbuffer.py:40-51, deepinfer/model_executor/models/v4_modules/mlp.py:602-603).

Worked example. A device has 148 SMs, and DeepEP asks for 64. Compute keeps min(32, 148 // 4) = 32 SMs. Communication gets min(64, 148 − 32) = 64 SMs. While the shared expert runs, the GEMM libraries use 148 − 64 = 84 SMs.

Deep dive

CUDA graphs in DeepInfer: sizes, capture and replay

Which sizes. The runner captures graphs up to max_num_seqs × (1 + nextn) tokens (deepinfer/worker/model_runner.py:76-79). The size list has powers of two below the interval, then steps of the interval (deepinfer/worker/cuda_graph_runner.py:41-51):

Worked example with the defaults: 256 × 6 = 1,536 and interval 8 (DEEPINFER_CUDAGRAPH_BATCH_SIZE_INTERVAL, deepinfer/environ.py:155). The list is [1, 2, 4, 8, 16, 24, …, 1,528, 1,536]: 3 + 191 + 1 = 195 graphs.

Capture (deepinfer/worker/cuda_graph_runner.py:82-141):

  1. Build input metadata for the largest size, with placeholder sequences, and copy it to the device (lines 93-96).
  2. Go from the largest size to the smallest (line 102). Each size uses slices of the same buffers (lines 104-110).
  3. Run the model once to warm up (lines 112-115). Then capture it into a torch.cuda.CUDAGraph (lines 124-128).
  4. All graphs share one memory pool: the first graph makes it, the others reuse it (lines 139-140). The first graph is the largest one.

Replay. For a decode batch of total_q tokens, select() takes the smallest captured size that is not smaller (deepinfer/worker/cuda_graph_runner.py:143-148). The runner fills the static input buffers and pads with placeholder entries (deepinfer/worker/model_runner.py:184-191). Then replay() calls graph.replay() once (deepinfer/worker/cuda_graph_runner.py:150-154).

Example: 37 sequences × 6 tokens = 222 tokens. The graph of size 224 runs, with 2 padding tokens (0.9 % waste). With 3 tokens, the graph of size 4 runs.

Ascend. On NPU the same class works through torch.cuda, which torch_npu maps to torch.npu (deepinfer/platform.py:120-123). NPU graphs have no keep_graph argument and need no instantiate() (deepinfer/worker/cuda_graph_runner.py:121-132).

Switches. DEEPINFER_ENFORCE_EAGER turns graphs off, and a PROMPT engine never uses them (deepinfer/worker/model_runner.py:73).

What can go wrong#

  • A batch larger than the largest graph. select() raises ValueError("No captured graph for total_q=...") (deepinfer/worker/cuda_graph_runner.py:144-146). The scheduler normally prevents this, because a decode batch has at most max_num_seqs × (1 + nextn) tokens.
  • A sync inside the forward pass. A .item() or .cpu() in model code raises under forbid_cuda_sync(). For debugging only, DEEPINFER_DISABLE_SYNC_GUARD=1 turns the guard off (deepinfer/utils.py:127-131).
  • A kernel that one platform does not have. If the selected backend has no factory with that name, ops raises KernelUnavailableError (deepinfer/model_executor/layers/tilelang_ops/ops.py:25-32).
  • An unsupported NVIDIA GPU. get_bf16_tflops_limit() raises RuntimeError("unknown GPU type") for an NVIDIA GPU that is not SM 10.x (deep_cluster/hardware/device.py:151-156). The engine calls it at start-up (deepinfer/engine/llm_engine.py:304).
  • Eager mode is slow. With DEEPINFER_ENFORCE_EAGER=1, every decode kernel needs its own launch, so small batches become CPU-bound.

Why it matters. Most inference speed work does one of three things. It moves fewer bytes (smaller formats, fused kernels). It does more math per byte (larger batches). Or it removes CPU gaps (graphs, overlap). When you read a DeepInfer optimization, ask which of the three it does.

Check yourself#

  1. 1
    A kernel adds two vectors element by element. Is it memory-bound or compute-bound? Why?
    easy
    Show answer

    Memory-bound. It does 1 FLOP for every 6 bytes it moves (two BF16 reads, one BF16 write). Its intensity, 1/6 FLOP per byte, is far below any ridge point.

  2. 2
    The peak is 2,250 TFLOP/s and the bandwidth is 8 TB/s. A BF16 GEMM has a 4,096 × 4,096 weight. About how many tokens must it have before math sets its time?
    medium
    Show answer

    The ridge point is 2,250 / 8 ≈ 281 FLOP per byte. For a small batch, the intensity is about the batch size M. So M must be about 281 or more. The deep dive table gives 4.8 µs for memory and 4.2 µs for math at M = 281. At 512, math wins.

  3. 3
    Why does DeepInfer capture many CUDA graphs and not only one?
    medium
    Show answer

    A graph records fixed shapes and addresses, so it fits only one batch size. The runner captures one graph per size in a list (195 sizes with the defaults) and pads a batch up to the next size (deepinfer/worker/cuda_graph_runner.py:41-51, deepinfer/worker/cuda_graph_runner.py:143-148).

  4. 4
    A decode step has 50 sequences, each with 6 tokens, and the defaults are in use. Which graph size runs, and how many padding tokens does it have?
    hard
    Show answer

    50 × 6 = 300 tokens. The sizes above 8 are multiples of 8, so bisect_left selects 304 (deepinfer/worker/cuda_graph_runner.py:143-148). Padding: 304 − 300 = 4 tokens.

  5. 5
    A device has 132 SMs. DeepEP asks for 128 SMs and DEEPINFER_USERBUFFER_COMM_SMS is not set. How many SMs does DeepInfer give to MoE communication?
    hard
    Show answer

    Compute keeps min(32, 132 // 4) = 32 SMs. Communication gets min(128, 132 − 32) = 100 SMs (deepinfer/model_executor/parallel_utils/userbuffer.py:86-90).
