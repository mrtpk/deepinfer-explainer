Parallelism basics

BeginnerLearn the basicsabout 8 min read + 5 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Batching Beginner
  • GPUs, kernels, and speed Beginner

In one sentence

Parallelism splits the work of one model over many devices; the devices then exchange data with collective operations.

The idea#

Why use more than one device?#

There are two reasons. First, a large model does not fit in the memory of one device. Second, one device is too slow for the number of requests. So the engine runs on many devices. Each device is driven by one process, the rank.

The ranks must then split the work and exchange data. There are five common ways to split the work. Each way splits a different thing, and each way needs a different kind of communication.

Five ways to split the work#

NameWhat each rank holdsWhat the ranks exchangeIn DeepInfer
Data parallel (DP)a full copy of the model part; its own requestsnothing in the forward passyes, for attention
Tensor parallel (TP)a slice of every weight matrixan all-reduce (or all-gather) in every layerno
Pipeline parallel (PP)some of the layers (a stage)activations, from one stage to the nextno
Context parallel (CP)a part of the tokens of one long promptkeys and values (all-gather)yes, for prefill
Expert parallel (EP)some of the experts of each MoE layertokens to experts and back (all-to-all)yes, for the experts

Real systems combine them. A common plan for an MoE model is "attention DP, MoE EP". Every rank keeps the full attention weights and its own requests, but holds only some of the experts. This is the plan of DeepInfer (README.md:12).

Collectives, with small numbers#

A collective operation is a communication step in which all ranks of a group take part. Every rank calls the same function, and every rank gets a result. Here are the four that this site uses, with three ranks:

CollectiveRank 0 givesRank 1 givesRank 2 givesEach rank gets
all-reduce (sum)[1, 2][3, 4][5, 6][9, 12]
all-gather[1, 2][3, 4][5, 6][1, 2, 3, 4, 5, 6]
all-to-all[1, 2, 3][4, 5, 6][7, 8, 9]rank 0: [1, 4, 7]; rank 1: [2, 5, 8]; rank 2: [3, 6, 9]
broadcast from rank 0[1, 2](anything)(anything)[1, 2]

In an all-to-all, rank j gets part j of every rank. That is a transpose of the data over the ranks. MoE uses it: each rank sends each token to the rank that holds its expert.

All-reduce has more than one use. With "sum" it adds partial results, as in TP. With "max" or "min" it works as a vote: all ranks learn the same answer to a yes/no question.

The cost of communication#

Communication takes time, and it also uses SMs and memory bandwidth on the device. Links inside one machine or rack (NVLink on NVIDIA) are much faster than the network between machines. So the plan tries to keep heavy traffic on fast links. A simple cost rule for a ring all-reduce of S bytes over n ranks: each rank sends and receives 2 × (n − 1) / n × S bytes.

Example: an all-reduce of 16 MiB over 8 ranks. Each rank sends 2 × 7/8 × 16 = 28 MiB. TP does this in every layer, for every step. This is one reason why an MoE engine can prefer DP for attention: DP needs no communication in the attention layers.

Simplified

Libraries such as NCCL also use tree and other algorithms. The ring formula is a good first estimate, not an exact cost.

An everyday comparison#

Think of a restaurant group with eight kitchens. With DP, each kitchen cooks the full menu for its own guests. With TP, every dish is half-cooked in two kitchens, and the halves are joined before the next step. With PP, each kitchen does one stage of every dish, like an assembly line. With EP, each kitchen has specialist cooks for some dishes, and orders go to the kitchen with the right specialist. With CP, very large orders are shared between kitchens.

The comparison stops here: kitchens can work alone for hours, but ranks must exchange data many times in every step. And in a collective, all ranks wait for the slowest one. So one slow rank slows down the whole group.

In DeepInfer#

This is a basics page, so this part only gives pointers. The concept pages explain each kind of parallelism in DeepInfer.

  1. The groups. ParallelProcessGroup holds the device groups dp, cp, ep, ep_in_dp, enp (Engram), world and local, and CPU (gloo) copies of the DP, CP and EP-in-DP groups:
  1. No tensor parallelism. The linear layers use ReplicatedLinear: every rank holds the full weight (deepinfer/model_executor/layers/linear.py:36-45). The only other linear class, ParallelRoutedLinear, holds the full weights of the local experts of one EP rank. It splits by expert, not inside a matrix (deepinfer/model_executor/models/v4_modules/linear.py:23-34). Even VocabParallelEmbedding keeps the whole table on each rank (deepinfer/model_executor/layers/vocab_parallel_embedding.py:19-24). The "model parallel size" is the CP size (deepinfer/config.py:171). The deployment notes say that attention uses data parallelism, with #DP = #EP (doc/inference_deployment_qa.md:33).
  2. Where to read more. DP ranks vote on the kind of each step: Data parallelism and step votes. CP ranks share one long prefill: Context parallelism (mirror CP). EP ranks exchange tokens with DeepEP: Expert parallelism: dispatch, grouped GEMM, combine and Expert load balancing (EPLB).

Deep dive

Sizes, ranks and group layouts, with a worked example

Sizes. ParallelConfig gets four sizes (deepinfer/config.py:150-182):

  1. Line 162: if data_parallel_size is 0 (the EngineArgs default, deepinfer/engine/arg_utils.py:28-31), it becomes max(1, ep // cp).
  2. Line 171: model_parallel_size = context_parallel_size.
  3. Lines 172-173: the Engram size defaults to cp × dp. The world size is max(cp × dp, enp).
  4. Lines 177-182: EP must divide cp × dp, and the world size must be a multiple of cp × dp and of enp.

Rank numbers. A rank is engine_rank × cp_size + cp_rank (deepinfer/worker/base.py:329). engine_rank is the DP index of the engine. The CP ranks of one engine are neighbours.

Layouts. create_process_groups uses einops.rearrange on torch.arange(world) (deepinfer/model_executor/parallel_utils/parallel_state.py:80-118):

GroupRearrange patternLine
DP(replica dp cp) -> (replica cp) dp92
CP(dp cp) -> dp cp97
EPthe world group if ep_size = world size, else (edp ep) -> edp ep102-106
Engram(replica enp) -> replica enp109
EP-in-DP(edp ep_in_dp) -> edp ep_in_dp; the local group if ep_size = 1113-117

Worked example. Run with --ep 8 --cp 2 and no DP size. Then dp = max(1, 8 // 2) = 4, enp = 2 × 4 = 8, world = 8. The ranks are 0..7, and rank r has engine_rank = r // 2 and cp_rank = r % 2.

  • CP groups: [0, 1], [2, 3], [4, 5], [6, 7]. Each pair runs one engine.
  • DP groups: [0, 2, 4, 6] and [1, 3, 5, 7]. Each group has one rank of each engine with the same cp_rank.
  • EP group: [0..7], the world group. Engram group: [0..7].
  • With --ep 4 instead: EP groups [0, 1, 2, 3] and [4, 5, 6, 7]. Each rank holds 1/4 of the experts.

One group object per layout. _split_group_cached makes a group for every row of the layout on every rank, because torch.distributed.new_group must be called by all ranks. It keeps only the row that contains this rank, and caches the result (deepinfer/model_executor/parallel_utils/parallel_state.py:26-48).

Deep dive

Backends and lazy start-up of the device groups

The default process group uses gloo, a CPU backend (deepinfer/worker/base.py:334-340). The device groups use the backend of the platform: nccl or hccl (deepinfer/model_executor/parallel_utils/parallel_state.py:82-83). See Hardware platforms: NVIDIA and Ascend.

With a CPU default group, the device groups start lazily. So DeepInfer runs one small all-reduce on each device group at start-up:

The CPU copies of the groups are for small control messages. For example, with ZOS the scheduler votes over the CPU DP group (deepinfer/engine/llm_engine.py:313). The CPU CP group carries the shared-memory message queue that sends method calls from the driver to the other CP ranks (deepinfer/model_executor/parallel_utils/parallel_state.py:122-124).

The CP all-gathers go through DeepInfer's own buffer (userbuffer.cp), and the EP exchange goes through DeepEP. This site does not explain the insides of DeepEP.

Worked example: the size of an MoE dispatch. The numbers are illustrative, not from the repo. One rank has 1,536 tokens, top-8 routing, hidden size 4,096 and FP8 tokens (1 byte per value). Each token goes to up to 8 experts. So the rank sends at most 1,536 × 8 × 4,096 B = 48 MiB in the dispatch, plus the small scale factors. The combine brings the same number of BF16 results back, 96 MiB at most. Tokens whose expert is on the same rank do not leave the rank. In a real model, top-k and the hidden size come from the checkpoint config.

Deep dive

What the deployment notes say about TP, CP and EP sizes

The Q&A document describes the production service of DeepSeek V4.1 Flash. It is about the service, not only about this repo:

  • Prefill uses EP2-8 / DP2-8, the smallest size that HBM allows. Decode uses EP64-128 / DP64-128 ("Wide-EP") (doc/inference_deployment_qa.md:47-49).
  • "TP and CP are not used for now" (doc/inference_deployment_qa.md:53). The code supports CP, and the examples show --cp 8 (examples/README.md:8).
  • Wide EP reduces the memory traffic per step in the expert part (doc/inference_deployment_qa.md:57).

Why wide EP helps decode, with numbers. Take 256 experts (illustrative) and 64 ranks: each rank holds 4 experts. With 8 ranks, each rank holds 32 experts. A decode step must read the weights of every expert that gets at least one token. With fewer experts per rank, each rank reads fewer weight bytes per step. Also, each expert gets the tokens of more ranks, so the batch per expert is larger. A larger batch per expert gives the expert GEMMs a higher arithmetic intensity. See GPUs, kernels, and speed and Mixture of Experts (MoE).

What can go wrong#

  • Sizes that do not fit. ParallelConfig asserts that EP divides cp × dp, and that the world size fits CP, DP and Engram (deepinfer/config.py:176-182). A wrong combination stops start-up.
  • Experts that do not divide by EP. The number of physical experts must be a multiple of ep_size. DeepInfer rounds the number of extra (redundant) experts up and logs a warning (deepinfer/model_executor/model_loader.py:93-100, deepinfer/model_executor/eplb/__init__.py:21-28).
  • A hang in a collective. All ranks of a group must call the same collectives in the same order. The scheduler keeps decode_step equal on all ranks for this reason. Translated: "decode_step is the same on all ranks. So the number and meaning of the votes match, and the group does not hang in the allreduce." (csrc/engine/scheduler.hpp:307).
  • A slow rank. In a collective, every rank waits for the slowest one. One rank with too much MoE load slows all EP ranks. This is the job of Expert load balancing (EPLB).
  • A long start-up wait. The CPU group waits up to DEEPINFER_GLOO_TIMEOUT seconds, default 14,400 (deepinfer/environ.py:110, deepinfer/worker/base.py:334-340).

Why it matters. The parallel plan decides how much memory each rank needs, how much it communicates, and which ranks wait for which. When a DeepInfer page says "the DP group" or "the EP group", it means one of the groups on this page.

Check yourself#

  1. 1
    Three ranks hold [2, 0], [1, 1] and [0, 3]. What does each rank get from an all-reduce (sum)? And from an all-gather?
    easy
    Show answer

    All-reduce: every rank gets [3, 4]. All-gather: every rank gets [2, 0, 1, 1, 0, 3], in rank order.

  2. 2
    Does DeepInfer split the attention weights over ranks with tensor parallelism? Give evidence from the code.
    medium
    Show answer

    No. ParallelProcessGroup has no TP group (deepinfer/model_executor/parallel_utils/parallel_state.py:51-65). The attention layers use ReplicatedLinear, which keeps the full weight (deepinfer/model_executor/layers/linear.py:36-45). Only the expert weights are split, by expert (EP). Attention uses DP (doc/inference_deployment_qa.md:33).

  3. 3
    In an all-to-all over 4 ranks, rank 2 holds [a, b, c, d]. Which rank gets c?
    medium
    Show answer

    Rank j gets part j of every rank. c is part 2 of rank 2, so rank 2 keeps it. a goes to rank 0, b to rank 1 and d to rank 3.

  4. 4
    You start DeepInfer with --ep 8 --cp 4 and no DP size. What are dp, the world size, the CP groups and the DP groups?
    hard
    Show answer

    dp = max(1, 8 // 4) = 2 (deepinfer/config.py:161-162). enp = 4 × 2 = 8, world = 8. CP groups (dp cp) -> dp cp: [0, 1, 2, 3] and [4, 5, 6, 7]. DP groups (replica dp cp) -> (replica cp) dp: [0, 4], [1, 5], [2, 6], [3, 7] (deepinfer/model_executor/parallel_utils/parallel_state.py:92-98). The EP group is all 8 ranks.

  5. 5
    Why does init_device_groups run an all-reduce on a zero tensor for every NCCL or HCCL group, also for groups with one rank?
    hard
    Show answer

    The default group uses gloo, so the device groups start lazily. A collective must run once to make the communicator. Single-rank groups are included because Engram's DeepEP code reuses that communicator, and a null pointer would crash (deepinfer/model_executor/parallel_utils/parallel_state.py:173-187).

Related pages

  • Data parallelism and step votesEach data-parallel replica is a separate engine process with its own requests. All replicas must run the same kind of step at the same time, so they vote with all-reduces over the DP group.
  • Context parallelism (mirror CP)With context parallelism, the devices of one engine share the tokens of a long prefill. A mirrored token order gives each device the same amount of causal attention work.
  • Expert parallelism: dispatch, grouped GEMM, combineDeepInfer splits the expert slots of every MoE layer evenly over the EP ranks. DeepEP dispatch sends each token to the ranks of its experts, DeepGEMM runs grouped GEMMs there, and DeepEP combine brings the results back.
  • Expert load balancing (EPLB)EPLB counts the tokens of every expert slot in every step. Every N steps it gives busy experts extra copies, places all copies so that the EP ranks get about the same work, and moves the expert weights in place.
  • Engram n-gram memoryEngram gives some decoder layers a large learned table. Each token hashes its last few tokens (its n-grams) to rows of that table, and the layer adds those rows to its hidden states. The table is split across the ranks of the enp group.
  • Hardware platforms: NVIDIA and AscendDeepInfer runs on NVIDIA GPUs and on Huawei Ascend NPUs. At start-up it makes one Platform object, and the shared code reads all hardware choices from it.
  • parallel_utils/parallel_state.py: the process groupsparallel_state.py makes all torch.distributed process groups of one rank (world, local, DP, CP, EP, EP-in-DP, Engram and three Gloo copies), the shared-memory queue of the CP group, and the global PG object that the rest of the code reads.
