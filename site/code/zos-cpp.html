csrc/engine/zos.cpp: the C++ helpers of zero-overhead scheduling

AdvancedCode mapabout 7 min read + 3 min deep dives

Purpose#

zos.cpp does the CPU part of a ZOS decode step: it matches the sequences of two steps, packs pinned input arrays for the device kernels, and corrects the CPU metadata before the sampler.

Filecsrc/engine/zos.cpp, 307 lines of C++, and the header csrc/engine/zos.hpp, 30 lines. Built into the extension deepinfer._C (setup.py:28).
Main functionsprepare_zos_inputs (csrc/engine/zos.cpp:142), prepare_decode_zos_inputs (csrc/engine/zos.cpp:198), update_metadata_for_sampling_zos (csrc/engine/zos.cpp:279). Helpers in an anonymous namespace: compress_token and prepare_token_inputs.
Runs inThe driver worker thread, on the CPU. The two prepare_* functions release the Python GIL.
Called byWorker._correct_seqlens_qk, Worker.execute_model_step and prepare_decode_inputs_zos (Python).
CallsTorch tensor allocation in pinned memory, the engram helpers (lookup table, fill_engram_row) and SequenceMetadata::refresh_for_sampling. No device work.
Not in this fileThe length kernel, the token gather and the slot mapping run on the device, in TileLang kernels (deepinfer/model_executor/layers/tilelang_ops/compute_seqlens_k_zos.py:10-32, deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:235-244, deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:336-367).

Where it sits#

Who calls it#

  • prepare_zos_inputs: Worker._correct_seqlens_qk, at the start of each step that has a kept step (deepinfer/worker/worker.py:209-211).
  • prepare_decode_zos_inputs: prepare_decode_inputs_zos in the ZOS input path of the model runner (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:49-69).
  • update_metadata_for_sampling_zos: a method of SchedulerOutputs, called by Worker.execute_model_step before the sampler (deepinfer/worker/worker.py:150-152).

The Python bindings and stubs:

The stubs are in deepinfer/_C/engine.pyi (deepinfer/_C/engine.pyi:374, deepinfer/_C/engine.pyi:721, deepinfer/_C/engine.pyi:727).

What it calls#

  • pinned(dtype): tensor options with pinned_memory(true) (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:8).
  • get_engram_lookup_table() and fill_engram_row, for models with engram n-gram inputs (csrc/engine/input_metadata/prepare_tensor_input.hpp:59-63).
  • SequenceMetadata::refresh_for_sampling (csrc/engine/sequence.hpp:408-418).

Walk through the main methods#

prepare_zos_inputs: match two batches#

  1. Lines 148-157: fast path. If both lists have the same length and the same seq_id at each index, remap[i] = i. A placeholder in the previous list stops the fast path.
  2. Lines 159-173: else, a hash map from seq_id to the previous index. Placeholders are not in the map, so they never match.
  3. Lines 174-176: no common sequence: return three empty optionals and false. The worker then does no correction.
  4. Lines 178-189: three pinned int32 arrays of length n_seq_with_padding. Line 188 sends seqlen_k − seqlen_q; the kernel adds the (maybe new) seqlen_q back. With nextn = 0, it sends seqlen_k unchanged.
  5. Lines 190-194: CUDA graph padding rows get remap = -1 and lengths 1.

The sort in the scheduler orders the decode batch by length every step (csrc/engine/scheduler.hpp:648-649). So the hash path is normal when the lengths change their order.

prepare_decode_zos_inputs: pack the decode inputs#

The block count of each sequence uses the largest possible length, seqlen_k − seqlen_q + max_seqlen_q. The English comment at lines 220-221 gives the reason. With DSpark, the device can give a sequence more query tokens than the CPU planned. Example: seqlen_k = 112, seqlen_q = 6, max_seqlen_q = 6, smallest compress ratio 1, 128 tokens per block: ceil(112 / 128) = 1 block. A placeholder gets 1 block.

  1. Lines 238-241: default lengths only when there is no correction (need_default_seqlens, which Python sets to metadata_zos is None).
  2. Lines 242-246: cumulative query lengths, state ids, placeholder flags, and the block tables in CSR form: block_table_offsets [n+1] and one flat block_tables [total_blocks].
  3. Lines 258-271: one loop fills them. Each sequence copies only its first num_blocks[i] table entries.
  4. Lines 272-273: the token arrays come from prepare_token_inputs.

prepare_token_inputs: which tokens the CPU still writes#

  1. Without overlap (no kept step, or no common sequence), the CPU writes the final packed input_ids [total_q]: the last real token, then seqlen_q − 1 drafts. Python copies it to the device as it is (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:215-223).
  2. With overlap, the CPU writes fresh_input_ids [n_seq, max_seqlen_q]. Line 94 fills it with 0. Lines 106-113 fill only the rows with remap = -1. The device kernel takes the other rows from the outputs of the previous step.
  3. Lines 115-135: for engram models, the CPU also writes the window of compressed history tokens (win_compressed). The device kernel gather_engram_tokens_zos adds the new tokens of the previous step (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:246-274).

update_metadata_for_sampling_zos: catch up before sampling#

  1. Lines 282-288: checks. The metadata list and the scheduled sequences must have the same length; the arrays must be CPU int32 and contiguous.
  2. Line 297: seqlen_q from the pinned array. Without DSpark it does not change. With DSpark, the worker copied the device values back into this array first (deepinfer/worker/worker.py:230-234).
  3. Line 299: seqlen_k = seqlen_q + cache.num_tokens. At this point the previous step is post-processed, so the cache count is exact.
  4. Lines 300-302: a matched sequence refreshes its last token, its draft slots, its grammar state and its golden tokens (csrc/engine/sequence.hpp:408-418).
  5. Line 303: the scheduler outputs get the same seqlen_q, for the post-process of this step.

Deep dive

Threads, the GIL and object lifetimes

  • prepare_zos_inputs and prepare_decode_zos_inputs run with py::gil_scoped_release (csrc/engine/pybind_sequence.cpp:51-55). They only read C++ objects and write new tensors.
  • update_metadata_for_sampling_zos keeps the GIL, because refresh_for_sampling assigns the Python grammar matcher (csrc/engine/pybind_scheduler.cpp:51, csrc/engine/sequence.hpp:416).
  • The previous metadata list must stay valid until the post-process of the previous step. WorkerStepState holds it. The engine post-process gives it to DeferredRelease, which returns it to the pool in the pre_sampler_sync of the same call (deepinfer/worker/zos_status.py:11, deepinfer/engine/llm_engine.py:1013, deepinfer/engine/llm_engine.py:830-831).
  • A refreshed sequence keeps its old write slot for the draft pool if ZOS already released the request. Comment: "Keep the slot captured for an in-flight sample after ZOS releases the request" (csrc/engine/sequence.hpp:411-414).

Check yourself#

  1. 1
    What does remap[i] = -1 mean?
    easy
    Show answer

    Sequence i of the current step was not in the previous step, or row i is CUDA graph padding (csrc/engine/zos.cpp:168-171, csrc/engine/zos.cpp:190-194).

  2. 2
    Why does prepare_zos_inputs send seqlen_k − seqlen_q and not seqlen_k?
    medium
    Show answer

    The kernel adds seqlens_q back, and with DSpark that value can be a new device value (csrc/engine/zos.cpp:188, deepinfer/model_executor/layers/tilelang_ops/compute_seqlens_k_zos.py:22-23, deepinfer/worker/worker.py:218-219). So the result is always "old length + the real query length − rejected drafts".

  3. 3
    With overlap, which rows of fresh_input_ids does the CPU fill?
    medium
    Show answer

    Only the rows with remap < 0, which are not placeholders. All other entries stay 0; the device gathers those rows from the previous step (csrc/engine/zos.cpp:94, csrc/engine/zos.cpp:101-113).

  4. 4
    A sequence has CPU seqlen_k = 300 and seqlen_q = 3 (DSpark gave it 2 drafts). max_seqlen_q = 6. How many 128-token blocks go into the CSR table, and why not fewer?
    hard
    Show answer

    max_k = 300 − 3 + 6 = 303, so ceil(303 / 128) = 3 blocks (csrc/engine/zos.cpp:222-225). The device can raise seqlen_q up to 6 with the newest confidences, so the table must cover the longest case (comment at lines 220-221). See the deep dive "A worked example of the block count".

Related pages

  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • worker/worker.py: the per-step WorkerWorker.execute_model_step runs every engine step on one rank in a fixed order - forward N, post-process N-1, sample N - and keeps a ZOS decode step for the next call. zos_status.py holds the two records that it keeps.
  • Tour: One engine stepFollow one decode step of three requests through LLMEngine.step() and Worker.execute_model_step in 11 stops, and see which step's data each phase touches (N or N-1), with ZOS on and off.
  • csrc/engine/sequence.hpp: Sequence and SequenceMetadatasequence.hpp defines the C++ Sequence (one record per request, owned by the scheduler) and SequenceMetadata (a per-step view of one scheduled sequence that the worker reads). It also defines the status enum, the finish reasons and the image token offsets.
  • csrc/engine/scheduler.hpp: the C++ Schedulerscheduler.hpp holds the C++ Scheduler: the waiting and running queues, the choice between prefill and decode, block allocation, preemption, and the bookkeeping after each step. It also defines SchedulerOutputs and three free functions.
  • Paged KV cache and block managerThe engine side of the paged KV cache. Two C++ BlockManager objects hand out KV blocks and state slots, the scheduler decides when, and C++ code turns block tables into index tensors for the kernels.
  • Input metadata (varlen batching)Before each forward pass, DeepInfer packs the tokens of all scheduled sequences into one flat list and computes index tensors that tell each kernel where every token is, where to write its cache entry and which keys to read.
