worker/worker.py: the per-step Worker

AdvancedCode mapabout 8 min read + 3 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Purpose#

Worker runs the device work of one engine step on one rank, in the order forward, post-process of the previous step, sample. With ZOS it keeps a decode step for the next call.

Filedeepinfer/worker/worker.py, 283 lines, and deepinfer/worker/zos_status.py, 40 lines. The header of worker.py says "Derived from vLLM; modified by DeepSeek." (deepinfer/worker/worker.py:2)
Main classWorker(WorkerBase) (deepinfer/worker/worker.py:51). Also EngineCallbacks (deepinfer/worker/worker.py:43-48), _SeqlensCorrection (deepinfer/worker/worker.py:34-40), and in zos_status.py the dataclasses WorkerStepState and MetadataZOS.
Runs inThe driver worker runs in the engine process, in the main thread. Context-parallel followers run the same methods in their own processes.
Called byLLMEngine through run_workers: execute_model_step every step, flush_inflight_reqs at the end (deepinfer/engine/llm_engine.py:965-973, deepinfer/engine/llm_engine.py:979).
CallsModelRunner (forward, sample, post-process), the C++ functions prepare_zos_inputs and SchedulerOutputs.update_metadata_for_sampling_zos, two TileLang kernels, and the two engine callbacks.
Not in this fileStart-up, the model load and the KV cache: they are in the base class (worker/base.py: WorkerBase, the resource layer of a worker). Input tensors and the model call: worker/model_runner.py: the ModelRunner class.

The class docstring gives the rule: "Every step runs the Forward-Post_process-Sample round in execute_model_step; under ZOS the post-process of a decode step is deferred to overlap with the next forward" (deepinfer/worker/worker.py:52-55).

Where it sits#

The figure on Tour: One engine step shows the phases of one call in code order. This section lists the neighbours.

Who calls it#

  • LLMEngine._init_workers makes the driver Worker with is_driver_worker=True and an EngineCallbacks object that holds post_process and pre_sampler_sync (deepinfer/engine/llm_engine.py:398-413).
  • _spawn_worker makes a follower Worker in each context-parallel process (deepinfer/engine/llm_engine.py:122-127). Its constructor never returns: it ends in the call loop of the base class (deepinfer/worker/base.py:120-123).
  • LLMEngine._execute_model_async_step calls execute_model_step every step (deepinfer/engine/llm_engine.py:961-975).
  • LLMEngine.flush_inflight_reqs calls flush_inflight_reqs (deepinfer/engine/llm_engine.py:977-982).

What it calls#

  • ModelRunner.execute_main_model, execute_sample, post_process and _placeholder_seq_metadata (deepinfer/worker/worker.py:122-127, deepinfer/worker/worker.py:154-159, deepinfer/worker/worker.py:268).
  • C++: prepare_zos_inputs (deepinfer/worker/worker.py:209-211) and update_metadata_for_sampling_zos (deepinfer/worker/worker.py:150-152). See csrc/engine/zos.cpp: the C++ helpers of zero-overhead scheduling.
  • Kernels: compute_seqlens_q_by_confidence_rates (DSpark only) and compute_seqlens_k_zos (deepinfer/worker/worker.py:218-227).
  • Engine callbacks on the driver only: pre_sampler_sync_fn and post_process_fn (deepinfer/worker/worker.py:163-164, deepinfer/worker/worker.py:270-271).
  • Timers: cpu_timer, cuda_timer and cuda_graph_timer from deepinfer/timer.py.

Walk through the main methods#

execute_model_step, part 1: correct and forward#

  1. Lines 116-118: only the driver, and only for a real batch, computes total_q and the correction. A prefill sums seqlen_q; a decode step reads num_batched_tokens from the scheduler.
  2. Lines 121-124: launch the forward pass of step N. execute_main_model must not sync (its docstring, deepinfer/worker/model_runner.py:315-318).
  3. Lines 125-127: an empty batch still runs the model on one placeholder sequence (a placeholder step). The code gives no reason. This site infers that every rank must join the collective calls of the model.
  4. Lines 130-138: with DSpark, the driver keeps the timing events of the forward pass for the cost model of a decode step.
  5. Line 140: Movable wraps the model output, so that the sampler can take it and free it early.

execute_model_step, part 2: post-process N−1, sample N, keep N#

  1. Line 144: post-process the kept step. With no kept step, this returns an empty array.
  2. Lines 147-152: with a correction, wait for the copy event if there is one (DSpark only), then update the CPU metadata of step N.
  3. Line 154: launch the sampler of step N.
  4. Lines 162-165: the pre_sampler_sync callback (driver only) and the garbage collector run while the device samples.
  5. Lines 167-168: record sample_end_evt. It marks the end of all work queued so far in the stream.
  6. Lines 183-187: a prefill step, or any step with ZOS off, is post-processed at once and its outputs are added. A ZOS decode step is kept in prev_step_state.

A placeholder step is kept too

With ZOS, an empty decode step is also kept. Its post-process passes no sampler output to the engine (deepinfer/engine/llm_engine.py:987), and the next correction skips it (deepinfer/worker/worker.py:199-200).

_correct_seqlens_qk#

  1. Lines 199-200: no kept step, or a kept placeholder: return None.
  2. Lines 203-207: the arrays need one row per CUDA graph padding row. Example: 3 sequences with 6 tokens each use the graph of 24, so n_seq_with_padding = 3 + 24 − 18 = 9.
  3. Lines 209-213: C++ builds the remap and the CPU lengths. No overlap: return None.
  4. Lines 214-216: non-blocking copies to the device. The source is pinned memory.
  5. Lines 218-219: DSpark only. A kernel splits the verification budget with the newest confidences of the kept step (see DSpark: DFlash drafts and confidence-scheduled verification).
  6. Lines 220-227: the length kernel. It needs drafts, so it runs only with nextn > 0.
  7. Lines 230-234: DSpark only. Copy the new seqlens_q back into the same pinned array and record d2h_evt.
  8. Lines 236-244: the result for the input preparation of the model runner.

_post_process_step and flush_inflight_reqs#

  1. Line 263: the wait for the end of the sampler of that step. With ZOS this is the event of step N−1.
  2. Line 266: the CUDA graph timer reads the times of finished graphs. The comment says that this does not touch the running graph.
  3. Line 268: ModelRunner.post_process runs the sampler's post_funcs and, for a prefill, the prompt log-probabilities (deepinfer/worker/model_runner.py:370-384).
  4. Lines 270-271: only the driver calls the engine. A follower returns an empty array.
  5. Lines 281-282: the flush post-processes the kept step and clears it. The docstring warns: "It may cause CPU-GPU synchronization" (deepinfer/worker/worker.py:276).

Deep dive

Processes and threads

  • The driver Worker runs in the main thread of the engine process. All engine callbacks run in this thread, inside the worker call.
  • A follower Worker (context parallelism) has is_driver_worker=False. It skips the correction (line 116), gets its input tensors by broadcast inside the model runner (deepinfer/worker/model_runner.py:216-230), and never calls the engine (line 270). It still keeps prev_step_state and waits on its own events.
  • The follower gets only is_prompt and is_placeholder as arguments. seq_metadata_list stays None there (deepinfer/engine/llm_engine.py:965-973).

Check yourself#

  1. 1
    In which order does execute_model_step do its three main parts?
    easy
    Show answer

    Forward of the current step, post-process of the previous step, sample of the current step (deepinfer/worker/worker.py:96-102).

  2. 2
    Why does Worker.__init__ set prev_step_state before it calls super().__init__()?
    medium
    Show answer

    A follower worker enters start_slave_worker_loop inside the base constructor and never returns (deepinfer/worker/base.py:120-123). The loop calls methods such as execute_model_step, which read prev_step_state and nextn. The comment says so (deepinfer/worker/worker.py:70-74).

  3. 3
    A prefill step runs with ZOS on. Is it kept for the next call?
    medium
    Show answer

    No. Line 183 post-processes a prompt step at once and sets prev_step_state = None (deepinfer/worker/worker.py:183-185). Only ZOS decode steps are kept.

  4. 4
    Three sequences with 6 query tokens each run with CUDA graphs of sizes 1, 2, 4, 8, 16, 24. How many rows do remap, seqlens_q and seqlens_k have, and which rows does the length kernel get?
    hard
    Show answer

    total_q = 18, the selected graph has 24 tokens, so n_seq_with_padding = 3 + 24 − 18 = 9 (deepinfer/worker/worker.py:203-205). The kernel gets only the first n_seq = 3 rows (deepinfer/worker/worker.py:221-227); the 6 padding rows keep length 1 (csrc/engine/zos.cpp:190-194). See the deep dive "Data flow".

Related pages

  • worker/base.py: WorkerBase, the resource layer of a workerWorkerBase sets up one device for one rank - torch settings, NUMA and CPU binding, process groups, the model, the memory profile, the KV cache and the CUDA graphs - and runs the call loop of the context-parallel followers.
  • csrc/engine/zos.cpp: the C++ helpers of zero-overhead schedulingzos.cpp has three functions for ZOS decode steps - match the batch with the previous step (remap), pack the decode inputs into pinned arrays, and refresh the CPU metadata before sampling. The device kernels do the rest.
  • worker/model_runner.py: the ModelRunner classModelRunner owns the model object on one rank. It builds the input metadata, runs the forward pass (eager or as a CUDA graph replay), prepares the sampler inputs, runs the memory profile and captures the graphs.
  • engine/llm_engine.py: the LLMEngine classLLMEngine starts the workers, sizes the KV cache, owns the C++ scheduler, and runs one engine step each time LLM calls step().
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • Tour: One engine stepFollow one decode step of three requests through LLMEngine.step() and Worker.execute_model_step in 11 stops, and see which step's data each phase touches (N or N-1), with ZOS on and off.
  • DSpark: DFlash drafts and confidence-scheduled verificationDSpark makes 5 drafts per request with the DFlash draft model and predicts how likely each draft is to pass. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time.
  • Offline API and the step loopLLM.generate() adds all requests, then calls LLMEngine.step() until no request is left. Each step schedules one batch, runs the model once, and returns handles to the new outputs. With ZOS, a decode step returns the tokens of the step before it.
