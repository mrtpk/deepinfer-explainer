deepinfer/entrypoints/llm.py: the offline LLM class

BeginnerCode mapabout 8 min read + 5 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • What an LLM does Beginner
  • Offline API and the step loop Intermediate

Purpose#

LLM is the class that a user script calls. It turns a list of prompts into a list of results, and hides the engine step loop.

Filedeepinfer/entrypoints/llm.py, 198 lines. The header says "Derived from vLLM; modified by DeepSeek." (deepinfer/entrypoints/llm.py:2)
Main classLLM (deepinfer/entrypoints/llm.py:23). It is the only class in the file.
Runs inThe user's process. That process is also the engine process of one data-parallel rank, with the driver worker in it. The step loop runs on the calling thread, and generate() blocks until all requests end.
Called byUser scripts, examples/_config.py (create_llm), eval/run_eval.py.
CallsEngineArgs, LLMEngine, the Hugging Face tokenizer, RequestOutput.clone, tqdm.
Not in this fileBatching, scheduling, sampling (all in the engine). No streaming, no abort, no online server: the engine docstring says that this release has no online-serving wrapper (deepinfer/engine/llm_engine.py:140-141).

Where it sits#

Panel 1 runs once per prompt and does no device work. Panel 2 is the loop. The flush runs only once, at the end.

Who calls it#

  • The examples make the object in create_llm, with trust_remote_code=True, chunked_prefill=True, decode_sequence=False and statistics on (examples/_config.py:110-125). examples/offline_inference.py then calls generate (examples/offline_inference.py:95).
  • The eval script uses decode_sequence=False and passes token ids (eval/run_eval.py:189).
  • The benchmark uses the private method llm._add_request and then calls llm.llm_engine.step() itself (examples/benchmark.py:304-309, examples/benchmark.py:369).

What it calls#

  • EngineArgs(...) and LLMEngine.from_engine_args (deepinfer/entrypoints/llm.py:70-84). See engine/llm_engine.py: the LLMEngine class.
  • tokenizer.encode and tokenizer.decode (deepinfer/entrypoints/llm.py:156, deepinfer/entrypoints/llm.py:190).
  • LLMEngine.add_request, has_unfinished_requests, step, flush_inflight_reqs, get_num_unfinished_requests and close.
  • RequestOutput.clone from the C++ extension (deepinfer/entrypoints/llm.py:15). See csrc/engine/outputs.hpp: RequestOutput and its pool.

Walk through the main methods#

__init__: defaults that differ from the engine#

  1. Lines 56-64: nine named arguments. All other arguments go through **kwargs to EngineArgs, for example max_model_len, max_num_seqs or chunked_prefill. An unknown name raises TypeError, because EngineArgs is a dataclass.
  2. Line 67: statistics logging is off, unless you pass disable_log_stats=False.
  3. Line 68: stop_preempted_request=False. The EngineArgs default is True (deepinfer/engine/arg_utils.py:40). So with LLM, a preempted request is computed again, not stopped (see The KV cache).
  4. Line 69: TOKENIZERS_PARALLELISM=false, unless the variable is already set.
  5. Line 79: offline_inference=True. The engine stores it (deepinfer/engine/llm_engine.py:195); no other line in the release reads it.
  6. Line 82: decode_sequence chooses the result type of generate() (text or outputs).

The docstring has a note in Chinese. Translated: "With CUDA graphs on, the error 'CUDA error: an illegal memory access was encountered' can mean that the CUDA graph ran out of memory. Lower gpu_memory_utilization and try again." (deepinfer/entrypoints/llm.py:50-51).

generate: the input rules#

  1. Lines 117-118: you must give prompts, prompt_token_ids, or both.
  2. Lines 119-122: one string becomes a list of one. multi_modal_data is wrapped too, so pass one dict for one string.
  3. Lines 123-124: if you give both lists, they must have the same length. Then the token ids win; _add_request tokenizes only when the ids are None (deepinfer/entrypoints/llm.py:153-156).
  4. Lines 125-127: no settings means one SamplingParams() for all requests: temperature 1.0, 16 tokens (deepinfer/sampling_params.py:49-53).
  5. Line 138: one object for all, or a list with one object per prompt. The comment says, translated: "when the same SamplingParams is shared, no copy is needed here: _add_request does a deepcopy" (line 137).

_add_request: one request#

  1. Line 151: a deep copy, because the engine changes the object (it sets eos_id, see deepinfer/sampling_params.py: SamplingParams).
  2. Line 152: the request id is the next value of a counter that starts at 0, as a string. The counter lives in the LLM object, so a second generate() call goes on from the last id.
  3. Line 156: text goes through tokenizer.encode(prompt). With token ids, DeepInfer uses them as they are and adds no BOS token.
  4. Line 157: the engine needs a 1-D np.int32 array; the C++ Sequence refuses other types (see deepinfer/_C/engine.pyi: the C++ engine API, as seen from Python).
  5. Lines 158-159: if the engine has an image processor and you gave no image data, the request gets an empty image dict. The only registered model is a vision-language model, so the NORMAL engine always has that processor (deepinfer/model_executor/models/__init__.py:15-17, deepinfer/engine/llm_engine.py:209-221).
  6. Line 160: the return value is a Sequence, or None for a dropped request. generate() ignores it.

_run_engine: the loop#

  1. Line 171: the progress bar counts local unfinished requests at the start.
  2. Line 177: has_unfinished_requests() asks all data-parallel ranks with an all-reduce MAX, when there is more than one rank (deepinfer/engine/llm_engine.py:665-679). So this rank goes on while any rank has work.
  3. Line 178: work left: one engine step. No work left: one flush, which returns the outputs that the Worker still holds from the last ZOS decode step (deepinfer/worker/worker.py:274-283).
  4. Lines 179-182: every handle is cloned at once. The engine releases the pool objects at the next pre_sampler_sync (deepinfer/engine/llm_engine.py:830-831).
  5. Lines 185-186: the loop ends after the flush.
  6. Line 187: the request ids are sorted as integers, so "10" comes after "9".
  7. Lines 189-190: with decode_sequence=True, each request becomes one string: the decode of all its output token ids.

A dropped request moves the results

The result list has one entry per request id that produced an output (line 188). add_request drops a request with a bad token id and returns None (deepinfer/engine/llm_engine.py:582-589). That request gets no output, so the list is shorter, and later results move up by one. The docstring promises "the same order as the input prompts" (lines 113-115). Check that len(results) == len(prompts).

One output per token. Each RequestOutput holds one token (RequestOutput). A decode step with accepted drafts gives several outputs for one request (see csrc/engine/outputs.hpp: RequestOutput and its pool). To get the token ids of request i: [o.token_id for o in results[i]], as line 190 does.

Worked example: the calls of one generate()

Two prompts, A and B, each with max_tokens=3. ZOS is on (the default for LLM). To keep the table short, assume that the sampler accepts no draft, so each decode step gives one token per request.

Simplified

The table assumes one data-parallel rank and a multimodal worker that answers before the fetch() of call 70; else the prefill comes at call 101 (the ANY point). Real runs accept some drafts, so a decode step can give up to nextn + 1 = 6 tokens per request. The pattern stays: with ZOS, decode tokens arrive one call late, and the run ends with one or two calls that return nothing.

Deep dive

Seeds: the LLM seed and the request seed

There are two seeds, and they do different things.

  • LLM(seed=0) goes to ModelConfig.seed. The Worker calls set_random_seed(seed + global_rank) for Python random, NumPy and PyTorch, at start-up and again after the memory profile and graph capture (deepinfer/worker/base.py:170-172, deepinfer/worker/base.py:194, deepinfer/worker/base.py:286-288, deepinfer/model_executor/utils.py:13-18).
  • SamplingParams(seq_seed=...) is the seed that the sampling kernels use for that request. Without it, the constructor takes 64 bits from Python random (deepinfer/sampling_params.py:86-88). The Worker runs in the same process, so a SamplingParams object made after LLM(...) takes its bits from the state that LLM(seed) set.

One shared SamplingParams gives one seed to all requests

The seed is made in the constructor, and _add_request copies the object with copy.deepcopy, which does not run the constructor again (line 151). So if you pass one object (or none: then generate() makes one), every request gets the same seq_seed. Two requests with the same prompt then get the same random numbers, and they can give the same text. Pass a list of objects with different seeds if you need different samples, as eval/run_eval.py does (eval/run_eval.py:225-234).

Deep dive

Processes, threads and data parallelism

  • One process per data-parallel rank. Each rank makes its own LLM. examples/_launch.py starts the processes (examples/_launch.py:35-44).
  • All ranks loop together. has_unfinished_requests() and the scheduler's votes are collective calls (deepinfer/engine/llm_engine.py:675-678). So a rank with no prompts also calls generate(), and runs empty steps until all ranks are done.
  • Context-parallel ranks are follower processes that the engine starts; LLM does not see them (deepinfer/engine/llm_engine.py:377-395).
  • Threads. generate() is not thread-safe: two threads would share one engine and one counter. Tokenization runs on the calling thread; TOKENIZERS_PARALLELISM=false turns off the tokenizer's own thread pool (line 69).

Check yourself#

  1. 1
    What does generate() return with the default decode_sequence=True, and with False?
    easy
    Show answer

    True: one string per request, the decode of its output token ids. False: one list[RequestOutput] per request, one object per token (deepinfer/entrypoints/llm.py:187-190).

  2. 2
    Which defaults does LLM change compared with EngineArgs, and what is the effect of the second one?
    medium
    Show answer

    disable_log_stats=True and stop_preempted_request=False (deepinfer/entrypoints/llm.py:67-68). With the second one, a preempted request goes back to the waiting queue and is computed again, instead of an early stop with insufficient_system_resource (csrc/engine/scheduler.hpp:771-788).

  3. 3
    Why does _run_engine call flush_inflight_reqs() after the last step()?
    medium
    Show answer

    With ZOS, the Worker post-processes a decode step during the next call. When no work is left, the outputs of the last step are still in the Worker; the flush post-processes them (deepinfer/worker/worker.py:182-187, deepinfer/worker/worker.py:274-283).

  4. 4
    You call llm.generate(["Hi"] * 4) with no sampling parameters. Why can all four texts be the same?
    hard
    Show answer

    generate() makes one SamplingParams(), which draws one random seq_seed in its constructor (deepinfer/entrypoints/llm.py:125-127, deepinfer/sampling_params.py:74). _add_request deep-copies that object for each request, so all four copies have the same seed (line 151). The sampler draws its random numbers from the seed and the position, so all four requests get the same numbers. If their logits are also equal, they get the same tokens. This is the deep dive "Seeds".

Related pages

  • engine/llm_engine.py: the LLMEngine classLLMEngine starts the workers, sizes the KV cache, owns the C++ scheduler, and runs one engine step each time LLM calls step().
  • deepinfer/sampling_params.py: SamplingParamsSamplingParams holds the per-request settings: temperature, top-p, top-k, seed, length, logprobs, EOS rules, grammar and golden tokens. This page lists every field with its default and checks, and follows each one to the sampler.
  • csrc/engine/outputs.hpp: RequestOutput and its pooloutputs.hpp defines RequestOutput (one new token of one request), a fixed pool of 10000 of them, and build_request_outputs, which turns one engine step into output handles. pybind_output.cpp binds them, with clone and raw-pointer accessors.
  • Offline API and the step loopLLM.generate() adds all requests, then calls LLMEngine.step() until no request is left. Each step schedules one batch, runs the model once, and returns handles to the new outputs. With ZOS, a decode step returns the tokens of the step before it.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
