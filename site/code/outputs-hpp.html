csrc/engine/outputs.hpp: RequestOutput and its pool

IntermediateCode mapabout 9 min read + 4 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Request and sequence lifecycle Intermediate
  • Speculative decoding Intermediate

Purpose#

outputs.hpp turns the sampled tokens of one step into C++ RequestOutput objects, one per new token, inside a pool that the engine reuses.

Filescsrc/engine/outputs.hpp, 308 lines, header only. csrc/engine/pybind_output.cpp, 138 lines: lines 9-46 bind this header; lines 48-135 bind the input-metadata and sampler-input types (see deepinfer/_C/engine.pyi: the C++ engine API, as seen from Python).
Main thingsstruct RequestOutput (csrc/engine/outputs.hpp:18), class RequestOutputPool (csrc/engine/outputs.hpp:45), the function build_request_outputs (csrc/engine/outputs.hpp:94).
Runs inThe engine process of each data-parallel rank, on the main thread, on the CPU. build_request_outputs releases the GIL while it works (csrc/engine/outputs.hpp:104).
Called byLLMEngine._process_model_outputs (build), DeferredRelease.release (pool release), LLM._run_engine (clone).
CallsSchedulerOutputs and Sequence from scheduler.hpp and sequence.hpp, get_finished_reason (csrc/engine/sequence.hpp:45-64), and the data pointers of CPU tensors.
Not in this fileSampling and the logprob math (the sampler), the stop decision (Scheduler::_check_stop), and the text decode (LLM).

Where it sits#

Read panel 1 from left to right: the counters draft_tok and accept_tok are only on the last output of the step. Panel 2 shows the three owners of an output in time order.

Who calls it#

  • LLMEngine.__init__ makes one RequestOutputPool (deepinfer/engine/llm_engine.py:230).
  • LLMEngine._process_model_outputs calls build_request_outputs with 17 arguments, right after scheduler.process_outputs (deepinfer/engine/llm_engine.py:743-761).
  • DeferredRelease.release gives the handles of the last step back to the pool (deepinfer/engine/llm_engine.py:106-107). It runs at the start of pre_sampler_sync (deepinfer/engine/llm_engine.py:830-831).
  • LLM._run_engine calls RequestOutput.clone for every handle (deepinfer/entrypoints/llm.py:179-182).

What it calls#

  • seq->is_finished(), get_output_len(), get_prompt_len(), get_last_token_id() and the MTP fields of each scheduled sequence (csrc/engine/sequence.hpp:295-305).
  • get_finished_reason, which maps a status to text such as "stop" or "length" (csrc/engine/sequence.hpp:45-64).
  • aligned_alloc and std::free for the pool memory (csrc/engine/outputs.hpp:54, csrc/engine/outputs.hpp:62).

RequestOutputPool: 10000 slots#

  1. Line 51: the size is a compile-time constant, 10000.
  2. Lines 53-60: the constructor allocates raw memory for all slots at once, and puts every slot on a free stack.
  3. Lines 64-70: allocate takes the last free slot and builds the object in it with placement new. It returns the address as uint64: an output handle. Line 65 raises if no slot is free.
  4. Lines 72-80: release takes an array of handles, destroys each object and puts the slot back. It does not check that a handle came from this pool, or that it is still in use.

build_request_outputs: setup#

Lines 102-174 only read data pointers. Every input tensor must be contiguous and on the CPU (comment at line 106). The accepted-token tensors are optional; when they exist, first_token_positions_ must exist too (line 152). Line 176 reuses one static vector for the list of handles, so that list needs no new memory per step. (The strings and vectors inside each output still allocate.)

build_request_outputs: one sequence#

The loop runs over the first n scheduled sequences, where n = token_logprobs.size(0) (line 179). For each sequence it first counts the accepted drafts:

  1. Line 205: the request's rows end where the next request's rows start, or at total_q.
  2. Line 206: num_draft_i = rows − 1. The last row is the fresh sample.
  3. Lines 207-213: count accepted drafts until the first -1.
  4. Lines 215-216: with drafts, draft_tok = drafts + 1 and accept_tok = accepted + 1. Without drafts, both are 1.
  1. Lines 230-234: stop at a -1, or when the output count reaches pushed_tokens. pushed_tokens comes from process_outputs: the number of tokens it appended before the sequence finished (csrc/engine/scheduler.hpp:982-995).
  2. Line 247: only the last pushed token can have finished = true.
  3. Line 248: num_output_tokens counts back from the current output length.
  4. Line 251: earlier tokens get an empty finish reason.
  1. Lines 257-259: if one pushed token is left, it is the freshly sampled token token_ids[i]. Line 259 checks that exactly one was left.
  2. Lines 282-283: only this output carries the prompt logprobs. So a prefill step returns them in its single output.
  3. Lines 288-293: the last output of the step gets the draft counters and the confidence values.

Lines 297-304 add one output for each sequence in ignored_seqs: prompts that were too long, requests aborted while they waited, requests whose multimodal or grammar step failed, and sequences that preemption stopped. Their token_id is the last token of the sequence, and the logprob fields have the invalid values.

The bindings and the clone rule#

  1. Lines 12-14: for each field, the macro makes a read-only property and a static function RequestOutput.get_<field>(ptr). The comment calls it "the raw-pointer fast path on the Python side". The static function reads one field at a handle without a copy. No Python file in this release calls a get_ function.
  2. Line 18: clone(ptr) runs the C++ copy constructor and returns a unique_ptr, so Python owns the copy. Strings and vectors are copied too.
  3. Line 24: max_num_batched_tokens has a property but no get_ function.
  4. Line 39: release takes the argument name unused_request_outputs.

A handle is valid for about one step

step() returns handles of step N. The engine releases them at the pre_sampler_sync of the next step() call (deepinfer/engine/llm_engine.py:974, deepinfer/engine/llm_engine.py:830-831). After that, the slot can hold a different request's output. Clone each handle, or read it with a get_ function, before you call step() again. The docstring of step() says the same (deepinfer/engine/llm_engine.py:866-870).

Worked examples: how many outputs per request

All examples have nextn = 5, so a decode request has 6 rows: 5 draft rows and 1 fresh row.

In the EOS case, the loop stops after 77 because the next row is -1 (lines 230-231). (If that row held a token, line 233 would stop the loop, because appended_tokens would exceed pushed_tokens.) Now appended_tokens equals pushed_tokens, so line 257 skips the sampled token: it is dropped. But accept_tok was counted before the loop, so it is still 3 (lines 207-216).

How a script uses the counters. examples/offline_inference.py computes the accept rate of a request: drafts = Σ draft_tok − count(draft_tok > 0), accepted = Σ accept_tok − count(draft_tok > 0) (examples/offline_inference.py:82-86). For the first row of the table: (6 − 1) drafts and (3 − 1) accepted, so 2 / 5 = 40 %.

Deep dive

Pool size: how many outputs can be alive

Follow one call of step() with ZOS on, number k (deepinfer/worker/worker.py:143-189):

  1. The Worker post-processes step k − 1. build_request_outputs allocates the set Sk.
  2. The Worker starts sampling and calls pre_sampler_sync. DeferredRelease releases Sk−1, which the last step() returned.
  3. step() returns Sk, and the engine collects it for the next release.

So for a short time, two sets are alive. Without ZOS, the Worker post-processes after pre_sampler_sync (line 183-185), so only one set is alive.

Worst case. A decode step makes at most nextn + 1 outputs per request, plus one per ignored sequence. With ZOS:

alive ≤ 2 × max_num_seqs × (nextn + 1)   (+ ignored sequences)
max_num_seqs = 256, nextn = 5:  2 × 256 × 6 = 3,072   (fits in 10,000)
max_num_seqs = 834, nextn = 5:  2 × 834 × 6 = 10,008  (can exceed 10,000)

The second line is an upper bound: it needs every draft of every request to be accepted in two steps in a row. If the pool runs out, allocate raises "RequestOutputPool exhausted (max_size=10000); outputs are not being released" (line 65). The limit is a constant in the header; no setting changes it.

Deep dive

Threads, the GIL and memory

  • GIL. build_request_outputs reads the NumPy array pushed_tokens_before_finish first, while it still holds the GIL (lines 102-103). Then it releases the GIL (line 104) and takes it back only to make the NumPy result (line 306). The tensor reads and the pool calls do not need Python.
  • One thread. The function uses a static result vector (line 176). Two threads that call it at the same time would share that vector. The engine calls it only from the main thread.
  • Pool memory. aligned_alloc(alignof(RequestOutput), sizeof(RequestOutput) × 10000) (line 54). The strings and vectors inside each object allocate their own heap memory; release frees it with std::destroy_at (line 77).
  • Clone memory. A clone is a normal heap object that Python owns. LLM keeps all clones of all requests until generate() returns (deepinfer/entrypoints/llm.py:175-188).

Check yourself#

  1. 1
    Why does LLM._run_engine call RequestOutput.clone(raw_output)?
    easy
    Show answer

    A handle is the address of an object in the pool. The engine releases it at the next pre_sampler_sync, and the slot is used again (deepinfer/engine/llm_engine.py:974, csrc/engine/outputs.hpp:72-80). The clone is a Python-owned copy that stays valid (csrc/engine/pybind_output.cpp:17-18).

  2. 2
    In a decode step with nextn = 5, a request's accepted rows are [8, -1, -1, -1, -1] and nothing stops it. How many outputs does it get, and what are draft_tok and accept_tok on the last one?
    medium
    Show answer

    Two outputs: token 8, then the sampled token. draft_tok = 5 + 1 = 6, accept_tok = 1 + 1 = 2, both on the sampled token (csrc/engine/outputs.hpp:215-216, csrc/engine/outputs.hpp:288-290).

  3. 3
    A prompt is too long and the scheduler ignores it. What does its one output contain?
    medium
    Show answer

    token_id = the last token of the prompt, finished = true, finish_reason = "prompt_length_exceeded", token_logprobs = 1.0 (invalid), num_output_tokens = 1 (csrc/engine/outputs.hpp:297-304, csrc/engine/sequence.hpp:53-54).

  4. 4
    With ZOS on, max_num_seqs = 1000 and nextn = 5. Can the pool run out? Explain with the order of the calls in one step().
    hard
    Show answer

    Yes, in the worst case. In call k, post-processing of step k − 1 allocates the new outputs before pre_sampler_sync releases the outputs of call k − 1 (deepinfer/worker/worker.py:143-164). So two sets are alive: up to 2 × 1000 × 6 = 12,000 > 10,000 if all drafts are accepted. Then allocate raises (csrc/engine/outputs.hpp:65). This is the deep dive "Pool size".

  • Request and sequence lifecycleEach request becomes a C++ Sequence. It waits until it is schedulable, runs one or more prefill steps and many decode steps, and ends with one of seven finish reasons. Preemption stops it or sends it back to the queue for a recompute.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
