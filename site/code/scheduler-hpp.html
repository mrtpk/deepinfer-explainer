csrc/engine/scheduler.hpp: the C++ Scheduler

AdvancedCode mapabout 19 min read + 8 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

  • The scheduler Intermediate
  • Request and sequence lifecycle Intermediate

Purpose#

scheduler.hpp decides, for every engine step, which sequences run and with how many tokens, and then records the tokens that the step produced.

Filecsrc/engine/scheduler.hpp, 1,329 lines of C++ in one header. Many comments are in Chinese.
Main classstruct Scheduler (csrc/engine/scheduler.hpp:79). Also SchedulerOutputs (csrc/engine/scheduler.hpp:45), enum class EngineType (csrc/engine/scheduler.hpp:39-43), and the free functions process_MTPInfo, clone_and_zero_states_and_blocks and get_finished_seqs_info (csrc/engine/scheduler.hpp:1196, csrc/engine/scheduler.hpp:1264, csrc/engine/scheduler.hpp:1315).
Runs inThe engine process of one data-parallel rank, on the main thread. Python calls it through the pybind11 module deepinfer._C.engine (csrc/engine/pybind_scheduler.cpp:79-125). Only clone_and_zero_states_and_blocks copies data between device buffers. Without ZOS, the votes also use a one-value tensor on the device (csrc/engine/scheduler.hpp:172-173).
Called byLLMEngine (every step), MultimodalProcessor.fetch, StatsLogger, and examples/benchmark.py.
CallsBlockManager (two instances), Sequence and SequenceMetadata, MTPVarlen, FlopsEstimator, and c10d::ProcessGroup::allreduce for the votes.
Not in this fileThe Python bindings (pybind_scheduler.cpp), the RequestOutput objects (outputs.hpp), the tensor inputs of the model (input_metadata/), and the ZOS corrections (zos.cpp).

Where it sits#

The scheduler is a passive object. It has no thread and no loop of its own. LLMEngine makes it once and calls its methods from step() and from the post-process callback. The page The scheduler explains the policy with diagrams; this page walks through the code.

Who calls it#

  • Construction. LLMEngine._create_scheduler passes 14 arguments (deepinfer/engine/llm_engine.py:307-327). Then the engine sets decode_perf_curve and gives the scheduler to the image processor (deepinfer/engine/llm_engine.py:267-270).
  • Admission. _enqueue calls add_sequence (deepinfer/engine/llm_engine.py:623). abort_request calls abort_sequence (deepinfer/engine/llm_engine.py:651).
  • Every step. step() calls schedule(pool) (deepinfer/engine/llm_engine.py:885-887). The Worker runs clone_and_zero_states_and_blocks when the scheduler asks for copies (deepinfer/worker/base.py:160-168).
  • After a step. _process_model_outputs calls process_MTPInfo, process_outputs and get_finished_seqs_info (deepinfer/engine/llm_engine.py:717-738). post_process calls update_mtp_runtime (deepinfer/engine/llm_engine.py:995-1002). finalize_seq calls free_seq (deepinfer/engine/llm_engine.py:804-806).
  • Loop tests. has_unfinished_seqs and get_num_unfinished_seqs (deepinfer/engine/llm_engine.py:660, deepinfer/engine/llm_engine.py:673).
  • Images. MultimodalProcessor.fetch calls set_schedulable(id) (deepinfer/ve/multimodal_processor.py:303).
  • Statistics. StatsLogger reads the free blocks, the queue sizes and the preempted and aborted counts (deepinfer/engine/stats_logger.py:411-423).
  • Benchmark. examples/benchmark.py calls try_allocate_seq, fork_seq, and sets decode_step = 0 to force an attempt point (examples/benchmark.py:314-317, examples/benchmark.py:337-350).

What it calls#

  • Blocks and state slots. BlockManager and BlockManagerMutexAcquire (csrc/engine/block_manager.hpp:119-243). The scheduler holds two managers: one for KV blocks and one (optional) for state slots.
  • Sequences. The fields of Sequence and the constructor of SequenceMetadata (csrc/engine/sequence.hpp:275-321, csrc/engine/sequence.hpp:374-389).
  • Draft lengths. MTPVarlen::schedule sets seqlen_q in decode (csrc/engine/mtp_varlen.hpp:150-267).
  • Statistics. FlopsEstimator::calc_flops, only with log_stats (csrc/engine/scheduler.hpp:712-719).
  • Votes. dp_group->allreduce in _dp_allreduce (csrc/engine/scheduler.hpp:170-182).
  • Device copies. deepinfer::cuda::utils::cuda_copy_async in clone_and_zero_states_and_blocks (csrc/engine/scheduler.hpp:1283, csrc/engine/scheduler.hpp:1297).

Walk through the main methods#

The constructor#

  1. Lines 94-100: copy seven values from the Python SchedulerConfig.
  2. Lines 101-104: a COMPLETION engine must stop preempted requests.
  3. Lines 105-108: both attempt intervals must be 1 or more.
  4. Line 109: a Gloo group means "do the votes on the CPU".
  5. Line 112: prompt_limit: max_model_len with chunked prefill, else min(max_model_len, max_num_batched_tokens).
  6. Line 116: the budget must hold at least one block.
  7. Line 118: nextn comes from the environment variable DEEPINFER_USE_NEXTN_DECODE, read with getenv (default 5, csrc/engine/utils.hpp:36-40).
  8. Lines 120-121: the prefill sum limit must be at least prompt_limit.
  9. Lines 126-128: MTP slots max_num_seqs … 1 go into a stack, so slot 1 comes out first. Slot 0 is padding.
  10. Lines 130-132: reserve the clone vectors for the worst case.

add_sequence and abort_sequence#

  1. Line 136: the arrival time is set here, in milliseconds since the epoch (csrc/engine/block_manager.hpp:20-25). This value goes into the time-to-first-token statistic (line 1009).
  2. Lines 138-139: reserve token ids for max_tokens outputs and block-table entries for ceil((len + max_tokens) / block_size) + 1 blocks.
  3. Lines 147-157: only an unfinished sequence with the same id is marked. The function returns the list of the aborted sequences.
  4. Lines 158-161: prompted is not scanned. That queue only holds forked sequences.

_schedule: the step type#

The concept page shows the voting code line by line (The scheduler, step 2). The structure is:

  1. Line 276: release the Python GIL. Other Python threads, such as the grammar builders, can run during scheduling.
  2. Line 277: lock the block manager and the state manager. Lockable::lock_ refuses to run while the GIL is held, and gives up after 20 seconds (csrc/utils/lockable.hpp:16-28).
  3. Lines 282-284: clear the clone vectors of the previous step. The previous SchedulerOutputs borrowed them.
  4. Lines 288-294: PROMPT and COMPLETION engines skip the vote.

_schedule_prefill: the loop, part 1#

The doc comment says, translated: "Prefill (prompt) scheduling: pick runnable prompts from the waiting queue. For a NORMAL engine, return nullptr if this round scheduled no prompt (scheduled and ignored both empty); _schedule then decides whether to switch to decode. Other engine types always return SchedulerOutputs." (csrc/engine/scheduler.hpp:347-349).

  1. Line 355: num_curr_seqs starts at the size of running, so finished but not yet removed sequences also count.
  2. Line 372: the work of this sequence is its full length minus the cached tokens. For a recompute, that includes its earlier outputs.
  3. Line 374: an empty block table means "first chunk". The local name prefix_caching_hit is set to true here. It only switches off the lookahead check at line 454.
  4. Lines 386-396: get_num_blocks() of a new sequence is ceil(len / block_size), because it has no drafts and no in-flight tokens yet.

_schedule_prefill: forked prompts#

  1. Line 398: a forked sequence has a branch_id that starts with _ and a block table that it shares with its parent.
  2. Lines 413-415: it keeps the full blocks of the shared prefix, and needs new blocks for the rest.
  3. Lines 425-430: it gets its own state slot (a copy) and a copy of the half-full last block.
  4. Lines 431-437: the other parent blocks are only unpinned (pair (block, 0)), then the table gets the new blocks.

The pairs go to clone_states and clone_blocks. LLMEngine.step() sends them to the Worker in the same step (deepinfer/engine/llm_engine.py:889-905).

_schedule_prefill: the loop, part 2#

  1. Lines 440-442: the slot limit.
  2. Lines 444-449: the sum limit counts the full length of each sequence, not the chunk.
  3. Lines 451-458: a sequence that is neither new nor forked (a later chunk) must have num_tokens == 0 or at least lookahead_tokens cached tokens. The comment says that the block size is assumed to be larger than nextn.
  4. Line 464: the work must be at least lookahead_tokens.
  5. Lines 470-475: the chunk cut (see the concept page).

Lines 477-511 adjust the chunk for checkpoints and images, and lines 513-546 commit the side effects. The concept page explains both parts. _make_outputs (lines 263-268) wraps the result and adds references to the clone vectors.

_adjust_chunk_size#

The doc comment of the first helper says, translated: "Check whether position k_len is inside an image of the form MM_TOKEN_IMAGE + MM_TOKEN_IMAGE_PAD*N. True only if token_ids[k_len] == IMAGE_PAD and an MM_TOKEN_IMAGE comes before it. If token_ids[k_len] == MM_TOKEN_IMAGE, the cut is exactly at the start of an image: allowed, return false." (csrc/engine/scheduler.hpp:214-216).

  1. Line 218: a cut position that is not a pad token is never inside an image.
  2. Lines 221-228: walk back over pad tokens. Reaching the image token means "inside". Any other token means "not inside".
  3. Lines 237-239: a cut at or after the end of the sequence needs no change.
  4. Lines 244-246: grow until the first non-pad token.
  5. Lines 249-254: shrink over the pads and the image token, but not below the cached length.

_schedule_decode: clean-up and forked admission#

The doc comment says, translated: "Decode (completion) scheduling: first move the seqs from the prompted queue into running, then pick the seqs of this round in LCFS order; when blocks are not enough, preempt the seq with the shortest output." (csrc/engine/scheduler.hpp:556-557). The last part is wrong (see the warning below).

  1. Line 562: finished sequences leave running. Their MTP slots go back now, if process_outputs did not give them back already (line 993). Their blocks go back later, in finalize_seq.
  2. Lines 569-577: finished sequences anywhere in waiting go to ignored_seqs.
  3. Lines 595-620: forked sequences in prompted join running, as long as there is room and a free block and state slot. The comment above line 556 is wrong about the preemption order (see below).

_schedule_decode: the decode loop#

  1. Lines 624-625: std::sort with "more output first". std::sort is not stable, so the order of equal lengths is not fixed.
  2. Line 629: take running[r - 1], the fewest outputs among the sequences left.
  3. Lines 630-634: while the free list is empty and two or more sequences are left, preempt running[l], the most outputs.
  4. Lines 635-640: with a free block, call _append_slot; without one (only the current sequence is left), preempt it.
  5. Line 645: every sequence is either scheduled or preempted. A sequence that does not fit because of max_seqs would fail this check.
  6. Line 646: running is cleared. schedule() sets it to the batch (line 679).
  7. Lines 648-652: sort the batch by length, then MTPVarlen gives seqlens_q.

The comment and the code disagree

The comment says that the scheduler preempts the sequence with the shortest output (lines 556-557). The code preempts from the front of a list sorted with the longest output first. This site describes the code.

schedule: the public entry#

  1. Line 689: max_seqlen_q = nextn + 1.
  2. Line 694: count one more schedule for the MTP bookkeeping.
  3. Line 695: the "golden" tokens: an optional list of reference tokens from SamplingParams.golden_token_ids (deepinfer/engine/llm_engine.py:562, csrc/engine/sequence.hpp:155-165). The YOCO equivalence example sets them (examples/yoco/yoco_equiv.py:682).
  4. Line 697: seqlen_k = cached + in flight + seqlen_q.
  5. Lines 700-705: the highest position must stay below runtime_max_model_len, or the call fails.
  6. Lines 706-707: one SequenceMetadata from the pool. It holds references into the Sequence, not copies.
  7. Line 726: reserve nextn + 1 in-flight tokens on the sequence.

_preempt, _append_slot and the free functions#

free_seq_nolock gives back the MTP slot, the state slot and all blocks. BlockManager::free_blocks_nolock frees the table in reverse order, and a block whose reference count reaches 0 goes to the tail of the free list (csrc/engine/block_manager.hpp:95-103, csrc/engine/block_manager.hpp:147-149). free_finished_seqs gives back only the MTP slot. _preempt calls free_seq_nolock in both of its paths (csrc/engine/scheduler.hpp:779, csrc/engine/scheduler.hpp:787).

Line 820 adds at most one block per call; the check at line 826 fails if one block is not enough. Lines 821-825 free extra blocks when the reserve shrinks.

process_outputs: after the step#

For each scheduled sequence, in order:

  1. finish_inflight_step() (line 903).
  2. Finished already (an abort while in flight): skip, give back the MTP slot; in a prompt step, put it into running so that the next decode removes it (lines 906-915).
  3. Preempted while in flight (decode step, status WAITING): skip all bookkeeping (lines 920-925).
  4. advance_optimistically(seqlen_q) and the structured-output status (lines 927-929).
  5. Prompt complete or decode: read the accepted drafts, append them and the sampled token with _check_stop after each one, then commit_processed_tokens in decode (lines 940-1000).
  6. Prompt not complete: back to the front of waiting (lines 1011-1020).

It returns two arrays: the time to the first token for sequences with exactly 1 output, and the number of tokens pushed per sequence (lines 1030-1032). Both borrow static buffers.

fork_seq#

A fork copies the tokens of a sequence that already has a cached prefix, shares its blocks and its state slot (with pin), and puts the new sequence either at the front of waiting (prompt not complete) or into prompted (csrc/engine/scheduler.hpp:1108-1120). No file in the deepinfer package calls it. examples/benchmark.py uses it to copy one cached prompt to a batch (examples/benchmark.py:331-352).

process_MTPInfo#

A comment at the top of the loop says, translated: "ZOS async: a seq that _preempt preempted for recompute while this step was in flight already had all its MTP counters reset; drop this step's bookkeeping too (same test as in process_outputs). Else process_cnt would run ahead of schedule_cnt, and the pairing check in MTPVarlen::schedule would fail." (csrc/engine/scheduler.hpp:1214-1216).

  1. Line 1220: process_cnt counts processed steps; schedule() counts scheduled steps (line 694). MTPVarlen uses the difference to know which round an accept rate belongs to (csrc/engine/mtp_varlen.hpp:195-201).
  2. Lines 1235-1238: the new drafts replace the old ones.
  3. Lines 1246-1251: accept_rates[j] is the product of the first j + 1 confidence values. Example: confidences [0.9, 0.8, 0.5] give accept rates [0.9, 0.72, 0.36].
  4. Lines 1253-1256: in a decode step, mark that the new draft info is in the MTP pool and not yet read.

clone_and_zero_states_and_blocks#

Line 1267 says, translated: "The returned numpy arrays borrow this storage (empty capsule). The caller must use them before the next call." The storage is the function-level static vectors of line 1268.

Each pair (src, dst) copies one state row or one block row on the current stream; dst = 0 skips the copy. Every src is returned for unpinning. The engine unpins them after a CUDA event, in the pre_sampler_sync of the same step (deepinfer/engine/llm_engine.py:109-116).

Deep dive

Threads, locks and static buffers

  • GIL. _schedule releases the GIL for its whole run (line 276). It must, because Lockable::lock_ fails if the caller holds the GIL. Translated: "Holding the GIL when you call this function is forbidden, to avoid deadlock!" (csrc/utils/lockable.hpp:16). fork_seq and free_seq release it too (csrc/engine/scheduler.hpp:1109, csrc/engine/pybind_scheduler.cpp:100-102).
  • Lock order. BlockManagerMutexAcquire locks the state manager first, then the block manager, and unlocks in the opposite order (csrc/engine/block_manager.hpp:189-204).
  • Lock timeout. A lock that is not free after 20 seconds fails with "failed to lock mutex" (csrc/utils/lockable.hpp:22-27).
  • One caller thread. The queues have no lock of their own. The engine calls the scheduler from its main thread only.
  • Static buffers. process_outputs (lines 880-881, 896-897) and clone_and_zero_states_and_blocks (line 1268) keep function-level static vectors. They are shared by all Scheduler objects in the process, and the results of one call are overwritten by the next.
  • Object pool. SequenceMetadataPool::allocate reuses a released object with placement new, or makes a new one (csrc/utils/object_pool.hpp:21-32). release destroys and keeps only objects that came from the pool (csrc/utils/object_pool.hpp:34-42).

Deep dive

Interaction with ZOS and speculative decoding

With ZOS, schedule() for step N+1 runs before process_outputs for step N. Four parts of this file handle that order:

  1. In-flight tokens. start_inflight_step(nextn + 1) at schedule time and finish_inflight_step() at process time (csrc/engine/scheduler.hpp:726, csrc/engine/scheduler.hpp:903). Example: after step N is scheduled, total_inflight_tokens = 6. After step N+1 is scheduled, it is 12. When step N is processed, total == last is false, so it becomes last = 6 (csrc/engine/sequence.hpp:249-256).
  2. Optimistic counters. process_outputs first adds the whole seqlen_q to num_tokens, then sets it to the old value plus the accepted tokens (csrc/engine/scheduler.hpp:927, csrc/engine/scheduler.hpp:999).
  3. Preempted in flight. Skipped in process_outputs and in process_MTPInfo (lines 920-925, 1217-1219).
  4. Device corrections. The CPU seqlen_q and seqlen_k are estimates. The Worker corrects them on the device, and update_metadata_for_sampling_zos writes the final values back into the metadata and into scheduler_outputs.seqlens_q (csrc/engine/zos.cpp:279-305).

The MTP counters. MTPVarlen::schedule checks that process_cnt <= schedule_cnt <= process_cnt + 1 for every sequence (csrc/engine/mtp_varlen.hpp:195-196). The scheduler increments schedule_cnt in schedule() and process_MTPInfo increments process_cnt, so at most one step can be in flight per sequence.

Worked example: one prefill and one decode, with all counters

One sequence, prompt 300 tokens, budget 32768, block size 128, nextn = 5, ZOS on, one DP rank, 100 KV blocks, a state manager.

  1. Prefill. decode_step = 0 → ALL point. Usage 1/100 ≤ 0.9. _can_allocate_with_state(3) → OK. seqlen_q = 300, num_batched_tokens = 300. allocate_seq: blocks [1, 2, 3] (head of a fresh free list), state slot 1. Status RUNNING, MTP slot 1. schedule(): decode_step = 0, seqlen_k = 0 + 0 + 300 = 300, schedule_cnt = 1, in-flight 6.
  2. Process. In-flight back to 0. num_tokens = 300 = len → into running. process_MTPInfo: 5 placeholder drafts, process_cnt = 1. One token appended: len = 301. Output length 1, so the time to the first token is recorded.
  3. Decode. decode_step = 0 → ALL point, but waiting is empty → want = false → vote fails → decode. Sort, serve; _append_slot: ceil((301 + 0 + 5) / 128) = 3 blocks, no change. seqlens_q = [6], 6 tokens. decode_step = 1. seqlen_k = 300 + 0 + 6 = 306; position end 306 − 6 + 6 + 5 = 311 must be ≤ runtime_max_model_len.

The block ids in step 1 assume a fresh free list: Blocks starts with _head = 1 and links 1, 2, 3, … (csrc/engine/block_manager.hpp:28-35).

Check yourself#

  1. 1
    Which method does LLMEngine.step() call on the scheduler, and what does it return?
    easy
    Show answer

    schedule(sequence_metadata_pool). It returns a tuple: a list of SequenceMetadata objects from the pool, and a SchedulerOutputs object (csrc/engine/scheduler.hpp:667, csrc/engine/scheduler.hpp:735).

  2. 2
    Why does _schedule release the GIL before it locks the block managers?
    medium
    Show answer

    Lockable::lock_ fails if the caller holds the GIL, to avoid a deadlock (csrc/utils/lockable.hpp:16). Releasing the GIL also lets other Python threads, such as the grammar builders, run during scheduling (csrc/engine/scheduler.hpp:276).

  3. 3
    In process_outputs, a decode sequence has num_tokens = 100 and seqlen_q = 6, and the sampler accepts 2 drafts. What is num_tokens after the call, and why not 106?
    medium
    Show answer

    103. advance_optimistically(6) first sets it to 106, then commit_processed_tokens(3) sets it to 100 + 3 (csrc/engine/scheduler.hpp:927, csrc/engine/scheduler.hpp:999). Rejected drafts take no KV cache.

  4. 4
    The confidence head gives [0.9, 0.8, 0.5, 0.5, 0.2] for one sequence. What does process_MTPInfo store in accept_rates, and which earlier values does build_request_outputs see?
    hard
    Show answer

    The running products: [0.9, 0.72, 0.36, 0.18, 0.036] (csrc/engine/scheduler.hpp:1246-1251). The raw values go to confidence_raw, and the old raw values move to prev_confidence_raw first (line 1241). build_request_outputs reads prev_confidence_raw, so process_MTPInfo must run before it (csrc/engine/scheduler.hpp:1244-1245, csrc/engine/outputs.hpp:291-293).

  5. 5
    Which members of Scheduler are written but never read, and what does that tell you about DEEPINFER_YOCO_PREFILL_KEEP_TOKENS?
    hard
    Show answer

    truncate_len, dp_size, dp_rank, schedule_counter, last_step_num_batched_tokens, last_step_cached_tokens and tokens_chunked_prefill_remaining (see the deep dive "Member variables"). The engine passes the YOCO keep length as truncate_len (deepinfer/engine/llm_engine.py:315), but the scheduler does not use it in this release. Only the FLOP estimate that the scheduler calls gets the value, through a separate argument (deepinfer/engine/llm_engine.py:318-322).

  • The schedulerIn every engine step, the C++ scheduler runs either a prefill batch or a decode batch. It starts prefills only at attempt points, cuts long prompts into chunks, gives KV blocks, and preempts sequences when the blocks run out.
  • Data parallelism and step votesEach data-parallel replica is a separate engine process with its own requests. All replicas must run the same kind of step at the same time, so they vote with all-reduces over the DP group.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
