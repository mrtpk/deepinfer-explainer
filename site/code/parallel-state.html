parallel_utils/parallel_state.py: the process groups

Purpose#

parallel_state.py makes the process groups of one rank and keeps them in the global object PG, which all other code reads.

Filedeepinfer/model_executor/parallel_utils/parallel_state.py, 230 lines of Python.
Main classParallelProcessGroup (deepinfer/model_executor/parallel_utils/parallel_state.py:51), and the module-level instance PG (deepinfer/model_executor/parallel_utils/parallel_state.py:190).
Runs inEvery rank process: the engine process (CP rank 0) and each CP follower process. Called once per process, at worker start-up.
Called by_init_distributed_environment in deepinfer/worker/base.py. About 20 files read PG.
Callstorch.distributed.new_group, einops.rearrange, PLATFORM (backend and options), MessageQueue, and deep_ep.get_physical_domain_size.
Not in this fileThe first connection of all ranks (init_process_group, in worker/base.py). The collectives themselves (communication_op.py, cp.py, DeepEP). No tensor- or pipeline-parallel group.

Where it sits#

Panel 2 is the result of create_process_groups for dp_size = 4, cp_size = 2, ep_size = 8. The rest of this page shows how the file computes those lists.

Who calls it#

  • _init_distributed_environment joins all ranks with a Gloo default group, then calls init_parallel_groups(dp_size, ep_size=..., cp_size=..., enp_size=...) (deepinfer/worker/base.py:315-344). Each Worker runs it in init_dist (deepinfer/worker/base.py:196-201).
  • Readers of PG. The engine reads the DP group for the votes (deepinfer/engine/llm_engine.py:313, deepinfer/engine/llm_engine.py:665-679). The model reads the CP group for mirror CP (deepinfer/model_executor/models/deepseek.py:168) and the EP group for MoE (deepinfer/model_executor/models/v4_modules/mlp.py:192-194). The worker reads the world group to agree on the KV block count (deepinfer/worker/base.py:265-266) and the CPU CP group to send method calls (deepinfer/worker/base.py:298-300).
  • cp_broadcast_object is used by the worker loop (deepinfer/worker/base.py:132), broadcast_tensor_dict (deepinfer/model_executor/parallel_utils/communication_op.py:72-75) and InputMetadata.broadcast (deepinfer/model_executor/input_metadata/input_metadata.py:153-156).
  • PG_dict is read by the NCCL memory statistics, which label each communicator with its group name (deepinfer/model_executor/parallel_utils/nccl_memory.py:26-34).

What it calls#

  • torch.distributed.new_group through _split_group_cached (deepinfer/model_executor/parallel_utils/parallel_state.py:26-37).
  • PLATFORM.distributed_backend ("nccl" or "hccl") and PLATFORM.get_distributed_options() (deepinfer/model_executor/parallel_utils/parallel_state.py:82-83). See Hardware platforms: NVIDIA and Ascend.
  • MessageQueue.create_from_process_group for the CP group (deepinfer/model_executor/parallel_utils/parallel_state.py:122-124). See distributed/shm_broadcast.py: MessageQueue.
  • deep_ep.get_physical_domain_size in is_within_nvl_domain (deepinfer/model_executor/parallel_utils/parallel_state.py:130-134).

Walk through the main methods#

create_process_groups: the rank lists#

  1. Line 80: the rank list is 0 … max(enp_size, dp_size × cp_size) − 1. It is the world of this job.
  2. Lines 86-89: world is one group of all ranks. local has one group per rank (each rank alone).
  3. Line 92: DP groups. The pattern "(replica dp cp) -> (replica cp) dp" makes one group for each (replica, cp_rank) pair. Its members are the ranks with that cp_rank in each engine.
  4. Line 97: CP groups are blocks of cp_size neighbour ranks: the ranks of one engine.
  5. Lines 102-106: EP groups are blocks of ep_size neighbour ranks. If ep_size is the world size, the code reuses the world group object.
  6. Line 109: Engram groups are blocks of enp_size neighbour ranks.
  7. Lines 113-118: EP-in-DP groups use the same block rule as EP. With ep_size = 1, the code reuses local.
  8. Lines 94, 99, 118: Gloo copies of the DP, CP and EP-in-DP groups, for CPU tensors.
  9. Lines 123-124: with more than one CP rank, the CPU CP group gets a shared-memory queue: chunks of 1 << 20 bytes (1 MiB), 10 chunks.
  10. Line 126: start the device communicators (next section).

Every rank must make every group

_split_group_cached calls dist.new_group for every rank list, also for lists that do not contain this rank (deepinfer/model_executor/parallel_utils/parallel_state.py:33-36). PyTorch requires that all processes call new_group for each group, in the same order. So all ranks must call create_process_groups with the same sizes.

_split_group_cached: one group per rank list, made once#

The cache key is (rank lists, backend, options). The caller turns the lists into tuples, because the cache needs hashable keys (line 45). Inside one call of create_process_groups, the options object is the same for all device groups (line 83). So two splits with the same rank lists return the same group object. The deep dive shows where this happens.

cp_broadcast_object: objects from the CP driver#

The writer of the queue is CP rank 0 (the default writer_rank, deepinfer/distributed/shm_broadcast.py:432-437). On rank 0, the function puts the object into the queue and returns it. On the other ranks, it waits for the next object and returns it. The call order must be the same on all CP ranks: the k-th call on a follower returns the object of the k-th call on the driver.

init_device_groups: start the communicators#

  1. Line 179: walk all attributes of the object, in the order of __init__: dp, cp, ep, ep_in_dp, enp, world, local, then the rest.
  2. Lines 180-184: skip everything that is not a NCCL or HCCL process group (the Gloo copies, the tag, the queue).
  3. Lines 185-187: run one all-reduce of a one-element tensor on each group object once. A group object that two attributes share runs once (the id check).

All ranks walk the same attribute order, so the collectives match.

init_parallel_groups: the entry point#

The function makes a new object, stores it in PG_dict[tag], and for the default tag copies all its attributes into the global PG (line 227). Modules that ran from ... import PG before this call see the new groups, because PG is the same object. The log line lists the ranks, for example RANK 3, DP 1/4, CP 1/2, EP 3/8 (ep_in_dp:3), ENP 3/8, WORLD 3/8, GPU 1 for --ep 8 --cp 2 (lines 214-229). The ENP part appears because enp_size defaults to 8 here.

The small methods#

  • is_within_nvl_domain(group): True on NPU. On GPU, True for a group of one rank, or if the group size is at most the NVLink domain size that DeepEP reports (deepinfer/model_executor/parallel_utils/parallel_state.py:130-134). The MoE layer uses it to choose mega-MoE (deepinfer/model_executor/models/v4_modules/mlp.py:184-188).
  • cleanup_shm_broadcast(): closes the shared memory of the queue, and unlinks it on the rank that made it. The docstring gives the reason: "so that the resource_tracker won't report leaked shared_memory warnings" (deepinfer/model_executor/parallel_utils/parallel_state.py:161-169). WorkerBase.stop calls it (deepinfer/worker/base.py:147).

Deep dive

Worked example: --ep 8 --cp 2 (8 ranks)

dp = max(1, 8 // 2) = 4 (deepinfer/config.py:161-162). enp defaults to cp × dp = 8 (deepinfer/config.py:172). So ranks = [0 … 7], and rank r is engine r // 2, CP rank r % 2.

SplitRank listsObject
world[[0..7]]W
local[[0], [1], …, [7]]8 groups, each rank keeps its own
dp[[0, 2, 4, 6], [1, 3, 5, 7]]new
cp[[0, 1], [2, 3], [4, 5], [6, 7]]new
epep_size == 8W (line 103)
enp[[0..7]]W again (cache hit: same key as world)
ep_in_dp[[0..7]]W again (cache hit)

So init_device_groups runs only four all-reduces on rank 3: dp, cp, W and local. The Gloo copies are three more splits (DP, CP and EP-in-DP), with backend="gloo" and no options. Each split calls new_group once per rank list.

With --ep 2 --dp 8: ep is [[0,1],[2,3],[4,5],[6,7]], and ep_in_dp has the same lists. The cache returns the ep object for ep_in_dp, because the key (lists, backend, options) is the same.

With a larger Engram group (for example dp = 2, cp = 1, enp = 4): the world has 4 ranks, and replica = 2. The DP groups are [0, 1] and [2, 3]: two separate DP worlds that share one Engram group [0..3].

Deep dive

Processes, order and start-up cost

  • Who runs it. Every rank process, once. In a CP engine, the driver and each follower run it inside their own Worker.__init__ (deepinfer/worker/base.py:114-118).
  • Order of collectives. Each new_group call, the queue handshake and the warm-up all-reduces are collectives. They run in program order, the same on all ranks.
  • The queue handshake. create_from_process_group broadcasts a handle object over the Gloo CP group and then waits until all readers connected (deepinfer/distributed/shm_broadcast.py:446-461).
  • The device tensor. The warm-up uses torch.zeros(1).cuda() (deepinfer/model_executor/parallel_utils/parallel_state.py:187). On Ascend, torch.cuda is mapped to torch.npu (Hardware platforms: NVIDIA and Ascend).
  • Several tags. init_parallel_groups can make extra group sets with another tag. Only the default tag goes into PG. In this release, only the worker calls it, with the default tag (deepinfer/worker/base.py:343).

Check yourself#

  1. 1
    Does DeepInfer have a tensor-parallel group?
    easy
    Show answer

    No. ParallelProcessGroup has dp, cp, ep, ep_in_dp, enp, world and local, and three Gloo copies (deepinfer/model_executor/parallel_utils/parallel_state.py:52-65). There is no TP or PP group.

  2. 2
    Which backend do the CPU groups use, and which group carries the method calls from the CP driver?
    easy
    Show answer

    Gloo. The method calls go through the shared-memory queue that is set up on cpu_cp_group (deepinfer/model_executor/parallel_utils/parallel_state.py:99, deepinfer/model_executor/parallel_utils/parallel_state.py:123-124).

  3. 3
    With dp_size = 2 and cp_size = 4, what are the DP groups and the CP groups?
    medium
    Show answer

    Ranks 0..7. CP: (dp cp) -> dp cp gives [0, 1, 2, 3] and [4, 5, 6, 7]. DP: (replica dp cp) -> (replica cp) dp gives [0, 4], [1, 5], [2, 6] and [3, 7] (deepinfer/model_executor/parallel_utils/parallel_state.py:92-98).

  4. 4
    Why does init_device_groups run an all-reduce on the local group, which has only one rank?
    hard
    Show answer

    The default process group is Gloo, so the NCCL/HCCL subgroups start lazily; a collective must run once to make the communicator. The translated docstring says that single-rank groups cannot be skipped: Engram's deep_ep reuses the communicator through backend._comm_ptr(), and a null pointer gives a segmentation fault (deepinfer/model_executor/parallel_utils/parallel_state.py:174-176).

  5. 5
    In a run with --ep 8 --cp 1 (8 ranks), are PG.ep, PG.enp and PG.world three groups or one?
    hard
    Show answer

    One object. ep_size equals the rank count, so ep = world (line 103). enp_size defaults to 8, so the Engram split is [[0..7]] with the same backend and options as the world split, and _split_group_cached returns the cached world group (deepinfer/model_executor/parallel_utils/parallel_state.py:26-37, deepinfer/config.py:172). init_device_groups warms it up once, because of the id check.

Related pages

  • distributed/shm_broadcast.py: MessageQueueMessageQueue sends pickled Python objects from one writer process to several reader processes through a ring buffer in shared memory. DeepInfer uses it inside each context-parallel group, from the driver to the followers.
  • parallel_utils/userbuffer.py: the communication buffer manageruserbuffer.py owns all long-lived communication buffers of one loaded model: the DeepEP buffer for MoE, the DeepGEMM symmetric buffers for mega-MoE, the context-parallel bucket buffer, and the Engram buffer. It also limits the SMs of compute kernels while DeepEP runs.
  • worker/base.py: WorkerBase, the resource layer of a workerWorkerBase sets up one device for one rank - torch settings, NUMA and CPU binding, process groups, the model, the memory profile, the KV cache and the CUDA graphs - and runs the call loop of the context-parallel followers.
  • deepinfer/platform.py: the Platform classes and get_platform()platform.py defines the Platform base class, PlatformGPU and PlatformNPU, and get_platform(), which makes one of them per process from the device files. The package exposes it as deepinfer.PLATFORM, made on first use.
  • Expert parallelism: dispatch, grouped GEMM, combineDeepInfer splits the expert slots of every MoE layer evenly over the EP ranks. DeepEP dispatch sends each token to the ranks of its experts, DeepGEMM runs grouped GEMMs there, and DeepEP combine brings the results back.
  • Hardware platforms: NVIDIA and AscendDeepInfer runs on NVIDIA GPUs and on Huawei Ascend NPUs. At start-up it makes one Platform object, and the shared code reads all hardware choices from it.
  • Tour: One step on many GPUsFollow one prefill step on 4 GPUs (2 data-parallel engines, each with 2 context-parallel ranks) in 10 stops, from the step vote to the outputs, with the rank, the group and the tensor shapes at each stop.
  • Parallelism basicsLarge models run on many devices. The work can be split by requests (DP), by matrices (TP), by layers (PP), by tokens (CP) or by experts (EP). DeepInfer uses DP for attention, CP for long prefills and EP for the MoE experts. It has no TP and no PP group.
