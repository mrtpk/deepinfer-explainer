worker/model_runner.py: the ModelRunner class

Purpose#

ModelRunner is the layer between the Worker and the model: for each step it turns the scheduled sequences into device inputs, starts the forward pass and the sampler, and it does the start-up work for memory profiling and CUDA graph capture.

Filedeepinfer/worker/model_runner.py, 644 lines of Python. The header says "Derived from vLLM; modified by DeepSeek." (deepinfer/worker/model_runner.py:2)
Main classModelRunner (deepinfer/worker/model_runner.py:53). Also the result type MainModelOutput (deepinfer/worker/model_runner.py:46-50).
Runs inEvery worker process: the driver worker (in the engine process) and each context-parallel follower. Only the driver has the sequence list.
Called byWorker.execute_model_step each step, and WorkerBase at start-up and shutdown.
CallsThe model (DeepseekForCausalLM), ModelMetadata.prepare_inputmetadata_dict, C++ prepare_sampler_inputs, CudaGraphRunner, DFlashCudaGraphRunner, CacheEngine (profile only).
Not in this fileNo scheduling, no kernels, no cache allocation for serving. The C++ code computes the index tensors; the model and the sampler do the math.

Where it sits#

Blue is the driver rank. Pink is a follower rank, which exists only with context parallelism. Amber is the eager path, and violet marks the broadcasts.

Who calls it#

  • WorkerBase.__init__ makes the runner with the block size of the cache (deepinfer/worker/base.py:90-96).
  • Start-up: load_model (deepinfer/worker/base.py:207), profile_run inside profile_num_available_blocks (deepinfer/worker/base.py:222-225), then capture_model, profile_decode_perf and capture_dflash_model inside warm_up_model (deepinfer/worker/base.py:274-285).
  • Each step: Worker.execute_model_step calls execute_main_model and execute_sample (deepinfer/worker/worker.py:121-159), and later post_process (deepinfer/worker/worker.py:268). For a placeholder step it first asks for _placeholder_seq_metadata (deepinfer/worker/worker.py:126-127).
  • Shutdown: WorkerBase.stop calls destroy_cuda_graphs (deepinfer/worker/base.py:142-146).

What it calls#

  • The input builder. self.model.model_metadata.prepare_inputmetadata_dict (deepinfer/worker/model_runner.py:131-139), which calls the C++ functions of prepare_tensor_input_v4.cpp: the C++ input builder.
  • The sampler input builder. C++ prepare_sampler_inputs (deepinfer/worker/model_runner.py:15, deepinfer/worker/model_runner.py:244-249); see engine/prepare_sample.cpp: the sampler inputs.
  • The model. self.model(...) for the forward pass and self.model.sample(...) for sampling (deepinfer/worker/model_runner.py:329, deepinfer/worker/model_runner.py:361-365).
  • The graph runners. worker/cuda_graph_runner.py: CUDA graph capture and replay (deepinfer/worker/model_runner.py:34-36).
  • Collectives. broadcast_tensor_dict to the context-parallel group (deepinfer/worker/model_runner.py:212, deepinfer/worker/model_runner.py:259).

Walk through the main methods#

__init__: graphs on or off#

  1. Line 73: graphs are on unless DEEPINFER_ENFORCE_EAGER is set or the engine is a PROMPT engine.
  2. Line 77: the largest graph has max_num_seqs × (1 + nextn) rows.
  3. Line 78: with ZOS, the graph inputs live on the device.
  4. Lines 80-85: DFlash graphs need main graphs, nextn > 0, a dflash_cfg and no DEEPINFER_DFLASH_ENFORCE_EAGER.

load_model: sizes and the YOCO keep guard#

YOCO keep tokens must cover the window and the backtracking

With YOCO truncation on, start-up stops with AssertionError unless window_size + DEEPINFER_MAX_BACKTRACKING_TOKENS ≤ DEEPINFER_YOCO_PREFILL_KEEP_TOKENS. With a window of 128 and 6 backtracking tokens, the minimum is 134. The README value is 140 (README.md:25).

  1. Lines 98-99: only the driver of a non-PROMPT engine makes the MTP info pool of the draft model.
  2. Lines 101-102: the window size comes from the model config. The ring size is window + DEEPINFER_MAX_BACKTRACKING_TOKENS, plus extra rows when DEEPINFER_PREFILL_STORE_EXTRA_STATE is on (deepinfer/worker/cache_engine.py:88-110).
  3. Lines 107-113: the YOCO guard. C++ checks the same rule again in each prefill (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:355-357).
  4. Line 115: the width of a decode block table. With runtime_max_model_len = 32784: ⌈32784 / 128⌉ = 257, rounded up to 320.

_prepare_input_tensors#

The dict from C++ becomes the keyword arguments of the metadata class: InputMetadataV4, or InputMetadataV4VL for a vision model (deepinfer/model_executor/model_metadata_utils.py:142-144). num_reqs is the number of sequences, with padding when the caller added it. On the graph path the caller passes out_dict, and the function returns None.

_prepare_input_driver: graph or eager#

The helper _graph_input_metadata sets the real request count. Its comment says, translated: "The real request count, without padding. It must match the sampler inputs, which have no padding. It is in input_metadata because with CP only the driver has the sampling inputs." (deepinfer/worker/model_runner.py:164-169).

  1. Line 180: total_q is the sum of seqlen_q, unless the Worker passes it. For a decode step the driver Worker passes scheduler_outputs.num_batched_tokens (deepinfer/worker/worker.py:117).
  2. Line 182: a graph runs for a decode step when graphs are on and captured.
  3. Lines 185-191: select the graph, add graph_size − total_q padding sequences, and let the builder write into the graph's source buffers. Then set the real request count on the device object.
  4. Lines 194-198: the eager path builds a new object and copies every tensor to the device without a wait.
  5. Lines 200-212: with CP above 1, broadcast a small dict. Only an eager step also sends all tensor fields, flattened to one dict level.

_prepare_input_follower#

A follower selects the same graph from total_q. The tensor values reach its graph buffers inside the replay: the recorded InputMetadata.broadcast() copies them from rank 0 (deepinfer/worker/cuda_graph_runner.py:64-65).

execute_main_model#

  1. Line 319: build the input (driver) or receive it (follower).
  2. Lines 321-325: two timers and the sync guard. The CPU timer name contains the request count and the row count, for example launch_forward_N2_B12.
  3. Lines 326-329: replay or eager call. Both return at once; the device works in the background.

prepare_sampler_inputs and execute_sample#

The driver passes the real sequence list, without graph padding. So the sampler reads only real rows. With CP, the followers get the row indices and build a SamplerInputs without the driver part (deepinfer/worker/model_runner.py:260-275). execute_sample then calls self.model.sample(...) inside the sync guard. It passes kv_caches only when nextn > 0, because the draft model needs the cache (deepinfer/worker/model_runner.py:348-365).

post_process#

The sampler leaves work that needs finished device results in post_funcs. The Worker calls post_process after it waits for the sample event (deepinfer/worker/worker.py:262-268). For a prefill step, the driver converts the prompt log-probabilities in C++ (update_prompt_logprobs).

profile_run: the memory profile#

  1. Line 448: a NORMAL engine profiles a prefill batch; only a COMPLETION engine profiles a decode batch.
  2. Line 452: the lengths come from _build_prompt_profile_seq_lens (deep dive).
  3. Line 476: each sequence gets its own blocks, in order, so the profile cache has exactly the blocks it needs.
  4. Lines 505-507: a temporary CacheEngine with these blocks, filled with zeros.
  5. Lines 510-512: the run uses a forced MoE imbalance of 1.8, so the profile sees a bad expert load. Then the value goes back to 0.0.

Capture and destroy#

capture_model passes _prepare_input_tensors and a decode placeholder to the graph runner (deepinfer/worker/model_runner.py:514-529). capture_dflash_model needs the main graphs and reuses their pool and stream (deepinfer/worker/model_runner.py:538-549). destroy_cuda_graphs frees both runners; its docstring explains that NCCL inside graphs holds extra resources that block the destruction of the process group (deepinfer/worker/model_runner.py:633-644). The page worker/cuda_graph_runner.py: CUDA graph capture and replay reads the runners line by line.

Deep dive

The profile batch: lengths with numbers

  1. Lines 407-409: split max_num_batched_tokens evenly over max_num_seqs sequences for seqlen_q.
  2. Line 414: the first sequence gets the longest possible seqlen_k, runtime_max_model_len.
  3. Lines 417-439: with DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K set, the other sequences grow until the sum of seqlen_k hits the limit (clamped between the minimum and max_num_seqs × runtime_max_model_len).

Example A, the settings of examples/offline_inference.py (max_num_seqs=4, max_num_batched_tokens=32768, examples/offline_inference.py:52-54) and runtime_max_model_len = 32784: seqlen_q = [8192, 8192, 8192, 8192], seqlen_k = [32784, 8192, 8192, 8192]. Blocks: ⌈32784/128⌉ + 3 × 64 = 257 + 192 = 449.

Example B, the same with DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K=65536: the minimum sum is 57360, so 8176 tokens remain. The loop adds 2726, 2725 and 2725: seqlen_k = [32784, 10918, 10917, 10917], sum 65536.

The prefill sequences use top_p=0.99 and top_logprobs=20 (deepinfer/worker/model_runner.py:484), so the profile also counts the memory of the log-probability path. Each sequence gets its own MTP write slot seq_id + 1, unlike padding, which uses slot 0 (deepinfer/worker/model_runner.py:491-492).

Check yourself#

  1. 1
    Which method of ModelRunner does the Worker call to start the forward pass, and does it wait for the device?
    easy
    Show answer

    execute_main_model (deepinfer/worker/worker.py:122). It does not wait: the docstring says it "must NOT contain any cuda synchronize", and the launch runs inside forbid_cuda_sync() (deepinfer/worker/model_runner.py:315-324).

  2. 2
    You set DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact and DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=128, with a window of 128 and the default backtracking. What happens?
    medium
    Show answer

    Start-up stops in load_model with AssertionError: 128 + 6 = 134 > 128 (deepinfer/worker/model_runner.py:107-113). The default backtracking is at least nextn + 1 = 6 (deepinfer/environ.py:132).

  3. 3
    On the graph path, the device buffers have 16 rows but only 2 real sequences. Where does the model find the real count, and why is it stored in the input metadata?
    medium
    Show answer

    _graph_input_metadata sets input_metadata.num_reqs to the real count (deepinfer/worker/model_runner.py:164-169). The comment says that with CP only the driver has the sampling inputs, so the count must travel in the metadata.

  4. 4
    With max_num_seqs=4, max_num_batched_tokens=32768, runtime_max_model_len=32784 and DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K=65536, what seqlen_k values does the profile batch use, and how many KV blocks does the temporary cache get?
    hard
    Show answer

    [32784, 10918, 10917, 10917] (deep dive "The profile batch"; deepinfer/worker/model_runner.py:405-441). Blocks: ⌈32784/128⌉ + ⌈10918/128⌉ + 2 × ⌈10917/128⌉ = 257 + 86 + 86 + 86 = 515 (deepinfer/worker/model_runner.py:476).

Related pages

  • worker/worker.py: the per-step WorkerWorker.execute_model_step runs every engine step on one rank in a fixed order - forward N, post-process N-1, sample N - and keeps a ZOS decode step for the next call. zos_status.py holds the two records that it keeps.
  • worker/base.py: WorkerBase, the resource layer of a workerWorkerBase sets up one device for one rank - torch settings, NUMA and CPU binding, process groups, the model, the memory profile, the KV cache and the CUDA graphs - and runs the call loop of the context-parallel followers.
  • model_executor/input_metadata/: the InputMetadata classesThe Python side of the input metadata. InputMetadataV4 holds the per-step index tensors, expands them on the device, broadcasts them to CP ranks and makes the YOCO and DFlash views; prepare_tensor_input_zos.py builds the decode metadata on the device when ZOS is on.
  • worker/cuda_graph_runner.py: CUDA graph capture and replayCudaGraphRunner records the main model's decode forward once per graph size and replays it; DFlashCudaGraphRunner does the same for the DFlash draft model, per number of sequences.
  • prepare_tensor_input_v4.cpp: the C++ input builderprepare_prompt_v4 and prepare_decode_v4 turn the scheduled SequenceMetadata list into a dict of pinned int32 tensors: positions, offsets, cache slot maps, load plans and window descriptions for the V4 attention layers.
  • engine/prepare_sample.cpp: the sampler inputsprepare_sampler_inputs reads the scheduled sequences once and builds the arrays that the sampler needs: which model-output rows to sample, per-sequence temperature, top-p, top-k and seed, and the draft-token bookkeeping of speculative decoding.
  • layers/sampler.py: the Sampler classsampler.py holds the Sampler module. It turns selected hidden states into float32 logits, samples prefill tokens, verifies draft tokens in decode steps and calls DFlash. sampler_utils.py holds the logits, sampling and prompt-logprob helpers.
  • models/deepseek.py: the DeepSeek-V4.1 modeldeepseek.py holds DeepseekModel (embedding, N decoder layers, final mix and norm) and DeepseekForCausalLM (lm head, sampler, DFlash, EPLB, weight loading). The forward returns hidden states.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • Context parallelism (mirror CP)With context parallelism, the devices of one engine share the tokens of a long prefill. A mirrored token order gives each device the same amount of causal attention work.
  • Tour: Life of a requestFollow one request from llm.generate() to its output tokens in 13 stops: tokenizer, admission, C++ scheduler, batch metadata, worker step, forward pass, KV cache, sampler, draft tokens and output objects.
