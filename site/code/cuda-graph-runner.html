worker/cuda_graph_runner.py: CUDA graph capture and replay

AdvancedCode mapabout 6 min read + 2 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • CUDA graphs Intermediate
  • Input metadata (varlen batching) Intermediate

Purpose#

These two small files hold the CUDA graph logic: they build the list of sizes, record one graph per size at start-up, pick the right graph for a step, replay it, and free it at shutdown.

Filesdeepinfer/worker/cuda_graph_runner.py, 168 lines. deepinfer/worker/dflash_cuda_graph_runner.py, 100 lines.
Main classesCudaGraphRunner (deepinfer/worker/cuda_graph_runner.py:69) and DFlashCudaGraphRunner (deepinfer/worker/dflash_cuda_graph_runner.py:31). Data classes CudaGraphData and DFlashCudaGraphData; the function build_graph_batch_sizes.
Runs inEvery worker process (driver and context-parallel followers), on the device of that rank.
Called byModelRunner (capture, select, replay, destroy); Worker._correct_seqlens_qk (select only); the DFlash model (DFlash replay).
Callstorch.cuda.CUDAGraph, the model's forward, the graph timer, the DFlash run_drafts.
Not in this fileThe decision to use a graph (ModelRunner), the values in the input buffers (the input builder), and the padding sequence (ModelRunner._placeholder_seq_metadata).

Where it sits#

Who calls it#

  • ModelRunner.__init__ makes both runners when graphs are on (deepinfer/worker/model_runner.py:75-91).
  • ModelRunner.capture_model and capture_dflash_model call capture at start-up (deepinfer/worker/model_runner.py:521-526, deepinfer/worker/model_runner.py:543-549).
  • ModelRunner._prepare_input_driver and _prepare_input_follower call select; execute_main_model calls replay (deepinfer/worker/model_runner.py:185, deepinfer/worker/model_runner.py:224, deepinfer/worker/model_runner.py:327).
  • Worker._correct_seqlens_qk calls select to count the padding sequences for ZOS (deepinfer/worker/worker.py:203-205).
  • DFlash.decode_forward calls the DFlash replay (deepinfer/model_executor/models/mtp/dflash.py:385-386).
  • ModelRunner.destroy_cuda_graphs calls destroy (deepinfer/worker/model_runner.py:641-644).

What it calls#

  • The model: model(kv_caches=..., input_metadata=...) and model.allocate_output (deepinfer/worker/cuda_graph_runner.py:66, deepinfer/worker/cuda_graph_runner.py:96).
  • The input builder that the caller passes as prepare_input_fn (deepinfer/worker/cuda_graph_runner.py:94).
  • The graph timer: register_graph, flip_event_buffer, unbind_graphs (deepinfer/worker/cuda_graph_runner.py:134-136, deepinfer/worker/cuda_graph_runner.py:152, deepinfer/worker/cuda_graph_runner.py:157).
  • DFlash: run_drafts, MTPDecodeInput.build_padding, the copy kernel copy_dflash_decode_input (deepinfer/worker/dflash_cuda_graph_runner.py:12-13).

Walk through the main methods#

build_graph_batch_sizes#

  1. Line 43: the interval cannot be larger than the maximum.
  2. Lines 46-48: powers of two below the interval.
  3. Line 49: multiples of the interval below the maximum.
  4. Line 50: the maximum itself, always last.

Examples with interval 8: maximum 24 gives [1, 2, 4, 8, 16, 24]; maximum 6 gives [1, 2, 4, 6]; maximum 1536 gives 195 sizes.

_run_model#

This function runs in the warm-up and inside the recording. With ZOS off (copy_inputs true), rank 0 copies the pinned CPU inputs to the device first, so the copy is part of the graph. With CP above 1, broadcast() sends the device tensors from rank 0 to the other ranks, also inside the graph (deepinfer/model_executor/input_metadata/input_metadata.py:120-167).

capture#

  1. Line 89: a new capture first destroys the old graphs.
  2. Lines 93-96: max_batch_size placeholder sequences give one input object; .cuda(non_blocking=True) gives the device object. With ZOS the input builder already makes device tensors, so both objects share memory.
  3. Line 102: largest size first.
  4. Lines 104-110: _cut takes the first bs rows of every tensor. The assert makes sure that every tensor has max_batch_size rows. This is true for decode metadata, where every field is per row.
  5. Lines 113-115: the warm-up on the side stream.
  6. Lines 117-119: fields from get_clean_list() go back to None, on both objects, so the recording computes them.
  7. Lines 124-127: the recording, with the shared pool and the side stream. capture_error_mode="thread_local" limits capture errors to this thread.
  8. Lines 130-137: instantiate (NVIDIA), register with the timer, and let the default stream wait for the side stream.
  9. Lines 139-141: keep the pool of the first graph; store the graph.

select, replay and destroy#

select raises ValueError when total_q is larger than the largest size. replay returns the stored output object: its tensors have graph_size rows and are the same memory in every replay of this graph. So the caller must read the result before the next replay of a graph that shares this memory. destroy also unbinds the timer.

The DFlash runner#

  1. Lines 52-54: two padding inputs: one for the graph, one kept as the fill value for unused rows.
  2. Lines 58-59: sizes are numbers of sequences; each graph cuts its views with cut(num_seqs).
  3. Lines 62-71: warm-up and recording of run_drafts, with the pool and stream of the main runner. Only the driver (do_sample) copies a sampled output.
  4. Lines 84-91: replay selects by the request count, copies the real decode input into the graph's buffers (copy_dflash_decode_input, which uses the padding for the rest), replays, and cuts the output to the real count.

run_drafts reads main_input_metadata: the device object of the largest main graph (deepinfer/worker/model_runner.py:546). This works for every step because the input fields of all main graphs are views of the same buffers: a smaller graph writes the first rows of the same memory. (The derived fields, such as kv_swa_index, are not shared: each graph computes its own.)

The docstring explains why the two metadata objects stay separate: "Metadata objects stay separate because forward populates derived fields" (deepinfer/worker/cuda_graph_runner.py:31). The forward pass writes fields such as kv_swa_index into the device object only.

Example sizes. With max_num_seqs=4 and nextn=5: max_batch_size = 24, sizes [1, 2, 4, 8, 16, 24]; the decode block tables of all graphs are views of one int32 [24, 320] tensor (max_num_blocks = 320 for runtime_max_model_len = 32784). DFlash sizes: [1, 2, 4].

Deep dive

The graph timer in the runner

On NVIDIA the capture keeps the raw graph (keep_graph=True) and wraps it in a C++ GraphHandle. The handle reads the raw graph and the executable graph from raw_cuda_graph() and raw_cuda_graph_exec() (csrc/graph_timer/graph_timer_cuda.cpp:62-65). get_event_record_nodes walks the graph nodes and keeps the event-record nodes (csrc/graph_timer/graph_timer_cuda.cpp:67-85). Before each replay, flip_event_buffer swaps the events of these nodes with cudaGraphExecEventRecordNodeSetEvent (csrc/graph_timer/graph_timer_cuda.cpp:57-60, deepinfer/timer.py:169-187). The page CUDA graphs explains why two sets of events are necessary.

On Ascend, cuda_graph_timer.supported() is false (deepinfer/timer.py:94-98), so the runner makes no handle. The capture logs "cuda_graph_timer probes not supported on this platform." (deepinfer/worker/cuda_graph_runner.py:90-91).

Check yourself#

  1. 1
    In which order does capture record the graph sizes, and why?
    easy
    Show answer

    Largest first (reversed(self.batch_sizes), deepinfer/worker/cuda_graph_runner.py:102). The first graph sets the memory pool, and the smaller graphs reuse it (deepinfer/worker/cuda_graph_runner.py:139-140).

  2. 2
    What does select(9) return when the sizes are [1, 2, 4, 8, 16, 24]?
    medium
    Show answer

    Size 16 and its CudaGraphData. bisect_left gives the index of the first size that is not less than 9 (deepinfer/worker/cuda_graph_runner.py:143-148).

  3. 3
    The DFlash graphs read the input metadata of the largest main graph. Why is that correct in a step that replays the size-8 main graph?
    hard
    Show answer

    All main graphs use views of the same size-max buffers (_cut, deepinfer/worker/cuda_graph_runner.py:104-109). The size-8 step writes rows 0-7 of the same memory that the largest object sees, and the comment in profile_decode_perf says the buffers are shared (deepinfer/worker/model_runner.py:581). This is in the deep dive "Data flow".

Related pages

  • worker/model_runner.py: the ModelRunner classModelRunner owns the model object on one rank. It builds the input metadata, runs the forward pass (eager or as a CUDA graph replay), prepares the sampler inputs, runs the memory profile and captures the graphs.
  • model_executor/input_metadata/: the InputMetadata classesThe Python side of the input metadata. InputMetadataV4 holds the per-step index tensors, expands them on the device, broadcasts them to CP ranks and makes the YOCO and DFlash views; prepare_tensor_input_zos.py builds the decode metadata on the device when ZOS is on.
  • models/mtp/dflash.py: the DFlash draft modeldflash.py holds DFlash, the draft model of DSpark. It writes draft keys from main-model features during the forward pass, makes 5 drafts per request in one pass after the verification, and stores drafts, logprobs and confidences in the MTP info pool.
  • DSpark: DFlash drafts and confidence-scheduled verificationDSpark makes 5 drafts per request with the DFlash draft model and predicts how likely each draft is to pass. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
