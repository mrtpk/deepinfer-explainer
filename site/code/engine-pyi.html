Purpose#

engine.pyi is the readable list of everything that the C++ engine gives to Python: 34 names, with types, but no code.

Filedeepinfer/_C/engine.pyi, 735 lines. A generated type stub (.pyi): make stubgen runs pybind11_stubgen on deepinfer._C (Makefile:27-28, scripts/gen_stub.sh:11-13).
DescribesThe submodule deepinfer._C.engine of the extension module deepinfer._C (csrc/pybind.cpp:12-13). Its sibling stubs are cuda_utils.pyi and graph_timer.pyi (deepinfer/_C/__init__.pyi:1-5).
Exported names34, listed in __all__ (deepinfer/_C/engine.pyi:8): 19 classes, 2 enums, 12 functions and 1 constant.
Runs inNothing runs: Python never imports a .pyi file. Editors and type checkers read it. The real module is the compiled .so in deepinfer/_so/<accelerator>-<arch>/ (deepinfer/__init__.py:28-32).
Bound inThree pybind11 files: pybind_sequence.cpp, pybind_scheduler.cpp, pybind_output.cpp (csrc/engine/pybind.cpp:5-9). The same engine sources build on NVIDIA and on Ascend (setup.py:22-34).
Not in this fileAny behaviour. Read the C++ sources for that; this page tells you where.

Where it sits#

The groups follow the job of each name, not the binding file. pybind_output.cpp binds three groups: outputs, input metadata and sampler inputs.

Who reads it#

  • Editors and type checkers. The Python imports carry # pyright: ignore[reportMissingModuleSource], because pyright finds the stub but not the compiled source (deepinfer/engine/llm_engine.py:19).
  • You. The stub is the shortest way to learn the C++ API: argument names, types and the docstrings, which are in Chinese. This page translates them.

What it describes: the Python importers#

  • deepinfer/engine/llm_engine.py: 11 names, for example Scheduler and build_request_outputs (deepinfer/engine/llm_engine.py:19-31).
  • deepinfer/sequence.py: the sequence types (deepinfer/sequence.py:14-20). deepinfer/entrypoints/llm.py: RequestOutput (deepinfer/entrypoints/llm.py:15).
  • model_metadata_utils.py: the input-metadata functions (deepinfer/model_executor/model_metadata_utils.py:6-11). sampling_inputs.py: the eight sampler-input classes (deepinfer/model_executor/sampling_inputs.py:18-27).
  • worker/base.py, worker/model_runner.py, worker/worker.py, worker/zos_status.py, prepare_tensor_input_zos.py and v4_modules/engram.py: one to three names each (deepinfer/worker/base.py:22, deepinfer/worker/model_runner.py:15, deepinfer/worker/worker.py:16-19, deepinfer/worker/zos_status.py:5, deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:7, deepinfer/model_executor/models/v4_modules/engram.py:18).

Walk through the main methods#

A stub has no method bodies. This part reads the stub lines that matter most, and the rules that the docstrings state.

The header and __all__#

Line 8 lists all exported names. The script that makes the stub then replaces typing.Sequence with Sequence in this file (scripts/gen_stub.sh:17-18). Note the name clash: Sequence is also the engine class at line 421. In argument types, collections.abc.Sequence means "a list or tuple".

Scheduler: the constructor and two docstrings#

  1. Line 310: the constructor takes 14 arguments. LLMEngine._create_scheduler passes them in this order (deepinfer/engine/llm_engine.py:307-327). scheduler_config is typing.Any: C++ reads its attributes by name, for example max_num_seqs (csrc/engine/scheduler.hpp:94-100).
  2. Line 316: fork_seq takes 9 arguments. In this release only examples/benchmark.py calls it (examples/benchmark.py:337-347).
  3. Lines 336-343: the two docstrings give the borrow rules. The deep dive "Borrowed memory" lists all of them.

Two names, one method

BlockManager.unpin_blocks (stub line 24) has no C++ method of that name. The binding maps it to BlockManager::free_blocks (csrc/engine/pybind_scheduler.cpp:68). To unpin and to free are the same operation.

SchedulerOutputs: views into scheduler memory#

The binding builds these NumPy arrays on the scheduler's own vector, with an empty capsule as owner (csrc/engine/pybind_scheduler.cpp:41-48). So the array is valid only until the next schedule() clears that vector (csrc/engine/scheduler.hpp:282-284).

RequestOutput: properties and raw-pointer readers#

Every field except max_num_batched_tokens has a property and a static get_<field>(ptr) that reads the field at an output handle without a copy (csrc/engine/pybind_output.cpp:12-14, csrc/engine/pybind_output.cpp:24). max_num_batched_tokens has only the property. clone(ptr) makes a Python-owned copy. The page csrc/engine/outputs.hpp: RequestOutput and its pool explains why a handle is valid for about one step.

Sequence and SequenceMetadata: what Python can change#

  • Lines 422-430: plain attributes, so Python can read and write them, for example status and so_matcher. They are properties in C++ that point into the nested state structs (csrc/engine/pybind_sequence.cpp:109-137).
  • prompt_token_ids must be an int32 C-contiguous NumPy array: the binding uses noconvert() (csrc/engine/pybind_sequence.cpp:103). A Python list or an int64 array raises TypeError. This is why LLM._add_request converts with np.asarray(..., dtype=np.int32) (deepinfer/entrypoints/llm.py:157).
  • SequenceMetadata is almost read-only. Only so_status has a setter (stub lines 582-587; csrc/engine/pybind_sequence.cpp:167).

The engine follows these rules. It copies the clone ids into DeferredRelease before the next schedule, and it releases metadata and outputs one step later (deepinfer/engine/llm_engine.py:889-905, deepinfer/engine/llm_engine.py:1013).

The opposite case: copies. A C++ std::vector field becomes a new Python list on every access. For example, Sequence.chunk_checkpoints or RequestOutput.top_logprobs. A change to that list does not change the C++ object. The module docstring of sampling_inputs.py states this rule (deepinfer/model_executor/sampling_inputs.py:7-9). To change a vector field, assign a new list, as LLMEngine.add_request does with seq.chunk_checkpoints = ... (deepinfer/engine/llm_engine.py:615-616).

Deep dive

Types in the stub, and where they are loose

  • typing.SupportsInt | typing.SupportsIndex is how pybind11-stubgen writes a C++ int argument. A Python int or a NumPy integer works.
  • typing.Any marks a C++ py::object: the C++ code reads attributes by name. Examples: scheduler_config, sampling_params, so_matcher (deepinfer/_C/engine.pyi:310, deepinfer/_C/engine.pyi:431). The stub cannot check these. For sampling_params, C++ reads nine attributes once (csrc/engine/sequence.hpp:103-115).
  • Return widths. get_finished_seqs_info returns tuple[int, int, int, int] in the stub; in C++ the last value is int64_t (csrc/engine/scheduler.hpp:1315). Python int has no width, so nothing is lost.
  • 13-tuple. prepare_decode_zos_inputs returns 13 values with no names (stub line 721). The only caller unpacks them by position (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:49-69).
  • Enums. SequenceStatus and YocoPrefillTruncationMode are pybind11 enums: they compare with ==, convert with int(), and have .name and .value (stub lines 593-653, 667-706).
Deep dive

How to make the stub again after a C++ change

  1. Build the extension for your platform: make build-nvidia or make build-ascend (Makefile:3-11).
  2. Run make stubgen. The script preloads the CUDA stub library libcuda.so from CUDA_HOME/lib64/stubs, if that file exists (scripts/gen_stub.sh:6-10).
  3. pybind11-stubgen imports deepinfer._C and writes deepinfer/_C/*.pyi (scripts/gen_stub.sh:11-13).
  4. The script replaces typing.Sequence with Sequence in engine.pyi (scripts/gen_stub.sh:17-18).

The stub can be older than the code

Nothing in the build checks that the stub matches the compiled module. If you change a binding and do not run make stubgen, the stub is wrong. We compared the names in the stub with the three binding files at commit 9bd9cf2 and found no difference.

Deep dive

Worked example: read a call from the stub

LLMEngine.step() calls self.scheduler.schedule(self.sequence_metadata_pool) (deepinfer/engine/llm_engine.py:885-887). The stub tells you:

  1. Line 340: schedule(self, sequence_metadata_pool: SequenceMetadataPool) -> tuple. The return type is a plain tuple; the docstring (translated above) says it holds (seq_metadata_list, scheduler_outputs).
  2. Lines 537-587: each SequenceMetadata has seqlen_q, seqlen_k, is_prompt and more.
  3. Lines 371-420: SchedulerOutputs has scheduled_seqs, prompt_run, num_batched_tokens and the three borrowed arrays.
  4. Then grep -n "\"schedule\"" csrc/engine/pybind_*.cpp finds the binding: &Scheduler::schedule (csrc/engine/pybind_scheduler.cpp:97-99), and the C++ body is at csrc/engine/scheduler.hpp:667-736.

Example values for a decode step with 4 sequences and nextn = 5:

  • 4 metadata objects with seqlen_q = 6 each, or less with variable draft lengths.
  • prompt_run = False and num_batched_tokens = 24 at most.
  • clone_blocks with shape [0, 2] when there is no fork (csrc/engine/pybind_scheduler.cpp:44-45).

Check yourself#

  1. 1
    Does Python import engine.pyi at run time?
    easy
    Show answer

    No. A .pyi file is only for editors and type checkers. At run time Python loads the compiled deepinfer._C from deepinfer/_so/<tag>/, which deepinfer/__init__.py adds to the package path (deepinfer/__init__.py:28-32).

  2. 2
    Which C++ file binds prepare_sampler_inputs, and which file implements it?
    easy
    Show answer

    pybind_output.cpp binds it (csrc/engine/pybind_output.cpp:133-135). prepare_sample.cpp implements it (csrc/engine/prepare_sample.cpp:40).

  3. 3
    You call Sequence(seq_id=0, prompt_token_ids=[1, 2, 3], ...) with a Python list. What happens, and why?
    medium
    Show answer

    A TypeError: the binding declares prompt_token_ids with noconvert() and type py::array_t<int32_t, c_style>, so pybind11 does not convert a list (csrc/engine/pybind_sequence.cpp:93, csrc/engine/pybind_sequence.cpp:103). Pass np.asarray(ids, dtype=np.int32).

  4. 4
    A script saves outs.clone_blocks in a list after each schedule() and reads the list after 10 steps. What does it read, and why?
    hard
    Show answer

    Wrong data. The array is a view on the scheduler's vector with an empty capsule as owner (csrc/engine/pybind_scheduler.cpp:41-48). Each schedule() clears and refills that vector (csrc/engine/scheduler.hpp:282-284), so all saved arrays show the storage of the latest step (or freed memory). Copy with np.array(outs.clone_blocks) instead. This is the deep dive "Borrowed memory".

It also defines the status enum, the finish reasons and the image token offsets.
  • engine/prepare_sample.cpp: the sampler inputsprepare_sampler_inputs reads the scheduled sequences once and builds the arrays that the sampler needs: which model-output rows to sample, per-sequence temperature, top-p, top-k and seed, and the draft-token bookkeeping of speculative decoding.
  • prepare_tensor_input_v4.cpp: the C++ input builderprepare_prompt_v4 and prepare_decode_v4 turn the scheduled SequenceMetadata list into a dict of pinned int32 tensors: positions, offsets, cache slot maps, load plans and window descriptions for the V4 attention layers.
  • csrc/engine/zos.cpp: the C++ helpers of zero-overhead schedulingzos.cpp has three functions for ZOS decode steps - match the batch with the previous step (remap), pack the decode inputs into pinned arrays, and refresh the CPU metadata before sampling. The device kernels do the rest.
