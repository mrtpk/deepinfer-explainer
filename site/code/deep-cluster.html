deep_cluster/: hardware discovery and NUMA binding

IntermediateCode mapabout 7 min read + 3 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Hardware discovery (deep_cluster) Intermediate

Purpose#

deep_cluster tells the rest of DeepInfer which accelerator and which devices the host has, and binds a process near its device, without any device runtime.

Files8 Python files, 656 lines: hardware/ (__init__.py 35, device.py 182, nvidia.py 129, ascend.py 155, cpu.py 47) and topology/ (__init__.py 9, bind.py 99). deep_cluster/__init__.py is empty.
Main functionaccelerator_kind() (deep_cluster/hardware/device.py:17-23). No classes, except a ctypes structure in bind.py.
Runs inAny process: setup.py, the example launchers, the engine and worker processes, the image worker, the kernel tests. CPU only.
Called bysetup.py, deepinfer/__init__.py, platform.py, utils.py, worker/base.py, worker/runtime_config.py, engine/llm_engine.py, ve/multimodal_processor.py, vit.py, examples and tests.
CallsThe file system (/proc, /sys, /dev), lscpu and npu-smi through subprocess, libnvidia-ml and libnuma through ctypes, psutil.
Not in this packageNo PyTorch, no CUDA, no CANN. No choice of the Platform object (that is platform.py). No process launch.

The package is installed together with deepinfer: find_packages(include=("deepinfer", "deepinfer.*", "deep_cluster", "deep_cluster.*")) (setup.py:87). The example scripts add the repository root to sys.path, so they can import it from a clean checkout (examples/_config.py:17-24).

Walk through the main methods#

device.py: the dispatcher#

The functions that depend on the hardware call accelerator_kind() first. physical_device_count and device_numa_node then call the function with the same name in ascend.py or nvidia.py. The visible_* functions read the variable whose name depends on the kind:

The CPU kind has no devices: the count is 0 and the variable name is None. Most functions take a keyword-only _root, so a test can point the paths at a fake tree (get_bf16_tflops_limit and is_sm_major_10 do not). The @functools.cache key includes _root.

nvidia.py: procfs first, device nodes second#

  1. Lines 14-15: _path joins the root and an absolute path, so _root=Path("/tmp/x") reads /tmp/x/proc/....
  2. Lines 18-25: one folder per GPU in /proc/driver/nvidia/gpus, sorted by name. An unreadable folder raises OSError with the path.
  3. Lines 28-37: numbers of the files /dev/nvidia<N>, sorted. The pattern ^nvidia(\d+)$ skips nvidiactl and nvidia-uvm (deep_cluster/hardware/nvidia.py:11).
  4. Lines 40-44: the procfs names win; the device nodes are the fall-back.

ascend.py: three signals and a device list#

discover_npu_devices returns one tuple per device: the ubcore entry name, a physical id, and the raw NUMA value (−1 if unknown). The physical id is the name of the folder that device resolves to, unless that name is "device" (line 80-81). The module also has IS_NPU, set at import time from /dev/davinci_manager only (deep_cluster/hardware/ascend.py:153), and its own get_actual_num_gpus, which raises on a host with no Ascend device (deep_cluster/hardware/ascend.py:147-150). The public get_actual_num_gpus is the one in device.py.

cpu.py: physical cores per NUMA node#

For each (node, socket, core), the function keeps the smallest logical CPU number. So a core with two hyper-threads counts once. Offline CPUs and CPUs with no node (−1) are skipped (line 39). Only the Ascend NUMA code uses this function.

topology/bind.py: from a device to a bound process#

  1. Line 49: the caller must give a device index or an InfiniBand index.
  2. Lines 51-61: for a device, map the visible index to the physical id, then to the physical index (trailing digits on Ascend), then to the NUMA node.
  3. Lines 62-63: any IndexError on the way becomes AssertionError("no such GPU found").
  4. Lines 65-71: for an InfiniBand index i, read /sys/class/infiniband/mlx5_<i>/device/numa_node. No caller in the repository uses this branch.

bind_numa then sets the CPU affinity and the memory policy with libnuma (deep_cluster/topology/bind.py:79-93), and set_cpu_affinity sets a CPU list with psutil (deep_cluster/topology/bind.py:96-99). The page Hardware discovery (deep_cluster) reads bind_numa line by line.

The cached values never change during the life of a process. A process that changes CUDA_VISIBLE_DEVICES still gets fresh answers from the visible_* functions, because those are not cached.

Deep dive

Worked example: one engine on a host with 8 GPUs

Run examples/offline_inference.py --ep 4 --cp 2 on one host with 8 SM100 GPUs, 2 NUMA nodes, 128 physical cores. Two engines start (DP 2).

  1. The launcher imports deep_cluster.hardware: accelerator_kind() = "nvidia", get_actual_num_gpus() = 8.
  2. setup_cuda_visible_devices(engine_rank=1, cp_size=2, device_count=8): local_engine_rank = 1 × 2 % 8 // 2 = 1, so CUDA_VISIBLE_DEVICES = "2,3" (examples/_config.py:55-61).
  3. The engine 1 process makes its driver worker with local_rank = 0: which_numa(0) → physical id "2" → physical index 2 → the NUMA node of GPU 2, say 0. bind_numa(0) binds to node 0.
  4. bind_cpu(gpu_id=2): 128 // 8 = 16 cores per GPU, so cores 32 to 47 (deepinfer/utils.py:143-151).
  5. The CP follower (local_rank = 1) does the same for GPU 3: cores 48 to 63.
  6. The engine computes tflops_limit = 2250 × 2 = 4500 on x86 (deepinfer/engine/llm_engine.py:304).

The NUMA node number in step 3 is an example. On a real host, it comes from /sys/bus/pci/devices/<bus id of GPU 2>/numa_node.

Deep dive

Ascend: what a visible id looks like

On Ascend, which_numa reads the visible id with re.search(r"(\d+)$", identifier), so "5" and "npu5" both give 5 (deep_cluster/topology/bind.py:56-58). An id that starts with "-" raises IndexError (lines 53-54), which becomes the AssertionError. A value of exactly "-1" gives an empty visible list, so physical_device_id raises first, with the same result (deep_cluster/hardware/device.py:64-65, deep_cluster/hardware/device.py:88-89). The example launcher copies CUDA_VISIBLE_DEVICES into ASCEND_RT_VISIBLE_DEVICES (examples/_config.py:62-63), so the two variables agree, as PlatformNPU requires.

Check yourself#

  1. 1
    Which files in /dev make accelerator_kind() return "nvidia" when /proc/driver/nvidia/gpus does not exist?
    easy
    Show answer

    Files named nvidia<N>, such as /dev/nvidia0. The pattern ^nvidia(\d+)$ does not match nvidiactl (deep_cluster/hardware/nvidia.py:11, deep_cluster/hardware/nvidia.py:28-44). And no Ascend signal must exist, because Ascend is tested first.

  2. 2
    Does get_actual_num_gpus() count the visible devices?
    easy
    Show answer

    No. It returns physical_device_count(), all devices of the host (deep_cluster/hardware/device.py:139-140). num_gpus() returns the visible count (deep_cluster/hardware/device.py:143-148).

  3. 3
    With CUDA_VISIBLE_DEVICES="-1" on an NVIDIA host with 8 GPUs, what do visible_device_ids() and visible_device_count() return?
    medium
    Show answer

    () and 0. The value "-1" means no visible device (deep_cluster/hardware/device.py:64-65), and the count is min(0, 8) = 0 (deep_cluster/hardware/device.py:74-78).

  4. 4
    Why does cpu.physical_core_cpus_by_numa keep only the smallest logical CPU of each (node, socket, core)?
    hard
    Show answer

    So that each physical core appears once, not once per hardware thread. The Ascend NUMA code compares an NPU's CPU affinity with these sets, and the node with the largest overlap wins (deep_cluster/hardware/cpu.py:13-15, deep_cluster/hardware/ascend.py:121-126). The docstring says the lists "contain only physical cores (one id per core, not per hardware thread)".
