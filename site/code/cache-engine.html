worker/cache_engine.py: CacheEngine and the cache layout

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Purpose#

CacheEngine allocates the two cache buffers of a rank and gives every attention layer a KVCache object with views into them. The page The KV cache explains the layout in simple terms; this page reads the code.

Filedeepinfer/worker/cache_engine.py, 978 lines of Python. "Derived from vLLM; modified by DeepSeek." (deepinfer/worker/cache_engine.py:2). Many comments are in Chinese.
Main classesCacheEngine (deepinfer/worker/cache_engine.py:851), GPUCacheInterface (deepinfer/worker/cache_engine.py:540), KVCacheManager (deepinfer/worker/cache_engine.py:309), StateBlock (deepinfer/worker/cache_engine.py:221) and the dataclass KVCache (deepinfer/worker/cache_engine.py:205-218).
Runs inEvery worker process, at start-up (twice: a temporary cache for the profile run, then the real cache).
Called byWorkerBase.init_cache_engine and profile_num_available_blocks; ModelRunner.profile_run.
Callscuda_utils.alloc_tensor (C++, cuMemAlloc), ModelMetadata, iter_runtime_attn_modules, and the state kernels select_state_slice and load_state_to_cache.
Not in this fileWhich block belongs to which sequence: the C++ BlockManager (csrc/engine/block_manager.hpp: BlockManager and the free list). The slot mappings: the input metadata code. The reads and writes of the cache: the attention kernels.

Where it sits#

Panel 1 reads left to right, then the second row. The agreed block count goes from the profile into cache_config, and the real CacheEngine reads it there. Panel 2 is the worked example of the deep dive "process() on a toy config".

Who calls it#

  • WorkerBase.init_cache_engine makes the real cache (deepinfer/worker/base.py:270-272). The engine calls it on every rank after the profile (deepinfer/engine/llm_engine.py:453).
  • WorkerBase.profile_num_available_blocks calls the static methods get_cache_block_size and get_state_shape (deepinfer/worker/base.py:237-242).
  • ModelRunner.profile_run makes a temporary CacheEngine with only the blocks of the dummy sequences (deepinfer/worker/model_runner.py:504-507).
  • The model reads one KVCache per layer: kv_caches[i] (deepinfer/model_executor/models/deepseek.py:212), for example kv_cache.ca_cache and kv_cache.swa_cache in the attention module (deepinfer/model_executor/models/v4_modules/attn.py:519-520, deepinfer/model_executor/models/v4_modules/attn.py:642-644).
  • The engine reads gpu_states and gpu_blocks for clones (deepinfer/worker/base.py:166-168) and the unused state copy (deepinfer/engine/llm_engine.py:797).

What it calls#

  • cuda_utils.alloc_tensor(size): "Allocate a 1D byte tensor by calling cuMemAlloc directly, bypassing torch's caching allocator" (csrc/cuda_utils.cpp:77-89, csrc/cuda_utils.cpp:99-102).
  • ModelMetadata(cfg) for the alignment and the FP4 flag (deepinfer/worker/cache_engine.py:320-332).
  • iter_runtime_attn_modules, which skips the LM-head entry of the attention list (deepinfer/model_executor/layer_utils.py:6-16).

Walk through the main methods#

allocate_gpu_cache: two buffers#

  1. Line 919: the row size of one block comes from a layout pass without memory.
  2. Lines 937-938: one gpu_blocks buffer, uint8 [num_gpu_blocks, bytes_per_block]. The comment on line 936 shows a 6-D shape from vLLM. It does not describe this layout.
  3. Lines 948-951: the state shape is (num_state_slots, bytes_per_slot). Three sizes go into the shared cache_config; the engine reads them to make the two block managers (deepinfer/engine/llm_engine.py:262-266).
  4. Lines 955-958: the gpu_states buffer. A model with no state gets an empty tensor.
  5. Lines 960-965: GPUCacheInterface runs the layout again, now with the buffers, and keeps the per-layer views.

Memory outside the PyTorch allocator

alloc_tensor calls cuMemAlloc and rounds the size up to a page (csrc/cuda_utils.cpp:77-82). So the cache does not appear in torch.cuda.memory_allocated(). On Ascend, asc_utils.cpp has its own alloc_tensor (csrc/asc_utils.cpp:88).

KVCacheManager.process: one layer#

  1. SWA. A layer with sink_mode == "swa" gets a ring of swa_block_size entries in the state row. A YOCO consumer layer puts its ring into the "dropped" part (deepinfer/worker/cache_engine.py:113-116). The view [slots, ring, 1, bytes_per_token] uses the full slot stride.
  2. Indexer keys. A sparse layer (index_topk > 0) gets block_size // ratio FP4 keys per block. A layer that reuses the keys of an earlier layer takes that view and adds no bytes.
  3. Main cache. A layer with ratio > 0 gets block_size // ratio entries per block. A ratio above 1 (for example 2) also gets fp32 compression state in the state row (deepinfer/worker/cache_engine.py:119-120).
  4. Each block-row part and each SWA ring is padded to 32 bytes; the fp32 compression state is not padded. A full-attention layer (ratio 0 and no SWA) raises AssertionError (deepinfer/worker/cache_engine.py:466-468).

finalize: the row size#

The row is padded to lcm(128, bytes_per_token): 1,152 bytes for FP4 entries and 4,224 bytes for MXFP8 entries. The comment gives the reasons: DeepGEMM needs a block stride that is a multiple of 128 bytes, and the main attention needs a multiple of the entry size.

StateBlock: one state slot#

PE and CE mean the prefill engine and the completion engine of a disaggregated deployment, which is not in this release. The offline engine uses only the inference sizes.

Deep dive

process() on a toy config: every offset

Toy config (example values, not from the repo): 3 layers, FP4 main entries (288 B), index_head_dim = 128, a window of 128, nextn = 5, max_num_seqs = 4.

LayerKindBlock row: offset, lengthState row: offset, length
L0SWA only (ratio 0)none (kv_length = 0, not in layout)SWA ring: 0, 70,752
L1ratio 1, sparse, SWAica_cache: 0, 128 × 68 = 8,704; ca_cache: 8,704, 128 × 288 = 36,864SWA ring: 70,752, 70,752 (ratio 1 has no state)
L2ratio 2, dense, SWAca_cache: 45,568, 64 × 288 = 18,432SWA ring: 141,504, 70,752; ca_state: 212,256, 28,672
  1. Backtracking. DEEPINFER_MAX_BACKTRACKING_TOKENS is at least nextn + 1 = 6 (deepinfer/environ.py:132). SWA ring: 128 + 6 = 134 entries (deepinfer/worker/cache_engine.py:88-93); 134 × 528 = 70,752 B, already a multiple of 32.
  2. Indexer key. 128 / 2 + 128 / 32 = 68 B (deepinfer/worker/cache_engine.py:76-78); 128 × 68 = 8,704, a multiple of 32.
  3. Compression state for ratio 2: ring 2 + max(0, 6 − 1) = 7 tokens (deepinfer/worker/cache_engine.py:131-133); fp32 [7, 2, 512] = 7 × 2 × 512 × 4 = 28,672 B (deepinfer/worker/cache_engine.py:41-43). The view is [slots, 7, 2, 512] float32 (deepinfer/worker/cache_engine.py:367-374).
  4. Block row. The offset ends at 64,000. lcm(128, 288) = 1,152; ceil(64,000 / 1,152) × 1,152 = 56 × 1,152 = 64,512 B per block.
  5. State row. The offset ends at 240,928. With SWA, the slot is aligned to lcm(32, 528) = 528: 457 × 528 = 241,296 B (deepinfer/worker/cache_engine.py:301-305).
  6. Slots. int(4 × 1.2) + 1 = 5 (deepinfer/worker/cache_engine.py:201-202), so gpu_states is uint8 [5, 241,296]. Slot 0 is never handed out (csrc/engine/block_manager.hpp:27-35).

Views share one row. ca_cache of L1 is gpu_blocks[:, 8704:45568] seen as [num_blocks, 128, 1, 288] with stride (64,512, 288, 288, 1) (deepinfer/worker/cache_engine.py:455-458). So block id b means row b for every layer.

Deep dive

The profile run and the temporary cache

  1. The dummy sequences use blocks 0, 1, 2, ... in order, so num_blocks is the sum of their block counts (deepinfer/worker/model_runner.py:476-495).
  2. The constructor argument num_gpu_blocks overrides cache_config.num_gpu_blocks, which is still None at this time (deepinfer/worker/cache_engine.py:869, deepinfer/worker/cache_engine.py:882, deepinfer/config.py:137).
  3. The profile sets DEEPINFER_FORCE_IMBALANCE_RATIO = 1.8 for the run and sets it back to 0 after (deepinfer/worker/model_runner.py:510-512). The comment says only "MoE simulated imbalance enabled"; this site infers that the aim is a high MoE memory peak.
  4. After the run, profile_num_available_blocks subtracts 2 × prod(state_shape) bytes and divides by get_cache_block_size (deepinfer/worker/base.py:237-245). With the toy config: 2 × 5 × 241,296 = 2,412,960 B for state, then free // 64,512 blocks.
Deep dive

Clones and the state copy: who else touches the buffers

clone_and_zero_states_and_blocks copies whole rows on the current stream with cudaMemcpyAsync (csrc/engine/scheduler.hpp:1273-1301). One state copy is states[0].nbytes(), one block copy is blocks[0].nbytes(): a full row each. A block pair with dst = 0 is not copied; only its source is returned for release (csrc/engine/scheduler.hpp:1296-1299). zero_states clears whole state rows (csrc/engine/scheduler.hpp:1303-1309).

The engine's do_copy_state copies one state row into copy_state for KV saving (deepinfer/engine/llm_engine.py:787-798). copy_state is None in this release, so this does nothing.

Check yourself#

  1. 1
    How many device buffers does CacheEngine allocate for the cache, and what are their shapes?
    easy
    Show answer

    Two: gpu_blocks, uint8 [num_gpu_blocks, bytes_per_block], and gpu_states, uint8 [num_state_slots, bytes_per_slot] (deepinfer/worker/cache_engine.py:937-938, deepinfer/worker/cache_engine.py:948-958). Every layer gets views into them.

  2. 2
    Does the SWA cache of a layer use KV blocks? Where is it?
    medium
    Show answer

    No. It is a ring in the state slot of the sequence, cut from the state row (deepinfer/worker/cache_engine.py:406-422). A layer with only SWA has kv_length = 0 and is not in the block layout (deepinfer/worker/cache_engine.py:640-642).

  3. 3
    Why does the profile run zero its temporary cache?
    medium
    Show answer

    The comment says that the full gather of chunked prefill reads cache areas that nothing wrote, and the values must be finite (deepinfer/worker/model_runner.py:498-507).

  4. 4
    In the toy config, a layer has ratio 2 and is dense. How many bytes does it take in one block row and in one state slot, without SWA?
    hard
    Show answer

    Block row: 128 // 2 = 64 entries of 288 B = 18,432 B (deepinfer/worker/cache_engine.py:452-453). State: a ring of 2 + 6 − 1 = 7 tokens of fp32 [2, 512] = 28,672 B (deepinfer/worker/cache_engine.py:131-133, deepinfer/worker/cache_engine.py:41-43). See the deep dive "process() on a toy config".

Related pages

  • The KV cacheThe KV cache keeps the keys and values of earlier tokens, so each new token needs only its own keys and values. DeepInfer stores the cache in blocks of 128 tokens.
  • Paged KV cache and block managerThe engine side of the paged KV cache. Two C++ BlockManager objects hand out KV blocks and state slots, the scheduler decides when, and C++ code turns block tables into index tensors for the kernels.
  • worker/base.py: WorkerBase, the resource layer of a workerWorkerBase sets up one device for one rank - torch settings, NUMA and CPU binding, process groups, the model, the memory profile, the KV cache and the CUDA graphs - and runs the call loop of the context-parallel followers.
  • csrc/engine/block_manager.hpp: BlockManager and the free listblock_manager.hpp holds the C++ free list of KV blocks with reference counts, the BlockManager class with its mutex, and the helper that allocates blocks and a state slot for one sequence.
  • Sliding-window attentionEvery attention layer of DeepSeek-V4.1-Flash reads the most recent tokens (a window of 128 in the docs) from a ring of 134 slots per sequence and layer. This page shows the ring, the decode and prefill index paths, and how the window joins the compressed keys.
  • KV compression (C1 and C2)A compressed layer stores one 512-value cache entry per token (C1) or per 2 tokens (C2). C2 mixes the two tokens with a learned softmax gate and keeps the score and latent of the most recent tokens in a small fp32 state ring. Entries are FP4 (288 B) by default, or FP8 (528 B).
  • Cross-layer KV sharingA layer can reuse the compressed KV, the indexer keys or the top-k list of an earlier source layer. SharedLayerTopology turns three lists of source layers from config.json into checked segment maps; the cache engine then allocates the compressed-KV and index-K caches only for source layers.
  • Sparse attention with an indexerIn a sparse layer, a small indexer scores all compressed keys for each query and keeps the best index_topk. The main attention then reads only those keys plus the sliding window.
