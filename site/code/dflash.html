models/mtp/dflash.py: the DFlash draft model

AdvancedCode mapabout 8 min read + 3 min deep dives

Purpose#

DFlash proposes the draft tokens of the next decode step, with their logprobs and their predicted accept chances, from the hidden states of the main model.

Filedeepinfer/model_executor/models/mtp/dflash.py, 392 lines. The folder mtp/ has only this file and an empty __init__.py.
Main classDFlash(nn.Module) (deepinfer/model_executor/models/mtp/dflash.py:82). Also ConfidenceHead (deepinfer/model_executor/models/mtp/dflash.py:46) and _clone_linear_weight (deepinfer/model_executor/models/mtp/dflash.py:38).
Runs inEvery rank that runs the model. Only the driver rank samples drafts and owns the MTP info pool (deepinfer/worker/model_runner.py:97-99).
Called byDeepseekModel.forward (update_main_cache, every step) and Sampler.forward (decode_forward, decode steps).
CallsDFlashDecoderLayer (attention and MLP/MoE), process_sampling and get_logits from the sampler helpers, confidence_head_fused, MTPInfoPool.store, build_dflash_input.
Not in this fileThe accept test (sampler), the confidence scheduling (C++ MTPVarlen), the CUDA graph capture (DFlashCudaGraphRunner), the attention kernel (FlashMLA).

Where it sits#

Who calls it#

  • DeepseekForCausalLM.__init__ makes it when DEEPINFER_USE_NEXTN_DECODE > 0, with the main model's embedding and LM head (deepinfer/model_executor/models/deepseek.py:300-306).
  • DeepseekModel.forward calls update_main_cache after the last main layer, in prefill and in decode (deepinfer/model_executor/models/deepseek.py:220-223).
  • Sampler.forward calls decode_forward in decode steps: on the driver after the verification, on followers with no driver input (deepinfer/model_executor/layers/sampler.py:155-160, deepinfer/model_executor/layers/sampler.py:236-251).
  • ModelRunner makes the pool on the driver of non-PROMPT engines and captures the DFlash CUDA graphs after the main graphs (deepinfer/worker/model_runner.py:97-99, deepinfer/worker/model_runner.py:532-550).

What it calls#

  • DFlashDecoderLayer.update_main_cache and forward_drafts (deepinfer/model_executor/models/decoder_layer.py:208-239), which use DFlashAttention (deepinfer/model_executor/models/v4_modules/attn.py:928-1008).
  • InputMetadataV4.build_dflash_input for the fixed-stride metadata of the draft block (deepinfer/model_executor/input_metadata/dflash.py:36-84).
  • get_logits and process_sampling (deepinfer/model_executor/models/mtp/dflash.py:14), confidence_head_fused (deepinfer/model_executor/models/mtp/dflash.py:15).
  • MTPInfoPool.store (deepinfer/model_executor/layers/mtp_info_pool.py:54-78).

Walk through the main methods#

__init__, part 1: layers and the main-key projection#

  1. Lines 112-114: a PROMPT engine (prefill only) needs only the main-key path. It skips the MLP, the layer norms of the DFlash layers and the heads (deepinfer/model_executor/models/decoder_layer.py:197-200, deepinfer/model_executor/models/mtp/dflash.py:162).
  2. Lines 117-123: main_kv_proj joins the KV-A weights of all DFlash layers into one linear layer with L × head_dim outputs. One matrix multiply then makes the keys of all layers.
  3. Lines 126-136: one DFlashDecoderLayer per checkpoint block. Their layer ids follow the main layers, so the KV cache has an entry for each of them.
  4. Lines 139-141: the noise token id and the window come from the checkpoint config. The block size is the number of drafts, not a config value.
  5. Lines 146-152: projection maps H × T concatenated features to H.

__init__, part 2: the heads#

  1. Lines 155-156: the Markov term exists only if dspark_markov_rank > 0.
  2. Line 159: enable_confidence is always True.
  3. Lines 165-176: markov_w1 is an embedding table [V, rank]; markov_w2 is a linear layer rank → V with float32 output.
  4. Lines 180-186: the confidence head weight is cast to BF16.

update_main_cache: keys from the target layers#

  1. Lines 213-217: without prefill context parallelism, there is one feature row per query token. With it, the rows are in the mirror layout of the rank, and the positions come from positions_cp.
  2. Line 219: [rows, H × T] → [rows, H], then RMSNorm.
  3. Line 220: [rows, H] → [rows, L, head_dim].
  4. Lines 221-228: each layer normalizes, applies RoPE, casts to FP8 (e4m3 with ue8m0 scales) and writes its key into its SWA cache (deepinfer/model_executor/models/v4_modules/attn.py:928-961).

Rejected drafts need no mask here

In decode, this method replays inside the main CUDA graph. The verification has not run yet, so it also writes keys for drafts that the sampler will reject. The docstring explains why this is safe: the next draft block writes its keys at exactly those positions, before any read (deepinfer/model_executor/models/mtp/dflash.py:204-209).

forward_drafts: one pass over the draft block#

  1. Lines 232-239: an int tensor [R, 5], all noise ids, then column 0 = the golden token. It is flattened to [R × 5] and embedded.
  2. Lines 250-256: every DFlash layer runs on the block. Each layer writes the 5 draft keys into its cache, then attends to the main-key window (128 tokens in the docs) plus the 5 draft keys (deepinfer/model_executor/models/v4_modules/attn.py:963-1008).
  3. Lines 258-267: with hyper-connections, the residual streams are mixed back into one hidden state; else the residual is added.

sample_drafts: 5 drafts, one step at a time#

  1. Lines 288-289: final norm, then logits for all R × 5 rows at once: float32 [R × 5, V].
  2. Lines 290-294: the sample positions of the drafts: sample_position + last_valid_offset + (1 … 5), int32 [5, R].
  3. Lines 298-306: output buffers. The logprobs have width V, or force_topk with force top-k.

The loop over the 5 steps (lines 308-334) is explained on DSpark: DFlash drafts and confidence-scheduled verification, Step 4. After the loop:

The pool store skips requests whose write slot is 0, so the placeholder slot keeps its padding (deepinfer/model_executor/layers/mtp_info_pool.py:61-66).

run_drafts and decode_forward#

  1. Lines 353-357: the docstring. With the DFlash CUDA graph, the broadcast, the metadata, the layers and the sampling (with the pool write) are all one graph.
  2. Line 362: a rank without driver input must be a context-parallel follower, else an assertion fails.
  3. Line 365: cp_broadcast_multi_tensor sends last_valid_offset and golden_tokens from the driver.
  4. Lines 374-376: followers stop after the layers and return None.
  5. Lines 385-387: if a graph runner exists, replay; else run eagerly.

Deep dive

The MTP info pool

The pool is device memory that keeps the draft data from one step to the next (deepinfer/model_executor/layers/mtp_info_pool.py:14-52):

  • token_ids int32 [pool_rows], logprobs float32 [pool_rows, N or V], confidence float32 [pool_rows] (initialized to 1), and logprobs_index int32 [pool_rows, N] with force top-k.
  • pool_rows = (max_num_seqs + 1) × nextn. The scheduler gives each running sequence one slot (csrc/engine/scheduler.hpp:792-800).
  • Slot 0: token V − 1 with logprob 0 (probability 1). With force top-k, column 0 holds id V − 1.

Worked example. max_num_seqs = 64, nextn = 5, force top-k 4096: 325 rows. Token ids 1.3 KB, logprobs 5.3 MB, index 5.3 MB, confidence 1.3 KB. Without force top-k and with the inferred V = 129280, the logprobs need 168 MB.

Who reads which slot. A sequence reads its own slot only if it has unread draft info; else it reads slot 0 (csrc/engine/sequence.hpp:149-153). It always writes its own slot (csrc/engine/sequence.hpp:409-413). The verification of step N reads what DFlash wrote in step N−1, and DFlash then writes the slot again in step N. A docstring note says that both run on the same stream, so the stream keeps this order (deepinfer/model_executor/layers/sampler.py:85).

Deep dive

CUDA graph of the DFlash pass

DFlashCudaGraphRunner captures one graph per batch size. The sizes come from build_graph_batch_sizes(max_num_seqs, DEEPINFER_DFLASH_CUDAGRAPH_BATCH_SIZE_INTERVAL), with the default step 8 (deepinfer/worker/dflash_cuda_graph_runner.py:32-40).

  • Capture. Largest size first, with a warm-up run, on the graph stream and memory pool of the main graphs. The inputs are padding buffers with the noise token as golden token (deepinfer/worker/dflash_cuda_graph_runner.py:42-75). The main graphs must exist first (deepinfer/worker/model_runner.py:539).
  • Replay. Pick the smallest captured size that fits, copy the real inputs into the graph buffers, replay, and cut the output to the real request count (deepinfer/worker/dflash_cuda_graph_runner.py:77-91).
  • Too many requests. A batch larger than the largest size raises ValueError("No DFlash CUDA graph for ...") (deepinfer/worker/dflash_cuda_graph_runner.py:79-80).
  • Off switch. DEEPINFER_DFLASH_ENFORCE_EAGER=1, or no CUDA graphs at all (deepinfer/worker/model_runner.py:80-85).

Check yourself#

  1. 1
    Which two methods of DFlash run in every decode step, and who calls them?
    easy
    Show answer

    update_main_cache, called by DeepseekModel.forward (deepinfer/model_executor/models/deepseek.py:220-223), and decode_forward, called by Sampler.forward (deepinfer/model_executor/layers/sampler.py:236-251).

  2. 2
    Why does DFlash keep a second copy of the KV-A weights of its layers?
    medium
    Show answer

    The main-key projection joins the weights of all layers into one matrix, and needs another contiguous layout than the draft projection. The comment says that the KV weights are kept twice and memory grows a little (deepinfer/model_executor/models/mtp/dflash.py:117-123).

  3. 3
    A request accepted 2 drafts at input positions 49 to 54. At which positions does DFlash place its draft block, and what is the input token at the first position?
    medium
    Show answer

    Positions 52 to 56 (a = 49 + 2 = 51, block a + 1 … a + 5) (deepinfer/model_executor/layers/tilelang_ops/get_kv_index.py:168-174). The first input is the golden token, the token that the sampler just made; the others are the noise token (deepinfer/model_executor/models/mtp/dflash.py:230-239).

  4. 4
    With max_num_seqs = 64 and no force top-k, how much memory do the draft logprobs of the pool use, and why so much?
    hard
    Show answer

    325 rows × 129280 × 4 bytes ≈ 168 MB (vocabulary size inferred). The pool keeps a full row of logprobs for every draft of every slot, because the verification needs p for every token to build the residual (deepinfer/model_executor/layers/mtp_info_pool.py:20-37). This is in the deep dive "The MTP info pool".

Related pages

  • DSpark: DFlash drafts and confidence-scheduled verificationDSpark makes 5 drafts per request with the DFlash draft model and predicts how likely each draft is to pass. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
  • layers/sampler.py: the Sampler classsampler.py holds the Sampler module. It turns selected hidden states into float32 logits, samples prefill tokens, verifies draft tokens in decode steps and calls DFlash. sampler_utils.py holds the logits, sampling and prompt-logprob helpers.
  • models/deepseek.py: the DeepSeek-V4.1 modeldeepseek.py holds DeepseekModel (embedding, N decoder layers, final mix and norm) and DeepseekForCausalLM (lm head, sampler, DFlash, EPLB, weight loading). The forward returns hidden states.
  • models/decoder_layer.py: one decoder layerdecoder_layer.py holds DeepseekDecoderLayer (one main-model layer: mHC, attention, mHC, MoE, plus the Engram, YOCO and DFlash hooks) and DFlashDecoderLayer (one draft-model layer).
  • v4_modules/attn.py: the MLA attention runtimeattn.py turns the MLA weight container into runtime weights and runs one attention layer per call: projections, sliding-window and compressed KV stores, the indexer, the FlashMLA kernel and the output projection. It also holds the DFlash draft attention.
  • Sliding-window attentionEvery attention layer of DeepSeek-V4.1-Flash reads the most recent tokens (a window of 128 in the docs) from a ring of 134 slots per sequence and layer. This page shows the ring, the decode and prefill index paths, and how the window joins the compressed keys.
  • CUDA graphsAt start-up DeepInfer records the decode forward pass once for each of a list of batch sizes. Each decode step then pads its rows to the next recorded size and replays the recording with one call.
  • Tour: One speculative decoding roundFollow request "1" through one decode step with 5 drafts, in 12 stops: verification length, inputs, forward pass, sampler inputs, accept test, residual, DFlash drafts, confidences, results, cache rollback, and the length of the next check.
