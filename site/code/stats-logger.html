engine/stats_logger.py: step statistics, MFU and moe_lb

IntermediateCode mapabout 8 min read + 5 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

Purpose#

StatsLogger turns per-step numbers into a periodic log line, so that you can see the speed and the health of a running engine.

Filedeepinfer/engine/stats_logger.py, 477 lines. Also on this page: deepinfer/timer.py (295 lines) and deepinfer/engine/profile_server.py (320 lines).
Main classStatsLogger (deepinfer/engine/stats_logger.py:129), with the records StepStats (deepinfer/engine/stats_logger.py:33), Aggregates (deepinfer/engine/stats_logger.py:53) and Window (deepinfer/engine/stats_logger.py:92).
Runs inThe engine process. log_step runs in the main thread; a daemon thread writes the lines.
Called byLLMEngine: it makes the logger at the end of start-up (deepinfer/engine/llm_engine.py:298-305) and calls log_step from post_process (deepinfer/engine/llm_engine.py:1004-1008).
CallsThe C++ scheduler for counts, the timers of timer.py, and NCCLMemoryStatsLogger.
Not in this fileThe FLOP counts (C++ FlopsEstimator) and the expert token counts (EPLB). The logger only sums what it gets.

Where it sits#

Read panel 1 from left to right. Blue work happens in every step, green work only in a logging step, and the amber thread does the slow logging call. Panel 2 shows three formulas from the code with small invented numbers.

Who calls it#

  • LLMEngine.__init__ passes itself, three configs and the device peak: tflops_limit = get_bf16_tflops_limit() × 2, an FP8-equivalent peak (deepinfer/engine/llm_engine.py:298-305).
  • _process_model_outputs makes a StepStats record and returns a function that calls log_step, only when statistics are on (deepinfer/engine/llm_engine.py:763-785). post_process calls it and only logs an error if it fails (deepinfer/engine/llm_engine.py:1004-1008).
  • step() calls log_nccl_memory() in every step with statistics on (deepinfer/engine/llm_engine.py:954-955).
  • close() stops the log thread (deepinfer/engine/llm_engine.py:355-356).

Statistics are on when disable_log_stats is false. LLM turns them off by default; the example scripts turn them on (deepinfer/entrypoints/llm.py:67, examples/_config.py:122).

What it calls#

  • Scheduler counters: free blocks, running and chunked prompt counts, preempted and aborted counts (deepinfer/engine/stats_logger.py:410-423).
  • cpu_timer and the two device timers, through get_timers() (deepinfer/timer.py:293-295).
  • A daemon thread stats_log_worker with a queue.SimpleQueue (deepinfer/engine/stats_logger.py:185-187).

Walk through the main methods#

log_step: once per step#

  1. Line 449: _record appends the step to the windows. A prefill step goes into the prompt window; a decode step into three windows for generated tokens, verified tokens and confidence errors. Every step goes into the FLOP window, and into the moe_lb window when it has a value (deepinfer/engine/stats_logger.py:359-377).
  2. Line 452: a log line is due at step 0 and then every DEEPINFER_LOGGING_INTERVAL_STEP steps. A PROMPT engine logs five times as often (deepinfer/engine/stats_logger.py:381-390).
  3. Lines 453-458: on a logging step, each window keeps only the entries that are at most interval steps old (so interval + 1 steps). The moe_lb window keeps at least DEEPINFER_MOE_LB_STAT_INTERVAL steps (default 128), because a new value comes only that often.
  4. Line 459: _collect computes the values. Cheap values are computed in every step; the expensive ones only on a logging step.
  5. Lines 462-467: the message goes to the queue, not to the logger. The main thread never waits for log I/O (deepinfer/engine/stats_logger.py:342-344).
  6. Lines 470-474: on a logging step, all timers are cleared, so each line shows the time since the last line.

With the interval at 0, the windows stay empty

DEEPINFER_LOGGING_INTERVAL_STEP=0 turns the line off. The condition on line 453 is then true in every step, so every window except the moe_lb window is trimmed to age 0 in every step (line 456). The benchmark script uses this to turn the log off in parts of its run (examples/README.md:49).

Throughput and MFU#

MFU divides by model_parallel_size, which is the CP size (deepinfer/config.py:171). The code does not say why. The peak tflops_limit is two times the BF16 peak of deep_cluster: 2 × 2250 on x86_64 SM100, 2 × 2500 on ARM, 2 × 432 on Ascend (deep_cluster/hardware/device.py:151-156).

Draft accept rates#

The sampler reports two lists per decode step: num_generated_tokens and num_verified_tokens. Item 0 is the request count; item i is the count for draft position i (deepinfer/sequence.py:242-246, deepinfer/model_executor/layers/sampler.py:294-295). So nextn_rates[i-1] is the accept rate of draft i among the drafts that were verified. avg_verified_len is the mean number of drafts sent per request; it is lower than 5 only with DSpark.

moe_lb: sum of maxima over sum of means#

Each payload is (mean, max). The EPLB code makes it every DEEPINFER_MOE_LB_STAT_INTERVAL steps: it gathers the token counts of every EP rank, takes the mean and the maximum over ranks for each step and MoE layer, and sums each over all steps and layers (deepinfer/model_executor/eplb/__init__.py:180-193). The logger then divides the sum of maxima by the sum of means. 1.0 is perfect balance.

Not the same as the doc's wording

The deployment Q&A calls moe_lb "slowest rank / mean" (doc/inference_deployment_qa.md:99). The code takes the maximum per step and layer first, then sums. So the busiest rank can change from layer to layer, and the result is never smaller than the ratio of the total of the busiest rank to the mean. The page Expert load balancing (EPLB) explains the counting.

_build_log_messages makes one [stats] line and up to two timer lines, [cpu] and [cuda] (deepinfer/engine/stats_logger.py:272-340). A shortened example from a decode step (invented values):

Deep dive

Worked example: one window, all formulas

Invented numbers: one DP rank, --cp 1, x86_64 SM100 (tflops_limit = 4500), interval 10. Steps 110 to 120 are decode steps, 10 ms apart, each with 4 sequences and 24 query tokens.

  1. completion_TPS. The generated-token window has 11 entries. Each counts sum(gen_tokens): for example 4 + 3 + 3 + 2 + 2 + 1 = 15 tokens (4 sampled tokens and 11 accepted drafts). The first entry only marks the start. 10 × 15 / 0.1 s = 1500 tokens per second.
  2. MFU. Each step reports 0.9 TFLOP. (11 × 0.9 − 0.9) / 0.1 s / 1 / 4500 = 0.02.
  3. Accept rate of draft 1. 4 drafts verified per step at position 1, and 3 accepted. All 11 entries count here: 33 / 44 = 75 %.
  4. avg_verified_len. sum(verified[1:]) / sum(num_seqs) = 11 × 20 / 44 = 5.0 with fixed 5 drafts.
  5. KV_cache_usage. (num_gpu_blocks − 1 − free) / (num_gpu_blocks − 1); block 0 is not counted (deepinfer/engine/stats_logger.py:410-411).
  6. cur_SPS. With ZOS, 1 / last_step_interval, the time between two step() calls (deepinfer/engine/stats_logger.py:405-406): 1 / 0.010 = 100.
Deep dive

Threads, timing and a small sleep

The log thread sleeps (rank % 8) × 5 ms before it writes, but only when no backlog waits in the queue (deepinfer/engine/stats_logger.py:116-126). So the 8 ranks of one host do not all write at the same moment. close() puts None on the queue and joins the thread, so queued lines are written before the engine stops (deepinfer/engine/stats_logger.py:346-349).

The CPU split prefill/decode comes from two extra timer names. _record adds the time since the last step to engine_step:prefill or engine_step:decode, but not for empty steps (deepinfer/engine/stats_logger.py:362-372).

Deep dive

profile_server.py: torch.profiler traces over HTTP

With DEEPINFER_PROFILE_HTTP_ENABLE=1, the engine starts a small HTTP server in a daemon thread (deepinfer/engine/llm_engine.py:235-239). It listens on port DEEPINFER_PROFILE_HTTP_PORT_BASE + driver_gpu_id, default 6070 + gpu (deepinfer/engine/profile_server.py:117).

  1. A client sends POST /profile (or GET) with num_steps (1 to 50, default 20) and an optional output_dir (deepinfer/engine/profile_server.py:167-205).
  2. The engine thread picks the request up at the start of the next step() and starts torch.profiler (deepinfer/engine/profile_server.py:256-295, deepinfer/engine/llm_engine.py:878-879).
  3. After num_steps steps it stops the profiler. A worker thread writes the profiler trace to profile-<ip>-gpu<id>-rank<rank>-<time>.json (deepinfer/engine/profile_server.py:311-320, deepinfer/engine/profile_server.py:224-226).
  4. The HTTP reply holds the file path. A second request during a run gets 409; a request that the engine does not pick up in 30 s gets 503 (deepinfer/engine/profile_server.py:216-252, deepinfer/engine/profile_server.py:277-278).

Only the driver device is traced, because the profiler works in one process; CP followers are not in the trace (Translated, deepinfer/engine/profile_server.py:7-8). A comment gives a measured size of about 4.9 MB per step (Translated, deepinfer/engine/profile_server.py:45). Missing fastapi or uvicorn, or a busy port, only turns the endpoint off with an error log (deepinfer/engine/profile_server.py:140-152).

DEEPINFER_PROFILE_HTTP_ENABLE=1 python3 examples/offline_inference.py
curl -XPOST "http://<host-ip>:6073/profile?num_steps=5"    # device 3

Check yourself#

  1. 1
    You use LLM(...) and see no [stats] lines. Why?
    easy
    Show answer

    LLM.__init__ sets disable_log_stats=True unless you pass it (deepinfer/entrypoints/llm.py:67). Then _process_model_outputs returns an empty function (deepinfer/engine/llm_engine.py:782-783). Pass disable_log_stats=False, as create_llm does (examples/_config.py:122).

  2. 2
    Two windows give moe_lb payloads (mean, max) = (100, 120) and (100, 150). What does the log show? What would "slowest rank / mean" of each payload give?
    medium
    Show answer

    The code: (120 + 150) / (100 + 100) = 1.35 (deepinfer/engine/stats_logger.py:238-241). Per payload: 1.2 and 1.5, with a mean of 1.35 here only because both means are equal. With different means, the two methods give different numbers; the code weights each payload by its mean.

  3. 3
    A decode run stops getting new steps. Why does completion_TPS go down, but MFU stays the same, in the next log line?
    medium
    Show answer

    _throughput divides by now − t_first, so empty time after the last sample counts. _mfu divides by t_last − t_first (deepinfer/engine/stats_logger.py:199-209). The translated comments state this difference.

  4. 4
    On x86_64 SM100 with --cp 2, the FLOP window has 11 entries of 18 TFLOP each, 0.1 s from first to last. What MFU does the logger print?
    hard
    Show answer

    (11 × 18 − 18) / 0.1 = 1800 TFLOP/s. Divide by model_parallel_size = 2 and by tflops_limit = 2 × 2250 = 4500: 1800 / 2 / 4500 = 0.2 (deepinfer/engine/stats_logger.py:208-209, deepinfer/engine/llm_engine.py:304, deep_cluster/hardware/device.py:155).

In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
