deepinfer/ve/: the multimodal worker, the image processor and the schema

Purpose#

deepinfer/ve/ does all image work on the CPU: it plans how many tokens each image takes, prepares the pixels in a separate process, and gives each prefill chunk the image data that it needs.

Filesmultimodal_processor.py (326 lines), prepare_tensor_input_vl.py (163), schema.py (77), processor/image_processor.py (318), processor/common.py (52), processor/mm_processor.py (30), processor/text_processor.py (13). __init__.py files are empty.
Main classMultimodalProcessor (deepinfer/ve/multimodal_processor.py:29). Also ImageProcessorAnyRes (deepinfer/ve/processor/image_processor.py:245), MMProcessor (deepinfer/ve/processor/mm_processor.py:10), prepare_input_metadata_vl (deepinfer/ve/prepare_tensor_input_vl.py:78).
Runs inThe rank process (placeholder expansion, fetch, chunk slicing) and one forked worker process per engine (decode, resize, layout).
Called byLLMEngine (overwrite_prompt, add, fetch, abort, stop), ModelMetadata.prepare_inputmetadata_dict (chunk slicing), DeepseekVLForCausalLM (processors).
CallsPIL, torch.multiprocessing queues, SharedTorchMemoryPool, the C++ Scheduler.set_schedulable, deep_cluster.topology for NUMA and CPU binding.
Not in this fileAny device work: the ViT, the patch padding and the merge are in vision_encoder/ and image_embed_ops.py.

Where it sits#

  • LLMEngine.__init__ makes the processor when the model class has multi_modal_mapper and the engine is not COMPLETION, and gives it the scheduler (deepinfer/engine/llm_engine.py:209-221, deepinfer/engine/llm_engine.py:269-270).
  • add_request calls overwrite_prompt (deepinfer/engine/llm_engine.py:547-551); _enqueue calls add (deepinfer/engine/llm_engine.py:624-625).
  • step calls fetch and fetch_to_abort_requests after schedule() (deepinfer/engine/llm_engine.py:939-945). After a prefill, _process_model_outputs calls abort to drop the processor's reference to the dict (deepinfer/engine/llm_engine.py:734-735).
  • prepare_inputmetadata_dict calls prepare_input_metadata_vl for prefill batches (deepinfer/model_executor/model_metadata_utils.py:182-187).
  • DeferredRelease calls free_deferred_pool_handles in pre_sampler_sync (deepinfer/engine/llm_engine.py:118-119).

Walk through the main methods#

overwrite_prompt#

  1. Lines 118-124: extra placeholders stay as text, with an error log.
  2. Line 145: the token count comes from the declared size, without a decode.
  3. Lines 146-148: the first token is vocab_size + 2, the others vocab_size + 1. The span (start, count) goes into image_spans.
  4. Lines 158-162: the dict gets segment_input and loses image_sizes and image_bytes (the bytes now live in the segments). The function always returns a new array.

_processor: the worker loop#

Before the loop, the worker binds to the NUMA node of the engine's first visible device. With 2-way SMT, it uses the sibling hyperthreads of that device's cores, to stay off the main process's cores. It uses 2 torch threads. A binding failure only logs a warning. On NPU, it first resets SIGTERM to the default, because torch_npu's fork path ignores the signal (deepinfer/ve/multimodal_processor.py:165-171). The loop itself is in Vision encoder (VL) (step 3).

fetch#

  1. Lines 287-289: any result, also a failure, proves that the worker is alive and resets the hang clock.
  2. Lines 290-292: a failure goes to to_abort_ids; the engine aborts it in the same step.
  3. Lines 293-295: a result for an aborted request frees its pool blocks.
  4. Lines 296-299: with the pool, each handle becomes a tensor view of the shared pool. The "handle" key stays in the dict and marks pool ownership.
  5. Lines 301-303: the original dict object, which the C++ sequence also holds, is updated in place. Then the sequence becomes schedulable.

compute_image_layout#

  1. Lines 166-167: a very wide image is clamped to max_wh_ratio.
  2. Lines 170-173: a small image is scaled up to min_pixels.
  3. Lines 178-179: round both sides up to a multiple of the patch size.
  4. Lines 180-188: safe_resize keeps that size if the token count fits, else solve_resize_ratio solves h × (w + 1) = max_n_token − 2 with the aspect ratio (deepinfer/ve/processor/image_processor.py:95-127).

_chunk_mm_metadata#

  1. Lines 36-37: cut the per-token keys to the chunk.
  2. Lines 43-47: binary search for the first image that ends after the chunk start and the first image that starts at or after the chunk end.
  3. Lines 50-52: no overlap: all image keys become None.
  4. Lines 55-73: cut the per-image keys, the raw bytes and the patch positions to the overlapping images, and shift the running sums to start at 0.

Deep dive

Processes, queues and the shared pool

  • Processes. The engine passes no num_workers, so the default of 1 applies: one worker process per engine (per DP rank) (deepinfer/ve/multimodal_processor.py:36, deepinfer/engine/llm_engine.py:213-219). The worker is a daemon ForkProcessWithCrashHeader (deepinfer/ve/multimodal_processor.py:99-101).
  • Queues. input_queue has no limit. output_queue holds at most DEEPINFER_MULTI_MODAL_BUFFER_SIZE results; a full queue blocks the worker, which gives back-pressure.
  • Pool. With DEEPINFER_USE_MULTIMODAL_POOL, the worker copies each non-empty tensor into a SharedTorchMemoryPool block and sends (handle, shape, dtype) (deepinfer/ve/multimodal_processor.py:202-211). The pool is one multiprocessing.shared_memory block, pinned for fast copies to the device (deepinfer/shared_memory.py:80-84, deepinfer/shared_memory.py:114-120).
  • Pool lifetime. When a prefill covers all tokens of a sequence, defer_expiring_pool_handles takes the blocks and records an event after the host-to-device copy is queued. free_deferred_pool_handles waits for that event and frees the blocks in pre_sampler_sync of the same step (deepinfer/ve/schema.py:53-77).
  • Shutdown. stop terminates the workers, joins them when the pool is on, and closes the pool (deepinfer/ve/multimodal_processor.py:317-326).
Deep dive

Worked example: a two-image prompt in two chunks

Prompt: 40 text tokens, image A (206 tokens), 10 text tokens, image B (206 tokens), 30 text tokens. Total 492. Image spans: A = (40, 206), B = (256, 206). Assume a token budget of 300 and chunked prefill on.

  1. Chunk 1 would be tokens 0-299. Position 300 is inside B (B covers 256-461), so the scheduler must move the end. This is the first sequence of the batch, so it tries to grow to 462. 462 tokens exceed the budget, so it shrinks to the start of B: chunk 1 is tokens 0-255 (csrc/engine/scheduler.hpp:487-493).
  2. _chunk_mm_metadata(0, 256): ends = [246, 462], bisect_right(ends, 0) = 0; starts = [40, 256], bisect_left(starts, 256) = 1. So only image A is in chunk 1.
  3. Chunk 2 starts at 256, the first token of B, which is an IMAGE id. Its 236 tokens fit the budget. bisect_right(ends, 256) = 1, bisect_left(starts, 492) = 2: only image B.

So each image goes to the ViT exactly once, in the chunk that holds all its tokens. The slicing code also handles the theoretical case that a chunk cuts an image, but the scheduler rule prevents it.

Check yourself#

  1. 1
    Which process decodes the JPEG bytes of an image?
    easy
    Show answer

    The forked multimodal worker. The image processor returns a lazy ImageTensorLoader, and the mapper calls load() in the worker (deepinfer/ve/processor/image_processor.py:292-302, deepinfer/model_executor/models/deepseek_vl.py:81-89).

  2. 2
    What does TextLengthInput carry, and why not the text tokens?
    medium
    Show answer

    Only a length. The engine already has the ids; the processor only needs to make mm_token_type zeros of that length (deepinfer/ve/processor/common.py:24-27, deepinfer/ve/processor/text_processor.py:10-13).

  3. 3
    When are the pool blocks of a request freed in the normal case?
    medium
    Show answer

    In the step whose prefill covers all tokens of the sequence. defer_expiring_pool_handles takes them during preparation, and free_deferred_pool_handles frees them in pre_sampler_sync after the copy event (deepinfer/ve/schema.py:53-77, deepinfer/engine/llm_engine.py:118-119).

  4. 4
    In the worked example, why does chunk 1 end at token 255 and not at 299?
    hard
    Show answer

    Position 300 is inside image B. The first sequence of a batch may grow to the image end (462), but that exceeds the budget of 300, so _adjust_chunk_size shrinks the chunk to the start of B at 256 (csrc/engine/scheduler.hpp:235-260, csrc/engine/scheduler.hpp:487-493).

Related pages

  • Vision encoder (VL)DeepInfer reads images in the prefill of the same engine. A worker process prepares each image, the scheduler keeps whole images in one chunk, and a ViT plus a projector turn the pixels into vectors at the image-token positions of the prompt.
  • models/deepseek_vl.py: the vision-language model classDeepseekVLForCausalLM is the only registered model class. It adds the vision encoder to DeepseekForCausalLM, prepares image metadata in the multimodal worker process (multi_modal_mapper), and computes the input embeddings of every prefill.
  • vision_encoder/vit.py, vl_aligner.py, mlp_projector.py: the vision encodervit.py is the fixed 32-block ViT of V4.1. vl_aligner.py turns raw RGB bytes into patches, runs the ViT, joins blocks of patches, runs the MLP projector of mlp_projector.py, and writes the result into the image-token rows of the prefill embeddings.
  • engine/llm_engine.py: the LLMEngine classLLMEngine starts the workers, sizes the KV cache, owns the C++ scheduler, and runs one engine step each time LLM calls step().
  • The schedulerIn every engine step, the C++ scheduler runs either a prefill batch or a decode batch. It starts prefills only at attempt points, cuts long prompts into chunks, gives KV blocks, and preempts sequences when the blocks run out.
  • shared_memory.py: the pinned memory pool for imagesshared_memory.py has SharedTorchMemoryPool, a pool of pinned host memory that the image worker process and the engine process share. The image worker writes preprocessed image tensors into it, and the engine copies them to the device with no extra copy. The file also has an unused SharedMemory class.
