engine/prepare_sample.cpp: the sampler inputs

AdvancedCode mapabout 6 min read + 2 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • The sampler Intermediate
  • Input metadata (varlen batching) Intermediate

Purpose#

This file has one public function, prepare_sampler_inputs. It makes the sampler inputs of one step: the rows of the model output that the sampler reads, and the values that each sequence brings.

Filescsrc/engine/prepare_sample.cpp, 284 lines of C++, and csrc/engine/prepare_sample.hpp, 66 lines (the result structs).
Main functionprepare_sampler_inputs (csrc/engine/prepare_sample.cpp:40-284).
Runs inThe driver worker process, on the CPU. It releases the Python GIL for the whole call (csrc/engine/prepare_sample.cpp:42).
Called byModelRunner.prepare_sampler_inputs, inside execute_sample (deepinfer/worker/model_runner.py:244-249).
Callstorch::empty with pinned memory, and Tensor.to(device, non_blocking=true). No kernels.
Not in this fileThe sampling math (layers/sampler.py and its kernels), the input metadata of the model (prepare_tensor_input_v4.cpp: the C++ input builder), and the update of the sequences after sampling (process_output.hpp).

Where it sits#

Who calls it#

  • ModelRunner.prepare_sampler_inputs on the driver. It passes the sequence list without graph padding, nextn, and the YOCO mode (prefill) or OFF (decode) (deepinfer/worker/model_runner.py:238-249).
  • The binding with default arguments: yoco_prefill_truncation_mode=OFF, yoco_prefill_keep_tokens=0 (csrc/engine/pybind_output.cpp:133-135).

Who reads the result#

  • The sampler gathers the selected hidden-state rows first: gather(hidden_states, selected_token_indices) (deepinfer/model_executor/layers/sampler.py:125, deepinfer/model_executor/layers/sampler.py:141). So it computes logits only for these rows.
  • The prefill EOS rows (deepinfer/model_executor/layers/sampler.py:184), the speculative rows (deepinfer/model_executor/layers/sampler.py:456) and the golden tokens (deepinfer/model_executor/layers/sampler.py:665-671).
  • With context parallelism, the followers get only the row indices by broadcast (deepinfer/worker/model_runner.py:250-259).

Walk through the main methods#

Checks and sizes#

  1. Line 42: the function runs without the GIL, so other Python threads can run.
  2. Lines 48-49: a prefill step has no draft tokens to verify, so nextn_token_cnt is 0 there.
  3. Line 61: all sequences must be prefill or all decode.
  4. Lines 72-77: prefill samples one row per sequence; decode samples every row (seqlen_q rows per sequence).

Allocation#

Line 82: the number of parameter entries is the number of sequences in both cases. So temperatures, top_ps, top_ks, seq_seeds and sample_positions have one entry per sequence, not per row. All arrays are pinned CPU tensors.

The prefill branch#

  1. Lines 168-180: with YOCO compact, the model output has only the kept rows. The same clip_prefix formula as in the input builder gives their count.
  2. Lines 181-189: prompt log-probabilities. Row j of the chunk predicts prompt token q_start + j + 1.
  3. Lines 192-195: on the last chunk with first_n_token_no_eos == 1, the sampler must not pick EOS.
  4. Lines 197-199: the sampled row is the last row of the chunk; sample_positions is seqlen_k, the position of the next token.

The decode branch and the speculative fields#

  1. Lines 203-205: every row of the sequence is sampled. Row j (0 to 4) gives the distribution that checks draft j + 1. The last row samples a new token after the last draft (see lines 221-225).
  2. Line 206: sample_positions is the position after the last real token.
  3. Lines 210-212: every decode sequence must have exactly nextn draft tokens, and at most 1 + nextn rows.
  4. Lines 221-225: rows 0 to seqlen_q − 2 read the draft information of the sequence's MTP slot. The last row reads slot 0, the padding slot.

The first loop also writes mtp_first_token_positions and mtp_seqlens_q for every decode sequence (csrc/engine/prepare_sample.cpp:151-154). With ZOS, the Worker first corrects seqlen_q on the CPU metadata from the device values, so these arrays match the real step (deepinfer/worker/worker.py:147-152).

Golden tokens and the copies#

Golden tokens force the sampled result for testing ("golden teacher forcing", deepinfer/model_executor/layers/sampler.py:92). -1 means "sample normally". At the end, every array starts a non-blocking copy to the default device. The CPU does not wait for these copies.

Worked example: the decode step of the figure

Sequences C (seqlen_q = 6, seqlen_k = 306, MTP slot 2) and D (seqlen_q = 6, seqlen_k = 134, MTP slot 1). nextn = 5. The graph has 16 rows, but this function gets only C and D.

  1. R = 12, S = 2.
  2. selected_token_indices = [0, 1, …, 11]. Rows 12-15 (padding) are not in it.
  3. mtp_first_token_positions = [0, 6], mtp_seqlens_q = [6, 6].
  4. sample_positions = [306 − 6 + 1, 134 − 6 + 1] = [301, 129].
  5. mtp_info_read_rows: C rows 0-4 read 2 × 5 + j = 10 … 14, row 5 reads 0; D rows 6-10 read 5 … 9, row 11 reads 0.
  6. mtp_info_write_slots = [2, 1]. The read slot is the same slot when the sequence has draft information, else 0 (csrc/engine/sequence.hpp:149-153).
  7. stop_token_ids = [[1, -1], [1, -1]] with the EOS id 1, or -1 in the first column when ignore_eos is set.

The prefill step of the figure: A (last chunk, q 60, k 260) and B (first chunk, q 200, k 200). selected_token_indices = [59, 259], sample_positions = [260, 200]. With YOCO compact and 140 kept tokens, B keeps 1 row, so the output has 61 rows and the indices are [59, 60]. B's sampled token is not used, because B is not on its last chunk; the scheduler drops it (csrc/engine/scheduler.hpp:1011-1020).

Check yourself#

  1. 1
    How many temperature values does a decode step with 3 sequences of 6 rows get?
    easy
    Show answer

    Three, one per sequence. num_sampling_positions is num_seqs in decode (csrc/engine/prepare_sample.cpp:82, csrc/engine/prepare_sample.cpp:84).

  2. 2
    A prefill batch has chunks with seqlen_q 60 and 200. Which output rows does the sampler read?
    medium
    Show answer

    Rows 59 and 259: the last row of each chunk, model_output_offset + out_len − 1 (csrc/engine/prepare_sample.cpp:197).

  3. 3
    In a decode step with nextn = 5, why does the last row of each sequence read MTP slot 0?
    hard
    Show answer

    The last row has no draft to verify: it samples a fresh token. The comment says "The final row is a fresh sample and reads padding from slot 0" (csrc/engine/prepare_sample.cpp:224-225). Slot 0 is the padding slot that no request uses (csrc/engine/scheduler.hpp:125-126). This is in the deep dive "Worked example".

Related pages

  • layers/sampler.py: the Sampler classsampler.py holds the Sampler module. It turns selected hidden states into float32 logits, samples prefill tokens, verifies draft tokens in decode steps and calls DFlash. sampler_utils.py holds the logits, sampling and prompt-logprob helpers.
  • worker/model_runner.py: the ModelRunner classModelRunner owns the model object on one rank. It builds the input metadata, runs the forward pass (eager or as a CUDA graph replay), prepares the sampler inputs, runs the memory profile and captures the graphs.
  • deepinfer/_C/engine.pyi: the C++ engine API, as seen from Pythonengine.pyi is the generated type stub of deepinfer._C.engine. This page maps its 34 names in five groups to the Python files that use them and to the C++ files that bind and implement them, with the rules for borrowed memory and the GIL.
  • csrc/engine/sequence.hpp: Sequence and SequenceMetadatasequence.hpp defines the C++ Sequence (one record per request, owned by the scheduler) and SequenceMetadata (a per-step view of one scheduled sequence that the worker reads). It also defines the status enum, the finish reasons and the image token offsets.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
  • DSpark: DFlash drafts and confidence-scheduled verificationDSpark makes 5 drafts per request with the DFlash draft model and predicts how likely each draft is to pass. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time.
  • YOCO and SWA bounded replayYOCO splits the main layers into producer and consumer layers. Consumer layers project their compressed KV from one shared hidden state. With the optional prefill truncation (README feature "Decoder SWA bounded replay"), a prefill computes the consumer layers only for the last KEEP_TOKENS prompt tokens (140 in the README), with the window cut at that range. Only their compressed KV still covers every token.
