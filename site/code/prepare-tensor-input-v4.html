prepare_tensor_input_v4.cpp: the C++ input builder

Purpose#

This C++ file computes the V4 part of the input metadata: for each row of the packed batch, where its cache entries go and which cache entries it reads.

Filecsrc/engine/input_metadata/prepare_tensor_input_v4.cpp, 655 lines of C++. It builds on prepare_tensor_input_base.cpp (251 lines), prepare_tensor_input.hpp (73 lines) and block_load_plan.cpp (60 lines) in the same folder.
Main functionsprepare_prompt_v4 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:391) and prepare_decode_v4 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:562).
Runs inThe driver worker process, on the CPU, with the GIL held (it writes Python dicts). Part of the extension deepinfer._C.engine.
Called byModelMetadata.prepare_inputmetadata_dict through the bindings (csrc/engine/pybind_output.cpp:73-74).
CallsThe base functions in prepare_tensor_input_base.cpp, BlockLoadPlanBuilder, and torch::empty for pinned tensors.
Not in this fileThe ZOS decode path (Python and a device kernel, see model_executor/input_metadata/: the InputMetadata classes), the sampler inputs (engine/prepare_sample.cpp: the sampler inputs), and the image fields (deepinfer/ve/prepare_tensor_input_vl.py).

Where it sits#

Who calls it#

  • ModelMetadata.prepare_inputmetadata_dict fills a PrepareArgs and calls prepare_prompt_v4 or prepare_decode_v4 (deepinfer/model_executor/model_metadata_utils.py:156-181).
  • With ZOS on (the default), decode steps call the Python prepare_decode_v4_zos instead (deepinfer/model_executor/model_metadata_utils.py:143). So in a default run, this file builds only prefill metadata.
  • The bindings: PrepareArgs and the two functions (csrc/engine/pybind_output.cpp:53-74). The build compiles the three .cpp files of the folder (setup.py:29-31).

What it calls#

  • prepare_prompt_base and prepare_decode_base: positions, token ids, the load-balance flag, Engram n-grams, the padding mask (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:65-186).
  • fill_decode_context_lens, fill_decode_block_tables, fill_decode_query_indices (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:188-251).
  • BlockLoadPlanBuilder for the load plans (csrc/engine/input_metadata/block_load_plan.hpp:19-34).

Walk through the main methods#

The two modes of every field#

Every function can make its tensors or fill existing ones. The comment at the top of update_common_v4 says, translated: "1. args.out has a value: the tensors are already allocated in result; only fill them. 2. Else: build the tensors from zero and write them into result." (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:20-25).

update_common_v4: where new entries go#

  1. Lines 47-49 (prefill): the new compressed entries of a sequence are seqlen_k/n − (seqlen_k − seqlen_q)/n, at least 1.
  2. Lines 58-61: entry j has position j × n and slot block_table[j / cbs] × cbs + j % cbs, with cbs = 128 / n.
  3. Lines 63-67: a sequence with no new entry gets one dummy entry with slot -1, so every sequence has at least one row in the compressor.
  4. Lines 80-91 (decode): one value per row. Only a row at position p with (p + 1) % n == 0 ends an entry.

Lines 103-106: the SWA slot. Only the last swa_block_size rows of a sequence write to the ring; older rows of a long chunk would be overwritten anyway. Lines 111-123: state_block_idx has one value per sequence in prefill and one per row in decode.

prepare_prompt_v4: the prefill fields#

Then the function adds, in this order:

  1. cu_compressed_seqlens_q per ratio, with at least 1 per sequence (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:420-432).
  2. ks and ke per sparse ratio. A row at position j sees (j + 1) / r compressed keys from the start of its sequence in the gathered buffer (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:434-459).
  3. The SWA load plan and the compressed load plans (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:461-476).
  4. kv_swa_full_index_pivots (next section).
  5. The YOCO fields, when the mode is not off (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:532).
  6. kv_ca_index_offset_len per dense ratio (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:534-557).

The SWA history and the pivots#

Each sequence gets exactly window_size history rows. Rows before position 0, or before swa_valid_start, are zero-filled (src_block_id = -1). The rest comes from the sequence's ring, in at most two pieces because the ring wraps.

  1. Lines 493-494: the gathered buffer has all histories first (window_size rows each), then all new rows.
  2. Lines 507-509: the oldest visible position is pos − window + 1, but not before swa_valid_start or 0.
  3. Lines 512-517: section 1 is a range of the sequence's history block.
  4. Lines 520-523: section 2 is a range of the sequence's new rows, up to the row itself (causal).

prepare_decode_v4: the decode fields#

The decode block table of a row uses the smallest ratio of the model (line 566, line 586). The offset of row i is i × max_num_blocks × tpb: it points at row i of the flat block_tables tensor in "compressed token" units.

Deep dive

The load plan builder, line by line

  1. Lines 9-12: a segment records its destination offset, which is the running total total_k_.
  2. Lines 14-21: a zero fill is cut into pieces of at most one source block.
  3. Lines 23-35: a paged range walks the block table. Each segment stays inside one block.

append_ring_range does the same for a ring: the source block id stays the state slot, and the position wraps with % source_block_size (csrc/engine/input_metadata/block_load_plan.cpp:37-46). The compressed plan of a sequence covers entries 0 to seqlen_k / n; a sequence with 0 entries gets a one-entry zero fill, "on par with" the max(1, …) in ks (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:51-63, csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:451-452).

Example (sequence A of the figure, ratio 2, block table [7, 2, 9], seqlen_k = 260): 130 entries, 64 per block: [7,0,64,0], [2,0,64,64], [9,0,2,128].

Deep dive

YOCO: the visibility rule and the compact layout

The "rectangle" is the kept range [data_len − keep_tokens, data_len). Rows outside it see nothing in mask mode. In compact mode they are dropped, but a chunk always keeps at least its last row as a placeholder (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:222-225). In compact mode, a kept row writes to the ring only if it is in the rectangle and among the last swa_block_size rows of the chunk (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:266-271).

With CP above 1, fill_yoco_consumer_cp_scalars computes two lengths for the device: the compact mirror length Σ 2 × ⌈keep_len / (2·cp)⌉ and the largest number of kept rows on one rank (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:173-201). Rank r holds parts r and 2·cp − 1 − r of each sequence (line 187), the CP mirror layout.

Settings that reach this file

All values come through PrepareArgs, set in deepinfer/model_executor/model_metadata_utils.py:160-180:

  • block_size: 128 for this model (deepinfer/model_executor/model_metadata_utils.py:133-135).
  • window_size and swa_block_size: from the model config, DEEPINFER_MAX_BACKTRACKING_TOKENS and, when it is on, DEEPINFER_PREFILL_STORE_EXTRA_STATE (deepinfer/worker/model_runner.py:101-102, deepinfer/worker/cache_engine.py:88-110).
  • yoco_prefill_truncation_mode, yoco_prefill_keep_tokens, max_backtracking_tokens: environment variables (deepinfer/model_executor/model_metadata_utils.py:175-178).
  • force_load_balance: DEEPINFER_FORCE_LOAD_BALANCE (deepinfer/model_executor/model_metadata_utils.py:166).
  • dense_compress_ratios, sparse_compress_ratios: from the attention configs; sparse means index_topk > 0 (deepinfer/model_executor/model_metadata_utils.py:29-34).

Check yourself#

  1. 1
    With ZOS on (the default), does prepare_decode_v4 run in a decode step?
    easy
    Show answer

    No. ModelMetadata picks prepare_decode_v4_zos when DEEPINFER_ZERO_OVERHEAD_SCHEDULING is on (deepinfer/model_executor/model_metadata_utils.py:143). Then a device kernel computes the decode fields.

  2. 2
    A decode row is at position 305 and the model has ratio-2 layers. Does it end a compressed entry, and which entry?
    medium
    Show answer

    Yes: (305 + 1) % 2 == 0. The entry is 305 / 2 = 152, with positions_c = 304 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:80-86).

  3. 3
    A prefill chunk has q_start = 200 and a window of 128. What are the pivots of its first row (position 200), if it is the first sequence of a batch of two?
    hard
    Show answer

    abs_lo = 73, so section 1 starts at slot 73 − (200 − 128) = 1 with 127 rows, and section 2 has 1 row at 2 × 128 + 0 = 256. Pivots: [1, 127, 256, 1] (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:493-523). This matches the deep dive of Input metadata (varlen batching).

  • Sliding-window attentionEvery attention layer of DeepSeek-V4.1-Flash reads the most recent tokens (a window of 128 in the docs) from a ring of 134 slots per sequence and layer. This page shows the ring, the decode and prefill index paths, and how the window joins the compressed keys.

With the optional prefill truncation (README feature "Decoder SWA bounded replay"), a prefill computes the consumer layers only for the last KEEP_TOKENS prompt tokens (140 in the README), with the window cut at that range. Only their compressed KV still covers every token.
