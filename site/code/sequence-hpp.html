csrc/engine/sequence.hpp: Sequence and SequenceMetadata

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

  • Request and sequence lifecycle Intermediate

Purpose#

sequence.hpp defines the record that the engine keeps for each request, and the small view of it that each step sends to the model and the sampler.

Filecsrc/engine/sequence.hpp, 419 lines of C++ in one header. Most comments are in Chinese.
Main classesstruct Sequence (csrc/engine/sequence.hpp:275) and struct SequenceMetadata (csrc/engine/sequence.hpp:325). Also the enums MMTokenOffset and SequenceStatus, and eleven helper structs (from SequenceData to SequenceInit).
Runs inCPU memory of the engine process. A Sequence lives in a std::shared_ptr; the scheduler queues and Python share it. No device code.
Used byscheduler.hpp, block_manager.hpp, mtp_varlen.hpp, outputs.hpp, prepare_sample.hpp, process_output.hpp, input_metadata/prepare_tensor_input.hpp, zos.cpp, and the bindings in pybind_sequence.cpp.
CallsOnly Python attribute reads: the constructor copies values out of the SamplingParams object (csrc/engine/sequence.hpp:103-115, csrc/engine/sequence.hpp:185-190).
Not in this fileThe queue logic (scheduler.hpp), the block allocator (block_manager.hpp), and the Python names of the fields (pybind_sequence.cpp).

Where it sits#

Who uses it#

  • Python makes a Sequence through the binding constructor, which builds a SequenceInit (csrc/engine/pybind_sequence.cpp:93-102). LLMEngine.add_request calls it (deepinfer/engine/llm_engine.py:594-598). Scheduler::fork_seq makes one in C++ (csrc/engine/scheduler.hpp:1074-1101).
  • The scheduler reads and writes almost every field (the page csrc/engine/scheduler.hpp: the C++ Scheduler).
  • The block manager fills cache.block_table and cache.state_id (csrc/engine/block_manager.hpp:207-214).
  • The schedule step makes one SequenceMetadata per scheduled sequence from the object pool (csrc/engine/scheduler.hpp:706-707).
  • The sampler preparation and the ZOS code read SequenceMetadata fields and call is_last_prompt_chunk and refresh_for_sampling (csrc/engine/prepare_sample.cpp:20-22, csrc/engine/zos.cpp:293-303).
  • The output builder reads the status, the lengths and the MTP values (csrc/engine/outputs.hpp:194-294).
  • Python imports the classes from deepinfer._C.engine through deepinfer/sequence.py (deepinfer/sequence.py:14-20).

What it calls#

Nothing outside the file, except py::object::attr for the sampling values and deepinfer::EnableObjectPool, the base class that marks pool objects (csrc/utils/object_pool.hpp:12-15).

Walk through the main methods#

Image tokens, statuses and reasons#

  1. Lines 21-28: five ids above the vocabulary. Only IMAGE (+2) and IMAGE_PAD (+1) appear in token lists (csrc/engine/scheduler.hpp:233-234); the scheduler uses them to protect image units in chunks (csrc/engine/scheduler.hpp:91-92).
  2. Lines 30-41: ten status values. SWAPPED exists, but no code sets it.
  3. Line 43: "finished" is an order test, so every value after FINISHED_STOPPED counts.

The comment at line 56 describes the intent. The scheduler picks the victim by output length only (csrc/engine/scheduler.hpp:624-625).

SequenceData: the token list#

  1. Lines 70-78: the Python path copies a C-contiguous int32 NumPy array with one memcpy. No value check happens here. add_request checks the ids before (deepinfer/engine/llm_engine.py:581-589).
  2. Line 83: the output length is computed, not stored: len − prompt_len. After a recompute, the prompt length does not change, so the old outputs still count as outputs.
  3. Line 85: get_last_token_id reads back(). On an empty list this is undefined behaviour; add_request refuses empty prompts (deepinfer/engine/llm_engine.py:553-554).

SamplingScalars and StoppingCriteria#

The constructor of Sequence calls capture once (csrc/engine/sequence.hpp:280-281). So a later change to the Python SamplingParams object does not reach the C++ copy. A missing attribute raises a Python error (AttributeError) when the sequence is made. StoppingCriteria copies only max_tokens and ignore_eos (csrc/engine/sequence.hpp:181-191).

MtpState: draft tokens#

  1. Lines 127-128: info_slot is the row of this sequence in the device-side MTP pool. The scheduler gives slots 1 … max_num_seqs (csrc/engine/scheduler.hpp:792-800).
  2. Lines 134-142: a recompute clears the draft state and both counters.
  3. Lines 149-153: take_draft_info_slot returns the slot only once per new draft info, then clears the flag. A second read in the same round gets slot 0 (padding).

next_golden_tokens returns 2 × nextn + 1 reference tokens, from position output_len on, padded with -1. Example: 10 golden tokens, output length 7, nextn = 5: positions 7 … 17, so [g7, g8, g9, -1, -1, -1, -1, -1, -1, -1, -1]. With no golden tokens, or output length 10 or more, it returns nothing.

KvCacheState: the cache counters#

  1. Line 203: num_tokens is the number of tokens whose KV entries are written (Python: num_cached_tokens).
  2. Line 206: block_table lists physical block ids. A real sequence never gets block 0 (csrc/engine/block_manager.hpp:27-35); only the placeholder step uses it.
  3. Line 207: state_id = -1 means "no state slot".
  4. Lines 216-219: advance_optimistically(n) remembers the old value and adds n.
  5. Line 221: commit_processed_tokens(n) sets the value to the old one plus n. Together, the two calls first assume that all query tokens are kept, then correct the value.

hit_tokens only goes from a parent to a fork (csrc/engine/scheduler.hpp:1086), and swa_valid_start is only reset to 0 in this file. No code in this release sets a value other than 0 for it, but the flop estimate and the tensor preparation read it.

SequenceScheduleState: status and in-flight tokens#

  1. Line 237: schedulable defaults to false here, but the binding sets it from the multimodal data (csrc/engine/pybind_sequence.cpp:35).
  2. Line 238: branch_id is "default". A fork waits with a _ prefix until its prefill is set up (csrc/engine/scheduler.hpp:398, csrc/engine/scheduler.hpp:423).
  3. Lines 244-247: schedule() adds nextn + 1 in-flight tokens for each scheduled step.
  4. Lines 249-256: process_outputs removes one step. If only one step was in flight, both counters go to 0. If two were in flight (ZOS), the total becomes the size of the last one.

Sequence: the record#

  1. Lines 280-281: copy the sampling and stop values once.
  2. Line 282: the first "last output token" is the last prompt token.
  3. Lines 286-289: reserve room for max_tokens more ids in both token lists.
  4. Lines 291-293: the number of blocks: ceil((len + total_inflight_tokens + drafts) / block_size). This is the core of all block decisions.
  5. Lines 307-311: a recompute resets the cache, schedule and MTP parts. The tokens stay.

SequenceMetadata: the per-step view#

  1. Lines 342 and 349: request_id and block_table are C++ references into the Sequence. A block added to the sequence later is visible through the metadata.
  2. Lines 346-348: pointers to the token lists; prompt_tokens is set only for prefill.
  3. Line 354: sampling is a copy, so the sampler reads plain numbers.
  4. Lines 357-358: seqlen_q (query tokens of this step) and seqlen_k (tokens after this step, including in-flight ones).
  5. Lines 363-365: the last output token and the two MTP pool slots (read and write).
  6. Line 371: prompt_logprobs is a reference, so prompt log-probabilities of several chunks add up in the Sequence (csrc/engine/process_output.hpp:23-27).

Line 382 calls take_draft_info_slot(), so building the metadata also clears has_draft_info. Lines 392-404 are a second constructor for Python dummies: the borrowed members point into owned, and the object never goes back to a pool. is_placeholder is true when the id is "placeholder" (csrc/engine/sequence.hpp:398).

  1. Line 406: the last prompt chunk is the one that reaches the full length.
  2. Lines 408-418: with ZOS, the metadata was made before the previous step was processed. refresh_for_sampling copies the newest values just before sampling (csrc/engine/zos.cpp:300-302). It keeps the old write slot if the sequence already gave back its slot.

Deep dive

Ownership and lifetime

  • Sequence. Held by std::shared_ptr (SequencePtr, csrc/engine/scheduler.hpp:34). The scheduler queues, SchedulerOutputs lists and Python handles share it. It dies when the last holder lets go.
  • SequenceMetadata from the pool. It holds references into its Sequence (request_id, block_table, mtp, prompt_logprobs) and raw pointers to the token lists. It must not outlive the Sequence. The engine keeps the step's SchedulerOutputs (and so the shared_ptrs) alive in the step state while the metadata is in use, and gives the metadata back one step later (deepinfer/engine/llm_engine.py:1013).
  • SequenceMetadata from Python. The second constructor owns its strings and vectors in owned, and the binding keeps seq_data and compressed_seq_data alive with keep_alive (csrc/engine/pybind_sequence.cpp:149-153).
  • Pool reuse. The pool destroys a released object and builds the next one in the same memory with placement new (csrc/utils/object_pool.hpp:26-31, csrc/utils/object_pool.hpp:34-41). So a Python reference to an old metadata object sees the new contents after reuse.

Worked example: counters through two ZOS decode steps

A running sequence has len = 501 (500 cached + the last sampled token), num_tokens = 500, 5 drafts, block size 128, and no step in flight. nextn = 5.

Eventtotal_inflightlast_inflightnum_tokenslenget_num_blocks()
start00500501ceil(506/128) = 4

step N+1 scheduled126500501ceil((501 + 6 + 5)/128) = 4

Lines: in-flight (csrc/engine/sequence.hpp:244-256), counters (csrc/engine/sequence.hpp:216-221), blocks (csrc/engine/sequence.hpp:291-293). The table assumes that the CPU schedules step N+2 after it processed step N, as in the Worker order: forward N+1, post-process N, then the next step() (deepinfer/worker/worker.py:113-189).

Check yourself#

  1. 1
    Which status values count as finished?
    easy
    Show answer

    Every value from FINISHED_STOPPED on: is_finished is the test status >= FINISHED_STOPPED (csrc/engine/sequence.hpp:43). That is seven values.

  2. 2
    A sequence has 260 tokens, 6 tokens in flight and 5 drafts. The block size is 128. How many blocks does it need?
    medium
    Show answer

    ceil((260 + 6 + 5) / 128) = ceil(271/128) = 3 (csrc/engine/sequence.hpp:291-293).

  3. 3
    The scheduler adds a block to a sequence after its SequenceMetadata was made. Does the metadata see the new block?
    medium
    Show answer

    Yes. block_table in SequenceMetadata is a reference to seq->cache.block_table, not a copy (csrc/engine/sequence.hpp:349, csrc/engine/sequence.hpp:379).

  4. 4
    With ZOS, two steps of a sequence are in flight: total_inflight_tokens = 12, last_inflight_tokens = 6. The older step is processed with 1 accepted draft, and num_tokens was 500. What are the three counters after process_outputs?
    hard
    Show answer

    finish_inflight_step sees 12 != 6, so total_inflight_tokens = 6 and last_inflight_tokens stays 6 (csrc/engine/sequence.hpp:249-256). advance_optimistically(6) gives 506, then commit_processed_tokens(2) gives num_tokens = 502 (csrc/engine/sequence.hpp:216-221). See the deep dive "Worked example".

Related pages

  • csrc/engine/scheduler.hpp: the C++ Schedulerscheduler.hpp holds the C++ Scheduler: the waiting and running queues, the choice between prefill and decode, block allocation, preemption, and the bookkeeping after each step. It also defines SchedulerOutputs and three free functions.
  • sequence.py: sampler output classes and C++ re-exportsdeepinfer/sequence.py re-exports the C++ Sequence classes and defines the dataclasses that carry the results of the sampler (tokens, log-probabilities, draft tokens and their confidence) from the device to the engine.
  • csrc/engine/block_manager.hpp: BlockManager and the free listblock_manager.hpp holds the C++ free list of KV blocks with reference counts, the BlockManager class with its mutex, and the helper that allocates blocks and a state slot for one sequence.
  • csrc/engine/outputs.hpp: RequestOutput and its pooloutputs.hpp defines RequestOutput (one new token of one request), a fixed pool of 10000 of them, and build_request_outputs, which turns one engine step into output handles. pybind_output.cpp binds them, with clone and raw-pointer accessors.
  • csrc/engine/zos.cpp: the C++ helpers of zero-overhead schedulingzos.cpp has three functions for ZOS decode steps - match the batch with the previous step (remap), pack the decode inputs into pinned arrays, and refresh the CPU metadata before sampling. The device kernels do the rest.
  • deepinfer/_C/engine.pyi: the C++ engine API, as seen from Pythonengine.pyi is the generated type stub of deepinfer._C.engine. This page maps its 34 names in five groups to the Python files that use them and to the C++ files that bind and implement them, with the rules for borrowed memory and the GIL.
  • Request and sequence lifecycleEach request becomes a C++ Sequence. It waits until it is schedulable, runs one or more prefill steps and many decode steps, and ends with one of seven finish reasons. Preemption stops it or sends it back to the queue for a recompute.
  • The schedulerIn every engine step, the C++ scheduler runs either a prefill batch or a decode batch. It starts prefills only at attempt points, cuts long prompts into chunks, gives KV blocks, and preempts sequences when the blocks run out.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
