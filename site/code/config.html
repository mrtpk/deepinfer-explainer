deepinfer/config.py: the four config classes

IntermediateCode mapabout 9 min read + 3 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • deepinfer/entrypoints/llm.py: the offline LLM class Beginner
  • engine/llm_engine.py: the LLMEngine class Intermediate

Purpose#

config.py turns the user's engine arguments into four checked objects, the engine config objects, and computes the limits that every later part reads.

Filedeepinfer/config.py, 228 lines. The header says "Derived from vLLM; modified by DeepSeek." (deepinfer/config.py:2). The maker of the objects is in deepinfer/engine/arg_utils.py, 114 lines.
Main classesModelConfig (deepinfer/config.py:19), CacheConfig (deepinfer/config.py:125), ParallelConfig (deepinfer/config.py:150), SchedulerConfig (deepinfer/config.py:185); in arg_utils.py: EngineArgs (deepinfer/engine/arg_utils.py:18).
Runs inThe engine process, one time at start-up. The CP follower processes get pickled copies.
Called byEngineArgs.create_engine_configs, which LLMEngine.from_engine_args calls (deepinfer/engine/llm_engine.py:460-469).
Callsload_model_config (reads the checkpoint config.json) and the envs class for DEEPINFER_USE_NEXTN_DECODE, DEEPINFER_ZERO_OVERHEAD_SCHEDULING and the prefill intervals.
Not in this fileModel sizes (they come from the checkpoint), the KV block count (measured later), and all DEEPINFER_* variables except four.

For a table of every field with its default, read Config classes. This page reads the code.

Where it sits#

Read panel 1 from left to right: the user calls LLM, which fills EngineArgs, which makes the four objects. Panel 2 lists what each object holds and which code reads it. Two objects get more fields after start-up measurements.

Who calls it#

  • LLM.__init__ makes EngineArgs from its arguments and calls LLMEngine.from_engine_args (deepinfer/entrypoints/llm.py:70-84).
  • create_engine_configs makes all four objects in one call (deepinfer/engine/arg_utils.py:62-114).
  • Scripts such as examples/benchmark.py also go through LLM (see deepinfer/entrypoints/llm.py: the offline LLM class).

What it calls#

  • load_model_config(model) reads <model>/config.json and asserts the vision part (deepinfer/model_config_loader.py:8-23).
  • envs.DEEPINFER_USE_NEXTN_DECODE and envs.DEEPINFER_ZERO_OVERHEAD_SCHEDULING for the length limits (deepinfer/config.py:13-14, deepinfer/config.py:224).
  • envs.DEEPINFER_PREFILL_ATTEMPT_INTERVAL and envs.DEEPINFER_PREFILL_ANY_ATTEMPT_INTERVAL, as default arguments (deepinfer/config.py:193-194).

Walk through the main methods#

_get_runtime_max_model_len: the real position limit#

  1. Line 13: nextn is the number of draft tokens, 5 by default.
  2. Line 14: scheduler_overhead is nextn positions, plus nextn + 1 more with ZOS. A decode step can be padded up to the largest query length, and with ZOS one step is still in flight (csrc/engine/scheduler.hpp:697-700).
  3. Line 15: draft_overhead is nextn more positions. The comment in the scheduler says that DFlash drafts go nextn positions further (csrc/engine/scheduler.hpp:698-699).

With the defaults and ZOS on, the limit is max_model_len + 16: 4096 becomes 4112, and 32768 becomes 32784. This is the runtime_max_model_len. A comment in the scheduler says that buffers that a position indexes, such as the RoPE cache, have this many rows, and the scheduler checks every step against the limit (csrc/engine/scheduler.hpp:699-701).

ModelConfig.__init__: lengths and the checkpoint#

  1. Line 63: _verify_load_format accepts only "auto" and "dummy", case-insensitive (deepinfer/config.py:115-119).
  2. Line 69: with max_model_len=None the value is 4096.
  3. Lines 70-71: the two derived limits.
  4. Lines 75-76: the dtype is always BF16. Engram can turn on the compressed tokenizer later (deepinfer/engine/arg_utils.py:89-91).
  5. Line 80 and lines 89-94: the checkpoint config is read here, at once. Four runtime values are copied into model_cfg.gpt, where the model code reads them.

The docstring says something else about max_model_len

The class docstring says: "If None, will be derived from the model" (deepinfer/config.py:39-40). The code does not read max_position_embeddings; it uses 4096 (line 69). Pass max_model_len yourself if you need longer sequences.

Pickling: why the follower re-reads config.json#

A CP follower is a spawned process, so its arguments are pickled (deepinfer/engine/llm_engine.py:377-395). The follower reads the same config.json again and then puts back the four runtime values. The checkpoint folder must be readable from every process.

CacheConfig: two inputs, four outputs#

The constructor takes the block size (always 128, from ModelMetadata, deepinfer/engine/arg_utils.py:83-84), gpu_memory_utilization and lookahead_tokens. Four fields start as None. Other code writes them during start-up:

  • num_gpu_blocks: the memory profile of the driver Worker (deepinfer/worker/base.py:267).
  • bytes_of_state_per_seqs, num_state_seqs, bytes_per_block: the cache engine (deepinfer/worker/cache_engine.py:949-951).

This works because the engine and the driver Worker hold the same CacheConfig object (deepinfer/engine/llm_engine.py:402-413). The engine reads the new values to size its two block managers (deepinfer/engine/llm_engine.py:265-266).

1.0 passes the check

The message says "must be less than 1.0", but the test is > 1.0 (line 146). So 1.0 is accepted, and so are 0 and negative values. A value of 0 or less leaves no memory for blocks, and start-up fails later with "No available memory for the cache blocks" (deepinfer/engine/llm_engine.py:441-444).

ParallelConfig: sizes and checks#

  1. Lines 161-162: data_parallel_size = 0 (the EngineArgs default) means max(1, ep // cp).
  2. Line 167: the DP rank is engine_rank % dp.
  3. Line 171: model_parallel_size is the CP size. There is no tensor parallelism.
  4. Lines 172-173: the Engram group size defaults to all ranks, and the world is the larger of the two.
  5. Lines 177-182: six asserts. The second one needs cp × dp to be a multiple of ep.

SchedulerConfig: limits for the C++ scheduler#

  1. Lines 193-194: the defaults of the two intervals are read when Python first imports this file, not when the object is made. See deepinfer/environ.py: the envs class and its EnvVar descriptors.
  2. Lines 196 and 199: the same derived values as in ModelConfig.
  3. Lines 209-212: without chunked prefill, a step must hold a full prompt, so the token budget must be at least max_model_len.
  4. Lines 213-216: both intervals must be 1 or more.

The engine adds two fields later: engine_type and driver_gpu_id (deepinfer/engine/llm_engine.py:252-253). The C++ scheduler reads nine attributes of this object by name with py::object::attr (csrc/engine/scheduler.hpp:94-108).

_get_max_num_batched_tokens: the step budget#

A decode step can need max_num_seqs × (1 + nextn) tokens. A given value must be at least that (an assert). Without a value, the budget is the largest of max_model_len, 4096 and that number.

EngineArgs and create_engine_configs#

SchedulerConfig gets model_config.max_model_len (line 110), so it sees 4096 when the user gave None. __post_init__ runs before this method; it sets DEEPINFER_ZERO_OVERHEAD_SCHEDULING and DEEPINFER_USE_MULTIMODAL_POOL if they are not set (deepinfer/engine/arg_utils.py:48-60). So the ZOS term of runtime_max_model_len sees the final value.

Check yourself#

  1. 1
    You call LLM(model=path) with no max_model_len. What is max_model_len, and where does the value come from?
    easy
    Show answer

    4096. ModelConfig.__init__ uses 4096 when the argument is None (deepinfer/config.py:69). The docstring says it comes from the model, but the code does not read the checkpoint for it (deepinfer/config.py:39-40).

  2. 2
    With max_model_len=32768, DEEPINFER_USE_NEXTN_DECODE=5 and ZOS on, what is runtime_max_model_len? What is it with ZOS off?
    medium
    Show answer

    ZOS on: 32768 + (5 + 6) + 5 = 32784. ZOS off: 32768 + 5 + 5 = 32778 (deepinfer/config.py:11-16).

  3. 3
    Why can the engine read cache_config.num_gpu_blocks right after _run_workers("profile_num_available_blocks"), although it never uses the return value?
    medium
    Show answer

    The driver Worker writes the value into the CacheConfig object (deepinfer/worker/base.py:267), and the engine passed that same object to the Worker (deepinfer/engine/llm_engine.py:402-413). So the engine sees the write (deepinfer/engine/llm_engine.py:437-438).

  4. 4
    You set DEEPINFER_PREFILL_ATTEMPT_INTERVAL=10 with os.environ in your script after import deepinfer.entrypoints.llm and before LLM(...). Does the scheduler use 10?
    hard
    Show answer

    No. The value is a default argument of SchedulerConfig.__init__ (deepinfer/config.py:193). Python computes default arguments when it runs the def, at the first import of deepinfer.config, and the import of llm.py already imports it. EngineArgs does not pass the interval (deepinfer/engine/arg_utils.py:107-113), so the scheduler gets 70. See the deep dive "Environment variables that this file reads".
