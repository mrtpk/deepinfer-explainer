shared_memory.py: the pinned memory pool for images

AdvancedCode mapabout 9 min read + 4 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Hardware platforms: NVIDIA and Ascend Intermediate
  • GPUs, kernels, and speed Beginner

Purpose#

shared_memory.py gives the image worker process and the engine process one shared block of pinned host memory, with a small allocator, so that preprocessed image tensors go from the worker to the device without a pickle and without a second copy.

Filedeepinfer/shared_memory.py, 363 lines of Python. Most comments and docstrings are in Chinese.
Main classSharedTorchMemoryPool (deepinfer/shared_memory.py:80). Also BlockHandle (deepinfer/shared_memory.py:68-72), the factory get_multi_modal_pool() (deepinfer/shared_memory.py:359-363), and a class SharedMemory that no file uses (deepinfer/shared_memory.py:24-65).
Runs inThe engine process (makes the pool, reads tensors, frees blocks) and the forked image worker process (allocates blocks, writes tensors). CPU only; the device copy happens elsewhere.
Called byMultimodalProcessor in deepinfer/ve/multimodal_processor.py and the helpers in deepinfer/ve/schema.py.
Callsmultiprocessing.shared_memory, torch (share_memory_(), from_numpy), multiprocessing.Lock, PLATFORM.pin_host_memory / unpin_host_memory.
Not in this fileNot the shared-memory queue of the CP group: that is distributed/shm_broadcast.py: MessageQueue. Not the KV cache. Not the image preprocessing itself.

What this module is, in one line

The name is general, but in this release the pool has one user: images. get_multi_modal_pool() is the only factory, and it reads DEEPINFER_USE_MULTIMODAL_POOL and DEEPINFER_MULTIMODAL_POOL_SIZE_GB (deepinfer/shared_memory.py:359-363).

Where it sits#

Who calls it#

  • The engine process makes the pool. MultimodalProcessor._start_workers calls get_multi_modal_pool() and passes the pool to the worker process, which it starts with fork (deepinfer/ve/multimodal_processor.py:93-104). The pool is made before the fork, so the child inherits the mapping, the shared metadata and the lock.
  • The image worker allocates and writes. For each tensor of a preprocessed image, it calls alloc_tensor, copies the tensor in, stores (handle, shape, dtype) and sets the dict value to None (deepinfer/ve/multimodal_processor.py:202-211). Only the small handles go back over the mp.Queue.
  • The engine reads. fetch() turns each handle back into a tensor view with get_tensor (deepinfer/ve/multimodal_processor.py:296-299).
  • The engine frees. In the input preparation of the step whose prefill reaches the last image token, defer_expiring_pool_handles takes the handles and records a device event (deepinfer/ve/schema.py:53-65, called at deepinfer/ve/prepare_tensor_input_vl.py:124). free_deferred_pool_handles waits for that event and frees the blocks, in pre_sampler_sync of the same step (deepinfer/ve/schema.py:68-77, deepinfer/engine/llm_engine.py:118-119). Aborts free at once (deepinfer/engine/llm_engine.py:654-655, deepinfer/ve/multimodal_processor.py:293-295).
  • Shut-down. MultimodalProcessor.stop stops the workers, clears the factory cache and calls close() (deepinfer/ve/multimodal_processor.py:317-326).

What it calls#

  • shared_memory.SharedMemory(create=True, size=...) for the data block (deepinfer/shared_memory.py:116).
  • PLATFORM.pin_host_memory(self.buffer): cudaHostRegister on NVIDIA, aclrtHostRegisterV2 on Ascend (deepinfer/shared_memory.py:119). See Hardware platforms: NVIDIA and Ascend.
  • torch.full(...).share_memory_().numpy() for the metadata arrays (deepinfer/shared_memory.py:75-77).

Walk through the main methods#

__init__: one pinned block and shared metadata#

  1. Lines 102-107: the size must be positive, max_blocks at least 2, and align a power of two.
  2. Lines 116-119: make the block, wrap it as a uint8 tensor, pin it.
  3. Lines 123-126: four arrays of max_blocks entries (default 4096): start, size, next node and state of each node.
  4. Lines 129-132: two list heads, each a one-element shared array.
  5. Line 135: the lock. A multiprocessing.Lock works across fork, because the child inherits it.

alloc: first fit, then wait#

  1. Line 174: round the size up to a multiple of align (64).
  2. Lines 177-212: under the lock, walk the free list from its head. The list is sorted by address, so this is first fit by address.
  3. Lines 187-195: an exact fit takes the free node itself.
  4. Lines 198-209: a larger block gives its first need bytes to a new node and keeps the rest.
  5. Lines 214-215: if no block fits, log a warning, sleep 10 ms (outside the lock) and try again. There is no time-out.

free: back in address order, then merge#

A double free raises ValueError (lines 230-231). Each merge returns one node to the list of unused metadata nodes (_push_meta_node, deepinfer/shared_memory.py:160-165).

get_tensor and alloc_tensor: typed views#

The view is a narrow of the pinned uint8 buffer, then a view(dtype) and a view(*shape). So the device copy of this tensor is a DMA from pinned memory. alloc_tensor frees the block again if the view fails (lines 306-310).

close: unpin, release, unlink#

If a tensor view is still alive, SharedMemory.close() raises BufferError. The code then drops its own references to the mapping instead (lines 340-343) and unlinks the name anyway. The memory stays until the last view is gone.

Step 8 waits for the event because the copy in step 6 is asynchronous. The docstring says, translated: "The pool memory is pinned and the H2D copy of try_concat is asynchronous, so wait for the event first; then reuse of a block does not overwrite a copy in flight." (deepinfer/ve/schema.py:69-70).

Deep dive

Worked example: the allocator on a 1024-byte pool

A pool with total_bytes = 1024 and align = 64. The table shows the free list (node, start, size) after each call (we ran a copy of the algorithm in plain Python).

CallReturns (block_id, offset, nbytes)Free list after
start-(0, 0, 1024)
A = alloc(100)(1, 0, 128)(0, 128, 896)
B = alloc(64)(2, 128, 64)(0, 192, 832)
C = alloc(300)(3, 192, 320)(0, 512, 512)
free(A)-(1, 0, 128), (0, 512, 512)
free(B)-(1, 0, 192), (0, 512, 512): B merged into A's node
D = alloc(200)(2, 512, 256)(1, 0, 192), (0, 768, 256): the first block is too small
free(C)-(1, 0, 512), (0, 768, 256)
free(D)-(1, 0, 1024): all merged again

Node ids move: after the last merge, node 0 is unused and node 1 holds the whole pool. Each free region and each allocated block uses one of the max_blocks nodes, so together they can use at most 4096 nodes. When alloc must cut a block and no unused node is left, _pop_meta_node raises MemoryError (deepinfer/shared_memory.py:152-158, deepinfer/shared_memory.py:197-198). An exact fit needs no new node (lines 187-195).

Sizes in practice. The default pool is 8 GiB = 8,589,934,592 bytes (deepinfer/environ.py:208). The log line counts it per rank: on a host with 8 devices it gives "expected resident 64GB" for the host (translated, deepinfer/ve/multimodal_processor.py:49-56).

Deep dive

Processes, the lock and why the metadata is shared

  • The pool is made in the engine process, then the image worker is forked (deepinfer/ve/multimodal_processor.py:97-104). A fork copies normal memory lazily (copy-on-write). A write in one process is then not seen in the other. So the metadata must be in shared memory: share_memory_() moves each tensor storage there before the fork (deepinfer/shared_memory.py:75-77).
  • The data block comes from multiprocessing.shared_memory, which is shared by name and by mapping.
  • The worker calls alloc, the engine calls free, both under the same mp.Lock. get_tensor and _validate_handle read the metadata without the lock.
  • The engine starts one image worker: num_workers defaults to 1, and the engine does not pass it (deepinfer/ve/multimodal_processor.py:36, deepinfer/engine/llm_engine.py:213-219).
  • Only the process with rank <= 0 logs the pool size (deepinfer/ve/multimodal_processor.py:49). Each DP replica has its own engine, so each has its own pool.

Deep dive

The unused SharedMemory class

This class wraps posix_ipc.SharedMemory: a named POSIX object, made with O_CREX (fail if it exists) and mode 0o777, sized with ftruncate, and mapped with mmap on the first access of buf. Its __reduce__ pickles only the name, so another process opens it by name. A search of the repository finds no import of it; the package posix_ipc==1.3.2 is in requirements.txt only for this file (requirements.txt:7). The pool above uses the standard multiprocessing.shared_memory instead.

Check yourself#

  1. 1
    Which two processes share the pool, and which one allocates?
    easy
    Show answer

    The engine process and the forked image worker. The image worker allocates and writes the tensors (deepinfer/ve/multimodal_processor.py:205-211). The engine reads them and frees the blocks (deepinfer/ve/schema.py:68-77).

  2. 2
    Why is the data block pinned?
    easy
    Show answer

    So that the copy to the device is a fast DMA from page-locked memory. The comment says so, translated: "pinned as host pinned memory to make H2D copies faster" (deepinfer/shared_memory.py:114-115, deepinfer/shared_memory.py:119).

  3. 3
    The pool has align = 64. A tensor of shape [3, 5] in float32 is allocated. How many bytes does the block have, and does get_tensor(handle, (3, 5), torch.float32) work?
    medium
    Show answer

    3 × 5 × 4 = 60 bytes, rounded up to 64. get_tensor checks align_up(60) == 64 == handle.nbytes, so yes; it views only the first 60 bytes (deepinfer/shared_memory.py:285-294).

  4. 4
    Why does free_deferred_pool_handles synchronize on an event before it frees, and what could go wrong without it?
    hard
    Show answer

    The device copy from the pool is asynchronous. Without the wait, the engine could free a block, the image worker could allocate it for a new image and overwrite it, while the old copy is still in flight. The event was recorded after the copies were issued (deepinfer/ve/schema.py:53-77).

  5. 5
    The pool is made in the engine process. Why are the metadata arrays made with share_memory_() and not as plain NumPy arrays?
    hard
    Show answer

    The image worker is forked after the pool exists (deepinfer/ve/multimodal_processor.py:97-104). Plain memory is copy-on-write after a fork: the worker's alloc would change only its own copy, and the engine's free would not see it. Shared storage makes both processes see one set of metadata (deepinfer/shared_memory.py:75-77).
