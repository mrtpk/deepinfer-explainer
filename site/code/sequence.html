sequence.py: sampler output classes and C++ re-exports

IntermediateCode mapabout 9 min read + 3 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Request and sequence lifecycle Intermediate
  • Offline API and the step loop Intermediate

Purpose#

deepinfer/sequence.py gives Python one import place for the C++ sequence classes, and defines SamplerOutput: the object that carries the sampler results of one step to the engine.

Filedeepinfer/sequence.py, 281 lines of Python. The header says "Derived from vLLM; modified by DeepSeek." (deepinfer/sequence.py:2). Many docstrings are in Chinese.
Main classSamplerOutput (deepinfer/sequence.py:172). Also SampledInfo, MTPPredictInfo, DeepInferTopkInfo and the helper _where_update.
Runs inThe process of the driver Worker, which is also the engine process. The tensors start on the device and move to the CPU at the end of sampling.
Called byThe sampler and DFlash (they make the objects), the model runner and the Worker (they finish and keep them), and LLMEngine._process_model_outputs (it reads them).
CallsOnly PyTorch, and the import of deepinfer._C.engine.
Not in this fileThe Sequence class itself: it is C++ (csrc/engine/sequence.hpp: Sequence and SequenceMetadata). The sampling math: it is in layers/sampler.py.

The name is from vLLM

In vLLM, sequence.py defines the sequence classes in Python. In DeepInfer those classes moved to C++. This file now only re-exports them and holds the sampler result types.

Where it sits#

Who calls it#

  • The sampler makes SampledInfo, DeepInferTopkInfo and SamplerOutput (deepinfer/model_executor/layers/sampler.py:555-560, deepinfer/model_executor/layers/sampler.py:626-630). A prefill step fills sampled_token only (deepinfer/model_executor/layers/sampler.py:198-203). A decode step fills the verified tokens, the drafts and the ZOS fields (deepinfer/model_executor/layers/sampler.py:277-291).
  • DFlash makes MTPPredictInfo with the new drafts (deepinfer/model_executor/models/mtp/dflash.py:338). Its CUDA-graph runner uses narrow and copy_ (deepinfer/worker/dflash_cuda_graph_runner.py:60-71, deepinfer/worker/dflash_cuda_graph_runner.py:91).
  • The model adds a post function that fills moe_load_balance_ratio (deepinfer/model_executor/models/deepseek.py:403-409).
  • The model runner runs the post functions after the step is on the CPU (deepinfer/worker/model_runner.py:369-378).
  • The Worker reads the ZOS fields of the previous step to correct the next one (deepinfer/worker/worker.py:219-243).
  • The engine reads the tokens, log-probabilities and drafts (deepinfer/engine/llm_engine.py:693-761).
  • Imports of the C++ classes. llm.py, llm_engine.py, worker.py, model_runner.py, the CUDA-graph runners and zos_status.py import Sequence, SequenceMetadata or SequenceData from here.

What it calls#

Only torch for tensor work, and deepinfer._C.engine for the re-exported names.

Walk through the main methods#

Imports and re-exports#

The C++ classes have no Python source. Their stubs are in deepinfer/_C/engine.pyi. A Sequence made in Python is the same object that the scheduler holds: the binding wraps a std::shared_ptr<Sequence> (csrc/engine/pybind_sequence.cpp:91).

_where_update and DeepInferTopkInfo#

  1. Lines 31-35: None means "no data". A None candidate keeps the current value.
  2. Lines 55-61: with topk = 0, no tensors are made. Else logps is float32 [req_cnt, topk] (zeros) and tokens is int32 [req_cnt, topk] (not set).
  3. Lines 63-68: sampler_epilogue starts the copies to the CPU with non_blocking=True. The values are valid only after the sampler's last sync.

MTPPredictInfo: the new drafts#

  1. Lines 88-91: token_ids [bs, nextn], and an optional confidence_rates [bs, nextn].
  2. Lines 93-98: narrow(req_cnt) drops the padding rows of a CUDA graph. It asserts 0 < req_cnt <= bs.
  3. Lines 100-104: copy_ copies in place; both objects must agree on the confidence tensor.
  4. Lines 106-110: the CPU copy is int32 for the ids.

The engine passes token_ids to process_MTPInfo, which stores them as the drafts of each sequence (deepinfer/engine/llm_engine.py:713-723, csrc/engine/scheduler.hpp:1235-1238).

SampledInfo: one kind of tokens#

  1. Lines 117-128: one SampledInfo holds either the sampled token of each request ([bs]) or the verified draft tokens (flat, [total_q] in decode).
  2. Lines 130-139: the CPU copy of token_ids becomes int32.
  3. Lines 141-151 (update) and 153-168 (from_reqcnt): no code outside this file calls them in this release. A search for from_reqcnt( and for .update(is_final finds only this file.

SamplerOutput: the result of one step#

The properties give old flat names to the nested fields: token_ids is sampled_token.token_ids, and accepted_token_ids is verified_tokens.token_ids. token_ids and token_logprobs return an empty tensor instead of None (lines 181-183, 187-189). So the engine can read output.token_ids.size(0) also for a placeholder output (deepinfer/engine/llm_engine.py:693-695).

  1. Line 226: first_token_positions is the key to the flat layout. Request i owns positions ftp[i] … ftp[i+1] − 1 of every [total_q] tensor.
  2. Line 230: predict_tokens holds the drafts for the next step.
  3. Lines 242-246: two statistics lists. The decode post function fills them as [req_cnt] + counts (deepinfer/model_executor/layers/sampler.py:293-296).
  4. Lines 254-255: so_status per request: -1 (aborted), 0 (no grammar), 1 (just started), 2 (started).
  5. Lines 259-269: four GPU tensors for ZOS. The next step reads them on the device to correct its seqlen_q and seqlen_k without a CPU sync (deepinfer/worker/worker.py:219-243).

post_funcs (line 177) is a list of functions that fill fields after the CPU copies are done. The model runner calls them once and clears the list (deepinfer/worker/model_runner.py:376-378).

Deep dive

Worked example: a decode step with two requests

Two requests, nextn = 5, both send 1 + 5 tokens, so total_q = 12. Request 0 gets 2 drafts accepted, request 1 gets 0. Illustrative values:

out.first_token_positions          # tensor([0, 6], dtype=torch.int32), CPU
out.accepted_token_ids             # shape [12]: [t1, t2, -1, -1, -1, *, -1, -1, -1, -1, -1, *]
out.token_ids                      # shape [2]: [s0, s1]  (the new sampled token of each request)
out.next_n_token_ids               # shape [2, 5]: new drafts for the next step
out.next_n_token_confidence_rates  # shape [2, 5] or None
out.num_accepted_tokens_gpu        # device, [2]: [2, 0]

The engine passes accepted_token_ids to C++ without a copy, because first_token_positions is set (deepinfer/engine/llm_engine.py:698-702). process_outputs walks the flat array with seqlens_q: request 0 appends t1, t2, s0; request 1 appends s1. The * slots are the main token positions and are not read (csrc/engine/scheduler.hpp:873-875). build_request_outputs uses first_token_positions to find each request's slice (csrc/engine/outputs.hpp:203-213).

A prefill step has only sampled_token. next_n_token_ids is None, so a NORMAL engine pads it with vocab_size − 1 ids, shape [bs, 5] (deepinfer/engine/llm_engine.py:706-711).

Deep dive

CPU copies, syncs and post functions

  1. The sampler calls sampler_epilogue() on each SampledInfo and MTPPredictInfo (deepinfer/model_executor/layers/sampler.py:259-264). Each one starts .to("cpu", non_blocking=True).
  2. The Worker records sample_end_evt after sampling (deepinfer/worker/worker.py:167-168).
  3. Before the post-process, the Worker waits for that event (deepinfer/worker/worker.py:262-263). Only now are the CPU tensors valid.
  4. The model runner calls the post functions: the prefill one splits the prompt log-probabilities per request; the decode one turns the device counters into lists (deepinfer/model_executor/layers/sampler.py:205-210, deepinfer/model_executor/layers/sampler.py:293-298).
  5. The engine reads the fields in _process_model_outputs.

Read the CPU fields only after the sync

A field that sampler_epilogue moved holds a CPU tensor at once, but its values arrive later. Code that reads it before sample_end_evt.synchronize() can read old memory. The comment says the same: "call this before the last sync of the sampler" (translated, deepinfer/sequence.py:64).

Deep dive

Unused code in this release

  • SampledInfo.update, SampledInfo.from_reqcnt, DeepInferTopkInfo.update, DeepInferTopkInfo.from_reqcnt_topk and _where_update call each other, but no other file calls them.
  • is_verified_token is set to True for verified tokens (deepinfer/model_executor/layers/sampler.py:555-557), but no code reads it.
  • nextn on SampledInfo is read only by update (line 145).

These helpers look like the tools for a merge of two sampler passes by a mask, but the release does not use them. This site describes them, and does not guess their future use.

Check yourself#

  1. 1
    Where is the Sequence class defined, and why does from deepinfer.sequence import Sequence work?
    easy
    Show answer

    In C++, in csrc/engine/sequence.hpp. sequence.py imports it from deepinfer._C.engine and lists it in __all__ (deepinfer/sequence.py:14-20, deepinfer/sequence.py:272-281).

  2. 2
    Why does SamplerOutput.token_ids return an empty tensor and not None when no token was sampled?
    medium
    Show answer

    The property makes an empty IntTensor on first access (deepinfer/sequence.py:179-183). The engine reads output.token_ids.size(0) for every step, also for a placeholder step whose output is a fresh SamplerOutput() (deepinfer/engine/llm_engine.py:693-695).

  3. 3
    In a decode step, request 2 has first_token_positions[2] = 12 and request 3 has first_token_positions[3] = 18. Which positions of accepted_token_ids belong to request 2, and which one is not read?
    medium
    Show answer

    Positions 12 to 17. Positions 12 to 16 are the 5 draft results; position 17 is the main token position, which process_outputs does not read (csrc/engine/scheduler.hpp:873-875, deepinfer/sequence.py:226-228).

  4. 4
    Which four fields of SamplerOutput stay on the device, and which component reads them? Why are they not copied to the CPU?
    hard
    Show answer

    sampled_token_ids_gpu, predict_token_ids_gpu, num_accepted_tokens_gpu and confidence_rates_gpu (deepinfer/sequence.py:259-269). With ZOS, the Worker of the next step reads them on the device to correct seqlen_q and seqlen_k before the CPU has the results (deepinfer/worker/worker.py:214-243). A CPU copy would need a sync and would stop the overlap. See the deep dive "Every field of SamplerOutput".

Related pages

  • csrc/engine/sequence.hpp: Sequence and SequenceMetadatasequence.hpp defines the C++ Sequence (one record per request, owned by the scheduler) and SequenceMetadata (a per-step view of one scheduled sequence that the worker reads). It also defines the status enum, the finish reasons and the image token offsets.
  • layers/sampler.py: the Sampler classsampler.py holds the Sampler module. It turns selected hidden states into float32 logits, samples prefill tokens, verifies draft tokens in decode steps and calls DFlash. sampler_utils.py holds the logits, sampling and prompt-logprob helpers.
  • engine/llm_engine.py: the LLMEngine classLLMEngine starts the workers, sizes the KV cache, owns the C++ scheduler, and runs one engine step each time LLM calls step().
  • worker/worker.py: the per-step WorkerWorker.execute_model_step runs every engine step on one rank in a fixed order - forward N, post-process N-1, sample N - and keeps a ZOS decode step for the next call. zos_status.py holds the two records that it keeps.
  • worker/model_runner.py: the ModelRunner classModelRunner owns the model object on one rank. It builds the input metadata, runs the forward pass (eager or as a CUDA graph replay), prepares the sampler inputs, runs the memory profile and captures the graphs.
  • models/mtp/dflash.py: the DFlash draft modeldflash.py holds DFlash, the draft model of DSpark. It writes draft keys from main-model features during the forward pass, makes 5 drafts per request in one pass after the verification, and stores drafts, logprobs and confidences in the MTP info pool.
  • The samplerThe sampler turns the hidden states of the rows that need a token into float32 logits, applies temperature, top-p and top-k, and draws one token per request with a seeded hash. In decode steps it also verifies the draft tokens.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
