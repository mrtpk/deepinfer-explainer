v4_modules/index_attn.py: the sparse-attention indexer

AdvancedCode mapabout 6 min read + 3 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Sparse attention with an indexer Advanced

Purpose#

index_attn.py chooses, for each query token of a sparse layer, the index_topk compressed keys that the main attention reads. It also writes the index keys into ica_cache.

Filedeepinfer/model_executor/models/v4_modules/index_attn.py, 575 lines. Role 2 "runtime adapter" (deepinfer/model_executor/models/v4_modules/__init__.py:10-15).
Main classMQA (deepinfer/model_executor/models/v4_modules/index_attn.py:56). Also the helper _align_mqa_weights (line 40).
Runs inEvery worker process, once per sparse index-source layer per step. Device kernels only; decode runs inside a CUDA graph.
Called byV4Attention in attn.py.
CallsDeepGEMM MQA-logits kernels, DeepSelect topk, TileLang interface kernels, KProject from compress.py.
Not in this fileThe indexer weights (MQAIndexer in mla_attn.py), the index query projection and the weights projection (merged in attn.py), the compressed KV itself (compress.py), the attention kernel.

The module docstring: "MQA computes the relu(q @ k) * weights logits that drive sparse attention, and keeps the prefill and decode metadata, candidate-block restriction and cross-layer index-K sharing in sync with cross_layer.py" (deepinfer/model_executor/models/v4_modules/index_attn.py:1-6).

Where it sits#

Who calls it#

  • V4Attention._init_compressor_and_indexer makes one MQA in each layer with its own indexer. It passes store_index_k (index-K source or not) and the shared topology (deepinfer/model_executor/models/v4_modules/attn.py:354-363).
  • V4Attention._compute_kv_ca_index calls self.index_attn(...) in every step (deepinfer/model_executor/models/v4_modules/attn.py:557-567).
  • In YOCO compact prefill, _store_yoco_full_kv calls store_index_kv for the full context (deepinfer/model_executor/models/v4_modules/attn.py:714-721).
  • V4Attention.get_max_ag_bytes_per_token adds MQA.get_max_ag_bytes_per_token() (deepinfer/model_executor/models/v4_modules/attn.py:382-383).

What it calls#

  • DeepGEMM (DeepGEMM): fp8_fp4_mqa_logits, fp8_fp4_sparse_mqa_logits, fp8_fp4_paged_mqa_logits, fp8_fp4_paged_sparse_mqa_logits and their metadata functions.
  • DeepSelect (DeepSelect): topk (deepinfer/model_executor/models/v4_modules/index_attn.py:12).
  • TileLang interface kernels: fused_norm_rope_hadamard_cast_store_kvcache, load_paged_kv_cache, convert_kv_index, candidate_block_max, get_candidate_compact_lens, restore_candidate_indices_inplace (deepinfer/model_executor/models/v4_modules/index_attn.py:18-32).
  • KProject: k_proj + k_norm (deepinfer/model_executor/models/v4_modules/compress.py:32-53).

Walk through the main methods#

__init__: sizes and the chunk size#

  1. Lines 86-87: Q and K use the FP4 index format; scores use bf16.
  2. Lines 93-94: only an index-K source makes a KProject. A consumer reads the source's cache.
  3. Line 95: max_kv_len = the longest possible number of compressed keys.
  4. Lines 97-109: candidate settings. A candidate consumer has narrower score rows: candidate_topk_blocks × candidate_block_size keys.
  5. Lines 111-118: the chunk size. The comment says the 8192 cap exists because the MQA kernel "downclocks when the chunk size is large".

forward#

  1. Line 546: the index query: RoPE on the last 64 values of each head, then FP4.
  2. Lines 549-555: store the index keys of the new compressed entries, unless YOCO already did it (store_kv=False).
  3. Lines 557-558: GPU only: align the weights for DeepGEMM.
  4. Lines 560-569: a candidate source resets the candidate state in the cross-layer runtime and allocates block_candidate_idxs filled with −1.
  5. Lines 571-575: prefill loads the keys and runs _topk_prefill; decode runs _topk_decode on the paged cache.

_topk_prefill#

  1. Line 339: without candidates, topk_lens = klen (valid keys per query). With candidates, the counts of the compact candidate rows.
  2. Line 346: the result buffer, int32 [total_q, topk_tokens].
  3. Lines 359-360: the candidate source also picks its candidate blocks from the same scores.
  4. Lines 361-372: topk writes straight into the chunk's rows of the result. output_idx_offset=ks makes the index global in the gathered key buffer. With candidates there is no offset, because line 374 restores the indices with ks.

_topk_decode#

  1. Lines 483-491: scores from the paged ica_cache.
  2. Lines 494-503: topk returns a tuple; [1] is the index tensor. The comment on line 498 is a rule: always pass end, because old scores stay in the buffer.
  3. Lines 508-513: convert_kv_index turns logical positions into ca_cache slots in place, through block_tables. −1 stays −1.

store_index_kv#

A layer that is not an index-K source returns at once (line 140). The input is the Compressor's output after norm and before RoPE. The positions are the compressed positions positions_c (line 150), and the store slots are the same as for the main compressed KV (line 159). So entry i of ica_cache and entry i of ca_cache describe the same compressed token.

Deep dive

Worked example: the score memory per layer

max_model_len = 32768 gives runtime_max_model_len = 32768 + 5 + 6 + 5 = 32784 with 5 drafts and ZOS on (deepinfer/config.py:11-16). For a C2 layer, max_kv_len = 32784 // 2 = 16392 (line 95).

  • Prefill. psum_row_bytes = 16392 × 2 = 32,784 (line 111). compute_chunk_size = min(8192, 10 GiB // 32,784 // 8 × 8) = 8192 (line 117). One chunk of scores: 8192 × 32,784 B = 268,566,528 B, about 256 MiB. A prefill of 20,000 query tokens runs three chunks.
  • Decode. 32 sequences × 6 tokens = 192 rows. p_sum = 192 × 32,784 B ≈ 6.0 MiB. There is no chunking in decode.

With candidates, a consumer layer's rows hold only candidate_topk_blocks × block size keys. For example 512 blocks of 16 keys give 8,192 keys = 16,384 B per row. This is a multiple of 1024 B, as line 109 asserts.

Simplified

512 blocks of 16 keys is an example. The candidate settings come from config.json.

Deep dive

NVIDIA and Ascend differences

  • _align_mqa_weights runs only on GPU (line 557).
  • Prefill candidate kernels get use_unaligned_ks=True on GPU only (lines 280, 324).
  • The dense decode metadata takes (block size, SM count) on GPU and (n_head,) on NPU (line 394). That is why all indexer layers must have the same head count (deepinfer/model_executor/model_metadata_utils.py:71-73).
  • The paged logits call passes use_ascend_kv_layout=False on NPU, with a TODO (lines 443-444).

The Python code imports the same module names on both platforms. The vendor build script builds DeepGEMM-Ascend and DeepEP-Ascend for Ascend (scripts/build_vendor.sh:8-16; see Hardware platforms: NVIDIA and Ascend).

Check yourself#

  1. 1
    What does MQA.forward return?
    easy
    Show answer

    An int32 tensor [T, topk_tokens]: for each query, the selected compressed keys, with −1 for missing keys. In prefill the values are rows of the gathered key buffer; in decode they are physical ca_cache slots (deepinfer/model_executor/models/v4_modules/index_attn.py:541-544).

  2. 2
    A layer has an indexer but is not an index-K source. What does store_index_kv do, and where do its keys come from?
    medium
    Show answer

    It returns at once (line 140). In decode the layer reads the ica_cache view of its source, which the cache engine gives it (deepinfer/worker/cache_engine.py:429-431). In prefill it reuses loaded_prefill_index_kv (deepinfer/model_executor/models/v4_modules/index_attn.py:193-196).

  3. 3
    Why does the prefill topk call pass output_idx_offset=ks only when there are no candidate blocks?
    medium
    Show answer

    With candidates, topk returns positions inside the compact candidate row. restore_candidate_indices_inplace then maps them back and adds ks itself (deepinfer/model_executor/models/v4_modules/index_attn.py:369, deepinfer/model_executor/models/v4_modules/index_attn.py:373-374).

  4. 4
    You lower DEEPINFER_INDEX_ATTN_MEMORY_LIMIT to 64 MiB, with max_model_len = 32768 and the defaults. What chunk size does a C2 layer get?
    hard
    Show answer

    One row is 32,784 B. 64 × 220 // 32,784 = 2,047; // 8 × 8 = 2,040. min(8192, 2040) = 2,040 rows (deepinfer/model_executor/models/v4_modules/index_attn.py:117). This is the deep dive "Worked example: the score memory".

Related pages

  • Sparse attention with an indexerIn a sparse layer, a small indexer scores all compressed keys for each query and keeps the best index_topk. The main attention then reads only those keys plus the sliding window.
  • MLA attention: one latent vector per tokenIn DeepInfer's MLA, all query heads of a layer read one 512-value vector per token. This vector is the key and also the value, so the KV cache keeps one small entry per token.
  • Cross-layer KV sharingA layer can reuse the compressed KV, the indexer keys or the top-k list of an earlier source layer. SharedLayerTopology turns three lists of source layers from config.json into checked segment maps; the cache engine then allocates the compressed-KV and index-K caches only for source layers.
  • KV compression (C1 and C2)A compressed layer stores one 512-value cache entry per token (C1) or per 2 tokens (C2). C2 mixes the two tokens with a learned softmax gate and keeps the score and latent of the most recent tokens in a small fp32 state ring. Entries are FP4 (288 B) by default, or FP8 (528 B).
  • v4_modules/attn.py: the MLA attention runtimeattn.py turns the MLA weight container into runtime weights and runs one attention layer per call: projections, sliding-window and compressed KV stores, the indexer, the FlashMLA kernel and the output projection. It also holds the DFlash draft attention.
  • v4_modules/mla_attn.py: the attention weight containersmla_attn.py allocates the weights of one attention layer with their Hugging Face names and shapes: the low-rank Q and KV projections, the compressor, the indexer, the grouped output projection and the attention sinks. It has no forward.
  • v4_modules/compress.py: the KV compressorcompress.py holds two small runtime classes. Compressor turns the projected KV of a C1 or C2 layer into compressed entries, stores them in ca_cache and returns the pre-RoPE vector for the indexer. KProject is the indexer's key projection of that vector.
  • v4_modules/cross_layer.py: sharing topology and the cross-layer runtimecross_layer.py builds and checks the static sharing topology of the model (SharedLayerTopology), holds the per-forward values that a source layer passes to later layers (CrossLayerRuntime), and exports flat per-layer flags for the cost estimate (SharedLayerMetadata).
