distributed/shm_broadcast.py: MessageQueue

AdvancedCode mapabout 9 min read + 4 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

Purpose#

shm_broadcast.py sends Python objects from one process to several processes on the same host, through a ring buffer in shared memory, with ZeroMQ sockets for set-up and for large objects.

Filedeepinfer/distributed/shm_broadcast.py, 461 lines of Python. "Derived from vLLM; modified by DeepSeek." (deepinfer/distributed/shm_broadcast.py:1-2). deepinfer/distributed/__init__.py is empty.
Main classesShmRingBuffer (deepinfer/distributed/shm_broadcast.py:33), Handle (deepinfer/distributed/shm_broadcast.py:152-159), MessageQueue (deepinfer/distributed/shm_broadcast.py:162).
Runs inThe CPU side of every rank of a CP group with more than one rank: the writer in the engine process (CP rank 0), a reader in each CP follower process. No device code.
Called byParallelProcessGroup.create_process_groups (set-up) and cp_broadcast_object (every message), both in parallel_state.py.
Callsmultiprocessing.shared_memory, pickle, zmq, torch.distributed.broadcast_object_list (one time, for the handle).
Not in this fileTensor data. Device tensors go through NCCL or HCCL broadcasts in communication_op.py. The pinned memory pool for images is a different module: shared_memory.py: the pinned memory pool for images.

Where it sits#

Read panel 2 from left to right. The dashed arrow is the writer that comes back to the same chunk 10 messages later. Panel 3 is the path of every call from the CP driver to its followers.

Who calls it#

  • Set-up. create_process_groups makes one queue per CP group, with 1 MiB chunks and 10 chunks, only if cp_size > 1 (deepinfer/model_executor/parallel_utils/parallel_state.py:122-124).
  • Every message. cp_broadcast_object calls enqueue on the writer and dequeue on a reader (deepinfer/model_executor/parallel_utils/parallel_state.py:17-23). Three kinds of callers use it:
    • method calls of the worker: run_workers on the driver, the slave loop on the followers (deepinfer/worker/base.py:296-300, deepinfer/worker/base.py:129-133);
    • the non-tensor part of broadcast_tensor_dict (deepinfer/model_executor/parallel_utils/communication_op.py:72-75);
    • the non-tensor fields of InputMetadata.broadcast (deepinfer/model_executor/input_metadata/input_metadata.py:153-156).
  • Shut-down. cleanup_shm_broadcast closes and unlinks the buffer (deepinfer/model_executor/parallel_utils/parallel_state.py:161-169).
  • Test. tests/distributed/test_shm_broadcast.py sends 10,000 random arrays (about 400 MB) from rank 2 of 4 processes, with 40 KiB chunks, so that many arrays use the overflow path (tests/distributed/test_shm_broadcast.py:108-136).

What it calls#

  • multiprocessing.shared_memory.SharedMemory to make or open the buffer (deepinfer/distributed/shm_broadcast.py:100-121).
  • zmq XPUB and SUB sockets on 127.0.0.1 (deepinfer/distributed/shm_broadcast.py:193-201, deepinfer/distributed/shm_broadcast.py:260-264).
  • dist.broadcast_object_list on the Gloo CP group, to send the handle to the readers (deepinfer/distributed/shm_broadcast.py:454-458).
  • deepinfer.utils.get_open_port and get_ip (deepinfer/utils.py:40-49).

Walk through the main methods#

create_from_process_group: set-up over a group#

  1. Line 442: the comment states the assumption. Every reader is a local (shared-memory) reader. So the group must be on one host.
  2. Lines 446-454: the writer (group rank 0 by default) makes the queue and broadcasts its Handle with broadcast_object_list. This is a Gloo collective on the CPU CP group.
  3. Lines 455-459: the readers get the handle and open the queue.
  4. Line 460: all ranks call wait_until_ready.

MessageQueue.__init__ and create_from_handle: the two sides#

The writer makes a ShmRingBuffer with one flag per local reader, and binds an XPUB socket on a free local port. XPUB_VERBOSE makes the socket pass every subscription message to the writer, so the writer can count the readers (the comment on lines 194-196). A reader opens the same buffer from the handle and connects a SUB socket that accepts all messages (deepinfer/distributed/shm_broadcast.py:252-264). The reader's position in local_reader_ranks is its flag number (deepinfer/distributed/shm_broadcast.py:256).

When a reader opens the buffer, the code patches multiprocessing.resource_tracker.register to do nothing. The comment explains: "Python incorrectly tracks shared memory even if it is not created by the process" (deepinfer/distributed/shm_broadcast.py:110-115).

acquire_write: wait for a free chunk#

  1. Lines 326-335: look at the flag row of chunk current_idx. If it is written and not read by all readers, wait one turn and look again.
  2. Line 341: set written = 0. The chunk is now "not written" for all readers.
  3. Lines 343-344: give the chunk to the caller, which writes the data.
  4. Lines 351-355: set all reader flags to 0, then set written = 1. The comment on lines 347-350 says the order is important: with the other order, a reader could see "written and already read" for a short time.
  5. Line 356: the next write uses the next chunk, modulo 10.

acquire_read: wait for a new chunk#

Each reader keeps its own current_idx. It waits until its chunk is written and its own flag is 0. After the caller has read the data, it sets its own flag to 1 and moves to the next chunk. Readers never touch the written flag.

enqueue and dequeue: the object path#

  1. Line 392: pickle the object with the highest protocol.
  2. Line 396: the object "overflows" if its pickle has max_chunk_bytes bytes or more (1 MiB in the CP queue).
  3. Lines 397-400: byte 0 of the chunk is the overflow flag. A small object goes into bytes 1 and up.
  4. Lines 401-402: a large object goes over the local XPUB socket. The chunk still goes through the ring, as a ticket.
  5. Lines 410-417: the reader reads byte 0. For a small object, pickle.loads(buf[1:]) reads the object; pickle knows its own length (comment, lines 412-414). For a large object, the reader reads one message from its SUB socket.

Why the order of messages is safe

The ring and the socket are two channels. A reader always takes the chunk first, and reads the socket only when byte 0 says "overflow". The writer sends a large object over the socket in the same order as the chunks. So the k-th socket message belongs to the k-th overflow chunk.

wait_until_ready and _spin_wait#

The handshake (lines 290-306) makes sure that every SUB socket is connected before the first large object goes out. A ZeroMQ publisher drops messages for subscribers that are not connected yet (general ZeroMQ behaviour). The wait loop (lines 308-318) calls os.sched_yield() on each turn. It does not sleep.

Deep dive#

Deep dive

Data flow: what goes through the queue in one step

With CP above 1, each prefill step sends these objects from the driver, in this order (the first three come from run_workers, _prepare_input_driver and prepare_sampler_inputs):

#ObjectTypical sizeSource
1("execute_model_step", {"is_prompt": True, "is_placeholder": False})tens of bytesdeepinfer/worker/base.py:300
2list of (key, value): the input metadata, with a TensorMetadata(dtype, size) for each tensora few KiBdeepinfer/model_executor/parallel_utils/communication_op.py:64-72
3the sampler metadata dict, the same waysmalldeepinfer/worker/model_runner.py:252-259

The tensor data does not go through the queue. After each metadata list, cp_broadcast_multi_tensor sends the tensors with one device broadcast per tensor (deepinfer/model_executor/parallel_utils/communication_op.py:36-43). So the 1 MiB chunk is large enough for normal steps, and the overflow path is rare. (Sizes in the table are estimates, not measured.)

Types. Any picklable object can go. The input metadata dict contains a class object ("type": type(input_metadata)), which pickle stores by name (deepinfer/worker/model_runner.py:204).

Deep dive

Processes, threads and CPU use

  • Writer: the engine process, on the thread that runs step(). enqueue spins only if the reader is 10 messages behind.
  • Readers: each CP follower process, in start_slave_worker_loop. Between steps, the follower sits in acquire_read. That loop calls os.sched_yield() and checks the flag again, with no sleep (deepinfer/distributed/shm_broadcast.py:308-318, deepinfer/distributed/shm_broadcast.py:364-377). So an idle follower keeps one CPU core busy.
  • ZeroMQ context: Context.instance() is one context per process (deepinfer/distributed/shm_broadcast.py:182).
  • The slow-reader log. After 60 s of waiting (DEEPINFER_RINGBUFFER_WARNING_INTERVAL), the waiter writes a debug log "No available shared memory block after ... seconds", then again after 120 s, and so on (deepinfer/environ.py:184, deepinfer/distributed/shm_broadcast.py:312-315). At the default log level, a debug log may not show.
Deep dive

Worked example: chunk numbers over 12 messages

CP group of 4: writer W, readers R0, R1, R2, 10 chunks. W sends messages m0 to m11.

  1. m0 to m9 go into chunks 0 to 9. Each chunk becomes 1 0 0 0.
  2. R0 and R2 are fast. They read m0 to m9; the rows become 1 1 0 1. R1 is slow and has read only m0 to m3: chunks 0-3 are 1 1 1 1.
  3. m10 goes to chunk 0 (10 % 10). Chunk 0 is 1 1 1 1, so W can write at once.
  4. m11 goes to chunk 1, also free.
  5. m14 would go to chunk 4. Chunk 4 is 1 1 0 1, so W waits until R1 reads m4.

So the writer can be at most 10 messages ahead of the slowest reader. In DeepInfer, each step sends 3 messages (the method call, the input metadata and the sampler metadata), so the driver CPU can be about 3 steps ahead before it waits.

Simplified

The count of 3 comes from the code paths in the first deep dive. A decode step that replays a CUDA graph also sends 3: its input metadata message holds only the five small values (deepinfer/worker/model_runner.py:202-212). InputMetadata.broadcast uses the queue only while the graph is captured; a replay does not run that Python code. Other worker methods, such as start-up calls, add their own messages.

Deep dive

Remote readers: in the code, not used by DeepInfer

The class can also serve readers on other hosts. For them, the writer binds a second XPUB socket on tcp://*:<port>, and enqueue sends every object over it (deepinfer/distributed/shm_broadcast.py:211-220, deepinfer/distributed/shm_broadcast.py:403-404). The writer's IP comes from get_ip(), which opens a UDP socket toward 8.8.8.8 to learn the local address; no packet is needed (deepinfer/utils.py:40-43). IPv6 addresses set the IPV6 socket option.

create_from_process_group always sets n_local_reader = n_reader (deepinfer/distributed/shm_broadcast.py:443-453), so in DeepInfer the remote path stays unused.

Check yourself#

  1. 1
    Which process writes to the CP queue, and which processes read from it?
    easy
    Show answer

    CP rank 0 (the engine process with the driver worker) writes. Each CP follower reads. The writer is writer_rank = 0 of the CPU CP group (deepinfer/distributed/shm_broadcast.py:436, deepinfer/model_executor/parallel_utils/parallel_state.py:124).

  2. 2
    Does the queue carry the tensor data of the input metadata?
    easy
    Show answer

    No. It carries the keys, the small values and a TensorMetadata(dtype, size) for each tensor. The tensors go with device broadcasts (deepinfer/model_executor/parallel_utils/communication_op.py:64-81).

  3. 3
    A pickled object has exactly 1,048,576 bytes (1 MiB). Which path does it take in the CP queue?
    medium
    Show answer

    The overflow path. overflow = len(serialized_obj) >= max_chunk_bytes (deepinfer/distributed/shm_broadcast.py:396), and 1 MiB is not smaller than 1 MiB. Byte 0 of the chunk becomes 1, and the bytes go over the local ZeroMQ socket. (The chunk also needs byte 0 for the flag, so an inline object can have at most max_chunk_bytes − 1 bytes.)

  4. 4
    Why does acquire_write reset the reader flags before it sets written = 1, and not after?
    hard
    Show answer

    With the other order, the row would go from 0 1 1 1 to 1 1 1 1 and 1 0 1 1 before it reaches 1 0 0 0. These intermediate rows say "written and already read" for a message that nobody has read. The docstring calls this intermediate case 3 "not correct" (deepinfer/distributed/shm_broadcast.py:80-85, deepinfer/distributed/shm_broadcast.py:347-355). The reset-first order keeps the row in a valid state at every moment. (Our reading of acquire_read: a reader that sees its own flag still at 1 does not skip the chunk. It waits one more turn, because it moves to the next chunk only after it reads, lines 365-377.)

  5. 5
    A follower is idle for an hour between two requests. What does its CPU do, and what appears in the logs?
    hard
    Show answer

    It spins in acquire_read: each turn reads the flag row and calls os.sched_yield(), with no sleep, so one core stays busy (deepinfer/distributed/shm_broadcast.py:364-377). Every 60 s it writes a debug line "No available shared memory block after ... seconds" (deepinfer/distributed/shm_broadcast.py:312-315). Note: with LLM.generate, the driver keeps calling step() while there is work. When it stops, the follower waits.
