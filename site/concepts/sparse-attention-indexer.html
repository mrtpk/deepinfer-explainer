Sparse attention with an indexer

AdvancedDeepInfer conceptsabout 8 min read + 7 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Attention, step by step Beginner
  • MLA attention: one latent vector per token Advanced
  • KV compression (C1 and C2) Advanced

In one sentence

In a sparse layer, a small indexer scores every compressed key for each query and keeps the best ones. The main attention reads only those keys.

The idea#

In full attention, each query reads every earlier key. For a prompt of 100,000 tokens, the last query reads 100,000 keys. The work grows with the length of the sequence.

sparse attention sets a limit. Each query reads only a fixed number of keys, index_topk, plus its sliding window. The problem is to choose good keys without reading all of them with the expensive attention. DeepInfer uses an indexer for this choice. The indexer is a second, cheaper attention:

  • it has its own head count and head size (index_n_heads, index_head_dim, from config.json);
  • its queries and keys are FP4 numbers;
  • it gives each key one score: relu(q·k), weighted per head, with no softmax (deepinfer/model_executor/models/v4_modules/index_attn.py:3);
  • a top-k selection kernel keeps the index_topk keys with the highest scores.

The indexer scores the compressed keys: one per token in a C1 layer, one per 2 tokens in a C2 layer (see KV compression (C1 and C2)). The selected positions then go to the MLA kernel as an index list.

An everyday comparison. In a large library, you do not read every book to answer a question. You look at the catalog cards first. The cards are short, so this is fast. Then you take the 20 books with the best cards to your desk. The indexer is the catalog check. The main attention reads the books on the desk. The comparison stops here: the indexer does a new catalog check for every single query token, and its "cards" are learned numbers, not titles. A good book with a bad card is never read.

In the code#

The parameter container is MQAIndexer in mla_attn.py. The runtime is the class MQA in index_attn.py. V4Attention in attn.py calls it.

Step 1: which layers have an indexer#

The HF loader gives every compressed layer the same index_topk and an indexer config with use_kproj=True (deepinfer/hugging_face/config.py:111-128). A layer is sparse when index_topk is above 0 (deepinfer/model_executor/models/v4_modules/attn.py:85). The container makes the indexer only in an "index source" layer:

With cross-layer sharing, a later layer can reuse the top-k list of an earlier layer. Such a layer has no indexer of its own (deepinfer/model_executor/models/v4_modules/attn.py:568-570). The value of index_topk is in config.json, not in the repo.

Step 2: the index query and the weights share projections#

The index query starts from the same query latent q_a as the main query. Its q_B matrix is merged into q_b_proj. The per-head weights come from the hidden state; their matrix weights_proj is merged into current_hidden_proj:

So the indexer usually needs no GEMM of its own for its query and its weights. One exception is a YOCO consumer layer that is a KV source. There the compressed KV has its own projection from the shared hidden state, so current_hidden_proj holds only the index weights (deepinfer/model_executor/models/v4_modules/attn.py:349-352).

Step 3: the index key comes from the compressed KV#

The Compressor stores each new compressed entry in ca_cache. It also returns a copy before RoPE, pre_rope_kv. The indexer projects this copy to index_head_dim values, normalizes it, applies RoPE, casts it to FP4 and stores it in ica_cache:

The index key format FP4_INDEX_KV_FORMAT holds 128 FP4 values and one UE8M0 scale per 32 values (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:129-137). The cache engine sizes it as index_head_dim / 2 + index_head_dim / 32 bytes (deepinfer/worker/cache_engine.py:76-78): 64 + 4 = 68 B for 128 values. The deployment notes say the same: "Indexer KV: per-32, ue8m0, MXFP4" (doc/inference_deployment_qa.md:219).

Step 4: score and select in prefill#

  1. Line 347: the queries go in chunks of compute_chunk_size rows, to limit the memory of the score matrix.
  2. Line 349: a DeepGEMM kernel computes p_sum, one bf16 score for each query of the chunk and each compressed key.
  3. Lines 361-372: DeepSelect topk keeps the best topk_tokens keys of each row. end limits the search to the valid keys of the row. output_idx_offset=ks turns a position in the sequence into a row of the gathered key buffer. Missing keys get −1.

Step 5: score and select in decode#

Decode reads the index keys straight from the paged ica_cache, with the block table. The comment on line 498 is a real trap: the score buffer is not cleared, so the call must pass end. After topk, convert_kv_index turns each logical position into a physical slot of ca_cache.

Step 6: the indices go to the attention kernel#

_compute_kv_ca_index returns the list as kv_ca_index and stores it in the cross-layer runtime for later layers (deepinfer/model_executor/models/v4_modules/attn.py:585-587). In prefill, kv_index_cat puts the sliding-window list in front (deepinfer/model_executor/models/v4_modules/attn.py:603-607). In decode, the list goes to FlashMLA as the index of the extra cache ca_cache (deepinfer/model_executor/models/v4_modules/attn.py:641-647). So one query reads at most window + index_topk keys.

Deep dive

Prefill, step by step, with a worked example

  1. Quantize Q (line 546): RoPE on the last 64 values of each index head, then FP4 cast.
  2. Store K (lines 549-555): only if store_kv is true and this layer is an index-K source.
  3. Align weights (lines 557-558): on GPU, _align_mqa_weights copies the weights into a buffer whose row stride is a multiple of 16 bytes, which DeepGEMM needs (deepinfer/model_executor/models/v4_modules/index_attn.py:40-53).
  4. Load all index keys of the batch from ica_cache into one buffer, in the same order as the main compressed keys (load_segments_ca) (deepinfer/model_executor/models/v4_modules/index_attn.py:181-191).
  5. For each chunk of queries: deep_gemm.fp8_fp4_mqa_logits(q, kv, weights, ks, ke, max_seqlen_k=L) gives p_sum (deepinfer/model_executor/models/v4_modules/index_attn.py:298-306). ks[t] and ke[t] are the start and end of the keys of query t in the gathered buffer (deepinfer/model_executor/input_metadata/input_metadata.py:280-287).
  6. Select: topk(..., end=klen, output_idx_offset=ks), with klen = ke − ks (deepinfer/model_executor/input_metadata/input_metadata.py:368-369).

Worked example: the chunk size. max_model_len = 32768 gives runtime_max_model_len = 32768 + 5 + 6 + 5 = 32784 with 5 drafts and ZOS on, as EngineArgs sets it (deepinfer/config.py:11-16; see engine/llm_engine.py: the LLMEngine class). In a C2 layer, L = 32784 // 2 = 16392. One score row is 16392 × 2 B = 32,784 B. With the default limit of 10 GiB (deepinfer/environ.py:126):

compute_chunk_size = min(8192, 10 * 2**30 // 32784 // 8 * 8)
                   = min(8192, 327520) = 8192
p_sum per chunk    = 8192 rows * 32784 B = 268,566,528 B  (about 256 MiB)

A prefill of 20,000 tokens therefore runs 3 chunks: 8192 + 8192 + 3616 rows.

Deep dive

Decode, step by step, with a worked example

  1. Schedule metadata (line 470): deep_gemm.get_paged_mqa_logits_metadata, made once per compress ratio and step, by the first indexer layer that needs it (deepinfer/model_executor/models/v4_modules/index_attn.py:389-397).
  2. Scores: deep_gemm.fp8_fp4_paged_mqa_logits reads the FP4 keys from ica_cache through block_tables (deepinfer/model_executor/models/v4_modules/index_attn.py:433-445).
  3. Select: topk(p_sum, topk_tokens, end=topk_lens, ...) returns logical positions inside the sequence (deepinfer/model_executor/models/v4_modules/index_attn.py:494-503).
  4. Map to slots: convert_kv_index rewrites the list in place (deepinfer/model_executor/models/v4_modules/index_attn.py:508-513).

The reference function shows the mapping exactly:

Worked example. C2 layer, so a block holds 128 / 2 = 64 compressed entries. A query selected logical entry 130. Its sequence has block_tables row [7, 3, 12, …].

  • logical block = 130 // 64 = 2, offset = 130 % 64 = 2;
  • physical block = block_tables[2] = 12;
  • slot = 12 × 64 + 2 = 770.

Lines 50-51 of the reference set every list position at or after context_lens to −1. DeepInfer passes topk_lens there, so a short sequence with fewer valid entries than index_topk gets −1 in the rest of its row.

Deep dive

Candidate blocks: a coarse first choice that later layers reuse

The config can name one candidate source layer (candidate_source_layer_id). Every later main layer then uses its candidates (deepinfer/hugging_face/config.py:76-84).

  1. The source layer computes its full p_sum. It cuts each row into blocks of candidate_block_size keys (8 or 16), and gives each block the score of its best key. The last valid block gets +inf, so it is always kept (deepinfer/model_executor/layers/tilelang_ops/candidate_blocks.py:17-36).
  2. topk keeps candidate_topk_blocks blocks per query in block_candidate_idxs (deepinfer/model_executor/models/v4_modules/index_attn.py:204-226).
  3. Later layers in the group compute scores only for the tokens of these blocks, with the "sparse" DeepGEMM kernels (fp8_fp4_sparse_mqa_logits, fp8_fp4_paged_sparse_mqa_logits) (deepinfer/model_executor/models/v4_modules/index_attn.py:317-325, deepinfer/model_executor/models/v4_modules/index_attn.py:447-454).
  4. restore_candidate_indices_inplace turns the compact positions back into sequence positions (deepinfer/model_executor/models/v4_modules/index_attn.py:373-374).

The topology checks that the candidates can hold enough tokens: candidate_topk_blocks × block size ≥ index_topk of each consumer (deepinfer/model_executor/models/v4_modules/cross_layer.py:237-238). Consumers must also have at most 32 index heads and index_head_dim == 128 (deepinfer/model_executor/models/v4_modules/index_attn.py:103).

Deep dive

Sharing between layers: index source, index-K source

Three maps from the config control sharing (deepinfer/hugging_face/config.py:71-75):

  • Index source (index_source_layer_ids): a consumer layer has no indexer and reuses cross_layer_runtime.topk_indices (deepinfer/model_executor/models/v4_modules/attn.py:568-570).
  • Index-K source (index_k_source_layer_ids, default: the KV sources): a consumer has its own index Q and weights, but reads the ica_cache of its source. In decode it uses the cache view of the source layer (deepinfer/worker/cache_engine.py:429-431). In prefill it reuses the loaded buffer (deepinfer/model_executor/models/v4_modules/index_attn.py:193-196).
  • The index-topk segments must lie inside the index-K segments, which must lie inside the KV segments (deepinfer/model_executor/models/v4_modules/cross_layer.py:191-197).

The page Cross-layer KV sharing explains the maps.

What can go wrong#

Always pass end to topk

The score buffer of a decode step is not cleared. Old values stay after the valid keys of a row. The comment says: "We must pass end to the topk kernel since OOB p_sum is not cleaned" (deepinfer/model_executor/models/v4_modules/index_attn.py:498). A change that drops end selects stale keys with no error.

  • Memory limit too small. If DEEPINFER_INDEX_ATTN_MEMORY_LIMIT is below 8 score rows, start-up stops with an assert that names the minimum (deepinfer/model_executor/models/v4_modules/index_attn.py:117-118).
  • Wrong indexer variant. Only use_kproj=True is supported (deepinfer/model_executor/models/v4_modules/mla_attn.py:272); mlp_kproj raises an assert (deepinfer/model_executor/models/v4_modules/mla_attn.py:123).
  • Sparse layer without SWA. A sparse layer must also have the sliding window (deepinfer/model_executor/models/v4_modules/attn.py:95-96).
  • Different head counts. Two indexer layers with different index_n_heads fail an assert (deepinfer/model_executor/model_metadata_utils.py:71-73).
  • Few keys. Not an error: a query with fewer valid keys than index_topk gets −1 entries. The metadata docs define −1 as an invalid entry (deepinfer/model_executor/input_metadata/input_metadata.py:241-242).

Why it matters. With the indexer, the cost of the main attention per query has a fixed upper limit: the window plus index_topk keys. The indexer itself still scores every compressed key, but with FP4 numbers and no softmax. This makes long contexts affordable.

Check yourself#

  1. 1
    How many compressed keys does the main attention read for one query in a sparse layer, at most?
    easy
    Show answer

    index_topk compressed keys, plus the keys of its sliding window. The top-k list has shape [T, index_topk], and −1 marks missing keys (deepinfer/model_executor/models/v4_modules/index_attn.py:541-544).

  2. 2
    The index key is not a separate projection of the hidden state. Where does it come from?
    medium
    Show answer

    From the compressed entry before RoPE, pre_rope_kv, that the Compressor returns. KProject maps it to index_head_dim values; then norm, RoPE and FP4 cast store it in ica_cache (deepinfer/model_executor/models/v4_modules/attn.py:544-557, deepinfer/model_executor/models/v4_modules/index_attn.py:133-162).

  3. 3
    In decode, why does _topk_decode call convert_kv_index, and why does prefill not need it?
    medium
    Show answer

    In decode the attention kernel reads the paged ca_cache, so it needs physical slots. topk returns logical positions, and convert_kv_index maps them through block_tables. In prefill the kernel reads the gathered BF16 buffer, and output_idx_offset=ks already gives rows of that buffer (deepinfer/model_executor/models/v4_modules/index_attn.py:361-372).

  4. 4
    C2 layer, decode. A query selects logical entry 200. The block table row of its sequence is [4, 9, 2, 6]. Which slot does the attention read?
    hard
    Show answer

    A C2 block holds 128 / 2 = 64 entries. 200 // 64 = 3, 200 % 64 = 8. block_tables[3] = 6, so the slot is 6 × 64 + 8 = 392 (deepinfer/model_executor/layers/tilelang_ops/flash_mla_utils.py:47-49). This is in the deep dive "Decode, step by step".

  5. 5
    You set max_model_len = 1,048,576 and keep the defaults. What is compute_chunk_size for a C2 layer without candidates?
    hard
    Show answer

    runtime_max_model_len = 1,048,576 + 5 + 6 + 5 = 1,048,592 with ZOS on (deepinfer/config.py:11-16). L = 524,296, so one row is 1,048,592 B. 10 GiB // 1,048,592 = 10,239; // 8 × 8 = 10,232. min(8192, 10232) = 8192 (deepinfer/model_executor/models/v4_modules/index_attn.py:111, deepinfer/model_executor/models/v4_modules/index_attn.py:117). One chunk of scores then uses about 8 GiB.

Related pages

  • MLA attention: one latent vector per tokenIn DeepInfer's MLA, all query heads of a layer read one 512-value vector per token. This vector is the key and also the value, so the KV cache keeps one small entry per token.
  • KV compression (C1 and C2)A compressed layer stores one 512-value cache entry per token (C1) or per 2 tokens (C2). C2 mixes the two tokens with a learned softmax gate and keeps the score and latent of the most recent tokens in a small fp32 state ring. Entries are FP4 (288 B) by default, or FP8 (528 B).
  • Cross-layer KV sharingA layer can reuse the compressed KV, the indexer keys or the top-k list of an earlier source layer. SharedLayerTopology turns three lists of source layers from config.json into checked segment maps; the cache engine then allocates the compressed-KV and index-K caches only for source layers.
  • Sliding-window attentionEvery attention layer of DeepSeek-V4.1-Flash reads the most recent tokens (a window of 128 in the docs) from a ring of 134 slots per sequence and layer. This page shows the ring, the decode and prefill index paths, and how the window joins the compressed keys.
  • Paged KV cache and block managerThe engine side of the paged KV cache. Two C++ BlockManager objects hand out KV blocks and state slots, the scheduler decides when, and C++ code turns block tables into index tensors for the kernels.
  • v4_modules/index_attn.py: the sparse-attention indexerindex_attn.py holds the class MQA. It stores the FP4 index keys, scores every compressed key for each query with DeepGEMM, and selects the top-k keys with DeepSelect, in prefill and in decode, with optional candidate blocks.
  • v4_modules/attn.py: the MLA attention runtimeattn.py turns the MLA weight container into runtime weights and runs one attention layer per call: projections, sliding-window and compressed KV stores, the indexer, the FlashMLA kernel and the output projection. It also holds the DFlash draft attention.
