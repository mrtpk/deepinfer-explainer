Hardware platforms: NVIDIA and Ascend

IntermediateDeepInfer conceptsabout 10 min read + 14 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • GPUs, kernels, and speed Beginner
  • Parallelism basics Beginner
  • Mixture of Experts (MoE) Beginner

In one sentence

At start-up, DeepInfer checks the device files of the machine and makes one Platform object for NVIDIA or for Ascend. All shared code reads its hardware choices from that object.

The idea#

DeepInfer supports two kinds of accelerators: NVIDIA SM100 GPUs and Huawei Ascend 950 NPUs (README.md:33-36). The two chips need different software:

  • NVIDIA uses CUDA. Ascend uses CANN and the PyTorch plug-in torch_npu.
  • NVIDIA GPUs talk to each other with NCCL. Ascend NPUs use HCCL.
  • Each chip needs its own kernels: the small programs that do the math on the device.

Most of DeepInfer is the same for both chips: the scheduler, the model code, the sampler and the engine loop. Only a small number of places are different. DeepInfer collects those places in one object, the Platform object, in deepinfer/platform.py.

An everyday comparison. Think of a travel plug adapter. Your laptop is the same in every country. Only the adapter changes. You choose the adapter once, when you arrive, and not each time you use the laptop. In DeepInfer, the shared code is the laptop. The Platform object is the adapter. DeepInfer chooses it once per process, at start-up.

The work has three steps:

  1. Detect. The deep_cluster package looks for device files such as /dev/davinci0 or /dev/nvidia0. It does not import PyTorch.
  2. Choose. get_platform() makes a PlatformNPU on Ascend and a PlatformGPU in all other cases.
  3. Use. Shared code reads names such as PLATFORM.distributed_backend. A kernel dispatcher loads the kernel folder for the chosen hardware.

One process uses one platform. One deployment uses one hardware type. The last part of this page explains why DeepInfer is therefore not an AFD system.

In the code#

Step 1: detect the hardware without PyTorch#

accelerator_kind() returns "ascend", "nvidia" or "cpu". It only looks at files. It checks Ascend first.

The Ascend check looks for /dev/davinci_manager, for /dev/davinci<N> files, or for UB devices in /sys/class/ubcore (deep_cluster/hardware/ascend.py:61-68). The NVIDIA check looks for folders in /proc/driver/nvidia/gpus or for /dev/nvidia<N> files (deep_cluster/hardware/nvidia.py:40-48). The page Hardware discovery (deep_cluster) explains this package in full.

Step 2: make the Platform object, once#

Code does not call get_platform() directly. It writes from deepinfer import PLATFORM. The package makes this name on first use, with a module-level __getattr__:

The first line of deepinfer/__init__.py is a rule in Chinese. Translated: "It is strictly forbidden to import torch or to initialize a device in this file in any form. It causes failures in child processes." (deepinfer/__init__.py:1). The lazy PLATFORM follows this rule: import deepinfer does not import PyTorch.

The base class Platform lists four names that every platform must set (deepinfer/platform.py:19-27). The NVIDIA class is short:

Deep dive#

Deep dive

accelerator_kind(): the exact detection rules

The function is in deep_cluster/hardware/device.py. It has a keyword-only parameter _root (default Path("/")). Tests use it to point the checks at a fake file tree.

  1. Line 62: /dev/davinci_manager exists, or at least one /dev/davinci<N> file exists (_DAVINCI_PATTERN, deep_cluster/hardware/ascend.py:13).
  2. Lines 64-67: else, for each udma* entry in /sys/class/ubcore, read device/ub_totalues. A value above 0 means Ascend.

Order and edge cases.

  • Ascend is checked first (deep_cluster/hardware/device.py:19-20). A host with both kinds of device files is treated as Ascend.
  • No device files: the result is "cpu". get_platform() then makes a PlatformGPU (deepinfer/platform.py:226). PlatformGPU() itself does not check for a GPU (deepinfer/platform.py:60-63). The first real CUDA call fails later.
  • The result is cached with @functools.cache (deep_cluster/hardware/device.py:17). Device files are read once per process.
  • ascend.py also has a module constant IS_NPU that checks only /dev/davinci_manager (deep_cluster/hardware/ascend.py:153). get_platform() does not use it.

Related helpers in the same file. visible_device_env_name() returns "ASCEND_RT_VISIBLE_DEVICES", "CUDA_VISIBLE_DEVICES", or None when it finds no accelerator (deep_cluster/hardware/device.py:36-43). get_bf16_tflops_limit() returns a peak BF16 speed in TFLOPS: 432 on Ascend, 2250 on x86 SM100 hosts and 2500 on Arm SM100 hosts (deep_cluster/hardware/device.py:151-156). All other hosts raise RuntimeError("unknown GPU type") there: an NVIDIA GPU that is not compute capability 10.x, or a host with no accelerator (deep_cluster/hardware/device.py:159-164).

Deep dive

Pinned host memory on both platforms

DeepInfer keeps a large shared-memory buffer for data that goes from the CPU to the device. The buffer is pinned so that copies can use DMA:

NVIDIA. cudaHostRegister(ptr, nbytes, 0) through torch.cuda.cudart() (deepinfer/platform.py:65-73).

Ascend. torch_npu has no such call, so DeepInfer loads libascendcl.so with ctypes:

  • The flag _ACL_HOST_REG_PINNED = 0x10000000 asks for pinned memory (line 158).
  • Error 507910 (already registered) on pin and 507911 (not registered) on unpin are ignored. All other errors give a warning, not an exception (lines 202-207 here; deepinfer/platform.py:215-219 for unpin). The copy then uses the slow pageable path.
  • The ACL device context is per thread. Without it, a bare register call fails with error 107002. So each call first runs torch.npu.set_device(torch.npu.current_device()) (lines 186-193).
  • If the driver is too old and the functions are missing, start-up stops with RuntimeError (lines 169-178).

The base class has empty pin_host_memory and unpin_host_memory methods. A future platform that cannot pin memory still works, with slower copies (deepinfer/platform.py:37-49).

Deep dive

Communication: backends, options and SM limits

Start-up first joins all ranks with a CPU-only Gloo group (deepinfer/worker/base.py:334-340). Then create_process_groups makes the device groups. Every device group uses the same backend:

NCCL options. PlatformGPU.get_distributed_options() sets config.max_ctas and config.min_ctas to DEEPINFER_NCCL_NUM_SMS (deepinfer/platform.py:75-83). The default is 32 (deepinfer/environ.py:108). A CTA is one thread block, and one CTA runs on one SM. So this value sets how many SMs an NCCL operation uses. The other SMs stay free for compute kernels that run at the same time.

HCCL options. PlatformNPU.get_distributed_options() returns a default ProcessGroupHCCL.Options() (deepinfer/platform.py:145-149). The HCCL settings come from the HCCL_* environment variables in the constructor.

Other platform checks in this area.

  • is_within_nvl_domain() always returns True on NPU. On GPU it asks DeepEP for the size of the NVLink domain (deepinfer/model_executor/parallel_utils/parallel_state.py:130-134).
  • EPLB moves expert weights through symm_mem only on GPU. The comment says: NPU doesn't support symm_mem yet (deepinfer/model_executor/eplb/__init__.py:199-200).
  • The NVIDIA build script installs NCCL 2.32.3 over the version that comes with PyTorch (build.sh:16-19).
Deep dive

The kernel dispatcher ops.py, line by line

  1. Line 13. from deepinfer import PLATFORM makes the platform if it does not exist yet.
  2. Line 15. Imports ...tilelang_ops.cuda or ...tilelang_ops.asc.
  3. Lines 16-17. pkgutil.iter_modules lists every module in that folder, and each one is imported. An import only defines the factories. Most kernel factories use the @tilelang.jit decorator. They compile a kernel when they are called, not at import.
  4. Lines 18-20. Keeps only public names that end in _tl and are not modules.
  5. Line 21. If two modules define the same _tl name with different objects, an assert fails with the message backend symbol collision, so the import fails.
  6. Line 22. Copies the factory into the namespace of ops. Callers then write ops.name_tl.
  7. Lines 25-32. Python calls a module-level __getattr__ only when normal lookup fails (PEP 562). So ops.unknown_tl raises KernelUnavailableError. It is a subclass of AttributeError, so hasattr(ops, "x_tl") still returns False.

Coverage. At this commit, cuda/ exports 43 _tl factories and asc/ exports 42. The one that exists only on CUDA is detect_outlier_and_abort_tl, a debug check (deepinfer/model_executor/layers/tilelang_ops/outlier_detection.py:10-26). Kernel tests turn KernelUnavailableError into a skip on non-NVIDIA hosts (deepinfer/model_executor/layers/tilelang_ops/conftest.py:100-113).

The same kernel, two versions. Both files below define expand_swa_index_tl(width). They take the same tensors: int32 pivots of shape [n, 4] and int32 output of shape [n, width] (deepinfer/model_executor/layers/tilelang_ops/swa_index.py:10-22). The way they split the work is different:

Deep dive

fp8_sf_type: why int32 on NVIDIA and int16 on Ascend

DeepInfer stores many weights and activations in FP8. Each block of FP8 values has a scale factor. One common scale format is UE8M0: an 8-bit exponent with no sign and no mantissa, so one scale uses one byte. DeepInfer packs several one-byte scales into one integer. The integer type is PLATFORM.fp8_sf_type:

So on NVIDIA one int32 holds 4 scales. On Ascend one int16 holds 2 scales. The pack factor is simply fp8_sf_type.itemsize:

A worked example: a row has d_scale = 8 scales. On NVIDIA, the packed row-major tensor has shape (B, M, 2) in int32. On Ascend, it has shape (B, M, 4) in int16. Both use 8 bytes per row. Line 51 shows one more difference. On NVIDIA, the column-major layout pads M up to a multiple of 4. On Ascend, it does not pad.

Other code checks the type directly. The FP8 linear layer converts loaded weight scales if their type is not fp8_sf_type (deepinfer/model_executor/layers/linear.py:67-70). It asserts the type before each FP8 GEMM (deepinfer/model_executor/layers/linear.py:164). The KV cache sizes its scale tensor with the same type (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:244-248). The page Low-precision formats in DeepInfer explains the formats.

Deep dive

The npu_ops import hook in detail

patch_imports() replaces the built-in builtins.__import__ with its own function. It changes only statements of the form from X import a, b.

Step by step, for from deep_select.interface import topk on Ascend:

  1. Python calls _hooked_import("deep_select.interface", ..., fromlist=("topk",), level=0).
  2. _patch_map has {"deep_select.interface": {"topk": "deepinfer.npu_ops.deep_select.topk"}}, so the name is patched.
  3. The hook returns a new, empty module object. Its topk is a Lazy wrapper (deepinfer/npu_ops/patch_imports.py:33-52). The real NPU function loads only on the first call.
  4. Exception: deepinfer/npu_ops/deep_select.py itself imports topk from deep_select.interface. Because the caller is the source module, it gets the original vendor function (lines 86-89). Without this rule, the NPU version would call itself.
  5. Other names of the module go to the real module through the fake module's __getattr__ (line 92).

The hook does not change sys.modules, and patch_imports() can run only once (deepinfer/npu_ops/patch_imports.py:114-116). Its docstring is in Chinese. Translated: "Replace from dst.mod import name with a lazy src.mod.name. Only from-imports are intercepted; sys.modules is not faked. src loads only when the patched object is first used." (deepinfer/npu_ops/patch_imports.py:97-111).

The two replacements.

The vision encoder imports _flash_attn_fwd in deepinfer/model_executor/models/vision_encoder/vit.py:13. The ViT replacement calls torch_npu.npu_fusion_attention in "TND" layout, with no causal mask, and with scale 1/sqrt(head_dim) (deepinfer/npu_ops/vit_attn.py:9-31). Its docstring says, translated: "varlen attention for the ViT: not causal, full attention inside each segment." Both files carry a TODO(NPU): To be removed note.

Is DeepInfer AFD (Attention-FFN Disaggregation)?#

No. AFD runs the attention layers on one group of devices and the FFN or expert layers on another group. In every layer, hidden states go from the attention group to the FFN group and back. DeepInfer does not do this. There are four reasons in the code and docs.

  1. One hardware type per deployment. Each process makes its platform from its own device files. Every device process group then uses PLATFORM.distributed_backend, which is "nccl" or "hccl" (deepinfer/model_executor/parallel_utils/parallel_state.py:82-117). NCCL and HCCL are different libraries, and the code has no path that connects an NCCL group to an HCCL group. So all ranks of one job use the same hardware type.
  2. Attention and MoE run in the same layer, on the same device. DeepseekDecoderLayer.forward calls attention and then the MoE block, one after the other:
  3. MoE uses expert parallelism, not a separate pool. With expert parallelism, each device holds a part of the experts. DeepEP dispatch sends each token to the devices of its experts, and combine sends the results back (deepinfer/model_executor/models/v4_modules/mlp.py:461-511). Every one of these devices also runs attention, with data parallelism: "attention uses data parallelism (#DP = #EP)" (doc/inference_deployment_qa.md:33).
  4. The only split in the docs is E/P/D, and it is not in this release. The docs describe separate vision-encoder, prefill and decode instances (doc/inference_deployment_qa.md:31, doc/inference_deployment_qa.md:41-63). Each prefill or decode instance runs the whole language model, attention and MoE. A VE instance runs only the vision encoder, on one GPU (doc/inference_deployment_qa.md:51). The README lists "VE/Prefill/Decode disaggregation" under "not included in this release" (README.md:38-41). See E/P/D disaggregation.

Simplified

Point 1 is about one job. The docs say DeepInfer "runs on both NVIDIA and Huawei Ascend platforms" (doc/inference_deployment_qa.md:19). That means two separate deployments, one per hardware type, not one mixed job.

What can go wrong#

Visible-device mismatch on Ascend

If CUDA_VISIBLE_DEVICES is set and is not equal to ASCEND_RT_VISIBLE_DEVICES, start-up stops with RuntimeError (deepinfer/platform.py:101-102). This also happens when only CUDA_VISIBLE_DEVICES is set. Set both to the same value, or set only ASCEND_RT_VISIBLE_DEVICES.

  • Wrong .so folder. If DEEPINFER_ACCELERATOR is not exported on Ascend, the package looks in _so/nvidia-<arch>/. The import of deepinfer._C can then fail or find the wrong build. See the deep dive on the _so folder.
  • Platform made too early. On Ascend, the first access to PLATFORM starts the device runtime. It must happen after ASCEND_RT_VISIBLE_DEVICES is set (deepinfer/__init__.py:58-59). Do not touch deepinfer.PLATFORM in code that runs before the worker sets its devices.
  • torch in deepinfer/__init__.py. The package rule forbids it, because it breaks child processes (deepinfer/__init__.py:1).
  • Missing kernel on one platform. A call to a factory that the backend does not have raises KernelUnavailableError (deepinfer/model_executor/layers/tilelang_ops/ops.py:31-32).
  • Old Ascend driver. If libascendcl.so has no aclrtHostRegisterV2, start-up stops with RuntimeError (deepinfer/platform.py:169-178).
  • Slow copies, no error. A failed pin only gives a warning. Copies from shared memory then use the slow pageable path (deepinfer/platform.py:202-207). Look for "aclrtHostRegisterV2 ... failed" in the logs.
  • No accelerator. On a machine with no device files, DeepInfer still makes a PlatformGPU. The error comes later, at the first CUDA call.

Why it matters. The Platform object keeps vendor checks out of most of the code. To read the model or the scheduler, you can ignore the hardware. A third hardware type needs a Platform subclass, a kernel folder next to cuda/ and asc/, and a build branch in setup.py.

Check yourself#

  1. 1
    Which function decides between NVIDIA and Ascend? Does it import PyTorch?
    easy
    Show answer

    accelerator_kind() in deep_cluster/hardware/device.py. It does not import PyTorch. It only checks device files, such as /dev/davinci_manager and /proc/driver/nvidia/gpus.

  2. 2
    What is the value of PLATFORM.distributed_backend in an Ascend process?
    easy
    Show answer

    "hccl" (deepinfer/platform.py:89). On NVIDIA it is "nccl".

  3. 3
    An interface file calls ops.expand_swa_index_tl(width). On Ascend, which file has the kernel code? Which file makes that choice?
    medium
    Show answer

    The code is in tilelang_ops/asc/swa_index.py. The choice is in tilelang_ops/ops.py, line 15: it imports the subpackage named by PLATFORM.tilelang_ops_backend, which is "asc". (tilelang_ops/__init__.py is empty.)

  4. 4
    On an Ascend host, CUDA_VISIBLE_DEVICES=0,1 is set and ASCEND_RT_VISIBLE_DEVICES is not set. What happens when the process makes the platform?
    medium
    Show answer

    RuntimeError. The first branch needs CUDA_VISIBLE_DEVICES to be unset. The second branch compares "0,1" with None, and they are not equal (deepinfer/platform.py:94-102).

  5. 5
    Can one DeepInfer job use 8 NVIDIA GPUs for attention and 8 Ascend NPUs for the MoE experts? Give two reasons from the code.
    hard
    Show answer

    No. (1) All device process groups use one backend from PLATFORM.distributed_backend, NCCL or HCCL, and the code cannot connect the two. (2) DeepseekDecoderLayer.forward runs attention and the MoE block one after the other on the same device. Expert parallelism moves tokens between devices that all run attention too. It does not put the experts on a separate pool. (Also: E/P/D disaggregation is not in this release.)

  • Expert parallelism: dispatch, grouped GEMM, combineDeepInfer splits the expert slots of every MoE layer evenly over the EP ranks. DeepEP dispatch sends each token to the ranks of its experts, DeepGEMM runs grouped GEMMs there, and DeepEP combine brings the results back.
  • Low-precision formats in DeepInferDeepInfer keeps most weights in FP8 E4M3 with 32 × 32 block scales, routed experts in MXFP4, activations in FP8 with one scale per 32 values, the compressed KV in FP4 and the window KV in MXFP8. Scales are UE8M0 bytes, packed 4 per int32 on NVIDIA and 2 per int16 on Ascend.
