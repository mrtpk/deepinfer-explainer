MLA attention: one latent vector per token

AdvancedDeepInfer conceptsabout 10 min read + 8 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Attention, step by step Beginner
  • The KV cache Beginner
  • Model map: DeepSeek-V4.1-Flash in DeepInfer Intermediate

In one sentence

All query heads of an MLA layer read one 512-value vector per token. This vector is the key and also the value.

The idea#

In standard attention, each attention head makes its own key and its own value for every token. The KV cache must keep all of them: 2 × heads × head_dim numbers per token and layer. The page The KV cache shows how fast this grows.

MLA (Multi-head Latent Attention) keeps less. The model first squeezes the hidden state of a token into one small latent vector. The cache keeps only this vector. All query heads then read the same vector.

DeepSeek-V4.1 in DeepInfer takes this idea to its simplest form:

  • The latent vector has 512 values. The cache code asserts this number (deepinfer/worker/cache_engine.py:53-54).
  • The 512 values are the key and the value for every head. So the layer is MQA: many query heads, one key/value head (deepinfer/model_executor/models/v4_modules/mla_attn.py:175-176).
  • Each query head also has 512 values, so a query and a key have the same size.
  • The last values of the vector carry the token position, with RoPE. The first values carry no position.
  • The queries and the output use low-rank projections: a matrix to a small size, then a matrix back to a large size.

An everyday comparison. Think of a reading room with one summary card for each book. Many readers (the heads) come with their own questions (the queries). They all read the same card. The room keeps one card per book, not one card per reader. The comparison stops here. In DeepInfer, part of the card also records where the book stands on the shelf (RoPE). Also, the readers combine their notes in groups before they report.

In DeepInfer, an attention layer can read the keys below. All of them are vectors of the same 512 values:

  1. the sliding window: the most recent tokens, one vector each;
  2. the compressed keys: one vector per token (C1) or per 2 tokens (C2), see KV compression (C1 and C2);
  3. in sparse layers, only a selected subset of the compressed keys, see Sparse attention with an indexer.

In the code#

Two files hold MLA. The parameter container mla_attn.py allocates the weights. The runtime file attn.py owns the forward. The file roles are listed in deepinfer/model_executor/models/v4_modules/__init__.py:6-20.

Step 1: the weights of one layer#

The container class is LoraRopeCompressFlashMHAAutoRecomp. The query projection Wq is low-rank: A maps the hidden state to q_lora_rank values, an RMSNorm normalizes them, and B maps them to all heads.

The KV projection Wkv has only an A part (out_features is 0). Its output has kv_lora_rank + qk_rope_head_dim values for one head. That is the 512-value vector.

The HF loader sets kv_lora_rank = head_dim − qk_rope_head_dim. The comment says: "HF's shared KV vector includes RoPE; the internal rank excludes it" (deepinfer/hugging_face/config.py:287-289). So head_dim in the config is the full 512.

Step 2: the runtime merges projections#

V4Attention joins weights that read the same input into one matrix. Then one GEMM makes all the outputs. Wq.A and Wkv.A both read the hidden state, so they become one projection:

In a YOCO consumer layer with yoco_swa_share_hidden, the two inputs differ, so the merge is off (line 280). The HF loader sets yoco_swa_share_hidden to False by default (deepinfer/hugging_face/config.py:47).

Step 3: the query and the sliding-window KV#

The first q_lora_rank values are the query latent q_a. The next qk_head_dim (512) values are kv_swa, the KV vector of the current token for the sliding window. Then the query goes up to all heads:

_q_b_norm_rope applies RoPE to the last qk_rope_head_dim values of each head: the offset is qk_head_dim − qk_rope_head_dim (deepinfer/model_executor/models/v4_modules/attn.py:161-171). The same function can also normalize each head, but the HF loader sets use_qnorm to False (deepinfer/hugging_face/config.py:44).

The SWA vector goes through one fused kernel: RMSNorm, RoPE, cast to FP8 with one UE8M0 scale per 32 values. In decode the kernel writes the result straight into swa_cache. In prefill it returns a BF16 copy of the cast values (cast_back=True), so the attention sees the same numbers that the cache keeps (deepinfer/model_executor/models/v4_modules/attn.py:412-445).

Step 4: the compressed KV#

A layer with a compress ratio of 1 or 2 also makes compressed keys. A second projection reads the BF16 hidden state. The Compressor turns its output into one 512-value entry per token (C1) or per 2 tokens (C2), and stores the entry in ca_cache:

The page KV compression (C1 and C2) explains the compression. For MLA, only one fact matters: a compressed entry holds the same 512 values as a sliding-window entry. Only the number format can differ. The sliding-window cache is FP8. The compressed cache is FP4 by default (deep dive "FP8 flags and number formats"). So one kernel call can read both caches.

Step 5: the attention kernels#

Head count: 64 or 128

FlashMLA accepts only 64 or 128 query heads. DeepInfer pads other counts with zero heads, and a count above 128 raises ValueError (deepinfer/model_executor/layers/attention_backend.py:5, deepinfer/model_executor/layers/attention_backend.py:8-23).

Prefill and decode call different wrappers in layers/attention_backend.py. Prefill builds one BF16 buffer with all keys that the step needs, and one index list per query:

Decode does not build a buffer. It passes the two caches and two index lists. The kernel reads the quantized entries (FP8 in swa_cache, FP4 or FP8 in ca_cache) from the caches:

Both calls pass attn_sink=self.attn_sink_params: one attention sink value per head (deepinfer/model_executor/models/v4_modules/attn.py:269-271). Both use softmax_scale = qk_head_dim ** -0.5 = 512−0.5 ≈ 0.0442 (deepinfer/model_executor/models/v4_modules/attn.py:78).

Step 6: back to the hidden size#

  1. Line 193: the output of each head is a weighted sum of 512-value vectors, so its last values still carry RoPE. The code applies RoPE again with conjugate=True at the query position.
  2. Lines 194-202: the output is cast to FP8 (if the fused kernel did not do it already) and viewed as [T, o_groups, heads_per_group × 512].
  3. Lines 215-221: deep_gemm.fp8_einsum("bhr,hdr->bhd", ...) projects each group to o_lora_rank values.
  4. Line 225: out_proj maps o_groups × o_lora_rank values back to the hidden size.

Which sizes are fixed by the code.

  • D = kv_lora_rank + R = 512: the cache format asserts it (deepinfer/worker/cache_engine.py:46-56, deepinfer/model_executor/layers/tilelang_ops/cache_common.py:109-118).
  • R = 64 in a model with indexer layers. The indexer asserts rope_dim == 64 (deepinfer/model_executor/models/v4_modules/mla_attn.py:115, deepinfer/model_executor/models/v4_modules/mla_attn.py:121), and the HF loader gives the indexer the same qk_rope_head_dim as the main attention (deepinfer/hugging_face/config.py:127). Then kv_lora_rank = 512 − 64 = 448.
  • H is 64 or 128 for FlashMLA without padding (deepinfer/model_executor/layers/attention_backend.py:5).
  • H must be a multiple of G (deepinfer/model_executor/models/v4_modules/mla_attn.py:222-223).

H, rq, G, ro and the window are config values. They are not in the repo.

Deep dive

Worked example: bytes per token, and one decode step

Cache bytes. One sliding-window entry is 512 FP8 values plus 16 UE8M0 scales = 528 B. A compressed entry is 528 B in MXFP8 or 288 B in FP4 (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:109-128). The HF loader turns FP4 on unless the config says otherwise (use_fp4_sparse_kv, default True, deepinfer/hugging_face/config.py:302-303).

Compare a classic multi-head layer with the same query size: 64 heads, separate K and V of 512 values each, in BF16. One token needs 2 × 64 × 512 × 2 B = 131,072 B per layer. DeepInfer's SWA entry needs 528 B: about 248 times less.

Simplified

The comparison model is made up. It only shows the effect of "one KV head, one vector for K and V". The real head count of V4.1 is in config.json, not in the repo.

One decode step. 32 sequences, each with 1 new token and 5 draft tokens (the default DEEPINFER_USE_NEXTN_DECODE = 5), give T = 192.

  1. _prepare_swa_kv writes 192 SWA entries: 192 × 528 = 101,376 B for this layer (deepinfer/model_executor/models/v4_modules/attn.py:421-432).
  2. A C2 layer writes about one compressed entry per 2 tokens of each sequence into ca_cache.
  3. decode_mla_mqa_sparse gets q bf16 [192, H, 512], kv_swa_index int32 [192, window] and kv_ca_index int32 [192, topk].
  4. Each query reads at most window + topk entries, whatever the length of the sequence.
Deep dive

Why the output gets a second RoPE

The value of a key is the same 512-value vector as the key. Its last R values were turned by RoPE at the key position j. The output of a head is a weighted sum of such vectors. Line 193 turns the last R output values back by the query position i (conjugate=True):

A rotation by j and a rotation by −i give a rotation by j − i. So the RoPE part of the output depends on the distance between the two tokens, not on the absolute position.

Simplified

The reason above is the general property of rotations. The repo does not state the design reason. When the fused kernel runs, this step happens inside FlashMLA: the name fused_norm_rope_attn_rope_cast lists "rope" two times, and line 192 skips the Python step.

The decode wrapper passes head_dim_v = qk_head_dim (deepinfer/model_executor/models/v4_modules/attn.py:662). So the value size is 512, the full vector.

Deep dive

The kernels: wrappers, arguments, head padding, fused path

layers/attention_backend.py wraps four FlashMLA entry points: flash_mla_sparse_fwd, flash_mla_with_kvcache and fused_norm_rope_attn_rope_cast.prefill / .decode (deepinfer/model_executor/layers/attention_backend.py:1-3). This site does not explain their insides.

  1. Line 124: the query gets a sequence axis of 1 and maybe zero heads (padding to 64 or 128).
  2. Line 133: causal=False. Translated comment: "sparse attention supports only non-causal." The index lists already contain only the keys that a query may see.
  3. Line 134: is_fp8_kvcache=True. Translated comment: "the V4.1 KV cache is paged FP8."
  4. Lines 137-140: the extra_* arguments carry the second cache (ca_cache) and its index list.
  5. Lines 143-145: the padded heads are cut off again.

The fused path. use_fused_norm_rope_attn_rope_cast is true when all three conditions are true (deepinfer/model_executor/models/v4_modules/attn.py:87-92):

  1. The platform is GPU.
  2. The layer has 64 or 128 query heads.
  3. The layer is sparse, or it has no compressed KV, or the engine is a PROMPT engine without batch invariance.

Then:

  • the q_b weight rows are permuted once at start-up (deepinfer/model_executor/models/v4_modules/attn.py:111-120);
  • the query goes into the kernel before norm and RoPE (_q_b_norm_rope returns it unchanged, line 160);
  • the kernel returns (fp8, scales) with 32 values per scale, so _wv_and_o_proj skips its own cast (deepinfer/model_executor/models/v4_modules/attn.py:174-189).

Scheduler metadata. Decode passes flash_mla_sched_meta_dict[self.sched_meta_key]. The key is "{ratio}_{has_packed_kv}_{use_swa}_{index_topk}" (deepinfer/model_executor/models/v4_modules/attn.py:241). Layers with the same key share one FlashMLASchedMeta object, made on first access (deepinfer/model_executor/input_metadata/input_metadata.py:388-389).

Batch invariance. DEEPINFER_BATCH_INVARIANT (default off, deepinfer/environ.py:197) goes to the decode kernel as batch_invariant (deepinfer/model_executor/models/v4_modules/attn.py:666). See Determinism and batch invariance.

Deep dive

Attention sinks

The container makes one fp32 value per head, attn_sink_params, when attn_sink_init_value is set (deepinfer/model_executor/models/v4_modules/mla_attn.py:285-292). The HF loader sets attn_sink_init_value=0 for every layer kind (deepinfer/hugging_face/config.py:103, deepinfer/hugging_face/config.py:114), so every layer has sinks. The checkpoint gives the real values.

When the wrapper pads the heads, it pads the sinks with zeros too (deepinfer/model_executor/layers/attention_backend.py:21-22). The runtime also asserts sink_mode == "swa" (deepinfer/model_executor/models/v4_modules/attn.py:270).

Simplified

The glossary meaning of a sink (one extra score per head with no value) is the usual meaning of the term. How FlashMLA uses the value is inside the vendor library and not shown here.

Deep dive

RoPE details: which table, which values

  • One rotary table per layer. Layers with compressed KV use compress_rope_theta; SWA-only layers use rope_theta (deepinfer/model_executor/models/v4_modules/mla_attn.py:275-280). So in a compressed layer the SWA keys use compress_rope_theta too.
  • Compressed layers use YaRN scaling when the config has rope_scaling (deepinfer/hugging_face/config.py:130-131).
  • The container asserts rope_interleaved (deepinfer/model_executor/models/v4_modules/mla_attn.py:193).
  • RoPE always acts on the last R values: offset = qk_head_dim − qk_rope_head_dim (deepinfer/model_executor/models/v4_modules/attn.py:441).
  • Compressed entries use their own positions, positions_c (deepinfer/model_executor/models/v4_modules/compress.py:144).

What can go wrong#

Most problems are config checks at start-up. They stop the load with an assert or an exception.

  • More than one KV head. The HF loader raises ValueError unless num_key_value_heads is 1 (deepinfer/hugging_face/config.py:55-57). The container asserts it again (deepinfer/model_executor/models/v4_modules/mla_attn.py:176).
  • Wrong vector size. If kv_lora_rank + qk_rope_head_dim is not 512, the cache engine asserts (deepinfer/worker/cache_engine.py:53-54).
  • Unsupported options. compress_overlap or use_ape raise ValueError (deepinfer/model_executor/models/v4_modules/mla_attn.py:170-171). The container also asserts a q LoRA rank, interleaved RoPE, no q-norm weight, no attention bias and FP8 attention (lines 192-196).
  • Too many heads. More than 128 query heads raise ValueError in the kernel wrapper (deepinfer/model_executor/layers/attention_backend.py:15-16). Head counts below 128 that are not 64 work, but the padded heads cost compute and the fused kernel is off.
  • Sink dtype. A checkpoint with non-fp32 sinks fails the assert in runtime_attn_sink (deepinfer/model_executor/models/v4_modules/mla_attn.py:298).
  • Merge alignment. FP8 weights that are merged must have a row count that is a multiple of 128, except the last one (deepinfer/model_executor/models/v4_modules/utils.py:53-55). For q_a_kv_swa_proj, q_lora_rank must be a multiple of 128.

Why it matters. The KV cache decides how many sequences fit on a device. DeepInfer keeps one 512-value vector per token, in FP8 or FP4. That is hundreds of times less KV data than a classic layer of the same query size. The price is a fixed format: many sizes in the config are not free choices.

Check yourself#

  1. 1
    How many KV heads does a DeepInfer attention layer have, and how many values does one cached key have?
    easy
    Show answer

    One KV head (deepinfer/model_executor/models/v4_modules/mla_attn.py:176). One key is a 512-value vector: kv_lora_rank + qk_rope_head_dim (deepinfer/worker/cache_engine.py:53-54). The same vector is also the value.

  2. 2
    Which two weight matrices does q_a_kv_swa_proj merge, and why can it merge them?
    medium
    Show answer

    Wq.A and Wkv.A (deepinfer/model_executor/models/v4_modules/attn.py:281-288). Both read the same input, the normalized hidden state, so one GEMM can make both outputs. The split at line 399 separates them. In a YOCO consumer layer with yoco_swa_share_hidden, the KV input is a different hidden state, so the merge is off.

  3. 3
    In prefill, what are the three parts of the BF16 buffer kv, in order?
    medium
    Show answer

    The sliding-window history loaded from swa_cache, the SWA KV of the current tokens, and the compressed KV loaded from ca_cache (deepinfer/model_executor/models/v4_modules/attn.py:813-857). Its shape is [total_kv, 1, 512].

  4. 4
    A config has head_dim = 512 and qk_rope_head_dim = 32, and every compressed layer has an indexer. Where does the load stop?
    hard
    Show answer

    The HF loader gives the indexer the same qk_rope_head_dim (deepinfer/hugging_face/config.py:127). MQAIndexer asserts rope_dim == 64 (deepinfer/model_executor/models/v4_modules/mla_attn.py:121), so building the first indexer fails. The cache check would pass, because 480 + 32 = 512. This is in the deep dive "Shapes at each step".

  5. 5
    Why does _wv_and_o_proj apply RoPE to the attention output, and when does it skip this step?
    hard
    Show answer

    The values are the keys, so the last R output values carry RoPE from the key positions. Line 193 turns them by the query position with conjugate=True, which leaves a rotation by the distance. It skips the step when the fused FlashMLA kernel runs, because the kernel does the second RoPE itself (deepinfer/model_executor/models/v4_modules/attn.py:192-193).

  • Sparse attention with an indexerIn a sparse layer, a small indexer scores all compressed keys for each query and keeps the best index_topk. The main attention then reads only those keys plus the sliding window.
  • Sliding-window attentionEvery attention layer of DeepSeek-V4.1-Flash reads the most recent tokens (a window of 128 in the docs) from a ring of 134 slots per sequence and layer. This page shows the ring, the decode and prefill index paths, and how the window joins the compressed keys.
  • KV compression (C1 and C2)A compressed layer stores one 512-value cache entry per token (C1) or per 2 tokens (C2). C2 mixes the two tokens with a learned softmax gate and keeps the score and latent of the most recent tokens in a small fp32 state ring. Entries are FP4 (288 B) by default, or FP8 (528 B).
  • Cross-layer KV sharingA layer can reuse the compressed KV, the indexer keys or the top-k list of an earlier source layer. SharedLayerTopology turns three lists of source layers from config.json into checked segment maps; the cache engine then allocates the compressed-KV and index-K caches only for source layers.
  • Low-precision formats in DeepInferDeepInfer keeps most weights in FP8 E4M3 with 32 × 32 block scales, routed experts in MXFP4, activations in FP8 with one scale per 32 values, the compressed KV in FP4 and the window KV in MXFP8. Scales are UE8M0 bytes, packed 4 per int32 on NVIDIA and 2 per int16 on Ascend.
  • v4_modules/attn.py: the MLA attention runtimeattn.py turns the MLA weight container into runtime weights and runs one attention layer per call: projections, sliding-window and compressed KV stores, the indexer, the FlashMLA kernel and the output projection. It also holds the DFlash draft attention.
  • v4_modules/mla_attn.py: the attention weight containersmla_attn.py allocates the weights of one attention layer with their Hugging Face names and shapes: the low-rank Q and KV projections, the compressor, the indexer, the grouped output projection and the attention sinks. It has no forward.
  • v4_modules/compress.py: the KV compressorcompress.py holds two small runtime classes. Compressor turns the projected KV of a C1 or C2 layer into compressed entries, stores them in ca_cache and returns the pre-RoPE vector for the indexer. KProject is the indexer's key projection of that vector.
