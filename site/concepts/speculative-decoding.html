Speculative decoding

IntermediateDeepInfer conceptsabout 11 min read + 9 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • The sampler Intermediate
  • Prefill and decode Beginner

In one sentence

A small draft model guesses the next 5 tokens. The main model checks all of them in one step, keeps a correct prefix and adds one token of its own.

The idea#

A normal decode step makes one token per request. For that one token, the device reads all weights of the model. In a decode step, the device spends most of the time on these reads, not on math. So the step can process a few more tokens per request for a small extra cost.

Speculative decoding uses this. It has four parts:

  1. Draft. A small, fast model guesses the next tokens. In DeepInfer the draft model is DFlash, and it makes 5 draft tokens per request (deepinfer/environ.py:129).
  2. Verify. The next step sends the last real token and the drafts to the main model, the target model. By default (DEEPINFER_ENABLE_MTP_VARLEN off) it sends all 5 drafts, so one forward pass gives 6 rows of probabilities (deepinfer/environ.py:131, csrc/engine/mtp_varlen.hpp:153-158). Row j says what the target model wants after input j.
  3. Accept or reject. Row 0 checks draft 1, row 1 checks draft 2, and so on. The first rejected draft stops the check. All drafts after it are dropped.
  4. One more token. At the first rejected row, the sampler draws a replacement token. If no draft is rejected, the last row gives a bonus token. So a step always makes at least 1 token and at most 6.

The accept test is rejection sampling. It does not ask "is the draft equal to the best token". It accepts a draft with probability min(1, q/p). Here p is the probability of the token in the draft model, and q is its probability in the target model. After a reject, it draws from the residual distribution. This rule makes the output follow q exactly, as if the target model made every token itself. DeepInfer changes the residual a little, so its output follows q up to a very small, bounded error (deep dive DRAFT_PROB_PENALTY).

An everyday comparison. Think of a junior writer and a senior editor. The junior writes the next five words fast. The editor reads all five at once and keeps the words she agrees with, up to the first word she does not like. She writes that word herself and stops. The comparison stops being true in one place. The editor does not accept only the words that she would choose. She accepts each word with a probability, and she chooses her replacement word from a special distribution. Only this makes the text statistically equal to text that the editor writes alone.

In the code#

Step 1: the drafts wait in the MTP info pool#

DFlash runs at the end of each decode step and stores its drafts in the MTP info pool. Each request owns one slot of 5 rows. A row holds the draft token id, the draft logprobs and a confidence (deepinfer/model_executor/models/mtp/dflash.py:336-345). Slot 0 is special. It holds placeholder drafts for a request that has no real drafts yet:

After a prefill step there are no real drafts. The first decode step reads slot 0 (csrc/engine/sequence.hpp:149-153). The target model almost never gives the token vocab_size - 1 a high probability, so row 0 rejects the placeholder. The step then makes one token from the residual, which is almost the plain target distribution.

Step 2: which pool row each sampler row reads#

C++ decides, for each row of the batch, which pool row holds its draft:

Row j of a request reads pool row slot × 5 + j, which is draft j + 1. The last row of the request reads slot 0, because it is a fresh sample and has no draft. stop_token_ids is int32 [num_seqs, 2]: the EOS id, or -1 with ignore_eos (lines 217-219).

Step 3: map rows to requests#

_verification first labels every row (deepinfer/model_executor/layers/sampler.py:427-431). The reference code shows the rule in three lines:

row_to_req gives the request of each row. local_step gives the row number inside the request. is_verify is false only for the last row of each request.

Step 4: the accept test and the residual sample#

The rejection sampling happens inside the fused_sample kernel, in the same pass as temperature, top-p and top-k. The reference implementation shows the math:

  1. Line 232. The residual weights: r = max(q − α·p, 0) for every token, with α = exp(−5e-5). The deep dive explains α.
  2. Line 233. accept_probs = max(1 − Σ r, 0), an estimate of the chance that this row accepts its draft. DSpark compares it with the confidence (page DSpark: DFlash drafts and confidence-scheduled verification).
  3. Lines 235-237. Look up the logprob of the draft token in the draft row (log p) and in the target row (log q).
  4. Line 238. accept_lp = min(log q − log p, 0), so exp(accept_lp) = min(1, q/p).
  5. Lines 239-242. U is a seeded number in [0, 1), case 2 of the hash. Accept if min(1, q/p) > U. A draft id of -1 is always rejected.
  6. Line 245. Draw a replacement token from the residual weights, with hash case 1.
  7. Line 246. The candidate token of a verify row is the draft if accepted, else the residual sample. The last row keeps its fresh sample.

The same file also holds the tests. They run the same checks on the TileLang kernel and on this reference (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:738-750). A distribution test counts the output tokens for 16 edge cases. On NVIDIA it uses a batch of 2,097,152 rows and 1024 rounds, so about 2.1 × 109 samples per case (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:528-531, deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:714-733).

Step 5: keep only the accepted prefix#

The kernel decides each row alone. But a draft counts only if all drafts before it were accepted. get_accept_result applies this rule:

  1. Lines 239-242: a golden token overrides the decision. The row accepts only if the draft equals the golden token.
  2. Line 243: a row is blocked if it is the fresh row or a rejected row.
  3. Lines 244-245: a running count of blocked rows. A row is alive if no row before it in the same request is blocked.
  4. Line 246: an accepted draft counts only if its row is alive.
  5. Line 247: is_final marks the first blocked row of each request. Its token is the new sampled token.

Step 6: pack the results#

finalize_verification turns the row results into request results (deepinfer/model_executor/layers/sampler.py:518-566). The reference shows the main outputs:

  • last_valid_offset int32 [num_reqs]: the row of the final token inside its request. This is also the number of accepted drafts.
  • sampled_token_ids int32 [num_reqs]: the token of the final row. It is either the residual sample or the bonus token.
  • verified_token_ids int32 [total_q]: the draft id in accepted rows, -1 in all other rows.

Step 7: the engine appends the tokens#

The CPU reads these arrays one step later. Scheduler::process_outputs takes the accepted drafts of a request until the first -1, then adds the sampled token:

So the request gets accepted + 1 new tokens. The stop check runs after each token, so an EOS among the accepted drafts ends the request there (csrc/engine/scheduler.hpp:982-990). The KV cache then counts only the kept tokens (csrc/engine/scheduler.hpp:997-1000). The tour Tour: One speculative decoding round follows these steps with real positions.

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

The math: why the output distribution equals q

Take one position. The draft model proposes token x with probability p(x). The target model wants probabilities q(x). The rule:

  1. Accept x with probability min(1, q(x)/p(x)).
  2. On a reject, draw from r(x) = max(q(x) − p(x), 0) / Z, with Z = Σ max(q − p, 0).

Proof. The chance to output x by acceptance is p(x) · min(1, q(x)/p(x)) = min(p(x), q(x)). The total chance of a reject is 1 − Σ min(p, q). Because Σ p = Σ q = 1, that is equal to Σ max(q − p, 0) = Z. So the residual adds Z · max(q(x) − p(x), 0) / Z, which is max(q(x) − p(x), 0). The sum of both parts is min(p, q) + max(q − p, 0) = q(x).

Worked example (panel 2 of the figure). Tokens A, B, C, D have p = [0.6, 0.3, 0.1, 0]. The target gives q = [0.4, 0.4, 0.1, 0.1].

Tokenmin(p, q)max(q − p, 0)Accept chance if proposedTotal
A0.400.4 / 0.6 = 0.6670.4
B0.30.110.4
C0.1010.1
D00.1never proposed0.1

Z = 0.2, so the residual is [0, 0.5, 0, 0.5]. If the draft is A and U = 0.8, then 0.667 > 0.8 is false: reject. The sampler draws B or D, each with chance 0.5 (about 0.5 in DeepInfer, because of the penalty in the next deep dive).

Many drafts. Each row applies the same rule, given that all drafts before it were accepted. So the accepted prefix plus the final token has the distribution of the target model, token by token. Take a general case: each draft passes with rate a, and there are γ drafts. Then a step gives (1 − a^(γ+1)) / (1 − a) tokens on average. For a = 0.8 and γ = 5, that is about 3.69.

Measured numbers. The deployment Q&A gives a "fixed-5 accepted length" of 3.25 to 3.32 (doc/inference_deployment_qa.md:249-256). The Q&A does not say if this number includes the token that the last row adds.

Deep dive

DRAFT_PROB_PENALTY: a small and bounded change to the rule

DeepInfer does not use max(q − p, 0) for the residual. It uses max(q − α·p, 0) with α = exp(−DRAFT_PROB_PENALTY) and DRAFT_PROB_PENALTY = 5e-5:

Why. If q and p are equal up to rounding, max(q − p, 0) can be all zeros. Then a reject has nothing to sample. With α < 1, a token with q = p > 0 keeps a weight of at least (1 − α)·p. A test checks such a case: all residual weights are below 2^-31, and the kernel still returns a valid token (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:620-651).

The cost. The module docstring proves a bound. Translated from deepinfer/model_executor/layers/tilelang_ops/common.py:3-19:

  • Let p be the draft distribution and q the target distribution. Sample from p. If the sample j has p[j] ≤ q[j], accept. Otherwise sample from the normalized weights r[i] = max(q[i] − α·p[i], 0).
  • Let ε = 1 − α, and let A[j] be the real output probability of token j. Then q[j] − ε/(1 + ε) ≤ A[j] ≤ (1 + ε)·q[j].

With DRAFT_PROB_PENALTY = 5e-5, ε ≈ 5.0e-5. So no token gets more than 1.00005 times its target probability. No token loses more than about 0.00005 (an absolute amount, not a factor). The distribution test checks the upper bound: each count must stay below (1 + ε)·q times the number of samples, plus a statistical margin (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:566-573, deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:598-600).

The docstring shortens the accept step. The code accepts with the unchanged ratio min(1, q/p), also when p[j] > q[j] (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:238). Only the residual uses α.

Deep dive

How the accepted tokens and the bonus token reach the user

  1. The sampler returns a SamplerOutput with sampled_token (one per request), verified_tokens (one per row) and first_token_positions (CPU int32 [req_cnt]) (deepinfer/model_executor/layers/sampler.py:277-291).
  2. LLMEngine._process_model_outputs passes the flat [total_q] array of accepted ids to C++ without a copy (deepinfer/engine/llm_engine.py:697-703).
  3. Scheduler::process_outputs appends the accepted drafts and the sampled token, and checks the stop conditions after each one (Step 7 above).
  4. build_request_outputs makes one RequestOutput per new token. The last one carries draft_tok = drafts + 1 and accept_tok = accepted + 1 (csrc/engine/outputs.hpp:214-216, csrc/engine/outputs.hpp:287-292).

For request A of the previous example, the user gets three objects. The third has draft_tok = 6 and accept_tok = 3. With ZOS, these objects arrive one step() call later (Zero-overhead scheduling (ZOS)).

Device copies for the next step. With ZOS, the next step is already scheduled before the CPU sees these results. So the sampler also keeps device copies: sampled_token_ids_gpu [num_seqs], predict_token_ids_gpu [num_seqs, 5] and num_accepted_tokens_gpu (= last_valid_offset) (deepinfer/model_executor/layers/sampler.py:258-291, deepinfer/sequence.py:259-269). A kernel uses them to fix seqlens_k of the next step on the device (deepinfer/worker/worker.py:220-227).

Deep dive

Stop tokens inside the drafts

  • On the CPU. _check_stop runs after each appended token. A stop at accepted draft 1 drops draft 2 and the sampled token (csrc/engine/scheduler.hpp:982-990, csrc/engine/scheduler.hpp:1035-1052).
  • On the device. finalize_verification sets emitted_stop_token for each request whose emitted tokens contain one of its stop_token_ids (deepinfer/model_executor/layers/tilelang_ops/sampler.py:376-382). The sampler then sets the confidences of that request's next drafts to 0:

With DSpark, a confidence of 0 gives the request no drafts in the next step. This matters because the CPU schedules that step before it sees the stop.

Deep dive

Backtracking limits: how far can the cache go back?

A decode step writes cache entries for all 6 input tokens before the sampler knows which drafts survive. So every cache that keeps a fixed window must have room for these extra writes. DeepInfer calls this backtracking.

Why 134 is enough. Let the cache hold tokens up to position P − 1. A step writes positions P … P + 5 into ring slots pos % 134, before its attention reads the ring. These slots last held positions P − 134 … P − 129. The query at P is the oldest query of the step. With a 128-token window, it reads keys P − 127 … P (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:631-649). So the writes never remove a key that a query of this step or a later step needs.

Why the rejected keys do no harm. A rejected key at position y is also never read. A query reads only keys up to its own position. The first later step with a query at y also writes the real key of y before its attention. The docs give the same number: "128-token window + 6 tokens of speculative backtracking" (doc/inference_deployment_qa.md:191).

Nothing is copied back after a reject. The next step simply writes the same positions again. The tour Tour: One speculative decoding round shows this for every cache.

What can go wrong#

  • The first decode step makes only one token. This is normal. The placeholder drafts of slot 0 almost always fail (Step 1).
  • Low acceptance. If the drafts often fail, each step still costs 6 rows but gives about 1 token. DSpark reduces this waste (doc/inference_deployment_qa.md:243).
  • Too many rows. prepare_sampler_inputs stops with a check failure in two cases. A request has more than nextn + 1 rows, or its draft list does not have nextn entries (csrc/engine/prepare_sample.cpp:209-212).
  • Small change in the distribution. The penalty α can raise a token probability by a factor of at most about 1.00005. It can lower it by at most about 0.00005 (deep dive). Tests that need the exact target distribution must allow this.
  • Memory. Without force top-k, the pool keeps full-vocabulary draft logprobs: about 168 MB for 64 sequences (see The sampler).

Why it matters. Speculative decoding lets one decode step make several tokens per request, without a change in the output distribution. The Q&A measured an average "accepted length" of about 3.3 with 5 drafts (doc/inference_deployment_qa.md:249-256).

Check yourself#

  1. 1
    A request has 5 drafts. What is the smallest and the largest number of new tokens that one decode step can give it?
    easy
    Show answer

    At least 1: the first draft fails, and the residual gives one token. At most 6: all 5 drafts pass, and the last row adds the bonus token (deepinfer/model_executor/layers/tilelang_ops/sampler.py:243-247).

  2. 2
    Which row of a request checks draft 3?
    easy
    Show answer

    Row 2. Row j reads pool row slot × nextn + j, which is draft j + 1 (csrc/engine/prepare_sample.cpp:221-223).

  3. 3
    The draft model gives a token p = 0.5 and the target model gives it q = 0.2. The hash gives U = 0.3. What happens?
    medium
    Show answer

    min(1, q/p) = 0.4 > 0.3, so the sampler accepts the draft (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:238-242). With U = 0.5, it rejects it and samples from max(q − α·p, 0).

  4. 4
    Row 1 rejects its draft, but the kernel accepts the draft of row 3. Does draft 4 count?
    medium
    Show answer

    No. Row 1 is blocked, so every later row of the request is not alive. get_accept_result keeps only the prefix before the first blocked row (deepinfer/model_executor/layers/tilelang_ops/sampler.py:243-247).

  5. 5
    Why can DeepInfer use max(q − α·p, 0) instead of max(q − p, 0), and how large is the error?
    hard
    Show answer

    With α < 1, the residual is never all zeros when q equals p, so a reject can always sample a token. The docstring proves q[j] − ε/(1+ε) ≤ A[j] ≤ (1+ε)·q[j] with ε = 1 − exp(−5e-5) ≈ 5e-5 (deepinfer/model_executor/layers/tilelang_ops/common.py:3-19, deepinfer/model_executor/layers/tilelang_ops/common.py:53). This is in the deep dive on DRAFT_PROB_PENALTY.

  • DSpark: DFlash drafts and confidence-scheduled verificationDSpark makes 5 drafts per request with the DFlash draft model and predicts how likely each draft is to pass. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time.
  • The samplerThe sampler turns the hidden states of the rows that need a token into float32 logits, applies temperature, top-p and top-k, and draws one token per request with a seeded hash. In decode steps it also verifies the draft tokens.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • layers/sampler.py: the Sampler classsampler.py holds the Sampler module. It turns selected hidden states into float32 logits, samples prefill tokens, verifies draft tokens in decode steps and calls DFlash. sampler_utils.py holds the logits, sampling and prompt-logprob helpers.
  • models/mtp/dflash.py: the DFlash draft modeldflash.py holds DFlash, the draft model of DSpark. It writes draft keys from main-model features during the forward pass, makes 5 drafts per request in one pass after the verification, and stores drafts, logprobs and confidences in the MTP info pool.
