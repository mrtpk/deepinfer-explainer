The Python and C++ boundary

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

In one sentence

DeepInfer runs the scheduler and the step bookkeeping in C++. Python reaches that code through one compiled pybind11 module, deepinfer._C.

The idea#

Most of DeepInfer is Python. The entry point, the engine, the workers and the model forward pass are Python code that calls PyTorch and device kernels. One part is C++: the code that decides what each engine step does, and the code that prepares the inputs for that step. This C++ code is in the folder csrc/.

The C++ code is compiled into one extension module: a .so file that Python imports like a normal module. Its name is deepinfer._C (setup.py:59-60). It has three submodules:

  • _C.engine: the scheduler, the block managers, sequences, output objects, and the functions that prepare model and sampler inputs. This is the largest part: 34 names.
  • _C.cuda_utils: three functions for raw device memory and for memory that another process opens.
  • _C.graph_timer: three classes that time regions inside a captured CUDA graph.

Why C++? The code and the docs do not give a direct reason. The deployment doc gives the context: in a decode step, schedule and post-process are "pure CPU logic", and the device sits idle while they run (doc/inference_deployment_qa.md:270). Zero-overhead scheduling hides this CPU time behind device work (doc/inference_deployment_qa.md:274). So the CPU time of each step matters. This site does not claim more than that.

An everyday comparison. Think of a shop with a front desk and a stock room. Customers talk only to the front desk (Python). The stock room (C++) keeps the stock lists and counts fast. Items go between the two through one window (the pybind11 module). The comparison stops here: sometimes the stock room lends its own shelf to the front desk instead of a copy of the items. The front desk must finish with that shelf before the next step, because the stock room then uses it again. On this page, such a shelf is a borrowed view.

Deep dive

The GIL and the block-manager locks

Two kinds of lock meet at the boundary: the Python GIL and the C++ mutex of each BlockManager. The base class Lockable has one strict rule:

  1. Line 16: if the calling thread holds the GIL, TORCH_CHECK fails. Python sees a RuntimeError.
  2. Line 17: the fast path tries the lock without a wait.
  3. Lines 20-27: else it waits for at most 20 seconds (CLOCK_MONOTONIC). After that, TORCH_CHECK fails with "failed to lock mutex".
  4. Line 35: the mutex is an error-check mutex. A second lock from the same thread gives an error, not a hang.

Why no GIL while you lock. The code comment gives only "to avoid a deadlock". The general case is this: thread A holds the GIL and waits for the mutex. Thread B holds the mutex and waits for the GIL. Neither can continue. When every caller first releases the GIL, this cannot happen.

Lock order. BlockManagerMutexAcquire locks the state manager first, then the block manager. It unlocks in the opposite order (csrc/engine/block_manager.hpp:189-204). A fixed order prevents a second kind of deadlock between two threads that both want both locks.

How the code releases the GIL. There are three patterns:

  • Inside the C++ function: py::gil_scoped_release as the first line, as in _schedule (csrc/engine/scheduler.hpp:276) and prepare_sampler_inputs (csrc/engine/prepare_sample.cpp:42).
  • In the binding: py::call_guard<py::gil_scoped_release>(), for example for BlockManager.lock and free_seq (csrc/engine/pybind_scheduler.cpp:67-71, csrc/engine/pybind_scheduler.cpp:100-102).
  • Release, work, then get the GIL again to build a Python result. build_request_outputs reads its NumPy input pointers first, releases the GIL (csrc/engine/outputs.hpp:102-104), and gets it back before it makes the result array (csrc/engine/outputs.hpp:306-307).

One call must keep the GIL: update_metadata_for_sampling_zos assigns a Python object (csrc/engine/pybind_scheduler.cpp:51-53). The page deepinfer/_C/engine.pyi: the C++ engine API, as seen from Python lists every call that releases the GIL.

Which other Python threads run. The released GIL helps these threads in the engine process:

  • the structured-output compile pool (deepinfer/structure_output/so_matcher_builder.py:45);
  • the statistics log thread (deepinfer/engine/stats_logger.py:186);
  • the image-processing pool of the VL model (deepinfer/model_executor/models/deepseek_vl.py:84);
  • the optional profiling HTTP server (deepinfer/engine/profile_server.py:157).

Worked example: one borrowed array. A forked sequence moves into the running queue. It has 130 tokens and the block size is 64 (an example value), so it uses 3 KV blocks. The scheduler gives it one new block for its last, part-full block and pushes the pair (old last block, new block) (csrc/engine/scheduler.hpp:606-611). Each extra block after the last used block adds a pair (block, 0), which gives the block back with no copy (lines 612-615). Here there is no extra block, so clone_blocks holds 2 ints. The property returns a NumPy array of shape (1, 2). Its strides are (8, 4) bytes, that is 2 × sizeof(int) and sizeof(int). Its data pointer is clone_blocks.data() (csrc/engine/pybind_scheduler.cpp:46-47). The empty capsule py::capsule([]() {}) tells NumPy that it does not own the memory. When the next schedule() calls clone_blocks.clear(), the array points at stale or reused memory. With no fork, the property returns a new empty array of shape (0, 2) (line 45). The engine does not keep the three arrays. It uses them at once, in the same step. It gives them to the worker, which clones and zeroes the blocks and states on the device (deepinfer/engine/llm_engine.py:889-903).

The device buffer. alloc_tensor rounds the size up to a multiple of 4096 bytes for cuMemAlloc, but the tensor shape keeps the requested size (csrc/cuda_utils.cpp:24-27, csrc/cuda_utils.cpp:79-82). If the allocation fails, the function logs an error and returns None. The cache engine asserts the type and stops with a message (deepinfer/worker/cache_engine.py:914-915).

IPC handles. export_ipc_tensor(ptr, nbytes) returns a byte string that holds a cudaIpcMemHandle_t and the size. import_ipc_tensor opens it in another process (csrc/cuda_utils.cpp:43-47). The deleter of the tensor closes the handle when the tensor dies (csrc/cuda_utils.cpp:15-22). In the package, only utils.CudaIPCWrapper uses these calls (deepinfer/utils.py:52-69), and only a test uses that class (tests/distributed/test_expert_shuffle.py:89). Deep dive

What C++ reads from Python, and when

Config objects. The Scheduler constructor takes scheduler_config as a plain py::object. It reads nine attributes by name, once, and keeps C++ copies (csrc/engine/scheduler.hpp:94-108). A later change to the Python object has no effect on the scheduler. A missing attribute raises an error at construction.

Process groups. The scheduler gets the data-parallel group as a c10d::ProcessGroup and runs its all-reduce votes from C++ (csrc/engine/scheduler.hpp:169-182). A Gloo group keeps the vote tensor on the CPU; any other backend puts it on the device (csrc/engine/scheduler.hpp:109).

Deep dive

Build and import, step by step

  1. DEEPINFER_ACCELERATOR=nvidia ./build.sh first checks that the variable is nvidia or ascend. Then it installs requirements-<accelerator>.txt and, on NVIDIA, NCCL 2.32.3. Last, it builds the vendor libraries and runs scripts/build.sh build (build.sh:5-25).
  2. scripts/build.sh computes PY_BUILDTAG (for example linux-x86_64-cpython-312; an example, not from the repo) and the platform tag. The tag uses nvidia when the variable is not set (scripts/build.sh:11-14).
  3. It sets MAX_JOBS to 16 unless you set it (scripts/build.sh:6-9), and runs python setup.py build --build-base build/<tag>.
  4. setup.py picks the extension type from accelerator_kind(), that is, from the device files of the build machine (setup.py:10-12). It needs the C++11 ABI of PyTorch (setup.py:18-19). The CUDA branch needs a conda env or a virtualenv (setup.py:55-57).
  5. The script links every .so into deepinfer/_so/<tag>/ with a relative symlink. If no file was linked, it exits with an error. Then it byte-compiles the package (scripts/build.sh:23-29).
  6. At run time, import deepinfer computes the tag from DEEPINFER_ACCELERATOR (default "nvidia", deepinfer/environ.py:101) and appends the folder to __path__ if it exists (deepinfer/__init__.py:9-32).
  7. Import torch before deepinfer._C. The extension links against the PyTorch libraries, and the package files do this in order (deepinfer/model_executor/sampling_inputs.py:16).

Two different signals choose the platform

setup.py uses the device files of the machine. The folder tag uses the environment variable. On an Ascend host, a build with the variable not set compiles the NPU extension into _so/nvidia-aarch64/. An import with the variable not set also looks there, so it works. But an import with DEEPINFER_ACCELERATOR=ascend looks in _so/ascend-aarch64/ and does not find it. (We derived this from the code; we did not run it.) Use make build-ascend, which sets the variable (Makefile:8-11).

Clean. scripts/build.sh clean removes build/<tag>, deepinfer/_so/<tag>, old deepinfer/*.so files and all __pycache__ folders (scripts/build.sh:32-38).

What can go wrong#

Do not keep borrowed arrays

Copy clone_states, clone_blocks, zero_states and the result of process_outputs before the next call (for example with np.array(x)). A saved view shows the data of a later step, or freed memory. Nothing raises an error.

  • Import order. If deepinfer._C loads before torch, the import fails. A script comment says, translated: "Load libtorch first, or deepinfer._C reports libc10.so not found" (examples/yoco/yoco_equiv.py:200).
  • Wrong .so folder. If the tag at run time differs from the tag at build time, the import finds no module or an old one. See the deep dive "Build and import".
  • Lock with the GIL held. New C++ code that locks a block manager without releasing the GIL fails the check in Lockable::lock_ (csrc/utils/lockable.hpp:16).
  • Lock time-out. If another thread holds a block manager for more than 20 seconds, the call fails with "failed to lock mutex" (csrc/utils/lockable.hpp:25-27).
  • Wrong argument type. Sequence(...) with a Python list for prompt_token_ids raises TypeError, because of noconvert() (csrc/engine/pybind_sequence.cpp:103).
  • Old stub. After a binding change, the .pyi files are wrong until you run make stubgen.
  • Default drift. C++ has its own default for DEEPINFER_USE_NEXTN_DECODE (5). A change in environ.py alone makes the two sides disagree (csrc/engine/utils.hpp:38-39).

Why it matters. The scheduler, the block managers and the input preparation run in C++. So many engine bugs show up at this boundary. Examples are data that a later step changed, a lock that waits, and a module from the wrong build. When you know who owns each buffer and which call releases the GIL, you can find these bugs fast.

Check yourself#

  1. 1
    How many submodules does deepinfer._C have, and what are their names?
    easy
    Show answer

    Three: cuda_utils, engine and graph_timer. csrc/pybind.cpp makes them with def_submodule (csrc/pybind.cpp:9-16).

  2. 2
    Does the repository say why the scheduler is in C++?
    easy
    Show answer

    No. The deployment doc only says that schedule and post-process are pure CPU work and that the device is idle during them without asynchronous scheduling (doc/inference_deployment_qa.md:270). The code gives no reason.

  3. 3
    On an NVIDIA x86 machine, you run make build-nvidia. Where does the .so go, and how does import deepinfer._C find it?
    medium
    Show answer

    The build writes to build/nvidia-x86_64 and links each .so into deepinfer/_so/nvidia-x86_64/ (scripts/build.sh:12-14, scripts/build.sh:23-26). deepinfer/__init__.py computes the same tag and appends that folder to the package __path__ (deepinfer/__init__.py:30-32).

  4. 4
    A new Python thread calls scheduler.try_allocate_seq(seq) while the main thread is inside schedule(). What happens?
    medium
    Show answer

    The binding releases the GIL and then waits for the block-manager locks (csrc/engine/pybind_scheduler.cpp:87-90). The main thread holds them during _schedule(), so the new thread waits. If it waits more than 20 seconds, the lock fails with "failed to lock mutex" (csrc/utils/lockable.hpp:25-27).

  5. 5
    Why does Lockable::lock_ refuse to run when the thread holds the GIL, and why does BlockManagerMutexAcquire always lock the state manager first?
    hard
    Show answer

    Both rules prevent deadlocks. A thread can hold the GIL and wait for a mutex. If the mutex holder needs the GIL to finish, both threads stop. So the check at csrc/utils/lockable.hpp:16 makes every caller release the GIL first. A fixed lock order (state manager, then block manager; csrc/engine/block_manager.hpp:190-196) prevents two threads from each holding one lock and waiting for the other. This is the deep dive "The GIL and the block-manager locks".
