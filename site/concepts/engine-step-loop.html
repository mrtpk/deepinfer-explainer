Offline API and the step loop

IntermediateDeepInfer conceptsabout 9 min read + 7 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Prefill and decode Beginner
  • The KV cache Beginner

In one sentence

LLM.generate() adds all requests, then calls LLMEngine.step() again and again. Each step runs one batch and returns the outputs that are ready.

The idea#

An LLM makes one token at a time for each request. DeepInfer serves many requests together, so it works in rounds. One round is an engine step. In each step, the engine selects a batch of requests and runs the model once for the whole batch. Then it adds new tokens to each request in the batch.

The offline API is the class LLM in deepinfer/entrypoints/llm.py. It has one main method, generate(), which does three things:

  1. It adds every prompt to the engine as a request.
  2. It calls step() while a request is not finished. It copies the outputs of each step.
  3. When all requests are finished, it calls flush_inflight_reqs() once, sorts the results, and returns them.

One step has fixed phases. The C++ scheduler selects the batch. The Worker runs the model on the device and samples the next tokens. The engine then updates each sequence and makes one RequestOutput for each new token. With zero-overhead scheduling (ZOS), the engine updates the sequences of a decode step during the next step. So the CPU work overlaps with the device work.

An everyday comparison. Think of a ferry that crosses a river again and again. On each trip it takes all cars that are ready. A car must make many trips to reach its goal, because each trip moves it only a short distance (one or a few tokens). The comparison stops being true in two places. A real ferry unloads at the end of the same trip. With ZOS, DeepInfer reports the result of a decode trip during the next trip. Also, all ferries of a fleet (the data-parallel ranks) must make the same number of trips, also when one of them is empty.

The picture#

Read panel 1 as a loop: test, step, copy, test again. Panel 2 shows that the Worker calls back into the engine twice in one step. Panel 3 is the most important one. A prefill step returns its tokens at once, but a decode step returns the tokens of the step before it.

In the code#

Step 1: generate() adds all requests first#

Each _add_request call tokenizes the prompt (if the caller gave text), gives the request the next counter value as its id, and calls LLMEngine.add_request (deepinfer/entrypoints/llm.py:151-166). The engine makes a C++ sequence and puts it into the waiting queue of the scheduler (deepinfer/engine/llm_engine.py:620-630). No model work happens yet. The page Request and sequence lifecycle follows one sequence from here to its end.

Step 2: the loop in _run_engine()#

  1. Line 177: the loop asks the engine if any request is unfinished.
  2. Line 178: if yes, it runs one step. If no, it calls flush_inflight_reqs() instead.
  3. Lines 179-182: each step returns an array of handles. The loop copies each output with RequestOutput.clone before the next step. The engine gives the original objects back to their pool one step later.
  4. Lines 185-186: the loop ends after the flush.
  5. Lines 187-190: the results are sorted by request id as an integer, so they come back in prompt order. With decode_sequence=True (the default), each list of outputs becomes a string (deepinfer/entrypoints/llm.py:64).

Step 3: is any request unfinished?#

The local answer is true if a scheduler queue (waiting, running or prompted) holds a sequence (csrc/engine/scheduler.hpp:165-167). It is also true if a structured output grammar is still in the build queue. With more than one data-parallel rank, the engine takes the maximum over all ranks. So all ranks keep calling step() until the last rank is done. A rank with no work then runs a placeholder step.

Step 4: one call of step()#

LLMEngine.step() is short. It schedules, does some checks, and hands the batch to the Worker:

The phases, in order:

  1. Schedule (lines 885-887). The C++ scheduler picks a prefill batch or a decode batch. It returns one SequenceMetadata per sequence and a SchedulerOutputs object. The page The scheduler explains the rules.
  2. Clone or zero (lines 889-905). Only for forked sequences. The offline API never forks.
  3. Checks (lines 907-928). An empty hook, and a check of the structured-output state at the last prefill chunk.
  4. Multimodal fetch (lines 939-945). The engine collects the results of the image worker. In the engine, a request becomes schedulable only here. A failed request is aborted.
  5. Execute (line 952). The engine calls the Worker. The Worker runs the device work and calls back into the engine (next step).
  6. Return (line 959). The handles of the outputs that are ready now.

Step 5: the Worker part of the step#

The Worker method execute_model_step has four parts. Its docstring lists them:

The post-process calls back into the engine. LLMEngine.post_process runs three C++ functions (deepinfer/engine/llm_engine.py:717-761). process_MTPInfo stores the new draft tokens. scheduler.process_outputs appends the tokens to each sequence and checks the stop conditions. build_request_outputs makes the output objects. The second callback, pre_sampler_sync, runs while the device samples. It gives back the buffers of the previous step and frees finished sequences (deepinfer/engine/llm_engine.py:830-846).

Step 6: what step() returns#

step() returns a NumPy array of uint64 values. Each value is the address of a RequestOutput object in the RequestOutputPool. The docstring gives the rule:

One request can get several outputs in one step, one per accepted token. A step can also return no output at all. Panel 3 of the figure shows steps with no output. Its footnote mentions the case with accepted drafts.

Step 7: the end of the loop and the flush#

With ZOS, the Worker keeps the last decode step in prev_step_state. No later step post-processes it, so the flush does it. In the offline loop, the kept step at that time has no real sequence, so the flush returns no output (deep dive below). A custom loop must still call it: if the loop stops earlier, the flush returns the last tokens.

What each call returns: the worked example, line by line

Two requests, A with max_tokens=3 and B with max_tokens=4, are schedulable and start in the same prefill step. ZOS is on. To keep the numbers simple, every decode step accepts no draft, so each step adds one token per request. This site derived the table from the code and did not run it.

  1. Why step 2 returns nothing. A prefill step sets prev_step_state = None (deepinfer/worker/worker.py:185). The first decode step after it has nothing to post-process.
  2. Why A still runs in step 4. The scheduler of step 4 runs before the post-process of step 3. At that moment A has 2 output tokens.
  3. Why step 6 happens. Before step 6, B is finished but is still in running, so has_unfinished_requests() is true. The decode schedule of step 6 removes B, and pre_sampler_sync frees its blocks (deepinfer/engine/llm_engine.py:844-846).
  4. Cost. With ZOS, each request does one forward pass whose token is dropped: the step that ran while its last token was still in flight.

With ZOS off, each step post-processes itself. Then step 2 returns A2, B2, step 3 returns A3 and B3, and A leaves running one step earlier.

With accepted drafts, one decode step appends several tokens. build_request_outputs makes one object for each accepted draft and one for the sampled token (csrc/engine/outputs.hpp:219-285).

The all-reduce. With dp_group.size() > 1, the answer becomes an int64 tensor, and an all-reduce MAX combines all ranks (deepinfer/engine/llm_engine.py:675-678). With ZOS the group is the CPU (Gloo) group, else the device group (lines 667-672). Every rank calls this function once per loop, so every rank calls step() the same number of times. This matters because the scheduler of each rank votes with all-reduce calls inside schedule() (csrc/engine/scheduler.hpp:315-332).

The progress bar. With use_tqdm=True, the total is get_num_unfinished_requests() at the start (deepinfer/entrypoints/llm.py:170-172). It is a local count: the sum of the three queues plus pending grammar builds (deepinfer/engine/llm_engine.py:658-663). The bar moves when an output has finished=True.

Buffers that live for one step

Three kinds of objects that a step makes are valid only until the next step. DeferredRelease collects them and gives them back in the next pre_sampler_sync, while the device samples (deepinfer/engine/llm_engine.py:67-121).

Copying an output. RequestOutput.clone(ptr) copies the C++ object into a new object that Python owns (csrc/engine/pybind_output.cpp:17-18). The fields include request_id, token_id, finished, finish_reason, token_logprobs, top_logprobs, num_output_tokens, draft_tok and accept_tok (csrc/engine/outputs.hpp:18-43).

Pool size. The pool has 10000 objects. If no object is free, allocate fails with "RequestOutputPool exhausted" (csrc/engine/outputs.hpp:64-70). One decode step makes at most max_num_seqs × (1 + nextn) outputs, for example 256 × 6 = 1536.

Deep dive

Placeholder steps: steps with no sequence

A step can have no scheduled sequence. This happens when the decode branch finds no running sequence, or when another data-parallel rank runs a prefill step and this rank has no prompt. step() still calls the Worker, with is_placeholder = scheduler_outputs.is_empty() (deepinfer/engine/llm_engine.py:972).

The Worker runs the forward pass and the sampler on this one sequence (deepinfer/worker/worker.py:125-127). The post-process gets no sampler output (deepinfer/engine/llm_engine.py:987), so it makes no RequestOutput. The forward pass still runs the collective operations of the model, such as the MoE dispatch and combine. That keeps every rank in the same order of collective calls.

Empty steps at the start. In this release, every request of a NORMAL engine waits for the multimodal worker before its first prefill. The first prefill then waits for an attempt point, so the first steps of a run are placeholder steps (Tour: Life of a request, stop 5).

What can go wrong#

Copy outputs before the next step

A handle from step() points into the output pool. The engine gives the object back to the pool in the next step (deepinfer/engine/llm_engine.py:830-831). Call RequestOutput.clone(handle) before the next step, as LLM does (deepinfer/entrypoints/llm.py:181).

  • A custom loop without the flush. With ZOS, the outputs of the last kept decode step come only from flush_inflight_reqs() (deepinfer/worker/worker.py:274-283).
  • A loop on one data-parallel rank only. The scheduler votes with all-reduce calls in every step. If one rank stops calling step(), the other ranks wait in the vote. Use has_unfinished_requests(), which combines all ranks.
  • Lost token ids. With decode_sequence=True (the default), generate() returns only text (deepinfer/entrypoints/llm.py:189-190). The examples set decode_sequence=False to keep the objects (examples/_config.py:121).
  • A slow start. The first steps of a run can be empty, because requests wait for the multimodal worker and for an attempt point.
  • A request that is never added. add_request returns None for a token id outside the vocabulary and writes only an info log line (deepinfer/engine/llm_engine.py:582-589). generate() then has no output for that prompt, and the result list is shorter than the prompt list.

Why it matters. The step loop is the heartbeat of the engine. A driver of your own (a server or a benchmark) must keep three rules. Copy the outputs before the next step. Flush at the end. Keep all data-parallel ranks in the same number of steps.

Check yourself#

  1. 1
    What does LLMEngine.step() return?
    easy
    Show answer

    A NumPy array of uint64 handles. Each handle is the address of a RequestOutput object in the RequestOutputPool. The objects are valid until the next step (deepinfer/engine/llm_engine.py:860-871).

  2. 2
    When does _run_engine call flush_inflight_reqs()?
    easy
    Show answer

    Once, when has_unfinished_requests() returns false. Then it copies the outputs and leaves the loop (deepinfer/entrypoints/llm.py:177-186).

  3. 3
    ZOS is on. A prefill step is followed by a decode step. What does the decode step return, and why?
    medium
    Show answer

    Nothing. A prefill step post-processes at once and sets prev_step_state to None (deepinfer/worker/worker.py:183-185). The decode step keeps its own state for the next call, and has no kept step to post-process (deepinfer/worker/worker.py:186-187, deepinfer/worker/worker.py:259-260).

  4. 4
    Two data-parallel ranks run. Rank 0 has no request left, rank 1 has one. What does rank 0 do in the next loop?
    medium
    Show answer

    It calls step(). has_unfinished_requests() takes the MAX over the DP group, so it is true on both ranks (deepinfer/engine/llm_engine.py:675-678). Rank 0 schedules an empty batch and runs a placeholder step (deepinfer/worker/worker.py:125-127).

  5. 5
    With ZOS on, request A has max_tokens=3 and starts in a prefill step alone. No draft is accepted. How many calls of step() run, and in which one does A's last output come back?
    hard
    Show answer

    Prefill (returns A1), decode (returns nothing), decode (returns A2), decode (returns A3, finished). In the fourth call the post-process of the third step finds the 3rd token. A is still in running, so a fifth call runs. Its schedule removes A, and its post-process drops A's 4th token, so it returns nothing. Then the loop flushes. So 5 calls of step() and one flush; A's last output comes back in call 4. See the deep dive "What each call returns".

Related pages

  • Request and sequence lifecycleEach request becomes a C++ Sequence. It waits until it is schedulable, runs one or more prefill steps and many decode steps, and ends with one of seven finish reasons. Preemption stops it or sends it back to the queue for a recompute.
  • The schedulerIn every engine step, the C++ scheduler runs either a prefill batch or a decode batch. It starts prefills only at attempt points, cuts long prompts into chunks, gives KV blocks, and preempts sequences when the blocks run out.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • Data parallelism and step votesEach data-parallel replica is a separate engine process with its own requests. All replicas must run the same kind of step at the same time, so they vote with all-reduces over the DP group.
  • deepinfer/entrypoints/llm.py: the offline LLM classLLM is DeepInfer's offline Python API. It makes one LLMEngine, adds every prompt as a request, calls step() until no data-parallel rank has work, clones the outputs, and returns token lists or decoded text.
  • engine/llm_engine.py: the LLMEngine classLLMEngine starts the workers, sizes the KV cache, owns the C++ scheduler, and runs one engine step each time LLM calls step().
  • worker/worker.py: the per-step WorkerWorker.execute_model_step runs every engine step on one rank in a fixed order - forward N, post-process N-1, sample N - and keeps a ZOS decode step for the next call. zos_status.py holds the two records that it keeps.
