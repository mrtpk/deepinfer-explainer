Determinism and batch invariance

AdvancedDeepInfer conceptsabout 9 min read + 6 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Number formats: BF16, FP8, FP4 Beginner
  • Sampling: temperature, top-k, top-p Beginner
  • The sampler Intermediate
  • Batching Beginner

In one sentence

With one switch, a request gets the same logits in any batch; with two more settings, it also gets the same tokens.

The idea#

Run the same prompt twice. The first time it is alone; the second time it shares a batch with 63 other requests. Many inference engines give a slightly different answer the second time. The reason is not a random bug. It is the arithmetic of floating-point number numbers.

Each floating-point addition rounds its result. So (a + b) + c and a + (b + c) can give different last bits. A kernel that adds thousands of numbers must choose an order. Many fast kernels choose it from the size of the batch. With a large batch, they add in one way. With a small batch, they split the sum into parts to keep the device busy. So the reduction order depends on the other requests, and so do the last bits of the logits. One different bit can change one sampled token, and after that token the two texts differ.

DeepInfer has two levels of control (README.md:27-28):

  1. Batch invariance: DEEPINFER_BATCH_INVARIANT=1 (NVIDIA only). A request gets the same model results in any batch composition.
  2. Deterministic sampling: batch invariance, plus DEEPINFER_ENABLE_MTP_VARLEN=0, plus a fixed seq_seed. The same input tokens and sampling parameters give the same output tokens.

An everyday comparison. Think of a long shopping receipt and a cheap calculator that shows only 8 digits. One cashier adds the items from top to bottom. A second cashier splits the receipt into four parts, adds each part, and then adds the four subtotals. Each cashier is correct by the rules of the calculator. But the totals can differ in the last digit, because the calculator rounds at different moments. Batch invariance tells every cashier to use one fixed way to split the receipt, whatever the length of the queue. The comparison stops being true in one point: a real cashier can redo the sum on paper and get the exact total. A kernel cannot. Each order gives a different rounded result, and no order is "the correct one".

In the code#

Step 1: the switch#

DEEPINFER_BATCH_INVARIANT is a bool with default off (deepinfer/environ.py:197). It is in the group "Profiling & Debug" of environ.py (deepinfer/environ.py:196). Some scripts turn it on for you:

  • examples/offline_inference.py sets it to 1 on NVIDIA, unless the variable is already set (examples/offline_inference.py:42-43).
  • eval/run_eval.py --batch-invariant sets it. The help text says the result is "independent of batch composition (slower)" (eval/run_eval.py:73-75, eval/run_eval.py:130-131).
  • The model tests set it too (see step 6).

Step 2: deterministic GEMM kernels#

Each worker configures its kernel libraries once, at start-up (deepinfer/worker/base.py:188):

  1. Lines 61-63: on Ascend, the switch must be off. The worker stops with AssertionError if it is on. This is the code behind "NVIDIA only".
  2. Lines 67-69: with the switch on, both DeepGEMM and tile_kernels get use_deterministic_algorithms(True). On Ascend, this call runs always, for stable CI numbers.

Simplified

What "deterministic algorithms" means inside DeepGEMM and tile_kernels is not in this repository. DeepInfer only sets the flag.

Step 3: batch-invariant decode attention#

Each attention layer decides once, when it is built, if it uses the fused norm-RoPE-attention kernels or the plain path with FlashMLA. The decision applies to prefill and decode (deepinfer/model_executor/models/v4_modules/attn.py:615-624, deepinfer/model_executor/models/v4_modules/attn.py:656-669):

The switch appears only in the first term, which is about the prefill-only engine type (EngineType.PROMPT). The offline LLM uses the NORMAL engine (deepinfer/engine/arg_utils.py:41), so there the choice does not depend on the switch. Take a NORMAL engine on GPU with 64 or 128 heads. There, sparse layers and layers without packed KV use the fused kernel, and dense packed-KV layers use the plain call.

The decode call passes the switch on (deepinfer/model_executor/models/v4_modules/attn.py:660-669). Only the plain path forwards it to FlashMLA:

The fused path, a few lines higher, has no batch-invariant argument (deepinfer/model_executor/layers/attention_backend.py:107-121). The draft model DFlash calls the same function with the switch (deepinfer/model_executor/models/v4_modules/attn.py:994-1007).

Step 4: the MoE combine#

DeepInfer turns off allow_multiple_reduction of the DeepEP buffer only when the switch is on and EPLB moves experts (DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL > 0, default 0: deepinfer/environ.py:116). The code gives no reason for the second condition. The KL test in the deep dive below turns on both conditions.

Simplified

The DeepEP source is not checked out, so this site does not say what allow_multiple_reduction does inside DeepEP. Its name suggests a reduction order, but the repository does not say so.

Step 5: deterministic sampling#

Batch invariance fixes the logits. The sampler adds two more sources of difference: the random numbers and the number of verified drafts.

Random numbers. The sampling kernels do not use a global random generator. They hash the seed of the request with the position of the token:

The PyTorch reference shows the hash input: (3 × position + case) mixed with seq_seed (deepinfer/model_executor/layers/tilelang_ops/random_sampling.py:76-81). The row index and the batch size do not appear. But the seed must be the same in both runs. Without seq_seed, SamplingParams draws a new 64-bit seed (deepinfer/sampling_params.py:85-91).

Number of drafts. With DSpark (DEEPINFER_ENABLE_MTP_VARLEN=1), the batch shares one budget of query tokens. A kernel ranks the drafts of all requests by confidence and gives the budget to the best ones (deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py:11-32). Its PyTorch reference shows the rule:

So the verification length of one request depends on the other requests. A different number of verified drafts changes which random numbers the sampler uses, and so the tokens. The README does not give this reason; it gives only the recipe (README.md:28). The variable is off by default (deepinfer/environ.py:131); the explicit 0 also overrides a value that a script exported.

Step 6: the tests#

The main test runs 64 random prompts in one batch, then each prompt alone, and compares everything bit for bit:

  1. Lines 87-94: sampling with temperature 1.0 and top-p 0.7, 50 tokens, 5 top logprobs.
  2. Line 96: the batched run.
  3. Lines 100-102: each prompt alone, with golden tokens: the single run must output the tokens of the batched run. So the test compares the model numbers, not the random draws.
  4. Line 105: token ids, logprobs, top token ids and top logprobs must be equal. There is no tolerance.

The case uses EP 8 and 5 drafts (tests/models/test_batch_invariant.py:32-34). The deep dive below describes three more tests.

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

Worked example: one sum, three orders, three results

Take four FP32 numbers: x = [1e8, 1, −1e8, 1]. The exact sum is 2. Near 108, FP32 values are 8 apart (226 × 2−23), so 1e8 + 1 rounds back to 1e8.

OrderLike a kernel that…StepsResult
Aadds one row from left to right1e8 + 1 → 1e8; 1e8 − 1e8 = 0; 0 + 1 = 11
Bsplits K into 2 halves(1e8 + 1 → 1e8) + (−1e8 + 1 → −1e8) = 00
Csplits K by stride 2(1e8 − 1e8 = 0) + (1 + 1 = 2) = 22

Real kernels add thousands of products in FP32. So the differences are much smaller than in this example: usually a few units in the last place. But they are not zero.

From one bit to one token. Suppose two tokens have the logits 12.500000 and 12.499999 in run 1. In run 2, another order of a sum moves the second one up by 2 × 10−6. Greedy decoding now picks the other token. With random sampling, the seed fixes the draw u. But the running sum of the probabilities moves a little, and u can fall on the other side of a boundary. After one different token, the two runs see different inputs, so all later tokens can differ.

Where batch size enters. A kernel library tunes its work split for each problem shape. In a GEMM, the token count M is part of the shape. In decode attention, the number of requests and their lengths set how the key range is split across SMs. A batch-invariant kernel uses one split for every batch, and may be slower for some shapes.

Simplified

The last paragraph is general knowledge about GPU kernels, not a description of DeepGEMM or FlashMLA: their sources are not in this repository.

Scope of the promise. The README promises identical results "across different batch compositions" (README.md:27). It does not promise equal results for another EP size, another GPU model, or another library version. The tests compare runs of one deployment only.

Deep dive

The four tests, in detail

1. Batched against single (tests/models/test_batch_invariant.py). 64 prompts of random non-special tokens, with lengths from a normal distribution (mean 2,500, standard deviation 1,000, at least 1) (tests/models/test_batch_invariant.py:72-85). ignore_eos=True, so every request makes 50 tokens. The engine gets max_num_seqs=64 and 16,384 batched tokens (tests/models/test_batch_invariant.py:54-68). The single runs use golden tokens, so the comparison covers the logprobs of the same token sequence.

2. Decode against prefill (tests/models/test_kl.py). It checks a stronger property: the logprobs of decode steps must equal the logprobs that a full prefill of the same text gives.

  1. Pass 1: 3 image-and-text prompts of 16,384 tokens, 1,024 golden output tokens, with prompt_logprobs=True (tests/models/test_kl.py:127-151).
  2. Pass 2: each prompt plus its 1,024 output tokens as a new prompt, 1 new token (tests/models/test_kl.py:153-173).
  3. The prompt logprobs of the two passes must be equal (tests/models/test_kl.py:194-196). For the output part, the test computes a KL divergence estimate and requires it to be at most max_kl, which is 0.0 by default (tests/models/test_kl.py:30, tests/models/test_kl.py:197-206).

The environment also turns on EPLB moves every 1,000 steps with 32 extra experts. So the DeepEP flag of step 4 is active. The case uses CP 2 and 5 drafts (tests/models/test_kl.py:33-35, tests/models/test_kl.py:102-110). cal_diff returns 0 at once for equal tensors; otherwise it computes mean(exp(x − y) − 1 − (x − y)) (deepinfer/testing.py:4-12).

3. Vision encoder (tests/models/test_ve_batch_invariant.py). It encodes fixed random images in batches of 1, 2, 64 and 256 copies, and in random mixes of shapes (tests/models/test_ve_batch_invariant.py:47-49). Every image's embeddings must be bitwise equal to a batch with only that image (tests/models/test_ve_batch_invariant.py:1-14, tests/models/test_ve_batch_invariant.py:113-144). This test does not set the variable; it checks the encoder alone.

4. Random sampling kernel. The same probabilities give the same tokens after a permutation of the rows, and row by row (deepinfer/model_executor/layers/tilelang_ops/random_sampling.py:308-332).

Deep dive

Seeds: one SamplingParams for many prompts

SamplingParams makes its seed in the constructor: random.getrandbits(64) when seq_seed is None, else the value masked to 64 bits (deepinfer/sampling_params.py:74, deepinfer/sampling_params.py:85-91).

LLM.generate accepts one SamplingParams for all prompts. _add_request makes a deep copy for each request (deepinfer/entrypoints/llm.py:137-138, deepinfer/entrypoints/llm.py:151). A deep copy does not run the constructor again, so every request of that call gets the same seed. So, with the settings of this page, two requests with the same prompt in one call get the same tokens, also without a fixed seed. Across two calls of generate with two new SamplingParams objects, the seeds differ, unless you pass seq_seed.

Two requests with the same seed get the same random number u at the same position. Their tokens still differ when their probabilities differ.

What can go wrong#

  • The switch on Ascend. The worker stops with AssertionError at start-up (deepinfer/worker/runtime_config.py:61-63).
  • =off turns it on. Only 0, empty, false and False are false (deepinfer/environ.py:12-13). Use 0 and 1.
  • DSpark is on. The logits stay batch-invariant, but the draft budget depends on the batch (deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py:70-98), so the tokens can differ.
  • No fixed seed. Two separate SamplingParams objects get two random seeds (deepinfer/sampling_params.py:87-88).
  • Different deployment. Another EP size or GPU model is outside the promise of the README (README.md:27).

Why it matters. Bit-identical results make bugs reproducible, make A/B evaluations fair, and let a test compare a batched run with a single run without a tolerance. DeepInfer's own regression tests depend on this: they compare logprobs with ==.

Check yourself#

  1. 1
    Which three settings does the README give for deterministic sampling, and on which hardware?
    easy
    Show answer

    DEEPINFER_BATCH_INVARIANT=1, DEEPINFER_ENABLE_MTP_VARLEN=0 and a fixed seq_seed in SamplingParams, on NVIDIA only (README.md:28). On Ascend the worker asserts that the switch is off (deepinfer/worker/runtime_config.py:61-63).

  2. 2
    In FP32, what is (1e8 + 1) − 1e8, and why?
    easy
    Show answer

    0. FP32 values near 108 are 8 apart, so 1e8 + 1 rounds to 1e8 before the subtraction. In the other order, (1e8 − 1e8) + 1 = 1.

  3. 3
    Why does test_batch_invariant.py pass the batched output as golden_token_ids to the single runs?
    medium
    Show answer

    So that both runs process the same token sequence. The test then compares the model numbers (logprobs and top logprobs) exactly, and a single different sample cannot make all later positions different (tests/models/test_batch_invariant.py:99-105).

  4. 4
    With the offline LLM (NORMAL engine), does DEEPINFER_BATCH_INVARIANT change which attention kernel a dense packed-KV layer uses in decode?
    medium
    Show answer

    No. The switch appears only in the term for the PROMPT engine type (deepinfer/model_executor/models/v4_modules/attn.py:87-92). In a NORMAL engine, a dense packed-KV layer uses the plain FlashMLA call in any case. The switch changes the argument enable_batch_invariant of that call (deepinfer/model_executor/layers/attention_backend.py:141).

  5. 5
    The KL test sets DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL=1000. Which batch-invariance switch does that turn on, and what does the test require of the output logprobs?
    hard
    Show answer

    With both variables on, the DeepEP buffer gets allow_multiple_reduction=False (deepinfer/model_executor/parallel_utils/userbuffer.py:79, tests/models/test_kl.py:105-107). The prompt logprobs must be equal. The KL estimate between the decode logprobs and the logprobs of a full prefill must be at most max_kl = 0.0 (tests/models/test_kl.py:194-206).

Related pages

  • DSpark: DFlash drafts and confidence-scheduled verificationDSpark makes 5 drafts per request with the DFlash draft model and predicts how likely each draft is to pass. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
  • MLA attention: one latent vector per tokenIn DeepInfer's MLA, all query heads of a layer read one 512-value vector per token. This vector is the key and also the value, so the KV cache keeps one small entry per token.
  • Expert load balancing (EPLB)EPLB counts the tokens of every expert slot in every step. Every N steps it gives busy experts extra copies, places all copies so that the EP ranks get about the same work, and moves the expert weights in place.
  • deepinfer/sampling_params.py: SamplingParamsSamplingParams holds the per-request settings: temperature, top-p, top-k, seed, length, logprobs, EOS rules, grammar and golden tokens. This page lists every field with its default and checks, and follows each one to the sampler.
  • Environment variablesDeepInfer reads 59 DEEPINFER_* environment variables through one class, envs, in deepinfer/environ.py. This page lists each variable with its type, default, effect and the code that reads it, and tells when the value is read.
