MoE routing: the gate, top-k and the shared expert

IntermediateDeepInfer conceptsabout 9 min read + 7 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Mixture of Experts (MoE) Beginner
  • Parallelism basics Beginner
  • Number formats: BF16, FP8, FP4 Beginner

In one sentence

In each MoE layer, a small gate gives every token one score for each expert. The token goes to its k best experts and to the shared expert.

The idea#

A DeepSeek V4.1 MoE layer has many feed-forward networks, the experts. There are two kinds:

  • Routed experts. Each token uses only a few of them.
  • The shared expert. Every token uses it.

The gate decides which routed experts a token uses. The gate is one small linear layer. It turns the hidden state of a token into one score for each routed expert. Then top-k routing keeps the k experts with the highest scores. The layer output of the token is the weighted sum of its k expert outputs, plus the output of the shared expert.

Some experts get many more tokens than others. A busy expert makes its device slow, and the other devices must wait for it. The gate therefore adds a correction bias to the scores before it chooses. A negative bias makes a busy expert a little less attractive. The bias changes only the choice, not the weights of the chosen experts.

DeepInfer adds one more step. An expert can have more than one copy on the devices. The gate chooses a logical expert, and then a lookup table gives one physical copy (a "slot"). The page Expert load balancing (EPLB) explains why copies exist.

An everyday comparison. Think of a hospital help desk. For each patient, the desk picks the two best specialists. Every patient also sees the general nurse, who is the shared expert. The desk also knows that one specialist is often busy, so it sends a borderline patient to the next specialist. The comparison stops here: the help desk sees live queues, but the gate does not. In DeepInfer the bias is a fixed value from the checkpoint. Run-time balance comes from EPLB.

The picture#

Read panel 1 from stage 1 to stage 6. Amber marks the only place where the bias acts. Panel 2 shows one token with toy numbers. The weights in the result box use the score s, not s + bias.

Simplified

The gate math runs inside kernel libraries that are not in this repository: DeepGEMM on NVIDIA and tile_kernels on both platforms. DeepInfer only passes the settings. Stages 2 to 4 show the usual meaning of the setting names sqrtsoftplus, noaux_tc and norm_topk_prob. The repository does not show the formulas. Also, the rule that picks one copy of an expert is inside the kernel.

In the code#

Step 1: the parameter containers in moe.py#

The file v4_modules/moe.py holds only parameters, with the names and shapes of the Hugging Face checkpoint. Its docstring defines the expert counts that the whole MoE code uses:

TopKGate holds the gate weight and two biases. It accepts only one scoring function and one top-k method:

  • Lines 58-60: other values for scoring_func, topk_method or norm_topk_prob stop start-up with an AssertionError.
  • Lines 62 and 64: one fp32 bias for text tokens and one for image tokens. The loader fills them from the checkpoint names ffn.gate.bias and ffn.gate.bias_vl (deepinfer/hugging_face/names.py:61-62). No code changes them at run time.
  • Line 67: the gate weight stays in BF16. It does not use FP8.

Step 2: DeepseekMoE checks the config and builds the gate#

DeepseekMoE in v4_modules/mlp.py is the runtime class. It checks the same settings again and reads the routing values:

The gate is a ReplicatedLinear with an fp32 output (line 225). "Replicated" means that every device has the full gate. The image bias exists only for a vision model. Line 236 uses the text bias when e_score_correction_bias_vl is None. TopKGate always makes that parameter (deepinfer/model_executor/models/v4_modules/moe.py:63-64), so in practice the image bias comes from the checkpoint name ffn.gate.bias_vl.

Step 3: gate_forward#

gate_forward runs once per MoE layer and step. It collects the settings and calls one of two kernels:

  1. Lines 381-396: the settings. bias and image_bias are the correction biases. to_physical_map and logical_count come from EPLB (line 379). mask marks the valid tokens of the batch.
  2. Line 398: on NVIDIA (use_mega_gate = PLATFORM.is_gpu, deepinfer/model_executor/models/v4_modules/mlp.py:228), one DeepGEMM call does the gate GEMM and the top-k.
  3. Line 400: on Ascend, self.gate(hidden_states) makes the fp32 logits first. Then moe_topk_gate from tile_kernels does the top-k.

Both calls return topk_idx and topk_weights. The ids in topk_idx are physical slots, not logical experts. The comment at deepinfer/model_executor/models/v4_modules/mlp.py:196-198 says so: "The gate selects logical routed experts. EPLB maps each logical expert to one or more physical slots".

Step 4: where the choices go#

The layer gives the two tensors to the expert step. There are two paths (deepinfer/model_executor/models/v4_modules/mlp.py:571-574):

  • The DeepEP path: dispatch, grouped GEMMs, combine. See Expert parallelism: dispatch, grouped GEMM, combine.
  • The mega-MoE path: one DeepGEMM call. Here the gate writes its output straight into the symmetric buffer (deepinfer/model_executor/models/v4_modules/mlp.py:537-541). See Mega-MoE: the whole MoE layer in one call.

Step 5: the shared expert#

The checkpoint can have more than one shared expert. ReplicatedSharedExpert joins them into one wide MLP:

Every device has the full shared expert, so its tokens do not travel. On the DeepEP path, DeepInfer runs it on the local tokens and gives the result to combine as bias. Combine adds it to the sum of the routed outputs (deepinfer/model_executor/models/v4_modules/mlp.py:601-609). On the mega path, the shared expert is part of the one kernel call (deepinfer/model_executor/models/v4_modules/mlp.py:256, deepinfer/model_executor/models/v4_modules/mlp.py:554).

Step 6: routed expert weights are MXFP4#

The loader accepts only one checkpoint format: FP8 for most weights and FP4 for the routed experts, with blocks of 32 and UE8M0 scales:

The docs give the same format: "MoE routed-expert weights: per-32, ue8m0, MXFP4" (doc/inference_deployment_qa.md:221). MXFP4 stores two 4-bit values in one byte, and one scale factor byte for each 32 values. The shared expert and the gate do not use FP4.

The interactive visual on the page Expert load balancing (EPLB) shows what top-k routing does to the load of each device. Try it after this page.

The real numbers are not in the repository. The expert count, k and the scaling factor are in the config.json of the checkpoint, which the repository does not contain. This site uses toy numbers only.

No group-limited routing. Some DeepSeek models first pick expert groups and then experts inside the groups. _build_moe reads no group fields, and gate_forward passes no group setting. So DeepInfer V4.1 routing has no group limit.

Deep dive

gate_forward, line by line

  1. Lines 367-371. A profiling setting. If DEEPINFER_FORCE_IMBALANCE_RATIO is above 0 and the EP size is above 1, the gate is skipped. Random choices send more tokens to the first EP rank (see the deep dive on profiling settings).
  2. Line 373. images_seq_mask marks image tokens. Only a vision batch has it.
  3. Lines 374-377. gate_force_random is a bool per token. A prefill with context parallelism uses its reordered copy gate_force_random_cp.
  4. Lines 383-384. use_shared_as_routed=False and num_shared_experts=0: the gate does not treat the shared expert as a routed choice. The shared expert runs on its own path.
  5. Line 386. ep_rank goes to the kernel. The repository does not show what the kernel does with it.
  6. Lines 392-393. The EPLB tables of this layer: logical_to_physical_map (int32 [n_logical, extra + 1], -1 = no copy) and logical_count (int32 [n_logical]) (deepinfer/model_executor/eplb/__init__.py:51-52).
  7. Line 395. out: with mega-MoE, the gate writes into slices of the symmetric buffer and makes no new tensors.
Deep dive

A worked example with numbers

This example uses 8 logical experts, k = 2, and 4 extra slots on 4 EP ranks. All numbers are toy values. The formulas are the usual meaning of the setting names (see the note on the picture).

  1. Gate GEMM. The token has the logits [1.2, -0.5, 2.0, 0.3, 1.9, -1.0, 0.8, 0.1] in fp32.
  2. Score. softplus(z) = ln(1 + e^z), then the square root. For expert 2: ln(1 + e^2.0) = 2.127, and sqrt(2.127) = 1.458. All scores are positive.
  3. Choose. The biases are -0.35 for expert 2, +0.05 for expert 4, and 0 for the others. The values of s + bias are 1.210 (expert 0), 1.108 (expert 2) and 1.478 (expert 4). The top 2 are experts 4 and 0. Without the bias, the top 2 are experts 2 and 4.
  4. Weights. Normalize the scores without the bias: 1.428 / (1.428 + 1.210) = 0.541 and 0.459. Then multiply by routed_scaling_factor. With an example factor of 1.5, the weights are 0.812 and 0.688.
  5. Physical slots. 8 logical plus 4 extra gives 12 slots, so 3 slots per rank. The first layout is [0, 1, 2, 3, 4, 5, 6, 7, 0, 1, 2, 3] (deepinfer/model_executor/eplb/__init__.py:31-39). Expert 4 has one copy, in slot 4 (rank 1). Expert 0 has two copies: slot 0 (rank 0) and slot 8 (rank 2). The kernel picks one of the two.

The result for this token is topk_idx = [4, 0 or 8] and topk_weights = [0.812, 0.688].

Deep dive

Routed expert weights in MXFP4: layout and size

The runtime parameter of the routed experts is an int8 tensor (n_local, h_out, h_in // 2): two e2m1 values per byte. Its scale tensor .sf holds packed UE8M0 bytes in column-major order (deepinfer/hugging_face/weights.py:281-289). The loader reads the experts of this rank one at a time, joins w1 and w3 into linear1, and checks every shape (deepinfer/hugging_face/weights.py:300-326).

The grouped GEMM gets the block sizes as recipes: activations in blocks of 32, FP4 weights in blocks of 32 (deepinfer/model_executor/models/v4_modules/mlp.py:118-128). The FP8 block size is always 32 (deepinfer/model_executor/layers/linear.py:13-14).

A size example with toy sizes H = 4096 and moe_intermediate_size = 2048. The linear1 weight of one expert has 2 × 2048 × 4096 = 16,777,216 values.

  • MXFP4: 8 MiB of data plus 16,777,216 / 32 = 512 KiB of scales.
  • FP8 with 32 × 32 weight blocks: 16 MiB plus 16,777,216 / 1024 = 16 KiB of scales (one byte per scale). The checkpoint uses these blocks for FP8 weights (deepinfer/hugging_face/config.py:258).
  • BF16: 32 MiB.

The dummy-weight path. With load_format="dummy", process_moe_weight converts synthetic FP8 values into the FP4 layout. It asserts that the two low bits of each FP8 byte are zero: "Only support FP4-QAT checkpoint" (deepinfer/model_executor/models/v4_modules/mlp.py:59-60). A comment says that real loading fills the packed layout directly (deepinfer/model_executor/models/v4_modules/mlp.py:85-86).

Deep dive

Profiling settings: forced imbalance and forced random

DEEPINFER_FORCE_IMBALANCE_RATIO (float, default 0.0, deepinfer/environ.py:119). With a value ratio ≥ 1 and EP size above 1, the gate is replaced by random scores. The local experts of each rank get scores in U(0, f), the others in U(0, 1). Then torch.topk picks k (deepinfer/model_executor/models/v4_modules/mlp.py:329-345). The factor f comes from a mean-field formula:

Example: EP 8, 64 slots (8 per rank), k = 8, ratio 1.8:

  1. x = 1.8 / (1.8 + 7) = 0.2045: the share of all selections that rank 0 must get.
  2. t = 1 − (1 − 0.2045) × 8 / 56 = 0.886: the estimated top-k threshold.
  3. denom = 1 − 0.2045 × 8 / 8 = 0.7955, so f = 0.886 / 0.7955 = 1.114.

Line 336 gives the higher range to the first 8 columns. So EP rank 0 gets about 1.8 times the selections of each other rank.

Your value of DEEPINFER_FORCE_IMBALANCE_RATIO does not stay

The memory profile at start-up sets the value to 1.8, runs the profile, and then sets it to 0.0 (deepinfer/worker/model_runner.py:509-512). These lines write to envs directly. So after start-up the value is 0.0, also when you set the variable in the environment.

DEEPINFER_FORCE_LOAD_BALANCE (bool, default off, deepinfer/environ.py:120). The C++ input preparation copies it into gate_force_random for every token (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:82-86). The gate kernel gets it as force_random (deepinfer/model_executor/models/v4_modules/mlp.py:391). The field docstring says: "True: replace the token's gate logits with random values to balance MoE load" (deepinfer/model_executor/input_metadata/input_metadata.py:48-50).

What can go wrong#

Do not read topk_idx as logical expert ids

The gate returns physical slot ids. With extra experts, slot 8 can hold logical expert 0. To get the logical id, use physical_to_logical_map of the layer (deepinfer/model_executor/eplb/__init__.py:50).

  • Unsupported checkpoint. A checkpoint with another scoring function or top-k method stops start-up with an AssertionError (deepinfer/model_executor/models/v4_modules/moe.py:58-60). A checkpoint without FP4 experts stops with ValueError: Unsupported HF expert_dtype (deepinfer/hugging_face/config.py:261-262).
  • Forced imbalance below 1. A value between 0 and 1 fails the assertion at line 369 (deepinfer/model_executor/models/v4_modules/mlp.py:369).
  • One hot expert. The correction bias is fixed. If the traffic makes one expert very busy, its device is slow, and all EP ranks wait for it at combine. Use EPLB with extra experts (Expert load balancing (EPLB)).
  • Image tokens. A vision batch uses bias_vl only for tokens in images_seq_mask (deepinfer/model_executor/models/v4_modules/mlp.py:389-390). A text-only batch passes image_bias=None.

Why it matters. The gate decides where every token goes in every MoE layer. Its output decides the communication volume of dispatch and combine, and the load of each device. EPLB, expert parallelism and mega-MoE all start from topk_idx and topk_weights.

Check yourself#

  1. 1
    Which two kinds of experts does a token use in a DeepInfer MoE layer?
    easy
    Show answer

    Its k routed experts, which the gate chooses, and the shared expert, which every token uses. The shared expert is one wide MLP with a full copy on every device (deepinfer/model_executor/models/v4_modules/moe.py:24-37).

  2. 2
    Does the correction bias change the weight of a chosen expert?
    easy
    Show answer

    No, in the usual meaning of noaux_tc. The bias changes only which experts win the top-k, and the weights come from the scores without the bias. The kernel that does this is not in the repository. In the worked example, the weights are 1.428 / 2.638 and 1.210 / 2.638.

  3. 3
    On which platform does DeepInfer call deep_gemm.bf16_mega_gate, and what does the other platform call?
    medium
    Show answer

    On NVIDIA, because use_mega_gate = PLATFORM.is_gpu (deepinfer/model_executor/models/v4_modules/mlp.py:228). On Ascend, the gate ReplicatedLinear makes fp32 logits, and tile_kernels.moe.moe_topk_gate picks the experts (deepinfer/model_executor/models/v4_modules/mlp.py:397-400).

  4. 4
    A layer has 8 logical experts and 4 extra slots on 4 EP ranks, with the first layout. The gate chooses logical expert 1. Which slots can appear in topk_idx, and on which ranks are they?
    hard
    Show answer

    The first layout is [0..7, 0, 1, 2, 3] (deepinfer/model_executor/eplb/__init__.py:36-39). Logical expert 1 is in slot 1 and slot 9. With 3 slots per rank, slot 1 is on rank 0 and slot 9 is on rank 3. logical_count[1] = 2, and the gate kernel picks one of the two.

  5. 5
    You export DEEPINFER_FORCE_IMBALANCE_RATIO=2.0 before start-up. Is routing random during serving?
    hard
    Show answer

    No. The memory profile writes 1.8 and then 0.0 into envs.DEEPINFER_FORCE_IMBALANCE_RATIO (deepinfer/worker/model_runner.py:509-512). After start-up the value is 0.0, so gate_forward uses the real gate (deepinfer/model_executor/models/v4_modules/mlp.py:367).

Related pages

  • Expert parallelism: dispatch, grouped GEMM, combineDeepInfer splits the expert slots of every MoE layer evenly over the EP ranks. DeepEP dispatch sends each token to the ranks of its experts, DeepGEMM runs grouped GEMMs there, and DeepEP combine brings the results back.
  • Mega-MoE: the whole MoE layer in one callInside one NVLink domain, DeepInfer replaces dispatch, the expert GEMMs, the shared expert and combine with one DeepGEMM mega-MoE call that works on a symmetric buffer. The choice is fixed per layer at start-up.
  • Expert load balancing (EPLB)EPLB counts the tokens of every expert slot in every step. Every N steps it gives busy experts extra copies, places all copies so that the EP ranks get about the same work, and moves the expert weights in place.
  • Low-precision formats in DeepInferDeepInfer keeps most weights in FP8 E4M3 with 32 × 32 block scales, routed experts in MXFP4, activations in FP8 with one scale per 32 values, the compressed KV in FP4 and the window KV in MXFP8. Scales are UE8M0 bytes, packed 4 per int32 on NVIDIA and 2 per int16 on Ascend.
  • v4_modules/mlp.py: the DeepseekMoE layerDeepseekMoE is the runtime MoE layer of DeepInfer. It converts the moe.py containers into the runtime layout, runs the gate, and then either DeepEP dispatch, grouped GEMMs and combine, or one mega-MoE call.
