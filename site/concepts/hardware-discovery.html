Hardware discovery (deep_cluster)

IntermediateDeepInfer conceptsabout 9 min read + 7 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • GPUs, kernels, and speed Beginner
  • Hardware platforms: NVIDIA and Ascend Intermediate

In one sentence

The package deep_cluster reads Linux files to find the accelerator type, the devices and their NUMA nodes. It never imports PyTorch, so code can use it before the device runtime starts.

The idea#

A process must choose its devices before the device runtime starts. On NVIDIA, a CUDA_VISIBLE_DEVICES value that is set after CUDA starts has no effect. A source comment says this, in Chinese: "Importing dependencies can call torch.cuda.is_available. If CUDA initializes early, a later CUDA_VISIBLE_DEVICES has no effect, so the NVML check is used instead." (translated, deepinfer/__init__.py:37-39). On Ascend, import torch alone starts the ACL runtime, and a later ASCEND_RT_VISIBLE_DEVICES fails (translated, examples/_config.py:102).

But to choose devices, a launcher must know what the host has. So DeepInfer needs a way to look at the hardware with no PyTorch, no CUDA and no CANN. That is deep_cluster. It has two parts:

  • deep_cluster.hardware answers "which accelerator, how many devices, which NUMA node for each device, how fast". It reads procfs (/proc), sysfs (/sys) and device files in /dev. For two values it runs a small tool or library: npu-smi and lscpu for the Ascend NUMA node (deep_cluster/hardware/ascend.py:109-110), and NVML for the NVIDIA compute capability (deep_cluster/hardware/nvidia.py:82-108).
  • deep_cluster.topology binds the current process to the CPU cores and the memory of one NUMA node (deep_cluster/topology/__init__.py:1). Its module docstring says: "NUMA lookup and process binding without accelerator runtime imports" (deep_cluster/topology/bind.py:1).

The main function is accelerator_kind(). It returns "ascend", "nvidia" or "cpu" (deep_cluster/hardware/device.py:14). The page Hardware platforms: NVIDIA and Ascend shows how DeepInfer turns this answer into a Platform object.

An everyday comparison. Before you move into an office building, you read the floor plan at the door. It shows how many rooms there are, and which kitchen is nearest to each room. You do not need a key to read it. deep_cluster is the floor plan: the devices are the rooms, and the NUMA nodes are the kitchens. The analogy stops at trust: a floor plan can be old. A device file can exist while the driver does not work. deep_cluster does not test the devices. The first real device call does that.

Read panel 1 from left to right: the first box that finds a device wins. Panel 2 shows that every other answer depends on that first answer. In panel 3, the blue steps run before the device runtime starts. This is the reason the package must not import PyTorch.

In the code#

Step 1: which accelerator#

The Ascend test is true if any one of three signals exists (deep_cluster/hardware/ascend.py:61-68):

  • the file /dev/davinci_manager;
  • a file /dev/davinci<N> (deep_cluster/hardware/ascend.py:13);
  • an entry /sys/class/ubcore/udma* whose device/ub_totalues is above 0 (deep_cluster/hardware/ascend.py:21-37).

The NVIDIA test is true if the driver lists a GPU folder in /proc/driver/nvidia/gpus, or if a file /dev/nvidia<N> exists:

With no signal, the answer is "cpu". There is no error at this point.

Step 2: how many devices, and which are visible#

physical_device_count() counts all devices of the host for the kind from step 1 (deep_cluster/hardware/device.py:26-33). get_actual_num_gpus() is the same number (deep_cluster/hardware/device.py:139-140). It does not look at the visible devices. Other functions read the visible-device variable of the kind: ASCEND_RT_VISIBLE_DEVICES or CUDA_VISIBLE_DEVICES (deep_cluster/hardware/device.py:36-43):

  • Variable not set: all physical devices are visible, as "0", "1", ... (line 63).
  • Empty or "-1": no device is visible (lines 64-65).
  • physical_device_id(local_rank) maps a visible index to the id in the variable, and raises IndexError for a bad index (lines 87-90).

Step 3: the NUMA node of a device#

A device sits on a PCI bus near one CPU socket. Copies between the CPU and the device are faster with memory of that socket's NUMA node. device_numa_node(index) finds the node (deep_cluster/hardware/device.py:129-136).

NVIDIA. Take the PCI bus id of device index from /proc/driver/nvidia/gpus, then read /sys/bus/pci/devices/<bus id>/numa_node:

Ascend. First ask npu-smi info -t topo -i 0 for the CPU affinity of each NPU. Then pick the NUMA node whose physical cores (from lscpu) overlap that affinity most (deep_cluster/hardware/ascend.py:107-127). If the tool is missing or fails, use the numa file of the ubcore entry (deep_cluster/hardware/ascend.py:130-144). The deep dive gives both paths in detail.

Step 4: bind the process near its device#

which_numa(i_gpu) turns a visible index into a physical device index, then calls device_numa_node (deep_cluster/topology/bind.py:42-63). bind_numa(node) then sets the CPU affinity of the process to the cores of the node, and its memory policy to that node:

Each worker does three things in a fixed order at start-up:

  1. _bind_numa(local_rank): CPU affinity and memory policy for the NUMA node of the worker's device (deepinfer/worker/base.py:347-357).
  2. torch.cuda.set_device: the device runtime starts here, after the memory policy is set.
  3. bind_cpu(gpu_id): a narrower CPU affinity, an even share of the physical cores per device (deepinfer/utils.py:143-151). gpu_id is the physical id from CUDA_VISIBLE_DEVICES (deepinfer/worker/base.py:125-127).

Step 5: the speed limit and the SM check#

get_bf16_tflops_limit() returns the peak BF16 speed in TFLOPS. It is 432 on Ascend. With an SM 10.x GPU, it is 2250 on x86 hosts and 2500 on Arm hosts. Any other host raises RuntimeError("unknown GPU type"). is_sm_major_10() reads the compute capability of device 0 through NVML, so no CUDA context starts (deep_cluster/hardware/nvidia.py:111-129). The engine uses the limit for its MFU statistic: tflops_limit=get_bf16_tflops_limit() * 2, with the comment "FP8-equivalent peak: 2x BF16" (deepinfer/engine/llm_engine.py:298-305, deepinfer/engine/stats_logger.py:203-209).

Step 6: the callers that run before the device runtime#

  • The build. setup.py builds an NPU or a CUDA extension: IS_NPU = accelerator_kind() == "ascend" (setup.py:10-12).
  • The example launcher. examples/_config.py imports deep_cluster.hardware at the top and must not import deepinfer there (examples/_config.py:5-6, examples/_config.py:26). setup_cuda_visible_devices gives each engine cp_size devices, and copies the value to ASCEND_RT_VISIBLE_DEVICES on Ascend (examples/_config.py:55-63).
  • The package import. deepinfer/__init__.py picks the folder of the compiled extension. It calls accelerator_kind() only when DEEPINFER_ACCELERATOR is empty (deepinfer/__init__.py:15-25).
  • The platform. get_platform() makes PlatformNPU only for "ascend" (deepinfer/platform.py:222-227).
  • Kernel tests. The test configuration binds each pytest-xdist worker to one GPU at import time, "using only deep_cluster.hardware (no CUDA initialization)" (deepinfer/model_executor/layers/tilelang_ops/conftest.py:30-46).

Deep dive#

Deep dive

NVIDIA discovery on a sample host

Assume a host with 8 GPUs. The driver makes these folders (bus ids are an example):

/proc/driver/nvidia/gpus/0000:18:00.0/
/proc/driver/nvidia/gpus/0000:2a:00.0/
/proc/driver/nvidia/gpus/0000:3a:00.0/
/proc/driver/nvidia/gpus/0000:5d:00.0/
/proc/driver/nvidia/gpus/0000:9a:00.0/
/proc/driver/nvidia/gpus/0000:ab:00.0/
/proc/driver/nvidia/gpus/0000:ba:00.0/
/proc/driver/nvidia/gpus/0000:db:00.0/
  1. _proc_entries() lists the folders, sorted by name (deep_cluster/hardware/nvidia.py:18-25). device_ids() returns the 8 names. accelerator_kind() returns "nvidia" (if no Ascend signal exists), and physical_device_count() returns 8.
  2. device_numa_node(5): bus id 0000:ab:00.0. Read /sys/bus/pci/devices/0000:ab:00.0/numa_node. If that file is missing, try /sys/bus/pci/drivers/nvidia/0000:ab:00.0/numa_node (deep_cluster/hardware/nvidia.py:64-78). The value is parsed with int(text, 0), so "1" gives 1.
  3. Without /proc/driver/nvidia/gpus (for example in some containers), the ids come from /dev/nvidia0 to /dev/nvidia7 (deep_cluster/hardware/nvidia.py:28-44). The count still works, but device_numa_node raises RuntimeError("NUMA metadata is unavailable ..."), because it needs the bus ids (deep_cluster/hardware/nvidia.py:60-62).

The compute capability. _nvml() loads libnvidia-ml with ctypes and calls nvmlInit_v2. It returns None if the library is missing or the call fails (deep_cluster/hardware/nvidia.py:82-108). compute_capability(index=0) asks NVML for device 0 and returns (major, minor), or None (deep_cluster/hardware/nvidia.py:111-129). Its docstring: "no CUDA context is created".

Deep dive

Ascend discovery: ubcore entries and two NUMA paths

Device list. _entries() lists /sys/class/ubcore entries named udma<N> or udmac<C>d<D>e<E>. It sorts plain numbers first, then the controller/die/entity form (deep_cluster/hardware/ascend.py:12, deep_cluster/hardware/ascend.py:21-37). discover_npu_devices() keeps the entries with ub_totalues > 0 and returns (entry name, physical id, numa) for each (deep_cluster/hardware/ascend.py:71-85). Without such entries, it uses the /dev/davinci<N> numbers and NUMA −1.

NUMA path 1: npu-smi.

  1. Line 109: run npu-smi info -t topo -i 0.
  2. Line 110: get the physical cores per NUMA node from lscpu -p=CPU,NODE,SOCKET,CORE,ONLINE. One logical CPU per (node, socket, core), the smallest one, so hyper-threads do not count twice (deep_cluster/hardware/cpu.py:9-47).
  3. Lines 115-121: take each line that starts with NPU<id>. Parse every field that looks like a CPU list (0-23,48-71), and keep the largest set.
  4. Lines 123-126: the NUMA node is the one with the largest overlap between its physical cores and that set.

This path runs only for the real root /, and errors of the tool are caught (deep_cluster/hardware/ascend.py:131-137). The result is cached once per process (line 107).

NUMA path 2: the ubcore file. If the index is not in the npu-smi result, the code reads the raw node from the device list. It returns (raw_numa // 2) × 2 + index % 2 (deep_cluster/hardware/ascend.py:138-144). Example: raw node 3 for device 4 gives 2 + 0 = 2. Raw node 3 for device 5 gives 2 + 1 = 3. The code has no comment that gives the reason for this formula. A raw value of −1 raises RuntimeError.

Visible ids on Ascend. which_numa takes the trailing digits of the visible id as the physical index, so an id such as "npu5" gives 5 (deep_cluster/topology/bind.py:56-58).

Deep dive

bind_numa and bind_cpu: a worked example

bind_numa(node), line by line (deep_cluster/topology/bind.py:79-93):

  1. Line 80: load libnuma.so.1 once. If it is missing, raise OSError("libnuma.so.1 is required for NUMA binding") (deep_cluster/topology/bind.py:25-39).
  2. Lines 81-84: get the CPU mask of the node. On failure, print an error to stderr and return −1.
  3. Lines 85-87: set this process's CPU affinity to the mask. On failure, print and return −1.
  4. Lines 88-92: make a node mask with one bit, and call set_mempolicy(MPOL_BIND, ...). On failure, print and return −1.
  5. Line 93: return 0.

bind_cpu(gpu_id) splits the physical cores evenly over the physical devices (deepinfer/utils.py:143-151). Example: 2 sockets with 64 physical cores each and 8 GPUs. psutil.cpu_count(logical=False) = 128, so each GPU gets 16 cores. The worker of GPU 3 binds to cores 48 to 63. The calculation does not ask which cores are in which NUMA node. It assumes that core numbers follow the device order.

The order. In init_model, _bind_numa sets the CPU affinity to all cores of the node and the memory policy to the node. Then bind_cpu replaces only the CPU affinity, with the 16 cores. The memory policy stays (deepinfer/worker/base.py:185-191).

The image workers. The engine process binds itself with _bind_numa(local_rank=0) before it forks the image workers (deepinfer/engine/llm_engine.py:211-213). Each image worker binds to the NUMA node of visible device 0. With 2-way SMT, it then takes the sibling hyper-threads phy_cpus + [0, n) (deepinfer/ve/multimodal_processor.py:173-190). The comment says the goal is "to stay off the main process's cores".

Open question

The image worker computes its CPU list from visible_index = 0, not from the physical device id. The worker uses the physical id (deepinfer/worker/base.py:191). So for an engine on GPU 3, the image worker takes the siblings of cores 0-15, not of cores 48-63. This is derived from the code; we did not run it. The supervisor has the question.

What can go wrong#

Set the visible devices before the first device call

Call deep_cluster functions, set CUDA_VISIBLE_DEVICES (and ASCEND_RT_VISIBLE_DEVICES on Ascend), and only then import PyTorch code that can start the runtime. The example launcher follows this order (examples/_config.py:104-110).

  • Wrong kind on a mixed host. A host with both Ascend and NVIDIA files is Ascend, because that test runs first (deep_cluster/hardware/device.py:19-20).
  • Old answer. accelerator_kind, physical_device_count and device_numa_node are cached. A change of the device files during the process is not seen.
  • Engine start-up fails on other GPUs. get_bf16_tflops_limit() runs in every engine, and raises on an NVIDIA GPU that is not SM 10.x (deepinfer/engine/llm_engine.py:304). The README supports only SM100 GPUs and Ascend 950 (README.md:33-36).
  • Slow copies with no error. A failed NUMA binding gives only a warning or a stderr line. Memory can then come from the far node.
  • Counts are physical, not visible. get_actual_num_gpus() counts all devices of the host. bind_cpu divides the cores by this number, also when the process sees only 2 devices (deepinfer/utils.py:145-147).

Why it matters. Start-up order is strict on both platforms: discover, choose devices, then start the runtime. deep_cluster makes the first part possible with no runtime. NUMA binding then keeps each rank's host memory and CPU work near its device, which matters for the many host-to-device copies of an inference engine.

Check yourself#

  1. 1
    What are the three possible values of accelerator_kind(), and which one is tested first?
    easy
    Show answer

    "ascend", "nvidia" and "cpu". Ascend is tested first (deep_cluster/hardware/device.py:17-23).

  2. 2
    Why does deep_cluster not import PyTorch?
    easy
    Show answer

    Callers use it before the device runtime starts, to choose the visible devices. On NVIDIA, CUDA ignores a later CUDA_VISIBLE_DEVICES; on Ascend, import torch starts ACL (deepinfer/__init__.py:37-39, examples/_config.py:102).

  3. 3
    On an NVIDIA host, how does device_numa_node(2) find the node?
    medium
    Show answer

    It takes the third folder name (sorted) in /proc/driver/nvidia/gpus, which is a PCI bus id. Then it reads /sys/bus/pci/devices/<bus id>/numa_node, or the same file under /sys/bus/pci/drivers/nvidia/ (deep_cluster/hardware/nvidia.py:55-79).

  4. 4
    A host has 96 physical cores and 8 GPUs. The worker uses GPU 6. Which cores does bind_cpu give it?
    medium
    Show answer

    96 // 8 = 12 cores per GPU, so cores 72 to 83 (deepinfer/utils.py:143-151). This comes after _bind_numa, which already set the memory policy to the NUMA node of GPU 6.

  5. 5
    An Ascend host has no npu-smi. The ubcore entry of device 7 has numa = 5. What does device_numa_node(7) return, and why is no exception raised?
    hard
    Show answer

    (5 // 2) × 2 + 7 % 2 = 4 + 1 = 5. The missing tool raises FileNotFoundError inside _npu_smi_numa_nodes, and device_numa_node catches it and uses the ubcore value (deep_cluster/hardware/ascend.py:130-144).
