Mega-MoE: the whole MoE layer in one call

AdvancedDeepInfer conceptsabout 7 min read + 4 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • MoE routing: the gate, top-k and the shared expert Intermediate
  • Expert parallelism: dispatch, grouped GEMM, combine Advanced

In one sentence

Mega-MoE does a whole MoE layer, from dispatch to combine, in one DeepGEMM call. DeepInfer uses it when the EP group fits in one NVLink domain.

The idea#

On the DeepEP path, one MoE layer is a chain of separate steps. They are dispatch, a grouped GEMM, the SwiGLU activation, a second grouped GEMM, the shared expert, and combine. Each step is at least one kernel launch, and the two communication steps go through a DeepEP buffer.

In one NVLink domain, every GPU can read and write the memory of the other GPUs directly. A symmetric memory buffer has the same layout on every rank, so a kernel on one rank knows where to write on another rank. Mega-MoE uses this. One DeepGEMM call moves the tokens, runs both expert GEMMs and the shared expert, and adds the results. DeepInfer prepares the inputs in the symmetric buffer and makes this one call.

The docs answer the question "When is Mega MoE used?" with two claims (doc/inference_deployment_qa.md:229-231):

  • "Mega MoE is the general solution within a scale-up domain".
  • "regardless of EP size or batch size, Mega MoE is significantly faster than unfused MoE".

An everyday comparison. Think of a team that writes a report together. On the DeepEP path, each writer mails pages to the others, waits for answers, edits, and mails the pages back. With mega-MoE, the team works in one shared document. Each writer edits the right place directly, and nobody waits for the mail. The comparison stops here: the shared document works only for people in the same building. Mega-MoE works only inside one NVLink domain.

In the code#

Step 1: the decision#

  1. Lines 177-181: mma_type joins the activation type and the weight type, for example "fp8xfp4". Line 182 allows only three values.
  2. Line 185: on GPU, the type does not matter. On Ascend, only "fp8xfp4" qualifies.
  3. Line 186 repeats the check of line 182, so it is always true here.
  4. Line 187: the EP group must fit in one NVLink domain.

The checkpoint loader accepts only FP8 checkpoints with FP4 experts (deepinfer/hugging_face/config.py:254-262). So fp8_mlp and mxfp4 are both true (deepinfer/hugging_face/config.py:300-305), and mma_type is "fp8xfp4". In practice:

  • On NVIDIA, a layer uses mega-MoE when its EP group fits in the NVLink domain.
  • On Ascend, a layer always uses mega-MoE.

Step 2: the weights get a new layout at start-up#

Line 255 picks the kernel: fp8_fp4_mega_moe for FP8 activations, else bf16_mega_moe. Line 256 puts the shared expert into the same call when the layer has one. _convert_mega_moe_weight calls deep_gemm.transform_weights_for_mega_moe, keeps a copy, and frees the old storage (deepinfer/model_executor/models/v4_modules/mlp.py:93-106).

Step 3: a symmetric buffer instead of an EP buffer#

A mega layer asks the userbuffer manager for a deep_gemm.SymmBuffer. DeepInfer uses its fields for the token rows (x), their scales (x_sf), and the top-k ids and weights. The manager makes the buffer for the first spec and gives later layers views of it (deepinfer/model_executor/parallel_utils/userbuffer.py:183-225). A mega layer never makes a DeepEP EPBuffer.

Step 4: the norm writes into the buffer#

Before the MoE layer, the FFN norm casts the hidden states to FP8. On the mega path, the layer asks the norm to write the result straight into the symmetric buffer:

The decoder layer calls this method through _fused_cast_kwargs before the norm (deepinfer/model_executor/models/v4_modules/hc.py:52-54, deepinfer/model_executor/models/v4_modules/hc.py:146). Lines 283-288 set the FP8 format: e4m3, a UE8M0 scale for each 32 values, packed, in row-major order. With a fused shared expert on GPU, the norm also writes the scales that the shared expert needs (lines 291-300).

Step 5: mega_moe_forward#

  1. Lines 537-541: the gate writes topk_idx and topk_weights into the buffer (out=).
  2. Lines 542-546: with FP8, the code only checks that the norm wrote into the buffer. With BF16, it copies the input in.
  3. Lines 549-559: the one call. It also gets the EPLB counter of the layer, so EPLB works on both paths.
  4. Lines 561-562: only a layer with no fused shared expert runs shared_forward after the call. With out_acc=out, the shared output is added into out.

No log line names the path. You can see it in the start-up log. The first symmetric buffer logs "Created DeepGEMM ... SymmetricBuffer" (deepinfer/model_executor/parallel_utils/userbuffer.py:222-223). The first EP buffer logs "Created DeepEP-V2 ... EPBuffer" (deepinfer/model_executor/parallel_utils/userbuffer.py:91-94). Later layers that get the same buffer, or a view of it, log nothing.

The docs and deployment sizes. The docs recommend EP2–8 for prefill and EP64–128 for decode (doc/inference_deployment_qa.md:47-49). Whether a given EP size fits in one NVLink domain depends on the hardware. DeepInfer asks DeepEP for the domain size at start-up and does not hard-code it.

Deep dive

The SymmBuffer: spec, base and views

A spec has exactly the arguments of deep_gemm.SymmBuffer. The manager keeps one buffer per spec in a dict:

  1. Line 210: an equal spec gets the same buffer object.
  2. Line 214: the first buffer in the dict is the base. It owns the memory.
  3. Lines 215-220: before the first buffer on GPU, DeepInfer starts DeepGEMM's SM locality probe. The comment says that the probe synchronizes, so it must run before CUDA-graph capture.
  4. Line 221: a later spec becomes a view of the base (base=base).

The docstring gives a rule: "The first spec allocated must be the largest" (line 195). The model allocates the main layers first and the DFlash draft layers after them (deepinfer/model_executor/models/deepseek.py:422-428). The unit test checks that a smaller spec becomes a view of the first one (tests/worker/test_userbuffer.py:66-73).

Size inputs. num_max_tokens_per_rank is max_num_tokens: the prefill limit for a NORMAL engine, the decode limit for a COMPLETION engine (deepinfer/model_executor/models/v4_modules/mlp.py:175). intermediate_hidden is prod(gate_up_proj_weight.shape[1:-1]) // 2 (deepinfer/model_executor/models/v4_modules/mlp.py:311). num_shared_experts is the real count only when the shared expert is fused.

The call has no num_sms argument. On the DeepEP path, DeepInfer splits the SMs between communication and compute itself. On the mega path, that choice is inside DeepGEMM.

Deep dive

The fused norm: what it writes, byte by byte

On the mega path with FP8 activations, the norm gets three extra arguments (deepinfer/model_executor/models/v4_modules/mlp.py:280-290):

  • out = (sym_buffer.x[:T], sym_buffer.x_sf[:T]): the first T rows of the buffer.
  • fp8_cast_params: format e4m3, 32 values per scale, rounded scales, packed UE8M0, and not the TMA-aligned column-major layout.
  • extra_sf_layout = "mega_moe".

Packed UE8M0 means that one scale factor byte covers 32 values, and 4 bytes (NVIDIA, int32) or 2 bytes (Ascend, int16) share one integer (deepinfer/platform.py:63, deepinfer/platform.py:138). The norm module documents this layout as "the mega-MoE x_sf layout" (translated, deepinfer/model_executor/layers/tilelang_ops/norm.py:34-36). Example with a toy hidden size 4096: one token has 4096 / 32 = 128 scale bytes. On NVIDIA, that is 32 int32 values per row.

On GPU with a fused shared expert, the norm also writes shared_l1_acts_sf. Its block size comes from deep_gemm.get_block_m_for_mega_moe(ep_size, num_physical_experts, num_max_tokens_per_rank, T, k, mma_type) (deepinfer/model_executor/models/v4_modules/mlp.py:291-300).

What can go wrong#

A larger EP group silently uses the other path

If the EP group grows past the NVLink domain on NVIDIA, the layer uses the DeepEP path. Nothing fails, and no message names the path. Check the start-up log for "SymmetricBuffer" or "EPBuffer".

  • The norm did not write into the buffer. With FP8, mega_moe_forward asserts that the input tensors are the buffer tensors (deepinfer/model_executor/models/v4_modules/mlp.py:543-544). If sym_buffer was not made yet, fused_norm_cast_kwargs returns {} and the assertion fails (deepinfer/model_executor/models/v4_modules/mlp.py:277-279). The model makes the buffers in its constructor, before any forward pass (deepinfer/model_executor/models/deepseek.py:319-321).
  • Buffer order. The first SymmBuffer spec must be the largest. DeepInfer does not check this rule; it is only in the docstring (deepinfer/model_executor/parallel_utils/userbuffer.py:195).
  • Ascend with other data types. On Ascend, only fp8xfp4 layers use mega-MoE. Other types use DeepEP-Ascend.
  • Memory. The weights are converted with clone(), and the old storage is freed after the copy (deepinfer/model_executor/models/v4_modules/mlp.py:99-105). For a short time, a layer needs memory for both layouts.

Why it matters. For the released checkpoint format, mega-MoE is the normal path for prefill and for decode inside one NVLink domain. The DeepEP page describes the steps that the one call replaces.

  1. 1
    What replaces dispatch, the two grouped GEMMs, the shared expert and combine on the mega path?
    easy
    Show answer

    One call of deep_gemm.fp8_fp4_mega_moe (or bf16_mega_moe for BF16 activations) (deepinfer/model_executor/models/v4_modules/mlp.py:255, deepinfer/model_executor/models/v4_modules/mlp.py:549-559).

  2. 2
    A deployment runs the released checkpoint on Ascend with EP 16. Which path does each MoE layer use? Why?
    medium
    Show answer

    Mega-MoE. mma_type is "fp8xfp4", so condition A is true, and is_within_nvl_domain always returns True on NPU (deepinfer/model_executor/parallel_utils/parallel_state.py:132-133).

  3. 3
    Where does the FFN norm put its FP8 output on the mega path?
    medium
    Show answer

    Straight into sym_buffer.x and sym_buffer.x_sf, through the out argument of fused_norm_cast_kwargs (deepinfer/model_executor/models/v4_modules/mlp.py:281). mega_moe_forward checks the pointers (deepinfer/model_executor/models/v4_modules/mlp.py:543-544).

  4. 4
    Does EPLB still get token counts when a layer uses mega-MoE? Which argument carries them?
    hard
    Show answer

    Yes. The mega call gets cumulative_local_expert_recv_stats=self._eplb_layer().expert_count (deepinfer/model_executor/models/v4_modules/mlp.py:555), the same counter that DeepEP dispatch gets on the other path (deepinfer/model_executor/models/v4_modules/mlp.py:474). Also, the gate gets the EPLB tables on both paths.

Related pages

  • Expert load balancing (EPLB)EPLB counts the tokens of every expert slot in every step. Every N steps it gives busy experts extra copies, places all copies so that the EP ranks get about the same work, and moves the expert weights in place.
  • Hardware platforms: NVIDIA and AscendDeepInfer runs on NVIDIA GPUs and on Huawei Ascend NPUs. At start-up it makes one Platform object, and the shared code reads all hardware choices from it.
  • Low-precision formats in DeepInferDeepInfer keeps most weights in FP8 E4M3 with 32 × 32 block scales, routed experts in MXFP4, activations in FP8 with one scale per 32 values, the compressed KV in FP4 and the window KV in MXFP8. Scales are UE8M0 bytes, packed 4 per int32 on NVIDIA and 2 per int16 on Ascend.
  • mHC residual mixingDeepSeek-V4.1 keeps the residual stream as hc_mult parallel streams. Before each sub-layer, learned weights mix the streams into one input. After it, the output goes back into all streams. The model ends with one fold.
  • v4_modules/mlp.py: the DeepseekMoE layerDeepseekMoE is the runtime MoE layer of DeepInfer. It converts the moe.py containers into the runtime layout, runs the gate, and then either DeepEP dispatch, grouped GEMMs and combine, or one mega-MoE call.
  • parallel_utils/userbuffer.py: the communication buffer manageruserbuffer.py owns all long-lived communication buffers of one loaded model: the DeepEP buffer for MoE, the DeepGEMM symmetric buffers for mega-MoE, the context-parallel bucket buffer, and the Engram buffer. It also limits the SMs of compute kernels while DeepEP runs.
