Context parallelism (mirror CP)

AdvancedDeepInfer conceptsabout 11 min read + 6 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

  • Parallelism basics Beginner
  • Attention, step by step Beginner
  • Prefill and decode Beginner
  • Input metadata (varlen batching) Intermediate

In one sentence

With context parallelism, several devices of one engine share the tokens of a prefill. Each device takes one early part and one late part of each prompt, so the work is balanced.

The idea#

A long prompt needs much prefill work. Context parallelism (CP) splits this work by tokens. One engine uses cp_size devices. Each device computes the rows of some tokens of each prompt. The README lists this feature as "balanced CP" (README.md:12).

A plain split has a problem. Attention is causal: token i reads the keys of tokens 0 to i. So late tokens cost more than early tokens. If device 0 takes the first half and device 1 takes the second half, device 1 does much more attention work.

DeepInfer uses a mirrored order, the CP mirror. It cuts each prompt into 2 × cp_size equal parts. Rank r takes part r and part 2 × cp_size − 1 − r. So each rank gets one cheap part from the start and one expensive part from the end.

The ranks still need each other's keys and values. In every attention layer, each rank computes K and V for its own rows. Then an all-gather gives every rank the K and V of all tokens. At the end of the model, a second all-gather gives every rank the output of all tokens.

An everyday comparison. Two people must read a staircase of books: book 1 has 1 page, book 2 has 2 pages, up to book 8 with 8 pages. One person takes books 1 to 4, and the other takes books 5 to 8. Then the first reads 10 pages and the second reads 26. If the first takes books 1, 2, 7 and 8, and the second takes books 3 to 6, both read 18 pages. The analogy stops here: in DeepInfer, the ranks also exchange data (the keys and values) in every layer, and all ranks store the full result.

Simplified

The page counts are the number of keys that each query reads in plain causal attention. The real cost per token also depends on sliding-window and sparse attention, which read a limited number of keys. See Sliding-window attention and Sparse attention with an indexer.

The picture#

Read panel 1 from top to bottom. The colour of a token shows its rank. In panel 2, green cards run on the own rows of one rank. Amber cards are all-gathers over the CP group. After an amber card, every rank has the data of all 8 tokens again.

In the code#

Step 1: CP ranks are processes of one engine#

One engine is one data-parallel replica. With context_parallel_size above 1, the engine starts cp_size − 1 extra processes. The engine process itself is CP rank 0, the driver:

A spawned process makes a Worker and never returns. At the end of its constructor, a CP follower enters a loop. In the loop, it gets a method name and arguments from the driver, and calls that method (deepinfer/worker/base.py:120-123, deepinfer/worker/base.py:129-133). The driver sends each call before it runs the same method itself:

The channel is a MessageQueue in shared memory on the CPU CP group (deepinfer/model_executor/parallel_utils/parallel_state.py:17-23, deepinfer/model_executor/parallel_utils/parallel_state.py:122-124). The page distributed/shm_broadcast.py: MessageQueue explains it.

The global rank of a process is engine_rank × cp_size + cp_rank (deepinfer/worker/base.py:329). So the CP ranks of one engine are neighbours, and each CP group is a block of cp_size ranks (deepinfer/model_executor/parallel_utils/parallel_state.py:96-99). The "model parallel size" of DeepInfer is the CP size (deepinfer/config.py:171).

Step 2: the driver sends the inputs#

Only the driver has the scheduler and the sequence list. The followers get seq_metadata_list = None. So the driver builds the input metadata and sends it to the followers:

broadcast_tensor_dict splits the dict. Small Python values and the shapes of the tensors go through the shared-memory queue. The tensor data goes through a device broadcast (NCCL or HCCL):

The sampler inputs use the same function a second time in each step (deepinfer/worker/model_runner.py:250-275).

Step 3: each rank takes its mirror rows#

The model reorders the rows at the start of a prefill step. Every CP rank embeds all tokens, then keeps only its own rows:

prepare_for_mirror_cp calls a TileLang kernel that makes two index tensors (deepinfer/model_executor/input_metadata/input_metadata.py:169-208):

  • mirror_cp_index, int32 [cp_mirror_len]: for each row of this rank, the token index in the original batch, or −1 for a padding row (deepinfer/model_executor/input_metadata/input_metadata.py:65-67).
  • mirror_cp_reverse_index, int32 [total_q]: for each token, its row in the tensor that the CP all-gather makes (deepinfer/model_executor/input_metadata/input_metadata.py:68-69).

The method also reorders positions and sets valid_token_mask = mirror_cp_index != −1 (deepinfer/model_executor/input_metadata/input_metadata.py:203-208). The C++ side computes the row count of one rank: cp_mirror_len = 2 × Σ ⌈seqlen_q / (2 × cp_size)⌉ (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:146-155).

Step 4: attention gathers K and V over the CP group#

In a prefill step with CP, each attention layer opens a session on the CP buffer. It starts the all-gather of the projected K and V first, and computes the query projection while the data moves:

The all-gather is a method of CPManager. It returns a function. The caller calls that function later to wait and to get the result:

The layer then puts the gathered window (SWA) keys back in the original token order, with mirror_cp_reverse_index (deepinfer/model_executor/models/v4_modules/attn.py:826-829). It writes the window keys of all tokens to its own SWA cache (deepinfer/model_executor/models/v4_modules/attn.py:855). The compressor kernels read the gathered K/V rows through the same reverse index, so the compressed cache also gets all tokens (deepinfer/model_executor/layers/tilelang_ops/compress.py:34-43). So every CP rank holds the full KV cache of each sequence. The queries stay on their own rank: each rank computes attention only for its cp_mirror_len rows (deepinfer/model_executor/models/v4_modules/attn.py:859-868).

The buffer under CPManager is a DeepEP BucketBuffer (deepinfer/model_executor/parallel_utils/cp.py:16-20). This site does not explain DeepEP internals.

Step 5: the end of the forward pass, and who samples#

After the last layer, a second all-gather collects the output rows. Every CP rank then has the hidden states of all tokens, in the original order:

All CP ranks call the sampler, but only the driver samples. A follower builds its SamplerInputs without driver inputs (deepinfer/worker/model_runner.py:271-275). In the sampler, a follower computes the logits, then returns an empty output (deepinfer/model_executor/layers/sampler.py:142-161). In a decode step it also runs the draft model (deepinfer/model_executor/layers/sampler.py:155-160). The code gives no reason. Our reading: the draft layers have MoE blocks, and their EP collectives need every rank (deepinfer/model_executor/models/mtp/dflash.py:389-392). A source comment says: "sampler is after CP, CP is transparent to the sampler" (translated, deepinfer/worker/model_runner.py:240).

Step 6: decode steps#

The mirror layout is for prefill only. Both the reorder and the attention all-gather check is_prompt (deepinfer/model_executor/models/deepseek.py:168, deepinfer/model_executor/models/v4_modules/attn.py:766). In a decode step, the driver sends the same input metadata to all CP ranks, and each CP rank runs the full decode batch. This works because each CP rank holds the full KV cache from step 4.

CP in the docs

The deployment notes say: "TP and CP are not used for now" (doc/inference_deployment_qa.md:53). The code and the examples support CP, for example python examples/offline_inference.py --ep 2 --cp 8 (examples/README.md:8).

Deep dive#

Deep dive

The mirror layout: formulas and worked examples

The repository has a plain Python reference of the kernel. Its docstring says: "Pure Python reference that directly expands the zigzag definition."

  1. Line 135: the part size of sequence i is ps = ⌈sq / (2 × cp)⌉.
  2. Line 136: each rank gets 2 × ps rows per sequence. cu_elems is the running row offset inside one rank. total_per_rank is cp_mirror_len.
  3. Line 146: rank r takes block r (half 0) and block 2cp − 1 − r (half 1).
  4. Line 150: the reverse index of a token is rank × total_per_rank + cu_elems[i] + half × ps + j. This is its row in the gathered tensor [cp × cp_mirror_len, ...].
  5. Line 152: a slot past the end of the sequence gets −1. The row is padding.
  6. Lines 153-156: ks and ke are the start and end of the compressed keys that the query can see. Only models with indexer attention use them (deepinfer/model_executor/input_metadata/input_metadata.py:196-199).

Example 1: 8 tokens, cp = 2 (values from the reference function). ps = 2, cp_mirror_len = 4.

rankblocksmirror_cp_indexkeys read (causal)
00, 3[0, 1, 6, 7]1 + 2 + 7 + 8 = 18
11, 2[2, 3, 4, 5]3 + 4 + 5 + 6 = 18

mirror_cp_reverse_index = [0, 1, 4, 5, 6, 7, 2, 3]. The gathered tensor has the rows [t0, t1, t6, t7 | t2, t3, t4, t5]. Row 4 of it is t2, so token 2 maps to 4.

Example 2: 16 tokens, cp = 4 (eight parts of 2 tokens). The ranks get [0, 1, 14, 15], [2, 3, 12, 13], [4, 5, 10, 11] and [6, 7, 8, 9]. Each rank reads 34 keys. A plain split gives 10, 26, 42 and 58.

Example 3: padding. 10 tokens with cp = 2: ps = ⌈10 / 4⌉ = 3, so each rank has 6 rows. Rank 0 gets [0, 1, 2, 9, −1, −1]. Rank 1 gets [3, 4, 5, 6, 7, 8]. The −1 rows are zero rows, because gather fills out-of-range indices with 0 (deepinfer/model_executor/layers/tilelang_ops/gather.py:29-39). Their valid_token_mask is False, so the MoE gate masks them (deepinfer/model_executor/models/v4_modules/mlp.py:387).

Example 4: a one-token placeholder. With cp = 2, rank 0 gets [0, −1] and rank 1 gets [−1, −1]. A rank can have only padding rows. It still takes part in every collective.

Why the work is balanced. For a part size p and part k, the causal key count is p × (k × p) + p(p+1)/2. Parts r and 2cp − 1 − r add up to p² × (2cp − 1) + p(p+1), which does not depend on r. (This is our arithmetic for a prompt with no cached context. With cached context, each query reads the same extra keys, and the sum stays equal.)

Deep dive

CPManager and the size of the CP buffer

The model makes the CP buffer once, after the MoE buffers:

  1. Line 104: with one CP rank there is no buffer, and cp_session does nothing (line 121).
  2. Line 107: the size is max_num_tokens × max_ag_bytes_per_token × cp_size, plus 8 alignment pads (line 108), rounded up to the DeepEP allocation alignment (lines 109-110).
  3. max_num_tokens is max_num_prefilling_tokens = max_num_batched_tokens // cp_size (deepinfer/model_executor/model_loader.py:120, deepinfer/model_executor/models/deepseek.py:432-436).
  4. max_ag_bytes_per_token starts at hidden_size × 2 (the BF16 output gather, deepinfer/model_executor/models/deepseek.py:415). Each attention layer can raise it: its SWA keys in FP32 plus its projected K/V and indexer keys (deepinfer/model_executor/models/v4_modules/attn.py:375-384).

Sessions. session() asserts that no other session is open (deepinfer/model_executor/parallel_utils/cp.py:26-34). The class docstring gives two rules: the wait functions must run inside the session, and gathered tensors alias the buffer, which the next session reuses (deepinfer/model_executor/parallel_utils/cp.py:10-14). So a layer must copy what it keeps, before the session ends. get_inplace_tensor gives a rank its slot in the gathered region, so a kernel can write its rows there directly, with no copy (deepinfer/model_executor/parallel_utils/cp.py:36-40, deepinfer/model_executor/models/v4_modules/attn.py:411).

Worked example (illustrative numbers): max_num_batched_tokens = 32768 and cp = 8 give 4096 tokens per rank. With 12 KiB per token, one session needs 4096 × 12 KiB × 8 = 384 MiB, plus the pads.

Deep dive

The scheduler side: alignment to 2 × cp

The scheduler knows the CP size and pads each prompt chunk in its token budget to a multiple of 2 × cp (csrc/engine/scheduler.hpp:90, csrc/engine/scheduler.hpp:1175-1176):

  • A chunk that does not fit is cut to the free budget, rounded down to a multiple of cp_align (csrc/engine/scheduler.hpp:467-472).
  • Each scheduled chunk counts as ⌈seqlen_q / cp_align⌉ × cp_align tokens (csrc/engine/scheduler.hpp:515).

Example with cp = 4 (cp_align = 8): a 41-token prompt counts as 48 tokens in the budget. Its mirror layout has ps = ⌈41 / 8⌉ = 6, so each rank gets 12 rows and 48 rows exist in total. The scheduler count matches the padded rows.

The benchmark script also checks the alignment of its prefill batch: cp_alignment = 2 * cp_size (examples/benchmark.py:83-84, examples/benchmark.py:118-121).

What can go wrong#

Keep one CP group on one host

MessageQueue.create_from_process_group assumes that the group does not cross hosts: every reader is a shared-memory reader (deepinfer/distributed/shm_broadcast.py:442-444). A follower on another host cannot open the shared memory (deepinfer/distributed/shm_broadcast.py:117-121). The examples give each engine cp devices of one host (examples/_config.py:55-63).

  • A follower that waits forever. A follower blocks in cp_broadcast_object until the driver sends a call. If the driver dies, the kernel stops the follower with SIGKILL, because the follower set PR_SET_PDEATHSIG (deepinfer/worker/base.py:42-46, deepinfer/worker/base.py:129-130).
  • A CPU tensor in a broadcast. broadcast_tensor_dict asserts that every tensor is on the device (deepinfer/model_executor/parallel_utils/communication_op.py:67). The source rank must be 0 (line 59).
  • Nested CP sessions. CPManager.session asserts that no session is open (deepinfer/model_executor/parallel_utils/cp.py:28). The YOCO path opens its own session before the main one, "with no nesting" (deepinfer/model_executor/models/v4_modules/attn.py:773).
  • Data that changes after the session. A gathered tensor aliases the buffer. The next session overwrites it (deepinfer/model_executor/parallel_utils/cp.py:12-13).
  • A wrong engine type. CP with a COMPLETION engine stops start-up with an AssertionError (deepinfer/engine/llm_engine.py:248-249).
  • Decode does not get faster. In a decode step, every CP rank runs the full batch (step 6). CP helps prefill only.

Why it matters. CP makes the prefill of a long prompt faster without a split of the weights. The mirror layout keeps the ranks equally busy, so no rank waits for a slower neighbour at each all-gather. The cost is extra memory: each CP rank stores the full KV cache.

Check yourself#

  1. 1
    With cp_size = 2, which tokens of an 8-token prompt does rank 1 compute?
    easy
    Show answer

    Tokens 2, 3, 4 and 5. The prompt has 4 parts of 2 tokens. Rank 1 takes part 1 and part 2 × 2 − 1 − 1 = 2 (deepinfer/model_executor/layers/tilelang_ops/prepare_cp_mirror.py:146).

  2. 2
    Which CP rank samples the next token, and why do the other ranks call the sampler at all?
    easy
    Show answer

    Only the driver (CP rank 0). The followers have no driver sampler inputs and return an empty output after the logits (deepinfer/model_executor/layers/sampler.py:145-161). The code does not say why they call it. In a decode step, the follower runs the draft model there (lines 155-160). Our reading: the draft layers have MoE blocks, whose EP collectives need all ranks.

  3. 3
    A 41-token prompt runs with cp = 4. What is cp_mirror_len, and how many tokens does the scheduler charge to the budget?
    medium
    Show answer

    ps = ⌈41 / 8⌉ = 6, so cp_mirror_len = 2 × 6 = 12 rows per rank (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:151-153). The scheduler rounds 41 up to a multiple of cp_align = 8: 48 tokens (csrc/engine/scheduler.hpp:515). That equals 4 × 12 rows.

  4. 4
    Does each CP rank hold the whole KV cache of a sequence, or only the K and V of its own rows?
    medium
    Show answer

    The whole KV cache. Each attention layer all-gathers the K and V and reads them in token order through mirror_cp_reverse_index. Then it stores the entries of all tokens (deepinfer/model_executor/models/v4_modules/attn.py:826-829, deepinfer/model_executor/models/v4_modules/attn.py:855, deepinfer/model_executor/layers/tilelang_ops/compress.py:34-43). This is why a decode step can run the full batch on each CP rank.

  5. 5
    In a decode step that replays a CUDA graph, the driver sends only five small values to the followers. How do the followers get the metadata tensors (slot mappings, positions)?
    hard
    Show answer

    The graph was captured around _run_model, which calls input_metadata_device.broadcast() when the CP group has more than one rank (deepinfer/worker/cuda_graph_runner.py:61-65). That method broadcasts the tensors from rank 0 with cp_broadcast_multi_tensor (deepinfer/model_executor/input_metadata/input_metadata.py:120-167). The device broadcast is part of the graph, so each replay sends the new values into the fixed graph buffers. The followers select the same graph from total_q (deepinfer/worker/model_runner.py:223-225).
