Zero-overhead scheduling (ZOS)

AdvancedDeepInfer conceptsabout 12 min read + 9 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Offline API and the step loop Intermediate
  • GPUs, kernels, and speed Beginner
  • Speculative decoding Intermediate

In one sentence

With ZOS, the CPU schedules step N+1 while the device still runs step N. So the device does not wait for the CPU.

The idea#

One decode step has CPU parts and device parts. The CPU scheduler selects the batch, and the CPU prepares the input tensors. The device runs the forward pass and the sampler. Then the CPU reads the sampled tokens and updates each request. This last part is the post-process.

Without overlap, these parts run one after the other. The CPU must wait for the sampled tokens before it can post-process, so it makes a CPU-device sync. The deployment notes describe the result: "the GPU sits idle during post-process(N) and schedule(N+1)" (doc/inference_deployment_qa.md:270). On a fast device, this CPU time can be a large part of each step.

Zero-overhead scheduling (ZOS) changes the order of the CPU work. The CPU schedules and prepares step N+1 first. It puts the forward pass of N+1 into the device queue. Only then does it post-process step N. So the device always has queued work. The notes call this "asynchronous scheduling", after SGLang and NanoFlow (doc/inference_deployment_qa.md:274).

ZOS has a cost. When the CPU schedules step N+1, it does not know the result of step N. It does not know which token step N sampled, or how many draft tokens step N accepted. So two things change:

  • The device must correct the lengths and the input tokens of step N+1. It reads them from the outputs of step N, which are still in device memory (seqlen correction).
  • The engine returns the tokens of a decode step one step late. step() number N+1 returns the tokens of step N (deferred post-process).

An everyday comparison. Think of a cook and a helper in a kitchen. Without ZOS, the helper waits until a dish is ready. Then the helper writes the dish in the order book and puts the next ingredients on the counter. During that time the cook stands still. With ZOS, the helper puts the next ingredients on the counter while the cook still cooks. The helper writes the book for the last dish while the cook works on the next one. The comparison stops being true in one place. The helper does not know how much of the last dish the guests accepted, so the quantities on the counter can be wrong. In DeepInfer, a small device kernel corrects them before the cook uses them.

In the code#

Step 1: ZOS is on by default#

The switch is the environment variable DEEPINFER_ZERO_OVERHEAD_SCHEDULING. Its default in environ.py is off (deepinfer/environ.py:179). But EngineArgs sets it before the engine starts, if you did not set it:

NORMAL is the default engine type of EngineArgs (deepinfer/engine/arg_utils.py:41). The offline API LLM gives its keyword arguments to EngineArgs (deepinfer/entrypoints/llm.py:70-80). So if you do not set engine_type, LLM makes a NORMAL engine, and ZOS is on. The deep dive "How to turn ZOS on or off" lists the places that read the switch.

Deep dive

Events, streams and the waits that remain

All step work goes into the current device stream, in launch order. A CUDA graph replay also goes into that stream (deepinfer/worker/cuda_graph_runner.py:150-154). So the device runs forward N+1 after sample N without any wait. The CPU never needs to wait to keep the device busy. It only waits when it needs a result.

The waits that remain, with ZOS on:

WaitWhenWhere
sample_end_evt.synchronize() of step N−1every call with a kept step; the device still has forward N in its queuedeepinfer/worker/worker.py:262-263

Why the CPU group. Without ZOS, the all-reduce of has_unfinished_requests uses a device tensor and then calls .item() (deepinfer/engine/llm_engine.py:675-678). .item() on a device tensor waits until the device finishes all work before it in the stream. With ZOS that wait would remove the overlap. So with ZOS, the engine and the C++ scheduler use the CPU group (the scheduler checks the backend name "gloo", csrc/engine/scheduler.hpp:109).

The sync guard. The launch parts of execute_main_model and execute_sample (the forward pass or graph replay, and the sampler call) run inside the sync guard forbid_cuda_sync(). The input preparation before them is outside the guard. A blocking copy or a stream synchronize inside the guard raises an error. An event synchronize() is not covered, so the planned waits above are allowed (deepinfer/utils.py:119-132, deepinfer/worker/model_runner.py:321-325, deepinfer/worker/model_runner.py:356-360).

Results to the CPU. The sampler copies its results to the CPU with non_blocking=True before it returns (deepinfer/model_executor/layers/sampler.py:258-275, deepinfer/sequence.py:63-68). These copies are queued before sample_end_evt. So after the event wait, the CPU arrays are complete.

Buffers live one call longer. DeferredRelease.release() runs in each pre_sampler_sync and gives buffers back to the pools (deepinfer/engine/llm_engine.py:100-107, deepinfer/engine/llm_engine.py:830-831). The metadata list of the kept step N−1 is collected in its post-process and released in the same call (deepinfer/engine/llm_engine.py:1013). The output handles that a call of step() returns are collected after the call, so the next call releases them (deepinfer/engine/llm_engine.py:974).

The notes and the code count the steps differently

The deployment notes list the CPU work during forward(N) → sample(N). The list is schedule(N+1) → launch_forward(N+1) → post-process(N−1) → launch_sample(N+1) (doc/inference_deployment_qa.md:274). The code names the same work from the call: the call that launches forward N+1 post-processes step N, the kept step (deepinfer/worker/worker.py:143-144). Both describe the same overlap: the CPU post-processes the previous step while the device runs the current step. Only the numbering is different. This site uses the numbering of the code.

Deep dive

Edge cases: prefill steps, finished, preempted and new sequences

  • Prefill steps are never kept (deepinfer/worker/worker.py:183). A prefill step still post-processes the kept decode step before it (deepinfer/worker/worker.py:144). The decode step after a prefill has no kept step, so its CPU values are exact.
  • No common sequence. If the two batches share no seq_id, prepare_zos_inputs returns has_overlap = False and no correction runs (csrc/engine/zos.cpp:174-176).
  • A new sequence in the batch (remap = -1). The kernel only adds seqlen_q back, so its length stays the CPU value. The C++ code fills its input tokens on the CPU (csrc/engine/zos.cpp:105-113).
  • A finished sequence runs one more step. The scheduler of step N+1 runs before the post-process of step N. So a sequence that finishes in step N is in the batch of N+1. process_outputs later skips it, and its result is dropped (csrc/engine/scheduler.hpp:905-915). The C++ comment at csrc/engine/zos.cpp:298 refers to this extra forward pass.
  • A sequence preempted while in flight. _preempt resets its counts and puts it back into the waiting queue. When the old step comes back, process_outputs sees WAITING in a decode step and ignores the result. Translated comment: "ZOS async: a seq that _preempt preempted for recompute while this step was still in flight ... the output of this step is invalid: skip all bookkeeping" (csrc/engine/scheduler.hpp:917-925).
  • No drafts (DEEPINFER_USE_NEXTN_DECODE=0): each step adds exactly 1 token, so the CPU guess is exact. C++ then sends seqlen_k unchanged and the worker skips the kernel (csrc/engine/zos.cpp:188, deepinfer/worker/worker.py:220).
  • The cache limit grows. The scheduler can plan a step whose positions go up to 6 tokens further. So with ZOS, runtime_max_model_len adds nextn + 1 (deepinfer/config.py:11-16), and the scheduler checks every position against it (csrc/engine/scheduler.hpp:698-705).

What can go wrong#

Clone each output before the next step()

step() returns raw pointers into the C++ output pool, with ZOS on and off. The pool takes them back at the pre_sampler_sync of the next call. Clone them first, as LLM does (deepinfer/entrypoints/llm.py:179-182, deepinfer/engine/llm_engine.py:866-870).

  • The last tokens are missing. A custom loop that stops without flush_inflight_reqs() loses the kept decode step (deepinfer/worker/worker.py:274-283).
  • Off-by-one outputs. Code that expects the tokens of step N from step() number N gets the tokens of step N−1. The hook docstring states the rule (deepinfer/engine/llm_engine.py:824-828).
  • An error from the sync guard. A debug print of a device tensor inside the forward pass or the sampler makes a sync. The guard then raises an error. Set DEEPINFER_DISABLE_SYNC_GUARD=1 only for debugging (deepinfer/environ.py:198, deepinfer/utils.py:127-131).
  • ZOS stays on. DEEPINFER_ZERO_OVERHEAD_SCHEDULING=off turns it on (deep dive above).
  • Start-up fails with a long max_model_len. ZOS adds nextn + 1 positions to the runtime limit, and the KV cache must hold that limit with 20 % spare (deepinfer/engine/llm_engine.py:445-451).

Why it matters. ZOS explains three surprises. step() returns old tokens. A finished request runs one more forward pass. The decode inputs come from the device, not from the CPU. When you change the scheduler, the sampler or the input preparation, you must keep the CPU guess and the device correction in agreement.

Check yourself#

  1. 1
    You use LLM.generate() and set no environment variable. Is ZOS on? Which code decides?
    easy
    Show answer

    Yes. environ.py has the default off, but EngineArgs.__post_init__ sets DEEPINFER_ZERO_OVERHEAD_SCHEDULING=1 for NORMAL and COMPLETION engines if the variable is not set (deepinfer/engine/arg_utils.py:51-55, deepinfer/engine/engine_type.py:15-17). LLM makes a NORMAL engine by default (deepinfer/engine/arg_utils.py:41).

  2. 2
    With ZOS on, which step's tokens does step() return in a decode step? And what gives the last tokens?
    easy
    Show answer

    The tokens of the previous decode step. The worker keeps step N and post-processes it in the next call (deepinfer/worker/worker.py:182-187). flush_inflight_reqs() post-processes the last kept step (deepinfer/worker/worker.py:274-283).

  3. 3
    Why does the engine use the CPU (Gloo) group for the data-parallel all-reduces when ZOS is on?
    medium
    Show answer

    A device all-reduce followed by .item() makes the CPU wait until the device finishes its queue (deepinfer/engine/llm_engine.py:675-678). With ZOS the queue holds the next forward pass, so this wait would remove the overlap. The CPU group needs no device work (deepinfer/engine/llm_engine.py:667-672, csrc/engine/scheduler.hpp:170-180).

  4. 4
    A sequence has 100 tokens in the cache. Step N is in flight. The scheduler plans step N+1 with seqlen_q = 6. Step N accepts 4 of 5 drafts. Which seqlen_k does the CPU compute, which value does C++ send, and which value does the kernel write?
    hard
    Show answer

    CPU: 100 + 6 + 6 = 112 (csrc/engine/scheduler.hpp:697). C++ sends 112 − 6 = 106 (csrc/engine/zos.cpp:188). The kernel writes 106 + 6 − (5 − 4) = 111 (deepinfer/model_executor/layers/tilelang_ops/compute_seqlens_k_zos.py:22-23). Check: step N adds 4 drafts and 1 sampled token, so the cache holds 105, and step N+1 adds 6 positions: 111. This is the deep dive "A worked timeline".

  5. 5
    With ZOS and DSpark on, where does the CPU wait for the device in one call of execute_model_step, and why is the second wait necessary?
    hard
    Show answer

    First at sample_end_evt.synchronize() of the kept step, in the post-process (deepinfer/worker/worker.py:262-263). Then at d2h_evt.synchronize() before the sampler (deepinfer/worker/worker.py:147-149). With DSpark, a device kernel changes seqlens_q with the newest confidences (deepinfer/worker/worker.py:218-219). The CPU needs these lengths to prepare the sampler inputs, so it copies them back and waits for the copy (deepinfer/worker/worker.py:229-234).

  • DSpark: DFlash drafts and confidence-scheduled verificationDSpark makes 5 drafts per request with the DFlash draft model and predicts how likely each draft is to pass. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time.
  • Offline API and the step loopLLM.generate() adds all requests, then calls LLMEngine.step() until no request is left. Each step schedules one batch, runs the model once, and returns handles to the new outputs. With ZOS, a decode step returns the tokens of the step before it.
  • CUDA graphsAt start-up DeepInfer records the decode forward pass once for each of a list of batch sizes. Each decode step then pads its rows to the next recorded size and replays the recording with one call.
  • engine/llm_engine.py: the LLMEngine classLLMEngine starts the workers, sizes the KV cache, owns the C++ scheduler, and runs one engine step each time LLM calls step().
