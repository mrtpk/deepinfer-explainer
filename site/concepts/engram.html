Engram n-gram memory

AdvancedDeepInfer conceptsabout 9 min read + 6 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Tokens and tokenizers Beginner
  • Model map: DeepSeek-V4.1-Flash in DeepInfer Intermediate
  • Parallelism basics Beginner

In one sentence

Engram looks up a learned vector for each recent n-gram of a token in a large hashed table. Some layers mix these vectors into their hidden states.

The idea#

A transformer layer gets all its knowledge from the hidden states. An Engram layer also gets a direct lookup. For each token, it takes the n-grams that end at that token, for example the last 2 tokens and the last 3 tokens. It turns each n-gram into a row number with a hash. Then it reads that row from a large learned table and gives the rows to the layer. So the layer gets a vector for "these exact words in this order" with no attention work.

The table is too large to copy to every device. DeepInfer splits it into equal parts across the ranks of the enp group. In each forward step, every rank asks the other ranks for the rows that its tokens need. On NVIDIA, the parts live in host (CPU) memory by default. On Ascend, they always live in device memory.

Before the hash, the engine maps every token id to a smaller id with the compressed tokenizer. Tokens with the same text after case folding and space removal, such as "Hello" and " hello", get the same compressed id. So two spellings of one n-gram share their table rows.

An everyday comparison. Think of a phrase book in a large library. When you hear a short phrase, you look up its page number in an index and read a ready-made note about the phrase. You do not think about the phrase again. The comparison stops in two places. First, the "index" is a hash, so two different phrases can share one page. Second, the notes are numbers that the model learned in training, not text.

Simplified

This page shows the hash with a toy formula and small numbers. The real hash runs in tile_kernels.engram.engram_hash, a pip package that is not in this repository. DeepInfer only prepares its inputs: odd 64-bit multipliers, prime table sizes and offsets (deepinfer/model_executor/models/v4_modules/engram_metadata.py:98-116).

The picture#

Read panel 1 from left to right. The token and its two older neighbours become one row of compressed ids. Each n-gram size has its own sub-tables (one per head), and each gives one hash. Panel 2 shows that the four rows can live on four different ranks. Panel 3 shows where the layer uses the rows: on the residual stream, before attention.

In the code#

Step 1: the config turns Engram and the compressed tokenizer on#

The checkpoint config.json decides if the model has Engram. With no engram_layer_ids, there is no Engram (deepinfer/hugging_face/config.py:197-199).

  1. Line 200: max_ngram_size gives max_ngram_size − 1 table groups: one for 2-grams, one for 3-grams, and so on.
  2. Lines 204-206: every n-gram size gets the same nominal vocabulary size, number of heads and head width.
  3. Line 209: tokenizer compression is on when engram_compressed_vocab_size is set and not zero.

Engram cannot run without compression. ModelMetadata asserts it (deepinfer/model_executor/model_metadata_utils.py:109-111). EngineArgs then copies the flag and the tokenizer.json path into the model config (deepinfer/engine/arg_utils.py:88-91).

Step 2: every request gets a second list of ids#

add_request maps the prompt with CompressedTokenizer.encode and gives both lists to the Sequence (deepinfer/engine/llm_engine.py:564-567, deepinfer/engine/llm_engine.py:594-598).

The C++ function returns lookup_table[t] for an id inside the table (0 ≤ t < len(lookup_table)) and the sentinel -1 for every other id (csrc/engine/pybind_sequence.cpp:40-46). The docstring says that image ids are outside the table, so they become -1 (deepinfer/model_executor/models/v4_modules/engram.py:64). For each new token, the scheduler appends the compressed id with map_engram (csrc/engine/scheduler.hpp:982-985).

Step 3: one row of n-gram ids per query token#

The input preparation makes ngram_token_ids, an int32 [total_q, max_ngram_size] tensor (deepinfer/model_executor/input_metadata/input_metadata.py:40-42, csrc/engine/input_metadata/prepare_tensor_input_base.cpp:126). Column r holds the compressed id of the token r places back:

  1. Line 19: s = pos − r is the position r steps back.
  2. Lines 21-22: before the start of the sequence, use the pad id.
  3. Lines 26-27: past the stored tokens, the id is a draft token of speculative decoding. It is still a raw id, so the function maps it here.
  4. Lines 29-31 and 15-16: an image token (-1) stops the n-gram. It and every older column get the pad id.

ZOS is on by default for the NORMAL engine. Then a decode step that overlaps the previous step builds this tensor on the device with the kernel gather_engram_tokens_zos (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:246-274). With no overlap (remap is not set), C++ fills it with the same fill_engram_row, and Python copies it to the device (csrc/engine/zos.cpp:49-81, deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:215-223). The deep dive explains why.

Step 4: hash once, fetch for all Engram layers#

DeepseekModel.forward hashes the whole batch once, before the layer loop. The image mask goes in too, so the kernel knows the image positions. EngramRuntime.fetch returns one callable ("hook") per Engram layer (deepinfer/model_executor/models/v4_modules/engram.py:214-219). The loop gives each layer its hook (deepinfer/model_executor/models/deepseek.py:210-216).

Step 5: the layer mixes the rows into the trunk#

The model keeps hc_mult residual streams side by side, with the shape [T, hc_mult, hidden] (the "trunk" of mHC). The hook runs after the previous sub-layer writes into the trunk, and before the attention reads from it (deepinfer/model_executor/models/v4_modules/hc.py:220-227). There the layer calls Engram.forward:

  1. Line 149: embed_hook() gives the fetched rows. One linear layer maps them to hc_mult + 1 vectors of the hidden size per token.
  2. Lines 151-160: engram_gate_fwd combines the trunk with these vectors and writes the result in place. The kernel is in tile_kernels; this repo does not show its formula.

Deep dive#

Deep dive

Worked example: from a token to four table rows

The numbers below are a toy. They follow the layout code exactly, but the hash formula is illustrative.

Config (toy). engram_vocab_size = 1000, engram_n_heads = 2, engram_max_ngram_size = 3, Engram layers 2 and 5, enp size 8.

1. Prime sizes. EngramLayout.from_cfg gives every (layer, n-gram size, head) its own prime. It starts at vocab_size − 1, takes the next prime, and skips primes that an earlier sub-table already uses (deepinfer/model_executor/models/v4_modules/engram_metadata.py:78-94).

Layer2-gram, head 02-gram, head 13-gram, head 03-gram, head 1Sum
210091013101910214062
510311033103910494152

2. Padding and split. The rows of one layer are padded to a multiple of lcm(256, enp_size) and split equally (deepinfer/model_executor/models/v4_modules/engram_parameters.py:26-31). Layer 2: lcm(256, 8) = 256, 4062 → 4096 rows, 512 rows per rank. Rank k holds rows 512k to 512k + 511. Layer 5: 4152 → 4352 rows, 544 per rank.

3. Ids. The token at position 10 has compressed id 17. Positions 9 and 8 have 42 and 7. So ngram_token_ids[q] = [17, 42, 7].

4. Hash (illustrative). Take multipliers 3, 5, 7 (the real ones are large odd 64-bit numbers). 2-gram: (17·3) XOR (42·5) = 51 XOR 210 = 225. 3-gram: 225 XOR (7·7) = 225 XOR 49 = 208. Each head takes the value modulo its own prime: 225, 225, 208, 208.

5. Global rows. Add the start of each sub-table (0, 1009, 2022, 3041): rows 225, 1234, 2230 and 3249. They live on ranks 0, 2, 4 and 6. The toy assumes that make_offsets gives these running sums; its code is in tile_kernels.

6. What the layer gets. Four rows of engram_head_dim values each. The projection input has sum(n_embed_per_ngram) = 2 × 2 × head_dim values (deepinfer/model_executor/models/v4_modules/engram_parameters.py:58-62). So the four rows form one input row per token. This shape is inferred from the projection size; the fetch code is in DeepEP.

Deep dive

The compressed vocabulary, step by step

  1. Line 27: the PAD token must have id 2, else AssertionError.
  2. Lines 29-40: the normalizer applies Unicode NFKC and NFD, removes accents and makes lower case. It turns each run of spaces, tabs and new lines into one space and strips the ends. A token that is only one space stays one space (lines 36 and 38).
  3. Lines 43-50: for each id, decode the token alone and normalize the text. Equal texts get the same new id, in order of first use.
  4. Lines 45-47: a token that does not decode to valid UTF-8 (its text contains U+FFFD) keeps its raw vocabulary string as the key. So different byte pieces do not merge.

Examples: "Hello", " hello" and "HELLO" map to the key "hello". "café" maps to "cafe". The hash uses the size of this compressed vocabulary to bound its multipliers (deepinfer/model_executor/models/v4_modules/engram_metadata.py:104-113).

The table lives in three places: a Python list, a NumPy array for encode, and an int32 device tensor for the ZOS kernel (deepinfer/model_executor/models/v4_modules/engram.py:46-53). The C++ scheduler gets a copy for generated tokens (deepinfer/engine/llm_engine.py:323), and the C++ prepare code gets another copy (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:3-6).

Pad id. DEEPINFER_ENGRAM_PAD_TOKEN (default 2) is a raw id. After initialize, the compressed pad id is lookup_table[2] (deepinfer/model_executor/models/v4_modules/engram.py:53).

Deep dive

The n-gram rows in decode, with and without ZOS

By default (DEEPINFER_ENABLE_MTP_VARLEN off), a decode step sends 1 + 5 query tokens per sequence: the last real token and 5 draft tokens (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:112-119). Each query needs its own n-gram row, and the draft tokens are not in the stored list yet.

Without ZOS, the CPU knows every token. fill_engram_row reads stored compressed ids for positions below L and maps draft ids for positions at or above L.

Example (max_ngram_size = 3, L = 10, stored ids end with ..., 7, 42, 17, drafts d0 ... d4). The query at position 9 (the last real token) gets [17, 42, 7]. The query at position 11 gets [c(d1), c(d0), 17], where c is the lookup.

With ZOS and a previous step in flight (remap is set), the CPU prepares step N+1 while the device still runs step N. So the CPU does not know the newest tokens. The kernel combines two sources (deepinfer/model_executor/layers/tilelang_ops/gather_engram_tokens_zos.py:27-41):

  • win_compressed [n_seq, nextn + max_ngram_size − 1]: the older compressed ids and the in-flight draft ids, built on the CPU.
  • For a sequence that ran in the previous step (remap ≥ 0), the current tokens come from the device outputs of that step, prev_sampled_token_ids and prev_predict_token_ids. The kernel maps them with lookup_table_gpu.
  • For a new sequence (remap = −1), the current tokens come from curr_fresh, which the CPU compressed.
  • For lookback columns before the current tokens, the window index shifts by the number of rejected drafts, nextn − prev_num_accepted_tokens. For a new sequence, the shift is nextn (deepinfer/model_executor/layers/tilelang_ops/gather_engram_tokens_zos.py:38-39).

The NVIDIA and Ascend kernels are in cuda/ and asc/. A CPU reference and a test compare both sides (deepinfer/model_executor/layers/tilelang_ops/gather_engram_tokens_zos.py:58-117, deepinfer/model_executor/layers/tilelang_ops/gather_engram_tokens_zos.py:132-193).

Deep dive

Storage: host memory, device memory and the enp group

Group. engram_parallel_size defaults to 0, which means "all ranks" (CP × DP) (deepinfer/engine/arg_utils.py:31, deepinfer/config.py:172-173). It must divide the world size (deepinfer/config.py:181). The ranks are cut into consecutive groups of enp ranks (deepinfer/model_executor/parallel_utils/parallel_state.py:108-110).

Where the shard lives. At load time, every parameter with is_engram goes to the CPU, unless DEEPINFER_ENGRAM_FORCE_GPU_STORAGE is on (deepinfer/model_executor/models/deepseek.py:473-477). That variable is always on with DEEPINFER_ACCELERATOR=ascend (deepinfer/environ.py:147).

The buffer is a DeepEP EngramBuffer. With host storage, it uses RDMA to read other ranks' host memory (use_cpu_rdma_storage). This page does not describe the insides of DeepEP. EngramRuntime.initialize writes the shard into the buffer and then drops the original tensors (deepinfer/model_executor/models/v4_modules/engram.py:195-212).

Data type. The HF loader sets fp8_embed when the checkpoint is FP8 (deepinfer/hugging_face/config.py:202-203), and the loader accepts only FP8 checkpoints. So the table is float8_e4m3fn with one UE8M0 scale per 32 values. The scales are packed 4 per int32 on NVIDIA and 2 per int16 on Ascend (deepinfer/model_executor/models/v4_modules/engram.py:173-188).

NVIDIA with device storage. A context-parallel follower process briefly makes all GPUs visible to the CUDA driver at start-up (deepinfer/worker/runtime_config.py:13-26, deepinfer/engine/llm_engine.py:122-126).

What can go wrong#

  • Hash collisions. Two different n-grams can give the same row. The model then reads the same vector for both. This is a general property of every hash table. The code does not detect collisions.
  • No bounds check for generated tokens. map_engram reads lookup_table[token_id] with no check. The code comment says that the caller must keep the id in range (csrc/engine/scheduler.hpp:184-187). A sampled id at or above the table length would read past the end.
  • A tokenizer with PAD not at id 2. CompressedVocabulary stops with an AssertionError (deepinfer/model_executor/models/v4_modules/engram_metadata.py:26-27).
  • A bad enp size. If engram_parallel_size does not divide the world size, ParallelConfig fails its assert (deepinfer/config.py:179-181).
  • The dummy-weight profile run. For the memory profile, the model runner draws random ids only in [0, len(lookup_table)). The comment says the compressed tokenizer cannot handle meaningless ids (deepinfer/worker/model_runner.py:468-471).

Why it matters. Engram adds a cross-rank read to every forward step of an Engram model. Its rows must be correct for draft tokens too, and also when the CPU runs one step ahead. The two-source ZOS kernel and the image sentinel exist for these cases.

Check yourself#

  1. 1
    Which two token spellings get the same compressed id: "Hello" and " hello", or "hello" and "help"?
    easy
    Show answer

    "Hello" and " hello". The normalizer makes lower case and strips the spaces at the ends, so both give the key "hello" (deepinfer/model_executor/models/v4_modules/engram_metadata.py:29-40). "help" is different text.

  2. 2
    Where in a decoder layer does Engram change the hidden states?
    easy
    Show answer

    On the mHC trunk, after the post mix of the previous sub-layer and before the pre mix and norm of the attention (deepinfer/model_executor/models/v4_modules/hc.py:220-227, deepinfer/model_executor/models/decoder_layer.py:111-118).

  3. 3
    A prompt is "text, image, text". What does the n-gram row of the first text token after the image hold, with max_ngram_size = 3?
    medium
    Show answer

    Column 0 holds its own compressed id. Column 1 would be the last image token, which has the sentinel -1. So column 1 and column 2 both get the compressed pad id (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:13-33).

  4. 4
    With enp size 8 and a layer whose sub-tables sum to 4062 rows, how many rows does each rank store, and why not 4062 / 8?
    hard
    Show answer

    512. The code pads the rows to a multiple of lcm(256, 8) = 256, which gives 4096, and then splits them equally (deepinfer/model_executor/models/v4_modules/engram_parameters.py:26-30). 4062 is not a multiple of 8, and the table also needs the 256-row alignment.

  5. 5
    With ZOS on, why can the CPU not build ngram_token_ids for a decode step that overlaps the previous step?
    hard
    Show answer

    In that case, the CPU prepares step N+1 while the device still samples step N. The newest tokens and the accept count exist only on the device. So gather_engram_tokens_zos reads them from prev_sampled_token_ids, prev_predict_token_ids and prev_num_accepted_tokens and compresses them on the device (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:186-209, deepinfer/model_executor/layers/tilelang_ops/gather_engram_tokens_zos.py:27-41). With no step in flight (remap not set), the CPU knows every token, and C++ fill_engram_row builds the rows (csrc/engine/zos.cpp:49-81).

Related pages

  • v4_modules/engram.py and engram_metadata.py: the Engram runtimeengram.py maps token ids to compressed ids, holds the sharded n-gram tables in a DeepEP EngramBuffer, and gates the fetched rows into the mHC trunk. engram_metadata.py builds the compressed vocabulary, the prime table sizes and the hash multipliers.
  • mHC residual mixingDeepSeek-V4.1 keeps the residual stream as hc_mult parallel streams. Before each sub-layer, learned weights mix the streams into one input. After it, the output goes back into all streams. The model ends with one fold.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • Vision encoder (VL)DeepInfer reads images in the prefill of the same engine. A worker process prepares each image, the scheduler keeps whole images in one chunk, and a ViT plus a projector turn the pixels into vectors at the image-token positions of the prompt.
  • models/deepseek.py: the DeepSeek-V4.1 modeldeepseek.py holds DeepseekModel (embedding, N decoder layers, final mix and norm) and DeepseekForCausalLM (lm head, sampler, DFlash, EPLB, weight loading). The forward returns hidden states.
