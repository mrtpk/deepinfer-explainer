Low-precision formats in DeepInfer

AdvancedDeepInfer conceptsabout 11 min read + 6 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Number formats: BF16, FP8, FP4 Beginner
  • The KV cache Beginner
  • Hardware platforms: NVIDIA and Ascend Intermediate

In one sentence

DeepInfer stores and computes most tensors in FP8 or FP4, and every scale except one is a power of two.

The idea#

The page Number formats: BF16, FP8, FP4 explains the formats in general: bit layouts, rounding and block scales. This page shows what DeepInfer does with them. It tells which tensor uses which format and how a kernel chooses a scale. It also shows how the scale bytes are packed, and what the loader does with the scales of the checkpoint.

The short version, for a V4.1 checkpoint with the default config:

TensorValuesScaleValues per scale
Most linear weightsFP8 E4M3UE8M032 × 32 block
Routed expert weightsFP4 E2M1 (MXFP4)UE8M01 × 32
Inputs of FP8 GEMMsFP8 E4M3UE8M01 × 32, per token
Compressed (main) KVFP4 E2M1E4M316
Sliding-window KVFP8 E4M3 (MXFP8)UE8M032
Indexer keys and queriesFP4 E2M1UE8M032
Gate, compressor, head, embeddingBF16none—

Two rules hold almost everywhere. First, a scale is a power of two, stored as one UE8M0 byte. Multiplying by a power of two changes only the exponent, so the scale adds no rounding error of its own. Second, the kernels compute the amax of each group and round the scale up to the next power of two. So the largest value of a group never passes the format maximum. The FP4 main KV is the only exception: it uses an E4M3 scale per 16 values.

An everyday comparison. Think of a set of maps. Each sheet has its own scale bar. The scale must be a power of two: 1 : 1,024, 1 : 2,048, and so on. The mapmaker picks the finest scale on which the whole area still fits the sheet. A town fits a fine scale; a country needs a coarse one. A block of 32 values is one sheet, and the UE8M0 byte is its scale bar. The comparison stops being true in one point: on a real map you can draw a point anywhere. An FP4 value can only sit on one of 8 marks per sign: 0, 0.5, 1, 1.5, 2, 3, 4 and 6. So small values on a coarse sheet fall onto the mark 0.

The picture#

Read each column from top to bottom. The weights column is fixed at load time. The middle column runs in every step: each FP8 GEMM first casts its BF16 input to FP8. The right column shows the bytes of one KV entry per token.

Try it: one number, three formats, one block#

Simplified

The visual is a model of the arithmetic, not of the kernels. It rounds from the exact decimal input; in the model the inputs are already BF16. It uses round to nearest, ties to even, for all three formats. For E4M3 overflow it offers both OCP conversion modes: saturation and NaN. DeepInfer's scale rule keeps scaled values at or below 448, so the kernels do not depend on that choice. The block part uses the kernel rule: exp = ceil(log2(max(amax, margin) × (1 / max))) in FP32 (deepinfer/model_executor/layers/tilelang_ops/cuda/fused_transform.py:514-520). It does not show the byte order of packed codes or the E4M3-scaled FP4 format of the main KV.

In the code#

Step 1: the checkpoint fixes the formats#

The config loader accepts exactly one quantization setup. It raises ValueError for any other:

So the flags fp8_attn, fp8_mlp, mxfp8 and mxfp4 are always true (deepinfer/hugging_face/config.py:301-306). "Dynamic" activation scheme means that the checkpoint stores no activation scales: the kernels compute them at run time. Only the KV format of the main cache is a choice: use_fp4_sparse_kv is True unless config.json says otherwise (deepinfer/hugging_face/config.py:302-303). The loader logs the result:

Step 2: FP8 and FP4 weights are declared on meta#

The model is first built on the meta device, with no data. prepare_meta_fp8 then changes the dtype of each FP8 linear weight and adds a scale tensor:

  1. Line 122: the embedding (tok_emb), the heads and the FP4 experts (mxfp4) keep their own paths.
  2. Lines 128-130: a linear with use_fp8_gemm gets one scale per 32 × 32 block: sf [ceil(N/32), ceil(K/32)].
  3. Lines 134-135: the weight becomes float8_e4m3fn, and the scale is FP32 on meta.

Some projections stay in BF16 on purpose: the MoE gate (deepinfer/model_executor/models/v4_modules/moe.py:66-67), the compressor A and Gate (deepinfer/model_executor/models/v4_modules/mla_attn.py:79-95), and the indexer weights_proj and k_proj (deepinfer/model_executor/models/v4_modules/mla_attn.py:131-142). The routed experts get their final packed layout when memory is allocated:

Line 85: two FP4 codes share one int8, so the last dimension is k // 2. Lines 78-80 and 87: the scales are packed in the platform scale dtype. So one element covers 32 × itemsize values of K: 128 values in an int32, 64 in an int16. The scale tensor is column-major inside each expert (.mT).

Step 3: the loader keeps the checkpoint scales#

The checkpoint stores scales as F8_E8M0 bytes. For ordinary FP8 weights, the loader turns each byte into an FP32 power of two:

Then it attaches the FP32 scales to the weight (deepinfer/hugging_face/weights.py:418-422). For the routed experts it does not decode anything. It views the bytes as int32 or int16 and copies them into the column-major scale tensor (deepinfer/hugging_face/weights.py:315-323). The docstring says that this changes no value and does no requantization (deepinfer/hugging_face/weights.py:283-288).

When a runtime ReplicatedLinear receives an FP8 weight with FP32 scales, it asks DeepGEMM to transform them into its required layout (deepinfer/model_executor/layers/linear.py:67-76). The page linear.py: ReplicatedLinear and the FP8 GEMM path walks through this class.

Step 4: activations are cast to FP8 in every GEMM#

All FP8 GEMMs share one set of cast parameters:

  1. "fmt": "e4m3" and 32 values per scale: one scale per 32 values of a token row. This is per-token quantization.
  2. round_sf: the scale is a power of two.
  3. use_packed_ue8m0: the scale bytes come packed in the platform dtype.
  4. use_tma_aligned_col_major_sf: the scale tensor is column-major and padded for the GEMM library.

The same parameters appear in the attention output, the norms and the SwiGLU of the experts (deepinfer/model_executor/models/v4_modules/attn.py:200, deepinfer/model_executor/layers/layernorm.py:50, deepinfer/model_executor/models/v4_modules/mlp.py:140-141). Before the GEMM, the code checks that both scale tensors have the platform dtype (deepinfer/model_executor/layers/linear.py:164). The routed experts multiply FP8 inputs with FP4 weights. In the grouped-GEMM path, both sides have a scale per 32 values (deepinfer/model_executor/models/v4_modules/mlp.py:118-128). With mega-MoE, DeepInfer calls deep_gemm.fp8_fp4_mega_moe instead (deepinfer/model_executor/models/v4_modules/mlp.py:255).

Step 5: three KV cache formats#

  1. V41_FORMAT: 512 E4M3 values, a UE8M0 scale per 32. 512 + 16 = 528 bytes. Used by the sliding-window cache, and by the main cache when FP4 is off.
  2. V41_FP4_FORMAT: 512 E2M1 values, an E4M3 scale per 16. 256 + 32 = 288 bytes. The default main cache.
  3. FP4_INDEX_KV_FORMAT: 128 E2M1 values, a UE8M0 scale per 32. 64 + 4 = 68 bytes. The indexer always uses it: "Indexer Q/K always use FP4 (E2M1 + UE8M0 scale)" (deepinfer/model_executor/models/v4_modules/index_attn.py:85-86).

The group size of the main cache comes from one helper: 16 for the FP4 main cache, else 32 (deepinfer/model_executor/model_metadata_utils.py:37-39). The window cache always casts to E4M3 with UE8M0 scales (deepinfer/model_executor/models/v4_modules/attn.py:412-428). The file defines two more index formats; outside the tests, no model code selects them.

Step 6: how a kernel chooses a UE8M0 scale#

The KV store kernel shows the rule in four lines:

  1. Line 13: scale = max(amax, 1e-4) / 448. The floor FP8_AMAX_MARGIN = 1e-4 avoids a zero scale for a block of zeros (deepinfer/model_executor/layers/tilelang_ops/common.py:25-26).
  2. Line 14: ue8m0_exp_scale returns −ceil(log2(scale)), the exponent of the multiplier.
  3. Line 15: the multiplier 2^exp_scale, built directly from its exponent bits.
  4. Line 16: the stored byte is −exp_scale + 127 = ceil(log2(scale)) + 127.

The general cast kernel uses the same rule for FP8 and FP4, with 448 or 6 as the maximum and its own floor (deepinfer/model_executor/layers/tilelang_ops/cuda/fused_transform.py:180-182, deepinfer/model_executor/layers/tilelang_ops/cuda/fused_transform.py:514-520). For the FP4 main cache with E4M3 scales, it stores the E4M3 value of amax / 6 instead (deepinfer/model_executor/layers/tilelang_ops/cuda/fused_transform.py:521-530).

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

The ceil(log2) bit trick, step by step

An FP32 value is sign | 8 exponent bits | 23 mantissa bits. For a positive normal number, bits >> 23 is the biased exponent e + 127, where 2^e ≤ scale < 2^(e+1).

  1. scale_bits − 1: if the scale is an exact power of two, its mantissa is 0, and subtracting 1 borrows from the exponent. So the exponent field drops by one. For any other scale, the mantissa is not 0 and the exponent field stays.
  2. >> 23, + 1, − 127: this gives e + 1 for a non-power, and e for an exact power of two. That is ceil(log2(scale)).
  3. The function returns the negative, the exponent of the multiplier.

Worked example. scale = 3.1 / 448 = 0.0069196. Its FP32 bits are 0x3BE2BE2C. Exponent field 0x77 = 119, so e = −8 (2−8 = 0.0039 ≤ 0.0069 < 0.0078). The trick gives −8 + 1 = −7. The multiplier is 27 = 128 and the byte is 127 − 7 = 120. For scale = 2^−7 exactly (amax = 3.5), the trick gives −7 too, and 3.5 × 128 = 448 fits exactly.

The floors. FP8: amax ≥ 10−4, so the smallest scale is 2ceil(log2(10−4/448)) = 2−22. FP4: amax ≥ 6 × 2−126, so the smallest scale is 2−126, byte 1 (deepinfer/model_executor/layers/tilelang_ops/common.py:23-27).

Compared to the OCP MX rule. The OCP MX specification takes floor(log2(amax)) minus the largest exponent of the element format, and lets the largest values saturate. DeepInfer's rule rounds up instead, so no value saturates, at the cost of up to one exponent step of precision for the other values.

Deep dive

Packed scale layouts, with shapes

PLATFORM.fp8_sf_type is torch.int32 on NVIDIA and torch.int16 on Ascend (deepinfer/platform.py:63, deepinfer/platform.py:138). Every packed UE8M0 tensor uses it.

Line 202 of attn.py shows the packing in one expression: the number of packed scale elements per row is dim // 32 // itemsize. The scale tensor of a GEMM output is made column-major with a TMA-aligned row count (deepinfer/model_executor/models/v4_modules/attn.py:206-211).

KV entries. Main and window caches store [data | scales] for each token ("token-interleaved"); index caches keep block-wide data and scale sections (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:28-32). The helper alloc_kv_cache rounds the block stride up to a multiple of lcm(32, bytes per token) for token-interleaved caches, else of 32 (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:264-266). Only the kernel tests call this helper. For 128 entries, no padding is necessary. The sizes are 36,864 B (128 × 288, FP4 main), 67,584 B (128 × 528, MXFP8) and 8,704 B (128 × 68, indexer). The runtime cache uses one shared byte buffer for all layers; see KV compression (C1 and C2).

Simplified

The bit order inside one packed int32 and the exact TMA padding are set by DeepGEMM and tile_kernels. The expert loader views row-major bytes as int32, so on a little-endian machine one int32 holds 4 consecutive K groups of one row. Other tensors are packed by library kernels.

Deep dive

Load paths: ordinary FP8, experts and dummy weights

Ordinary FP8 weights.

  1. Read the weight bytes and the .scale tensor (deepinfer/hugging_face/weights.py:414-419).
  2. Decode the scale: 2 ** (byte − 127) with torch.ldexp (deepinfer/hugging_face/weights.py:163-167).
  3. set_ue8m0_sf packs the FP32 scales again with tile_kernels.quant.batched_transpose_weight_sf and stores them as param.ue8m0_sf (deepinfer/hugging_face/parameters.py:30-70).
  4. The runtime layer transforms param.sf (FP32) with deep_gemm.transform_sf_into_required_layout, recipe (1, 32, 32) (deepinfer/model_executor/layers/linear.py:67-76).

Note: in this release no code outside hugging_face/ reads ue8m0_sf; the runtime layers use sf.

Routed experts. Each expert's w1 and w3 are concatenated into linear1; w2 becomes linear2 (deepinfer/hugging_face/weights.py:285). The scale bytes are copied without a decode, and param.mxfp4 = True keeps them out of the generic FP8 path (deepinfer/hugging_face/weights.py:318-325). With mega-MoE, DeepGEMM converts weights and scales once more into its own layout (deepinfer/model_executor/models/v4_modules/mlp.py:93-106).

Dummy weights. Without a checkpoint, the loader fills random BF16 values and casts them to FP8. For FP4 experts, it clears the two low mantissa bits of each byte (deepinfer/model_executor/models/v4_modules/utils.py:64-67). Then process_moe_weight converts the FP8 values to packed FP4 (deepinfer/model_executor/models/deepseek.py:493-494). It first checks that the low two bits are 0:

An E4M3 byte with both low mantissa bits at 0 has a 1-bit mantissa, the same precision as E2M1. The assert message names a QAT checkpoint. With a real checkpoint, this function never sees FP4 experts: DeepseekMoE uses the packed tensors directly (deepinfer/model_executor/models/v4_modules/mlp.py:207-213).

The QA document, and FLOP counting

The QA document has a short low-precision section (doc/inference_deployment_qa.md:213-221):

Main KV: per-16, e4m3, "like NVFP4 but without the global scale"V41_FP4_FORMAT: 16 values per E4M3 scale (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:119-128)
Indexer KV: per-32, ue8m0, MXFP4FP4_INDEX_KV_FORMAT (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:129-137)

The code and the document agree. The document lists only the FP4 uses; the FP8 parts are in the code only.

FLOP counting. The scheduler's FLOP estimator counts the expert GEMMs at the FP8 rate: "FP4 weight storage alone does not imply FP4 × FP4 compute" (csrc/engine/flops_estimator.hpp:84-86). The indexer is counted at the FP4 rate, because its queries and keys are both FP4 (csrc/engine/flops_estimator.hpp:156).

Deep dive

Ascend differences

  • Packed scales use int16: 2 UE8M0 bytes per element (deepinfer/platform.py:138).
  • The KV format with FP32 scales per token is not supported on NPU (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:160).
  • The Ascend kernels use the same amax floors (deepinfer/model_executor/layers/tilelang_ops/asc/kv_quant.py:53).
  • Mega-MoE runs on Ascend only with FP8 × FP4 (deepinfer/model_executor/models/v4_modules/mlp.py:184-188), which is always the case with the released checkpoint format.

What can go wrong#

  • Another checkpoint format. A different quantization method, expert dtype, block size, scale format or activation scheme raises ValueError("Unsupported HF ...") (deepinfer/hugging_face/config.py:254-262).
  • Wrong scale dtype. An FP8 GEMM asserts that both scale tensors have the platform dtype (deepinfer/model_executor/layers/linear.py:164). A scale tensor from the other platform fails here.
  • Experts that are not FP4. A checkpoint with another expert_dtype fails the config check above. The assert "Only support FP4-QAT checkpoint" (deepinfer/model_executor/models/v4_modules/mlp.py:60) runs only for dummy weights, and the dummy loader clears the two low bits first (deepinfer/model_executor/models/v4_modules/utils.py:64-67).
  • Outliers. One large value sets a coarse scale for its whole group. With FP4, small values of that group round to 0. Try Add an outlier in the converter.

Why it matters. Format choices set memory and speed. FP4 experts use about a quarter of the BF16 bytes. FP8 GEMM inputs halve the input traffic. The 288-byte FP4 entry lets the main cache hold 1.8 times more entries than the 528-byte MXFP8 entry in the same memory.

Check yourself#

  1. 1
    Which KV cache format is the only one with a scale that is not a power of two?
    easy
    Show answer

    The FP4 main cache, V41_FP4_FORMAT: 512 E2M1 values with one E4M3 scale per 16 values, 288 bytes (deepinfer/model_executor/layers/tilelang_ops/cache_common.py:119-128). The window cache and the indexer use UE8M0.

  2. 2
    How many UE8M0 bytes does one packed scale element hold on NVIDIA, and on Ascend?
    easy
    Show answer

    4 in an int32 on NVIDIA, 2 in an int16 on Ascend (deepinfer/platform.py:63, deepinfer/platform.py:138).

  3. 3
    A block of an MXFP8 KV entry has amax = 3.1. Which UE8M0 byte does the store kernel write, and what does 3.1 become?
    medium
    Show answer

    3.1 / 448 = 0.00692; ceil(log2) = −7; byte = 120 (deepinfer/model_executor/layers/tilelang_ops/cuda/store_kv_cache.py:13-16). 3.1 × 27 = 396.8, which rounds to the E4M3 value 384, so the stored value is 384 × 2−7 = 3.0.

  4. 4
    Why does the loader decode the scales of ordinary FP8 weights to FP32, but copy the expert scales as raw bytes?
    medium
    Show answer

    Ordinary FP8 weights go through a generic path that transforms FP32 scales into the GEMM layout (deepinfer/hugging_face/weights.py:418-427, deepinfer/model_executor/layers/linear.py:67-76). The expert scales are already packed UE8M0 bytes in the needed order. So the loader views them as int32 or int16 and copies them into the column-major tensor. The flag mxfp4 keeps them out of the generic path (deepinfer/hugging_face/weights.py:315-325).

  5. 5
    An FP8 GEMM input has 512 tokens and K = 7,168. How many packed scale elements does it need on Ascend, and why does the scale never let a value overflow 448?
    hard
    Show answer

    7,168 / 32 = 224 scale bytes per token; 2 per int16 gives 112 per token, 57,344 in all (deepinfer/platform.py:138). The kernel rounds amax / 448 up to a power of two, so amax / scale ≤ 448 (deepinfer/model_executor/layers/tilelang_ops/cuda/quant.py:4-9).
