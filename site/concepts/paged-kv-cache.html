Paged KV cache and block manager

IntermediateDeepInfer conceptsabout 11 min read + 10 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • The KV cache Beginner
  • The scheduler Intermediate

In one sentence

Two C++ block managers give each sequence its KV blocks and one state slot. C++ code then turns the block tables into indices for the kernels.

The idea#

The page The KV cache explains the basics. The KV cache is split into blocks of 128 tokens. A block table per sequence records which blocks it owns. That page also shows the memory layout and the preemption rule. This page looks at the same cache from the engine side. It answers four questions:

  1. Who hands out blocks? Two C++ objects of the class BlockManager. One manages KV blocks. The other manages state slots, one per running sequence.
  2. When? The C++ scheduler asks for blocks in each step. A prompt gets all its blocks at the first prefill chunk. A decode step adds one block when it needs one. Python code gives the blocks back when a sequence ends.
  3. Can two sequences share a block? Yes, but only a forked sequence. Each block has a reference count. There is no prefix caching in this release.
  4. How do the kernels find the blocks? Before each step, C++ code turns each block table into int32 index tensors, for example the slot mapping.

An everyday comparison. Think of a hotel with numbered rooms. The front desk keeps the free room keys in a box. A new guest gets keys from the front of the box. A guest who leaves puts the keys at the back of the box. Each guest has a card with a list of room numbers: that card is the block table. Two guests from one family can share a room. The room is free again only when both guests give back their key.

The comparison stops here: the front desk does not choose who gets a room. In DeepInfer the scheduler decides, and the block manager only counts and hands out numbers. Also, a hotel does not copy the contents of a room. DeepInfer copies the last, partly filled block when it forks a sequence.

The picture#

Read panel 1 first: each sequence owns blocks in the KV pool and one slot in the state pool. Then read panel 2 from top to bottom. A new block always comes from the head of the free list, and a freed block goes to the tail. So after some time, the blocks of one sequence are spread over the pool. The block table hides this from the kernels.

In the code#

Step 1: the engine makes two managers#

The sizes come from the memory profiling run at start-up. The KV cache shows that run in its deep dive "Where the memory comes from". Then the engine makes the managers:

  • num_gpu_blocks is the mean block count over all ranks, rounded down to an even number (deepinfer/worker/base.py:264-266).
  • num_state_seqs is int(max_num_seqs × DEEPINFER_NUM_STATE_SLOTS_RATIO) + 1. The ratio defaults to 1.2 (deepinfer/worker/cache_engine.py:201-202, deepinfer/worker/cache_engine.py:650, deepinfer/environ.py:162). With max_num_seqs = 256, the pool has 308 entries.
  • Both managers are the same C++ class. Entry 0 of each pool is never given out (csrc/engine/block_manager.hpp:27-35).

The engine passes both managers to the C++ Scheduler (deepinfer/engine/llm_engine.py:307-312). From then on, only the scheduler and the release code in Python touch them.

Step 2: one lock for both pools#

Each schedule() call takes both locks first. It holds them until the step's plan is complete:

BlockManagerMutexAcquire locks the state manager first, then the block manager. It unlocks in the opposite order (csrc/engine/block_manager.hpp:189-204). Line 276 releases the Python GIL, because the lock refuses to wait while the GIL is held (deep dive "Locks, the GIL and threads").

Step 3: prefill takes all blocks of a prompt at once#

A new prompt needs blocks and a state slot. The scheduler checks both together:

  • OK: the prompt fits now. LATER: it can fit when other sequences free blocks. The prefill batch stops here (csrc/engine/scheduler.hpp:386-388).
  • NEVER: the prompt needs num_blocks blocks or more, so it can never fit (csrc/engine/block_manager.hpp:128-136). The scheduler ends the request with status FINISHED_IGNORED (csrc/engine/scheduler.hpp:389-396).

When the scheduler accepts the prompt, it allocates at the first chunk, for the whole sequence:

The call site is csrc/engine/scheduler.hpp:518-520. get_num_blocks() is a round-up division: ceil((len + in-flight tokens + draft tokens) / 128) (csrc/engine/sequence.hpp:291-293). A chunked prompt therefore owns all its blocks before its second chunk runs.

Step 4: decode adds one block when the count grows#

  1. Line 818: count the blocks that the sequence needs now. The count includes tokens in flight and the draft tokens of speculative decoding.
  2. Lines 819-820: if the table is too short, take one block from the head of the free list.
  3. Lines 821-825: if the table is too long, free the extra blocks. This happens when the count goes down, for example when fewer tokens are in flight or fewer draft tokens are stored.

The decode loop calls _append_slot only after it made sure that one block is free. If no block is free, it preempts a sequence first (csrc/engine/scheduler.hpp:630-640). The page The KV cache explains that rule in its deep dive "Preemption in DeepInfer".

Step 5: Python gives the blocks back#

A sequence that ends does not free its blocks at once. The next decode schedule moves it from running to finished_seqs (csrc/engine/scheduler.hpp:752-763). Then the engine frees it in the callback pre_sampler_sync, while the device samples:

finalize_seq calls scheduler.free_seq (deepinfer/engine/llm_engine.py:804-806). The C++ code frees three things:

The KV blocks go back in reverse order, so the first block of the table goes to the very end of the free list (csrc/engine/block_manager.hpp:147-149). Panel 2 of the figure shows this in row 5.

Step 6: block tables become kernel indices#

The scheduler gives the worker a list of SequenceMetadata objects. Each one holds a reference to the block table of its sequence, not a copy (csrc/engine/sequence.hpp:349, csrc/engine/sequence.hpp:379). C++ code then builds the index tensors:

  • Prefill, and decode without ZOS: prepare_prompt_v4 and prepare_decode_v4 compute every slot on the CPU (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:41-108). The page The KV cache reads that code line by line in its deep dive "From token position to byte".
  • Decode with ZOS (the default for the offline API): the engine picks prepare_decode_v4_zos (deepinfer/model_executor/model_metadata_utils.py:143). C++ only packs all block tables into one flat array:

Then a device kernel, prepare_v4_decode_metadata, computes the slot mappings and the per-token block tables on the device (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:336-367). The page Input metadata (varlen batching) explains the other fields of the input metadata.

Finished sequences wait for a decode step. Only _schedule_decode calls free_finished_seqs() (csrc/engine/scheduler.hpp:562). A prefill step returns an empty finished_seqs list (csrc/engine/scheduler.hpp:549). So during a series of prefill steps, sequences that already ended keep their blocks.

Tokens in flight count. With ZOS, the scheduler plans step N+1 before step N is processed. Each scheduled step adds nextn + 1 = 6 in-flight tokens to the sequence (csrc/engine/scheduler.hpp:689, csrc/engine/scheduler.hpp:726). get_num_blocks() adds them, and the 5 draft tokens, to the length. Example: a sequence has 380 tokens, 6 tokens in flight and 5 drafts. It needs ceil(391 / 128) = 4 blocks, although 380 tokens fit in 3 blocks.

After a decode step. process_outputs commits only the accepted tokens. Drafts that the sampler rejects do not stay in the cache count (csrc/engine/scheduler.hpp:997-1000). The next _append_slot can then free a block again.

Deep dive

Reference counts and forked sequences, with numbers

A block can belong to two sequences. This happens only through Scheduler.fork_seq, which makes a forked sequence from the cached prefix of a parent. In this release, only examples/benchmark.py calls it, to start many requests from one prefilled prompt (examples/benchmark.py:331-353). No file in deepinfer/ calls it.

  1. Line 1110: every block of the parent table gets ref_count + 1 (csrc/engine/block_manager.hpp:88-93).
  2. Lines 1112-1113: the fork also shares the parent's state slot, with a pin.
  3. Lines 1115-1118: a fork with an incomplete prompt goes to the front of waiting. A fork with a complete prompt goes to the prompted queue, marked as forked.

The shared last block is a problem: both sequences will write new tokens into it. So, before a fork runs, the scheduler gives it its own copy of the last block and its own state slot. The comment above the loop says, translated: "a forked seq must first clone its state and its last (possibly half-written) block" (csrc/engine/scheduler.hpp:581-582).

Worked example. The parent has 1,000 cached tokens and the table [5, 6, 7, 8, 9, 4, 3, 2]. The fork gets the same table, and all 8 blocks now have ref_count = 2.

  1. Line 608: num_blocks = ceil(1000 / 128) = 8. The last used block is index 7, block 2. It holds 1,000 − 896 = 104 tokens.
  2. Line 607: a new block comes from the free list, for example block 1.
  3. Lines 610-611: the pair (2, 1) goes into clone_blocks: copy block 2 into block 1.
  4. Line 616: the fork's table becomes [5, 6, 7, 8, 9, 4, 3, 1]. Blocks 5 to 3 stay shared.
  5. The engine runs the copy on the device (deepinfer/engine/llm_engine.py:889-905). The C++ copy loop gives back every source id (csrc/engine/scheduler.hpp:1288-1301). At the next pre_sampler_sync, the engine waits for the copy event and calls unpin_blocks([2]). Block 2 goes back to ref_count = 1: only the parent owns it now.

A pair (src, 0) means "only give back src, do not copy" (deepinfer/_C/engine.pyi:380-383). Lines 612-615 use it for parent blocks after the last used one: the fork does not need them.

unpin_blocks is free_blocks

The Python name unpin_blocks is bound to the C++ method free_blocks (csrc/engine/pybind_scheduler.cpp:68). "Unpin" and "free" are the same operation: ref_count − 1, and a push to the free list at 0.

Deep dive

Prefix caching: what this release has, and what it does not have

Prefix caching reuses the KV cache of an earlier request that starts with the same tokens. The DeepInfer docs describe such a system, but the release does not include it:

  • The README lists "A KV cache system" under "not included in this release" (README.md:38-40).
  • The deployment notes describe the external system. It matches prefixes on a hash chain, moves the KV cache from 3FS storage into host shared memory, and then copies it into device memory (doc/inference_deployment_qa.md:157). The hit length is a multiple of the 128-token block size (doc/inference_deployment_qa.md:191).
  • The notes also say why the state matters: the SWA cache is in the state slot, not in blocks (doc/inference_deployment_qa.md:163). A hit on the blocks without the SWA state needs a replay of the last 128 tokens (doc/inference_deployment_qa.md:185).

What the engine has.

  1. No code compares the tokens of a new prompt with cached blocks. A new prompt always gets new, empty blocks (csrc/engine/scheduler.hpp:374-397).
  2. The local variable prefix_caching_hit in _schedule_prefill is true for every new prompt and for every fork. It only turns off a lookahead check for those sequences (csrc/engine/scheduler.hpp:373-375, csrc/engine/scheduler.hpp:451-458). It does not mean a cache hit.
  3. The field cache.hit_tokens (Python: Sequence.cached_hit_tokens) exists (csrc/engine/sequence.hpp:204, csrc/engine/pybind_sequence.cpp:118). Python can set it, because the stub has a setter (deepinfer/_C/engine.pyi:454-455). But only fork_seq copies it (csrc/engine/scheduler.hpp:1086), and no code in the release sets it to a value other than 0.
  4. The engine has empty hook methods for KV saving, for example do_save_kvcache (deepinfer/engine/llm_engine.py:815-822). An external system can fill them. The page engine/llm_engine.py: the LLMEngine class lists all hooks.
  5. The only in-engine reuse is the fork of the previous section.
Deep dive

Locks, the GIL and threads

BlockManager inherits a mutex from deepinfer::Lockable:

  1. Line 16: lock() raises an error if the calling thread holds the Python GIL. A thread that waits for the mutex while it holds the GIL can block every other Python thread.
  2. Line 17: the fast path tries the lock once.
  3. Lines 25-27: else it waits at most 20 seconds, then raises "failed to lock mutex".
  4. Line 35: the mutex is an error-check mutex. A second lock() from the same thread fails, and it does not hang.

The bindings follow this rule. pin_blocks, unpin_blocks, lock and reset release the GIL (csrc/engine/pybind_scheduler.cpp:67-71). Scheduler.try_allocate_seq releases the GIL, then takes both locks (csrc/engine/pybind_scheduler.cpp:85-92).

The _nolock methods. allocate_nolock, free_blocks_nolock and the others expect that the caller holds the lock. The scheduler holds it for the whole _schedule() call, and the decode code says so in a comment (csrc/engine/scheduler.hpp:560). The binding allocate_nolock is the only one of these that Python can call (csrc/engine/pybind_scheduler.cpp:72).

Which threads use the managers. The scheduler runs on the main thread. DeferredRelease.release() also runs on the main thread, inside the Worker's call of pre_sampler_sync (deepinfer/worker/worker.py:162-164). We found no second thread that calls the managers. So in this release the lock is mainly a safety check.

max_num_blocks. The model runner computes it once: ceil(runtime_max_model_len / 128), rounded up to a multiple of 64 (deepinfer/worker/model_runner.py:114-115). Example: runtime_max_model_len = 32784 gives ceil(256.1) = 257, then 320.

Why more state slots than sequences? The code does not say. But the code shows two cases where a slot is in use although its sequence does not run:

  • An ended sequence keeps its slot until the next decode step frees it (deep dive "Timing").
  • A fork gets a new slot while the parent's slot is still pinned for the fork.

Usage counts block 0. get_gpu_cache_usage divides the used entries by num_blocks, and entry 0 is never free (csrc/engine/scheduler.hpp:830-835). In the toy pool of the figure, an empty pool has a usage of 1/10.

Deep dive

Preemption and recompute, from the engine side

The KV cache explains which sequence the scheduler preempts. This section shows what happens to the cache state of that sequence.

  1. free_seq_nolock gives back the MTP info slot, the state slot and all blocks, and clears the table (csrc/engine/scheduler.hpp:738-745).
  2. For a recompute, reset_for_recompute sets the cache count, the in-flight count and the SWA start to 0, and clears the drafts (csrc/engine/sequence.hpp:223-227, csrc/engine/sequence.hpp:258-261, csrc/engine/sequence.hpp:134-142). The tokens stay.
  3. The sequence goes to the front of waiting. Its table is empty, so the next prefill treats it as a new prompt of len tokens: prompt plus output so far (csrc/engine/scheduler.hpp:374-386).
  4. With ZOS, the step that was in flight when the scheduler preempted the sequence still returns. process_outputs sees the status WAITING in a decode step and skips the sequence, so the old results do not change the reset counts (csrc/engine/scheduler.hpp:917-925).

The length check does not stop a recompute

The new prefill checks len > prompt_limit (csrc/engine/scheduler.hpp:376-384). Without chunked prefill, prompt_limit = min(max_model_len, max_num_batched_tokens) (csrc/engine/scheduler.hpp:112). But SchedulerConfig refuses max_num_batched_tokens < max_model_len without chunked prefill (deepinfer/config.py:208-212). So prompt_limit is always max_model_len. A running sequence ends with length as soon as it is longer than max_model_len (csrc/engine/scheduler.hpp:1043-1046). Thus a preempted sequence is never longer than the limit, and its recompute passes the check.

What can go wrong#

  • A prompt that can never fit. The scheduler logs "exceeds the capacity of block_manager" and ends the request with the finish reason prompt_length_exceeded (csrc/engine/scheduler.hpp:389-396, csrc/engine/sequence.hpp:53-54). The direct call Scheduler.try_allocate_seq raises instead: "can never allocate N blocks" (csrc/engine/block_manager.hpp:230-233).
  • Free blocks, but no state slot. A prompt waits with LATER when the state pool is empty, even if many KV blocks are free (csrc/engine/scheduler.hpp:197-199).
  • Lock errors. A call to BlockManager.lock() from C++ code that holds the GIL raises an error. A wait of more than 20 seconds raises "failed to lock mutex" (csrc/utils/lockable.hpp:16, csrc/utils/lockable.hpp:25-27).
  • Broken counts. A double free makes ref_count negative and raises "ref_count corrupted" (csrc/engine/block_manager.hpp:98-99). A table with the wrong length after _append_slot raises with both numbers (csrc/engine/scheduler.hpp:826-827). BlockManager.reset() does not reset anything: it only checks that all blocks are free (csrc/engine/block_manager.hpp:37).
  • Open question: an abort between two prefill chunks. We found no code that frees the blocks and the state slot of such a request. See the note below.

Open question: a possible leak after an abort between chunks

We read the code but did not run it. The steps below need chunked_prefill=True and a call of LLMEngine.abort_request.

  1. The first chunk gives the prompt all its blocks and its state slot (csrc/engine/scheduler.hpp:518-520).
  2. After each chunk, process_outputs puts the sequence back at the front of waiting (csrc/engine/scheduler.hpp:1016-1019).
  3. abort_sequence finds it there and sets FINISHED_ABORTED (csrc/engine/scheduler.hpp:147-160). abort_request frees nothing (deepinfer/engine/llm_engine.py:651-656).
  4. The next schedule moves it to ignored_seqs and does not free it (csrc/engine/scheduler.hpp:363-367, csrc/engine/scheduler.hpp:570-577).
  5. ignored_seqs only gets an output (csrc/engine/outputs.hpp:297-304). No Python code reads ignored_seqs, and the engine frees only finished_seqs (deepinfer/engine/llm_engine.py:844-846).

The offline LLM class never calls abort_request. The engine calls it only for multimodal failures (deepinfer/engine/llm_engine.py:942-945). Those requests never became schedulable (deepinfer/ve/multimodal_processor.py:290-292), so they own no blocks.

Why it matters. The block managers decide how many requests run and when a request must wait. Most questions of the type "why does my request wait?" have one of four answers. There is no free block, or no free state slot. Or usage is above the 90 % watermark, or ended sequences still hold blocks. When you read the scheduler, look for each call into the two managers.

    Show answer

    ceil(1000 / 128) = 8, so the last used block is index 7, block 2. The scheduler copies block 2 into a new block and puts (2, new) into clone_blocks (csrc/engine/scheduler.hpp:607-611). After the copy, DeferredRelease calls unpin_blocks([2]), so block 2 goes from 2 back to 1: only the parent owns it (deepinfer/engine/llm_engine.py:109-116). This is the deep dive "Reference counts and forked sequences".

  5. 5
    A new request repeats the prompt of an earlier request word for word. Does DeepInfer reuse the earlier KV blocks?
    hard
    Show answer

    No. The release has no prefix cache: a new prompt always gets new blocks (csrc/engine/scheduler.hpp:374-397), and the README lists the KV cache system as not included (README.md:38-40). The variable prefix_caching_hit does not mean a hit (csrc/engine/scheduler.hpp:373-375). Only a fork shares blocks.

  • The schedulerIn every engine step, the C++ scheduler runs either a prefill batch or a decode batch. It starts prefills only at attempt points, cuts long prompts into chunks, gives KV blocks, and preempts sequences when the blocks run out.
  • Request and sequence lifecycleEach request becomes a C++ Sequence. It waits until it is schedulable, runs one or more prefill steps and many decode steps, and ends with one of seven finish reasons. Preemption stops it or sends it back to the queue for a recompute.
  • Input metadata (varlen batching)Before each forward pass, DeepInfer packs the tokens of all scheduled sequences into one flat list and computes index tensors that tell each kernel where every token is, where to write its cache entry and which keys to read.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
