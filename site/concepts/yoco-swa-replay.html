YOCO and SWA bounded replay

AdvancedDeepInfer conceptsabout 9 min read + 8 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Model map: DeepSeek-V4.1-Flash in DeepInfer Intermediate
  • Sliding-window attention Intermediate
  • KV compression (C1 and C2) Advanced
  • Cross-layer KV sharing Advanced

In one sentence

Consumer layers take their compressed KV from one shared hidden state, so a prefill can run them only for the last 140 tokens.

The idea#

YOCO splits the N main layers at n_prefill_layer, the first layer with compress ratio 1:

  • Producer layers [0, n_prefill_layer) work as usual. The deployment notes call them "encoder layers".
  • Consumer layers [n_prefill_layer, N) make their compressed KV from one shared hidden state, not from their own input. The notes call them "decoder layers" (doc/inference_deployment_qa.md:187).

This changes what a long prefill must compute. The compressed KV of every consumer layer depends only on the shared hidden state, and that comes from the producer layers. So the consumer layers do not need to run attention and MoE on the full prompt to fill their compressed caches. They need the full prompt for two things only: the output of the last token, and their sliding-window KV.

SWA bounded replay uses this. With DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact, a prefill runs the consumer layers only for the last DEEPINFER_YOCO_PREFILL_KEEP_TOKENS tokens of the prompt. The README gives 140 as the V4.1 setting (README.md:25). The window of these tokens is cut at the start of the kept range. The consumer-layer SWA KV that results is then approximate. This is a deduction from the visibility rule. The deployment notes also call the replay result approximate, for use in decode only (doc/inference_deployment_qa.md:183, doc/inference_deployment_qa.md:187).

The truncation is off by default (deepinfer/environ.py:188). Without it, every layer computes every prompt token, and the shared hidden state only changes where the compressed KV comes from.

An everyday comparison. Think of a long meeting with a written summary. Late participants read the summary (the compressed KV from the shared state) and listen only to the last ten minutes (the kept tokens). They can then follow the next discussion well. The comparison stops here: their notes about those ten minutes differ a little from the notes of a full listener. The engine accepts that difference.

The name YOCO

The repo does not expand the name. In the research literature, YOCO ("You Only Cache Once") is a decoder-decoder design with a similar split. This site uses the name only as the code uses it.

The HF loader sets n_prefill_layer to the index of the first ratio-1 layer (deepinfer/hugging_face/config.py:158-161). By line 21, that layer is the first consumer. The docstring of the loader says otherwise; the page Model map: DeepSeek-V4.1-Flash in DeepInfer explains the difference. This site describes the code.

The first consumer layer saves its attention-norm output in the CrossLayerRuntime:

In a consumer layer that is a KV source, the compressor weights go into a separate projection, shared_hidden_kv_proj (deepinfer/model_executor/models/v4_modules/attn.py:345-352, deepinfer/model_executor/models/v4_modules/attn.py:372-373). Step 5: full compressed KV, compact attention#

In compact mode, each consumer layer first writes its compressed KV and index keys for all prompt positions, from the full hidden state:

Deep dive#

The sections below give the full detail. Open them one at a time, or use Open all deep dives at the top of the page.

Deep dive

Worked example: a 1,000-token prompt

Settings: compact, KEEP_TOKENS = 140, window 128 (the docs value), ring 134, one sequence, one prefill chunk (q_start = 0, q_len = data_len = 1,000), no context parallelism.

  1. Producer layers. All 1,000 rows, as without YOCO.
  2. Clip. clip_prefix = clamp(1,000 − 140 − 0, 0, 999) = 860 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:225). The kept rows are 860 … 999: yoco_consumer_total_q = 140, yoco_consumer_query_indices = [860 … 999] (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:261-265).
  3. Boundary. At layer n_prefill_layer, the hidden states shrink from [1000, hc, hidden] to [140, hc, hidden], by a gather with the query indices (deepinfer/model_executor/models/v4_modules/yoco.py:65-67).
  4. Compressed KV. Each KV-source consumer layer writes entries for all 1,000 positions: 1,000 in a C1 layer, 500 in a C2 layer. Index keys likewise (deepinfer/model_executor/models/v4_modules/attn.py:692-721).
  5. Window. For a kept query at pos, the oldest visible key is max(pos − 127, 860) (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:155). Query 860 sees 1 key; query 900 sees 41; queries 987 … 999 see 128.
  6. Ring. A kept row writes the ring only if it is among the last 134 rows of the chunk: rows 866 … 999 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:267-271). Rows 860 … 865 are computed but not stored.
  7. Top-k. The indexer selects keys only for the 140 kept queries. Each kept query reads (pos + 1) / ratio compressed entries, as without truncation (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:292-301).
  8. First decode step. The query at 1,000 reads ring positions 873 … 1,000. All of them were written: 873 … 999 by the prefill, 1,000 by the step itself.

Work. Each consumer layer runs its query projection, attention and MoE on 140 rows instead of 1,000. Only the KV path stays at full length. Each KV-source consumer layer projects, compresses and stores the KV of all 1,000 positions. It also stores their index keys. The deployment notes report "nearly halving total prefill computation" for V4.1 (doc/inference_deployment_qa.md:187).

Deep dive

Why the result is approximate, and why that is acceptable

The first consumer layer gets exact inputs for every kept row: they come from the producer layers, which saw the whole prompt. Its SWA KV is exact. But its attention output for rows 860 … 986 used a cut window. So the next consumer layer gets slightly different inputs for those rows, and stores slightly different SWA KV. The difference moves forward one window per layer. This is a deduction from the visibility rule (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:149-168).

The deployment notes agree. An exact rebuild "would require running the last 2,560 tokens through 20 decoder layers" (128 × 20). The replay result "is used for decode only and never enters the prefix cache" (doc/inference_deployment_qa.md:187). The numbers 20 and 2,560 come from the docs.

The cache layout follows the same rule. The SWA rings of consumer layers are in the "dropped" part of the state slot, which never goes to the external KV store (deepinfer/worker/cache_engine.py:113-116, deepinfer/worker/cache_engine.py:221-235). The compressed KV of consumer layers is exact, because it comes from the full shared hidden state.

Why KEEP_TOKENS ≥ window + backtracking. The translated comment says: after a rollback, the decoder must still get a full window of SWA (deepinfer/worker/model_runner.py:108). With 134 kept rows, the ring holds every position that the first decode step can read. The README value 140 is 6 rows above this minimum; the repo does not say why.

Deep dive

_store_yoco_full_kv, line by line

  1. Lines 684-685. An SWA-only consumer layer has no compressed KV, so it returns at once.
  2. Line 688. Expand the index fields of the full metadata (once; later calls do nothing).
  3. Lines 692-709. A KV source projects consumer_full_hidden with shared_hidden_kv_proj only. It skips the merged projection, so it does not compute unused index weights. Then it stores the main KV for all rows and keeps pre_rope_kv.
  4. Lines 710-712. A KV consumer with its own indexer reads pre_rope_kv from the runtime.
  5. Lines 714-721. The index-K store for all rows.

Cross-layer sharing must not cross the boundary: the first consumer layer must be a KV source (deepinfer/model_executor/models/v4_modules/cross_layer.py:114-116). At the boundary, compact_yoco_boundary also compacts a top-k list that a producer layer shares with consumer layers (deepinfer/model_executor/models/v4_modules/yoco.py:116-122).

Deep dive

Context parallelism, DFlash and Engram

  • CP. Compact mode cuts first and then splits for CP again. Each rank selects its kept rows, all ranks all-gather them, and each rank takes its new rows (deepinfer/model_executor/models/v4_modules/yoco.py:55-76). The view rebuilds the mirror index with prepare_cp_mirror (deepinfer/model_executor/input_metadata/yoco.py:130-182). The userbuffer grows to carry the mHC residual (deepinfer/model_executor/models/deepseek.py:417-420).
  • DFlash. The DFlash target layers must be all producers or all consumers (deepinfer/model_executor/models/deepseek.py:128-135). If they are consumers, dflash_input shrinks to the kept rows (deepinfer/model_executor/models/deepseek.py:199-205).
  • Engram. Engram layers must be producers in compact mode (deepinfer/model_executor/models/deepseek.py:136-138, deepinfer/model_executor/models/decoder_layer.py:136).
Deep dive

The scheduler, the cost estimate and the cache-hit policy

  • Cost estimate. The engine gives the mode and KEEP_TOKENS to the FlopsEstimator (deepinfer/engine/llm_engine.py:318-322). It counts the consumer rows from the cut-off, and keeps the last row of a fully cut chunk (csrc/engine/flops_estimator.hpp:259-278).
  • truncate_len. The engine passes KEEP_TOKENS to the C++ scheduler only in compact mode, else 0 (deepinfer/engine/llm_engine.py:260, deepinfer/engine/llm_engine.py:315). In this release, scheduler.hpp only stores the value (csrc/engine/scheduler.hpp:88, csrc/engine/scheduler.hpp:1167).
  • Hit policy (docs only). The deployment notes give two rules. First: "under the YOCO truncation requirement, the maximum hit length for an input of length L is at most L − 134". Second: "If an SWA KV cache exists in the range L1 − 128 to L1, the hit length is L1; otherwise it is L1 − 128" (doc/inference_deployment_qa.md:191). L1 is the hit length from the block KV cache, and 134 is "128-token window + 6 tokens of speculative backtracking". The KV cache system is not in this release (README.md:40).
Deep dive

Checking compact against mask: examples/yoco

The folder examples/yoco/ has an equivalence checker with two levels (examples/yoco/README.md:5-8):

  • L1 (mask-compact, one device, no weights). It compares the SWA pivots, the visible keys, the store slots and the compressed key ranges of both modes. The reference is: visible = window ∩ [N − KEEP_TOKENS, N) (examples/yoco/yoco_equiv.py:116-118). The cases cover a prompt shorter than, equal to and longer than KEEP_TOKENS, and chunks before, across and inside the range (examples/yoco/yoco_equiv.py:79-99).
  • L2 (logp + compare, 8 devices, a V4.1 checkpoint). It runs mask and then compact on a fixed trajectory. Then it compares logprobs and top-K element by element (examples/yoco/run_yoco_equiv_l2.sh:9-11).
python examples/yoco/yoco_equiv.py mask-compact --keep-tokens 140 --window 128
examples/yoco/run_yoco_equiv_l2.sh --model_name /path/to/compatible-v41-hf

The checker compares compact with mask, not with "off". It checks that compaction removes rows without other changes. It does not measure the approximation itself.

What can go wrong#

Set KEEP_TOKENS together with the mode

Set DEEPINFER_YOCO_PREFILL_KEEP_TOKENS when you set the mode. Its default is 0, and any mode other than off then fails an assert (deepinfer/model_executor/model_metadata_utils.py:90-92).

  • Too few kept tokens. A value below window + backtracking (134 with the defaults) fails at start-up (deepinfer/worker/model_runner.py:110-113). More draft tokens raise the minimum.
  • A model without consumer layers. The mode needs n_prefill_layer < N and above 0 (deepinfer/model_executor/model_metadata_utils.py:90-91).
  • Engram or split DFlash targets in compact mode. Asserts at model build (deepinfer/model_executor/models/deepseek.py:128-138).
  • Small differences in the output. With truncation on, the consumer-layer SWA KV of the last prompt tokens is approximate (a deduction from the visibility rule; the deployment notes agree). To compare with a reference run, set the mode to off.

Why it matters. With compaction on, the consumer half of the model costs much less in a long prefill. Only its KV path runs on every token. The price is an approximation in the consumer-layer SWA KV of the last prompt tokens, which the first decode tokens read. The attention and MoE work of the consumer layers does not grow with the prompt length.

Check yourself#

  1. 1
    What is the default of DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE, and which values does it accept?
    easy
    Show answer

    off; it accepts off, mask and compact (deepinfer/environ.py:188).

  2. 2
    With a window of 128 and the default 5 draft tokens, what is the smallest valid KEEP_TOKENS?
    medium
    Show answer

    128 + 6 = 134. The backtracking count is at least nextn + 1 = 6 (deepinfer/environ.py:132), and the runner asserts window + backtracking ≤ KEEP_TOKENS (deepinfer/worker/model_runner.py:110).

  3. 3
    In compact mode, why can the consumer layers skip most prompt rows but still have a complete compressed cache?
    medium
    Show answer

    Their compressed KV comes from the shared hidden state (deepinfer/model_executor/models/v4_modules/attn.py:345-352). The first consumer layer saves the full attention-norm output as consumer_full_hidden before the rows shrink (deepinfer/model_executor/models/decoder_layer.py:137-140), and _store_yoco_full_kv writes the KV of all positions from it (deepinfer/model_executor/models/v4_modules/attn.py:692-709).

  4. 4
    A 1,000-token prompt, compact, KEEP_TOKENS = 140, window 128. How many SWA keys does the consumer-layer query at position 900 see, and which kept rows write the ring?
    hard
    Show answer

    41 keys (860 … 900): the oldest visible key is max(900 − 127, 1,000 − 140) = 860 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:155). Rows 866 … 999 write the ring, because a row must be in the kept range and among the last 134 rows (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:267-271). See the deep dive "Worked example".

  5. 5
    The deployment notes say the replay result "never enters the prefix cache". Where does the code put the consumer-layer SWA rings to match this?
    hard
    Show answer

    In the "dropped" region of the state slot, after the stored SWA rings of the producer layers. Only the stored region goes to the store (deepinfer/worker/cache_engine.py:113-116, deepinfer/worker/cache_engine.py:221-235, deepinfer/worker/cache_engine.py:306).

  • Context parallelism (mirror CP)With context parallelism, the devices of one engine share the tokens of a long prefill. A mirrored token order gives each device the same amount of causal attention work.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
  • Input metadata (varlen batching)Before each forward pass, DeepInfer packs the tokens of all scheduled sequences into one flat list and computes index tensors that tell each kernel where every token is, where to write its cache entry and which keys to read.
