Data parallelism and step votes

IntermediateDeepInfer conceptsabout 11 min read + 5 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Parallelism basics Beginner
  • Prefill and decode Beginner
  • The scheduler Intermediate

In one sentence

Each data-parallel replica is its own engine process, but the MoE layers connect them. So the replicas vote with all-reduces, and then all run a prefill step or all run a decode step.

The idea#

DeepInfer uses data parallelism (DP) for attention. One DP replica is one engine: one Python process with its own LLMEngine, its own scheduler, its own requests and its own KV cache. Replicas do not share requests. The docs say "attention uses data parallelism (#DP = #EP)" (doc/inference_deployment_qa.md:33).

The replicas are not independent, because of the MoE layers. With expert parallelism, each rank holds only some experts. In each MoE layer, DeepEP sends tokens to the ranks of their experts and back. These are collectives: every rank of the EP group must call them, also a rank with no tokens.

So the replicas must keep in step. Three rules make this true:

  1. The same number of steps. A replica keeps calling step() while any replica has work.
  2. The same kind of step. At a prefill attempt point, the replicas vote. Then all run a prefill step, or all run a decode step.
  3. A step with no work is still a step. A replica with nothing to do runs a placeholder step: the model runs on one dummy sequence.

Each vote is an all-reduce over the DP group. We call it a step vote.

An everyday comparison. Think of rowers in one boat. Each rower has an own oar and own strength, like a replica with its own requests. The boat moves well only if all rowers pull at the same time. Before a change of stroke, the crew agrees on the new stroke. A rower with no strength left still moves the oar with the others. The analogy stops at the vote: DeepInfer replicas do not vote before every step, only at attempt points. Between attempt points, all replicas run decode steps without a vote.

In the code#

Step 1: one process per replica#

The example launcher starts one process per DP rank. It uses the spawn method and waits for all of them:

Each process makes its own LLM with engine_rank = dp_rank (examples/offline_inference.py:45-51, examples/_config.py:113-117). ParallelConfig stores data_parallel_rank = engine_rank % data_parallel_size (deepinfer/config.py:167). The engine rank also sets the global rank: engine_rank × cp_size + cp_rank (deepinfer/worker/base.py:329).

The example gives the replicas different work on purpose: replica r gets r + 1 copies of the test prompts (examples/_prompts.py:100). So replica 0 finishes first and then runs placeholder steps until the last replica is done.

Step 2: the DP group#

create_process_groups makes the DP group and a Gloo (CPU) copy of it:

The rearrange puts ranks with the same cp_rank into one group. With CP size 1, the DP group is all engines. With CP size 2 and 4 engines, the DP groups are [0, 2, 4, 6] and [1, 3, 5, 7]. The scheduler runs only in the engine process (CP rank 0), so only the group [0, 2, 4, 6] votes.

The engine gives the scheduler the Gloo copy when ZOS is on (the default for a NORMAL engine), else the device group (deepinfer/engine/llm_engine.py:313). The scheduler stores the choice and puts its vote tensor on the CPU or on the device (csrc/engine/scheduler.hpp:109-111, csrc/engine/scheduler.hpp:170-182).

Step 3: the same number of steps#

LLM._run_engine calls step() while has_unfinished_requests() is true (deepinfer/entrypoints/llm.py:176-178). That function takes the maximum over the DP group:

So the loop ends on all replicas in the same call. A replica with no requests keeps calling step() until the busiest replica is done.

Step 4: the same kind of step#

The C++ scheduler makes the decision in _schedule, in the branch for the NORMAL engine:

  1. Lines 308-312: if decode_step is not an attempt point, the step is a decode step. No vote runs.
  2. Line 313: this replica "wants" a prefill if the KV cache use is 90 % or less and the front of waiting is schedulable.
  3. Lines 315-319: vote 1, an all-reduce MIN. The encoding makes MIN mean "any" at an ANY point and "all" at an ALL point.
  4. Lines 324-326: only a replica that wants a prefill tries to schedule one.
  5. Line 332: vote 2. If no replica got a batch, all run a decode step.
  6. Line 340: a replica with no batch returns an empty prompt step. The engine turns it into a placeholder step.

decode_step is set to 0 after a prompt step and goes up by 1 after a decode step (csrc/engine/scheduler.hpp:676-680). All replicas run the same step types, so the counter has the same value on all of them. The page The scheduler explains the intervals and the watermark in full.

Step 5: placeholder steps#

The engine marks a step with no scheduled sequence as a placeholder (deepinfer/engine/llm_engine.py:972). The worker then runs the model on one dummy sequence:

The dummy sequence has one token with id 0, block table [0] and greedy sampling (deepinfer/worker/model_runner.py:386-403). The free list of the block manager starts at block 1, so block 0 is never given to a real sequence (csrc/engine/block_manager.hpp:27-30). So the dummy step does not change the data of real sequences. The model still runs every layer, so every MoE collective runs. The engine ignores the sampler output of a placeholder step (deepinfer/engine/llm_engine.py:987).

Step 6: why one step type#

The source comment states the rule (line 296 above) but not the reason. The code shows these collectives in a step:

  • MoE dispatch and combine over the EP group, in every MoE layer (deepinfer/model_executor/models/v4_modules/mlp.py:565-616). The EP group is a block of ep_size neighbour ranks, or the world group (deepinfer/model_executor/parallel_utils/parallel_state.py:101-106). So it holds the ranks of several replicas. The dispatch passes a different token limit in a prefill step and in a decode step (deepinfer/model_executor/models/v4_modules/mlp.py:476).
  • The draft model runs only in decode steps, and its layers have MoE blocks (deepinfer/model_executor/layers/sampler.py:236-248, deepinfer/model_executor/models/mtp/dflash.py:389-392).
  • CP all-gathers run only in prefill steps (deepinfer/model_executor/models/v4_modules/attn.py:766).
  • The EPLB statistics run an all-gather over the EP group once every 128 steps (DEEPINFER_MOE_LB_STAT_INTERVAL, deepinfer/environ.py:118, deepinfer/model_executor/eplb/__init__.py:167-190). This needs the same number of steps on all ranks.

A collective finishes only when every rank of the group calls it. If two ranks call different collectives, or the same collective with different arguments, they can wait for each other with no end. (This is general behaviour of collectives, not a DeepInfer rule.)

So a normal decode step has one all-reduce: the loop check. An attempt point has two or three. The vote tensors are one int32 value (csrc/engine/scheduler.hpp:170-182). The loop check uses one int64 value (deepinfer/engine/llm_engine.py:676).

Device or CPU. With ZOS on, both use the Gloo group and CPU tensors (deepinfer/engine/llm_engine.py:667-669, deepinfer/engine/llm_engine.py:313). A device all-reduce followed by .item() waits for the device. A CPU vote does not. With ZOS off, both use the device group.

A detail with one replica. The comment above _dp_allreduce says that it communicates also when dp_size == 1, and the caller must skip it (csrc/engine/scheduler.hpp:169). _schedule does not skip it. With one replica, the vote is an all-reduce over a group of one rank. The loop check in Python does skip it (deepinfer/engine/llm_engine.py:675).

Deep dive

A worked example with four replicas

Setting: --ep 4, so 4 replicas and an EP group of 4 ranks (examples/offline_inference.py:24-28). Default intervals: ALL every 70, ANY every 100 (deepinfer/environ.py:174-177). Replicas 0-2 have running sequences. Replica 3 has none.

  1. decode_step 1 to 69: decode steps, no vote. Replica 3 runs placeholder decode steps.
  2. decode_step = 70 (ALL): one new request has arrived at each of replicas 0, 1 and 2. Vote 1: MIN(1, 1, 1, 0) = 0. No prefill. All decode.
  3. 71 to 99: decode steps, no vote. The new requests wait.
  4. 100 (ANY): vote 1: MIN(0, 0, 0, 1) = 0, so a prefill step. Replicas 0-2 schedule their prompts. Vote 2: MIN(0, 0, 0, 1) = 0. Replica 3 returns an empty prompt step and runs a placeholder prefill. decode_step becomes 0 on all replicas.
  5. Next step, decode_step = 0 (ALL): replica 0 has a second chunk to prefill. Replica 3 has nothing, so vote 1 fails. All decode, and decode_step becomes 1. The second chunk waits until step 70 (ALL, fails again if replica 3 is still empty) or step 100 (ANY).

The result: the new requests waited 30 decode steps for their first prefill. Without the idle replica 3, they would have started at step 70. The ANY points bound the wait: a prefill waits at most about 100 decode steps, the comment says (csrc/engine/scheduler.hpp:301-302).

Where the 90 % watermark comes in: a replica with a full KV cache does not want a prefill (line 313). At an ALL point it blocks the others. At an ANY point the others prefill without it.

Deep dive

Data-parallel load balancing: in the docs, not in this release

In this release, nothing moves requests between replicas. Each process gets its own requests from its caller. The README lists "Load balancing across data-parallel replicas for both prefill and decode" under "Required for a complete inference service (not included in this release)" (README.md:38-42).

The deployment Q&A describes the production balancers in its section "Data-parallel load balancing" (doc/inference_deployment_qa.md:105-127):

  • Prefill. Requests go into 4 tiers by total context length: under 16K, 16-64K, 64-256K and 256K or more. Engines pull work by their remaining compute quota. Inside a DP group, each request goes to the DP rank with the lowest quota load (doc/inference_deployment_qa.md:109-113).
  • Inside one GPU. FIFO, with a chunk size from a time budget and a fitted quadratic cost model, at most 32,768 tokens. "The budget itself is further reduced by an all-reduce MIN within the DP group" (doc/inference_deployment_qa.md:115).
  • Decode. Uniform routing over all GPUs of all decode instances, which balances the request count and the total KV length (doc/inference_deployment_qa.md:119).
  • Result. "roughly 80% of a perfectly balanced offline benchmark" (doc/inference_deployment_qa.md:127).

The code of this release does not have the compute quota or the cost model in its scheduler. The step votes are the only coordination between replicas in this release.

What can go wrong#

Do not call step() on only some replicas

Every replica must call step() the same number of times. LLM.generate does this with the MAX vote. Code that drives the engine directly, such as a benchmark, must keep this rule too. A replica that stops early leaves the others waiting in a collective.

  • Slow first tokens with uneven load. One replica with no waiting request makes every ALL vote fail. New requests on the other replicas then wait for the next ANY point, up to about 100 decode steps (csrc/engine/scheduler.hpp:301-302).
  • Wasted device time. A replica with no work runs placeholder steps, each with a full pass through all layers. The example launcher makes this visible: replica 0 has the fewest prompts (examples/_prompts.py:100).
  • Finished requests in the queue. Without a clean-up, an aborted request that stays in waiting would block the ALL votes of the group for ever. The source comment gives this reason, and the decode branch removes such requests (csrc/engine/scheduler.hpp:564-577).
  • A hang, not an error. If the replicas disagree on a collective, nothing raises at once. The ranks wait. DEEPINFER_GLOO_TIMEOUT (4 hours) applies only to the default group (deepinfer/worker/base.py:334-340). The DP groups come from new_group with no time-out argument, so the PyTorch default applies (deepinfer/model_executor/parallel_utils/parallel_state.py:34).

Why it matters. DP for attention needs no communication in the attention layers, but MoE with EP ties all replicas together. The votes are the price: one replica with no work, or with a full cache, can delay the prefills of all replicas. A production system needs a load balancer in front of the replicas. This release does not have one.

Check yourself#

  1. 1
    Is one DP replica a thread, a process or a device group?
    easy
    Show answer

    A process. run_dp starts one process per DP rank with the spawn method (examples/_launch.py:35-44). Each process makes its own LLM and engine. With CP above 1, the replica also starts CP follower processes.

  2. 2
    Replica 2 has no requests, but replica 0 still has three. Does replica 2 call step()?
    easy
    Show answer

    Yes. has_unfinished_requests() takes the MAX over the DP group, so it is true on every replica (deepinfer/engine/llm_engine.py:673-678). Replica 2 runs placeholder steps (deepinfer/worker/worker.py:125-127).

  3. 3
    At an ANY point, replica 1 wants a prefill, but its _schedule_prefill returns nothing because all slots are full. The other replicas do not want a prefill. What kind of step runs?
    medium
    Show answer

    A decode step on all replicas. Vote 1 passes (replica 1 sent 0). Vote 2 fails: every replica sends 1 because no replica has a batch, and MIN = 1 (csrc/engine/scheduler.hpp:332-335). The comment explains why: an empty prompt step would reset decode_step and could loop for ever.

  4. 4
    Why does the vote use MIN for both ALL and ANY points?
    medium
    Show answer

    Only the encoding changes. For ALL, "wants" is 1, so MIN is 1 only if all send 1. For ANY, "wants" is 0, so MIN is 0 if one sends 0 (csrc/engine/scheduler.hpp:315-319). One reduce op serves both.

  5. 5
    You run --ep 2 --dp 8. Replicas 0 and 1 share an EP group. Could replicas 0-1 and replicas 2-3 safely run different step types? What does the code do?
    hard
    Show answer

    From the MoE side, perhaps: their EP groups are disjoint ([0,1] and [2,3], deepinfer/model_executor/parallel_utils/parallel_state.py:101-106). But the code does not make this choice. The scheduler votes over the whole DP group of 8 replicas (deepinfer/model_executor/parallel_utils/parallel_state.py:91-93, csrc/engine/scheduler.hpp:170-182). So all 8 run the same step type. One empty replica can make the ALL votes of all 8 fail.

Related pages

  • The schedulerIn every engine step, the C++ scheduler runs either a prefill batch or a decode batch. It starts prefills only at attempt points, cuts long prompts into chunks, gives KV blocks, and preempts sequences when the blocks run out.
  • Offline API and the step loopLLM.generate() adds all requests, then calls LLMEngine.step() until no request is left. Each step schedules one batch, runs the model once, and returns handles to the new outputs. With ZOS, a decode step returns the tokens of the step before it.
  • Expert parallelism: dispatch, grouped GEMM, combineDeepInfer splits the expert slots of every MoE layer evenly over the EP ranks. DeepEP dispatch sends each token to the ranks of its experts, DeepGEMM runs grouped GEMMs there, and DeepEP combine brings the results back.
  • Context parallelism (mirror CP)With context parallelism, the devices of one engine share the tokens of a long prefill. A mirrored token order gives each device the same amount of causal attention work.
  • Expert load balancing (EPLB)EPLB counts the tokens of every expert slot in every step. Every N steps it gives busy experts extra copies, places all copies so that the EP ranks get about the same work, and moves the expert weights in place.
  • Tour: One step on many GPUsFollow one prefill step on 4 GPUs (2 data-parallel engines, each with 2 context-parallel ranks) in 10 stops, from the step vote to the outputs, with the rank, the group and the tensor shapes at each stop.
  • csrc/engine/scheduler.hpp: the C++ Schedulerscheduler.hpp holds the C++ Scheduler: the waiting and running queues, the choice between prefill and decode, block allocation, preemption, and the bookkeeping after each step. It also defines SchedulerOutputs and three free functions.
  • engine/llm_engine.py: the LLMEngine classLLMEngine starts the workers, sizes the KV cache, owns the C++ scheduler, and runs one engine step each time LLM calls step().
  • parallel_utils/parallel_state.py: the process groupsparallel_state.py makes all torch.distributed process groups of one rank (world, local, DP, CP, EP, EP-in-DP, Engram and three Gloo copies), the shared-memory queue of the CP group, and the global PG object that the rest of the code reads.
