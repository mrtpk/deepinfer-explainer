Input metadata (varlen batching)

IntermediateDeepInfer conceptsabout 10 min read + 12 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Batching Beginner
  • The KV cache Beginner
  • Paged KV cache and block manager Intermediate

In one sentence

DeepInfer packs the new tokens of all sequences into one flat list and computes index tensors that tell the kernels where each token goes.

The idea#

The scheduler gives the worker a list of sequences. The sequences have different lengths. A prefill chunk can have thousands of new tokens, and a decode sequence has 1 + 5 tokens. The kernels on the device cannot read C++ sequence objects. They need flat tensors of numbers.

So DeepInfer puts the new tokens of all sequences end to end, with no gaps. This is a packed (varlen) batch. Each new token is one row. Then DeepInfer computes small index tensors for these rows. Together they are the input metadata:

  • Where each sequence starts. Offset arrays such as cu_seqlens.
  • Where each token is in its sequence. The position of each row.
  • Where to write. A slot mapping gives the cache row for each new cache entry.
  • What to read. Block tables, window descriptions and key ranges tell attention which earlier entries each row sees.

In a prefill step, C++ code computes these tensors on the CPU. In a decode step with ZOS (the default), C++ packs only per-sequence values and a device kernel computes the per-row tensors (deep dive). Python wraps the tensors in one object of the class InputMetadataV4, or of its subclass InputMetadataV4VL for a vision model (deepinfer/model_executor/model_metadata_utils.py:142-144). Every layer of the model reads this object.

An everyday comparison. Think of a delivery truck. The parcels of many customers go into the truck end to end, with no gaps. A packing list says where the parcels of each customer start. It also gives, for each parcel, the shelf in the warehouse where it goes. The kernels are the warehouse workers: they read only the list, not the customer files.

The comparison stops at two points. First, in a decode step with a CUDA graph, the truck has a fixed size, so DeepInfer adds empty parcels (padding rows). Second, some list entries are short descriptions that the device expands later into full index tables.

The picture#

Sequence A is the last chunk of a 260-token prompt: its first 200 tokens are already in the cache. Sequence B is a new 400-token prompt. The scheduler cut it at 200 tokens, so it is last in the batch. Every value in the figure comes from the rules in the next section. The deep dive repeats the example with all fields.

In the code#

Step 1: the scheduler gives one SequenceMetadata per sequence#

The C++ scheduler makes one SequenceMetadata object for each scheduled sequence. It has two lengths: seqlen_q (the new tokens of this step) and seqlen_k (all tokens that the step can see) (csrc/engine/scheduler.hpp:696-697). A step is a prefill step or a decode step, never both. The sampler preparation checks this: "Mixed prefill and decode batches are unsupported" (csrc/engine/prepare_sample.cpp:61).

Why the cut chunk is last

In a NORMAL engine, the scheduler stops the prefill batch right after it cuts a prompt (csrc/engine/scheduler.hpp:543-545). So a batch has at most one cut chunk, at the end. A continued chunk (like A) can come earlier.

Step 3: positions and token ids for every row#

The first loop is the same for prefill and decode. Row j of a sequence gets the position seqlen_k − seqlen_q + j:

In a prefill step, line 112 copies the seqlen_q prompt ids. In a decode step, it copies one id, the last real token. Lines 116-118 then add the draft tokens. So a decode sequence sends 1 + 5 rows with the default settings.

Step 4: where the new cache entries go#

DeepInfer has two kinds of cache for attention. The compressed cache is paged in blocks of 128 tokens. The sliding-window attention (SWA) cache is a ring per sequence in a state slot (Paged KV cache and block manager). update_common_v4 writes one slot map for each:

The dict slot_mapping_store_ca has one tensor per compress ratio, with keys such as "1" and "2". The model accepts only ratios 0, 1 and 2 (deepinfer/model_executor/model_metadata_utils.py:52-53). The SWA ring has swa_block_size rows: the window plus the backtracking tokens (deepinfer/worker/cache_engine.py:88-93, deepinfer/environ.py:132). The window size comes from the checkpoint config. The docs give 128 + 6 = 134 for V4.1 (doc/inference_deployment_qa.md:191), and this page uses these example values.

Step 5: what each row reads#

Prefill and decode read the cache in different ways.

  • Prefill gathers the history of all sequences into one flat buffer first. A block load plan (load_segments_swa, load_segments_ca) says which cache rows to copy (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:461-476). Then each row gets a short description of its window in that buffer: kv_swa_full_index_pivots (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:478-527).
  • Decode reads the paged cache in place. Each row gets a copy of its sequence's block table (block_tables), its visible length (context_lens) and an [offset, length] pair for its window (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:585-652).

The device expands the short descriptions into full index tables at the start of the forward pass. Each attention layer calls compute_attn_info, and the first call does the work (deepinfer/model_executor/models/v4_modules/attn.py:765, deepinfer/model_executor/input_metadata/input_metadata.py:343-389).

Step 6: decode with a CUDA graph#

A decode step usually replays a captured CUDA graph (CUDA graphs). The graph has fixed input buffers. So the model runner adds padding sequences up to the graph size, and C++ writes straight into the graph's buffers:

The second figure shows a decode step of two sequences with 6 rows each, padded to 16 rows.

Step 7: views for special features#

Three features change the metadata during the forward pass. The deep dive explains each one.

  • Context parallelism. With CP above 1, the model reorders the prefill rows for each rank: prepare_for_mirror_cp (deepinfer/model_executor/models/deepseek.py:168-170).
  • YOCO prefill truncation. At the first consumer layer, the model switches to a different view of the metadata: fewer rows in compact mode, narrower windows in mask mode (deepinfer/model_executor/models/deepseek.py:190-207).
  • DFlash drafts. The draft model gets its own fixed-stride view: build_dflash_input (deepinfer/model_executor/models/mtp/dflash.py:367-372).

Fields that the device computes. kv_swa_full_index, kv_ca_index, kv_ca_index_len, compressed_batch_mapping, kv_swa_index and the scheduling metadata of the attention libraries start as None. compute_attn_info fills them in the first attention layer (deepinfer/model_executor/input_metadata/input_metadata.py:343-389). The width of kv_ca_index is max_model_len / N, rounded up to a multiple of 128: the comment says that the sparse-attention kernel needs this (deepinfer/model_executor/input_metadata/input_metadata.py:362).

The size of a decode block table. max_num_blocks is the block count of runtime_max_model_len, rounded up to a multiple of 64 (deepinfer/worker/model_runner.py:114-115). With runtime_max_model_len = 32784 (max_model_len 32768 plus 16 extra positions with nextn 5 and ZOS on, deepinfer/config.py:11-16): 257 blocks, rounded up to 320. So 16 rows of block tables take 16 × 320 × 4 = 20,480 bytes. C++ copies only the blocks that the row needs; the rest of the row is not written (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:207).

Deep dive

Worked example: the prefill step of the figure, field by field

Settings: block size 128, window 128, ring 134, ratio 2 (64 compressed entries per block). Sequence A: seqlen_q = 60, seqlen_k = 260, block table [7, 2, 9], state slot 2. Sequence B: seqlen_q = 200, seqlen_k = 200, block table [3, 4, 5, 6], state slot 1. B has four blocks because the scheduler gives a new sequence the blocks of its whole prompt (csrc/engine/block_manager.hpp:207-209, csrc/engine/sequence.hpp:291-293).

  1. total_q = 60 + 200 = 260. cp_mirror_len = 2 × (⌈60/2⌉ + ⌈200/2⌉) = 260 for CP 1.
  2. positions: rows 0-59 = 200 … 259; rows 60-259 = 0 … 199.
  3. cu_seqlens_q = [0, 60, 260], cu_seqlens_k = [0, 260, 460].
  4. New compressed entries: A: 260/2 − 200/2 = 30 (entries 100-129). B: 100 (entries 0-99). n_cq = 130, cu_compressed_seqlens_q["2"] = [0, 30, 130].
  5. positions_c["2"] = 2 × j: 200, 202, …, 258, then 0, 2, …, 198.
  6. slot_mapping_store_ca["2"]: A entry 100 is in logical block 1 (block 2): 2 × 64 + 36 = 164, up to 191 for entry 127. Entries 128-129 are in block 9: 576, 577. B: 192-255 (block 3), then 256-291 (block 4).
  7. slot_mapping_store_swa: A rows: 2 × 134 + (200 … 259) % 134 = 334 … 393. B rows 60-125 (positions 0-65): -1, because only the last 134 rows of a chunk go to the ring. Positions 66-133: 200-267. Positions 134-199 wrap: 134-199.
  8. state_block_idx = [2, 1].
  9. ks["2"] and ke["2"] (if the ratio-2 layers are sparse): A rows: ks = 0, ke = (pos + 1) / 2 = 100 … 130. B rows: ks = 130, ke = 130 + (pos + 1)/2 = 130 … 230.
  10. load_segments_ca["2"]: [7,0,64,0], [2,0,64,64], [9,0,2,128], [3,0,64,130], [4,0,36,194]. So total_k_compressed["2"] = 230. The plan covers all seqlen_k / 2 entries of each sequence.
  11. load_segments_swa: A's history is positions 72-199. They are ring rows 72-133, then 0-65: [2,72,134,0], [2,0,66,62]. B has no history: [-1,0,128,128] fills zeros. total_k_swa = 256.
  12. Pivots of B row 259 (position 199) are [256, 0, 388, 128]. B has no history. The row reads 128 new rows from buffer row 388, which is 316 + 72: position 72 of B.

The C++ comment gives the rule for the pivots (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:478-486). X[0:P1] = P0 + arange(P1), then X[P1:P1+P3] = P2 + arange(P3), and the rest is −1. The window always has window_size slots: history count plus new count is at most 128.

Worked example: the decode step of the second figure

Settings: max_num_seqs = 4, nextn = 5, so the graph sizes are [1, 2, 4, 8, 16, 24] (deepinfer/worker/cuda_graph_runner.py:41-51). ZOS is off, so prepare_decode_v4 in C++ writes every row. Sequence C: 301 tokens, seqlen_k = 306, block table [5, 6, 8], state slot 3. Sequence D: 129 tokens, seqlen_k = 134, block table [10, 11], state slot 4. The scheduler sorts decode sequences by length, longest first (csrc/engine/scheduler.hpp:648-649).

  1. total_q = 12. select(12) returns 16, so 4 placeholder sequences follow (deepinfer/worker/model_runner.py:185-188).
  2. A placeholder has seqlen_q = 1, seqlen_k = 1 and block table [0] (deepinfer/worker/model_runner.py:386-403). It does not set state_id, so it gets the default state slot 0 (csrc/engine/pybind_sequence.cpp:152). C++ marks it with is_placeholder because its request id is "placeholder" (csrc/engine/sequence.hpp:398).
  3. positions: 300-305, 128-133, 0, 0, 0, 0. context_lens: 301-306, 129-134, 1, 1, 1, 1.
  4. slot_mapping_store_swa: 3 × 134 + 300 % 134 = 434 … 439; 4 × 134 + 128 = 664 … 669; padding 0.
  5. slot_mapping_store_ca["2"]: an entry ends only when (position + 1) % 2 == 0 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:82). Position 301 ends entry 150: block [5,6,8][150 / 64] = 8, slot 8 × 64 + 22 = 534. The row values are -1, 534, -1, 535, -1, 536.
  6. block_tables use the smallest ratio of the model (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:566, csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:586). With ratio 1: C needs ⌈306/128⌉ = 3 blocks, D needs 2.
  7. kv_swa_index_offset_len for C row 0: the window has 128 positions and starts at 300 − 127 = 173. That is ring row 173 % 134 = 39, so the pair is [3 × 134 + 39, 128] = [441, 128].
  8. kv_ca_index_offset_len["1"] for row i, with max_num_blocks = 320 (see the field reference): [i × 320 × 128, (pos + 1)]. The offset points at row i of the flat block_tables; the device turns it into cache rows (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:606-611).

Why padding is safe. Block 0 and state slot 0 are never given to a real sequence: the free list starts at 1 (csrc/engine/block_manager.hpp:27-30). So padding rows write only to these two places. The MoE gate gets valid_token_mask as its mask (deepinfer/model_executor/models/v4_modules/mlp.py:387), and the sampler does not read them (see engine/prepare_sample.cpp: the sampler inputs).

Deep dive

Decode with ZOS: half on the CPU, half on the device

Zero-overhead scheduling is on by default. Then the CPU does not know the real seqlen_k of a sequence: the previous step is still on the device. So the decode path splits the work (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:307-382):

  1. C++ prepare_decode_zos_inputs packs only per-sequence values: lengths, state ids, a flat block table with offsets, and the token ids of fresh sequences (csrc/engine/zos.cpp:198-277).
  2. The worker corrects seqlens_k on the device from the accepted-token counts of the previous step. With DSpark (DEEPINFER_ENABLE_MTP_VARLEN), it also sets seqlens_q from the confidence rates (deepinfer/worker/worker.py:191-245).
  3. The kernel prepare_v4_decode_metadata computes all per-row fields on the device: positions, masks, slot maps, block tables, offset pairs (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:336-367).
  4. gather_input_ids_zos takes the token ids of continuing sequences from the previous step's device tensors, so no copy to the CPU is necessary (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:235-244).

With ZOS, the output buffers are device tensors (get_or_create uses device="cuda", deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:113-117). The kernel writes several ratio buckets in one launch, through equally spaced row views of one allocation (get_or_create_stacked, deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:120-159).

Deep dive

YOCO prefill truncation: the consumer view

A YOCO model has consumer layers after layer n_prefill_layer (deepinfer/model_executor/model_metadata_utils.py:87-88). With YOCO prefill truncation, the prefill step needs the consumer layers only for the last KEEP_TOKENS tokens of the prompt. C++ computes the extra fields when the mode is not off (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:349-360):

  • mask: only yoco_mask_swa_index_pivots. The layout stays full; the windows of rows before the kept range are empty (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:155, csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:285-289).
  • compact: yoco_consumer_* fields in a smaller layout: query_indices (which full rows stay), cu_seqlens_q, total_q, positions, pivots, ks/ke, offset pairs and the SWA slot map (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:334-342).

The rows to drop: clip_prefix = clamp(data_len − keep_tokens − q_start, 0, q_len − 1) (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:225). The upper limit q_len − 1 keeps at least one row, because the sampler always reads the last row of a chunk. Example with KEEP_TOKENS = 140: A (data_len 260, q_start 200) keeps all 60 rows. B (data_len 400, q_start 0) has clip_prefix = 199 and keeps 1 row. The compact batch has cu = [0, 60, 61].

At the first consumer layer, DeepseekModel.forward calls get_consumer_view() (compact) or get_mask_view() (mask) (deepinfer/model_executor/models/deepseek.py:191-207). Each view is a shallow copy. It sets the derived fields to None, so that compute_attn_info expands them again for the new pivots or layout (deepinfer/model_executor/input_metadata/yoco.py:86-128). The page YOCO and SWA bounded replay explains the model side.

Deep dive

Context parallelism: the mirror layout and the broadcast

With CP above 1, only the driver rank builds the metadata. For an eager step it sends all fields with broadcast_tensor_dict. Dict fields are flattened to keys such as "slot_mapping_store_ca.2", because the broadcast handles one level only (deepinfer/worker/model_runner.py:200-212, deepinfer/model_executor/input_metadata/input_metadata.py:391-413).

In a prefill step, each rank then works on its own part of the rows: the CP mirror layout. prepare_for_mirror_cp computes mirror_cp_index and new ks/ke on the device. It reorders positions and ngram_token_ids. gate_force_random keeps the full layout; a reordered copy goes to gate_force_random_cp. It sets valid_token_mask to mirror_cp_index != -1 (deepinfer/model_executor/input_metadata/input_metadata.py:170-208). input_ids keeps the full layout, because the embedding runs before the reorder (deepinfer/model_executor/models/deepseek.py:161-170).

The length per rank is cp_mirror_len = 2 × Σ ⌈seqlen_q / (2 × cp)⌉ (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:147-155). Example: our prefill batch with cp = 2: 2 × (⌈60/4⌉ + ⌈200/4⌉) = 2 × (15 + 50) = 130 rows per rank.

Deep dive

DFlash: a second, fixed-stride view

The DFlash draft model runs after the main model in a decode step. Its attention needs one block of draft rows per request, not the varlen rows of the main model. build_dflash_input makes a shallow copy and replaces six fields with one fused kernel: dflash_newx_slot_mapping_store, positions, input_ids, valid_token_mask, gate_force_random and dflash_kv_index (deepinfer/model_executor/input_metadata/dflash.py:36-84).

  • dflash_newx_slot_mapping_store: [real_cnt × dflash_block_size], SWA slots for the draft-token KV.
  • dflash_kv_index: [real_cnt × dflash_block_size, pad64(window_size + dflash_block_size)], the SWA slots that each draft row reads (deepinfer/model_executor/input_metadata/dflash.py:30-34).

The module docstring says, translated: the C++ prepare does not make these fields. With the DFlash CUDA graph, the graph captures and replays them (deepinfer/model_executor/input_metadata/dflash.py:1-8). See models/mtp/dflash.py: the DFlash draft model.

What can go wrong#

The C++ builder checks its inputs with TORCH_CHECK. A failed check raises a Python RuntimeError and stops the step.

  • YOCO keep length too small. KEEP_TOKENS must be at least window_size + DEEPINFER_MAX_BACKTRACKING_TOKENS (134 with the defaults). The model runner checks this at load time with an assert (deepinfer/worker/model_runner.py:107-113), and C++ checks it again in each prefill (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:355-357).
  • Block table too short. In a decode step, a row needs more blocks than max_num_blocks or than the sequence has (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:223).
  • Index overflow. The decode offset total_q × max_num_blocks × (128/N) must fit in int32 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:615-616).
  • Wrong buffer size. On the graph path, each existing buffer must have exactly the expected shape and dtype (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:41-43).
  • Unsupported compression. Ratios other than 0 (no compression), 1 and 2 stop the model load with ValueError (deepinfer/model_executor/model_metadata_utils.py:52-53).

Why it matters. Every attention kernel trusts these numbers. A wrong slot writes a token into the cache of another sequence, and no error appears. The checks above catch only shape errors. So when you change the scheduler or the cache layout, test the slot maps with a small example like the one on this page.

Check yourself#

  1. 1
    A prefill batch has two chunks with seqlen_q 60 and 200 and seqlen_k 260 and 200. What are cu_seqlens_q and cu_seqlens_k?
    easy
    Show answer

    cu_seqlens_q = [0, 60, 260] and cu_seqlens_k = [0, 260, 460]. Both are running sums that start at 0, with n_seq + 1 values (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:407-418).

  2. 2
    Which function turns the list of SequenceMetadata into an InputMetadataV4 object, and where do the tensors live after it returns on the eager path?
    easy
    Show answer

    ModelRunner._prepare_input_tensors (deepinfer/worker/model_runner.py:120-146). In a prefill step, C++ makes the tensors in pinned CPU memory (also in a decode step without ZOS). _prepare_input_driver then copies them to the device with .cuda(non_blocking=True) (deepinfer/worker/model_runner.py:198).

  3. 3
    A prefill chunk has 200 rows, state slot 1, and the ring has 134 rows. Which rows get -1 in slot_mapping_store_swa, and why?
    medium
    Show answer

    Rows 0-65. Only rows with seqlen_q − j ≤ swa_block_size write, so only the last 134 rows (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:103-106). Older rows would be overwritten in the ring by later rows of the same chunk.

  4. 4
    In a decode step, a padding row has positions = 0, state_block_idx = 0 and slot_mapping_store_swa = 0. Why does its write not damage a real sequence?
    medium
    Show answer

    Slot 0 and block 0 are never given to a sequence: the block lists start at 1 (csrc/engine/block_manager.hpp:27-30). The placeholder uses block table [0] (deepinfer/worker/model_runner.py:386-403) and the default state slot 0 (csrc/engine/pybind_sequence.cpp:152). valid_token_mask is False for it, and the sampler skips it. This is in the deep dive "Worked example: the decode step".

  5. 5
    With DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact and KEEP_TOKENS=140, a new 400-token prompt is cut into a first chunk of 200 tokens. How many rows does this chunk have in the consumer layers, and why not zero?
    hard
    Show answer

    One row. clip_prefix = clamp(400 − 140 − 0, 0, 200 − 1) = 199, so keep_len = 1 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:225-229). The upper limit q_len − 1 keeps one row because every prefill chunk sends its last row through the sampler (csrc/engine/prepare_sample.cpp:173-180). This is in the deep dive "YOCO prefill truncation".

  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • Sliding-window attentionEvery attention layer of DeepSeek-V4.1-Flash reads the most recent tokens (a window of 128 in the docs) from a ring of 134 slots per sequence and layer. This page shows the ring, the decode and prefill index paths, and how the window joins the compressed keys.
  • YOCO and SWA bounded replayYOCO splits the main layers into producer and consumer layers. Consumer layers project their compressed KV from one shared hidden state. With the optional prefill truncation (README feature "Decoder SWA bounded replay"), a prefill computes the consumer layers only for the last KEEP_TOKENS prompt tokens (140 in the README), with the window cut at that range. Only their compressed KV still covers every token.
  • Context parallelism (mirror CP)With context parallelism, the devices of one engine share the tokens of a long prefill. A mirrored token order gives each device the same amount of causal attention work.
