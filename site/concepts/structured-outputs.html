Structured outputs

IntermediateDeepInfer conceptsabout 12 min read + 8 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Sampling: temperature, top-k, top-p Beginner
  • The sampler Intermediate
  • Speculative decoding Intermediate

In one sentence

A grammar matcher tells the sampler which tokens may come next, and a mask sets all other logits to minus infinity.

The idea#

A LLM writes free text. Many programs need text with a fixed shape: JSON with known keys, a product code, or "yes" or "no". A structured output request carries a grammar that sets this shape. DeepInfer accepts three grammar types (README.md:29):

  • a regular expression, for example [A-Z]{2}-[0-9]{3};
  • a JSON schema, which sets the keys, types and allowed values of a JSON object;
  • an EBNF grammar, for example root ::= "answer=" ("yes" | "no").

The model does not learn the grammar. The engine forces it at each sampling step. A grammar matcher follows the tokens of the request through the grammar. Before each sample, it gives a token bitmask: one bit per vocabulary token. A kernel sets the logit of every forbidden token to minus infinity. Softmax turns minus infinity into probability 0, so the sampler can only pick an allowed token.

DeepInfer adds three things to this basic idea:

  1. Compilation off the step. xgrammar compiles the grammar on a thread pool that runs on its own CPU cores. The request enters the scheduler only when its matcher is ready.
  2. Masks for drafts. With speculative decoding, one decode step checks up to 5 draft tokens. So the CPU fills one mask for each draft row, and then rolls the matcher back.
  3. Failure stays local. A grammar error ends only its own request, with the finish reason "xgrammar runtime errors or timeout" (csrc/engine/sequence.hpp:57-58).

An everyday comparison. Think of a form with boxes: "date: __ / __ / ____". You can write any digit in a box, but you cannot write a letter. The form does not tell you which date to write; it only blocks the wrong kind of mark. The grammar mask works in the same way: the model still chooses, but only among allowed tokens. The comparison stops being true in one point. A paper form shows all boxes at once. The matcher knows only the next step, and the set of allowed tokens changes after each token.

The picture#

Read panel 1 along the arrows: across the top row, then down, then back to the left. Steps 1, 2, 4, 5 and 6 run on the engine thread (step 6 is C++ code). Only step 3 runs on a pool thread. Panel 2 is the ledger that the sampler and the scheduler share: the sampler reads the status, and process_outputs writes the new value back.

In the code#

Step 1: the request names its grammar#

A caller puts the grammar into SamplingParams(so_args=...). The example script sends one request of each type. Each prompt asks for long free text on purpose, so that the test shows the grammar, not the prompt, sets the shape:

The script then checks that each request stops with finish reason "stop" and the EOS token, and that the text matches the grammar (examples/_structured_output.py:43-63). SamplingParams stores the dict and does not check it (deepinfer/sampling_params.py:82). Two optional keys add a trigger: the docstring explains them in Chinese (deepinfer/sampling_params.py:39-43). Translated: "optional "trigger_token_ids" (one list[int]): the token id sequence that starts the grammar. When it appears in full, the grammar starts; before that, generation is free. Optional "bound_token_id": a non-negative int (0 is valid). Missing or None means no bound. It needs a non-empty trigger_token_ids, and a list is not valid. After the bound, no free token is allowed. First the trigger sequence is forced token by token, then the grammar starts."

Step 2: add_request starts the build and returns#

LLMEngine.add_request makes the sequence first. Then, for a request with so_args, it hands the sequence to the builder instead of to the scheduler:

  1. Lines 609-611: with enqueue=False, the engine waits for the matcher at once.
  2. Lines 620-623: _enqueue is the callback that runs later. An aborted matcher changes the status to FINISHED_SO_FAILED before the sequence enters the scheduler.
  3. Line 628: the normal path. submit starts the build and keeps (seq, future, on_ready) in a pending list (deepinfer/structure_output/so_matcher_builder.py:97-107).

The builder is a property that the engine makes on first use. It gets DEEPINFER_SO_BUILDER_CPUS cores (default 4) of the share of this GPU, and one pool thread per core (deepinfer/engine/llm_engine.py:329-342, deepinfer/utils.py:154-161). Each pool thread pins itself to these cores when it starts (deepinfer/structure_output/so_matcher_builder.py:33-48).

Step 3: a pool thread compiles the grammar#

The build task calls the compiler and wraps the result in a matcher (deepinfer/structure_output/so_matcher_builder.py:78-92). The compiler selects the xgrammar function by schema_type:

Every error becomes a RuntimeError with a short prefix. An unknown schema_type raises ValueError inside the try, so it also becomes RuntimeError("xgrammar invalid input: ..."). The engine thread does not see this exception directly: it sees an aborted matcher (step 5).

Step 4: pump() moves ready requests into the scheduler#

Once per step, pre_sampler_sync calls pump() (deepinfer/engine/llm_engine.py:841-842). pump() never blocks:

try_result() returns None while the task runs. After DEEPINFER_XGRAMMAR_TIMEOUT seconds (default 20) it returns an aborted matcher (deepinfer/structure_output/matcher.py:319-338, deepinfer/environ.py:168). The scheduler then skips the prefill of the request and reports it as finished (csrc/engine/scheduler.hpp:362-367).

Step 5: the sampler fills one mask per draft row#

At the end of the prompt, the engine sets the status from 0 to 1 (deepinfer/engine/llm_engine.py:913-915). From then on, Sampler._get_so_mask works for this request in every step. It runs on the CPU. The comment at line 135 says that this work runs while the logits are computed. In the code, the sampler calls _get_so_mask before it calls get_logits, so the CPU work overlaps the device work that was launched before (deepinfer/model_executor/layers/sampler.py:135-142). The core of it:

  1. Lines 352-355: status 2 means "running". The matcher first accepts the tokens that the previous step committed: the accepted drafts and the new output token. A rejection here is a bug, so it raises.
  2. Lines 356-357: status 1 means "first sample after the prompt". There are no old tokens to accept. The status becomes 2.
  3. Lines 361-364: mask 0 is the grammar state now. It applies to row 0 of the request.
  4. Lines 367-375: the matcher accepts the drafts one by one. After draft k (counted from 1), it fills mask k. The loop stops at the first draft that the grammar rejects.
  5. Line 376: rollback undoes the accepted drafts. The drafts are only guesses; the device decides later which of them stay.

The draft model does not use the grammar, so it can propose an illegal token. The mask catches it at verification. The illegal draft has target probability 0, so the sampler rejects it. Then it samples a new token from the allowed ones.

Step 6: one kernel sets forbidden logits to minus infinity#

A side stream copies the pinned masks to the device (deepinfer/model_executor/layers/sampler.py:391-407). In decode, the sampler then calls one kernel per draft step k (deepinfer/model_executor/layers/sampler.py:433-437). In prefill, there is only mask 0 (deepinfer/model_executor/layers/sampler.py:187-188). The CUDA kernel:

  1. Line 39: a grid of ceil(V / 8192) × len(indices) blocks. Each block handles 8,192 vocabulary columns of one request.
  2. Lines 44-47: the logits row is the first row of the request (ftp) plus k. If the request has fewer rows in this step, the block returns.
  3. Lines 55-56: a 0 bit sets the logit to minus infinity.

Step 7: the status goes back to C++#

The sampler returns its so_status list with the step output. process_outputs copies it into the C++ sequence (csrc/engine/scheduler.hpp:928-929). Then it checks the stored value, not the value of this step:

A failed request gets one filler token, id 0, and the status FINISHED_SO_FAILED.

Deep dive

XGrammarMatcher: trigger, bound, grammar and EOS

XGrammarMatcher wraps one xgrammar GrammarMatcher and adds a small state machine in front of it (deepinfer/structure_output/matcher.py:58-85). Its fields:

FieldStart valueMeaning
trigger_progress0How many tokens of the trigger sequence match now.
_trigger_failureKMP tableFallback lengths for a mismatch (deepinfer/structure_output/matcher.py:24-33).
_progress_history[]Old trigger_progress values, for rollback. At most MAX_ROLLBACK_TOKENS entries.
tokens_after_bound−1−1 until the bound token appears; then the count of tokens after it.
tokens_in_matcher0Tokens that the inner xgrammar matcher accepted.
tokens_after_eos−1−1 until EOS; then the count of tokens after EOS.

Three phases. constrained() is true when the bound fired or the trigger is complete (deepinfer/structure_output/matcher.py:115-125). The sampler fills a mask only for a constrained matcher (deepinfer/model_executor/layers/sampler.py:361-364).

  1. Free phase (trigger pending, no bound): every token is accepted. KMP updates the trigger progress. The bound token, if it appears, starts the forced phase (deepinfer/structure_output/matcher.py:141-153).
  2. Forced phase (bound fired, trigger pending): only the next trigger token is accepted (deepinfer/structure_output/matcher.py:136-140). The mask has exactly one bit set (deepinfer/structure_output/matcher.py:183-187).
  3. Grammar phase (trigger complete, or no trigger): xgrammar accepts or rejects the token. EOS starts the count tokens_after_eos (deepinfer/structure_output/matcher.py:157-168). After EOS, the mask allows every token: mask_after_eos is a full mask (deepinfer/structure_output/matcher.py:105, deepinfer/structure_output/matcher.py:189-191).

Worked example: why KMP. Trigger [5, 5, 7], input tokens 5 5 5 7.

  1. The failure table is [0, 1, 0]: after a mismatch at position 2, the last 5 can still be the first 5 of the trigger.
  2. Tokens 5, 5: progress 1, then 2.
  3. Token 5: it does not match trigger[2] = 7. Progress falls back to failure[1] = 1. Now 5 matches trigger[1], so progress is 2 again.
  4. Token 7: progress 3 = complete. The grammar starts with the next token.

A simple "reset to 0 on a mismatch" would end step 3 at progress 1 and miss the trigger.

Deep dive

Rollback: why the depth is nextn + 2

The matcher keeps a limited history:

xgrammar gets the same limit: InnerMatcher(ctx, max_rollback_tokens=MAX_ROLLBACK_TOKENS) (deepinfer/structure_output/matcher.py:83). With the default DEEPINFER_USE_NEXTN_DECODE = 5, the limit is 7.

Why rollback at all? In one step the sampler accepts up to nextn drafts to fill the masks, and then undoes exactly those drafts (deepinfer/model_executor/layers/sampler.py:366-376). The committed tokens of the previous step are never rolled back. So the largest rollback is nextn = 5. The code keeps 2 more; it does not say why.

rollback(steps) undoes the phases in reverse order (deepinfer/structure_output/matcher.py:206-232):

  1. First the tokens after EOS, which only lower the counter.
  2. Then up to tokens_in_matcher tokens in xgrammar.
  3. Then trigger_progress from the history. A rollback deeper than the history raises RuntimeError.
  4. Then tokens_after_bound, which can fall back to −1.

The sampler catches every exception in this code and kills only the request (deepinfer/model_executor/layers/sampler.py:377-386).

Deep dive

Mask shapes and bytes, with numbers

The sampler keeps max_MTP_value + 1 pinned CPU masks. It makes them again only when the batch is larger than all earlier batches (deepinfer/model_executor/layers/sampler.py:323-327). So num_seqs below is the largest batch so far, not always the current batch:

bitmasks_cpu[k]   int32 [num_seqs, ceil(V / 32)]     k = 0 .. nextn   (pinned)
so_indices[k]     int32 [n_k]                         requests that use mask k
logits            float32 [total_q, V]               row ftp[r] + k belongs to request r, step k

Bit j of word w stands for token 32·w + j: the kernel tests bitmask[w] & (1 << (i % 32)) (deepinfer/model_executor/layers/tilelang_ops/cuda/structure_output.py:55). The forced-phase code writes one bit in the same way: word expected >> 5, bit expected & 31 (deepinfer/structure_output/matcher.py:186).

Worked example. The vocabulary size comes from the checkpoint; this example uses V = 129,280, the value in the kernel benchmark (deepinfer/model_executor/layers/tilelang_ops/structure_output.py:106).

  • One mask row: ceil(129,280 / 32) = 4,040 int32 = 16,160 bytes.
  • 64 rows (the largest batch so far), nextn = 5: 6 masks × 64 rows × 16,160 B = 6,205,440 B (about 5.9 MiB).
  • The copy sends all 6 full masks every step, also when only one request uses a grammar (deepinfer/model_executor/layers/sampler.py:398). A step with no active grammar sends nothing (deepinfer/model_executor/layers/sampler.py:318-319).
  • Kernel grid: ceil(129,280 / 8,192) = 16 blocks per listed request and step.

Streams. The copy stream first waits for an event that the main stream records at this point. Then it copies the masks and records so_mask_ready. The main stream waits for that event before the mask kernels (deepinfer/model_executor/layers/sampler.py:391-407, deepinfer/model_executor/layers/sampler.py:163-164). The code gives no comment about the first wait.

Deep dive

The thread pool, the compiler cache and the timeout

Threads. The engine thread calls submit and pump; pool threads only fill futures. A translated comment says: "submit and pump are both called on the main thread. The worker thread only fills the future. It does not touch the seq or the scheduling logic." (deepinfer/structure_output/so_matcher_builder.py:50). Even the compiler object is made on a pool thread, with num_threads=2 (deepinfer/structure_output/so_matcher_builder.py:49). The xgrammar compiler gets this value as max_threads (deepinfer/structure_output/compiler.py:34-39).

Pinning. get_idle_cpus returns the first DEEPINFER_SO_BUILDER_CPUS physical cores of the share of this GPU: range(local_rank × cores_per_gpu, … + 4). It raises RuntimeError if a GPU has fewer cores (deepinfer/utils.py:154-161). Each pool thread calls os.sched_setaffinity(0, …), which pins only the calling thread (deepinfer/structure_output/so_matcher_builder.py:37-41). Translated: "0 = the calling thread itself: this binds the worker thread that runs the initializer, not the whole process or the main thread."

Compiler cache. xgrammar can keep compiled grammars in a cache (deepinfer/structure_output/compiler.py:15-39):

  • DEEPINFER_XGRAMMAR_DISABLE_CACHE (default off) turns the cache off. The comment calls it a kill switch after production incidents with xgrammar 0.1.x.
  • DEEPINFER_XGRAMMAR_CACHE_LIMIT_BYTES (default 10 GiB) limits it. For a value of 0 or less, the code logs a warning. The warning says that the cache then has no size limit and can run out of memory with many different schemas (it names CVE-2025-32381).

Timeout. The clock starts when the future is made (deepinfer/structure_output/matcher.py:262-271). try_result() has three outcomes (deepinfer/structure_output/matcher.py:319-338):

  1. The task finished: return its matcher, or an aborted matcher if the task raised.
  2. The task still runs and the time is up: return an aborted matcher. The task is not cancelled here.
  3. The task still runs within the time: return None.

The messages can mislead: a compile error that arrives in time gets the text "xgrammar timeout when try_result, ..." (deepinfer/structure_output/matcher.py:328-329).

Counting. Pending requests count as unfinished, so LLM.generate keeps the loop alive while a grammar compiles (deepinfer/engine/llm_engine.py:658-663, deepinfer/engine/llm_engine.py:673-674). examples/benchmark.py calls pump() in a loop until no build is pending, before it allocates its sequences (examples/benchmark.py:311-313).

The QA document. It says that compilation runs "on a dedicated SO machine" and that a request gets the compiled result before it enters the engine (doc/inference_deployment_qa.md:284-288). The offline code in this repository compiles on the same machine and refuses a "serialized" grammar (deepinfer/structure_output/so_matcher_builder.py:60-61). The production setup is not in this release.

Deep dive

Interaction with ZOS, preemption and forks

Zero-overhead scheduling. With ZOS, the CPU schedules step N + 1 before the outputs of step N are processed. So, just before sampling, C++ refreshes the metadata of each sequence that was also in the previous step (remap ≥ 0). It copies the last output token, so_status and the matcher (csrc/engine/zos.cpp:300-302, csrc/engine/sequence.hpp:408-417). A middle prompt chunk has last_output_token = -1, and the sampler skips it (csrc/engine/sequence.hpp:387, deepinfer/model_executor/layers/sampler.py:339).

Preemption. A recompute would have to replay the matcher. DeepInfer does not do this: a preempted request with so_status != 0 stops with FINISHED_PREEMPTED, also when the engine would recompute other requests (csrc/engine/scheduler.hpp:766-780). The builder has a replay_tokens argument that would restore the state (deepinfer/structure_output/so_matcher_builder.py:87-91), but no caller in this release passes it.

Forks. fork_seq gives the new sequence a fresh copy of the matcher with copy_without_status(), and status 1 when the prompt is complete (csrc/engine/scheduler.hpp:1097-1100). The deepinfer package does not call fork_seq; examples/benchmark.py does.

Golden tokens. The masks apply before the sampler picks a token. Teacher forcing with golden_token_ids happens later: after the sampling kernels, the sampler replaces the sampled tokens with the golden tokens. So a golden token that the grammar forbids makes the matcher reject it at the next step, and that request fails.

Simplified

The last paragraph follows from the order of the calls in Sampler.forward (masks at deepinfer/model_executor/layers/sampler.py:187-190, golden tokens at deepinfer/model_executor/layers/sampler.py:469-490 and deepinfer/model_executor/layers/sampler.py:671) and from the raise at deepinfer/model_executor/layers/sampler.py:354-355. No test in the repository runs this case.

What can go wrong#

  • Wrong keys raise at once. "serialized" or the plural "bound_token_ids" raise ValueError inside build(), so add_request raises to the caller (deepinfer/structure_output/so_matcher_builder.py:60-63). A missing "schema" key raises KeyError the same way (deepinfer/structure_output/so_matcher_builder.py:64).
  • A bad trigger or bound does not raise. The builder returns an aborted matcher (deepinfer/structure_output/so_matcher_builder.py:71-76), and the request ends without a prefill.
  • Compile errors and slow grammars end the request. The finish reason is "xgrammar runtime errors or timeout" for both (csrc/engine/sequence.hpp:57-58). A large JSON schema can need more than 20 seconds; raise DEEPINFER_XGRAMMAR_TIMEOUT for it.
  • Preemption stops a grammar request. It does not recompute, even in the offline LLM, which recomputes other requests (csrc/engine/scheduler.hpp:770-780).
  • A matcher error in the sampler kills one request. A translated comment explains why: "This is the sampling main path on CP rank 0. A raise would take down all requests and time out the NCCL barrier." (deepinfer/model_executor/layers/sampler.py:377-386).

Why it matters. A grammar makes the output machine-readable, but it costs CPU time in every step: one matcher walk and up to 6 masks per request. DeepInfer keeps the slow part, the compile, off the step loop, and keeps the per-step part on the CPU while the device computes the logits.

Check yourself#

  1. 1
    Which three grammar types can so_args["schema_type"] name, and which xgrammar call does each one use?
    easy
    Show answer

    "json" uses compile_json_schema(schema, strict_mode=True), "regex" uses compile_regex, and "ebnf" uses compile_grammar (deepinfer/structure_output/compiler.py:56-61). Any other value raises inside the compiler and gives an aborted matcher.

  2. 2
    A request with so_args comes in. When does it enter the scheduler's waiting queue?
    easy
    Show answer

    Not in add_request. The builder compiles the grammar on a pool thread. pump(), which pre_sampler_sync calls once per step, sees the finished future and calls _enqueue, which calls scheduler.add_sequence (deepinfer/structure_output/so_matcher_builder.py:109-121, deepinfer/engine/llm_engine.py:620-628, deepinfer/engine/llm_engine.py:841-842).

  3. 3
    With 5 drafts, the grammar accepts drafts 1 and 2 and rejects draft 3. Which rows of the request get a mask, and what happens to draft 3 on the device?
    medium
    Show answer

    Rows 0, 1 and 2 get masks 0, 1 and 2. Rows 3 to 5 get none, because the loop stops at the first rejected draft (deepinfer/model_executor/layers/sampler.py:367-375). Row 2 checks draft 3 with mask 2, which has a 0 bit for draft 3. Its logit becomes minus infinity, so its probability is 0 and the verification rejects it. The sampler draws a new token from the allowed ones.

  4. 4
    Why does the scheduler decide on FINISHED_SO_FAILED from the stored status, and not from the status of this step?
    medium
    Show answer

    The sampler returns no status list for a step in which no request has an active grammar. A sequence whose stored status is already −1 would then generate freely. So process_outputs checks seq.structured_output.status == -1 (csrc/engine/scheduler.hpp:974-980).

  5. 5
    The matcher keeps a rollback history of nextn + 2 tokens. Take 64 sequences (also the largest batch so far) and nextn = 5. How many bytes of masks does one decode step copy, and what is the largest rollback?
    hard
    Show answer

    Six masks of [64, ceil(V/32)] int32. With V = 129,280: 6 × 64 × 4,040 × 4 B = 6,205,440 B (deepinfer/model_executor/layers/sampler.py:323-327, deepinfer/model_executor/layers/sampler.py:398). The largest rollback is 5, one per accepted draft (deepinfer/model_executor/layers/sampler.py:376); the limit is 7 (deepinfer/structure_output/matcher.py:20).

  • layers/sampler.py: the Sampler classsampler.py holds the Sampler module. It turns selected hidden states into float32 logits, samples prefill tokens, verifies draft tokens in decode steps and calls DFlash. sampler_utils.py holds the logits, sampling and prompt-logprob helpers.
  • deepinfer/sampling_params.py: SamplingParamsSamplingParams holds the per-request settings: temperature, top-p, top-k, seed, length, logprobs, EOS rules, grammar and golden tokens. This page lists every field with its default and checks, and follows each one to the sampler.
  • Request and sequence lifecycleEach request becomes a C++ Sequence. It waits until it is schedulable, runs one or more prefill steps and many decode steps, and ends with one of seven finish reasons. Preemption stops it or sends it back to the queue for a recompute.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • Environment variablesDeepInfer reads 59 DEEPINFER_* environment variables through one class, envs, in deepinfer/environ.py. This page lists each variable with its type, default, effect and the code that reads it, and tells when the value is read.
