Expert load balancing (EPLB)

AdvancedDeepInfer conceptsabout 12 min read + 8 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • MoE routing: the gate, top-k and the shared expert Intermediate
  • Expert parallelism: dispatch, grouped GEMM, combine Advanced

In one sentence

EPLB counts the tokens of each expert and gives busy experts extra copies. Then it moves expert weights, so that every EP rank gets about the same work.

The idea#

With expert parallelism, each EP rank holds some of the experts. The gate sends more tokens to some experts than to others. A rank with busy experts gets more rows and finishes last. All ranks wait for it at combine, so the busiest rank sets the speed.

EPLB (expert-parallel load balancer) fixes this in three ways:

  1. Extra copies. Each rank has a few more expert slots than it needs. These redundant experts hold second copies of busy experts. Two copies share the tokens of one expert.
  2. New placement. EPLB counts the tokens of each slot in each step. Every N steps, it computes a new layout from the counts of the last steps.
  3. Weight moves. Then it copies the expert weights between the ranks to match the new layout.

Every expert keeps one logical expert id, and the gate always chooses logical experts. A table then gives a physical slot. EPLB changes only this table and the weights in the slots.

The docs describe the same mechanism: "each GPU holds a few redundant experts that host replicas of hot experts. The load of each expert over the last N steps is collected, and every M steps experts are re-assigned to GPUs" (doc/inference_deployment_qa.md:97).

An everyday comparison. Think of a library with four branches. Popular books have two copies, in two branches. Every month, the librarian counts the loans of each book, decides which books get the spare shelf places, and moves books between the branches. The comparison stops here: EPLB counts tokens in every step, not loans per month. Also, it moves the copies of all MoE layers in one pause, while the engine waits.

Try it: router and EPLB#

Things to try:

  1. Click Run 4 steps two or three times. One rank is much busier than the mean. Look at moe_lb.
  2. Click Rebalance. The hot experts get the extra slots (green), and the copies move. Run more steps: moe_lb goes down.
  3. Set the extra experts to 1, 5 or 0. The value is only a lower limit: the code rounds it up so that 16 plus the extra slots divide by 4.
  4. Click Change hot experts. The old layout gets worse until the next rebalance.

Simplified

The visual is a model of one MoE layer with 16 experts, 4 ranks, k = 2 and 64 tokens per step. The rounding rule, the first layout and the Rebalance algorithm are the real ones from eplb/__init__.py and eplb/policy.py. Three things are different:

  • Seeded random choices replace the gate.
  • The copies of an expert get its tokens in turn. In DeepInfer, the gate kernel picks the copy, and the repository does not show the rule.
  • The window holds the steps since the last Rebalance (at most 16). DeepInfer keeps the last W steps in a ring and does not clear it.
  • The visual computes in float64. The code computes in float32, so two choices with exactly equal scores can resolve differently.

In the code#

Step 1: how many extra slots#

The variable DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS gives a lower limit. The default is 0 (deepinfer/environ.py:114). The loader rounds it up, separately for the main layers and for the DFlash draft layers:

An example: a toy expert count of 100, EP 8, and the lower limit 32 of the example scripts. Then the padding is -(100 + 32) % 8 = 4 (in Python, % gives a result from 0 to 7). The layer gets 36 extra slots and 136 slots in total, 17 per rank. The docs report the same rule for decode: "at EP64, for example, this works out to 7 experts per GPU after rounding" (doc/inference_deployment_qa.md:103).

Default 0, examples 32

In your own code the default is 0 extra slots. The example scripts set 32 with setdefault when set_override_experts is true (examples/_config.py:77-79). offline_inference.py sets it only with EPLB on (examples/offline_inference.py:35-40). benchmark.py sets it always, also when its EPLB flag is off (examples/benchmark.py:161-162). examples/README.md says "defaulting to 32" (examples/README.md:63); that is the value of the scripts, not of the code. Even with 0, the loader adds padding slots when the expert count does not divide by the EP size.

The extra slots first copy experts 0, 1, 2 and so on, whatever their load. The loader uses the same list to read the checkpoint weights for each slot (deepinfer/hugging_face/weights.py:254-267). The balancer keeps three tables per MoE layer:

Step 3: counting in every step#

Each MoE layer passes its row of expert_count to the kernels. DeepEP dispatch gets it as cumulative_local_expert_recv_stats (deepinfer/model_executor/models/v4_modules/mlp.py:474), and so does the mega-MoE call (deepinfer/model_executor/models/v4_modules/mlp.py:555). The argument name says that the kernels add the number of rows that each local slot receives. The kernels are not in the repository. After the step, sample calls the balancer:

With an EP size of 1, step returns at once: there is nothing to balance.

Step 4: when to rearrange#

  1. Line 147: with DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL = 0 (the default, deepinfer/environ.py:116), EPLB never rearranges. Counting and statistics still run.
  2. Lines 149-150: in a NORMAL engine without the after-prefill setting, prefill steps do not count.
  3. Lines 152-154: the counts of the step go into the window ring of W entries.
  4. Lines 156-159: with DEEPINFER_REARRANGE_AFTER_PREFILL_IN_NORMAL_ENGINE on, a prefill step sets the counter so that the next decode step rearranges.
  5. Lines 161-165: else, rearrange after N counted steps.

The first rearrangement comes early. The counter starts at N − max(1, N // 4). The comment says: "bring the first rearrange forward to 1/4 of the period, to correct the cold-start imbalance early" (translated, deepinfer/model_executor/eplb/__init__.py:121-123). With N = 30, the rearrangements happen at counted steps 7, 37, 67 and so on.

Step 5: the policy#

_rearrange_experts first adds up the window counts per logical expert over all EP ranks (deepinfer/model_executor/eplb/__init__.py:234-254). Then it calls rebalance_experts_global, which works in two steps (deepinfer/model_executor/eplb/policy.py:73-140):

  1. Replication. Start with one copy per expert. Give the extra slots one at a time. Each slot goes to the expert whose extra copy most lowers the sum, over the window steps, of the largest load per copy.
  2. Placement. Sort all copies by load. Put each copy on the rank that keeps the sum over steps of the busiest rank lowest. A full rank is skipped.

The second diagram shows both steps with numbers. The deep dives read the code line by line.

Step 6: moving the weights#

Two shuffle functions move the weights in place. Both write new weights only into slots whose expert changes, and both work on one layer at a time:

  • Inside one NVLink domain on GPU: each rank copies its weights into a symmetric memory mirror. The other ranks read the mirror directly (deepinfer/model_executor/eplb/shuffle.py:178-218).
  • Else (Ascend, or a larger EP group): batched point-to-point sends and receives of torch.distributed (deepinfer/model_executor/eplb/shuffle.py:94-147). The process group is NCCL on GPU and HCCL on Ascend (deepinfer/platform.py:58, deepinfer/platform.py:89). The comment in _initialize_shuffle says "NPU doesn't support symm_mem yet" (deepinfer/model_executor/eplb/__init__.py:199-200).

Step 7: measuring the balance#

Every DEEPINFER_MOE_LB_STAT_INTERVAL steps (default 128, deepinfer/environ.py:118), the EP ranks all-gather their rows per step and layer. The balancer keeps the sum of the mean and the sum of the maximum over ranks (deepinfer/model_executor/eplb/__init__.py:180-193). The statistics logger divides the sum of the maxima by the sum of the means (deepinfer/engine/stats_logger.py:238-241). The docs call this moe_lb "(slowest rank / mean)" (doc/inference_deployment_qa.md:99). The docs report measured values: 1.074 (EP4DP4) and 1.045 (EP2DP2) for prefill, and 1.090 for decode (doc/inference_deployment_qa.md:99, doc/inference_deployment_qa.md:103).

The EPLB tensors: shapes, types and writers

The maps are made on the CPU in the constructor, but _init_eplb builds the balancer inside torch.device("cuda") (deepinfer/model_executor/models/deepseek.py:345). The rearrangement writes the new maps with copy_, so the tensor objects that the layers hold stay valid (deepinfer/model_executor/eplb/__init__.py:276-278).

One balancer per layout. _init_eplb groups the MoE layers by their layout: the expert counts, the EP group, and the shapes and types of the weights. Each group gets one ExpertLoadBalancer (deepinfer/model_executor/models/deepseek.py:331-364). The main layers and the DFlash draft layers usually form two groups.

Deep dive

rebalance_experts_global, step by step

  1. Input. tokens_per_expert: [W, Lm, E], the window counts per logical expert, summed over all EP ranks.
  2. Start (line 97). One copy per expert. Slots 0 … E−1 hold experts 0 … E−1. The old layout is not used.
  3. Tie-break (line 109). Add e × 1e-4 to the count of expert e, so that no two scores are equal.
  4. One round (lines 111-117), per step s. Find the expert m with the largest load per copy. A new copy can only lower the maximum if it goes to m. So for every expert j ≠ m, the step maximum stays the same. For m, the new maximum is computed with one more copy of m.
  5. Choose (line 117). Sum these maxima over the window steps and take the expert with the lowest sum.
  6. Record (lines 119-123). Slot E + i holds the chosen expert. Its entry in logical_to_physical_map and its count go up.
  7. Placement (lines 125-138). If a rank has more than one slot, _batch_greedy_indices permutes the slots. Lines 129-138 renumber logical_to_physical_map with the inverse permutation.

Worked example (the policy diagram). Window: step 1 = [48, 6, 10, 4, 24, 4], step 2 = [40, 8, 12, 6, 28, 6].

  • Round 0: step 1 has its maximum at e0 (48). One more copy of e0 gives 24, so the step maximum becomes 24 (e4). Step 2 then gives 28 (e4). The sum is 52. Every other choice keeps 48 + 40 = 88. So e0 gets slot 6.
  • Round 1: now e0 has 24 and 20 per copy. A copy of e4 gives 24 + 20 = 44. Every other choice gives 24 + 28 = 52. So e4 gets slot 7.
Deep dive

_batch_greedy_indices: the placement, step by step

  1. Line 31: weights = total window load of each expert divided by its copy count. All copies of an expert have the same load.
  2. Line 34: sort the slots by that load, highest first. stable=True keeps the slot order for equal loads.
  3. Lines 46-48: loads [Lm, ranks, W], peaks [Lm, W] (the busiest rank per step so far), and occupancy per rank.
  4. Lines 58-60: for each rank, the score is the sum over steps of max(load of the rank + this copy, peak).
  5. Lines 62-66: full ranks get inf. The lowest score wins; a tie goes to the lowest rank id. The copy takes the next free slot of that rank.
  6. Lines 67-69: update the rank load and the peaks.

All layers run at the same time in tensor form; the loop runs once per slot. The unit tests lock the tie rules and the objective (tests/models/test_eplb_policy.py:97-117).

Two copies on one rank. The code has no rule against two copies of one expert on the same rank. Such a layout can come out when it gives the lowest score.

Deep dive

The P2P weight shuffle in detail

The shuffle runs per layer. Each rank works out its part of the plan from the same two lists, so the senders and receivers agree without extra messages.

  1. Local copies (_plan_intra_copies, deepinfer/model_executor/eplb/shuffle.py:16-25). A slot whose expert does not change needs nothing. A slot that needs an expert which this rank already has gets a local copy.
  2. Who sends (_remote_routes, deepinfer/model_executor/eplb/shuffle.py:28-44). The senders of expert e are the ranks that held e in the old layout, one entry per rank. The receivers are the ranks that need e in the new layout and did not hold it.
  3. Pairing (_paired_sender, deepinfer/model_executor/eplb/shuffle.py:47-53). With S senders and Rc receivers, each sender serves Rc // S receivers in a block, and the rest go round-robin.
  4. Buckets (lines 113-138). The sends and receives go into DEEPINFER_REARRANGE_P2P_GROUPS buckets (default 1) by rank distance. Each bucket is one batch_isend_irecv, and the code waits for each bucket.
  5. Finish (lines 140-147). Copy from the receive buffers into the slots.

One expert can fill two slots on the receiver. It is received once and copied locally to the second slot (line 127 skips the second slot). The receive buffers hold one layer and are reused, which assumes that all layers have the same weight shapes (the comment at line 81).

Worked example (the cycle diagram). Old [0, 1, 2, 3 | 4, 5, 0, 1], new [0, 4, 2, 5 | 0, 4, 1, 3]. Rank 1 already has e4, e0 and e1, so it fills slots 4, 5 and 6 locally. Rank 1 sends e4 and e5 to rank 0. Rank 0 sends e3 to rank 1. That is 3 remote weight sets per layer: for FP4 weights, each set is two weight tensors and two scale tensors (deepinfer/model_executor/models/deepseek.py:324-329).

Deep dive

The intranode shuffle with symmetric memory

Per layer, _shuffle_layer_intranode does these steps (deepinfer/model_executor/eplb/shuffle.py:186-218):

  1. Barrier: all ranks finished reading the mirrors of the previous layer.
  2. Copy all local slots of the layer into the own mirror. Barrier: all mirrors are ready.
  3. Local copies, from the own mirror (so that a slot is not read after it is overwritten).
  4. For each missing expert, copy straight from the mirror of the paired sender.
  5. Fill the second slot of the same expert from the first one.

No NCCL send or receive is used. The cost is one extra buffer of one layer, made at the first rearrangement.

What can go wrong#

Set the window when you set the interval

With rearrangement on, the window must be from 1 to the interval. The default window 100 with an interval of 30 stops start-up with ValueError (deepinfer/model_executor/eplb/__init__.py:106-111). The example scripts always set the window to 3. Their comment gives another reason: "save gpu mem when eplb is off" (examples/_config.py:80).

  • EPLB is off by default. With the code defaults there are no extra slots (except padding) and no rearrangement. Counting and moe_lb still run when the EP size is above 1.
  • A pause in the step. A rearrangement runs inside allow_cuda_sync. It does an all-reduce, reads the layouts to the CPU with .tolist() (a device synchronization), and moves weights for every layer (deepinfer/model_executor/eplb/__init__.py:222-278, deepinfer/model_executor/eplb/shuffle.py:84-88). The step with a rearrangement is slower. The log line gives the time.
  • Memory. Every extra slot holds one full expert in every MoE layer. The first rearrangement makes the symmetric mirror of one layer (deepinfer/model_executor/eplb/__init__.py:206-209). The P2P path makes receive buffers of one layer at each rearrangement (deepinfer/model_executor/eplb/shuffle.py:82).
  • Old counts after a rearrangement. The window ring is not cleared after a rearrangement (deepinfer/model_executor/eplb/__init__.py:152-154). The window is never longer than the interval (deepinfer/model_executor/eplb/__init__.py:106), so normally all its steps come after the last rearrangement. With the after-prefill setting, two rearrangements can be closer than W steps. Then some old slot counts are read with the new layout (deepinfer/model_executor/eplb/__init__.py:238-253).
  • Batch invariance. With DEEPINFER_BATCH_INVARIANT and a rearrangement interval above 0, the EP buffer is made with allow_multiple_reduction=False (deepinfer/model_executor/parallel_utils/userbuffer.py:79).
  • Bad statistics interval. DEEPINFER_MOE_LB_STAT_INTERVAL of 0 or less raises ValueError (deepinfer/model_executor/eplb/__init__.py:125-127).

Why it matters. With many EP ranks, the busiest rank sets the step time of all ranks. The docs say that Wide-EP raises throughput "with good EPLB support" (doc/inference_deployment_qa.md:57).

Check yourself#

  1. 1
    What does EPLB change: the gate, or the place of the experts?
    easy
    Show answer

    The place of the experts. The gate still chooses logical experts. EPLB changes logical_to_physical_map, logical_count and the weights in the slots (deepinfer/model_executor/eplb/__init__.py:276-278).

  2. 2
    You set DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS=5, the model has 64 routed experts, and the EP size is 8. How many extra slots does each MoE layer get?
    easy
    Show answer

    8. The padding is -(64 + 5) % 8 = 3, and 5 + 3 = 8. So there are 72 slots, 9 per rank (deepinfer/model_executor/eplb/__init__.py:27-28). The loader logs a warning about the rounding.

  3. 3
    With DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL=1000, at which counted step is the first rearrangement?
    medium
    Show answer

    At step 250. The counter starts at 1000 − max(1, 1000 // 4) = 750 (deepinfer/model_executor/eplb/__init__.py:122-123), and it rearranges when it reaches 1000. After that, every 1000 counted steps.

  4. 4
    In step A of the policy, why does the code only change the score of the argmax expert of each step?
    hard
    Show answer

    One more copy of expert j lowers only the load per copy of j. The step maximum can only go down if j is the expert with the maximum. For every other j, the maximum stays the same. So values keeps the old maximum for all j and recomputes it only for the argmax (deepinfer/model_executor/eplb/policy.py:106-116).

  5. 5
    The EP group is 64 GPUs that do not fit in one NVLink domain. How do the weights move at a rearrangement?
    hard
    Show answer

    With NCCL point-to-point: expert_model_parallel_shuffle_inplace, in DEEPINFER_REARRANGE_P2P_GROUPS buckets of batch_isend_irecv. The symmetric-memory path needs is_within_nvl_domain(ep_group) and PLATFORM.is_gpu (deepinfer/model_executor/eplb/__init__.py:200, deepinfer/model_executor/eplb/shuffle.py:113-138).
