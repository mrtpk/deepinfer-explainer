Cross-layer KV sharing

AdvancedDeepInfer conceptsabout 8 min read + 5 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • KV compression (C1 and C2) Advanced
  • Sparse attention with an indexer Advanced
  • Model map: DeepSeek-V4.1-Flash in DeepInfer Intermediate

In one sentence

A source layer computes and stores a value once; the next layers in its segment read the same cache or list instead of their own.

The idea#

Neighbour layers often need very similar keys. Cross-layer KV sharing uses this. A source layer computes a value and stores it. The layers right after it, its consumers, read that value and do not compute or store their own copy. A source and its consumers form a segment.

DeepInfer can share three values, each with its own map:

  1. KV (layer_kv_map): the compressed KV in ca_cache, and its compression state.
  2. Index K (layer_index_k_map): the keys of the indexer in ica_cache.
  3. Top-k (layer_index_module_map): the whole indexer and its result, the list of selected keys.

The sliding-window cache is never shared. Each layer also keeps its own query and its own attention output. So a consumer reads the same keys as its source, but asks its own question.

An everyday comparison. Think of a team that shares one set of notes. One person (the source) takes the notes; the next people read them and do not write their own. Each person still writes a personal report (the query and the output). The comparison stops here: the team order is fixed, and a reader can only use the notes of the nearest note-taker before it.

In the code#

Step 1: config.json gives lists of source layers#

_source_map maps each layer from the first source to the end to the nearest source at or before it. Example: sources [1, 3, 5, 6] with 8 layers give {1: 1, 2: 1, 3: 3, 4: 3, 5: 5, 6: 6, 7: 6}. If config.json has no index_k_source_layer_ids, the index-K map uses the KV sources (line 74). Every compressed layer gets the same layer_info_shared_cfg (deepinfer/hugging_face/config.py:129). SWA-only layers get none (deepinfer/hugging_face/config.py:99-108).

Step 2: SharedLayerTopology makes and checks the maps#

The model builds one SharedLayerTopology at start-up, for the main layers and the draft layers (deepinfer/model_executor/models/v4_modules/cross_layer.py:339-351). It turns each map into a list over all layers. A layer that is not in the map is its own source:

Line 151 fills the gaps with self-references. Lines 152-154 forbid sharing in the draft (MTP) layers. Then _validate checks the rules (deepinfer/model_executor/models/v4_modules/cross_layer.py:89-118). Each map must be contiguous segments. Each consumer must carry the shared config, with the same compress ratio and index_topk as its source. KV consumers must have the same SWA setting. The maps must nest. The deep dive "The validation rules" gives the details.

Step 3: the cache engine allocates caches only for sources#

A consumer gets the same tensor view as its source (lines 431 and 449). It adds no bytes to the block row and no compression state. The engine reads the maps from layer_info_shared_cfg of each layer, and asserts that a source comes before its consumers (deepinfer/worker/cache_engine.py:141-162).

Step 4: only sources get the modules#

The builder passes the source flags to each layer's container. A KV consumer gets no PackedWkv; a top-k consumer gets no indexer (deepinfer/model_executor/models/v4_modules/builder.py:63-73, deepinfer/model_executor/models/v4_modules/mla_attn.py:252-273). An index-source layer that is not an index-K source has an indexer, but it borrows k_proj and k_norm from its index-K source (deepinfer/model_executor/models/v4_modules/builder.py:76-91). At run time, V4Attention reads its three flags from the topology:

Step 5: values travel through CrossLayerRuntime#

Some values exist only during one forward: the top-k list, the pre-RoPE KV, and the BF16 prefill buffers. DeepseekModel.forward makes one CrossLayerRuntime object and passes it to every layer (deepinfer/model_executor/models/deepseek.py:165-166). A source writes; a consumer reads:

Each value has a single slot. This works because the segments are contiguous and the layers run in order, so the value in the slot always comes from the nearest source (deepinfer/model_executor/models/v4_modules/cross_layer.py:284-287).

The nesting check, step by step. _validate_map_refines tests coarse[fine[l]] == coarse[l] for every layer (deepinfer/model_executor/models/v4_modules/cross_layer.py:182-189). In words: the fine source of layer l must be in the same coarse segment as l.

  1. Example (valid): top-k map [0, 1, 2, 3, 3, 5, 6, 6], index-K map [0, 1, 1, 3, 3, 5, 6, 6]. Layer 2: fine source 2, coarse source of 2 is 1, coarse source of layer 2 is 1. Equal.
  2. Example (invalid): KV sources [1, 4] and index-K sources [1, 3]. Layer 4: index-K source 3, KV source of 3 is 1, KV source of 4 is 4. Not equal, so the assert fails. Layer 4 would read index keys that were projected from another KV segment.

A consequence: every KV source is also an index-K source and an index source (the comment on deepinfer/model_executor/models/v4_modules/cross_layer.py:93-96).

Memory saved: worked example

Use the example config of the figure (made-up values). It has 8 main layers with ratios [0, 2, 2, 2, 2, 1, 2, 2]. KV and index-K sources are [1, 3, 5, 6]. Assume FP4 entries (288 B) and an example index_head_dim of 128, so one index key takes 128 / 2 + 128 / 32 = 68 B (deepinfer/worker/cache_engine.py:73-80).

Each part is padded to 32 bytes; these numbers are already multiples of 32 (deepinfer/worker/cache_engine.py:437-439, deepinfer/worker/cache_engine.py:459-461). The whole row is then padded to lcm(128, 288) = 1,152 B (deepinfer/worker/cache_engine.py:481-484). The compression state also shrinks: 3 instead of 6 C2 rings of 28,672 B per state slot (deepinfer/worker/cache_engine.py:190-198). A smaller block row gives more blocks in the same memory, so more tokens fit.

Deep dive

Candidate blocks (an extra sharing feature)

config.json can name one candidate_source_layer_id. The HF loader then marks every layer from that one to the end as using its candidates, with candidate_topk_blocks and candidate_block_size (deepinfer/hugging_face/config.py:76-84). The source layer selects a set of candidate key blocks; later index-source layers score and select top-k only inside that set (deepinfer/model_executor/models/v4_modules/cross_layer.py:49-53).

The checks are in deepinfer/model_executor/models/v4_modules/cross_layer.py:199-238:

  • The candidate source is an index source with index_topk above 0.
  • candidate_topk_blocks is a positive multiple of 8, and the block size is 1 … 16.
  • Consumers have the same compress ratio as the source.
  • The candidate capacity is at least the consumer's index_topk.

The indexer adds more limits, for example 8 or 16 tokens per candidate block (deepinfer/model_executor/models/v4_modules/index_attn.py:101-109). The page v4_modules/index_attn.py: the sparse-attention indexer covers the kernels.

What can go wrong#

  • A gap in a segment. A map such as {4: 4, 6: 4} with layer 5 missing fails: layer 5 becomes its own source and cuts the segment (deepinfer/model_executor/models/v4_modules/cross_layer.py:44-47, deepinfer/model_executor/models/v4_modules/cross_layer.py:176-179).
  • A consumer without the shared config. The topology asserts; without the check, the layer would read a cache that nobody writes (deepinfer/model_executor/models/v4_modules/cross_layer.py:106-112).
  • Sharing across the YOCO boundary. If the first consumer layer reuses an earlier layer's KV, the assert on deepinfer/model_executor/models/v4_modules/cross_layer.py:116 fails. See YOCO and SWA bounded replay.
  • A source after its consumer. The cache engine asserts that a mapped layer is not later than the layer (deepinfer/worker/cache_engine.py:160-161).
  • A model with no shared layer. build_shared_layer_topology returns None, and every layer is a source (deepinfer/model_executor/models/v4_modules/cross_layer.py:346-351). The V4.1 HF loader always attaches the shared config to compressed layers, so this happens only without compressed layers.

Why it matters. Sharing cuts the bytes per token of the paged cache and the work of the compressor and indexer. The price is accuracy that the model must learn in training, and strict rules about the order of layers. When a layer reads strange keys, check its three source ids first.

Check yourself#

  1. 1
    Which cache is never shared between layers?
    easy
    Show answer

    The sliding-window ring (swa_cache). The cache engine allocates it for every SWA layer with no map lookup (deepinfer/worker/cache_engine.py:406-422).

  2. 2
    kv_source_layer_ids = [2, 5] with 8 main layers. Which layers read the compressed KV of layer 2?
    medium
    Show answer

    Layers 3 and 4: _source_map gives {2: 2, 3: 2, 4: 2, 5: 5, 6: 5, 7: 5} (deepinfer/hugging_face/config.py:62-65). Layers 0 and 1 are not in the map, so they are their own sources (deepinfer/model_executor/models/v4_modules/cross_layer.py:151).

  3. 3
    A layer is an index source but not an index-K source. What does it compute itself, and what does it read?
    medium
    Show answer

    It computes its own index query and weights and selects its own top-k (deepinfer/model_executor/models/v4_modules/attn.py:292-299). It reads the index keys of its index-K source: the cache engine gives it that layer's ica_cache (deepinfer/worker/cache_engine.py:429-431), and in prefill it reuses the loaded keys (deepinfer/model_executor/models/v4_modules/index_attn.py:193-196).

  4. 4
    KV sources are [1, 4] and index-K sources are [1, 3]. Is the config valid? Explain with the check.
    hard
    Show answer

    No. _validate_map_refines("index-k", ..., "kv", ...) checks kv[ik[l]] == kv[l]. For layer 4: ik[4] = 3, kv[3] = 1, kv[4] = 4, so the assert fails (deepinfer/model_executor/models/v4_modules/cross_layer.py:185-189, deepinfer/model_executor/models/v4_modules/cross_layer.py:196-197). See the deep dive "The validation rules".

  5. 5
    In the worked example, how many bytes per block row does sharing save, and why does the C1 layer save nothing?
    hard
    Show answer

    182,272 − 113,920 = 68,352 B. Layer 5 is a C1 source. A consumer must have the same compress ratio as its source (deepinfer/model_executor/models/v4_modules/cross_layer.py:253-261). So the C2 layers around it cannot share with it. See the deep dive "Memory saved: worked example".

Related pages

  • YOCO and SWA bounded replayYOCO splits the main layers into producer and consumer layers. Consumer layers project their compressed KV from one shared hidden state. With the optional prefill truncation (README feature "Decoder SWA bounded replay"), a prefill computes the consumer layers only for the last KEEP_TOKENS prompt tokens (140 in the README), with the window cut at that range. Only their compressed KV still covers every token.
  • MLA attention: one latent vector per tokenIn DeepInfer's MLA, all query heads of a layer read one 512-value vector per token. This vector is the key and also the value, so the KV cache keeps one small entry per token.
  • Paged KV cache and block managerThe engine side of the paged KV cache. Two C++ BlockManager objects hand out KV blocks and state slots, the scheduler decides when, and C++ code turns block tables into index tensors for the kernels.
  • v4_modules/cross_layer.py: sharing topology and the cross-layer runtimecross_layer.py builds and checks the static sharing topology of the model (SharedLayerTopology), holds the per-forward values that a source layer passes to later layers (CrossLayerRuntime), and exports flat per-layer flags for the cost estimate (SharedLayerMetadata).
  • v4_modules/attn.py: the MLA attention runtimeattn.py turns the MLA weight container into runtime weights and runs one attention layer per call: projections, sliding-window and compressed KV stores, the indexer, the FlashMLA kernel and the output projection. It also holds the DFlash draft attention.
  • worker/cache_engine.py: CacheEngine and the cache layoutCacheEngine allocates two raw uint8 device buffers - gpu_blocks for the paged KV cache and gpu_states for the per-sequence state slots - and KVCacheManager cuts them into one KVCache view object per attention layer.
