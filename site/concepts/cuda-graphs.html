CUDA graphs

IntermediateDeepInfer conceptsabout 8 min read + 6 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • GPUs, kernels, and speed Beginner
  • Prefill and decode Beginner
  • Input metadata (varlen batching) Intermediate

In one sentence

DeepInfer records the decode forward pass once per batch size at start-up, then replays the recording in each decode step to save CPU launch time.

The idea#

One forward pass of the model starts many kernels on the device. For each one, the CPU does a kernel launch, which costs CPU time. In a prefill step, each kernel works on thousands of tokens, so the launch cost is small next to the device work. In a decode step, each kernel works on only a few rows (1 + 5 per sequence). Then the CPU can need more time to launch the kernels than the device needs to run them.

A CUDA graph removes most of this cost. The CPU records all launches of one forward pass once. Later, one call replays the whole recording. The recording keeps the kernel arguments, also the memory addresses of the input and output tensors. So a replay must use the same buffers and the same number of rows.

DeepInfer therefore does three things:

  1. Capture at start-up. It records one graph for each size in a list, for example 1, 2, 4, 8, 16 and 24 rows (graph capture).
  2. Pad. A decode step with 12 rows uses the graph of size 16. It adds 4 padding rows.
  3. Replay. The step writes its input metadata into the fixed input buffers of that graph, and replays it.

Prefill steps do not use graphs. They run in eager mode.

An everyday comparison. Think of a coffee machine with programmed buttons. The first time, you program the button "medium": the amount of water, the grind, the time. After that, one press makes a medium coffee. You cannot program a button for every possible amount, so the machine has a few sizes, and you take the next larger cup. The comparison stops at one point: DeepInfer fills the extra space in the cup with padding rows, and it throws their results away.

The picture#

Read the panels from top to bottom. Panel 1 runs once, inside warm_up_model. Panel 2 runs in every decode step. All graphs share one set of input buffers: each graph uses the first rows of the size-24 buffers.

In the code#

Step 1: decide if graphs are on#

  1. Line 73: graphs are on unless DEEPINFER_ENFORCE_EAGER is set or the engine is a PROMPT engine. A PROMPT engine does only prefill, so it has no decode step to speed up.
  2. Line 77: the largest graph has max_num_seqs × (1 + nextn) rows: every sequence sends its last token plus nextn draft tokens.
  3. Line 78: with ZOS on, the input buffers are on the device (input_on_device).
  4. Lines 80-91: the DFlash draft model gets its own graph runner, with its own sizes.

Step 2: the list of sizes#

Below the interval, the sizes are powers of two. From the interval on, they grow in steps of the interval. The last size is the maximum. The interval is DEEPINFER_CUDAGRAPH_BATCH_SIZE_INTERVAL, default 8 (deepinfer/environ.py:155).

  • examples/offline_inference.py sets max_num_seqs=4 (examples/offline_inference.py:54): 24 rows, sizes [1, 2, 4, 8, 16, 24].
  • The default max_num_seqs is 256 (deepinfer/engine/arg_utils.py:36): 1536 rows, 195 sizes from [1, 2, 4, 8, 16, …] to […, 1520, 1528, 1536].

Step 3: capture at start-up#

The engine calls warm_up_model on all ranks after it makes the KV cache (deepinfer/engine/llm_engine.py:457). That function captures the main graphs, then the DFlash graphs (deepinfer/worker/base.py:274-285). The capture itself:

  1. Lines 93-96: one input object for the maximum size, built from placeholder sequences of one row each, and one output buffer.
  2. Line 102: the loop starts with the largest size.
  3. Lines 108-110: each size gets views of the first bs rows. The views share memory with the full buffers.
  4. Lines 113-115: a warm-up run outside the recording.
  5. Lines 117-119: the fields that the forward pass computes from the inputs are set to None. So the recording contains the kernels that compute them (deep dive).
  6. Lines 125-127: the recording. The output copy into the shared output buffer is also recorded.
  7. Lines 139-141: the first graph sets the graph memory pool; all smaller graphs reuse it.

Step 4: select, pad and fill in each decode step#

bisect_left finds the smallest size that is not less than total_q. The model runner then adds padding sequences and lets the input builder write straight into the graph's buffers:

Line 182 is the rule for graph use: a decode step, graphs on, and graphs already captured. The page Input metadata (varlen batching) shows the 16 rows of this example.

Step 5: replay#

The replay runs inside forbid_cuda_sync(), a sync guard. The call returns at once; the device works in the background. The output object has graph_size rows. The sampler reads only the real rows (engine/prepare_sample.cpp: the sampler inputs).

Deep dive#

Deep dive

What the recording contains, step by step

_run_model is the function that runs both in the warm-up and in the recording:

  1. Input copy (ZOS off only). With copy_inputs = not input_on_device, line 63 on CP rank 0 copies every tensor of the pinned CPU object into the device object. Because the copy is inside the recording, each replay repeats it. So C++ can write new values into the pinned buffers before each replay.
  2. CP broadcast. With context parallelism, line 65 broadcasts the device tensors from rank 0 to the other ranks. This collective is also recorded.
  3. The forward pass. Line 66. Each attention layer calls compute_attn_info, which expands the short index descriptions (offset pairs) into full index tables (deepinfer/model_executor/input_metadata/input_metadata.py:371-389).
  4. The output copy. output.copy_(model_output) writes into the shared output buffer (deepinfer/worker/cuda_graph_runner.py:127).

Why the clean list. After the warm-up, the derived fields already exist. Then compute_attn_info would skip them, and the recording would not contain the kernels that compute them. So the runner sets them to None first: kv_ca_index_len, kv_swa_index, kv_ca_index, mlp_relu_schedule_metadata and flash_mla_sched_meta_dict (deepinfer/model_executor/input_metadata/input_metadata.py:326-334). The docstring says: "Fields to clear (set to None) when reusing a cudagraph; they are recomputed in forward" (deepinfer/model_executor/input_metadata/input_metadata.py:73).

With ZOS on. The input builder makes device tensors (device="cuda", deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:113-117). Then .cuda() on line 95 returns the same tensors, so the "source" and "device" objects share memory. The docstring of CudaGraphData says this: "Source tensors are on CPU, or share device tensor storage under ZOS" (deepinfer/worker/cuda_graph_runner.py:28-32). No copy is recorded; a device kernel fills the buffers before the replay.

Deep dive

Memory: one pool, one set of buffers

  • Input buffers. One object for the maximum size. A smaller graph uses x[:bs] views (deepinfer/worker/cuda_graph_runner.py:104-109). A comment in profile_decode_perf says, translated: "each batch size shares slice views of the largest buffer; fill once for all graphs" (deepinfer/worker/model_runner.py:581).
  • Output buffer. model.allocate_output(max_batch_size), with narrow(batch_size) views (deepinfer/worker/cuda_graph_runner.py:96, deepinfer/worker/cuda_graph_runner.py:110).
  • Temporary tensors. All graphs use one memory pool. The largest graph is captured first, so its pool is large enough for all others (deepinfer/worker/cuda_graph_runner.py:125, deepinfer/worker/cuda_graph_runner.py:139-140).
  • One side stream. Warm-up and recording run on graph_stream. The default stream waits for it after each capture (deepinfer/worker/cuda_graph_runner.py:100, deepinfer/worker/cuda_graph_runner.py:137).

The DFlash graphs reuse the same pool and stream (deepinfer/worker/model_runner.py:543-549). The model runner logs the extra memory of the DFlash graphs, measured with torch.cuda.mem_get_info (deepinfer/worker/model_runner.py:552-559).

Deep dive

The DFlash graph runner

The draft model of speculative decoding has its own runner, DFlashCudaGraphRunner. It differs from the main runner in four points:

  1. Sizes count sequences, not rows. The maximum is max_num_seqs, with the interval DEEPINFER_DFLASH_CUDAGRAPH_BATCH_SIZE_INTERVAL (default 8) (deepinfer/worker/dflash_cuda_graph_runner.py:32-37, deepinfer/environ.py:157). With max_num_seqs=4: [1, 2, 4].
  2. It needs the main graphs. The capture uses the input metadata of the largest main graph, and it asserts that the main graphs exist (deepinfer/worker/model_runner.py:538-549).
  3. Inputs are copied in. replay copies the per-request decode input into the graph's buffers with a kernel, then replays, then cuts the padding from the output (deepinfer/worker/dflash_cuda_graph_runner.py:84-91).
  4. Only the driver keeps an output. do_sample is is_driver_worker. Only with do_sample does the runner make an output buffer, record the copy into it, and return the draft output (deepinfer/worker/model_runner.py:88-91, deepinfer/worker/dflash_cuda_graph_runner.py:54, deepinfer/worker/dflash_cuda_graph_runner.py:67-71, deepinfer/worker/dflash_cuda_graph_runner.py:90-91).

DFlash graphs are on when the main graphs are on, DEEPINFER_DFLASH_ENFORCE_EAGER is off, nextn > 0, and the model config has dflash_cfg (deepinfer/worker/model_runner.py:80-85). The draft model replays the graph when it has one, else it runs eager (deepinfer/model_executor/models/mtp/dflash.py:385-387).

Deep dive

Timing inside a graph: the graph timer

A normal CUDA event pair cannot measure one layer inside a replay, because the whole graph is one launch. The graph timer records events inside the graph instead.

  1. During capture, cuda_graph_timer.record(name) records a start and an end event with the "external" flag. The recording then contains two event-record nodes (deepinfer/timer.py:100-126, csrc/graph_timer/graph_timer_cuda.cpp:19-22).
  2. After capture, register_graph finds these nodes in the graph and makes a second set of events (deepinfer/timer.py:128-167).
  3. Before each replay, flip_event_buffer points the nodes at the other set of events (ping-pong). So the CPU can read the times of the previous replay while the next one runs (deepinfer/timer.py:169-187, deepinfer/worker/cuda_graph_runner.py:150-154).
  4. The worker reads the finished times after the sample event of a step (deepinfer/worker/worker.py:262-266).

The model uses it for the decode core attention: it times one layer and multiplies by the number of layers with the same shape (deepinfer/model_executor/models/v4_modules/attn.py:655-658). The timer works only on NVIDIA (deepinfer/timer.py:94-98). On Ascend, each event and node function of the C++ timer raises "NPU graph timer primitives are not implemented yet". Only the GraphHandle constructor does not raise (csrc/graph_timer/graph_timer_asc.cpp:7-43). The capture asks for keep_graph=True on NVIDIA only, because the NPU graph does not support it (deepinfer/worker/cuda_graph_runner.py:121-124).

Deep dive

Graphs and DSpark: the decode performance curve

With DEEPINFER_ENABLE_MTP_VARLEN=1 (DSpark), the scheduler needs to know how long a decode step takes for each graph size. So after the capture, profile_decode_perf replays every graph and measures it (deepinfer/worker/base.py:280-281):

  1. It fills valid_token_mask and gate_force_random with True once, in the shared buffers (deepinfer/worker/model_runner.py:582-584).
  2. For each size: 1 warm-up replay, then 5 timed replays with CUDA events (deepinfer/worker/model_runner.py:586-608).
  3. It drops the fastest and the slowest time and takes the mean of the other 3. Then it takes the mean over the expert-parallel group (deepinfer/worker/model_runner.py:616-623).
  4. It stores the curve in a cache file, and later runs load it from there (deepinfer/worker/model_runner.py:576-579, deepinfer/worker/model_runner.py:630).

The engine gives the curve to the C++ scheduler (deepinfer/engine/llm_engine.py:268). See DSpark: DFlash drafts and confidence-scheduled verification.

What can go wrong#

  • Too many rows. If a decode step has more rows than the largest graph, select raises ValueError("No captured graph for total_q=...") (deepinfer/worker/cuda_graph_runner.py:144-146). There is no eager fallback. A decode sequence sends at most 1 + nextn rows (csrc/engine/prepare_sample.cpp:212), and the decode scheduler takes at most max_num_seqs sequences (csrc/engine/scheduler.hpp:595). So this error points at a changed setting or a bug.
  • A CPU wait inside the forward pass. A sync in recorded code breaks the capture. At run time, the sync guard raises an error on any sync inside the forward and sample launch (deepinfer/utils.py:119-132). DEEPINFER_DISABLE_SYNC_GUARD=1 turns the guard off for debugging (deepinfer/environ.py:198).
  • New tensors in the forward pass. A graph replays fixed addresses. Code that makes a new input tensor each step would not reach the graph. So all decode inputs go through the fixed buffers (out_dict).
  • Hang at shutdown. NCCL calls inside graphs hold extra resources. The worker destroys the graphs before it destroys the process groups; the code says this avoids a hang (deepinfer/worker/base.py:142-146, deepinfer/worker/model_runner.py:633-644).
  • Start-up time and memory. With the defaults (max_num_seqs=256, nextn 5, interval 8), the main runner captures 195 graphs. A model with DFlash adds 35 DFlash graphs (sizes up to 256 sequences, deepinfer/worker/dflash_cuda_graph_runner.py:36). The log line "All graph capturing finished in ...s" shows the time (deepinfer/worker/model_runner.py:528-529).

Why it matters. Graphs make decode steps faster, but they fix the shapes and the memory addresses. When you change the model or the input metadata, keep the decode inputs in the captured buffers, and do not add a CPU wait. Else the replay uses old values, or the step stops with an error.

Check yourself#

  1. 1
    Which steps use CUDA graphs in DeepInfer: prefill, decode, or both?
    easy
    Show answer

    Only decode steps. run_cuda_graph needs not is_prompt (deepinfer/worker/model_runner.py:182). Prefill steps call self.model(...) directly (deepinfer/worker/model_runner.py:328-329).

  2. 2
    With max_num_seqs=4 and the default settings, which graph sizes does DeepInfer capture?
    easy
    Show answer

    [1, 2, 4, 8, 16, 24]. The maximum is 4 × (1 + 5) = 24 (deepinfer/worker/model_runner.py:77); the interval is 8, so powers of two below 8, then 8 and 16, then 24 (deepinfer/worker/cuda_graph_runner.py:41-51).

  3. 3
    A decode step has 3 sequences with 6 rows each. Which graph does it use, and how many padding rows does it add?
    medium
    Show answer

    total_q = 18. bisect_left over [1, 2, 4, 8, 16, 24] gives 24, so it adds 6 padding sequences of one row each (deepinfer/worker/cuda_graph_runner.py:143-148, deepinfer/worker/model_runner.py:186-188).

  4. 4
    Why does the capture set fields such as kv_swa_index to None between the warm-up and the recording?
    hard
    Show answer

    The warm-up run fills them. compute_attn_info computes a field only when it is None (deepinfer/model_executor/input_metadata/input_metadata.py:371-376). Without the reset, the recording would not contain the kernels that compute them, and every replay would reuse the values of the warm-up. The list is get_clean_list() (deepinfer/model_executor/input_metadata/input_metadata.py:326-334). This is in the deep dive "What the recording contains".

  5. 5
    With ZOS off, C++ writes the decode inputs into pinned CPU buffers. How do the new values reach the device in a replay?
    hard
    Show answer

    The copy is part of the recording. _run_model calls input_metadata_device.recursive_copy_(input_metadata_source) when copy_inputs is true, which is not input_on_device, and this runs inside torch.cuda.graph(...) (deepinfer/worker/cuda_graph_runner.py:62-63, deepinfer/worker/cuda_graph_runner.py:125-126). So each replay first copies the current CPU values.
