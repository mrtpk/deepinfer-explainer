Tour: One engine step

AdvancedGuided toursabout 13 min read + 1 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Tour: Life of a request Beginner
  • Offline API and the step loop Intermediate
  • Zero-overhead scheduling (ZOS) Advanced

In one sentence

We follow one decode step of three requests from the scheduler to the outputs, and we mark which step's data each part uses.

The idea#

The tour Tour: Life of a request followed one request through all its steps. This tour stays inside one engine step. It reads every phase of LLMEngine.step() and of Worker.execute_model_step in code order.

The main point of this tour is time. With zero-overhead scheduling (ZOS, the default), one call of step() works on two steps. It schedules, runs and samples step N. It also post-processes step N−1, which the worker kept from the call before. At each stop, a tag tells you which step the data belongs to.

The example batch has three decode requests, A, B and C. The previous step N−1 ran them in the order B, A, C. The scheduler now sorts them by length and plans step N as A, B, C. The numbers are illustrative; the formulas follow the code:

A1002 of 5103
B965 of 5102
C350 of 536

Other settings: nextn = 5, DSpark off (so each request sends 6 query tokens), CUDA graphs on, max_num_seqs = 4, one data-parallel rank.

The picture#

Read the CPU column from top to bottom. The CPU waits for the device only in phase 6. At that moment the device queue already holds forward N, so the device does not stop. Stops 2 to 10 of this tour follow the rows of the figure.

1The loop calls step()#

We are in LLM._run_engine in deepinfer/entrypoints/llm.py. The loop asks if work is left, calls step(), and clones every returned output:

has_unfinished_requests() combines the answers of all data-parallel ranks. With ZOS it uses the CPU (Gloo) group, so the call does not wait for the device (deepinfer/engine/llm_engine.py:665-679). Then step() records its start time (deepinfer/engine/llm_engine.py:872-879).

State now. The worker holds the WorkerStepState of step N−1 in prev_step_state. On the device, sample N−1 may still run. The CPU does not know the tokens of N−1 yet.

2The scheduler plans step N#

We are in LLMEngine.step(). The C++ scheduler selects the batch and fills one SequenceMetadata per request:

The decode branch sorts the running requests by length, longest first (csrc/engine/scheduler.hpp:648-649). So the order can change from step to step. Each request gets seqlen_q = 6. The CPU value of seqlen_k counts the 6 in-flight tokens of step N−1 and the 6 positions of step N. After line 726, each request has 12 in-flight tokens.

# data of step N (CPU view, before the post-process of N-1)
seq_metadata_list = [A, B, C]           # 3 SequenceMetadata objects from the pool
seqlen_q          = [6, 6, 6]
seqlen_k          = [112, 108, 47]      # 100+6+6, 96+6+6, 35+6+6
scheduler_outputs.num_batched_tokens == 18
Deep dive

Stop 2 in detail: the rest of step() before the worker

  • Clone and zero. If the scheduler asks to copy states or blocks (only for forked sequences), the engine runs a worker call first (deepinfer/engine/llm_engine.py:889-905).
  • Structured output check at the last prefill chunk; not used in a decode step (deepinfer/engine/llm_engine.py:910-928).
  • Multimodal fetch. The engine collects the results of the image workers after the schedule (deepinfer/engine/llm_engine.py:939-945).
  • The position limit. The scheduler checks seqlen_k − seqlen_q + max_seqlen_q + nextn ≤ runtime_max_model_len for a decode step (csrc/engine/scheduler.hpp:698-705). For A: 112 − 6 + 6 + 5 = 117.

3The engine calls the worker#

The engine sends the batch to the driver worker:

run_workers first sends the method name to the context-parallel follower ranks, if there are any, and then calls the method in this process (deepinfer/worker/base.py:290-302). Only the driver gets seq_metadata_list and scheduler_outputs. Now we are in Worker.execute_model_step (deepinfer/worker/worker.py:89-189).

4The device corrects the lengths of step N#

The first phase of the worker compares step N with the kept step N−1:

  1. Lines 199-200: no kept step (after a prefill), or a kept placeholder step: no correction.
  2. Lines 203-205: 18 query tokens use the CUDA graph of 24 tokens, so the arrays get 3 + 24 − 18 = 9 rows.
  3. Lines 209-213: C++ matches the requests by seq_id and returns the remap [1, 0, 2, -1, ...].
  4. Lines 221-227: the kernel compute_seqlens_k_zos uses the accepted counts of N−1, which are still on the device. It writes the real lengths.

All of this is queued work. The CPU only launches three non-blocking copies and one kernel. The page csrc/engine/zos.cpp: the C++ helpers of zero-overhead scheduling reads prepare_zos_inputs line by line.

# data of step N, on the device after the kernel
remap     = [1, 0, 2, -1, -1, -1, -1, -1, -1]   # int32 [9]
seqlens_q = [6, 6, 6, 1, 1, 1, 1, 1, 1]
seqlens_k = [109, 108, 42, 1, 1, 1, 1, 1, 1]     # 106+6-3, 102+6-0, 41+6-5

5Inputs are built and forward N starts#

Now the worker starts the main model:

With ZOS, the decode input function is prepare_decode_v4_zos (deepinfer/model_executor/model_metadata_utils.py:143). It does three things:

  1. C++ prepare_decode_zos_inputs packs the block tables, state ids and offsets into pinned arrays (csrc/engine/zos.cpp:198-277). Then prepare_decode_inputs_zos copies them to the device (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:70-77).
  2. The kernel prepare_v4_decode_metadata computes positions, cache slots and per-token block tables from the corrected lengths (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:336-367).
  3. The kernel gather_input_ids_zos builds the input tokens. For A, row 0 is the token that N−1 sampled, and rows 1-5 are the drafts that N−1 made (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:235-244).

Then execute_main_model replays the CUDA graph inside the sync guard (deepinfer/worker/model_runner.py:321-327). The call returns at once. The forward pass of N now waits in the device queue behind sample N−1.

# data of step N, on the device
input_ids  int32 [24] = [rA, eA1..eA5, rB, eB1..eB5, rC, eC1..eC5, pad x 6]
positions  int32 [24] = [103..108, 102..107, 36..41, ...]   # from seqlens_k - seqlens_q
hidden_states  [24, hidden_size]   # written later by the graph
Deep dive

Stop 5 in detail: why the graph does not copy inputs

The graph runner gets input_on_device = DEEPINFER_ZERO_OVERHEAD_SCHEDULING (deepinfer/worker/model_runner.py:76-79). The graph capture runs _run_model, which copies the inputs from the source buffers only when the inputs are not on the device (deepinfer/worker/cuda_graph_runner.py:54-66, deepinfer/worker/cuda_graph_runner.py:126). So with ZOS the captured graph has no input copy. With ZOS, the kernels of this stop write straight into the buffers that the graph reads. The graph sizes for max_num_seqs = 4 are 1, 2, 4, 8, 16 and 24. The largest size is 4 × (1 + 5) = 24, and the default interval is 8 (deepinfer/worker/model_runner.py:77, deepinfer/worker/cuda_graph_runner.py:41-51, deepinfer/environ.py:155). The page CUDA graphs explains capture and replay.

6The CPU post-processes step N−1#

While the device runs forward N, the CPU handles the kept step:

  1. Line 263: with the default settings, the only planned wait of this call. The CPU waits until sample N−1 and its copies to the CPU are done. Forward N is already queued, so the device keeps working.
  2. Line 268: ModelRunner.post_process runs the small functions that the sampler left in post_funcs, for example statistics of the drafts (deepinfer/worker/model_runner.py:370-384).
  3. Line 271: the engine callback LLMEngine.post_process calls _process_model_outputs. The C++ code appends the accepted tokens, checks stop conditions and builds the output objects (deepinfer/engine/llm_engine.py:984-1015).
# data of step N-1, after the post-process
A: cache 100 -> 103, outputs [eA1, eA2, rA]      # 2 drafts + 1 sampled
B: cache  96 -> 102, outputs [eB1..eB5, rB]      # 5 drafts + 1 sampled
C: cache  35 ->  36, outputs [rC]
request_outputs = np.array([...10 handles...], dtype=np.uint64)

The in-flight count of each request goes from 12 to 6: only step N is in flight now (csrc/engine/sequence.hpp:249-256). The page engine/llm_engine.py: the LLMEngine class reads _process_model_outputs line by line.

7The CPU metadata catches up#

The sampler of step N needs correct CPU metadata, for example seqlen_k for the sample positions (csrc/engine/prepare_sample.cpp:198-206). Now the CPU knows the result of N−1, so it updates each SequenceMetadata:

For A: seqlen_k = 6 + 103 = 109, the same value as the device value of stop 4. refresh_for_sampling copies the newest last token, draft slot and golden tokens of the sequence into the metadata (csrc/engine/sequence.hpp:408-418).

With DSpark (DEEPINFER_ENABLE_MTP_VARLEN=1), the device also changed seqlens_q in stop 4. Then line 149 waits for the copy of these lengths to the CPU. With the default settings, d2h_evt is None and there is no wait here (deepinfer/worker/worker.py:229-234).

8The sampler of step N starts#

execute_sample prepares the sampler inputs on the CPU and launches the sampler inside the sync guard (deepinfer/worker/model_runner.py:337-367). In a decode step, the sampler verifies the drafts, samples a new token per request, and runs DFlash for the next drafts (deepinfer/model_executor/layers/sampler.py:212-251). The tour Tour: One speculative decoding round reads this part in full.

Before it returns, the sampler queues non-blocking copies of its results to the CPU. It also keeps device copies for the next step, which stops 4 and 5 of the next call read:

# data of step N, on the device (CPU copies are queued, not done)
sampled_token_ids_gpu   int32 [3]
predict_token_ids_gpu   int32 [3, 5]
num_accepted_tokens_gpu int32 [3]     # last_valid_offset

9Old buffers go back, the end event is recorded#

pre_sampler_sync runs on the CPU while the device samples (deepinfer/engine/llm_engine.py:830-846). It releases the buffers that DeferredRelease collected (deepinfer/engine/llm_engine.py:100-107). These are the metadata list of step N−1, which stop 6 added (deepinfer/engine/llm_engine.py:1013), and the output handles of the previous call. It also pumps the grammar builder and frees the blocks of finished sequences. Every 1,000 calls (the default of DEEPINFER_GC_INTERVAL_STEP), the worker runs Python garbage collection (deepinfer/worker/base.py:153-157, deepinfer/environ.py:185).

Lines 167-168 record sample_end_evt in the stream. The event marks the end of all work queued so far: forward N, sample N and its copies. The next call waits on this event in its stop 6.

10The worker keeps step N and returns step N−1#

Step N is a decode step and ZOS is on, so the worker keeps it. The call returns the 10 handles of step N−1. The engine puts them into DeferredRelease (deepinfer/engine/llm_engine.py:974). Back in stop 1, LLM clones each handle before the next call.

Summary of the call. It scheduled, corrected, ran and sampled step N. It post-processed step N−1. It returned the tokens of N−1. The tokens of N come back in the next call.

11The last step: the flush#

When no request is left, LLM calls flush_inflight_reqs() instead of step() (deepinfer/entrypoints/llm.py:178):

The flush post-processes the kept step and clears it. In the offline loop, the kept step at that time is usually an empty step, so the flush returns no output. The page Offline API and the step loop shows why, call by call.

The same step with ZOS off#

Set DEEPINFER_ZERO_OVERHEAD_SCHEDULING=0 before the engine starts (see Zero-overhead scheduling (ZOS)). The same call then works on one step only:

StopZOS onZOS off
1all-reduce on the CPU groupall-reduce on the device group; .item() waits for the device (deepinfer/engine/llm_engine.py:667-678)
2seqlen_k counts the in-flight step N−1no step is in flight, so seqlen_k = 103 + 0 + 6 = 109 for A
4remap and length kernelno kept step: _correct_seqlens_qk returns None (deepinfer/worker/worker.py:198-200)
5inputs built on the deviceprepare_decode_v4 builds them on the CPU; the graph copies them (deepinfer/model_executor/model_metadata_utils.py:143)
6post-process N−1nothing kept, returns an empty array (deepinfer/worker/worker.py:259-260)
7metadata updateskipped (correction is None)
10keep Npost-process N at once: wait for sample N, then return the tokens of N (deepinfer/worker/worker.py:183-185)

So without ZOS, the device has no queued work while the CPU post-processes N and schedules N+1. The interactive timeline on the ZOS page shows the time that this costs.

What can go wrong#

Do not add a sync to the forward or sample launch

A .item(), a device-tensor print or a blocking copy in the launch part of execute_main_model or execute_sample raises an error from the sync guard (deepinfer/utils.py:119-132, deepinfer/worker/model_runner.py:321-325, deepinfer/worker/model_runner.py:356-360). Outside the guard, the same sync would stop the overlap without an error.

  • A kept handle becomes invalid. The handles that stop 10 returns go back to the pool at the next pre_sampler_sync (stop 9). Clone them first (deepinfer/entrypoints/llm.py:179-182).
  • A request finishes, but the next step still runs it. The scheduler of step N+1 runs before the post-process of step N. process_outputs then skips the finished request (csrc/engine/scheduler.hpp:905-915).
  • The metadata list and the scheduled sequences differ. The C++ checks in update_metadata_for_sampling_zos then fail with an error. They compare the lengths of the two lists and each seq_id (csrc/engine/zos.cpp:282-288, csrc/engine/zos.cpp:296).
  • A slow post-process delays the sampler. The sampler of N is launched only after the post-process of N−1 (stops 6 and 8). If the post-process takes longer than forward N, the device waits.

Why it matters. When you read a profile or a log of DeepInfer, each step mixes two steps. A slow "post-process" in step N is the cost of step N−1. The tokens that step N returns came from the device one call earlier.

Check yourself#

  1. 1
    In one call of step() with ZOS, which step's tokens does the CPU post-process?
    easy
    Show answer

    The tokens of step N−1, the step that the worker kept in prev_step_state (deepinfer/worker/worker.py:143-144, deepinfer/worker/worker.py:186-187).

  2. 2
    In which phase does the CPU wait for the device with the default settings, and for what?
    easy
    Show answer

    In the post-process of N−1, at sample_end_evt.synchronize(). It waits until sample N−1 and its copies to the CPU are done (deepinfer/worker/worker.py:262-263).

  3. 3
    Where do the input tokens of request A in step N come from, and why not from the CPU?
    medium
    Show answer

    From the device outputs of step N−1: the sampled token for row 0 and the 5 new drafts for rows 1-5, gathered by gather_input_ids_zos (deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py:235-244). When step N is prepared, the post-process of N−1 has not run, so the CPU does not know these tokens.

  4. 4
    Request B accepted all 5 drafts in step N−1. Its CPU seqlen_k for step N is 108. Which value does the kernel write, and which value does the CPU set in stop 7? Explain both.
    hard
    Show answer

    C++ sends 108 − 6 = 102 (csrc/engine/zos.cpp:188). The kernel writes 102 + 6 − (5 − 5) = 108 (deepinfer/model_executor/layers/tilelang_ops/compute_seqlens_k_zos.py:22-23). After the post-process, B's cache holds 96 + 6 = 102, so stop 7 sets 6 + 102 = 108 (csrc/engine/zos.cpp:299). When all drafts are accepted, the CPU guess was already right.

  5. 5
    Why does the event of stop 9 mark the end of the sampler copies, although the copies were launched in stop 8?
    hard
    Show answer

    All step work goes into the same stream in launch order. The sampler queues its non-blocking copies before it returns (deepinfer/model_executor/layers/sampler.py:258-275), and the worker records sample_end_evt after that (deepinfer/worker/worker.py:167-168). So when the event is complete, the copies are complete too. This is the deep dive "Events, streams and the waits that remain" on Zero-overhead scheduling (ZOS).

Related pages

  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • Offline API and the step loopLLM.generate() adds all requests, then calls LLMEngine.step() until no request is left. Each step schedules one batch, runs the model once, and returns handles to the new outputs. With ZOS, a decode step returns the tokens of the step before it.
  • worker/worker.py: the per-step WorkerWorker.execute_model_step runs every engine step on one rank in a fixed order - forward N, post-process N-1, sample N - and keeps a ZOS decode step for the next call. zos_status.py holds the two records that it keeps.
  • csrc/engine/zos.cpp: the C++ helpers of zero-overhead schedulingzos.cpp has three functions for ZOS decode steps - match the batch with the previous step (remap), pack the decode inputs into pinned arrays, and refresh the CPU metadata before sampling. The device kernels do the rest.
  • engine/llm_engine.py: the LLMEngine classLLMEngine starts the workers, sizes the KV cache, owns the C++ scheduler, and runs one engine step each time LLM calls step().
  • worker/model_runner.py: the ModelRunner classModelRunner owns the model object on one rank. It builds the input metadata, runs the forward pass (eager or as a CUDA graph replay), prepares the sampler inputs, runs the memory profile and captures the graphs.
  • The samplerThe sampler turns the hidden states of the rows that need a token into float32 logits, applies temperature, top-p and top-k, and draws one token per request with a seeded hash. In decode steps it also verifies the draft tokens.

  • CUDA graphsAt start-up DeepInfer records the decode forward pass once for each of a list of batch sizes. Each decode step then pads its rows to the next recorded size and replays the recording with one call.
