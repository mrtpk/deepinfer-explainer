Tour: Inside one decoder layer

AdvancedGuided toursabout 13 min read + 3 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Model map: DeepSeek-V4.1-Flash in DeepInfer Intermediate
  • mHC residual mixing Advanced
  • MLA attention: one latent vector per token Advanced
  • MoE routing: the gate, top-k and the shared expert Intermediate

In one sentence

We follow the 192 tokens of one decode step through one decoder layer, from the call in the model loop to the return value.

The idea#

The page Model map: DeepSeek-V4.1-Flash in DeepInfer showed the whole model. This tour stays inside one decoder layer and reads every call in code order. We name the file and the function at each stop, and we give the tensor shapes.

The example step:

  • A decode step with 32 sequences. Each sequence sends 1 token plus 5 drafts, so the step has T = 192 tokens.
  • We look at layer 7. It is a sparse compressed layer (it has an indexer), a DFlash target layer, and not an Engram layer.
  • Example model sizes: hidden size H = 4096, hc_mult = 4. These values are not in the repo; they come from config.json.
  • The device is a GPU, and the expert-parallel group fits in one NVLink domain. So the layer uses mega_mhc and mega-MoE.

Simplified

The layer number, the layer kind and the sizes are an example. Other layers and other configs take other branches; each stop says which.

The picture#

Read the cards from top to bottom. The teal cards are mHC work: they run twice per layer, once before each sub-layer. Look at stop 10: the MoE output leaves the layer as one stream. The trunk gets it only at stop 3 of the next layer.

1The layer gets its inputs#

We are in the loop of DeepseekModel.forward. It calls layer i with its own view of the KV cache:

The layer receives two things from layer 6. hidden_states is the MoE output of layer 6, which is not yet in the trunk. residual is an HCLazyPostData object: the trunk before the MoE of layer 6, plus the mixes for its post. Then DeepseekDecoderLayer.forward takes the tensor out of its Movable wrapper:

What the data looks like now:

hidden_states            bf16 [192, 4096]         # MoE output of layer 6
residual.residual        bf16 [1, 192, 4, 4096]   # trunk before that MoE
residual.post_layer_mix  fp32 [1, 192, 4, 1]
residual.comb_res_mix    fp32 [1, 192, 4, 4]
residual.pre_layer_mix   fp32 [1, 192, 4, 1]      # only with hc_shifted, else None
kv_cache                 KVCache views of layer 7: swa_cache, ca_cache, ica_cache, ...
Deep dive

Stop 1 in detail: layer 0 is different

Before the loop, residual = None (deepinfer/model_executor/models/deepseek.py:164). So layer 0 gets the embedding output [T, H] and no lazy data. At stop 3 it takes a different branch: it makes the trunk with expand_to_mhc (deepinfer/model_executor/models/v4_modules/hc.py:203-208). In a prefill, the VL class gives the embedding output (deepinfer/model_executor/models/deepseek_vl.py:232-233).

One CrossLayerRuntime object goes to all layers (deepinfer/model_executor/models/deepseek.py:166). It carries the shared hidden, the pre-RoPE KV and the top-k list from source layers to later layers. See Cross-layer KV sharing.

2Hooks and the YOCO boundary#

Still in DeepseekDecoderLayer.forward. Two optional blocks run before any math:

An Engram layer makes a closure here. Stop 3 calls it on the trunk. Layer 7 is not an Engram layer, so hc_post_intervention = None. The page Engram n-gram memory explains Engram.

This block runs only in the first YOCO consumer layer of a prefill with DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact (default off, deepinfer/environ.py:188). It keeps only the query rows of the last tokens of each prompt (deepinfer/environ.py:191-192). Our step is a decode step, so nothing happens. See YOCO and SWA bounded replay.

What the data looks like now: nothing changed. Lines 120-133 also open two timers; they record only in one sample layer per group of equal layers (deepinfer/model_executor/models/v4_modules/utils.py:139-143).

3mHC post of the previous MoE#

Line 143 calls attn_norm_forward. With mHC on, it goes to _hc_fused_post_pre (deepinfer/model_executor/models/v4_modules/hc.py:125-131). Its first job is the post mix of layer 6's MoE: write hidden_states into the trunk.

On our GPU, with hc_mult = 4 and H = 4096 (a multiple of 1024), use_mega_mhc is true (deepinfer/model_executor/models/v4_modules/hc.py:99-101). There is no Engram hook, the input is 2-D, and the lazy data has its post mix. So line 202 runs: one deep_gemm.mega_mhc call does this stop and stop 4. Without the fused path, lines 220-224 do the same in steps: hc_post, then _hc_pre.

Simplified

The post kernel is not in the repo. The page mHC residual mixing gives a simplified model. In it, each of the 4 new streams is a weighted sum of the 4 old streams plus a weighted copy of the MoE output. The post term of the engine's FLOP counter fits this model: 4 × 5 × 4096 = 81,920 per token, times a fixed cost factor (csrc/engine/flops_estimator.hpp:111).

What the data looks like now:

trunk (new_residual)     bf16 [192, 4, 4096]     # 6 MiB; layer 6 is now complete
old lazy data            cleared (all fields None)
Deep dive

Stop 3 in detail: the other cases

_hc_fused_post_pre has five cases. The page v4_modules/hc.py: the mHC runtime reads them all. In short:

  • Layer 0: no lazy data, so expand_to_mhc makes the trunk; with hc_shifted, a one-hot pre mix reads only stream 0 (deepinfer/model_executor/models/v4_modules/hc.py:203-208).
  • At its attention boundary, an Engram layer cannot use the fused call, because "no hook can be inserted inside the kernel" (deepinfer/model_executor/models/v4_modules/hc.py:184-186). It runs hc_post, then the hook, then _hc_pre (deepinfer/model_executor/models/v4_modules/hc.py:222-227). Its FFN boundary has no hook, so it can use mega_mhc.
  • On Ascend, use_mega_mhc is false (line 100), so every layer takes the step-by-step path.

4mHC pre and the attention norm#

Now the trunk must become one attention input. In the fused path, mega_mhc does it in the same call. The outputs show what it computes:

The call computes 24 mix values per token from the trunk (4 pre, 4 post, 16 residual-mix values). It applies a pre mix to make one [192, 4096] input. With hc_shifted (the HF default), this is the pre mix of the previous sub-layer (prev_pre_mix, line 249). Then it applies the attention RMSNorm and casts the result to FP8. Lines 264-268 prepare the MXFP8 scale layout, because the attention norm has FP8 output (deepinfer/model_executor/models/decoder_layer.py:43).

The new lazy data keeps the trunk and the mixes for the post at stop 7.

What the data looks like now:

hidden_states        (fp8 e4m3 [192, 4096], int32 scales [192, 32])   # 32 = 4096 / 128
hidden_states_bf16   bf16 [192, 4096]
residual             HCLazyPostData(
                       residual       bf16 [1, 192, 4, 4096],   # trunk after stop 3
                       post_layer_mix fp32 [1, 192, 4, 1],
                       comb_res_mix   fp32 [1, 192, 4, 4],
                       pre_layer_mix  fp32 [1, 192, 4, 1] or None)
Deep dive

Stop 4 in detail: the step-by-step path

Without mega_mhc, _hc_pre runs (deepinfer/model_executor/models/v4_modules/hc.py:317-364):

  1. Not shifted: mhc_pre_big_fuse. A TF32 GEMM multiplies the flat trunk [192, 16384] by fn (24 rows). One fused kernel then does the RMS, the split, Sinkhorn and the pre apply (deepinfer/model_executor/models/v4_modules/mhc_modeling.py:115-136).
  2. Shifted (the HF default, deepinfer/hugging_face/config.py:295): apply the pre mix of the previous sub-layer to the trunk. Then three operators compute the new mixes: mhc_pre_norm_fn (GEMM and RMS), mhc_pre_split_mixes and sinkhorn_normalize (deepinfer/model_executor/models/v4_modules/hc.py:343-358).
  3. Both: the attention RMSNorm gives FP8 and BF16 (deepinfer/model_executor/models/v4_modules/hc.py:359-363).

The int32 scale tensor packs four UE8M0 scales, one per 32 values. So 4096 values need 4096 / 32 / 4 = 32 int32 values per row (deepinfer/model_executor/models/v4_modules/hc.py:268).

5The DFlash copy and the YOCO shared hidden#

Back in DeepseekDecoderLayer.forward, right after the attention norm:

Layer 7 is a DFlash target, so lines 144-145 run. residual.residual is the trunk from stop 3 (after the Engram hook, when there is one). _store_dflash_input writes the mean of its 4 streams into this layer's column block of dflash_input:

After the last layer, DFlash.update_main_cache reads dflash_input (deepinfer/model_executor/models/deepseek.py:220-223). The tour Tour: One speculative decoding round (stop 3) follows it from there.

Lines 146-152 run only in the first YOCO consumer layer. Layer 7 is not that layer in our example.

What the data looks like now (with two target layers, layer 7 has index 1):

dflash_input   bf16 [192, 8192]            # [T, H × 2 targets]
dflash_input[:, 4096:8192] = trunk.mean(over the 4 streams)   # this layer's block

Simplified

The target list and the index of layer 7 are an example. They come from dspark_target_layer_ids in config.json (deepinfer/model_executor/models/deepseek.py:72-73).

6Attention: MLA, SWA and compressed keys, indexer#

The layer wraps the two inputs in Movable and calls V4Attention:

Inside V4Attention.forward, the decode path of a sparse compressed layer runs these steps (v4_modules/attn.py: the MLA attention runtime reads them in detail):

  1. Line 765: expand the compact index fields of the metadata into the index lists of the kernels.
  2. Line 768: one GEMM gives the input of the KV compressor and the weights of the indexer.
  3. Lines 787-790: project the query (low rank) and the sliding-window key vector.
  4. Lines 792-797: in decode, one fused kernel normalizes the SWA vector, applies RoPE, casts it to FP8 and stores it into swa_cache (deepinfer/model_executor/models/v4_modules/attn.py:421-448).
  5. Line 799: the query up-projection gives q_b [192, heads, 512].
  6. Lines 802-809: store the compressed KV entries, and let the indexer pick the top-k compressed entries for each token (deepinfer/model_executor/models/v4_modules/attn.py:544-567).

The decode kernel reads the SWA window and the selected compressed entries. Then _wv_and_o_proj maps the result back to the hidden size.

What the data looks like now:

q_b             bf16 [192, heads, 512]  # 512 = head size, inferred (not a config value in the repo)
kv_swa_index    int32 [192, window]           # from the metadata
kv_ca_index     int32 [192, index_topk]       # indexer output
attention out   bf16 [192, 4096]              # = hidden_states
residual        unchanged since stop 4
Deep dive

Stop 6 in detail: other layer kinds

  • A ratio-0 layer (SWA only) has no compressed KV: _compute_kv_ca_index returns None (deepinfer/model_executor/models/v4_modules/attn.py:534-535).
  • A sparse layer without its own indexer reuses cross_layer_runtime.topk_indices of its source layer (deepinfer/model_executor/models/v4_modules/attn.py:568-570).
  • A YOCO KV-source consumer projects its compressed KV from the shared hidden of stop 5 (deepinfer/model_executor/models/v4_modules/attn.py:775-780).
  • A prefill builds one buffer [SWA cache | current SWA | compressed] and calls the prefill kernel (deepinfer/model_executor/models/v4_modules/attn.py:812-869).

The concepts are on MLA attention: one latent vector per token, Sparse attention with an indexer, Sliding-window attention and KV compression (C1 and C2).

7mHC post of attention, and pre for the MoE#

Line 162 of DeepseekDecoderLayer.forward:

This is stop 3 and stop 4 again, with the MoE weights (hc_ffn, hc_ffn_fn, hc_ffn_scale) and the FFN norm (deepinfer/model_executor/models/v4_modules/hc.py:111-117). The post writes the attention output into the trunk. The pre makes the MoE input. One difference: ffn_norm_forward asks the MoE for cast arguments.

Our layer uses mega-MoE with FP8 activations. So fused_norm_cast_kwargs returns the MoE's symmetric buffer as out (deepinfer/model_executor/models/v4_modules/mlp.py:274-290). mega_mhc writes the FP8 MoE input and its scales straight into that buffer (deepinfer/model_executor/models/v4_modules/hc.py:259-263). No copy is needed at stop 9.

What the data looks like now:

trunk           bf16 [192, 4, 4096]      # now includes the attention output
hidden_states   (sym_buffer.x[:192] fp8 [192, 4096], sym_buffer.x_sf[:192])
hidden_states_bf16  bf16 [192, 4096]
residual        new HCLazyPostData for the MoE sub-layer

8The gate picks the experts#

The MoE timer opens (lines 164-168), and the layer calls self.mlp (deepinfer/model_executor/models/decoder_layer.py:169-173). DeepseekMoE.forward sends mega layers to mega_moe_forward, which starts with the gate:

The gate reads the BF16 copy. It writes the top-k physical expert slots and their weights straight into the buffer of the mega call. Lines 543-544 check that stop 7 really wrote the FP8 input into the same buffer.

What the data looks like now:

sym_buffer.topk_idx[:192]      [192, k]   # physical expert slots
sym_buffer.topk_weights[:192]  [192, k]   # routing weights
Deep dive

Stop 8 in detail: what the gate does

gate_forward passes the expert-score bias, the image-token bias, the padding mask and the EPLB map from logical to physical experts to the gate kernel (deepinfer/model_executor/models/v4_modules/mlp.py:381-401). The scoring function must be sqrtsoftplus (deepinfer/model_executor/models/v4_modules/mlp.py:169-170). The page MoE routing: the gate, top-k and the shared expert reads it line by line.

9The experts: dispatch, compute, shared expert, combine#

In our example, one DeepGEMM call does all the expert work:

This call does the dispatch, both expert GEMMs with SwiGLU, and the combine. In a mega layer, fuse_shared equals has_shared (deepinfer/model_executor/models/v4_modules/mlp.py:256), so the call also does the shared expert when the layer has one. The page Mega-MoE: the whole MoE layer in one call describes the call. This site does not describe the inside of DeepGEMM.

Without mega-MoE, forward runs the same parts one by one:

  1. Line 574: the gate.
  2. Lines 578-585: DeepEP dispatch sends the FP8 rows to the expert ranks.
  3. Lines 593-598: two grouped GEMMs with SwiGLU between them, on the received rows.
  4. Lines 601-603: capture an event, then launch the shared expert on the local tokens, with some SMs kept free for communication. The code launches combine after the shared expert, but combine waits on the event from before the shared expert. Whether the two overlap on the device is decided inside DeepEP.
  5. Lines 604-610: combine sums the expert outputs back, with the shared output as bias (deepinfer/model_executor/models/v4_modules/mlp.py:505).

What the data looks like now:

hidden_states   bf16 [192, 4096]      # MoE output (routed + shared)
residual        HCLazyPostData from stop 7 (trunk includes attention, not the MoE)

10Out: the layer returns#

The last line of DeepseekDecoderLayer.forward:

The layer returns the MoE output and the lazy data. It does not write the MoE output into the trunk. Layer 8 does that at its stop 3, in the same call as its attention pre mix (deepinfer/model_executor/models/v4_modules/hc.py:62-64). The code does not say why it waits.

After the last layer, DeepseekModel.forward does the last post and the fold:

What the data looks like now (after the last layer):

after line 227   bf16 [192, 4, 4096]    # full trunk
after line 230   bf16 [192, 4096]       # shifted: last pre mix (or HCHead, line 238)
after line 239   bf16 [192, 4096]       # output_norm; the sampler applies the lm head later

What can go wrong#

  • A wrong block type. A block that is not MoeDecoderBlockHC fails the assert at deepinfer/model_executor/models/decoder_layer.py:57.
  • DFlash targets with the wrong config. dspark_target_attn_input=False or mHC off raises an AssertionError at build time (deepinfer/model_executor/models/decoder_layer.py:65-67). A DFlash module without target layers fails in every forward (deepinfer/model_executor/models/deepseek.py:173).
  • Engram and YOCO compaction in one layer. Assert "yoco 层不能是 engram 层" (translated: "a YOCO layer cannot be an Engram layer") (deepinfer/model_executor/models/decoder_layer.py:136).
  • The FP8 buffer contract of mega-MoE. If the FFN norm did not write into the MoE buffer, the asserts at deepinfer/model_executor/models/v4_modules/mlp.py:543-544 fail.
  • An MoE error. The DeepEP path logs the rank and the topk_idx shape, then raises the error again (deepinfer/model_executor/models/v4_modules/mlp.py:612-614).

Why it matters. All model work of a step happens in these ten stops, N times. A slow layer shows up in the attention or MoE timers. A wrong output can come from any stop, so the shapes above help you to put a check in the right place. A check that synchronizes with the CPU fails inside the forward, because ModelRunner forbids it (deepinfer/worker/model_runner.py:320-329).

Check yourself#

  1. 1
    What two values does a decoder layer return, and what are their shapes in the example?
    easy
    Show answer

    The MoE output, bf16 [192, 4096], and an HCLazyPostData with the trunk [1, 192, 4, 4096] and the mixes (deepinfer/model_executor/models/decoder_layer.py:175, deepinfer/model_executor/models/v4_modules/hc_lazy.py:21-25).

  2. 2
    At which stop does a DFlash target layer copy its features, and what does it copy?
    easy
    Show answer

    Stop 5, after the attention norm and before attention. It copies the mean of the hc_mult streams of the trunk (deepinfer/model_executor/models/decoder_layer.py:144-145, deepinfer/model_executor/layers/tilelang_ops/dflash.py:134-143).

  3. 3
    In our example, how many kernel calls do stops 3 and 4 take, and why would an Engram layer take more?
    medium
    Show answer

    One deep_gemm.mega_mhc call (deepinfer/model_executor/models/v4_modules/hc.py:195-202). An Engram layer must change the trunk between the post and the pre, and "no hook can be inserted inside the kernel" (deepinfer/model_executor/models/v4_modules/hc.py:184-186). So it runs hc_post, the hook, and _hc_pre as separate calls.

  4. 4
    Why does the MoE not copy its FP8 input into its own buffer at stop 9?
    medium
    Show answer

    At stop 7, ffn_norm_forward passed the MoE's buffer as the output of the norm (deepinfer/model_executor/models/v4_modules/hc.py:146, deepinfer/model_executor/models/v4_modules/mlp.py:274-290). mega_moe_forward only checks the pointers (deepinfer/model_executor/models/v4_modules/mlp.py:542-544).

  5. 5
    The step has 192 tokens, H = 4096, hc_mult = 4. How many bytes of trunk does one layer write, and why does the post of the MoE wait for the next layer?
    hard
    Show answer

    Two posts per layer (stops 3 and 7), each writes 192 × 4 × 4096 × 2 bytes = 6 MiB, so 12 MiB. The code does not state the reason for the wait. It joins the previous post with the next pre (deepinfer/model_executor/models/v4_modules/hc.py:62-64), and on a GPU one mega_mhc call then does the post, the pre and the norm (deepinfer/model_executor/models/v4_modules/hc.py:236-238). A post at the end of the layer would need its own kernel call. See stop 3 and stop 10.

Related pages

  • models/decoder_layer.py: one decoder layerdecoder_layer.py holds DeepseekDecoderLayer (one main-model layer: mHC, attention, mHC, MoE, plus the Engram, YOCO and DFlash hooks) and DFlashDecoderLayer (one draft-model layer).
  • v4_modules/hc.py: the mHC runtimehc.py runs mHC around every sub-layer (HCLayerMixin) and folds the streams at the end (HCHead). mhc_ops.py and mhc_modeling.py wrap the kernels. hc_lazy.py holds the data that goes from one sub-layer to the next.
  • v4_modules/attn.py: the MLA attention runtimeattn.py turns the MLA weight container into runtime weights and runs one attention layer per call: projections, sliding-window and compressed KV stores, the indexer, the FlashMLA kernel and the output projection. It also holds the DFlash draft attention.
  • v4_modules/mlp.py: the DeepseekMoE layerDeepseekMoE is the runtime MoE layer of DeepInfer. It converts the moe.py containers into the runtime layout, runs the gate, and then either DeepEP dispatch, grouped GEMMs and combine, or one mega-MoE call.
  • mHC residual mixingDeepSeek-V4.1 keeps the residual stream as hc_mult parallel streams. Before each sub-layer, learned weights mix the streams into one input. After it, the output goes back into all streams. The model ends with one fold.
  • Sparse attention with an indexerIn a sparse layer, a small indexer scores all compressed keys for each query and keeps the best index_topk. The main attention then reads only those keys plus the sliding window.
  • Mega-MoE: the whole MoE layer in one callInside one NVLink domain, DeepInfer replaces dispatch, the expert GEMMs, the shared expert and combine with one DeepGEMM mega-MoE call that works on a symmetric buffer. The choice is fixed per layer at start-up.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
  • Tour: One speculative decoding roundFollow request "1" through one decode step with 5 drafts, in 12 stops: verification length, inputs, forward pass, sampler inputs, accept test, residual, DFlash drafts, confidences, results, cache rollback, and the length of the next check.
