Tour: One speculative decoding round

AdvancedGuided toursabout 13 min read + 4 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Tour: Life of a request Beginner
  • Speculative decoding Intermediate
  • DSpark: DFlash drafts and confidence-scheduled verification Advanced

In one sentence

We follow one request through one decode step with 5 drafts. We start at the scheduler and end at the length of the next check.

The idea#

The tour Tour: Life of a request showed one request from the prompt to the output. Its stops 10 and 11 touched the sampler and the drafts only briefly. This tour stays inside one decode step with draft tokens and reads every part of it.

We use the same request "1" as Tour 1 (temperature=0.4, seq_seed=1, top_logprobs=4). The step is a later decode step, the same one as the worked example in Tour 1, stop 12:

  • Before the step, the sequence has 50 tokens (positions 0 to 49). The KV cache holds 49 of them: cache.num_tokens = 49. Token 49 is the last real token t; it is not in the cache yet.
  • The previous step left 5 drafts d1 … d5 in the MTP info pool, in slot 2 (Tour 1, stop 5).
  • In this step the sampler accepts d1 and d2, rejects d3, and samples r from the residual distribution. DFlash then drafts e1 … e5.

Token ids, probabilities and random numbers in this tour are illustrative. Positions, shapes and slot numbers follow the code.

The picture#

Read panel 1 from left to right: the three boxes are the three device phases of one step. Panel 2 is the answer to "how does DeepInfer undo the rejected drafts". The short answer is: it does not copy anything back. Panel 3 shows the decision for the next step.

1The scheduler sets the verification length#

We are in Scheduler::_schedule, in the decode branch. After the scheduler has picked the running sequences, it sorts them by length and asks MTPVarlen for one seqlen_q per sequence:

Without DSpark there is no cost curve, so every sequence gets 1 + 5 = 6 (csrc/engine/mtp_varlen.hpp:153-158). Then schedule() builds the metadata of our sequence:

For request "1": seqlen_q = 6 and seqlen_k = 49 + inflight + 6. Without ZOS, inflight = 0, so seqlen_k = 55. The step will compute positions 49 to 54. start_inflight_step(nextn + 1) then reserves 6 positions for the in-flight step (csrc/engine/scheduler.hpp:726).

Deep dive

Stop 1 in detail: ZOS and the in-flight count

With ZOS, the CPU schedules step N+1 before it knows how many drafts step N accepted. So it assumes the most: total_inflight_tokens grows by nextn + 1 per step (csrc/engine/sequence.hpp:244-247), and seqlen_k includes it. A device kernel later fixes seqlens_k: it adds seqlens_q and subtracts nextn − accepted of the previous step (deepinfer/model_executor/layers/tilelang_ops/compute_seqlens_k_zos.py:10-31). Before sampling, the worker also sets seqlen_k = seqlen_q + cache.num_tokens on the CPU side (csrc/engine/zos.cpp:297-299). So in all cases the sampler sees seqlen_k = 55 for our step.

The counter seq.mtp.schedule_cnt grows by 1 here (csrc/engine/scheduler.hpp:694). DSpark compares it with process_cnt to know how old the stored accept rates are (stop 12).

2Six input tokens and their cache slots#

The batch metadata turns the sequence into tensors (Tour 1, stop 6). In a decode step, the input ids are the last real token, then seqlen_q − 1 drafts:

Line 109 checks the length rule: len − 1 + seqlen_q = seqlen_k, so 50 − 1 + 6 = 55. Line 112 copies token 49, and lines 114-118 add d1 … d5.

The sliding-window cache slot of each token is state_id × 134 + position % 134 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:98-107). The ZOS path on the device uses the same formula (deepinfer/model_executor/layers/tilelang_ops/prepare_v4_decode_metadata.py:217).

What the data looks like now (illustrative ids):

input_ids  int32 [6] = [t, d1, d2, d3, d4, d5]     # e.g. [9021, 1735, 304, 6040, 13, 418]
positions  int32 [6] = [49, 50, 51, 52, 53, 54]
slot_mapping_store_swa = state_id * 134 + [49, 50, 51, 52, 53, 54]   # 134 = 128 + 6
Deep dive

Stop 2 in detail: compressed KV entries

Compressed layers write a new entry only for a token where (position + 1) % ratio == 0. All other rows get slot -1 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:71-91). The slot depends only on position / ratio. For a ratio of 4, this step writes one entry at position 51 (the group 48-51). Position 52 to 54 start the next group. Stop 11 explains what this means for rejected drafts.

3The forward pass, and the DFlash keys#

The main model runs once on all 6 tokens. It returns 6 hidden states, not logits (Tour 1, stop 8). It also feeds the draft model. Some layers store a feature in dflash_input: the mean of the mHC trunk streams, after the attention mHC pre and norm and before attention (deepinfer/model_executor/models/decoder_layer.py:143-145, deepinfer/model_executor/layers/tilelang_ops/dflash.py:132). After the last layer:

update_main_cache writes one key per DFlash layer for positions 49 to 54, into the DFlash sliding-window cache (deepinfer/model_executor/models/mtp/dflash.py:219-228). The keys of 52 to 54 belong to drafts that will be rejected. That is fine (stop 11).

hidden_states  bf16 [rows_out, H]      # rows_out = 6 + CUDA graph padding
dflash_input        [rows_out, H × T]   # same rows as hidden_states; T target layers
DFlash cache        keys for positions 49 … 54 in every DFlash layer

4Sampler inputs: positions, pool rows, stop ids#

Now execute_sample builds the sampler inputs in C++ (deepinfer/worker/model_runner.py:348). For a decode sequence:

  1. Lines 202-204: all 6 rows of the request are selected.
  2. Line 206: sample_position = seqlen_k − seqlen_q + 1 = 55 − 6 + 1 = 50.
  3. Line 216: the write slot is the request's own slot, 2.
  4. Line 218: ignore_eos=False, so the stop ids are [1, -1] (EOS id 1).
  5. Lines 221-225: rows 0 to 4 read pool rows 2 × 5 + j = 10 … 14; row 5 reads row 0.

The read slot is 2 only because the sequence has unread draft info; otherwise it is 0, the placeholder slot (csrc/engine/sequence.hpp:149-153).

selected_token_indices  int32 [6]  = [0, 1, 2, 3, 4, 5]   # our request is first in the batch
kernel.sample_positions int32 [1]  = [50]
kernel.seq_seeds        uint64 [1] = [1]
mtp_first_token_positions          = [0];  mtp_seqlens_q = [6]
mtp_info_read_rows      int32 [6]  = [10, 11, 12, 13, 14, 0]
mtp_info_write_slots    int32 [1]  = [2]
stop_token_ids          int32 [1, 2] = [[1, -1]]

5Six rows of logits and their labels#

Sampler.forward gathers the 6 rows and makes float32 logits [6, V] (deepinfer/model_executor/layers/sampler.py:141-142). Then _verification labels the rows:

row_to_req = [0, 0, 0, 0, 0, 0]
local_step = [0, 1, 2, 3, 4, 5]
is_verify  = [T, T, T, T, T, F]     # row 5 is the fresh row
# per-row sample positions after expand_sampling_params:
#   50 + local_step × 10000019 = [50, 10000069, 20000088, 30000107, 40000126, 50000145]

With DEEPINFER_SAMPLER_FORCE_TOPK=4096 (the example script), the logits shrink to [6, 4096] plus token_index [6, 4096] (deepinfer/model_executor/layers/sampler_utils.py:166-167). The draft logprobs of pool rows 10 to 14 are moved into the same top-4096 space (deepinfer/model_executor/layers/sampler_utils.py:172-180).

6The accept test, row by row#

One fused_sample launch does temperature (0.4), top-p, top-k, log-softmax and the test for all 6 rows. The math, from the reference implementation:

Row j accepts its draft if min(1, q/p) > U. U is the hash of seed 1 and 3 × position + 2. With illustrative values:

RowDraftp (draft)q (target)min(1, q/p)UKernel result
0d10.810.8810.42accept
1d20.640.510.7970.35accept
2d30.580.120.2070.66reject → residual sample r
3d40.700.650.9290.10accept (but not used)
4d50.330.050.1520.80reject (not used)
5nonefresh sample (not used)

The kernel decides every row on its own. It does not know yet that rows 3 to 5 come after a reject. The residual sample of row 2 uses max(q − α·p, 0) and hash case 1 (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:232).

Deep dive

Stop 6 in detail: the three hash cases of row 2

Row 2 has position 20000088. The kernel uses three different sequence numbers for it (deepinfer/model_executor/layers/tilelang_ops/random_sampling.py:76-81, deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:239-245):

  • 3 × 20000088 + 0: the fresh sample of the row (not used, because the row verifies).
  • 3 × 20000088 + 1: the residual sample r.
  • 3 × 20000088 + 2: the number U of the accept test.

So the accept decision and the residual draw are independent, and both are the same in every run with seq_seed = 1. The kernel also writes accept_probs = max(1 − Σ residual, 0) for each verify row (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:233-234). For row 2 that is an estimate of the chance that the row accepts a draft of the draft model. The α penalty makes it a little lower than the exact chance.

7The accepted prefix and the new token#

get_accept_result keeps only the prefix before the first blocked row (deepinfer/model_executor/layers/tilelang_ops/sampler.py:243-247):

blocked     = [F, F, T, F, T, T]     # rejected verify rows and the fresh row
alive       = [T, T, T, F, F, F]     # no blocked row before it
eff_accept  = [T, T, F, F, F, F]     # row 3 had a raw accept, but it is not alive
is_final    = [F, F, T, F, F, F]     # first blocked row

finalize_verification then packs the request results (deepinfer/model_executor/layers/sampler.py:518-566):

last_valid_offset        int32 [1] = [2]          # accepted drafts
sampled_token.token_ids  int32 [1] = [r]          # token of row 2 (residual sample)
verified_tokens.token_ids int32 [6] = [d1, d2, -1, -1, -1, -1]
num_generated_tokens  [5] = [1, 1, 0, 0, 0]
num_verified_tokens   [5] = [1, 1, 1, 1, 1]
emitted_stop_token    [1] = [False]           # r, d1, d2 are not EOS

The logprob of r and its 4 top logprobs come from row 2, the final row. The logprobs of d1 and d2 come from rows 0 and 1 (deepinfer/model_executor/layers/tilelang_ops/sampler.py:390-399).

8DFlash drafts the next 5 tokens#

Still inside the sampler, DFlash starts from r (deepinfer/model_executor/layers/sampler.py:235-251). build_dflash_input places a block of 5 positions after the last accepted position:

accepted_pos = 49 + 2 = 51, so the block covers positions 52 to 56. Row 0 holds r at position 52; rows 1 to 4 hold the noise token. Every row attends to the main keys of positions up to 51 (128-token window) and to the 5 block keys. The block keys at 52 to 56 are written over the main keys of the rejected drafts.

sample_drafts then makes the drafts one step at a time. Step i adds the Markov term of the previous token and computes the confidence. Then it samples with seed namespace "mtp" at position 50 + 2 + (i + 1) (deepinfer/model_executor/models/mtp/dflash.py:290-294, deepinfer/model_executor/models/mtp/dflash.py:308-334).

draft positions        [52, 53, 54, 55, 56]      # inputs: r, noise × 4
predict_tokens.token_ids        int32 [1, 5] = [[e1, e2, e3, e4, e5]]   # predict positions 53 … 57
predict_tokens.confidence_rates fp32  [1, 5] = [[0.92, 0.80, 0.60, 0.30, 0.20]]   # illustrative
draft sample positions          [53, 54, 55, 56, 57]   # 50 + 2 + 1 … 5
MTP info pool rows 10 … 14 ← e1 … e5, their logprobs and confidences
Deep dive

Stop 8 in detail: why drafts and target use different random streams

The draft sample of step 1 uses position 53, case 0, with seed 1 + 1000000007 (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:93). In the next step, the target model checks e1 at row 0 with position 53, but with seed 1 and case 2. If both used the same number, the draft choice and the accept test would be correlated. The offset keeps them apart. The fused-sample test checks the "mtp" stream as its own case (deepinfer/model_executor/layers/tilelang_ops/fused_sample.py:686-697).

9Results leave the sampler#

The sampler starts non_blocking copies of all results to the CPU. It also keeps device copies for ZOS: the sampled token, the 5 new drafts, the confidences and last_valid_offset (deepinfer/model_executor/layers/sampler.py:287-290). Then the worker calls pre_sampler_sync and records sample_end_evt (deepinfer/worker/worker.py:162-168). With ZOS, the CPU reads these results during the next call of execute_model_step (Tour 1, stop 7).

10C++ appends the tokens#

LLMEngine._process_model_outputs makes three C++ calls in a fixed order (Tour 1, stop 12). First, process_MTPInfo stores the new drafts and the running product of the confidences:

For our request: draft_tokens = [e1 … e5] and accept_rates = [0.92, 0.736, 0.442, 0.132, 0.026]. Second, process_outputs reads the accepted ids until the first -1, appends d1, d2, r, and fixes the cache count (csrc/engine/scheduler.hpp:955-1000):

seq.input.tokens   len 50 → 53         # d1 at 50, d2 at 51, r at 52
seq.cache.num_tokens   49 → 52         # commit_processed_tokens(3): t, d1, d2 are cached
seq.mtp.last_output_token = r          # the input token of the next step
seq.mtp.accepted_tokens   = [d1, d2]

Third, build_request_outputs makes 3 RequestOutput objects. The last one (for r) has draft_tok = 6 and accept_tok = 3 (csrc/engine/outputs.hpp:214-216, csrc/engine/outputs.hpp:287-292).

Deep dive

Stop 10 in detail: why num_tokens becomes 52, not 53

The cache count is the number of tokens whose keys and values are valid in the cache. This step computed keys for positions 49 to 54. Only 49 (t), 50 (d1) and 51 (d2) are real tokens now. r at position 52 was sampled in this step, so the model has not seen it as an input yet. It is the first input of the next step. So num_tokens = 49 + 3 = 52, where 3 is the number of appended tokens (token_cnt) (csrc/engine/scheduler.hpp:997-1000, csrc/engine/sequence.hpp:216-221).

11What happens to the rejected drafts#

The step wrote cache entries for d3, d4 and d5 at positions 52 to 54. DeepInfer never copies anything back. Every store is indexed by position, and the next step writes the same positions again:

  • KV count. num_tokens = 52 says that positions 52 and later are not valid (stop 10). The next step writes them again.
  • Sliding-window ring. Positions 52 to 54 sit in ring slots 52 … 54 % 134. The next step writes positions 52 to 57 into the same slots. The ring has 6 extra slots, so the rejected writes never cover a key that a query still needs (deepinfer/worker/cache_engine.py:88-93).
  • Compressed KV. An entry exists only at the end of a group. Its slot depends only on the group number, so the real token writes the same slot later (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:78-91). The float32 compression state uses a ring of ratio + 5 positions for the same reason (deepinfer/worker/cache_engine.py:130-133).
  • DFlash cache. Stop 8 already wrote the block keys of 52 to 56 over the rejected main keys, in this step (deepinfer/model_executor/models/mtp/dflash.py:204-209).
  • MTP info pool. Slot 2 now holds e1 … e5. d3 … d5 are gone.
  • Grammar matcher. With a grammar, the sampler tried the drafts to build the masks, and then rolled the matcher back (deepinfer/model_executor/layers/sampler.py:366-376). Next step it accepts only d1, d2, r (deepinfer/model_executor/layers/sampler.py:352-355).
Deep dive

Stop 11 in detail: the backtracking limit

The ring sizes come from DEEPINFER_MAX_BACKTRACKING_TOKENS, which is at least nextn + 1 = 6 (deepinfer/environ.py:132).

Proof for the ring of 134: this step wrote positions 49 to 54. Before that, slots 49 % 134 to 54 % 134 held positions −85 to −80, which never existed. In general, a step that writes P … P + 5 overwrites P − 134 … P − 129. Its oldest query is at P, and with a 128-token window it needs keys back to P − 127 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:644-649). The next step writes 52 to 57 over the rejected keys of 52 to 54 before its attention reads them. The docs state the same budget: "128-token window + 6 tokens of speculative backtracking" (doc/inference_deployment_qa.md:191).

A preempted sequence goes back to the waiting queue. Its MTP counters and accept rates are cleared (csrc/engine/sequence.hpp:133-142), and its next prefill starts without drafts.

12The length of the next check#

The next step must send r and some of e1 … e5. Without DSpark, it sends all 5: seqlen_q = 6, positions 52 to 57. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler can send fewer. It sorts the accept rates of all requests and keeps the drafts with the best expected tokens per millisecond (csrc/engine/mtp_varlen.hpp:228-266).

Our request has the running products [0.92, 0.736, 0.442, 0.132, 0.026]. If the batch budget keeps its first 3 drafts, then seqlen_q = 4 and the inputs are r, e1, e2, e3 at positions 52 to 55. The page DSpark: DFlash drafts and confidence-scheduled verification shows how the budget comes from all requests together.

With ZOS, the CPU scheduled the next step before it saw these confidences. So the CPU fixes only the total total_q, and line 219 recomputes the split on the device with the confidences of this step. Lines 231-234 copy the new lengths back, and the worker waits for this copy before it samples (deepinfer/worker/worker.py:146-152). Then the round starts again at stop 1.

Deep dive

Stop 12 in detail: which accept rates the CPU uses

When the CPU schedules step N+1 with ZOS, step N is not post-processed yet. So schedule_cnt = process_cnt + 1 for our request, and its accept_rates are one round older than usual (csrc/engine/mtp_varlen.hpp:160-168). The CPU uses them for the total and for its own split, but the device replaces that split. The GPU kernel uses the newest confidences, confidence_rates_gpu of step N, for the split (deepinfer/worker/worker.py:219). A request that was not in step N gets the rate 0 in the GPU split. So its drafts come after all drafts with a rate above 0 (deepinfer/model_executor/layers/tilelang_ops/schedule_mtp_varlen.py:57-65).

What can go wrong#

  • A stop token among the accepted drafts. _check_stop runs after each appended token, so the request ends at that token and the rest is dropped (csrc/engine/scheduler.hpp:982-990). The sampler also sets the confidences of the next drafts to 0 (deepinfer/model_executor/layers/sampler.py:252-254).
  • The first decode step after prefill. It reads the placeholder slot 0, so it almost always makes only 1 token (deepinfer/model_executor/layers/mtp_info_pool.py:47-49).
  • Inconsistent lengths. The input builder checks len − 1 + seqlen_q = seqlen_k and that the sequence has enough drafts (csrc/engine/input_metadata/prepare_tensor_input_base.cpp:109, csrc/engine/input_metadata/prepare_tensor_input_base.cpp:115). A failure stops the engine.
  • Reading the outputs too early. With ZOS, the tokens of this round arrive one step() call later (Zero-overhead scheduling (ZOS)).

Why it matters. One round made 3 tokens from one forward pass, and it prepared 5 new drafts in the same step. Rejected work costs device time, but it never needs a copy or an undo. The position-indexed caches simply write the same positions again.

Related pages

  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
  • DSpark: DFlash drafts and confidence-scheduled verificationDSpark makes 5 drafts per request with the DFlash draft model and predicts how likely each draft is to pass. With DEEPINFER_ENABLE_MTP_VARLEN=1, the scheduler then sends only the drafts that give the most tokens per unit of device time.
  • The samplerThe sampler turns the hidden states of the rows that need a token into float32 logits, applies temperature, top-p and top-k, and draws one token per request with a seeded hash. In decode steps it also verifies the draft tokens.
  • layers/sampler.py: the Sampler classsampler.py holds the Sampler module. It turns selected hidden states into float32 logits, samples prefill tokens, verifies draft tokens in decode steps and calls DFlash. sampler_utils.py holds the logits, sampling and prompt-logprob helpers.
  • models/mtp/dflash.py: the DFlash draft modeldflash.py holds DFlash, the draft model of DSpark. It writes draft keys from main-model features during the forward pass, makes 5 drafts per request in one pass after the verification, and stores drafts, logprobs and confidences in the MTP info pool.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • Sliding-window attentionEvery attention layer of DeepSeek-V4.1-Flash reads the most recent tokens (a window of 128 in the docs) from a ring of 134 slots per sequence and layer. This page shows the ring, the decode and prefill index paths, and how the window joins the compressed keys.
