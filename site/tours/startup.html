Tour: Start-up

IntermediateGuided toursabout 21 min read + 16 min deep dives

Code version: DeepInfer @ 9bd9cf2 · 2026-10-21

Before you read

This page uses ideas from these pages:

  • Tour: Life of a request Beginner
  • The KV cache Beginner
  • Parallelism basics Beginner

In one sentence

We follow one engine process from the launcher script to the moment when LLM(...) returns and the engine can run its first step.

The idea#

The tour Tour: Life of a request starts after the engine is ready. This tour covers the part before it. The call LLM(model=...) does a lot of work. It starts processes, connects the devices and loads the weights. Then it measures the free memory, makes the KV cache and records CUDA graphs. Only after all that can generate() run.

The order of this work is strict. The KV cache gets the memory that the weights and a test run leave free, so it comes after them. The CUDA graphs record kernels that read the KV cache, so they come after the cache. The device settings must be in the environment before Python imports torch, so they come first of all.

The tour uses the settings of examples/offline_inference.py with its defaults: --ep 8 --cp 1 on one host with 8 devices (examples/offline_inference.py:13-15). So there are 8 data-parallel (DP) ranks, and each one builds a full engine with max_num_seqs=4, max_model_len=32768 and gpu_memory_utilization=0.85 (examples/offline_inference.py:45-57). Where the library defaults give other numbers, the deep dives say so.

An everyday comparison. Think of a restaurant before it opens. The owner picks the staff and gives each cook a station (stops 1 to 8). The cooks bring in the food and set up the kitchen (stops 9 and 10). Then the owner measures the free space in the cold room and fills it with shelves (stops 11 and 12). The cooks practise each dish one time, so that later they can repeat it fast (stop 13). The comparison stops being true in one place. Here all 8 "restaurants" (DP ranks) must open at the same time, because they share one set of experts.

The picture#

Read panel 1 from left to right and panel 2 from top to bottom. Amber stops run before Python imports deepinfer. Blue stops run one time in the engine process. Green stops run in every rank: in this example only the driver, but with --cp 2 also in a CP follower process.

1The launcher starts one process per DP rank#

We are in examples/offline_inference.py. The script reads the parallel sizes from the command line. dp_size is ep // cp, so 8 (examples/offline_inference.py:24-29). The last line calls launch_dp(main, dp_size) (examples/offline_inference.py:112-113).

  1. Lines 17-18: RANK is the index of this host and WORLD_SIZE the number of hosts. The defaults are one host.
  2. Lines 35-44: with more than one DP rank, the launcher starts one process per rank of this host with the spawn (start method) start method. Each process runs main(dp_size, dp_rank).
  3. Lines 46-48: it waits for all processes. A process with a non-zero exit code gives RuntimeError.
  4. Line 50: with one DP rank there is no child process.

The module docstring says that this file does not use deepinfer (Translated, examples/_launch.py:1-5). So the launcher process never imports torch or touches a device. Each child is a new Python interpreter and sets its own devices (stop 2).

What the data looks like now (in the process of DP rank 3):

os.environ["RANK"], os.environ["WORLD_SIZE"]   # "0", "1"   (one host)
dp_size, dp_rank                                # 8, 3
"deepinfer" in sys.modules                      # False
Deep dive

Stop 1 in detail: hosts, ranks and spawn

More than one host. run_dp starts the ranks with dp_rank // (dp_size // num_nodes) == node_rank (examples/_launch.py:39-40). With 16 ranks on 2 hosts, host 0 starts ranks 0-7 and host 1 starts ranks 8-15. dp_size must be a multiple of the host count (line 33).

What spawn gives. The code does not say why it uses spawn. A spawned child gets a copy of the environment of the parent but no copy of its memory. The child imports torch only after it sets the visible devices (stop 2).

Who else starts processes. The engine starts more processes later: CP followers with spawn (stop 6) and a multimodal worker with fork (stop 5). The launcher does not know about them.

The world size. world_size = dp_size * cp_size and it must be a multiple of ep_size (examples/offline_inference.py:28-29). With --ep 8 --cp 2 the script makes 4 DP ranks with 2 devices each.

Stop 2 in detail: the device formula, deep_cluster, and the import-time reads

The device formula. local_engine_rank = engine_rank * cp_size % device_count // cp_size. The process gets cp_size devices from DEVICE_OFFSET + local_engine_rank * cp_size (examples/_config.py:57-61). Examples on a host with 8 devices:

deep_cluster before deepinfer. _config.py imports deep_cluster.hardware at the top (examples/_config.py:26). That package reads the hardware from the file system and does not start CUDA. accelerator_kind() returns "ascend", "nvidia" or "cpu" (deep_cluster/hardware/device.py:18-23), and get_actual_num_gpus() counts the physical devices (deep_cluster/hardware/device.py:139-140). On Ascend, the script copies the device list to ASCEND_RT_VISIBLE_DEVICES (examples/_config.py:62-63). The docstring of create_llm gives the reason. Translated: "On Ascend NPU, import torch initializes the ACL environment, and then the ASCEND_RT_VISIBLE_DEVICES setting fails" (examples/_config.py:102). The page Hardware discovery (deep_cluster) explains the package.

Reads at import time. deepinfer/__init__.py reads DEEPINFER_ACCELERATOR (default "nvidia") for the folder of the compiled extension (deepinfer/__init__.py:15, deepinfer/environ.py:101). Later imports read more variables at import time: for example, SchedulerConfig uses DEEPINFER_PREFILL_ATTEMPT_INTERVAL as a default argument (deepinfer/config.py:193-194). The table Variables read at import time lists all of them. A change after the import has no effect on those values.

The other settings. DEEPINFER_EXPERT_COUNT_WINDOW_SIZE=3 is always set (examples/_config.py:80). With EPLB on (the default of this script), the script also asks for 32 extra experts and a rearrangement every 30 steps (examples/_config.py:77-83, examples/offline_inference.py:35-41). The library default for extra experts is 0 (deepinfer/environ.py:114).

The model path. resolve_model_path takes a local folder with config.json, or downloads the Hugging Face checkpoint deepseek-ai/DeepSeek-V4.1-Flash-1017 into the Hugging Face cache. DEEPINFER_HF_MODEL_DIR points the default name at a local copy (examples/_config.py:32-52).

Stop 5 in detail: what the HF parser checks

Required values. The checkpoint must use SwiGLU (hidden_act = "silu"), no attention bias, zero dropout, one KV head and BF16 parameters (deepinfer/hugging_face/config.py:51-59). The quantization must be FP8 with FP4 experts, dynamic activations, blocks of 32 × 32 and UE8M0 scales (lines 254-262). Any other value raises ValueError with the expected value.

Values that the parser derives. kv_lora_rank = head_dim - qk_rope_head_dim (deepinfer/hugging_face/config.py:288-289). window_size = (sliding_window, 0) (line 284). use_fp4_sparse_kv defaults to True (line 303). attn_module_list has one entry per layer, one None for the LM head and one per DFlash layer (deepinfer/hugging_face/config.py:146-155).

The fork happens early. The multimodal worker is forked before _init_workers (stop 6). With DEEPINFER_USE_MULTIMODAL_POOL=1 (set in stop 3), the processor logs the size of a pinned host pool: DEEPINFER_MULTIMODAL_POOL_SIZE_GB (default 8) per rank (deepinfer/ve/multimodal_processor.py:49-56, deepinfer/environ.py:208). Before the fork, get_multi_modal_pool() makes this pool and pins it, on GPU with cudaHostRegister (deepinfer/ve/multimodal_processor.py:99-100, deepinfer/shared_memory.py:360-363, deepinfer/shared_memory.py:116-119, deepinfer/platform.py:65-68). So the engine process calls the CUDA runtime already here, before stop 7.

NUMA binding here. _bind_numa(local_rank=0) runs only when the engine makes a multimodal processor. The same function runs again for every Worker in stop 7.

6Workers: CP followers, then the driver#

Next, _init_workers makes the Worker objects. A Worker owns one device. The engine process always holds the driver Worker. Extra processes exist only for context parallelism:

  1. Lines 377-395: one spawned process per CP rank 1 to cp_size − 1. Each one runs _spawn_worker, which makes a Worker with is_driver_worker=False (deepinfer/engine/llm_engine.py:122-127). With --cp 1 the loop is empty.
  2. Line 384: a follower uses local device cp_rank % ngpus of this process's visible devices.
  3. Lines 402-411: the driver Worker runs in this process, with local_rank = 0 and cp_rank = 0. It gets two callbacks into the engine.

The Worker constructor does stops 7 and 8 at once. A follower then never returns from its constructor: it waits in a loop for method calls from the driver (deepinfer/worker/base.py:120-133).

What the data looks like now (with --cp 2, for comparison):

Stop 6 in detail: the order of construction and the rendezvous address

Order. The followers start first, and then the driver Worker is built. All of them meet in init_dist (stop 8), so this order does not matter for correctness. A follower that starts late only makes the others wait.

The init method. All ranks of all DP processes meet at one TCP address. get_distributed_init_method returns tcp://MASTER_ADDR:(MASTER_PORT − 50 + engine_group_rank), with defaults localhost and 23333 (deepinfer/utils.py:222-230). So the example uses tcp://localhost:23283. The comment says that two independent jobs on one host must use different MASTER_PORT values.

Follower extras. _spawn_worker first calls expose_all_gpus_to_cuda_driver(). On NVIDIA with DEEPINFER_ENGRAM_FORCE_GPU_STORAGE on, it shows all devices to the CUDA driver for one cuInit call, then restores the old list (deepinfer/worker/runtime_config.py:13-26). A follower also asks the kernel for SIGKILL when its parent dies (deepinfer/worker/base.py:130).

The profiling server. Right after _init_workers, the engine starts the HTTP profiling server if DEEPINFER_PROFILE_HTTP_ENABLE=1 (deepinfer/engine/llm_engine.py:235-239). The page engine/stats_logger.py: step statistics, MFU and moe_lb describes it.

  2. Line 183: configure_worker_environment sets NCCL and JIT-cache variables for this process (deepinfer/worker/runtime_config.py:29-51).
  3. Line 185: NUMA binding for the device (below).
  4. Lines 186-187: the device is cuda:{local_rank}, so cuda:0 for the driver. The process sees only its own devices, so cuda:0 is physical device 3.
  5. Line 188: kernel-library settings, for example deterministic algorithms with DEEPINFER_BATCH_INVARIANT=1 (deepinfer/worker/runtime_config.py:54-69).
  6. Line 191: CPU affinity to a fixed range of physical cores.

Stop 7 in detail: two bindings and their order

  1. NUMA. which_numa(local_rank) maps the visible device to its physical id and reads its NUMA node (deep_cluster/topology/bind.py:42-61). bind_numa loads libnuma.so.1 with ctypes. It sets the CPU affinity to the cores of that node and the memory policy to MPOL_BIND on that node (lines 79-93).

If libnuma.so.1 is missing, bind_numa raises OSError (deep_cluster/topology/bind.py:25-30), and _bind_numa turns it into the warning above.

Other settings in this phase. gc.disable() stops automatic garbage collection; the worker runs gc.collect() every DEEPINFER_GC_INTERVAL_STEP steps instead (deepinfer/worker/base.py:102-106, deepinfer/worker/base.py:153-157). torch.set_num_threads(8) limits the CPU threads of PyTorch (line 178).

Simulated imbalance. Lines 510 and 512 set DEEPINFER_FORCE_IMBALANCE_RATIO to 1.8 for the run and to 0.0 after it. So the profile measures the memory of an unbalanced expert load. A value that you export for this variable has no effect after start-up.

The library defaults. With max_num_seqs=256 and max_model_len=None: max_num_batched_tokens = 4096, so seqlen_q is 16 for each of 256 sequences, and the first seqlen_k is 4112.

Why the mean. The docstring of _init_cache says "the minimum number of blocks across all workers" (deepinfer/engine/llm_engine.py:426-428). The code takes the mean (line 266 above). A rank that measured fewer blocks than the mean gets more blocks than it measured. The 2 × state reserve. The second copy is for copy_state, a buffer of the KV-saving hooks. In this release copy_state stays None (deepinfer/engine/llm_engine.py:284-285), but the memory is still reserved.

Stop 12 in detail: what decides the row sizes

Block row. get_cache_block_size returns the bytes of one block over all layers (deepinfer/worker/cache_engine.py:968-978). Each layer stores one entry per group of compress_ratio tokens. An entry is 288 bytes in FP4 or 528 bytes in FP8 (deepinfer/worker/cache_engine.py:211-213). The page worker/cache_engine.py: CacheEngine and the cache layout computes every offset.

State slots. The state shape is (get_num_state_slots(max_num_seqs), bytes per slot) (deepinfer/worker/cache_engine.py:646-651), and get_num_state_slots is int(max_num_seqs × DEEPINFER_NUM_STATE_SLOTS_RATIO) + 1 (deepinfer/worker/cache_engine.py:201-202). With the defaults (256 sequences, ratio 1.2) that is 308 slots. The sliding-window ring has window + DEEPINFER_MAX_BACKTRACKING_TOKENS rows (deepinfer/worker/cache_engine.py:88-93).

Memory outside PyTorch. Because alloc_tensor bypasses the PyTorch caching allocator, torch.cuda.memory_allocated() does not count the KV cache. Stop 13 in detail: counting the graphs, and when there are none

Count with the defaults. build_graph_batch_sizes(1536, 8) gives 1, 2 and 4 (below the interval), then range(8, 1536, 8) with 191 values, then 1536. That is 3 + 191 + 1 = 195 graphs. The DFlash runner counts sequences, not tokens: build_graph_batch_sizes(256, DEEPINFER_DFLASH_CUDAGRAPH_BATCH_SIZE_INTERVAL = 8) gives 3 + 31 + 1 = 35 (deepinfer/worker/dflash_cuda_graph_runner.py:32-37, deepinfer/environ.py:155-157).

Capture order. The runner captures the largest size first, and all graphs share one memory pool and one set of input buffers (deepinfer/worker/cuda_graph_runner.py:93-140). Each graph runs once as a warm-up before its capture. So capture time grows with the number of sizes: a larger DEEPINFER_CUDAGRAPH_BATCH_SIZE_INTERVAL means fewer graphs, but more padding rows in each decode step.

No graphs. use_cuda_graph is false with DEEPINFER_ENFORCE_EAGER=1 or for a PROMPT engine (deepinfer/worker/model_runner.py:73). Then warm_up_model only resets the seed. The DFlash graphs need the main graphs, nextn > 0, a dflash_cfg and no DEEPINFER_DFLASH_ENFORCE_EAGER (deepinfer/worker/model_runner.py:80-85).

Memory. The capture happens after the KV cache allocation. So the graph memory must fit in the memory that the budget left free. That is the 15 % that gpu_memory_utilization keeps, plus the activation memory of the profile run (a deduction from deepinfer/worker/base.py:228-245). The LLM docstring warns that an out-of-memory in a CUDA graph can show as "illegal memory access" (deepinfer/entrypoints/llm.py:50-51).

What can go wrong#

Set the devices before you import torch or deepinfer

If your script imports torch or deepinfer before it sets CUDA_VISIBLE_DEVICES (or ASCEND_RT_VISIBLE_DEVICES), the setting can have no effect. Follow the order of create_llm (examples/_config.py:104-110).

  • KeyError: 'CUDA_VISIBLE_DEVICES'. The engine and the Worker read this variable without a default (deepinfer/engine/llm_engine.py:188, deepinfer/worker/base.py:127). Set it, also on Ascend.
  • The ranks hang in stop 8. One DP process failed or did not start, or two jobs use the same MASTER_PORT (deepinfer/utils.py:222-230). The others wait up to the timeout of the default group, DEEPINFER_GLOO_TIMEOUT (4 hours by default).
  • ValueError: Unsupported HF ... The checkpoint is not a DeepSeek V4.1 checkpoint in the expected format (deepinfer/hugging_face/config.py:241-262).
  • "No available memory for the cache blocks" or "runtime max seq len ... is larger than ...". The weights and the test batch leave too little memory. Raise gpu_memory_utilization, or lower max_model_len, max_num_seqs or max_num_batched_tokens (deepinfer/engine/llm_engine.py:441-451).
  • Out of memory or "illegal memory access" in stop 13. The graphs did not fit in the memory that is left. Lower gpu_memory_utilization (deepinfer/entrypoints/llm.py:50-51).
  • RuntimeError: unknown GPU type at the very end: the device is not SM100 and not Ascend (deep_cluster/hardware/device.py:151-156).
  • A NUMA warning in the log. libnuma.so.1 is missing or the binding failed. Start-up continues, but host-to-device copies can be slower (deepinfer/worker/base.py:356-357).

Why it matters. Start-up decides the numbers that limit every later step. These are the number of blocks, the batch sizes that have a graph, and the ranks that talk to each other. When a step does something unexpected, read the start-up log first. It shows the block count, the graph sizes and the group layout.
