In one sentence

We follow one prompt from llm.generate() through the tokenizer, the C++ scheduler and the device, until its tokens come back as RequestOutput objects.

The idea#

A large language model makes text one token at a time. DeepInfer serves many requests at the same time. So it does not run one request from start to end. It runs steps. In each engine step, it selects a batch of requests, runs the model once for all of them, and adds new tokens to each request.

This tour follows one real request from examples/offline_inference.py. The request is the second prompt of the example, so its request id is "1":

prompt = ("Question: What is the largest planet in the solar system?\nAnswer: Jupiter\n\n"
          "Question: How many legs does a spider have?\nAnswer: Eight\n\n"
          "Question: Who wrote Romeo and Juliet?\nAnswer:")
params = SamplingParams(temperature=0.4, max_tokens=128, ignore_eos=False,
                        first_n_token_no_eos=1, top_logprobs=4, seq_seed=1)

The prompt and the parameters come from examples/_prompts.py:72-77 and examples/_prompts.py:106-116. The tour has 13 stops. Stops 1 to 4 run once per request. Stops 5 to 12 run in every engine step, for all requests in the batch. Stop 13 runs when the user script collects the results.

An everyday comparison. Think of a restaurant kitchen. A waiter writes each order on a ticket (stop 4). The head chef looks at all tickets and decides which dishes the kitchen cooks in this round (stop 5). The cooks cook all selected dishes together (stops 7 to 11). After each round, the waiter carries finished plates to the tables (stops 12 and 13). The comparison stops being true in one place: a dish is not done after one round. Each round adds only one or a few tokens to each request, and a request needs many rounds.

The picture#

Processes and threads#

The example starts more than one process. The diagram below shows which processes and threads touch the request, and how they talk to each other.

  • Each DP replica is a full engine with its own scheduler. Our request lives in exactly one replica, the one with dp_rank 0 in this tour.
  • The replicas are not independent. They vote on the step type (csrc/engine/scheduler.hpp:295-341) and exchange tokens in the MoE layers (expert parallelism).
  • All work of stops 2 to 13 runs in the main thread of the replica. That thread is the driver.

1The user script starts the engine and calls generate()#

We are in examples/offline_inference.py. The script reads the parallel sizes from the command line. The defaults give 8 data-parallel (DP) ranks: dp_size = ep // cp = 8 // 1 (examples/offline_inference.py:24-28). The last line calls launch_dp(main, dp_size) (examples/offline_inference.py:112-113).

Each child process runs main(dp_size, dp_rank). It sets environment variables, makes the LLM object, builds the prompts and calls generate():

The order of the work in create_llm is important. It sets the visible devices first and imports deepinfer after that:

The module docstring gives the rule. Translated: "This module must not import deepinfer at the top level. The environment setup must finish before import deepinfer, so create_llm imports deepinfer lazily inside the function." (examples/_config.py:1-7).

2The public API: LLM.generate() and _add_request()#

We are in deepinfer/entrypoints/llm.py. LLM is the offline API. It wraps one LLMEngine. generate() does two things: it adds every prompt as a request, then it runs the engine until all requests finish.

  1. Line 135: one _add_request call per prompt, in input order.
  2. Line 151: a deep copy of the SamplingParams. The engine later changes the copy (it sets eos_id), not the user object.
  3. Line 152: the request id is a counter, as a string. The prompts get "0", "1", ... so our request is "1".
  4. Line 156: if the caller gave text, the tokenizer makes the ids (stop 3).
  5. Line 157: the ids become a NumPy int32 array.
  6. Lines 158-159: a model with a vision part needs a multimodal dict, also for text. An empty dict is added if there is none.
  7. Line 142: after all prompts are added, _run_engine runs the loop (stop 13 and The loop).

What the data looks like now (illustrative values):

Stop 2 in detail: defaults that LLM sets

  • LLM.__init__ sets disable_log_stats=True and stop_preempted_request=False as defaults, and TOKENIZERS_PARALLELISM=false (deepinfer/entrypoints/llm.py:67-69). 3Tokenization: text becomes token ids#

A neural network works on numbers, not on letters. The tokenizer cuts the text into tokens and gives each token an integer id. DeepInfer uses the Hugging Face tokenizer files of the checkpoint. LLMEngine.__init__ loads it once with get_hf_tokenizer (deepinfer/engine/llm_engine.py:200-205). _add_request calls tokenizer.encode(prompt) (stop 2, line 156).

After loading, _apply_release_fixups checks the special tokens. With the default "release" policy, the checkpoint must have BOS (begin of sequence) at id 0 and the EOS token at id 1. If not, loading stops with ValueError. It also turns on add_bos_token, so encode() puts id 0 first:

Stop 3 in detail: tokenizer class, vision models and Engram

Which tokenizer class. get_hf_tokenizer needs tokenizer.json and tokenizer_config.json in the model folder, else it raises FileNotFoundError. If the tokenizer config has an auto_map, it loads the class from the checkpoint. Else, with tokenizer_compatibility: "native" in config.json, it uses AutoTokenizer, and else LlamaTokenizerFast. The fix-ups above run for every class when the policy is "release", the default (deepinfer/hugging_face/tokenizer.py:89-121).

Multimodal tokens. The 21 placeholder tokens must get the ids 129280 to 129300 (deepinfer/hugging_face/tokenizer.py:48-56). The comment says that inference computes the image token ids as vocab_size + ImageTokenOffset (deepinfer/hugging_face/tokenizer.py:25-28). The engine reads vocab_size from the model config.json (deepinfer/config.py:121-122), which is not in the repository. The two rules agree only if vocab_size is 129280, so this tour uses 129280 (text ids 0 to 129279). This is an inference from the code, not a value that the code sets. You will see 129279 (vocab_size - 1) again in stop 11.

A vision model changes the ids again. The only model class in this release, DeepseekVLForCausalLM, has a vision part. So a NORMAL engine always has a MultimodalProcessor (deepinfer/engine/llm_engine.py:209-221, deepinfer/model_executor/models/__init__.py:15-17). In stop 4, overwrite_prompt replaces each image placeholder with vocab_size + IMAGE and many vocab_size + IMAGE_PAD ids. Our prompt has no image, so the ids stay the same. The function always returns a new array (deepinfer/ve/multimodal_processor.py:105-162).

Engram models. A model with Engram n-gram memory also needs compressed ids. add_request maps each id through a lookup table with CompressedTokenizer.encode (deepinfer/engine/llm_engine.py:564-567). Ids outside the table, for example image ids, become IMAGE_SENTINEL = -1 (deepinfer/model_executor/models/v4_modules/engram.py:62-66). The sequence keeps both lists. Without Engram, the compressed list is the same as the normal list.

The way back. The same tokenizer object turns ids into text at the end (stop 13). get_tokenizer() returns it (deepinfer/entrypoints/llm.py:87-88).

4Admission: LLMEngine.add_request() makes a C++ Sequence#

We are in deepinfer/engine/llm_engine.py. add_request checks the request, makes the engine object for it, and puts it in the queue of the scheduler. The engine object is a sequence. It is a C++ object (deepinfer._C.engine.Sequence), so the scheduler can read it without Python.

  1. Lines 553-554: an empty prompt raises ValueError.
  2. Lines 581-589: every id must be in [0, vocab_size). A multimodal request may also use the 5 image ids above vocab_size. A bad request is dropped: the function writes a log line and returns None. It does not raise.
  3. Lines 594-598: the C++ Sequence copies the ids into a std::vector<int> and reads the sampling values once.
  4. Lines 607-613: a request with structured output (so_args) needs a grammar matcher first. The engine gives this work to a thread pool and enqueues the request later (line 628).
  5. Lines 620-626: _enqueue calls scheduler.add_sequence. For a vision model, it also sends the multimodal dict to the multimodal worker process.

Stop 4 in detail: the Sequence object, schedulable, and the helpers

Where the fields come from. The Python call passes flat arguments. make_sequence_init in the binding fills a SequenceInit (csrc/engine/pybind_sequence.cpp:25-38). The constructor reads the sampling values from the Python object once, into SamplingScalars and StoppingCriteria (csrc/engine/sequence.hpp:276-283). add_request sets sampling_params.eos_id = self.eos_id, the tokenizer EOS id (deepinfer/engine/llm_engine.py:527).

The schedulable flag. The binding sets schedulable = multi_modal_data.is_none() (csrc/engine/pybind_sequence.cpp:35). Our request has a multimodal dict, so it starts as not schedulable. The multimodal worker process prepares the request and sends it back through a queue. fetch() then calls scheduler.set_schedulable(id) (deepinfer/ve/multimodal_processor.py:281-305). A text-only model has no multimodal processor, so its sequences are schedulable at once.

Status values. A sequence is WAITING, RUNNING, SWAPPED, or one of seven FINISHED_* values (csrc/engine/sequence.hpp:30-43). Each finished value has a reason string: "stop", "length", "abort", "prompt_length_exceeded", "insufficient_system_resource", "xgrammar runtime errors or timeout", "ve_error" (csrc/engine/sequence.hpp:45-64).

Reserved memory. add_sequence reserves space in the token vector for max_tokens more ids, and in the block table for all blocks the request can need (csrc/engine/scheduler.hpp:135-142, csrc/engine/scheduler.hpp:190-192). For our request: (41 + 128 + 127) // 128 + 1 = 3 block entries.

Structured output. The SO builder is made on first use. It is a ThreadPoolExecutor with one worker per idle CPU (deepinfer/engine/llm_engine.py:329-342). get_idle_cpus returns DEEPINFER_SO_BUILDER_CPUS CPUs (default 4) (deepinfer/utils.py:154-161). submit() starts the build. pump() runs in every step and enqueues the requests whose matcher is ready (deepinfer/structure_output/so_matcher_builder.py:97-121, deepinfer/engine/llm_engine.py:841-842). Our request has no so_args, so this path is not used.

Other admission rules. If DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE is not "off", prompt_logprobs is forced to False with a warning (deepinfer/engine/llm_engine.py:529-537). If the multimodal data has image_bytes=None, the sequence starts as FINISHED_VE_FAILED (deepinfer/engine/llm_engine.py:547-550, deepinfer/engine/llm_engine.py:603-604).

5Scheduling in C++: which requests run in this step#

From here, the code runs in every engine step. LLMEngine.step() first asks the C++ scheduler for the batch (deepinfer/engine/llm_engine.py:881-887). The scheduler has three queues: waiting, prompted and running (csrc/engine/scheduler.hpp:1124-1126). It makes one decision first: is this step a prefill step or a decode step? DeepInfer never mixes the two in one batch.

So a prefill can start only at an attempt point. decode_step counts decode steps since the last prefill step. With the defaults, every 70th decode step is an ALL point and every 100th is an ANY point (deepinfer/environ.py:174-178). The first step has decode_step = 0, which is an ALL point. A rank wants a prefill if its KV cache is at most 90 % full and the first waiting request is schedulable (line 313).

Prefill for our request. _schedule_prefill takes requests from the front of waiting. For each one, it checks the limits, gives it KV blocks, and decides the chunk size:

Our prompt has 41 tokens and the budget is 32768, so it is not chunked. Line 519 gives the blocks. Line 524 sets RUNNING. With chunked prefill, a long prompt runs in several prefill steps, and only the last chunk sets RUNNING (lines 522-526).

What the data looks like now (illustrative values; requests "0" to "3" are ready and go into one prefill step):

Deep dive

Stop 5 in detail: limits, blocks, decode steps and preemption

The prefill limits, in order (csrc/engine/scheduler.hpp:360-546):

  1. A request that is already aborted or failed goes to ignored_seqs. It gets an output with its finish reason.
  2. A request that is not schedulable stops the loop (break). The requests behind it also wait.
  3. A prompt longer than prompt_limit becomes FINISHED_IGNORED. prompt_limit is max_model_len with chunked prefill, else min(max_model_len, max_num_batched_tokens) (csrc/engine/scheduler.hpp:112).
  4. The BlockManager answers OK, LATER or NEVER. NEVER means that the request needs num_blocks or more blocks, so it can never fit, because block 0 is not used (csrc/engine/block_manager.hpp:128-136). LATER stops the loop.
  5. At most max_num_seqs sequences run at the same time (lines 440-442).
  6. The sum of the full lengths in one prefill step must not be more than DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K (lines 444-449). The full length is get_len(): the prompt plus the output tokens. A request that runs its prefill again after a preemption has output tokens too (csrc/engine/sequence.hpp:81). If the variable is not set, the engine uses the limit 2**30, which is in practice no limit (deepinfer/environ.py:9, deepinfer/engine/llm_engine.py:317).
  7. The chunk may not cut an image in the middle. _adjust_chunk_size moves the cut (csrc/engine/scheduler.hpp:235-260).
  8. In a NORMAL engine, a chunked request is the last one in the step (lines 543-545).

How many blocks. get_num_blocks() is ceil((len + inflight + drafts) / block_size) (csrc/engine/sequence.hpp:291-293). The block size is 128 tokens (deepinfer/model_executor/model_metadata_utils.py:133-135). The free list starts at block 1, because block 0 means "empty" (csrc/engine/block_manager.hpp:27-35). The state manager uses the same class for the per-sequence state slots. allocate_seq takes the blocks and one state slot (csrc/engine/block_manager.hpp:207-214).

Decode steps. _schedule_decode runs when the step is not a prefill step (csrc/engine/scheduler.hpp:559-660):

  1. It removes finished sequences from running and returns them as finished_seqs.
  2. It sorts running by output length, longest first (lines 624-625).
  3. It takes sequences from the end of the list, so the shortest output comes first. Before each one, the loop checks that at least one block is free. Then _append_slot adds a block only if the sequence needs one (csrc/engine/scheduler.hpp:628-640, csrc/engine/scheduler.hpp:817-828).
  4. If no block is free, it preempts from the front of the list: the sequence with the longest output (lines 630-634).
  5. It sorts the batch by total length and asks MTPVarlen for each seqlen_q (lines 648-652). Without a performance curve, seqlen_q = 1 + number of drafts, so 6 (csrc/engine/mtp_varlen.hpp:150-158).

Code and comment do not agree

The comment above _schedule_decode says that the scheduler preempts the sequence with the shortest output (csrc/engine/scheduler.hpp:556-557). The code sorts by output length, longest first, and preempts running[l] from the front (lines 624-634). So the code preempts the longest output. The comment on FINISHED_PREEMPTED is closer to the code. Translated: "the task that uses the most KV cache is stopped" (csrc/engine/sequence.hpp:55-56). But the code sorts by output length only, not by total length with the prompt.

Preemption. _preempt stops the request with FINISHED_PREEMPTED if stop_preempted_request is true, or if the structured-output status of the request is not 0 (line 770). Status 0 means that structured output has not started; a request without structured output also has status 0 (csrc/engine/sequence.hpp:231). Else it resets the sequence, frees its blocks and puts it at the front of waiting. The request then runs its prefill again (csrc/engine/scheduler.hpp:766-790). The offline LLM uses the second policy (stop 2).

The vote and the DP group. _dp_allreduce runs an all-reduce on the DP group, also with one DP rank (csrc/engine/scheduler.hpp:169-182). With ZOS on, the group is the CPU (Gloo) DP group (deepinfer/engine/llm_engine.py:313).

A consequence for vision models. Read together, the lines above give the following sequence for one DP rank and the default intervals. This site derived it from the code and did not run it.

  1. Every request starts with schedulable=False, because the engine has a MultimodalProcessor and the request has a multimodal dict (stop 4). Only fetch() sets schedulable (deepinfer/ve/multimodal_processor.py:281-303).
  2. In each step(), schedule() runs first and fetch() runs later (deepinfer/engine/llm_engine.py:885, deepinfer/engine/llm_engine.py:939-941). So in step 1, the first waiting request is not schedulable, and no rank wants a prefill.
  3. Step 1 has decode_step = 0, an ALL point. The vote fails, so step 1 is an empty decode step. schedule() then sets decode_step to 1 (csrc/engine/scheduler.hpp:676-681).
  4. Steps 2 to 70 have decode_step 1 to 69. These are not attempt points, so they are empty decode steps too. Each one runs a placeholder forward pass (deepinfer/worker/worker.py:125-127).
  5. Step 71 has decode_step = 70, the next ALL point. If the multimodal worker answered for the first waiting request before the fetch() of step 70, the prefill runs in step 71.

So step 71 is the earliest prefill step. The code does not show how fast the worker process answers. If it is late, the next attempt points are decode_step 100 (ANY point, step 101) and 140 (ALL point, step 141). With one DP rank, ANY and ALL give the same result. With more DP ranks, the ALL point at 70 needs every rank to be ready. In this release the only model class has a vision part, so every request of a NORMAL engine goes through this wait. A model class without multi_modal_mapper would get no MultimodalProcessor and could prefill in step 1 (deepinfer/engine/llm_engine.py:210).

The output of this part. SchedulerOutputs holds scheduled_seqs, prompt_run, num_batched_tokens, finished_seqs, ignored_seqs, seqlens_q and statistics (csrc/engine/scheduler.hpp:45-77). schedule() checks that num_batched_tokens <= max_num_batched_tokens (csrc/engine/scheduler.hpp:671-673).

7The worker step: forward N, post-process N-1, sample N#

After the schedule, step() calls the worker through _run_workers("execute_model_step", ...) (deepinfer/engine/llm_engine.py:961-975). The driver worker runs in the same process. The function has a fixed order:

  1. Line 122: start the forward pass of step N on the device (stop 8). The call returns at once; the device works in the background.
  2. Line 144: post-process step N-1 (stop 12) while the device runs step N.
  3. Line 154: start the sampler of step N (stops 10 and 11).

Stop 7 in detail: why the CPU is one step behind, and how the device catches up

The problem. With ZOS, step N+1 is scheduled before step N is post-processed. So the CPU does not yet know how many drafts of step N the sampler accepted. The scheduler assumes the most: it adds nextn + 1 to total_inflight_tokens for each scheduled sequence (csrc/engine/scheduler.hpp:689, csrc/engine/scheduler.hpp:726). seqlen_k includes that number (csrc/engine/scheduler.hpp:697).

The fix on the device. _correct_seqlens_qk matches the sequences of step N+1 with those of step N by seq_id (prepare_zos_inputs, csrc/engine/zos.cpp:142-196). Then a kernel corrects seqlens_k on the device: seqlens_k[i] += seqlens_q[i] - (nextn - accepted[j]) (deepinfer/model_executor/layers/tilelang_ops/compute_seqlens_k_zos.py:10-31). The real input ids come from the sampled tokens of step N, which are still on the device (MetadataZOS, deepinfer/worker/zos_status.py:23-40). With the default settings, this correction needs no CPU-device sync. With DSpark (DEEPINFER_ENABLE_MTP_VARLEN=1), the worker copies the corrected seqlens_q back and waits for that copy before it samples (deepinfer/worker/worker.py:146-152, deepinfer/worker/worker.py:229-234).

No sync rule. execute_main_model and execute_sample run inside forbid_cuda_sync(). Their docstrings say: "This function must NOT contain any cuda synchronize" (deepinfer/worker/model_runner.py:315-324). The main wait of a step is sample_end_evt.synchronize() in _post_process_step, one step later (deepinfer/worker/worker.py:262-263).

Placeholder steps. If the batch is empty, the worker still runs a forward pass on one dummy sequence (_placeholder_seq_metadata, deepinfer/worker/model_runner.py:386-403).

CP workers. run_workers sends the method name to the CP worker processes before it calls the method on the driver (deepinfer/worker/base.py:290-302). The CP workers run the same method in start_slave_worker_loop (deepinfer/worker/base.py:129-133). They get only is_prompt and is_placeholder; the sequence list stays on the driver.

Settings. DEEPINFER_ZERO_OVERHEAD_SCHEDULING=0 turns ZOS off; then each step post-processes itself (deepinfer/environ.py:179). DEEPINFER_GC_INTERVAL_STEP (default 1000) sets how often the worker runs Python garbage collection (deepinfer/environ.py:185, deepinfer/worker/base.py:153-157).

9The KV cache: what this step writes#

Attention needs the keys and values of all earlier tokens. The KV cache keeps them, so the model does not compute them again in each step. In DeepInfer, the cache for one request has two parts:

  • Paged blocks for the compressed KV entries: one entry for every 1 or 2 tokens (KV compression). The block table of the sequence lists its blocks (stop 5).
  • A state slot for the sliding-window KV: a ring with room for the last 134 tokens per layer. The docs say: "The SWA KV cache does not go into paged KV blocks; it lives in the state cache" (doc/inference_deployment_qa.md:163).

The forward pass does the writes. The kernels of each attention layer use the slot maps from stop 6. No Python code runs per token. The block and state ids come from the scheduler; the device only follows them.

Stop 9 in detail: sizes, slots and what a decode step writes

Sizes. A compressed entry uses 528 bytes in MXFP8 or 288 bytes in FP4: data plus scale factors (deepinfer/worker/cache_engine.py:211-213). A sliding-window entry uses 528 bytes (deepinfer/worker/cache_engine.py:216-218). The docs give the stored part of one state slot as "20 layers × 134 tokens × 528 B = 1,415,040 B per sequence" (doc/inference_deployment_qa.md:169).

How many slots and blocks. The number of state slots is int(max_num_seqs * DEEPINFER_NUM_STATE_SLOTS_RATIO) + 1: int(4 * 1.2) + 1 = 5 here (deepinfer/worker/cache_engine.py:201-202, deepinfer/environ.py:162). Slot 0 is never given out (stop 5). The memory profile at start-up sets the number of blocks. It takes total memory * gpu_memory_utilization and subtracts the peak use of a test run and two times the state cache. It divides the rest by the size of one block (deepinfer/worker/base.py:228-245). Then all ranks use the same value: the mean over all ranks, rounded down to an even number (deepinfer/worker/base.py:264-266).

A decode step. The 6 query tokens of one request write 6 ring rows. A compressed entry is written only where (position + 1) % ratio == 0; other rows get slot -1 (csrc/engine/input_metadata/prepare_tensor_input_v4.cpp:70-95). The step writes entries for draft tokens too. If the sampler rejects a draft, its entries are wrong. They do no harm: cache.num_tokens counts only accepted tokens (stop 12), and the next step writes over the same rows. The DFlash docstring uses the same argument for its own cache (deepinfer/model_executor/models/mtp/dflash.py:204-209).

A new block. When the sequence grows past the end of its last block, _append_slot adds one block in the next decode schedule (csrc/engine/scheduler.hpp:817-828).

The end. When the request finishes, finalize_seq calls scheduler.free_seq, which frees the blocks and the state slot (deepinfer/engine/llm_engine.py:804-806, csrc/engine/scheduler.hpp:738-750). The pages The KV cache and Paged KV cache and block manager explain the cache in full.

  3. Line 952. After a full prefill, the sequence goes into running.
  4. Lines 955-967. The accepted drafts are read from the flat accepted_token_ids array, until the first -1.
  5. Lines 969-971. The list to append is: accepted drafts, then the sampled token.
  6. Lines 982-990. Each token goes into both id lists. _check_stop runs after each one, so a stop inside the accepted drafts drops the rest.
  7. Line 999. In decode, commit_processed_tokens(token_cnt) sets num_tokens to the old value plus the number of appended tokens. Rejected drafts do not count.

One output per token. build_request_outputs makes one object for each accepted draft and one for the sampled token. The last one gets draft_tok = drafts + 1 and accept_tok = accepted + 1 (csrc/engine/outputs.hpp:199-294). Ignored sequences get one output with their finish reason (csrc/engine/outputs.hpp:297-304). The engine collects the pointers and releases them in the next pre_sampler_sync (deepinfer/engine/llm_engine.py:92-107, deepinfer/engine/llm_engine.py:830-831). Deep dive

Stop 13 in detail: has_unfinished_requests and the end of the loop

has_unfinished_requests() asks the scheduler for the number of sequences in waiting, running and prompted, plus requests that wait for an SO matcher (deepinfer/engine/llm_engine.py:665-679, csrc/engine/scheduler.hpp:165-167). With more than one DP rank, it takes the maximum over the DP group. So a rank with no work runs placeholder steps until all ranks finish. This keeps the collective operations of all ranks in the same order.

A finished sequence still counts while it is in running. So the loop runs one more step after the last token: that step frees the blocks (stop 12). The ZOS step that was in flight at that time had our request in its batch. Its result is dropped: process_outputs skips finished sequences (csrc/engine/scheduler.hpp:905-915).

In the example, print_output also computes the acceptance rate from draft_tok and accept_tok, and a perplexity from token_logprobs (examples/offline_inference.py:79-86). llm.close() stops the workers (examples/offline_inference.py:109).

The loop: many steps for one request#

Stops 5 to 12 repeat for every engine step. One request sees one prefill step (or more with chunked prefill) and then many decode steps. Each decode step adds 1 to 6 tokens. The diagram shows the steps of request "1" alone. It counts the steps from the first prefill step and leaves out the empty steps before it (stop 5, deep dive).

  • Panel 1. The prefill step returns the first token in the same step. Each decode step returns the tokens of the step before it (stop 7). For 128 output tokens with about 3 tokens per step, the request needs about 40 decode steps.
  • Panel 2. This overlap is the reason for ZOS. The CPU work of the scheduler and of the output assembly hides behind the forward pass on the device.
  • Panel 3. The accepted drafts and the new sample are appended. The KV cache counts only them (stop 12).

Simplified

The diagram shows one request. In the example, four requests share each step. The fifth request does not start at the moment when one of them finishes. It starts at the next prefill attempt point after a slot becomes free (stop 5). In this release, empty steps come before the first prefill, because the model class has a vision part (stop 5, deep dive). With DSpark, a decode step can have fewer than 6 query tokens.

What can go wrong#

Clone each RequestOutput before the next step()

If you call LLMEngine.step() yourself, the returned pointers are valid only until the next step. Copy them with RequestOutput.clone() first (deepinfer/engine/llm_engine.py:866-870). LLM.generate() does this for you.

  • A request disappears. A token id outside [0, vocab_size) makes add_request drop the request with an info log line, not an error (deepinfer/engine/llm_engine.py:581-589). generate() then returns fewer results than prompts. The example checks this with an assert (examples/offline_inference.py:102).
  • An empty prompt. ValueError("prompt must not be empty") (deepinfer/engine/llm_engine.py:553-554).
  • A prompt that is too long. The request finishes at once with "prompt_length_exceeded" and no tokens (csrc/engine/scheduler.hpp:377-385).
  • The KV cache is full. The scheduler preempts the running request with the longest output. In the offline API, the request runs its prefill again later. A structured-output request with a status that is not 0 stops instead (csrc/engine/scheduler.hpp:766-790).
  • The pool is exhausted. Code that never releases outputs gets RequestOutputPool exhausted (max_size=10000) (csrc/engine/outputs.hpp:65).
  • A hung multimodal worker. If the worker makes no progress for DEEPINFER_MULTI_MODAL_WORKER_TIMEOUT seconds, the engine calls os.abort() (deepinfer/ve/multimodal_processor.py:264-275).
  • Devices set too late. Set CUDA_VISIBLE_DEVICES before you import deepinfer or torch (examples/_config.py:1-7). See Hardware platforms: NVIDIA and Ascend.

Why it matters. The tour shows the full path of the data in one picture. Most questions about DeepInfer behaviour start with "which stop is it?". A slow first token can be a schedule question (stop 5). A wrong token can be a sampler question (stop 10). Lost output can be an output-pool question (stops 12 and 13).

    With ZOS on, step N is a decode step. Which tokens does step() return? And why does a request that finished in step N's post-process still appear in the batch of step N+1?
    hard
    Show answer

    It returns the tokens of step N-1: the worker post-processes the previous step after it starts forward N, and keeps step N for later (deepinfer/worker/worker.py:143-144, deepinfer/worker/worker.py:182-187). Step N+1 is scheduled before the post-process of step N runs, so the scheduler does not know yet that the request is finished. process_outputs later skips the finished sequence, and the result of that extra step is dropped (csrc/engine/scheduler.hpp:905-915).

Related pages

  • Offline API and the step loopLLM.generate() adds all requests, then calls LLMEngine.step() until no request is left. Each step schedules one batch, runs the model once, and returns handles to the new outputs. With ZOS, a decode step returns the tokens of the step before it.
  • Request and sequence lifecycleEach request becomes a C++ Sequence. It waits until it is schedulable, runs one or more prefill steps and many decode steps, and ends with one of seven finish reasons. Preemption stops it or sends it back to the queue for a recompute.
  • The schedulerIn every engine step, the C++ scheduler runs either a prefill batch or a decode batch. It starts prefills only at attempt points, cuts long prompts into chunks, gives KV blocks, and preempts sequences when the blocks run out.
  • Paged KV cache and block managerThe engine side of the paged KV cache. Two C++ BlockManager objects hand out KV blocks and state slots, the scheduler decides when, and C++ code turns block tables into index tensors for the kernels.
  • Input metadata (varlen batching)Before each forward pass, DeepInfer packs the tokens of all scheduled sequences into one flat list and computes index tensors that tell each kernel where every token is, where to write its cache entry and which keys to read.
  • Zero-overhead scheduling (ZOS)With ZOS, the CPU schedules and prepares step N+1 while the device runs step N. The device corrects the lengths and inputs that the CPU cannot know yet, and step() returns the tokens one step late.
  • The samplerThe sampler turns the hidden states of the rows that need a token into float32 logits, applies temperature, top-p and top-k, and draws one token per request with a seeded hash. In decode steps it also verifies the draft tokens.
  • Speculative decodingA small draft model guesses the next 5 tokens. In the next decode step, the main model checks all 5 at the same time, keeps a prefix with rejection sampling, and samples one more token. The output distribution stays within a very small, proven bound of the target distribution (a 5e-5 penalty).
